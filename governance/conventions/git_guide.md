# Git 协作、提交与发布规范

本规范继承 `linux-note` 提交 `5fd52c4a37e484079b694daeb8af848898281fb1` 中的
`governance/conventions/git_guide.md`、提交模板和 `commit-msg` 钩子规则。
下文保留来源 1.1—1.9 的可迁移约定，将知识库和 Loop 的目录、构建命令替换为本项目实际入口。
来源、许可证与适配范围见 [框架继承记录](../architecture/framework_provenance.md)。

## 1.1 目标

Git 历史必须直接表达“哪个项目的哪个模块产生了什么可验证结果”。
本仓库的 HC32 移植、工程工具、Zephyr 学习正文和实验使用同一提交语法，按照真实修改对象表达归属。
不得使用 `add`、`update`、`rewrite`、`structure`、`meta` 等不能稳定表达变更性质的旧类型。

一次提交必须能够独立审查和回退。实现必需的测试、配置、帮助与使用说明随实现一起提交；
独立治理政策、纯知识内容重写或发布动作单独提交。

继承规则不是只继承一个标题正则。提交类型、范围选择、结果描述、正文、提交粒度、验证和历史保护
共同构成提交规范；钩子通过不能证明一项混合提交已符合这些要求。

## 1.2 分支与工作区

`master` 是可发布主线，只接受通过验证的提交。任务使用短生命周期分支，例如：

```text
feat/soc-hc32f4a0
fix/board-clock
refactor/build-tools
content/zephyr-scheduling
docs/repository-git
```

并行任务优先使用独立 worktree，避免多个进程共享索引和工作区：

```sh
git worktree add ../work-hc32-clock -b fix/board-clock
```

任务完成后基于远端主线整理：

```sh
git fetch origin
git rebase origin/master
git switch master
git merge --ff-only <任务分支>
```

上述变基只用于尚未交付的任务分支。已经确认或推送的提交不得借整理分支改写。
新建且远端为空的仓库先建立初始提交，之后才存在 `origin/master` 可供变基。
主线只允许快进更新；推送使用普通 `git push`，被拒绝时保留本地结果并先核对远端变化。

未推送的临时修正可以使用 `git commit --fixup` 和 `git rebase --autosquash`。
已交付历史的撤销与明确授权的历史迁移按 1.7 执行。

## 1.3 提交标题

统一格式：

```text
<类型>[(<project>/<module>)]!?: <中文结果>
[可选：标题无法完整表达时才添加]
- 描述1
- 描述2
```

`(<project>/<module>)` 整体可选，不设项目、模块或语言白名单。
需要定位归属时，按照本次修改的真实对象自由填写；变更横跨整个仓库且不存在准确范围时可以省略。
范围允许只写项目，也允许写“项目/模块”两层，中文和英文都合法，
只禁止会破坏提交语法的空白、括号、冒号和额外斜杠。
维护者习惯使用与目录一致的英文标识，这不是钩子的语言限制。`!` 表示破坏性变更。

允许的类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增用户或开发者可观察的能力 |
| `fix` | 修复错误行为 |
| `refactor` | 调整实现或架构，不以新增功能为主 |
| `perf` | 改善性能或资源占用 |
| `security` | 修改权限、校验、供应链或安全边界 |
| `content` | 新增或重写知识正文、题库和研究内容 |
| `docs` | 修改使用说明、设计文档和治理规范 |
| `test` | 新增或调整测试与验证工具 |
| `build` | 修改依赖、构建、安装和打包 |
| `ci` | 修改自动检查与发布流水线 |
| `release` | 发布版本和同步版本清单 |
| `revert` | 撤销已经确认的历史提交 |
| `chore` | 不改变产品、知识或构建语义的维护 |

Markdown 是文件格式，不能据此统一选择 `docs`。例如，讲解线程调度机制的知识正文属于 `content`；
说明怎样运行构建命令的使用指南、安排专题先后顺序的学习路线、协作治理规则属于 `docs`。
驱动实现所必需的使用说明随驱动提交，不为了文件扩展名另拆一个 `docs` 提交。

范围示例仅展示命名方式，不构成固定列表：

```text
board/uyup
soc/clock
drivers/serial
build/environment
knowledge/zephyr
repository/git
```

标题示例：

```text
feat(board/uyup): 增加核心板启动配置
fix(soc/clock): 修正12MHz晶振的时钟配置
refactor(build/environment)!: 统一环境初始化入口
content(knowledge/zephyr): 解释线程休眠与调度切换过程
docs(repository/git): 恢复继承的提交与历史保护规则
docs: 更新仓库级使用说明
```

禁止使用“更新信息”“修复一些问题”“同步修改”等无法定位结果的描述。
标题必须表达本次实际完成的结果，不能将专题规划写成专题全部完成，或将离线检查写成实板验证。

## 1.4 提交正文

标题能够完整表达单一结果时，不得为了格式强制增加正文。
只有存在多个结果、验证结论、风险或破坏性影响，无法在标题中清楚表达时才增加正文。
正文中的每个非空、非注释行必须使用 `- ` 列表，不允许混入分段标题或散文。
这里的多个结果应共同服务于 1.5 所述的同一个可审查变更，不是合并无关任务的理由。

需要正文时，例如：

```text
fix(soc/clock): 修正12MHz晶振的时钟配置
- 按实装晶振校对系统与总线分频
- 核对构建产物中的时钟配置；尚未连接开发板验证
```

示例中的验证结论只展示格式，实际提交必须改成确实执行过的验证及其结果。
正文不得使用“描述1”之类占位内容，不得重复标题，也不得把一句话机械拆成标题和正文两部分。

来源钩子没有尾注例外。新提交不能添加独立的 `Assisted-by:`、`Signed-off-by:`、
`Co-authored-by:` 等不以 `- ` 开头的正文行，也不要求代理添加身份尾注。
不得为了让原本不合规范的提交通过，自行增加尾注白名单或绕过钩子。
本规则只约束当前新提交，不构成删除源码版权信息或改写已发布提交元数据的理由。
将来向 Zephyr 上游投稿时，按上游要求另行准备提交格式。

## 1.5 提交粒度

一个提交只形成一个结果：

- 功能实现连同必要配置、测试与使用说明。
- 一个可独立说明的知识模块新增或重写。
- 一个完整且可验证的架构重构。
- 一项安全边界调整。
- 一次版本发布。

不得按文件类型机械拆分“代码提交”“文档提交”“信息更新提交”，
也不得把多个无关模块塞进一个笼统提交。
例如，学习知识正文、整套专题规划和私人环境入口治理可以分别审查与回退，
不能仅因为它们都是 Markdown 就合并为一个没有明确归属的 `docs` 提交。
随正文更新的目录链接可以随正文提交；是否拆分依据可独立验证的结果，而不是文件数量。

长任务中的临时修复使用 `fixup!` 提交，合入主线前 autosquash；
主线不保留“补一下”“再修一次”式噪声历史。

## 1.6 提交前验证

在本项目根目录初始化并检查本地 Git 配置：

```sh
python scripts/git_setup.py
python scripts/git_setup.py --check
```

该脚本使用 Python 3.10 或更新版本，只修改自身所在独立仓库的本地配置：

| 配置 | 值 | 用途 |
| --- | --- | --- |
| `core.hooksPath` | `.githooks` | 启用来源提交钩子 |
| `commit.template` | `governance/templates/git_commit_message.txt` | 使用来源提交模板 |
| `core.autocrlf` | `false` | 由 `.gitattributes` 决定行尾 |
| `core.longpaths` | `true` | 支持 Windows 长路径 |
| `pull.ff` | `only` | 拉取不创建意外合并提交 |
| `fetch.prune` | `true` | 清理已删除远端分支的跟踪引用 |

脚本拒绝将父级或官方参考仓库识别为本项目，不修改全局配置、远程连接、用户名或邮箱。
重复运行得到相同配置；`--check` 只读检查。
Git for Windows 自带提交钩子所需的 `sh`、`sed` 和 `grep`；Linux 使用相同 Shell 钩子。

钩子负责标题语法和正文列表格式检查；来源实现以非 ASCII 字符检测辅助判断中文，
并不具备严格的汉字识别能力。维护者仍须按本规范检查中文结果、类型、范围和提交粒度，
不能把非中文字符被钩子接受当成满足“中文结果”的证据。

项目检查先按根目录 README 激活已准备好的开发环境，再运行：

```sh
python scripts/project.py check
git diff --check
git status --short
git diff --stat
git diff
```

`project.py check` 执行工具测试、调试配置离线检查和项目差异检查。
修改模块、驱动、板级支持或示例后，还需运行受影响的构建和测试；当前入口为：

```sh
python scripts/project.py build
python scripts/project.py test
```

当前默认 `build` 构建 HC32 固件，默认 `test` 在 QEMU 的 MPS2 平台运行测试。
主机工具检查、编译成功和 QEMU 运行成功都不代表 HC32 实板已启动。
修改学习文档需检查正文涉及的源码位置、链接、实验入口与实际结果；
每次交付在 `project-docs/porting-status.md` 中记录本次范围、验证与未执行的硬件步骤。

提交前必须检查暂存区，而不是只看工作区：

```sh
git add <明确文件>
git diff --cached --check
git diff --cached
```

来源要求明确选择文件并检查暂存区。本项目另加执行限制：禁止使用 `git add .`、`git add -A` 或 `git commit -a`；
该限制比来源的明文要求更严格，不属于来源钩子的校验行为。
带 shebang 且设计为直接执行的 Shell 脚本必须以 Git 模式 `100755` 提交；
只供 `source` 的脚本库使用 `100644`。
Windows 首次暂存直接执行的提交钩子后，可用
`git update-index --chmod=+x .githooks/commit-msg` 设置模式；Python 工具通过解释器调用。

## 1.7 撤销与历史修改

- 工作区修改错误：直接编辑修正。
- 未推送且未交付的最后一次提交：允许 `git commit --amend`。
- 未推送、未交付任务分支中的临时提交：使用 `fixup` 和 `autosquash`。
- 已推送或已交付提交：确需撤销内容时使用 `revert(<范围>): <中文结果>`。
- 主分支禁止 `git reset`、强制移动分支和普通强推。
- 只有经过开发者明确授权的仓库级历史迁移才能使用 `--force-with-lease`；
  执行前必须创建并验证完整 bundle 备份。

发现已发布提交的标题、分类或粒度不符合规范时，应修复当前规则与执行流程并记录问题。
不得擅自改写已发布历史，也不得只为换一个提交标题而先撤销再原样重提内容，制造没有行为变化的历史。
用户要求“遵守 Git 规则”或普通“提交、推送”，不等于明确授权仓库级历史迁移。
确需历史迁移时，迁移范围、目标引用和完整备份必须具体可核对，再执行获授权的步骤。

## 1.8 项目版本与上游版本

来源规范为独立的 Loop 产品与知识库快照分别维护版本，示例标签为 `loop-v0.2.0`
和 `linux-note-v2026.07`。这些标签和 Loop 的 `package.json`、发布清单、Schema 检查
只属于来源项目，不能直接照搬到 HC32 工程。

本仓库包含完整 Zephyr 源码，当前 `VERSION` 和 `dependencies.lock.json` 记录上游版本与依赖基线；
它们不自动等于 HC32 移植项目已经发布了相同版本。
目前不在此虚构 HC32 发布版本号或标签。
需要正式发布时，先确定本项目的版本对象、标签规则和实际发布文件，
再把版本清单、变更记录、相关说明及构建验证作为一个完整发布结果维护。

## 1.9 不提交的内容

- 临时测试输出、编辑器缓存和构建产物。
- `.local/`、`.cache/`、虚拟环境、构建目录、固件输出和日志。
- 本机绝对路径、个人凭据和访问令牌。
- 未确认来源或授权的大体积资料。
- 没有入口说明、环境说明和验证结论的零散实验。
- 可由构建过程重新生成的中间文件。
- 外部依赖仓库的 `.git`、用户身份、远端配置和工作区状态。

本机配置与资料索引由 `AGENTS.md` 指向被忽略的私人环境文档。
版本控制中保留可移植的公共入口和来源说明，不纳入私人文档与缓存本体。
上游源码按本项目已确认的完整源码策略纳入版本控制并保留许可证，
不能因排除临时资料而遗漏实际构建必需的依赖源码。
