# 第1章\_UCRT64\_环境与目录约定

本目录保留源码下载、Git、清单、SDK 和主机工具的完整讲解，操作统一使用 **Windows x64 + MSYS2 UCRT64 Bash + Windows Python 3.12.10**。UCRT64 提供 Bash 和常见 Unix 命令，主机仍然是 Windows；下载 SDK、Python wheel 时仍选 Windows 包。Linux 主机和 Linux 内核的对照内容保留用于理解差异。

## 1.1\_先确认终端与工具

从开始菜单打开 MSYS2 UCRT64。安装终端和国内换源的完整步骤见[准备 UCRT64 环境与下载 Zephyr](../P01_zephyr_make_project/P001_准备UCRT64环境与下载Zephyr_Windows.md)。

```bash
# 当前位置：任意目录；终端：MSYS2 UCRT64 Bash。
printf '%s\n' "$MSYSTEM" "$MINGW_PREFIX"
```

预期分别是 `UCRT64` 和 `/ucrt64`。进入某个目录不会切换终端类型。UCRT64 的默认搜索路径包含 `/ucrt64/bin` 和 `/usr/bin`，见 [MSYS2 环境说明](https://www.msys2.org/docs/environments/)。

Zephyr 主机依赖按照[官方来源与平台选择](../P01_zephyr_make_project/主机工具与官方安装来源.md)安装。Windows 在 PowerShell 使用 winget，随后重开 UCRT64 检查 PATH。MSYS2 的 pacman 只在本教程的终端准备步骤安装 Bash 配套工具，不能替代该源码的官方主机依赖清单。`find`、`grep`、`xargs`、`sha256sum` 仍使用 MSYS2 的 Unix 工具。

Python 沿用本实验的 Windows 原生 Python 3.12；UCRT64 中可以调用 Windows Python Launcher `py`：

```bash
# 当前位置：任意目录；检查 Windows Python Launcher 和实际解释器。
type -a py
py -3.12 -c 'import sys; print(sys.version); print(sys.executable)'
type -a git cmake ninja dtc gperf 7z find grep sha256sum
```

`py` 能找到解释器不表示 PATH 中已经有 `python`。主线固定 3.12.10，Windows 图形安装、UCRT64 调用官方安装器及 PATH 配置见 [P002 的 2.1—2.2 节](../P01_zephyr_make_project/环境与依赖导航.md)。没有 `py` 时可直接定位已安装的 `python.exe`；不要为了解决命令缺失改用 `/usr/bin/python` 创建本教程环境。`type -a` 显示可能存在的多套工具；继续核对当前实际使用的解释器与工具路径。

## 1.2\_实验源码与配套目录

主线源码的 Windows 资源管理器路径为 `G:\zephyr_practice\zephyr-main`，UCRT64 Bash 写作 `/g/zephyr_practice/zephyr-main`。SDK 下载到 `G:\zephyr_practice`，解压根为 `G:\zephyr_practice\zephyr-sdk-1.0.1`，对应 Bash 路径 `/g/zephyr_practice/zephyr-sdk-1.0.1`；SDK 目录在下载并解压后才存在。P001/P002 主线的下载与 SDK 步骤都服务于这份源码；源码版本查 `VERSION`，SDK 选择查 `SDK_VERSION` 及构建规则，模块版本查 `west.yml`。

| 位置 | 用途 |
| --- | --- |
| 实验源码根的 `.venv` | 原生构建使用的 Windows Python 环境 |
| 实验源码根的 `learning/` | 按准备章放入的配套实验材料 |
| 实验源码根的 `build/learning-tools/` | 实验副本、模块下载和构建证据 |
| `/g/zephyr_practice/zephyr-sdk-1.0.1` | 主线 SDK 解压目录，可供多个实验共用 |

本目录早期参考草稿中的 `~/zephyr-download-lab/zephyr/`、Mini Manifest、ZIP、Git 和示意 `app/` 是不同组织方案，尚未逐条迁移为主线可执行命令。阅读时用于比较方法；实际从零操作以[工程准备主线](../P01_zephyr_make_project/大纲.md)为准，不把几种初始化步骤叠加到同一目录。

`hal_hc32`、`your-company`、`module1`、`vX.Y.Z` 等是概念或待替换示例。原文 `v4.4.0` 用于解释固定版本，不能替代实际源码身份。原生 ZIP 不自带 HC32 移植；板级代码、厂商 HAL、应用都必须在对应步骤准备完成后才能构建。

## 1.3\_Bash\_命令与路径写法

| 操作 | 本教程在 UCRT64 中的写法 |
| --- | --- |
| 多行命令 | 行尾 `\`，反斜杠后不再加空格 |
| 列目录，包含隐藏文件 | `ls -al` |
| 搜索命令位置 | `type -a python` |
| 搜索文本 | `grep -ni -- "hc32" ./west.yml` |
| 递归查文件 | `find . -type f`；管道传文件名时用 `-print0` 和 `xargs -0` |
| 文件摘要 | `sha256sum 文件名` |
| 移动文件或目录 | `mv -- 源 目标`，先核对目标是否存在 |
| 删除已搬空的目录 | `rmdir -- 目录`，非空会报错 |
| 设置环境变量 | `export 名称="值"`，对当前 shell 及随后启动的子进程生效 |
| 激活 Windows Python 环境 | `source .venv/Scripts/activate` |

`~/zephyr-download-lab` 中的 `~` 是 UCRT64 用户主目录，不是项目目录。Bash 命令中推荐使用 `"$HOME/zephyr-download-lab"`；双引号里的 `"~/..."` 不会展开 `~`。Windows 盘符路径可通过 `cygpath -u` 转成 Bash 路径，例如把自己从资源管理器复制的目录转换后再 `cd`。

Windows Python、CMake 和 SDK 读取的路径型环境变量使用 `cygpath -m` 转成盘符加正斜杠形式：

```bash
# 终端：Windows 的 UCRT64；源码和 SDK 已准备好。
cd /g/zephyr_practice/zephyr-main
export ZEPHYR_BASE="$(cygpath -m "$PWD")"
export ZEPHYR_SDK_INSTALL_DIR="$(cygpath -m /g/zephyr_practice/zephyr-sdk-1.0.1)"
export ZEPHYR_TOOLCHAIN_VARIANT="zephyr"
```

路径需要引用以保护空格。`ZEPHYR_MODULES` 是 CMake 的分号列表，Bash 中应给整个 `-D` 参数加引号，否则分号会把它拆成两条 shell 命令；它和 Bash 中用冒号分隔的 `PATH` 不是一回事。路径转换规则见 [MSYS2 Filesystem Paths](https://www.msys2.org/docs/filesystem-paths/)。

Windows SDK 的 setup.cmd 步骤使用 PowerShell：先用 Set-Location 进入含 sdk_version 的 SDK 根，再执行 `.\setup.cmd /t arm-zephyr-eabi`。该步骤结束后切回 UCRT64，继续摘要、解压、版本检查或工程操作，并按对应小节进入目录。两种终端的临时环境与当前目录互不继承；不要把 Windows 安装命令统一包装成 UCRT64 命令。

## 1.4\_网络与虚拟环境

访问 GitHub 前按[代理配置](代理配置.md)核对 `10808` 混合端口。Git 配置只供 Git 使用；浏览器 ZIP 下载、curl 和 pip 分别检查代理入口。MSYS2 换源按主教程操作，包名前缀仍使用 UCRT64，不能将 Linux 的 `apt` 安装命令直接搬过来。

主线先让 `python` 指向核对过的 3.12.10，再用 `python -m venv .venv` 创建环境；Launcher 路线的 `py -3.12 -m venv .venv` 只是另一种选择基础解释器的方式。之后在 Bash 中 `source .venv/Scripts/activate`。这仍然是 Windows 虚拟环境，包目录和可执行文件位于 `Lib/`、`Scripts/`；Linux 的 `.venv/bin/activate` 不适用于它。

源码、SDK 和缓存可按需搬运；复制来的旧 `.venv` 先移到别名位置，再在新位置创建全新的 `.venv`，从锁定依赖或匹配的 wheel 缓存恢复。Python 官方说明虚拟环境不应视为可直接复制的可移植目录，见 [venv 文档](https://docs.python.org/3/library/venv.html)。
