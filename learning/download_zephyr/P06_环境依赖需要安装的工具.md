```text
源码
│
├── Zephyr
├── CMSIS_6
└── HC32 HAL / DDL

工具链
│
├── Zephyr SDK Minimal
└── arm-zephyr-eabi
```

很多人到这里会产生一个很自然的问题：

> Zephyr SDK 和 ARM GCC 都下载好了，是不是就可以开始编译了？

还不够。

因为：

```text
arm-zephyr-eabi-gcc
```

只负责：

> 把已经准备好的 C/C++/汇编源码编译成 ARM 目标代码。

但在真正调用 GCC 之前，Zephyr 还要做大量工作：

```text
读取板卡
读取 Kconfig
处理 Devicetree
生成头文件
计算配置
寻找源码
生成编译参数
生成链接参数
生成 Ninja 构建规则
最后才调用 GCC
```

因此整个 Zephyr 构建链实际上更像：

```text
                 Zephyr Application
                         │
                         ▼
                       CMake
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
          Python      Kconfig     Devicetree
             │                       │
             │                      DTC
             │                       │
             └───────────┬───────────┘
                         │
                         ▼
                  生成构建配置
                         │
                         ▼
                       Ninja
                         │
                         ▼
              arm-zephyr-eabi-gcc
                         │
                         ▼
                    zephyr.elf
```

所以本章就把这些 Host 端工具全部拆开。

## 6.1\_认识并检查主机工具

先看构建由哪些主机程序协作，再核对本工程使用的 Windows Python。

### 6.1.1\_什么叫\_Host\_Tool

前面已经区分过：

```text
Host
=
开发电脑

Target
=
目标 MCU
```

比如：

```text
Host
Windows 11 x86-64

Target
HC32F4A0
ARM Cortex-M4F
```

因此：

```text
arm-zephyr-eabi-gcc
```

虽然运行在 Host 上，但它属于：

```text
Target Toolchain
```

因为它生成的是 Target 能执行的代码。

而：

```text
Python
CMake
Ninja
west
DTC
```

主要运行在开发电脑上，用来：

```text
分析
配置
生成
调度
管理
```

所以把它们称为：

```text
Host Tools
```

比较容易理解。

------

### 6.1.2\_先看最终需要哪些\_Host\_工具

以目前的 Windows Zephyr 环境为例，我们主要会遇到：

| 工具          | 主要作用                     | 第一阶段是否需要   |
| ------------- | ---------------------------- | ------------------ |
| Python        | 运行 Zephyr 构建脚本         | 必须               |
| CMake         | 配置整个构建系统             | 必须               |
| Ninja         | 真正执行编译任务             | 必须               |
| DTC           | 编译 Devicetree              | 必须               |
| west          | 多仓库管理和 Zephyr 命令封装 | 可以暂缓           |
| Git           | Git 仓库管理                 | ZIP 模式下可以暂缓 |
| gperf         | 某些源码生成流程需要         | 建议安装           |
| 7-Zip         | 解压 SDK/源码                | 推荐               |
| wget/curl     | 下载文件                     | 可选               |
| ccache        | 编译缓存                     | 可选               |
| OpenOCD/pyOCD | 烧录和调试                   | 编译阶段不是必须   |

当前 Zephyr 官方 Getting Started 把 CMake、Python 和 DTC 列为主要依赖；当前文档要求 CMake 3.28、Python 3.12、DTC 1.4.6 或以上，并在 Windows 官方安装列表中同时安装 Ninja、gperf、Git、wget、7-Zip 等工具。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

不过我们的教学环境和官方方案有一个明显区别：

```text
官方：
west + Git 优先

我们：
ZIP 源码优先
```

所以：

```text
Git
west
```

可以从：

```text
“第一天必须存在”
```

降级成：

```text
“后续按需要启用”
```

------

### 6.1.3\_Python\_到底在\_Zephyr\_里面干什么

很多 C/C++ 开发者第一次接触 Zephyr 时都会有这个疑问：

> 我写的是 C，为什么编译一个 RTOS 还必须装 Python？

因为：

> **Python 不是用来编译你的 C 程序，而是 Zephyr 构建系统自身大量使用 Python 脚本。**

Zephyr 官方明确说明，Python 3 被大量用于运行构建、环境维护和其他开发脚本。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/beyond-GSG.html?utm_source=chatgpt.com)

可以理解成：

```text
你的代码
main.c
    │
    │
    │ 并不是 Python 编译
    ▼
ARM GCC


但是编译之前：

Zephyr 构建系统
    │
    ├── Python script
    ├── Python script
    ├── Python package
    └── ...
```

所以关系是：

```text
Python
    ↓
帮助 Zephyr 准备构建

GCC
    ↓
真正编译 C/C++
```

------

### 6.1.4\_一个典型的\_Zephyr\_构建过程

例如我们运行：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
cmake -B build -GNinja -DBOARD=uyup_rpi_a/hc32f4a0pitb app
```

背后可能发生：

```text
CMake
 │
 ├── 加载 Zephyr CMake 脚本
 │
 ├── 调用 Python
 │      │
 │      ├── 处理配置
 │      ├── 分析文件
 │      ├── 生成代码
 │      └── 运行各种脚本
 │
 ├── 处理 Kconfig
 │
 ├── 处理 Devicetree
 │
 └── 生成 Ninja 文件
```

最后才得到：

```text
build.ninja
```

然后：

```text
Ninja
  │
  ├── arm-zephyr-eabi-gcc
  ├── arm-zephyr-eabi-gcc
  ├── arm-zephyr-eabi-gcc
  └── arm-zephyr-eabi-ld
```

所以：

```text
Python
```

本质上属于：

```text
Zephyr 构建基础设施
```

。

------

### 6.1.5\_为什么推荐\_Python\_3.12

当前 Zephyr 文档明确推荐：

```text
Python 3.12
```

并提醒使用更高版本 Python 在部分系统，尤其 Windows 上，可能出现某些依赖包安装兼容性问题。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

所以教学环境不要使用：

```text
“电脑上有什么 Python 就用什么”
```

。

应该固定：

```text
Python 3.12.x
```

。

这样学生之间：

```text
A：Python 3.11
B：Python 3.12
C：Python 3.14
```

产生环境差异的概率会小很多。

------

### 6.1.6\_怎么确认\_Python\_安装成功

UCRT64 Bash：

```bash
# 当前位置：任意目录；涉及 python 时先按正文激活 .venv；终端：UCRT64 Bash。
py -3.12 --version
```

或者：

```bash
# 当前位置：任意目录；涉及 python 时先按正文激活 .venv；终端：UCRT64 Bash。
python --version
```

可能输出：

```text
Python 3.12.x
```

这里：

```text
py
```

是 Windows Python Launcher。

：

```text
-3.12
```

表示：

> 指定 Python 3.12。

：

```text
--version
```

表示：

> 查看版本。

## 6.2\_创建并使用\_Windows\_Python\_虚拟环境

在 UCRT64 中创建、激活并定位虚拟环境，理解它与系统 Python 的关系。

### 6.2.1\_为什么不建议把所有\_Python\_包直接装进系统\_Python

假设：

```text
项目 A
Zephyr 4.4
```

需要：

```text
package-x 1.x
```

几年后：

```text
项目 B
Zephyr 5.x
```

可能需要：

```text
package-x 2.x
```

如果所有项目都往：

```text
C:\Python312\
```

里面安装：

```text
pip install ...
```

久而久之很容易形成：

```text
系统 Python
│
├── 项目 A 的包
├── 项目 B 的包
├── 其他 Python 工具
└── 各种不同版本依赖
```

然后某天：

```text
升级项目 B
        ↓
pip 升级 package-x
        ↓
项目 A 开始出问题
```

。

因此 Python 提供了：

```text
Virtual Environment
```

也就是：

```text
虚拟环境
```

。

------

### 6.2.2\_Python\_Virtual\_Environment\_是什么

可以理解成：

```text
系统 Python
C:\Python312\
       │
       ├───────────────┐
       │               │
       ▼               ▼
 Project A          Project B
 .venv              .venv
   │                  │
   ├── package A      ├── package X
   ├── package B      └── package Y
   └── west
```

两个项目各用各的。

不会轻易互相干扰。

Zephyr 官方 Getting Started 也明确推荐为 Zephyr 创建 Python virtual environment。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

------

### 6.2.3\_创建我们的虚拟环境

假设：

```text
~/zephyr-download-lab/
```

是整个教学环境。

可以：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
cd "$HOME/zephyr-download-lab"
```

然后：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
py -3.12 -m venv .venv
```

逐项解释。

------

#### (1)\_py\_-3.12

表示：

```text
使用 Python 3.12
```

。

------

#### (2)\_-m

表示：

> 运行一个 Python Module。

例如：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
python -m pip
```

就是：

> 用当前 Python 运行 pip module。

------

#### (3)\_venv

这是 Python 自带的：

```text
虚拟环境模块
```

。

------

#### (4)\_.venv

表示：

> 把虚拟环境创建到 `.venv` 目录。

所以：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
py -3.12 -m venv .venv
```

翻译成人话就是：

> 使用 Python 3.12，在当前目录创建一个名为 `.venv` 的 Python 虚拟环境。

------

### 6.2.4\_创建完成以后有什么

目录会变成类似：

```text
~/zephyr-download-lab/
│
├── .venv/
│   ├── Scripts/
│   ├── Lib/
│   └── pyvenv.cfg
│
├── zephyr/
├── modules/
└── zephyr-sdk-1.0.1/
```

其中：

```text
.venv/Scripts/
```

里面会有：

```text
python.exe
pip.exe
activate
```

。

------

### 6.2.5\_激活虚拟环境

Bash：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
source .venv/Scripts/activate
```

正常情况下命令行前面出现：

```text
(.venv)
```

例如：

```text
(.venv) UCRT64 ~/zephyr-download-lab
$
```

这表示：

> 当前 shell 优先使用 `.venv` 里的 Python 和 Python packages。

这里由 Windows Python 创建 `.venv`，因此 Bash 激活脚本位于 `Scripts/activate`；UCRT64 不是 Linux，不能换成 `.venv/bin/activate`。`source` 让脚本修改当前终端；关闭终端后需重新激活。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

------

### 6.2.6\_激活到底修改了什么

激活并不是：

```text
启动一个虚拟机
```

。

它主要是在当前终端环境里修改：

```text
PATH
```

。

原来可能：

```text
PATH:

/ucrt64/bin
/usr/bin
/c/Windows/...
/c/Python312/...
```

激活以后类似：

```text
PATH:

~/zephyr-download-lab/.venv/Scripts
/ucrt64/bin
/usr/bin
/c/Windows/...
/c/Python312/...
```

于是输入：

```text
python
```

当前 UCRT64 Bash 优先找到：

```text
~/zephyr-download-lab/.venv/Scripts/python.exe
```

。

------

### 6.2.7\_怎么确认当前\_Python\_真的是虚拟环境的

Bash：

```bash
# 当前位置：任意目录；涉及 python 时先按正文激活 .venv；终端：UCRT64 Bash。
type -a python
```

应该显示类似：

```text
~/zephyr-download-lab/.venv/Scripts/python.exe
```

再执行：

```bash
# 当前位置：任意目录；涉及 python 时先按正文激活 .venv；终端：UCRT64 Bash。
python --version
```

确认：

```text
Python 3.12.x
```

。

------

### 6.2.8\_什么是\_pip

Python 自己是：

```text
解释器
```

。

但是 Zephyr 还需要很多 Python Library。

比如构建脚本会依赖不同的 Python package。

负责安装 Python package 的工具通常就是：

```text
pip
```

。

因此：

```text
Python
│
└── pip
      │
      ├── package A
      ├── package B
      ├── package C
      └── west
```

。

------

### 6.2.9\_python\_-m\_pip\_和直接\_pip\_有什么区别

经常会看到：

```text
pip install xxx
```

也会看到：

```text
python -m pip install xxx
```

对于教学环境，我更推荐：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
python -m pip
```

。

因为它明确表达：

> 使用“这个 python”对应的 pip。

例如：

```text
系统有：

Python 3.11
Python 3.12
.venv Python
```

直接输入：

```text
pip
```

你有时候需要判断：

```text
这个 pip 到底属于谁？
```

而：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
python -m pip
```

等于明确说：

```text
当前 python
     ↓
运行它自己的 pip
```

。

## 6.3\_安装与源码匹配的\_Python\_依赖

区分已有 west 工作区与独立 ZIP 环境，各自沿匹配的依赖清单安装。

### 6.3.1\_Zephyr\_的\_Python\_依赖又从哪里知道

前面我们对 C/C++ external module 使用：

```text
west.yml
```

作为依赖依据。

Python 同样不能随便：

```text
想起来什么就 pip install 什么
```

。

Zephyr 源码本身维护了对应的 Python requirements。

官方当前推荐使用：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
west packages pip
```

读取 Zephyr 以及 Module 描述的 Python requirement，然后安装相匹配的依赖。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

但是我们当前有一个特殊条件：

```text
第一阶段不依赖 west。
```

所以教学文档里最好明确区分两个模式。

------

### 6.3.2\_模式\_A\_使用\_west\_管理\_Python\_Requirements

以后启用了 west：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
python -m pip install west
```

然后：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
west packages pip --install
```

或者在 UCRT64 Bash 中按 west 输出的参数安装（两种形式任选其一）。此手工形式要求实验目录及 requirements 路径不含空白；有空白时使用上面的 `--install` 形式：

```bash
# 当前位置：已初始化的 west 工作区中的 Zephyr 目录；已激活 .venv。
python -m pip install $(west packages pip)
```

由 west 帮我们：

```text
读取 Zephyr requirements
+
读取 external modules requirements
        ↓
交给 pip 安装
```

。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

------

### 6.3.3\_模式\_B\_我们的\_ZIP\_First\_环境

现在我们暂时不希望：

```text
安装 west
        ↓
又不小心进入 west update
        ↓
开始访问大量 Git 仓库
```

。

实际上：

```text
west
```

不是 CMake + Ninja 编译 Zephyr 的强制前置条件。

Zephyr 官方明确支持：

```text
没有 west
        ↓
直接 CMake
        ↓
Ninja
```

只需要我们自己提供 Modules。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/without-west.html)

因此我们的第一阶段可以是：

```text
Python
    ↓
Zephyr Python dependencies

CMake
    ↓

Ninja
    ↓

ARM GCC
```

而：

```text
west
```

先不进入主链。

<a id="section-6-4"></a>

## 6.4\_理解\_west\_CMake\_与\_Ninja\_的分工

从构建入口追到任务生成与执行，保留不用 west 的流程及其边界。

### 6.4.1\_west\_到底是什么

现在再解释 west，就不会把它误认为：

```text
Zephyr 编译器
```

。

west 本质上是 Zephyr 的：

```text
Meta Tool
+
Multi-repository Manager
+
Command Wrapper
```

官方称其为 Zephyr 的 meta-tool，并提供多 Git repository 管理能力，以及 Zephyr 自己扩展出来的 build、flash、debug 等命令。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/index.html?utm_source=chatgpt.com)

可以理解：

```text
west
│
├── workspace 管理
│   ├── west init
│   ├── west update
│   └── west manifest
│
├── build 包装
│   └── west build
│
├── 烧录包装
│   └── west flash
│
└── 调试包装
    └── west debug
```

。

------

### 6.4.2\_west\_build\_自己会不会编译\_C

不会。

例如：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
west build
```

背后仍然是类似：

```text
west
  │
  ▼
CMake
  │
  ▼
Ninja
  │
  ▼
arm-zephyr-eabi-gcc
```

。

所以：


更像：

而不是编译器。

### 6.4.6\_CMake\_又是什么

这是整个 Host 构建环境中最重要的工具之一。

但同样：

```text
CMake != Compiler
```

。

它主要负责：

> **根据工程描述和配置，生成真正给构建工具使用的构建规则。**

比如我们的应用：

```text
app/
├── CMakeLists.txt
├── prj.conf
└── src/
    └── main.c
```

其中：

```text
CMakeLists.txt
```

可能只有：

```text
cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})

project(my_app)

target_sources(app PRIVATE src/main.c)
```

当前 Zephyr `hello_world` 示例也采用这种典型结构。[GitHub](https://github.com/zephyrproject-rtos/zephyr/blob/main/samples/hello_world/CMakeLists.txt?utm_source=chatgpt.com)

### 6.4.7\_CMake\_做什么

例如：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
cmake -B build -GNinja app
```

CMake 会分析：

```text
app/CMakeLists.txt
Zephyr/CMakeLists.txt
Board
SoC
Kconfig
Devicetree
Toolchain
Modules
```

最后生成：

```text
build/
├── build.ninja
├── CMakeCache.txt
├── CMakeFiles/
└── zephyr/
```

。

重点是：

```text
CMake 的输出不是 MCU 固件。
```

而主要是：

```text
“怎么编译”的规则
```

。

------

### 6.4.8\_cmake\_-B\_build\_是什么意思

拆开：

```text
cmake
```

表示：

> 运行 CMake。

：

```text
-B build
```

其中：

```text
-B
```

可以理解为：

```text
Build Directory
```

。

即：

> 生成出来的构建文件放到 `build` 目录。

于是源码：

```text
app/
```

不会被：

```text
.o
.a
elf
ninja 文件
缓存
```

弄得乱七八糟。

最终：

```text
app/
├── CMakeLists.txt
├── prj.conf
└── src/

build/
├── build.ninja
├── CMakeCache.txt
└── zephyr/
```

。

这称为：

```text
out-of-tree build
```

也就是：

> 构建产物与源码目录分离。

### 6.4.9\_G\_Ninja\_又是什么

例如：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
cmake -B build -G Ninja app
```

这里：

```text
-G
```

表示：

```text
Generator
```

。

意思是：

> CMake 最终给哪一种构建工具生成规则。

我们选择：

```text
Ninja
```

所以：

```text
CMake
    ↓
生成
    ↓
build.ninja
```

。

Windows Zephyr 官方开发流程使用 Ninja；Zephyr 文档也说明 Windows 上需要使用 Ninja，而 `west build` 默认也是使用 Ninja。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)

### 6.4.10\_那\_Ninja\_又是什么

Ninja 可以理解成：

> **真正负责执行大量编译命令的构建执行器。**

例如 CMake 已经计算出：

```text
main.c
    ↓
arm-zephyr-eabi-gcc

spi.c
    ↓
arm-zephyr-eabi-gcc

uart.c
    ↓
arm-zephyr-eabi-gcc
```

Ninja 就负责：

```text
看看哪些文件需要重新编译
        ↓
安排编译任务
        ↓
并行调用 GCC
        ↓
最后调用 Linker
```

。

所以：

```text
CMake
=
规划怎么编

Ninja
=
执行这个计划

GCC
=
真正把 C 变成机器码
```

。

这是非常重要的三层关系。

> ninja和make的区别：因为 **Zephyr 并不是“不能用 make”**，而是它的构建体系选择了 **CMake + Ninja 作为默认组合**。Linux 内核则是另一套历史和架构完全不同的构建体系：**Kbuild + Makefile + GNU Make**。
>
> Zephyr 官方目前明确支持 **Ninja 和 Make 两种后端**，只是 `west build` 默认使用 Ninja；Linux/macOS 下你完全可以切换成 `Unix Makefiles`。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)
>
> 最关键的是把这两套体系分开看：
>
> ```
> Linux Kernel
> ────────────────────────────
> Kconfig
> Makefile / Kbuild
>       │
>       ▼
>    GNU Make
>       │
>       ▼
>  gcc / clang
> ```
>
> 而 Zephyr 是：
>
> ```
> Zephyr
> ────────────────────────────
> Kconfig
> Devicetree
> CMakeLists.txt
>       │
>       ▼
>     CMake
>       │
>       ├──── 生成 build.ninja ───► Ninja
>       │
>       └──── 生成 Makefile ──────► Make
>                                    │
>                                    ▼
>                               gcc / clang
> ```
>
> 因此，**Ninja 并不是 Zephyr 必须使用的东西，而是 CMake 生成构建系统时默认选择的后端。**
>
> ------
>
> ### 为什么 Zephyr 更倾向 Ninja？
>
> 一个重要原因是：
>
> > **Zephyr 已经把复杂的“工程逻辑”交给 CMake 处理了。**
>
> 这时候 Ninja 不需要像 Linux 内核的 Makefile 那样承担大量复杂逻辑。
>
> Linux 内核的 Makefile/Kbuild 本身就在做很多事情：
>
> ```
> 判断 CONFIG_xxx
> 决定哪些 .c 编译
> 决定哪些目录进入
> 决定哪些对象组合
> 控制 built-in.a
> 处理模块
> 处理架构
> 处理 generated headers
> ……
> ```
>
> 例如 Linux 里经常看到：
>
> ```
> obj-$(CONFIG_SPI) += spi.o
> obj-$(CONFIG_I2C) += i2c.o
> ```
>
> Make/Kbuild 不仅是在“执行 gcc”，它本身就是 Linux 构建系统的重要逻辑层。
>
> 而 Zephyr 里类似的逻辑大量已经发生在：
>
> ```
> CMake
> Kconfig
> Devicetree
> Python生成脚本
> ```
>
> 这一层。
>
> 例如：
>
> ```
> zephyr_sources(main.c)
>
> zephyr_library_sources_ifdef(
>     CONFIG_SPI
>     spi.c
> )
> ```
>
> CMake 配置阶段已经算出来：
>
> ```
> main.c 要编译
> spi.c 要编译
> uart.c 不需要编译
> ……
> ```
>
> 最后生成一个非常明确的任务图给 Ninja：
>
> ```
> main.c ──gcc──► main.o ──┐
>                          │
> spi.c ───gcc──► spi.o ───┼──ld──► zephyr.elf
>                          │
> kernel.c ─gcc─► kernel.o ┘
> ```
>
> 这个时候需要的不是一个功能非常丰富的脚本系统，而更像一个：
>
> > **“拿着已经算好的依赖图，尽快执行任务”的工具。**
>
> 而这正是 Ninja 的设计目标。
>
> ------
>
> ### Ninja 比 Make 更“笨”，反而是它的优势
>
> 这个地方很有意思。
>
> GNU Make 很强。
>
> Makefile 可以：
>
> ```
> ifeq (...)
> endif
>
> $(shell ...)
> $(foreach ...)
> $(eval ...)
> $(call ...)
> ```
>
> 甚至可以在 Makefile 里面写大量逻辑。
>
> 所以：
>
> ```
> Make
> = 构建执行器
> + 一套功能比较强的构建描述语言
> ```
>
> 而 Ninja 故意把自己设计得比较简单。
>
> 它基本认为：
>
> ```
> 别让我思考工程该怎么构建。
>
> 你直接告诉我：
>
> A依赖B
> B用什么命令生成
> C依赖A和D
>
> 我负责最快把它跑完。
> ```
>
> 因此：
>
> ```
> CMake
> 负责“思考”
>
> Ninja
> 负责“干活”
> ```
>
> 两者配起来非常合适。
>
> ------
>
> ### 举一个很直观的例子
>
> 假设工程：
>
> ```
> main.c
> uart.c
> spi.c
> gpio.c
> ```
>
> 你选择：
>
> ```
> CONFIG_SPI=y
> CONFIG_UART=y
> CONFIG_GPIO=n
> ```
>
> Zephyr 配置阶段：
>
> ```
> Kconfig
>    │
>    ▼
> .config
>    │
>    ▼
> CMake
> ```
>
> CMake 最后算出来：
>
> ```
> main.c 需要
> uart.c 需要
> spi.c 需要
> gpio.c 不需要
> ```
>
> 于是生成类似：
>
> ```
> build main.o: cc main.c
> build uart.o: cc uart.c
> build spi.o: cc spi.c
>
> build zephyr.elf: link main.o uart.o spi.o
> ```
>
> Ninja 根本不用知道：
>
> ```
> CONFIG_SPI 是什么？
> CONFIG_GPIO 为什么关闭？
> Devicetree 是什么？
> HC32F4A0 是什么？
> Zephyr 是什么？
> ```
>
> 它只知道：
>
> ```
> 我要生成：
>
> main.o
> uart.o
> spi.o
>
> 然后链接 zephyr.elf。
> ```
>
> 这就是 Ninja 很适合作为 CMake 后端的原因。
>
> ------
>
> ## 那为什么 Linux 内核不换 Ninja？
>
> 这就不是简单一句“因为 Make 老”能解释的了。
>
> Linux 内核从很早开始，就建立了：
>
> ```
> Kbuild
> +
> Makefile
> +
> GNU Make
> ```
>
> 整套体系。
>
> 今天 Linux 内核里的 Make 已经不是单纯：
>
> ```
> gcc main.c
> ```
>
> 这种东西了。
>
> 整个内核源码树存在大量：
>
> ```
> Makefile
> Kbuild
> Kconfig
> scripts/Makefile.*
> arch/*/Makefile
> drivers/*/Makefile
> ```
>
> 例如：
>
> ```
> obj-$(CONFIG_USB) += usb/
> obj-$(CONFIG_SPI) += spi/
> obj-$(CONFIG_I2C) += i2c/
> ```
>
> 背后已经积累了几十年的构建逻辑。
>
> 所以 Linux 如果换成：
>
> ```
> CMake + Ninja
> ```
>
> 并不是：
>
> ```
> make
> 换成
> ninja
> ```
>
> 这么简单。
>
> 实际上得把：
>
> ```
> Linux Kbuild
> ```
>
> 整个重写。
>
> 相当于：
>
> ```
> 现有：
>
> Kconfig
>    ↓
> Kbuild / Makefile
>    ↓
> GNU Make
> ```
>
> 改造成：
>
> ```
> Kconfig
>    ↓
> 某个新的生成系统
>    ↓
> build.ninja
>    ↓
> Ninja
> ```
>
> 这会涉及内核所有：
>
> ```
> arch/
> drivers/
> fs/
> net/
> mm/
> kernel/
> security/
> tools/
> ……
> ```
>
> 因此收益未必值得这种巨大迁移成本。
>
> ------
>
> ## Zephyr 则不一样
>
> Zephyr 的现代构建架构从设计上就把：
>
> ```
> 工程描述
> ```
>
> 和：
>
> ```
> 构建执行
> ```
>
> 拆开了。
>
> 也就是：
>
> ```
>                 配置层
>                    │
>        ┌───────────┼───────────┐
>        │           │           │
>     Kconfig    Devicetree   CMakeLists
>        │           │           │
>        └───────────┼───────────┘
>                    ▼
>                  CMake
>                    │
>               生成构建图
>                    │
>                    ▼
>                  Ninja
>                    │
>               执行编译命令
>                    │
>                    ▼
>               GCC / linker
> ```
>
> 所以 Zephyr 很自然地可以选择一个专门负责“执行”的工具。
>
> ------
>
> ## Ninja 还有一个现实优势：并行构建和增量构建很快
>
> Ninja 的核心目标之一就是：
>
> > **大型工程下，非常低开销地计算“现在到底需要重新执行哪些任务”。**
>
> 例如：
>
> ```
> 10000 个源文件
>
> 你修改了：
>
> drivers/spi/spi_hc32.c
> ```
>
> Ninja 希望快速确定：
>
> ```
> 只重新编译：
>
> spi_hc32.c
>        ↓
> spi_hc32.o
>        ↓
> 相关 archive
>        ↓
> zephyr.elf
> ```
>
> 而不是在构建系统自身的解析阶段花很多时间。
>
> 这里要注意：
>
> > Ninja 并不是“生成出来的机器码比 Make 更快”。
>
> 最终：
>
> ```
> Ninja → gcc
> Make  → gcc
> ```
>
> 调用的可能完全是同一个 GCC。
>
> 差别主要在：
>
> ```
> 依赖图解析
> 任务调度
> 并行执行
> 构建工具自身开销
> ```
>
> ------
>
> ## 还有一个 Zephyr 特别重要的原因：跨平台
>
> Zephyr 不只是 Linux 用户在开发。
>
> 它大量用户运行在：
>
> ```
> Linux
> Windows
> macOS
> ```
>
> 而 Ninja 在这三种平台上的行为比较统一。
>
> Zephyr 官方文档目前说明，Linux/macOS 可以选择 Ninja 或 Make，而 Windows 构建路径使用 Ninja；`west build` 默认也是 Ninja。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)
>
> 因此：
>
> ```
> Windows:
>     CMake + Ninja
>
> Linux:
>     CMake + Ninja
>
> macOS:
>     CMake + Ninja
> ```
>
> 整个教程、CI、开发流程比较统一。
>
> 如果默认采用 GNU Make：
>
> ```
> Linux：
> GNU Make
>
> Windows：
> MSYS Make?
> MinGW Make?
> NMake?
> GNU Make?
> ```
>
> 事情就更复杂。
>
> ------
>
> # 你其实可以让 Zephyr 用 Make
>
> 例如官方支持：
>
> ```
> west build -b <board> -- -G"Unix Makefiles"
> ```
>
> 之后生成的就不是：
>
> ```
> build/build.ninja
> ```
>
> 而是：
>
> ```
> build/Makefile
> ```
>
> 然后底层：
>
> ```
> west
>   ↓
> CMake
>   ↓
> Makefile
>   ↓
> make
>   ↓
> gcc
> ```
>
> 甚至可以把 west 默认 generator 改掉：
>
> ```
> west config build.generator "Unix Makefiles"
> ```
>
> 官方文档也明确给出了这种方式。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)
>
> 所以实际上：
>
> ```
> Zephyr + Ninja
> ```
>
> 不是一个强绑定关系。
>
> 更准确的是：
>
> ```
> Zephyr
>    ↓
> CMake
>    ↓
> 选择 Generator
>
>    ┌────────────┴─────────────┐
>    ▼                          ▼
> Ninja                      Unix Makefiles
>    │                          │
> ninja                       make
>    │                          │
>    └───────────┬──────────────┘
>                ▼
>               GCC
> ```
>
> ------
>
> ## 你可以这样理解 Linux 和 Zephyr 的根本区别
>
> 这比单纯记“Linux 用 Make，Zephyr 用 Ninja”重要得多：
>
> ```
> Linux：
>
> Make/Kbuild 自己就是构建系统的重要组成部分。
>
>               Kbuild
>                 +
>              GNU Make
>                 │
>                 ▼
>                GCC
> ```
>
> 而：
>
> ```
> Zephyr：
>
> CMake 才是主要的构建配置/生成系统。
>
>               CMake
>                 │
>         生成执行层描述
>                 │
>              Ninja
>                 │
>                 ▼
>                GCC
> ```
>
> 所以我会把前面那句话稍微修正成：
>
> > **Linux 内核选择 Make，是因为 Kbuild 本身就是建立在 GNU Make 之上的成熟构建体系。**
> >
> > **Zephyr 选择 Ninja 作为默认后端，是因为 Zephyr 把复杂的工程配置和依赖生成交给 CMake，Ninja 只需要高效执行 CMake 已经生成好的构建图。**
>
> 换句话说：
>
> ```
> Linux：
>
> Make 既参与“理解怎么构建”
> 又参与“执行构建”
>
>
> Zephyr：
>
> CMake：“怎么构建？”
> Ninja：“行，我执行。”
> GCC：“行，我编译。”
> ```
>
> 这也是为什么你接下来学 Zephyr 时，**CMake 比 Ninja 重要得多**。Ninja 通常你知道它“处于哪一层、为什么存在”就够了；真正经常需要理解和修改的是 `CMakeLists.txt`、Kconfig 和 Devicetree。

------

### 6.4.11\_一张图看懂三者

```text
CMakeLists.txt
Kconfig
Devicetree
Board
Toolchain
    │
    ▼
  CMake
    │
    │ 生成
    ▼
build.ninja
    │
    ▼
  Ninja
    │
    │ 调用
    ▼
arm-zephyr-eabi-gcc
arm-zephyr-eabi-as
arm-zephyr-eabi-ld
    │
    ▼
zephyr.elf
```

所以以后遇到报错时，可以初步区分：

```text
CMake 报错
    ↓
配置阶段的问题


Ninja 报某命令失败
    ↓
构建执行阶段


GCC error
    ↓
源码编译阶段


ld error
    ↓
链接阶段
```

这对排查问题非常有帮助。

## 6.5\_准备\_DTC\_和辅助工具

核对设备树工具、版本约束以及 gperf、ccache、wget 的作用。

### 6.5.1\_DTC\_又是什么

DTC：

```text
Device Tree Compiler
```

也就是：

```text
设备树编译器
```

。

Linux 驱动开发者对：

```text
DTS
DTSI
DTB
```

应该比较熟悉。

但 Zephyr 同样大量使用 Devicetree 来描述：

```text
Board Hardware
SoC Peripheral
Memory
GPIO
UART
SPI
I2C
Clock
Pin Control
```

等硬件信息。

------

### 6.5.2\_Zephyr\_Devicetree\_为什么需要\_DTC

例如板级 DTS：

```text
&uart1 {
    status = "okay";
    current-speed = <115200>;
};
```

或者：

```text
&spi5 {
    status = "okay";
};
```

这些：

```text
.dts
.dtsi
.overlay
```

并不能直接被 C Compiler 使用。

Zephyr 构建系统需要：

```text
DTS
    │
    ▼
Devicetree processing
    │
    ├── DTC
    ├── Python
    └── Zephyr scripts
    │
    ▼
生成 C 可使用的信息
```

。

因此 DTC 是：

```text
Build Host Tool
```

。

而不是：

```text
运行在 MCU 上的程序。
```

------

### 6.5.3\_DTC\_和\_Linux\_内核中的\_DTC\_是不是同一个概念

是同一类工具和语法体系。

但使用结果有所不同。

Linux 常见：

```text
board.dts
    ↓
dtc
    ↓
board.dtb
    ↓
Bootloader / Kernel
```

而 Zephyr 更偏向：

```text
board.dts
    ↓
Zephyr build
    ↓
Devicetree information
    ↓
生成头文件 / 编译时配置
    ↓
直接编进 Firmware
```

。

所以不要简单理解为：

> Zephyr 启动以后再加载一个 DTB。

大多数 MCU Zephyr 场景不是 Linux 的那个运行时 DTB 模式。

------

### 6.5.4\_DTC\_到底从哪里来

有两种主要方式。

#### (1)\_方式一\_Host\_单独安装

例如本教程使用的 UCRT64：

```bash
# 当前位置：任意目录；涉及 python 时先按正文激活 .venv；终端：UCRT64 Bash。
pacman -S --needed mingw-w64-ucrt-x86_64-dtc
```

DTC 是独立的 Host dependency，本教程通过 MSYS2 的 UCRT64 包安装，安装后使用 `type -a dtc` 和 `dtc --version` 检查。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

#### (2)\_方式二\_使用\_Zephyr\_SDK\_中的预编译\_Host\_Tool

Zephyr 官方 Linux Host 文档也明确说明，可以使用 Zephyr SDK 自带的 DTC。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/installation_linux.html?utm_source=chatgpt.com)

所以：

```text
DTC
```

和：

```text
ARM Toolchain
```

虽然都可能来自 SDK，但角色完全不同。

------

### 6.5.5\_为什么我仍然建议教学环境显式检查\_DTC

即使 SDK 中可能已有：

```text
dtc
```

也应该执行：

```text
dtc --version
```

确认最终：

```text
PATH 中实际使用的是谁。
```

因为 Windows 环境里可能同时存在：

```text
系统 DTC

MSYS2 DTC

Zephyr SDK DTC

其他开发环境带的 DTC
```

。

如果不知道当前运行的是哪个：

```bash
# 当前位置：任意目录；涉及 python 时先按正文激活 .venv；终端：UCRT64 Bash。
type -a dtc
```

可以查看。

------

### 6.5.6\_当前主要版本最低要求

截至当前 Zephyr `latest` 文档，主要依赖最低版本为：

| 工具   | 当前 latest 最低要求 |
| ------ | -------------------- |

例如我们如果固定：


这样也方便以后向后续 Zephyr 版本迁移。

------

### 6.5.7\_gperf\_又是干什么的

官方 Host dependency 里面还会看到：

```text
gperf
```

。

很多嵌入式开发者可能从来没直接用过。

GNU gperf 是一个：

```text
Perfect Hash Function Generator
```

。

也就是：

> 根据一组关键字生成高效查找代码的工具。

Zephyr 某些构建流程会使用它。

这里没必要要求初学者学习 gperf 算法。

只需要知道：

```text
gperf
```

属于：

```text
Build-time Code Generation Tool
```

。

如果 Zephyr 某个模块需要它：

```text
构建阶段调用
```

。

它：

```text
不会运行在 HC32F4A0 上。
```

------

### 6.5.8\_ccache\_又是什么

另一个常见工具：

```text
ccache
```

。

它不是必须项。

它解决的是：

> 重复编译相同内容时，能不能直接复用以前的编译结果。

例如：

```text
第一次：

main.c
   ↓
GCC
   ↓
main.o


第二次内容完全相同：

main.c
   ↓
ccache
   ↓
发现以前编过
   ↓
直接拿 main.o
```

。

所以它是：

```text
编译加速工具
```

而不是：

```text
Zephyr 编译正确性依赖。
```

教学第一阶段可以不管。

------

### 6.5.9\_wget\_又是什么

```text
wget
```

就是一个命令行下载工具。

例如：

```text
wget https://...
```

用途和浏览器下载类似。

我们的教程恰恰因为国内网络问题，准备优先采用：

```text
浏览器
企业镜像
下载器
离线包
```

所以：

```text
wget
```

不是 Mini Environment 的核心组件。

它可以保留为：

```text
辅助工具。
```

### 6.6.1\_Git\_在我们环境中的定位也应该重新定义

官方 Windows Host Dependencies 会直接安装 Git。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

但我们的教程应该明确：

```text

```

和：

```text

```

是两个不同概念。

```text

```

但是第一阶段：


。

都会需要。

所以我们的定义应该是：

```text

不依赖

后续版本管理：
需要
```

。

### 6.6.2\_west\_也是一样

我们可以提前：

```bash

```

但是：

> **不等于必须执行 `west update`。**

这一点非常重要。

west 安装本身只是：

```text
Python package
```

。

官方文档也说明 west 是 Python 3 编写并通过 PyPI 分发的。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/install.html?utm_source=chatgpt.com)

也就是说：

```bash

python -m pip install west
```

```text

+

```

不会自动下载：

```text

NXP HAL
Nordic HAL
```

。

真正开始下载 repository 的是后续：

```bash

```

。

------

### 6.6.3\_所以可以安装\_west\_但不让它管理源码

这其实是一种可以考虑的中间模式：

```text
ZIP 获得源码

+

安装 west Python package

但是：

不运行 west update
```

。

这样以后可能逐步使用某些 west 能力。

不过这里需要注意一个官方行为：

如果 west 已经安装，Zephyr 构建系统可能检测到它并尝试利用 workspace 信息；Zephyr 的 without-west 文档甚至建议，如果明确选择完全不用 west，可以卸载它，以免构建系统尝试使用它。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/without-west.html)

因此我们的教学第一阶段更干净的方式还是：

```text
Stage 1：

不安装 west


Stage 2：

理解 west 后再安装
```

。

## 6.7\_检查\_PATH\_与实际程序来源

### 6.7.1\_到底哪些需要加入\_PATH

这是 Windows 教程必须讲清楚的问题。


：

```text
env.sh
```

例如，将下面完整内容保存为实验根目录的 `env.sh`；它只服务于本章的独立 ZIP 环境，当前 HC32 集成工程继续使用已有的 `scripts/project_env.py`：

```bash
# 保存为下载实验根目录的 env.sh，通过 source ./env.sh 载入。
# BASH_SOURCE 定位脚本自身，不要求当前目录恰好与脚本目录一致。
download_lab_root="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"

if [[ "${MSYSTEM:-}" != UCRT64 ]]; then
    printf '%s\n' '请在 MSYS2 UCRT64 Bash 中载入此脚本。' >&2
    return 1
fi
if [[ ! -f "$download_lab_root/.venv/Scripts/activate" ]]; then
    printf '%s\n' '请先在实验根目录用 Windows Python 创建 .venv。' >&2
    return 1
fi
source "$download_lab_root/.venv/Scripts/activate" || return

# Windows Python / CMake 读取盘符加正斜杠路径。
export ZEPHYR_BASE="$(cygpath -m "$download_lab_root/zephyr")"
export ZEPHYR_SDK_INSTALL_DIR="$(cygpath -m "$download_lab_root/zephyr-sdk-1.0.1")"
export ZEPHYR_TOOLCHAIN_VARIANT="zephyr"
unset download_lab_root
```

先不用要求初学者马上理解全部 Bash。

这里先抓住三个动作：定位脚本目录、激活 Windows Python 虚拟环境、导出源码与 SDK 路径。必须用 `source`，直接执行 `bash env.sh` 只会影响子进程，不能准备当前终端。

最终他们只需要：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
source ./env.sh
```

环境就准备好。

### 6.8.7\_这样环境真正变成\_可搬运

例如整个：

```text
~/zephyr-download-lab/
```

复制到：

```text
/e/zephyr-download-lab/
```

如果脚本大量使用：

```text
相对路径
```

而不是：

```text
写死某个盘符和用户目录
```

源码、SDK 和下载缓存可以尽量随目录搬运；但 Python 的 `.venv` 含有绝对路径，不能直接复制后继续使用。换目录或换电脑后，先将复制过来的旧 `.venv` 移到别名位置，再在新位置执行 `py -3.12 -m venv .venv` 并按已保存的依赖清单重装；`env.sh` 不能消除这一限制。

准备好新目录的虚拟环境后，可以尽量做到：

```text
解压到任意目录
        ↓
source ./env.sh
        ↓
开始工作
```

。

这对于：

```text
教学
企业内网
CI
无互联网环境
新员工环境
```

非常有价值。

## 6.9\_衔接两条路线与离线依赖

保留 ZIP 与 west 的演进关系，将 Python wheel 缓存补入完整离线准备流程。

### 6.9.1\_我们现在真正形成了一套不同于官方教程的路线

官方典型路线：

```text

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
```

```text
    ↓
安装匹配的 Python Dependencies
    ↓
设置 ZEPHYR_BASE
    ↓
设置 ZEPHYR_MODULES
    ↓
CMake
    ↓
Ninja
    ↓
开始编译
```

暂时完全绕开：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
git clone
west init
west update
```

。

### 6.9.4\_把\_Zephyr\_Python\_依赖也做成离线包\_wheelhouse

也就是把：

```text
Python 3.12

+

Zephyr requirements
```

提前解析，然后下载成：

```text
downloads/
└── python-wheels/
    ├── west-xxx.whl
    ├── pyelftools-xxx.whl
    ├── pyyaml-xxx.whl
    ├── packaging-xxx.whl
    ├── ...
    └── requirements-lock.txt
```

最终学生在下载实验根目录、激活新建 `.venv` 后安装；先确认锁定清单及其全部依赖的匹配 Windows/Python wheel 均已准备齐，下面才可以不访问互联网：

```bash
# 当前位置：~/zephyr-download-lab；终端：UCRT64 Bash。
python -m pip install \
    --no-index \
    --find-links ./downloads/python-wheels \
    -r ./downloads/python-wheels/requirements-lock.txt
```

这样我们的环境才真正接近：

> **Zephyr 源码、Module、交叉编译器、Host 工具、Python 依赖全部能够预下载；拿到整个教学包以后，即使 GitHub 和 PyPI 都不可用，也可以直接开始工程。**

这一步做完以后，再进入第一次真正的 **“完全不用 west、完全不用 git 的 HC32F4A0 Hello World 编译”** 会非常顺。
