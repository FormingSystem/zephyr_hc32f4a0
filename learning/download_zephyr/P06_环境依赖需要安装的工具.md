# 6. Host 端工具：Python、CMake、Ninja、west、DTC 到底分别干什么

> 本篇为下载方案的参考草稿，保留原有讨论与示例，尚未完成逐项版本核验和完整安装实测。当前 HC32 工程请按[项目安装流程](../../project-docs/environment.md)操作；已整理的入门主线见[工程准备大纲](../P01_zephyr_make_project/大纲.md)。

前面我们已经准备好了两大类东西：

```
源码
│
├── Zephyr
├── CMSIS_6
└── HC32 HAL / DDL

工具链
│
├── Zephyr SDK Minimal
└── arm-zephyr-eabi
```

很多人到这里会产生一个很自然的问题：

> Zephyr SDK 和 ARM GCC 都下载好了，是不是就可以开始编译了？

还不够。

因为：

```
arm-zephyr-eabi-gcc
```

只负责：

> 把已经准备好的 C/C++/汇编源码编译成 ARM 目标代码。

但在真正调用 GCC 之前，Zephyr 还要做大量工作：

```
读取板卡
读取 Kconfig
处理 Devicetree
生成头文件
计算配置
寻找源码
生成编译参数
生成链接参数
生成 Ninja 构建规则
最后才调用 GCC
```

因此整个 Zephyr 构建链实际上更像：

```
                 Zephyr Application
                         │
                         ▼
                       CMake
                         │
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
          Python      Kconfig     Devicetree
             │                       │
             │                      DTC
             │                       │
             └───────────┬───────────┘
                         │
                         ▼
                  生成构建配置
                         │
                         ▼
                       Ninja
                         │
                         ▼
              arm-zephyr-eabi-gcc
                         │
                         ▼
                    zephyr.elf
```

所以本章就把这些 Host 端工具全部拆开。

------

## 6.1 什么叫 Host Tool

前面已经区分过：

```
Host
=
开发电脑

Target
=
目标 MCU
```

比如：

```
Host
Windows 11 x86-64

Target
HC32F4A0
ARM Cortex-M4F
```

因此：

```
arm-zephyr-eabi-gcc
```

虽然运行在 Host 上，但它属于：

```
Target Toolchain
```

因为它生成的是 Target 能执行的代码。

而：

```
Python
CMake
Ninja
west
DTC
```

主要运行在开发电脑上，用来：

```
分析
配置
生成
调度
管理
```

所以把它们称为：

```
Host Tools
```

比较容易理解。

------

## 6.2 先看最终需要哪些 Host 工具

以目前的 Windows Zephyr 环境为例，我们主要会遇到：

| 工具          | 主要作用                     | 第一阶段是否需要   |
| ------------- | ---------------------------- | ------------------ |
| Python        | 运行 Zephyr 构建脚本         | 必须               |
| CMake         | 配置整个构建系统             | 必须               |
| Ninja         | 真正执行编译任务             | 必须               |
| DTC           | 编译 Devicetree              | 必须               |
| west          | 多仓库管理和 Zephyr 命令封装 | 可以暂缓           |
| Git           | Git 仓库管理                 | ZIP 模式下可以暂缓 |
| gperf         | 某些源码生成流程需要         | 建议安装           |
| 7-Zip         | 解压 SDK/源码                | 推荐               |
| wget/curl     | 下载文件                     | 可选               |
| ccache        | 编译缓存                     | 可选               |
| OpenOCD/pyOCD | 烧录和调试                   | 编译阶段不是必须   |

当前 Zephyr 官方 Getting Started 把 CMake、Python 和 DTC 列为主要依赖；当前文档要求 CMake 3.28、Python 3.12、DTC 1.4.6 或以上，并在 Windows 官方安装列表中同时安装 Ninja、gperf、Git、wget、7-Zip 等工具。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

不过我们的教学环境和官方方案有一个明显区别：

```
官方：
west + Git 优先

我们：
ZIP 源码优先
```

所以：

```
Git
west
```

可以从：

```
“第一天必须存在”
```

降级成：

```
“后续按需要启用”
```

------

## 6.3 Python 到底在 Zephyr 里面干什么

很多 C/C++ 开发者第一次接触 Zephyr 时都会有这个疑问：

> 我写的是 C，为什么编译一个 RTOS 还必须装 Python？

因为：

> **Python 不是用来编译你的 C 程序，而是 Zephyr 构建系统自身大量使用 Python 脚本。**

Zephyr 官方明确说明，Python 3 被大量用于运行构建、环境维护和其他开发脚本。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/beyond-GSG.html?utm_source=chatgpt.com)

可以理解成：

```
你的代码
main.c
    │
    │
    │ 并不是 Python 编译
    ▼
ARM GCC


但是编译之前：

Zephyr 构建系统
    │
    ├── Python script
    ├── Python script
    ├── Python package
    └── ...
```

所以关系是：

```
Python
    ↓
帮助 Zephyr 准备构建

GCC
    ↓
真正编译 C/C++
```

------

## 6.4 一个典型的 Zephyr 构建过程

例如我们运行：

```
cmake -B build -GNinja -DBOARD=uyup_rpi_a/hc32f4a0pitb app
```

背后可能发生：

```
CMake
 │
 ├── 加载 Zephyr CMake 脚本
 │
 ├── 调用 Python
 │      │
 │      ├── 处理配置
 │      ├── 分析文件
 │      ├── 生成代码
 │      └── 运行各种脚本
 │
 ├── 处理 Kconfig
 │
 ├── 处理 Devicetree
 │
 └── 生成 Ninja 文件
```

最后才得到：

```
build.ninja
```

然后：

```
Ninja
  │
  ├── arm-zephyr-eabi-gcc
  ├── arm-zephyr-eabi-gcc
  ├── arm-zephyr-eabi-gcc
  └── arm-zephyr-eabi-ld
```

所以：

```
Python
```

本质上属于：

```
Zephyr 构建基础设施
```

。

------

## 6.5 为什么推荐 Python 3.12

当前 Zephyr 文档明确推荐：

```
Python 3.12
```

并提醒使用更高版本 Python 在部分系统，尤其 Windows 上，可能出现某些依赖包安装兼容性问题。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

所以教学环境不要使用：

```
“电脑上有什么 Python 就用什么”
```

。

应该固定：

```
Python 3.12.x
```

。

这样学生之间：

```
A：Python 3.11
B：Python 3.12
C：Python 3.14
```

产生环境差异的概率会小很多。

------

## 6.6 怎么确认 Python 安装成功

Windows PowerShell：

```
py -3.12 --version
```

或者：

```
python --version
```

可能输出：

```
Python 3.12.x
```

这里：

```
py
```

是 Windows Python Launcher。

：

```
-3.12
```

表示：

> 指定 Python 3.12。

：

```
--version
```

表示：

> 查看版本。

------

## 6.7 为什么不建议把所有 Python 包直接装进系统 Python

假设：

```
项目 A
Zephyr 4.4
```

需要：

```
package-x 1.x
```

几年后：

```
项目 B
Zephyr 5.x
```

可能需要：

```
package-x 2.x
```

如果所有项目都往：

```
C:\Python312\
```

里面安装：

```
pip install ...
```

久而久之很容易形成：

```
系统 Python
│
├── 项目 A 的包
├── 项目 B 的包
├── 其他 Python 工具
└── 各种不同版本依赖
```

然后某天：

```
升级项目 B
        ↓
pip 升级 package-x
        ↓
项目 A 开始出问题
```

。

因此 Python 提供了：

```
Virtual Environment
```

也就是：

```
虚拟环境
```

。

------

## 6.8 Python Virtual Environment 是什么

可以理解成：

```
系统 Python
C:\Python312\
       │
       ├───────────────┐
       │               │
       ▼               ▼
 Project A          Project B
 .venv              .venv
   │                  │
   ├── package A      ├── package X
   ├── package B      └── package Y
   └── west
```

两个项目各用各的。

不会轻易互相干扰。

Zephyr 官方 Getting Started 也明确推荐为 Zephyr 创建 Python virtual environment。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

------

## 6.9 创建我们的虚拟环境

假设：

```
D:\zephyr_hc32\
```

是整个教学环境。

可以：

```
cd D:\zephyr_hc32
```

然后：

```
py -3.12 -m venv .venv
```

逐项解释。

------

### `py -3.12`

表示：

```
使用 Python 3.12
```

。

------

### `-m`

表示：

> 运行一个 Python Module。

例如：

```
python -m pip
```

就是：

> 用当前 Python 运行 pip module。

------

### `venv`

这是 Python 自带的：

```
虚拟环境模块
```

。

------

### `.venv`

表示：

> 把虚拟环境创建到 `.venv` 目录。

所以：

```
py -3.12 -m venv .venv
```

翻译成人话就是：

> 使用 Python 3.12，在当前目录创建一个名为 `.venv` 的 Python 虚拟环境。

------

## 6.10 创建完成以后有什么

目录会变成类似：

```
D:\zephyr_hc32\
│
├── .venv\
│   ├── Scripts\
│   ├── Lib\
│   └── pyvenv.cfg
│
├── zephyr\
├── modules\
└── zephyr-sdk-1.0.1\
```

其中：

```
.venv\Scripts\
```

里面会有：

```
python.exe
pip.exe
Activate.ps1
```

。

------

## 6.11 激活虚拟环境

PowerShell：

```
.\.venv\Scripts\Activate.ps1
```

正常情况下命令行前面出现：

```
(.venv)
```

例如：

```
(.venv) PS D:\zephyr_hc32>
```

这表示：

> 当前 shell 优先使用 `.venv` 里的 Python 和 Python packages。

官方 Windows 指南也是这样激活虚拟环境的。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

------

## 6.12 激活到底修改了什么

激活并不是：

```
启动一个虚拟机
```

。

它主要是在当前终端环境里修改：

```
PATH
```

。

原来可能：

```
PATH:

C:\Windows\...
C:\Python312\...
```

激活以后类似：

```
PATH:

D:\zephyr_hc32\.venv\Scripts
C:\Windows\...
C:\Python312\...
```

于是输入：

```
python
```

Windows 首先找到：

```
D:\zephyr_hc32\.venv\Scripts\python.exe
```

。

------

## 6.13 怎么确认当前 Python 真的是虚拟环境的

PowerShell：

```
Get-Command python
```

应该显示类似：

```
D:\zephyr_hc32\.venv\Scripts\python.exe
```

再执行：

```
python --version
```

确认：

```
Python 3.12.x
```

。

------

## 6.14 什么是 pip

Python 自己是：

```
解释器
```

。

但是 Zephyr 还需要很多 Python Library。

比如构建脚本会依赖不同的 Python package。

负责安装 Python package 的工具通常就是：

```
pip
```

。

因此：

```
Python
│
└── pip
      │
      ├── package A
      ├── package B
      ├── package C
      └── west
```

。

------

## 6.15 `python -m pip` 和直接 `pip` 有什么区别

经常会看到：

```
pip install xxx
```

也会看到：

```
python -m pip install xxx
```

对于教学环境，我更推荐：

```
python -m pip
```

。

因为它明确表达：

> 使用“这个 python”对应的 pip。

例如：

```
系统有：

Python 3.11
Python 3.12
.venv Python
```

直接输入：

```
pip
```

你有时候需要判断：

```
这个 pip 到底属于谁？
```

而：

```
python -m pip
```

等于明确说：

```
当前 python
     ↓
运行它自己的 pip
```

。

------

## 6.16 Zephyr 的 Python 依赖又从哪里知道

前面我们对 C/C++ external module 使用：

```
west.yml
```

作为依赖依据。

Python 同样不能随便：

```
想起来什么就 pip install 什么
```

。

Zephyr 源码本身维护了对应的 Python requirements。

官方当前推荐使用：

```
west packages pip
```

读取 Zephyr 以及 Module 描述的 Python requirement，然后安装相匹配的依赖。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

但是我们当前有一个特殊条件：

```
第一阶段不依赖 west。
```

所以教学文档里最好明确区分两个模式。

------

## 6.17 模式 A：使用 west 管理 Python Requirements

以后启用了 west：

```
python -m pip install west
```

然后：

```
west packages pip --install
```

或者 Windows PowerShell 官方示例：

```
python -m pip install @((west packages pip) -split ' ')
```

由 west 帮我们：

```
读取 Zephyr requirements
+
读取 external modules requirements
        ↓
交给 pip 安装
```

。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

------

## 6.18 模式 B：我们的 ZIP First 环境

现在我们暂时不希望：

```
安装 west
        ↓
又不小心进入 west update
        ↓
开始访问大量 Git 仓库
```

。

实际上：

```
west
```

不是 CMake + Ninja 编译 Zephyr 的强制前置条件。

Zephyr 官方明确支持：

```
没有 west
        ↓
直接 CMake
        ↓
Ninja
```

只需要我们自己提供 Modules。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/without-west.html)

因此我们的第一阶段可以是：

```
Python
    ↓
Zephyr Python dependencies

CMake
    ↓

Ninja
    ↓

ARM GCC
```

而：

```
west
```

先不进入主链。

------

## 6.19 west 到底是什么

现在再解释 west，就不会把它误认为：

```
Zephyr 编译器
```

。

west 本质上是 Zephyr 的：

```
Meta Tool
+
Multi-repository Manager
+
Command Wrapper
```

官方称其为 Zephyr 的 meta-tool，并提供多 Git repository 管理能力，以及 Zephyr 自己扩展出来的 build、flash、debug 等命令。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/index.html?utm_source=chatgpt.com)

可以理解：

```
west
│
├── workspace 管理
│   ├── west init
│   ├── west update
│   └── west manifest
│
├── build 包装
│   └── west build
│
├── 烧录包装
│   └── west flash
│
└── 调试包装
    └── west debug
```

。

------

## 6.20 `west build` 自己会不会编译 C

不会。

例如：

```
west build
```

背后仍然是类似：

```
west
  │
  ▼
CMake
  │
  ▼
Ninja
  │
  ▼
arm-zephyr-eabi-gcc
```

。

所以：

```
west
```

更像：

> 一个统一的控制入口。

而不是编译器。

------

## 6.21 没有 west 能不能编译

能。

Zephyr 官方给出的 without-west 示例就是：

```
cmake -Bbuild -GNinja -DZEPHYR_MODULES=module1;module2 samples/hello_world

ninja -Cbuild
```

。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/without-west.html)

这对我们的教学非常重要。

说明：

```
west
```

和：

```
Zephyr Build System
```

不是完全绑定的。

所以我们的：

```
ZIP First Mini Environment
```

是有官方构建机制支持的。

------

## 6.22 但是不用 west 会失去什么

比如：

```
west flash
```

没有了。

：

```
west debug
```

也没有。

：

```
west update
```

自然也没有。

因为这些命令本身就是 west 提供的。

官方 without-west 文档明确指出，没有 west 时依然可以烧写和调试，但是需要自己直接调用 OpenOCD、pyOCD 等 Host Tool。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/without-west.html)

例如：

```
有 west：

west flash
    ↓
runner
    ↓
pyOCD
```

而我们第一阶段：

```
没有 west：

pyocd load zephyr.hex
```

直接调用底层工具。

------

## 6.23 这其实非常适合教学

因为学生会真正理解：

```
west flash
```

不是魔法。

它后面还是：

```
pyOCD
OpenOCD
J-Link
...
```

。

以后再引入：

```
west flash
```

他理解的是：

> west 帮我统一包装 Runner。

而不是：

> west 自己实现了 SWD。

------

## 6.24 CMake 又是什么

这是整个 Host 构建环境中最重要的工具之一。

但同样：

```
CMake != Compiler
```

。

它主要负责：

> **根据工程描述和配置，生成真正给构建工具使用的构建规则。**

比如我们的应用：

```
app/
├── CMakeLists.txt
├── prj.conf
└── src/
    └── main.c
```

其中：

```
CMakeLists.txt
```

可能只有：

```
cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})

project(my_app)

target_sources(app PRIVATE src/main.c)
```

当前 Zephyr `hello_world` 示例也采用这种典型结构。[GitHub](https://github.com/zephyrproject-rtos/zephyr/blob/main/samples/hello_world/CMakeLists.txt?utm_source=chatgpt.com)

------

## 6.25 CMake 做什么

例如：

```
cmake -B build -GNinja app
```

CMake 会分析：

```
app/CMakeLists.txt
Zephyr/CMakeLists.txt
Board
SoC
Kconfig
Devicetree
Toolchain
Modules
```

最后生成：

```
build/
├── build.ninja
├── CMakeCache.txt
├── CMakeFiles/
└── zephyr/
```

。

重点是：

```
CMake 的输出不是 MCU 固件。
```

而主要是：

```
“怎么编译”的规则
```

。

------

## 6.26 `cmake -B build` 是什么意思

拆开：

```
cmake
```

表示：

> 运行 CMake。

：

```
-B build
```

其中：

```
-B
```

可以理解为：

```
Build Directory
```

。

即：

> 生成出来的构建文件放到 `build` 目录。

于是源码：

```
app/
```

不会被：

```
.o
.a
elf
ninja 文件
缓存
```

弄得乱七八糟。

最终：

```
app/
├── CMakeLists.txt
├── prj.conf
└── src/

build/
├── build.ninja
├── CMakeCache.txt
└── zephyr/
```

。

这称为：

```
out-of-tree build
```

也就是：

> 构建产物与源码目录分离。

------

## 6.27 `-G Ninja` 又是什么

例如：

```
cmake -B build -G Ninja app
```

这里：

```
-G
```

表示：

```
Generator
```

。

意思是：

> CMake 最终给哪一种构建工具生成规则。

我们选择：

```
Ninja
```

所以：

```
CMake
    ↓
生成
    ↓
build.ninja
```

。

Windows Zephyr 官方开发流程使用 Ninja；Zephyr 文档也说明 Windows 上需要使用 Ninja，而 `west build` 默认也是使用 Ninja。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)

------

## 6.28 那 Ninja 又是什么

Ninja 可以理解成：

> **真正负责执行大量编译命令的构建执行器。**

例如 CMake 已经计算出：

```
main.c
    ↓
arm-zephyr-eabi-gcc

spi.c
    ↓
arm-zephyr-eabi-gcc

uart.c
    ↓
arm-zephyr-eabi-gcc
```

Ninja 就负责：

```
看看哪些文件需要重新编译
        ↓
安排编译任务
        ↓
并行调用 GCC
        ↓
最后调用 Linker
```

。

所以：

```
CMake
=
规划怎么编

Ninja
=
执行这个计划

GCC
=
真正把 C 变成机器码
```

。

这是非常重要的三层关系。

> ninja和make的区别：因为 **Zephyr 并不是“不能用 make”**，而是它的构建体系选择了 **CMake + Ninja 作为默认组合**。Linux 内核则是另一套历史和架构完全不同的构建体系：**Kbuild + Makefile + GNU Make**。
>
> Zephyr 官方目前明确支持 **Ninja 和 Make 两种后端**，只是 `west build` 默认使用 Ninja；Linux/macOS 下你完全可以切换成 `Unix Makefiles`。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)
>
> 最关键的是把这两套体系分开看：
>
> ```
> Linux Kernel
> ────────────────────────────
> Kconfig
> Makefile / Kbuild
>       │
>       ▼
>    GNU Make
>       │
>       ▼
>  gcc / clang
> ```
>
> 而 Zephyr 是：
>
> ```
> Zephyr
> ────────────────────────────
> Kconfig
> Devicetree
> CMakeLists.txt
>       │
>       ▼
>     CMake
>       │
>       ├──── 生成 build.ninja ───► Ninja
>       │
>       └──── 生成 Makefile ──────► Make
>                                    │
>                                    ▼
>                               gcc / clang
> ```
>
> 因此，**Ninja 并不是 Zephyr 必须使用的东西，而是 CMake 生成构建系统时默认选择的后端。**
>
> ------
>
> ### 为什么 Zephyr 更倾向 Ninja？
>
> 一个重要原因是：
>
> > **Zephyr 已经把复杂的“工程逻辑”交给 CMake 处理了。**
>
> 这时候 Ninja 不需要像 Linux 内核的 Makefile 那样承担大量复杂逻辑。
>
> Linux 内核的 Makefile/Kbuild 本身就在做很多事情：
>
> ```
> 判断 CONFIG_xxx
> 决定哪些 .c 编译
> 决定哪些目录进入
> 决定哪些对象组合
> 控制 built-in.a
> 处理模块
> 处理架构
> 处理 generated headers
> ……
> ```
>
> 例如 Linux 里经常看到：
>
> ```
> obj-$(CONFIG_SPI) += spi.o
> obj-$(CONFIG_I2C) += i2c.o
> ```
>
> Make/Kbuild 不仅是在“执行 gcc”，它本身就是 Linux 构建系统的重要逻辑层。
>
> 而 Zephyr 里类似的逻辑大量已经发生在：
>
> ```
> CMake
> Kconfig
> Devicetree
> Python生成脚本
> ```
>
> 这一层。
>
> 例如：
>
> ```
> zephyr_sources(main.c)
>
> zephyr_library_sources_ifdef(
>     CONFIG_SPI
>     spi.c
> )
> ```
>
> CMake 配置阶段已经算出来：
>
> ```
> main.c 要编译
> spi.c 要编译
> uart.c 不需要编译
> ……
> ```
>
> 最后生成一个非常明确的任务图给 Ninja：
>
> ```
> main.c ──gcc──► main.o ──┐
>                          │
> spi.c ───gcc──► spi.o ───┼──ld──► zephyr.elf
>                          │
> kernel.c ─gcc─► kernel.o ┘
> ```
>
> 这个时候需要的不是一个功能非常丰富的脚本系统，而更像一个：
>
> > **“拿着已经算好的依赖图，尽快执行任务”的工具。**
>
> 而这正是 Ninja 的设计目标。
>
> ------
>
> ### Ninja 比 Make 更“笨”，反而是它的优势
>
> 这个地方很有意思。
>
> GNU Make 很强。
>
> Makefile 可以：
>
> ```
> ifeq (...)
> endif
>
> $(shell ...)
> $(foreach ...)
> $(eval ...)
> $(call ...)
> ```
>
> 甚至可以在 Makefile 里面写大量逻辑。
>
> 所以：
>
> ```
> Make
> = 构建执行器
> + 一套功能比较强的构建描述语言
> ```
>
> 而 Ninja 故意把自己设计得比较简单。
>
> 它基本认为：
>
> ```
> 别让我思考工程该怎么构建。
>
> 你直接告诉我：
>
> A依赖B
> B用什么命令生成
> C依赖A和D
>
> 我负责最快把它跑完。
> ```
>
> 因此：
>
> ```
> CMake
> 负责“思考”
>
> Ninja
> 负责“干活”
> ```
>
> 两者配起来非常合适。
>
> ------
>
> ### 举一个很直观的例子
>
> 假设工程：
>
> ```
> main.c
> uart.c
> spi.c
> gpio.c
> ```
>
> 你选择：
>
> ```
> CONFIG_SPI=y
> CONFIG_UART=y
> CONFIG_GPIO=n
> ```
>
> Zephyr 配置阶段：
>
> ```
> Kconfig
>    │
>    ▼
> .config
>    │
>    ▼
> CMake
> ```
>
> CMake 最后算出来：
>
> ```
> main.c 需要
> uart.c 需要
> spi.c 需要
> gpio.c 不需要
> ```
>
> 于是生成类似：
>
> ```
> build main.o: cc main.c
> build uart.o: cc uart.c
> build spi.o: cc spi.c
>
> build zephyr.elf: link main.o uart.o spi.o
> ```
>
> Ninja 根本不用知道：
>
> ```
> CONFIG_SPI 是什么？
> CONFIG_GPIO 为什么关闭？
> Devicetree 是什么？
> HC32F4A0 是什么？
> Zephyr 是什么？
> ```
>
> 它只知道：
>
> ```
> 我要生成：
>
> main.o
> uart.o
> spi.o
>
> 然后链接 zephyr.elf。
> ```
>
> 这就是 Ninja 很适合作为 CMake 后端的原因。
>
> ------
>
> ## 那为什么 Linux 内核不换 Ninja？
>
> 这就不是简单一句“因为 Make 老”能解释的了。
>
> Linux 内核从很早开始，就建立了：
>
> ```
> Kbuild
> +
> Makefile
> +
> GNU Make
> ```
>
> 整套体系。
>
> 今天 Linux 内核里的 Make 已经不是单纯：
>
> ```
> gcc main.c
> ```
>
> 这种东西了。
>
> 整个内核源码树存在大量：
>
> ```
> Makefile
> Kbuild
> Kconfig
> scripts/Makefile.*
> arch/*/Makefile
> drivers/*/Makefile
> ```
>
> 例如：
>
> ```
> obj-$(CONFIG_USB) += usb/
> obj-$(CONFIG_SPI) += spi/
> obj-$(CONFIG_I2C) += i2c/
> ```
>
> 背后已经积累了几十年的构建逻辑。
>
> 所以 Linux 如果换成：
>
> ```
> CMake + Ninja
> ```
>
> 并不是：
>
> ```
> make
> 换成
> ninja
> ```
>
> 这么简单。
>
> 实际上得把：
>
> ```
> Linux Kbuild
> ```
>
> 整个重写。
>
> 相当于：
>
> ```
> 现有：
>
> Kconfig
>    ↓
> Kbuild / Makefile
>    ↓
> GNU Make
> ```
>
> 改造成：
>
> ```
> Kconfig
>    ↓
> 某个新的生成系统
>    ↓
> build.ninja
>    ↓
> Ninja
> ```
>
> 这会涉及内核所有：
>
> ```
> arch/
> drivers/
> fs/
> net/
> mm/
> kernel/
> security/
> tools/
> ……
> ```
>
> 因此收益未必值得这种巨大迁移成本。
>
> ------
>
> ## Zephyr 则不一样
>
> Zephyr 的现代构建架构从设计上就把：
>
> ```
> 工程描述
> ```
>
> 和：
>
> ```
> 构建执行
> ```
>
> 拆开了。
>
> 也就是：
>
> ```
>                 配置层
>                    │
>        ┌───────────┼───────────┐
>        │           │           │
>     Kconfig    Devicetree   CMakeLists
>        │           │           │
>        └───────────┼───────────┘
>                    ▼
>                  CMake
>                    │
>               生成构建图
>                    │
>                    ▼
>                  Ninja
>                    │
>               执行编译命令
>                    │
>                    ▼
>               GCC / linker
> ```
>
> 所以 Zephyr 很自然地可以选择一个专门负责“执行”的工具。
>
> ------
>
> ## Ninja 还有一个现实优势：并行构建和增量构建很快
>
> Ninja 的核心目标之一就是：
>
> > **大型工程下，非常低开销地计算“现在到底需要重新执行哪些任务”。**
>
> 例如：
>
> ```
> 10000 个源文件
>
> 你修改了：
>
> drivers/spi/spi_hc32.c
> ```
>
> Ninja 希望快速确定：
>
> ```
> 只重新编译：
>
> spi_hc32.c
>        ↓
> spi_hc32.o
>        ↓
> 相关 archive
>        ↓
> zephyr.elf
> ```
>
> 而不是在构建系统自身的解析阶段花很多时间。
>
> 这里要注意：
>
> > Ninja 并不是“生成出来的机器码比 Make 更快”。
>
> 最终：
>
> ```
> Ninja → gcc
> Make  → gcc
> ```
>
> 调用的可能完全是同一个 GCC。
>
> 差别主要在：
>
> ```
> 依赖图解析
> 任务调度
> 并行执行
> 构建工具自身开销
> ```
>
> ------
>
> ## 还有一个 Zephyr 特别重要的原因：跨平台
>
> Zephyr 不只是 Linux 用户在开发。
>
> 它大量用户运行在：
>
> ```
> Linux
> Windows
> macOS
> ```
>
> 而 Ninja 在这三种平台上的行为比较统一。
>
> Zephyr 官方文档目前说明，Linux/macOS 可以选择 Ninja 或 Make，而 Windows 构建路径使用 Ninja；`west build` 默认也是 Ninja。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)
>
> 因此：
>
> ```
> Windows:
>     CMake + Ninja
>
> Linux:
>     CMake + Ninja
>
> macOS:
>     CMake + Ninja
> ```
>
> 整个教程、CI、开发流程比较统一。
>
> 如果默认采用 GNU Make：
>
> ```
> Linux：
> GNU Make
>
> Windows：
> MSYS Make?
> MinGW Make?
> NMake?
> GNU Make?
> ```
>
> 事情就更复杂。
>
> ------
>
> # 你其实可以让 Zephyr 用 Make
>
> 例如官方支持：
>
> ```
> west build -b <board> -- -G"Unix Makefiles"
> ```
>
> 之后生成的就不是：
>
> ```
> build/build.ninja
> ```
>
> 而是：
>
> ```
> build/Makefile
> ```
>
> 然后底层：
>
> ```
> west
>   ↓
> CMake
>   ↓
> Makefile
>   ↓
> make
>   ↓
> gcc
> ```
>
> 甚至可以把 west 默认 generator 改掉：
>
> ```
> west config build.generator "Unix Makefiles"
> ```
>
> 官方文档也明确给出了这种方式。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/application/index.html?utm_source=chatgpt.com)
>
> 所以实际上：
>
> ```
> Zephyr + Ninja
> ```
>
> 不是一个强绑定关系。
>
> 更准确的是：
>
> ```
> Zephyr
>    ↓
> CMake
>    ↓
> 选择 Generator
>
>    ┌────────────┴─────────────┐
>    ▼                          ▼
> Ninja                      Unix Makefiles
>    │                          │
> ninja                       make
>    │                          │
>    └───────────┬──────────────┘
>                ▼
>               GCC
> ```
>
> ------
>
> ## 你可以这样理解 Linux 和 Zephyr 的根本区别
>
> 这比单纯记“Linux 用 Make，Zephyr 用 Ninja”重要得多：
>
> ```
> Linux：
>
> Make/Kbuild 自己就是构建系统的重要组成部分。
>
>               Kbuild
>                 +
>              GNU Make
>                 │
>                 ▼
>                GCC
> ```
>
> 而：
>
> ```
> Zephyr：
>
> CMake 才是主要的构建配置/生成系统。
>
>               CMake
>                 │
>         生成执行层描述
>                 │
>              Ninja
>                 │
>                 ▼
>                GCC
> ```
>
> 所以我会把前面那句话稍微修正成：
>
> > **Linux 内核选择 Make，是因为 Kbuild 本身就是建立在 GNU Make 之上的成熟构建体系。**
> >
> > **Zephyr 选择 Ninja 作为默认后端，是因为 Zephyr 把复杂的工程配置和依赖生成交给 CMake，Ninja 只需要高效执行 CMake 已经生成好的构建图。**
>
> 换句话说：
>
> ```
> Linux：
>
> Make 既参与“理解怎么构建”
> 又参与“执行构建”
>
>
> Zephyr：
>
> CMake：“怎么构建？”
> Ninja：“行，我执行。”
> GCC：“行，我编译。”
> ```
>
> 这也是为什么你接下来学 Zephyr 时，**CMake 比 Ninja 重要得多**。Ninja 通常你知道它“处于哪一层、为什么存在”就够了；真正经常需要理解和修改的是 `CMakeLists.txt`、Kconfig 和 Devicetree。

```

Devicetree
Board
Toolchain
    │
    ▼
  CMake
    │
    │ 生成
    ▼
build.ninja
    │
    ▼

    │

配置阶段的问题

```

这对排查问题非常有帮助。

## 6.30 DTC 又是什么

DTC：

```
Device Tree Compiler
```

也就是：

```
设备树编译器
```

。

Linux 驱动开发者对：

```
DTS
DTSI
DTB
```

应该比较熟悉。

但 Zephyr 同样大量使用 Devicetree 来描述：

```
Board Hardware
SoC Peripheral
Memory
GPIO
UART
SPI
I2C
Clock
Pin Control
```

等硬件信息。

## 6.31 Zephyr Devicetree 为什么需要 DTC

例如板级 DTS：

```
&uart1 {
    status = "okay";
    current-speed = <115200>;
};
```

或者：

```
&spi5 {
    status = "okay";
};
```

这些：

```
.dts
.dtsi
.overlay
```

并不能直接被 C Compiler 使用。

Zephyr 构建系统需要：

```
DTS
    │
    ▼
Devicetree processing
    │
    ├── DTC
    ├── Python
    └── Zephyr scripts
    │
    ▼
生成 C 可使用的信息
```

。

因此 DTC 是：

```
Build Host Tool
```

。

而不是：

```
运行在 MCU 上的程序。
```

------

## 6.32 DTC 和 Linux 内核中的 DTC 是不是同一个概念

是同一类工具和语法体系。

但使用结果有所不同。

Linux 常见：

```
board.dts
    ↓
dtc
    ↓
board.dtb
    ↓
Bootloader / Kernel
```

而 Zephyr 更偏向：

```
board.dts
    ↓
Zephyr build
    ↓
Devicetree information
    ↓
生成头文件 / 编译时配置
    ↓
直接编进 Firmware
```

。

所以不要简单理解为：

> Zephyr 启动以后再加载一个 DTB。

大多数 MCU Zephyr 场景不是 Linux 的那个运行时 DTB 模式。

## 6.33 DTC 到底从哪里来

有两种主要方式。

#### 方式一：Host 单独安装

例如 Windows：

```
winget install oss-winget.dtc
```

官方 Windows Getting Started 就把 DTC 作为 Host dependency 单独安装。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

#### 方式二：使用 Zephyr SDK 中的预编译 Host Tool

Zephyr 官方 Linux Host 文档也明确说明，可以使用 Zephyr SDK 自带的 DTC。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/installation_linux.html?utm_source=chatgpt.com)

所以：

```
DTC
```

和：

```
ARM Toolchain
```

虽然都可能来自 SDK，但角色完全不同。

## 6.34 为什么我仍然建议教学环境显式检查 DTC

也应该执行：

## 6.36 gperf 又是干什么的

官方 Host dependency 里面还会看到：

```
gperf
```

。

很多嵌入式开发者可能从来没直接用过。

GNU gperf 是一个：

```
Perfect Hash Function Generator
```

。

也就是：

> 根据一组关键字生成高效查找代码的工具。

Zephyr 某些构建流程会使用它。

这里没必要要求初学者学习 gperf 算法。

只需要知道：

```
gperf
```

属于：

```
Build-time Code Generation Tool
```

。

如果 Zephyr 某个模块需要它：

```
构建阶段调用
```

。

它：

```
不会运行在 HC32F4A0 上。
```

------

## 6.37 ccache 又是什么

另一个常见工具：

```
ccache
```

。

它不是必须项。

它解决的是：

> 重复编译相同内容时，能不能直接复用以前的编译结果。

例如：

```
第一次：

main.c
   ↓
GCC
   ↓
main.o


第二次内容完全相同：

main.c
   ↓
ccache
   ↓
发现以前编过
   ↓
直接拿 main.o
```

。

所以它是：

```
编译加速工具
```

而不是：

```
Zephyr 编译正确性依赖。
```

教学第一阶段可以不管。

## 6.38 wget 又是什么

```
wget
```

就是一个命令行下载工具。

例如：

```
wget https://...
```

用途和浏览器下载类似。

我们的教程恰恰因为国内网络问题，准备优先采用：

```
浏览器
企业镜像
下载器
离线包
```

所以：

```
wget
```

不是 Mini Environment 的核心组件。

它可以保留为：

```
辅助工具。
```

## 6.39 Git 在我们环境中的定位也应该重新定义

官方 Windows Host Dependencies 会直接安装 Git。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/getting_started/index.html?utm_source=chatgpt.com)

但我们的教程应该明确：

```
安装 Git
```

和：

```
必须用 Git 下载 Zephyr
```

是两个不同概念。

我们完全可以：

```

```

但是第一阶段：

```

。

```

。

## 6.40 west 也是一样

我们可以提前：

```

```

但是：

> **不等于必须执行 `west update`。**

这一点非常重要。

```

```

。

官方文档也说明 west 是 Python 3 编写并通过 PyPI 分发的。[Zephyr Project](https://docs.zephyrproject.org/latest/develop/west/install.html?utm_source=chatgpt.com)

```

```

## 6.41 所以可以安装 west，但不让它管理源码

这其实是一种可以考虑的中间模式：

+

但是：

```

。

这样以后可能逐步使用某些 west 能力。

因此我们的教学第一阶段更干净的方式还是：

```

Stage 2：

理解 west 后再安装
```

。

## 6.43 到底哪些需要加入 PATH

这是 Windows 教程必须讲清楚的问题。

假设某程序：

```
C:\Program Files\CMake\bin\cmake.exe
```

你每次如果都输入：

```
& "C:\Program Files\CMake\bin\cmake.exe"
```

当然可以。

但很麻烦。

如果：

```
C:\Program Files\CMake\bin
```

已经加入：

```
PATH
```

那么任何目录里都可以直接：

```
cmake
```

。

所以：

```
PATH
```

可以简单理解成：

> 操作系统寻找命令行程序的一组目录。

## 6.56 我们最终应该准备一个 `env.ps1`

因为每次手工设置：

```
$env:ZEPHYR_BASE = ...
$env:ZEPHYR_SDK_INSTALL_DIR = ...
$env:ZEPHYR_TOOLCHAIN_VARIANT = ...
```

很麻烦。

所以教学环境后面可以提供：

```
env.ps1
```

例如：

```
$Root = Split-Path -Parent $MyInvocation.MyCommand.Path

$env:ZEPHYR_BASE =
    Join-Path $Root "zephyr"

$env:ZEPHYR_SDK_INSTALL_DIR =
    Join-Path $Root "zephyr-sdk-1.0.1"

$env:ZEPHYR_TOOLCHAIN_VARIANT =
    "zephyr"

& (Join-Path $Root ".venv\Scripts\Activate.ps1")
```

先不用要求初学者马上理解全部 PowerShell。

后面可以专门解释。

最终他们只需要：

```
.\env.ps1
```

环境就准备好。
