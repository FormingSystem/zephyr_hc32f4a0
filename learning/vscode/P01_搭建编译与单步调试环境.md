# 1. 搭建编译与单步调试环境

## 1.1 插件、编译器和调试器各负责什么

VS Code 负责编辑与交互，扩展连接实际工具。CMake 生成规则，Ninja 执行构建，GCC 生成机器码；GDB 读取 ELF 中的符号并控制被调试程序。调试微控制器还需要 GDB server，把 GDB 请求转成探针操作。本项目使用 pyOCD 与 CMSIS-DAP。

| 用途 | 扩展 ID | 另行安装的程序 |
| --- | --- | --- |
| C/C++ 补全、主机 GDB 调试 | ms-vscode.cpptools | UCRT64 GCC、GDB |
| 普通 CMake 工程配置与目标选择 | ms-vscode.cmake-tools | CMake、Ninja、编译器 |
| Cortex-M 调试 | marus25.cortex-debug | SDK ARM GDB、pyOCD、探针驱动 |
| Python 解释器选择 | ms-python.python | Windows Python、本仓库 .venv |
| 设备树、Kconfig 辅助编辑 | plorefice.devicetree、luveti.kconfig | 实际检查仍由构建系统完成 |

扩展推荐不等于已经安装。根工作区已列工程需要的扩展；主机实验工作区单独推荐 C/C++ 和 CMake Tools。不要同时让多个语言服务为同一文件反复争抢诊断。

## 1.2 先在主机验证断点和单步

前提：[CMake P01](../cmake/P01_把源文件和库加入构建.md)已编译成功；终端能找到 UCRT64 的 gcc、gdb、cmake、ninja。从 UCRT64 Bash 启动编辑器，便于它继承这些工具路径：

```bash
code learning/vscode/tool-labs.code-workspace
```

打开 learning/cmake/labs/host/src/calibrate.c，在计算 corrected 的行按 F9 下断点。Ctrl+Shift+B 执行默认构建；运行和调试中选择主机 GDB 配置，按 F5。stopAtEntry 会先停在入口，再继续至断点。

观察 value=42；F10 执行当前行后 corrected=43。F11 进入函数，Shift+F11 返回调用者，F5 继续。不要在赋值语句尚未执行时把局部变量显示值当成结果。

工作区 tasks 将“配置 CMake”和“构建”建立依赖；launch 的 preLaunchTask 引用构建任务；program 指向生成的可执行文件；miDebuggerPath 指 gdb。改了程序路径时，这几处应一致。编译数据库让补全使用与编译器相同的参数，并不启动编译。

## 1.3 不依赖界面也能复核

```bash
gdb -q -batch -x learning/vscode/labs/inspect.gdb build/learning-tools/cmake-host/sensor_demo.exe
```

该命令文件依次 break calibrate、run、print value、next、print corrected、continue。预期观察 42、43，程序正常退出。Linux 去掉 .exe。断点灰色或未命中时检查是否加载了同一次 Debug 构建，源码是否与 ELF 对应，以及是否过度优化。

如果显示无法启动 gdb，先在启动 VS Code 的终端执行 gdb --version；安装扩展不会修好缺失的 GDB。若出现符号缺失，应修编译选项或程序路径，而非随意增加调试器参数。[VS Code 官方 MinGW 教程](https://code.visualstudio.com/docs/cpp/config-mingw)

## 1.4 当前 HC32 工程如何构建

打开根 zephyr_hc32f4a0.code-workspace，先按[工程环境](../../project-docs/environment.md)初始化。Ctrl+Shift+B 调用根 .venv 的 Python，再进入 project_env.py build。任务是 process 类型，不依赖 PowerShell 脚本。

C/C++ 读取 build/bringup/compile_commands.json；默认 Python 指向根 .venv。setup 将 SDK ARM 工具目录保存在忽略的 .vscode/settings.json 的 cortex-debug.armToolchainPath。UCRT64 终端配置若能被发现也写在本机设置中，不硬编码进公共工作区。新终端仍需激活 Python，或直接使用 .venv 的解释器。

根工程以明确的项目任务构建；安装 CMake Tools 不代表要让它另建一个不同目录/板目标。额外模块、设备树实验使用独立 build 目录，避免编辑器加载错误固件。

## 1.5 实板调试的连接顺序

以下步骤会连接硬件，先按[硬件记录](../../project-docs/hardware.md)接线。确认板上运行的固件与 build/bringup/zephyr/zephyr.elf 一致；ELF 含符号，BIN 不能替代调试符号文件。

```bash
source .venv/Scripts/activate
python scripts/project_env.py build
python scripts/project_env.py exec pyocd list
python scripts/project_env.py debug
```

debug 持续运行 GDB server；保留终端，再在 VS Code 选择 HC32 外部 pyOCD 附加配置。Cortex-Debug 用 ARM GDB 连接 localhost:3333，读取工程 ELF。它使用 attach，不自动烧录；若板上固件尚未下载或版本不匹配，应先按项目硬件流程处理，不能把“能连接”当成已运行新代码。

pyOCD 使用 debug/pyocd.yaml 指定目标、10 MHz SWD、禁止自动解锁，以及 HC32 SRAM 修正钩子。不要绕过配置直接启动默认服务。多个探针先用 list 获取编号，再给 debug 的 --probe 参数传真实编号。调试结束停止会话并终止服务；断点、暂停也会改变目标运行时序。

当前适合调试的配置片段见 [debug.conf](../board/labs/debug.conf)，通过 EXTRA_CONF_FILE 叠加。若调试独立目录的 ELF，要同步 launch.executable；不要仍指向 bringup 旧产物。

## 1.6 如何判断环境真正可用

主机实验完成“构建→命中断点→观察变量→继续退出”，可证明基本编辑器/调试操作。HC32 则还需实板连接、固件一致、命中目标函数等证据。QEMU 成功也不验证 SWD、Flash 或 PCB 接线。

本轮验收已运行底层构建与主机 GDB 命令；VS Code 图形界面按键流程和 HC32 实板附加尚未执行。读者应按以上观察点验收自己的机器。
