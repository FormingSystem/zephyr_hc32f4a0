# 1. 把源文件和库加入构建

## 1.1 为什么保存了 C 文件还没参与编译

你已经会写函数，本章只补齐构建工具的知识。CMake 读取 CMakeLists.txt，生成构建规则；Ninja 按规则调用编译器、链接器。CMake 的 target（构建目标）表示一个可执行文件或库，源文件必须归属某个目标，文件存在本身不建立这种关系。

头文件搜索路径只帮助编译器找到声明；链接时仍需要函数实现所在的目标文件或库。下面用主机程序把这两步分开观察，不需要 Zephyr、开发板或 SDK。前提是[实验准备](../P00_实验准备.md)以及 UCRT64 的 GCC、GDB、CMake、Ninja 可用；所有命令从仓库根目录执行。

## 1.2 先得到一个可观察的构建

源码在 [labs/host](labs/host/README.md)。main 调用 scale_sample 将 21 乘 2，再调用 calibrate 加 1，预期打印 value=43。

```bash
cmake -S learning/cmake/labs/host -B build/learning-tools/cmake-host -G Ninja -DCMAKE_C_COMPILER=gcc -DCMAKE_BUILD_TYPE=Debug
cmake --build build/learning-tools/cmake-host
ctest --test-dir build/learning-tools/cmake-host --output-on-failure
./build/learning-tools/cmake-host/sensor_demo.exe
```

-S 指定源码目录，-B 指定产物目录，-G 选择生成器。Debug 为主机实验保留调试信息并采用适合调试的优化设置。Linux 的执行文件名没有 .exe。CTest 是 CMake 的测试执行器，本例检查程序输出；预期 1/1 通过，程序打印 value=43。

查看 build 目录的 compile_commands.json：它记录每个 C 文件的真实编译参数，编辑器也用它理解 include 和宏。再次构建应报告无工作；改 calibrate.c 后，只需重新编译相关对象并重新链接。

## 1.3 新增一个源文件应该改哪里

实验的主目标使用：

```cmake
add_executable(sensor_demo src/main.c)
target_include_directories(sensor_demo PRIVATE include)
target_sources(sensor_demo PRIVATE src/calibrate.c)
```

add_executable 建目标，target_sources 加实现，target_include_directories 加声明查找目录。PRIVATE 表示只对本目标生效。

练习：新增 src/limit.c 与 include/limit.h，实现自己的整数限幅函数，在 main 调用；把 limit.c 加入 sensor_demo 的 target_sources。重新构建，确认 compile_commands.json 出现 limit.c，再改输入值验证输出。若改了预期输出，也要有意识地调整 CTest 的断言，不能把错误输出直接当成新的正确结果。

通常显式列源文件更利于审查“本次新增什么会被编译”；文件 glob 自动搜集容易把实验或备用文件意外加入。小工程先用明确列表，无须一开始建立复杂生成系统。

## 1.4 子目录与库如何接入

模块在 modules/scale。上层：

```cmake
add_subdirectory(modules/scale)
target_link_libraries(sensor_demo PRIVATE scale)
```

子目录用 STATIC 这个库类型关键字声明静态库；PUBLIC 是使用要求范围关键字，表示同时给库自身与调用者使用：

```cmake
add_library(scale STATIC src/scale.c)
target_include_directories(scale PUBLIC include)
```

add_subdirectory 让 CMake 执行子目录规则；add_library 创建静态库；target_link_libraries 建立链接和使用要求依赖。仅进入子目录不代表主程序会链接该库。

PUBLIC 的 include 同时给 scale 自己和链接它的调用者使用；PRIVATE 只给自己；INTERFACE 只给调用者。把公共头文件路径绑定在库上，主程序便不必知道库内部目录。这种做法也适用于非嵌入式项目。

## 1.5 故意漏一个实现，看错误发生在哪一步

在独立目录配置本例预留的故障开关：

```bash
cmake -S learning/cmake/labs/host -B build/learning-tools/cmake-missing -G Ninja -DCMAKE_C_COMPILER=gcc -DLESSON_OMIT_CALIBRATION=ON
cmake --build build/learning-tools/cmake-missing
```

预期配置成功、main 编译成功、最终链接报告 calibrate 未定义。这证明头文件已找到，但实现未加入。恢复：

```bash
cmake -S learning/cmake/labs/host -B build/learning-tools/cmake-missing -DLESSON_OMIT_CALIBRATION=OFF
cmake --build build/learning-tools/cmake-missing
ctest --test-dir build/learning-tools/cmake-missing --output-on-failure
```

若报 scale.h 找不到，查 include 使用要求；若 CMake 报 target 不存在，查创建顺序和名称；若换编译器或生成器，另建 -B 目录，不复用旧缓存。需要看完整命令时用 cmake --build 后加 --verbose。

## 1.6 回到当前工程

[samples/bringup/CMakeLists.txt](../../samples/bringup/CMakeLists.txt) 在 find_package(Zephyr) 后得到名为 app 的目标。新增应用文件时可加 `target_sources(app PRIVATE src/new_feature.c)`，声明自己的目录用 target_include_directories；不要编辑 build 下生成的 Ninja 文件。

一般业务文件属于 app；可复用的 Zephyr 模块有自己的发现入口，见[下一章](P02_接入Zephyr模块.md)。驱动集成还涉及驱动 Kconfig/CMake 条件，不能把所有文件塞进 app 来绕过驱动框架。

完成标志：你能从编译数据库找到新文件，解释头文件与链接错误的区别，且故障开关恢复后 CTest 通过。清理仅涉及本章两个 build/learning-tools 子目录；源码修改按练习需要保留。

依据：[CMake 官方入门](https://cmake.org/cmake/help/latest/guide/tutorial/index.html)、[target_link_libraries 使用要求](https://cmake.org/cmake/help/latest/command/target_link_libraries.html)、[Ninja 手册](https://ninja-build.org/manual.html)。
