# 5. 团队工作流与故障定位

实验已经覆盖获取、版本、配置和扩展。**west** 负责按清单协调仓库，**清单（manifest）** 记录配套声明；团队交付还要保证引用的对象别人能取得，开发状态和声明一致。本章把已有动作组成可迁移的协作流程，并用一个新增项目练习检验是否掌握。

## 5.1 清单放在哪个仓库

同一份清单机制可以对应不同工程布局。不要先记某种拓扑的缩写，先问“谁负责决定整体版本组合”。

| 清单拥有者 | 适合的职责 | 需要承担的维护工作 |
| --- | --- | --- |
| 核心框架仓库 | 随框架发布一套默认依赖 | 产品要跟随或另外覆盖框架的组合 |
| 应用仓库 | 应用版本直接决定依赖组合 | 应用变更与清单变更一起审查 |
| 独立清单仓库 | 同时协调多个应用与公共库 | 发布时额外记录清单仓库自身版本 |

本教程使用第三种，便于看清角色。真实项目中仓库名可以变化，顶层清单仓库“由 Git 手动管理版本、普通项目由 update 同步”的区别始终要保留。[West Workspaces](https://docs.zephyrproject.org/latest/develop/west/workspaces.html)给出官方布局讨论。

只有一个仓库时通常不必为了统一命令先拆成多个。**单仓库（monorepo）** 是将协作代码放进一个 Git 历史的组织方式；**Git 子模块（submodule）** 是在父仓库中记录另一仓库位置和提交的 Git 机制。west 将多个平级项目组合写进专门清单；选择依据是版本关系、团队边界和维护成本，不是代码是不是嵌入式。[Git 子模块文档](https://git-scm.com/book/en/v2/Git-Tools-Submodules)可用于进一步比较。

## 5.2 日常命令的先后关系

在明确的工作区内，先运行查询命令，再决定是否有更新需求：

```text
west topdir
west list -f "{name}: {revision} -> {path}"
west status
west diff
west compare
west forall -c "git status --short"
```

`status` 检查本地修改，`diff` 展示差异；`compare` 用于比较工作区与清单基线；`forall` 在选中的仓库分别执行命令。它们的结果不能相互替代：工作树干净仍可能检出了别的提交。`forall` 的参数会交给 shell 执行，适合明确的批量查询，不要把批量破坏性清理当成标准开工流程。

| 动作 | 什么时候做 | 完成后检查什么 |
| --- | --- | --- |
| `west init` | 建立一个新工作区 | topdir 与清单来源 |
| `west update` | 接受清单版本变化或补齐项目 | 实际提交、必要的应用测试 |
| `git switch -c ...` | 在某个项目开始开发 | 分支归属和未提交状态 |
| 修改清单并审查差异 | 让修复/升级成为团队配套版本 | 地址可访问、revision 正确、有效项目集合 |
| `west manifest --freeze --active-only` | 导出当前同步基线证据 | 与 manifest-rev 的对应，不遗漏本地补丁 |

普通开发不需要每次重新 init 或升级全部工具。接收清单仓库的新版本后，再按需要 update 并验证。更新多个项目不是一个全局事务：前两个成功、第三个失败时，前面的变更不会自动回滚；修复失败条件后重新同步并检查整个集合。

## 5.3 把本地修复交给团队的步骤

第一步在被修改项目上创建自己的分支并提交修复，测试它。第二步让提交存在于团队可访问的仓库；只有本机分支名不足以交付。第三步修改清单的获取地址或 revision，提交清单变化；最后从一份新工作区获取并执行验证。

使用分支名做 revision 便于持续跟踪，但同一清单明天可能解析到不同提交。标签便于阅读，仍依赖组织不重写标签；完整提交标识更明确。发布时优先审查固定对象，而不是把每日同步滚动分支等同于发布控制。

**HEAD** 是 Git 当前检出位置的特殊引用名称，不是需要展开英文全称的缩写。一个可追溯的交付至少记录清单仓库的地址和提交、有效清单、活动筛选、各项目实际 HEAD 和脏状态、Python 工具环境、编译工具链及测试命令。west 的冻结文件只覆盖其负责的源码版本层，不是 Python 包、编译器和构建选项的完整锁文件。源码可追溯、可重新构建、二进制逐字节一致也是不同验收目标。

为了让配置变化可审查，团队必须一致的参数优先放在受版本管理文件或脚本；用户偏好留在本地配置。新增本地便捷设置时，项目文档写清检查方法和取消方式，避免只有某个终端能构建。

## 5.4 按层定位失败

| 症状 | 用已有模型解释 | 第一个检查与修复方向 |
| --- | --- | --- |
| 找不到 west / 没有 west 模块 | 当前 Python 环境没有工具或命令路径不匹配 | 确认解释器，用该解释器 `-m pip show west` |
| 找不到工作区 | 当前目录没有正确祖先定位关系 | 检查路径、`west topdir`、遗留环境变量；进入正确工作区 |
| 重复初始化失败 | 该目录已有工作区，或当前目录处于其他工作区内 | 不删除未知 `.west`；查询定位，换全新实验目录 |
| 清单解析失败 | 缩进、字段、导入或格式版本不合法 | `west manifest --validate`，恢复最近一次修改 |
| Git 地址或 revision 获取失败 | 地址、凭据、网络、对象存在性之一不成立 | 查看失败项目的 url/revision，单独检查源仓库可访问性 |
| 更新后代码看似不变 | 清单固定旧提交、停用项目或不是预期工作区 | list 活动状态并比较 HEAD/manifest-rev |
| update 切换失败 | 未提交修改与检出目标冲突等 Git 条件 | 保存修改、检查 `git status`，不用清空整个工作区代替分析 |
| 扩展命令未知 | 声明未加载、提供者未获取或被禁用 | `west help`、扩展描述文件与 `commands.allow_extensions` |
| freeze 报未克隆项目 | 试图冻结尚无 Git 基线的项目 | 核实活动范围，按需要获取或使用已支持的 active-only |
| Python 包导入失败 | 工具依赖与源码同步属于不同层 | 在实际运行解释器中检查 pip，而不是重复 update |

若在某个真实 Zephyr 工作区，`build` 已被识别但 CMake、配置检查、编译或链接失败，应继续检查对应层的输入和日志。west 的存在不能把这些错误都变成 west 安装问题。本项目使用哪个构建目标和工具版本，由项目文档单独记录。

## 5.5 综合实验：增加一个自己的仓库

前提：原 demo-01 工作区正常，已理解 Git 分支与本地提交。本练习只增加本机数据，不推送远端。

1. 在 `demo-01/remotes/checklist/` 初始化新 Git 仓库，创建 `README.md`，写入自己的项目检查清单，提交并打标签 `v1.0`。可沿用 P02 的单次 `-c user.name` 与 email；无需修改全局身份。
2. 在顶层清单加入 name 为 checklist、url 为 `../../../remotes/checklist`、revision 为 v1.0、path 为 tools/checklist 的完整条目。此 url 从消费副本 workspace/tools/checklist 出发解析，不是从清单文件出发。
3. 运行 `west manifest --validate` 和 `west list checklist`。预测此时磁盘是否已有副本，再 `west update checklist` 并读取克隆后的文件。
4. 给它增加 `groups: [checks]`，本地停用 checks。用 `west list -a` 和磁盘目录验证“停用不删除”。
5. 恢复活动，使用 P04 的 inventory 报告检查集合；修改源仓库产生 v2.0，再通过清单接受升级。

参考验收：validate 成功只说明声明合法；第一次 list 能看见未克隆项目；update 后文件出现；组停用后目录仍在；源仓库新增版本不会自动改变固定 v1 的消费副本，只有改变清单并更新后才接受 v2。最后审查清单差异，保存有价值的实验，或删除自己生成的整个实验目录。

## 5.6 从通用知识回到本项目

回到本项目时，先确定 Python 工具环境和源码工作区的实际位置，再读取真实清单，确认顶层拥有者、项目集合与修订，最后查扩展和构建入口。把结果写入 [project-docs/west/](../../project-docs/west/README.md)，通用解释继续链接本教程。

目前本仓库没有正式 west 清单，因此这里不指定产品修订、板名或烧录参数。你已经能够独立建立和解释这些工具关系，后续项目接入可基于事实记录，而无需把某一份 Zephyr 示例的路径当成通用规则。
