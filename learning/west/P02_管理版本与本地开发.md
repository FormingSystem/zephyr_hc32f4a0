# 2. 管理版本与本地开发

第一次更新后，应用已经能调用算术库。但“文件存在”并不保证后续升级时仍使用配套版本。**west** 是按清单协调 Git 仓库的工具；**清单（manifest）** 记录希望使用的版本。本章在同一个实验工作区中，把希望、同步结果和实际开发位置分开观察，并从冻结文件重建第二份工作区。

## 2.1 四个版本对象不要混用

当前位置：P01 建立的 `build/learning-tools/west/demo-01/workspace/`，教学工具环境仍可用。

**revision** 是清单字段，值可以是分支、标签或提交标识。**manifest-rev** 是 west 在普通项目仓库里维护的 Git 引用名称，记录最近同步解析出的提交。**HEAD** 是当前检出的 Git 位置；本地开发分支是开发者维护的引用，不由清单自动吸收。

```text
west list arithmetic -f "{name}: wanted={revision}, path={path}"
git -C libs/arithmetic rev-parse HEAD
git -C libs/arithmetic rev-parse manifest-rev
git -C libs/arithmetic status --short --branch
```

第一次同步后两个提交标识应相同，清单仍显示 `v1.0`。**游离头状态（detached HEAD）** 指当前检出直接指向提交而不是某个本地分支；它适合消费固定依赖，不表示仓库损坏。`manifest-rev` 由 west 控制，不要在它上面进行日常开发。

**SHA（Secure Hash Algorithm）** 是散列算法家族名；Git 文档常把提交对象的散列标识简称 SHA。本教程比较完整提交标识，不硬编码每次随机实验产生的值。相同源文件内容并不保证实验提交标识相同，提交时间等也参与对象身份。

## 2.2 从第一版升级到第二版，再退回

打开 `manifest/west.yml`，只把 `name: arithmetic` 对应的 `revision: v1.0` 改成 `revision: v2.0`，其他条目保持原值。还没执行更新时，先运行上一节观察命令：清单希望 v2，但实际文件仍为 v1。

```text
west manifest --validate
west update arithmetic
git -C libs/arithmetic rev-parse HEAD
git -C libs/arithmetic rev-parse manifest-rev
python -c "import sys; sys.path.insert(0, 'libs/arithmetic'); from arithmetic import multiply; print(multiply(2, 3))"
python app/main.py
```

预期乘法输出 `6`，原应用仍输出 `2 + 3 = 5`。`sys.path.insert` 是本例显式加入导入目录的写法，不代表 west 自动替应用配置 Python 搜索路径。

再把 arithmetic 的 revision 改回 `v1.0` 并 `west update arithmetic`；乘法导入应失败，但原应用仍成功。恢复为 v2 并更新，供后续实验使用。这说明 update 根据声明移动，既可能向前也可能向后，不等于“把所有仓库拉到最新版”。

默认 update 的过程是：解析 revision→按需要 fetch 获取 Git 对象→移动 manifest-rev→检出该提交。它不会按每个本地分支的上游关系执行 `git pull`，也不会更新顶层清单仓库自身。清单仓库的版本切换由开发者使用 Git 管理。

官方对照：[west update](https://docs.zephyrproject.org/latest/develop/west/built-in.html#west-update)；安装版本的 `west update -h` 也逐项说明该流程。

## 2.3 在依赖里开发时先建立自己的分支

我们要给算术库添加开发备注，证明自己的提交和同步基线可以不同。先检查修改，再建立分支；下列提交只发生在实验库，不是本教程仓库。

```text
west status
west diff
git -C libs/arithmetic switch -c learning/local-note
```

手动在 `libs/arithmetic/` 新建 `LOCAL_NOTE.md`，写一行 `Local development experiment.`，然后：

```text
git -C libs/arithmetic add LOCAL_NOTE.md
git -C libs/arithmetic -c user.name="Learning Lab" -c user.email="learning@example.invalid" -c commit.gpgsign=false commit -m "Add a local development note"
git -C libs/arithmetic rev-parse HEAD
git -C libs/arithmetic rev-parse manifest-rev
git -C libs/arithmetic log --oneline manifest-rev..HEAD
```

此时 HEAD 前进了一次，manifest-rev 仍是 v2，差集日志应显示备注提交。命令中的 `-c` 只为本次 Git 调用提供教学身份，真实项目使用自己的提交身份和团队规范。

普通 `west update arithmetic` 默认会离开该开发分支并回到清单版本，但分支本身仍保留；`git -C libs/arithmetic switch learning/local-note` 可重新检出。更新前必须检查并保存未提交的变更，不能假定任何脏工作树都能顺利切换，也不要把批量清空仓库当作更新前置步骤。

`west update -k` 仅在本地分支是新基线后代等满足条件时保留检出；`-r` 尝试把本地提交变基到新基线，可能产生冲突。先掌握默认行为，再有意选择这些策略。它们不等于将补丁发布给团队。

## 2.4 冻结的不是任意当前 HEAD

**展开（resolve）** 将清单导入合成为一份声明；**冻结（freeze）** 在本次 west 1.5.0 中把普通项目 revision 换成最近 manifest-rev 的完整提交标识。它不把未提交文件或任意开发 HEAD 自动加入发布。

保持上一节 `learning/local-note` 分支已检出，执行：

```text
west manifest --resolve --active-only -o ../west-resolved.yml
west manifest --freeze --active-only -o ../west-frozen.yml
git -C libs/arithmetic rev-parse HEAD
git -C libs/arithmetic rev-parse manifest-rev
```

打开 `../west-frozen.yml`，arithmetic 的 revision 应等于 manifest-rev，而不是包含备注的新 HEAD。`--active-only` 只处理活动项目，避免尚未克隆的可选文档影响冻结；当前基线 1.5.0 支持该选项，使用别的版本先查帮助。

冻结是一个导出操作，不会自动替换当前清单。它也不完整锁定顶层清单仓库自身；发布还需记录其提交、工作树是否干净、有效分组配置以及工具版本。想把本地补丁纳入团队基线，应先让提交在团队可访问的仓库存在，再将清单明确指向该提交，更新并验证，而不是仅保存一个 freeze 输出。

官方对照：[Freezing Manifests](https://docs.zephyrproject.org/latest/develop/west/manifest.html#freezing-manifests)。对这一容易混淆的规则，本教程还以“开发 HEAD 已前进”的实验验证，而不只对比两个本来相等的值。

## 2.5 从冻结文件重建工作区

继续在原 workspace 执行，`../replay/` 必须不存在。先从顶层清单仓库复制它的受版本管理文件，再用冻结文件替换副本中的清单。UCRT64 Bash：

```bash
git clone ./manifest ../replay/manifest
cp ../west-frozen.yml ../replay/manifest/west.yml
(cd ../replay && python ../../../../../learning/west/labs/init_workspace.py -l manifest && west update && python app/main.py && git -C libs/arithmetic rev-parse HEAD)
```

预期新工作区应用成功，arithmetic 为冻结的 v2 提交，没有 `LOCAL_NOTE.md`。replay 与原 workspace 位于同一层，因此相对地址仍能找到兄弟目录 remotes。将整个 demo-01 复制到另一位置时，只要保留这组相对层次和 Git 对象，就可以继续实验；不要只拿走冻结文件而丢掉本地源仓库。团队跨机器协作则通常使用可访问的正式 Git 地址。

冻结覆盖了受管项目版本；这里覆盖文件后尚未提交的清单副本只是练习，不是完成发布。清理 replay 不影响原 workspace；删除整个 demo-01 会使其中所有本地源地址失效。
