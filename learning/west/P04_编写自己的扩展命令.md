# 4. 编写自己的扩展命令

目前已经能获取和配置仓库。团队接着希望每个人都用同一条命令报告“哪些依赖活动、哪些还没下载”。**west** 的核心管理命令已经提供基础信息，**扩展命令（extension command）** 则允许仓库自带 Python 实现，把项目专属操作接入同一入口。本章从实验附带的只读命令入手，不要求先通读 Python 语言教程。

## 4.1 命令怎样从仓库进入帮助列表

当前位置：原 `demo-01/workspace/`，默认只启用 app 与 arithmetic。**inventory** 是本实验自定义的命令名，表示项目清单报告；不是 west 内建命令。运行：

```text
west help
west inventory -h
west inventory
west inventory --format json
west inventory --require-cloned
```

默认文字输出应列出两个项目及路径、revision、cloned 状态。**JSON（JavaScript Object Notation）** 是结构化数据格式，本命令用它提供适合程序读取的列表。输出中的 revision 是清单文本，cloned 表示本地 Git 仓库是否存在，均不等于应用已经构建成功或 HEAD 已与基线相同。

扩展发现链在本例中是：

```text
.west/config 定位 manifest/west.yml
  → self.west-commands 指向 west-commands.yml
  → 描述文件把 inventory 映射到 commands/inventory.py 中的 Inventory
  → west 创建类实例，解析参数，再执行命令方法
```

描述文件的 `file` 路径相对于提供扩展的仓库根目录，本例是 manifest 仓库。命令名、文件路径和类名必须对应。官方对照：[Adding a West Extension](https://docs.zephyrproject.org/latest/develop/west/extensions.html#adding-a-west-extension)。

## 4.2 读懂完整实现的三个职责

打开实际运行副本 `manifest/commands/inventory.py`；教材原件是 [inventory.py](labs/templates/commands/inventory.py)。它使用 **WestCommand** 基类，这是 west 提供的扩展编程接口；可用 C++ 的“继承框架类并实现回调”来理解控制方向，但参数和状态以 Python 对象传递。

`__init__` 构造实例并声明名字、短帮助和完整描述。它不做克隆或打印报告，避免把副作用塞入命令准备阶段。

`do_add_parser` 向 **参数解析器（argument parser）** 登记选项并返回解析器。`--format` 的 choices 只接受 text/json；`--require-cloned` 是布尔开关。框架先完成解析，因此不合法参数无需在业务循环中重复判断。

`do_run` 取得解析后的 `args` 和框架提供的清单对象 `self.manifest`。`projects` 是清单项目序列，其中也有顶层 manifest 对象；实验主动排除这个特殊对象，只报告依赖项目。`is_active` 根据有效过滤规则判断活动性，`is_cloned` 检查 Git 副本是否存在。代码把每个项目转成 name/path/revision/cloned 的小字典，随后按格式输出。

`self.inf` 是 west 的信息输出方法；`self.die` 报错并以非零状态结束。先检查缺失项目再打印报告，使 `--require-cloned` 的失败不会产生一份看似完整的成功报告。该方法不修改清单或下载代码，因此可以用于自动化前置检查。

代码中的局部变量 rows/projects 只保存这一轮调用的数据；每次 `west inventory` 都是新调用，会重新读取当前清单。`unknown_args` 是框架回调参数，本命令不接受未登记的额外选项，依赖基类默认处理。这里不使用 shell 字符串拼接执行外部命令。

## 4.3 修改一个输出选项

完整修改参考为 [inventory_count.py](labs/solutions/inventory_count.py)，含所有类方法与错误分支；[实训第 8 节](<labs/README.md#8. 修改扩展命令，理解注册与执行的关系>)提供复制、对照差异和失败恢复命令。先理解下面两处修改的位置，再与完整文件比较，不把参考文件当成无需阅读的黑盒。

我们希望快速取得活动项目数量。修改运行副本，在 `do_add_parser` 的 `return parser` 之前加入：

```python
parser.add_argument("--count", action="store_true",
                    help="Print the number of active projects")
```

在 `do_run` 的缺失检查之后、原来的格式输出之前加入：

```python
if args.count:
    self.inf(str(len(rows)))
    return
```

`--count` 是本次新设计的选项，计数只覆盖活动依赖，不含清单仓库。选择放在缺失检查之后，是为了保留 `--require-cloned` 的保证；如果提前 return，该保证会被绕过。这就是一个小修改也需要考虑的控制流不变量。

```text
west inventory --count
west inventory --count --require-cloned
west inventory --format invalid
```

默认组配置下前两条应输出 `2`。最后一条是故意失败，参数解析器拒绝 invalid；Bash 用 `echo $?` 检查退出码，应非 0。该修改只改顶层清单仓库内的 Python 文件，下一次调用就生效，不需要重新安装 west，也不需要 update。

不要同时修改教材原件与实验副本来寻找“哪个会生效”；本次运行的是工作区内副本。要把改进纳入教材或产品，应另外审查并同步到权威源文件。

## 4.4 验证缺失与禁用两个失败分支

如果前一章已下载 guide，本工作区已无法演示“活动但未克隆”。可另用生成器建立 `demo-missing`，在新 workspace 完成 `west init -l manifest`，**先不执行 update**：

```text
west inventory
west inventory --require-cloned
west update
west inventory --require-cloned
```

第一次普通报告应显示 cloned=False；严格检查失败并提示先 update；更新后成功。它证明“能读取清单”与“源码已准备好”是两种状态。新工作区没有上一节 --count 的修改，这是正常的副本差异。

回到原 workspace，观察开关：

```text
west config --local commands.allow_extensions false
west inventory
west config --local commands.allow_extensions true
west inventory
west config --local -d commands.allow_extensions
```

禁用时自定义命令不可执行，但 `west config` 仍是内建命令，可重新启用；最后删除临时开关，恢复原有覆盖关系。若用户级本来禁用扩展，最后删除后仍会禁用，应遵循团队政策保留必要的本地明确配置。

执行扩展就是执行仓库提供的代码；它可以拥有当前进程的文件与网络权限。给团队加入扩展时像审查构建脚本一样审查代码与参数边界，不把描述 YAML 视为全部行为。正式扩展产生副作用时，还应明确输入、执行位置、失败返回和恢复方式。

## 4.5 为什么安装 west 后不一定有 build

`init`、`update`、`list`、`config` 等管理命令随 west 工具提供。Zephyr 的 `build`、`flash`、`debug` 则由它的仓库扩展提供。在本实验执行 `west build -h` 找不到命令是预期结果，不是安装损坏。

当回到真实项目时，先用 `west help` 看命令归属，再找清单声明和实现文件。若要统一团队的构建或报告入口，可以添加扩展；若只有一个简单脚本且不依赖工作区上下文，直接运行脚本也很合理。扩展不会替代底层编译器、调试服务器或构建系统。

清理修改前，使用 `git -C manifest diff` 检查 --count 和描述文件的变化。只有自己本节的练习修改且无需保留时，才将对应文件恢复；新实验目录可整体另行清理。下一章把这些模型组织成团队日常流程。
