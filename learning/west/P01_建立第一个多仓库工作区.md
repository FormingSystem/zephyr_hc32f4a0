# 1. 建立第一个多仓库工作区

一个嵌入式产品可能把应用、协议库和厂商适配层放在不同 Git 仓库。逐个 clone 能拿到文件，却没有回答“这一版应用究竟配哪一版库”。本章先用两个很小的普通软件仓库建立配套关系，不涉及编译器、硬件或 Zephyr 构建。完成后你能从一份清单得到正确目录和版本，再实际运行它们。

## 1.1 west 管的是哪一层

**west** 是工具名称，核心职责是按声明协调多个 Git 仓库。**清单（manifest）** 是这份声明，记录仓库的获取地址、版本和本地位置。**清单仓库（manifest repository）** 保存清单及其历史；**项目仓库（project repository）** 是清单管理的其他仓库；**工作区（workspace）** 是包含这些仓库与 `.west/` 元数据的目录范围。

用 Git 术语作最小对齐：**提交（commit）** 是保存的历史快照，**分支（branch）** 是可前进的提交引用，**标签（tag）** 常用于标记版本，**HEAD** 是 Git 表示当前检出位置的特殊名称。west 使用这些对象，不替代 Git 的历史模型。

本次生成的布局如下，图中 `remotes/` 只是实验源仓库目录名，即使在本机也可以作为获取来源：

```text
build/learning-tools/west/demo-01/
  remotes/                    模拟各团队已发布的源仓库
    app/                      应用 v1.0
    arithmetic/               算术库 v1.0、v2.0
    guide/                    可选文档 v1.0
  workspace/                  实际执行 west 的工作区
    .west/config              init 生成的本地定位配置
    manifest/                 清单仓库，生成器事先准备
      west.yml
      west-commands.yml
      commands/inventory.py
    app/                      update 获取的应用副本
    libs/arithmetic/          update 获取的库副本
```

工具所在的 Python 环境可以在工作区之外；一个工作区也不是一个大 Git 仓库。`.venv` 一类目录保存 Python 工具依赖，`.west` 记录 west 的定位和配置，各仓库的 `.git` 保存自己的历史。它们不会因为都以点开头就承担相同职责。

官方对照：[west Basics](https://docs.zephyrproject.org/latest/develop/west/basics.html)。文档由 Zephyr 项目维护，核心工作区模型并不要求工作区中必须有 Zephyr。

## 1.2 安装并确定正在使用的 west

当前位置：本仓库根目录。先创建教学工具环境，避免修改系统 Python。UCRT64 Bash：
先完成[准备章](../P00_实验准备.md)的解释器选择与 MSYS 参数设置，尤其不要混用两套 Python 的环境路径。

```bash
py -3.12 -m venv build/learning-tools/tools
build/learning-tools/tools/Scripts/python.exe -m pip install -r learning/requirements-tools.txt
source build/learning-tools/tools/Scripts/activate
python -c "import sys; print(sys.executable)"
west --version
git --version
```

已按验证说明建立此环境时可以复用。预期 west 版本为 `v1.5.0`；首次安装需要网络或团队离线包目录。若不想激活，后文每个 `west ...` 都可替换为工具环境解释器完整路径加 `-m west ...`，每个 `python ...` 也用同一完整路径。激活不是 west 工作区初始化。

## 1.3 准备源仓库，然后亲手初始化

仍在本仓库根目录，使用上节工具环境的 Python：

```text
python learning/west/labs/seed_workspace.py --name demo-01
cd build/learning-tools/west/demo-01/workspace
```

现在初始化。没有外层工作区时，直接执行 `west init -l manifest`。如果仓库根目录或父目录已有 .west，west 会先发现外层工作区并拒绝 init；本项目本机恰有这个情况。此时在刚进入的 workspace 中执行：

```bash
python ../../../../../learning/west/labs/init_workspace.py -l manifest
```

这两种方式只选一种。[初始化辅助器](labs/init_workspace.py) 从独立临时目录启动真正的 `python -m west init -l`，根据当前相对路径定位清单，并仅对子进程清除外层 west 路径覆盖；不删除或改写外层 .west。辅助器只用于实验初始化，后续仍直接操作 west。完成后：

```bash
west topdir
west config manifest.path
west manifest --path
```

生成器创建三份小型本地 Git 历史和一份清单仓库，使用仅对生成提交生效的教学身份，不修改全局 Git 用户名；它不运行 west、不下载第三方源码。已存在同名目录时拒绝覆盖，改用 `--name demo-02`，后续路径也相应修改。

`-l` 表示从已有本地清单仓库初始化。本例 `manifest/` 的父目录就是工作区，初始化生成它旁边的 `.west/`。预期 `west topdir` 末尾是 `demo-01/workspace`，`manifest.path` 为 `manifest`，清单路径末尾是 `manifest/west.yml`。此时应用和库还没被获取，不能运行 `app/main.py`。

查看 `.west/config`：用 `cat .west/config`。其中 `[manifest]` 下的 `path` 决定去哪个仓库读清单，`file` 决定该仓库内的文件；未显式存储时清单文件名默认是 `west.yml`。不要用“手工建一个空 `.west`”代替初始化。

## 1.4 读最小清单，再同步

**YAML（YAML Ain't Markup Language，数据描述格式）** 通过缩进表达层级，列表条目用 `-`，此处应使用空格而非制表符。打开生成的 `manifest/west.yml`；先关注其中的算术库条目：

```yaml
- name: arithmetic
  url: ../../../remotes/arithmetic
  revision: v1.0
  path: libs/arithmetic
```

这段取自实际模板。其中四个配置字段分别是：`name` 是 west 内标识，`url` 是 Git 获取位置，`revision` 是所需 Git 版本，`path` 是相对工作区根目录的落盘位置；`path` 与源仓库名可以不同。

这里有两个不同的相对基准：west 的 path 相对 workspace；本地 Git url 在项目仓库内执行获取时解析。因此从 `workspace/libs/arithmetic/` 向上三层，到达 demo-01，再进入 `remotes/arithmetic/`。app 只在 workspace 下一层，所以它的 url 是 `../../remotes/app`。不要把 url 误当成相对 west.yml 的路径。保持目录关系即可整体移动实验，不需要填写绝对路径。清单中的可选文档组、扩展声明会在后续实验展开。

继续在 `workspace/` 执行：

```text
west manifest --validate
west list -f "{name}: {path} @ {revision} [{cloned}]"
west update
west list -f "{name}: {path} @ {revision} [{cloned}]"
python app/main.py
```

`--validate` 成功时可无输出，表示清单可解析，不证明远端地址一定可访问。`list` 查询清单，格式占位符由 west 替换；因此未克隆的项目也可以被列出。`update` 真正获取活动项目并检出声明版本。程序应输出 `2 + 3 = 5`：应用读取旁边 `libs/arithmetic/arithmetic.py` 的 `add` 函数，没有通过 pip 安装该库。

生成器已经为可选文档设置默认停用，因此第一次更新只有应用和算术库。下一章研究版本状态，第三章再主动启用文档仓库。

官方对照：[west init 与 update](https://docs.zephyrproject.org/latest/develop/west/built-in.html)。`init` 建立定位关系，`update` 获取项目；二者都不负责安装 Python 运行依赖，也不编译你的 C/C++ 应用。

## 1.5 工作区发现与第一次失败练习

从 `workspace/app/` 执行 `west topdir`，仍应找到同一工作区，因为 west 沿父目录查找 `.west`。回到实验根目录 `demo-01/` 再执行它，若祖先没有其他工作区则失败，因为查找不向子目录递归；若存在外层 .west，则可能显示外层路径，这不等于实验工作区仍被选中。若意外找到别的工作区，检查当前目录祖先是否有 `.west`，以及继承的 `ZEPHYR_BASE` 是否引发回退查找；这个 Zephyr 源码位置变量不是初始化命令。

正确恢复是进入已确认的 `workspace/`，再次检查 `west topdir`，不是重复安装 west。可用 `west help` 比较工作区内外可发现的命令，后续会解释扩展为何随工作区变化。

正常日常循环是“进入工作区→检查状态→按需要同步→开发与测试”，不需要每天重新初始化。重新练习时换一个种子名字；删除整个 `demo-01/` 会连同源仓库和开发副本一起删除，先保存自己的提交。

## 1.6 从清单仓库地址初始化另一份工作区

`-l` 用于已有本地清单；团队通常让新人从清单仓库地址开始，因此还需要 `-m`。本地 Git 路径也能作为地址，我们仍不联网：从原 workspace 执行 `cd ..`，现在位于 demo-01，且 from-source 目录尚不存在。

```text
python ../../../../learning/west/labs/init_workspace.py -m ./workspace/manifest --mr main from-source
cd from-source
west topdir
west update
python app/main.py
cd ../workspace
```

这里继续用辅助器避开外层工作区；在独立目录中可直接用 `west init -m ./workspace/manifest --mr main from-source`。`-m` 指定要克隆的清单仓库，`--mr main` 选择它的 main 分支，最后的 from-source 是新工作区目录。它们分别选择“清单从哪来、清单什么版本、工作区建在哪”，不能把 `--mr` 理解成所有项目都用 main。`--mf` 则能选择清单仓库内另一个文件名，默认使用 west.yml。`-l` 不能与 `-m` 或 `--mr` 混用。

与 -l 不同，-m 还检查目标目录的祖先。辅助器因此先在系统临时目录运行真实 init -m，再把新工作区转入上述 from-source，随后才执行 update；相对的项目来源地址到此时才使用。临时目录用完清理，最终实验文件仍在 build 内。这样能观察实际克隆初始化，又不删除工程外层的 .west。

预期新工作区同样输出 5，最后返回原 workspace 继续下一章。from-source 与 workspace 层次相同，项目相对地址仍可找到 remotes。克隆得到的是清单仓库的已提交内容，未提交的本地编辑不会跟随，这是选择 -m 与直接使用 -l 的又一个差别。省略 -m 时 west 的默认来源指向 Zephyr；本实验始终显式指定来源。
