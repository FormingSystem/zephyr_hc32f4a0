# 3. 修改清单与配置

上一章已能控制应用和库的版本。现在团队可能希望默认不获取文档，本机临时启用它，又不改变所有人的选择。**west** 是多仓库管理工具；**清单（manifest）** 保存项目集合声明，**配置（configuration）** 保存工具的选择规则。本章沿“版本管理的默认值→当前工作区覆盖→一次命令覆盖”理解差异，再把清单拆分成可维护的文件。

## 3.1 先认清三类文件

当前位置：最初的 `demo-01/workspace/`，不是上一章的 replay。**YAML（YAML Ain't Markup Language）** 是清单的数据格式；本地配置使用类似 **INI** 的分区格式，INI 是这类配置格式的名称，不必把它理解成 west 专属语言。

| 位置 | 所有者与用途 | 改完怎样生效 |
| --- | --- | --- |
| `manifest/west.yml` | 团队维护的仓库集合、版本、组与导入 | 下一次 west 解析读取；获取/切换项目仍需 update |
| `.west/config` | 本机工作区配置，如清单定位与组过滤 | 后续 west 调用读取，不自动提交到团队仓库 |
| 各项目的 `.git/config` | Git 的获取地址、分支上游等 | Git 执行时读取；不等于 west 清单本身 |

不要因为这些文件都包含“地址”和“版本”就只改自己最先找到的那一份。先确定谁消费配置、什么时候消费，再修改。

## 3.2 把清单字段变成可修改的选择

打开生成的 `manifest/west.yml`，对应这些职责：

其中 **HEAD** 是 Git 当前检出位置的特殊引用名称；本章继续将它与清单希望使用的 revision 区分。

| 字段 | 当前实例 | 修改时必须一起考虑的事实 |
| --- | --- | --- |
| `manifest.version` | 字符串 `"1.2"` | 声明受支持的清单格式需求，不是应用版本；只能用已定义的格式版本 |
| `projects[].name` | `arithmetic` | west 命令选择项目的标识，保持唯一 |
| `projects[].url` | `../../../remotes/arithmetic` | 本地获取来源，相对于消费项目目录；换镜像也应核对提交 |
| `projects[].path` | `libs/arithmetic` | 工作区内的本地位置；变化后应用搜索路径也可能要改 |
| `projects[].revision` | `v2.0` | 希望取得的 Git 版本，更新后再检查 HEAD |
| `self.path` | `manifest` | 清单仓库的声明位置；已有工作区实际定位仍看 `manifest.path` |
| `self.west-commands` | `west-commands.yml` | 命令描述文件位置，下一章展开 |

`self` 不是普通依赖条目。仅改 `self.path` 不会把已有目录搬家；改项目 `path` 也不意味着 west 自动帮你迁移并清理旧目录的本地修改。路径变更应在新工作区验证，明确保存和清理旧数据。

**remote** 在清单里是可复用的地址前缀定义，**defaults** 是项目缺省设置，**repo-path** 是远端仓库的路径尾部。下面是算术库条目的等价重构形式，仍使用实验相对路径：

```yaml
manifest:
  version: "1.2"
  remotes:
    - name: local-lab
      url-base: ../../../remotes
  defaults:
    remote: local-lab
    revision: v1.0
  projects:
    - name: arithmetic
      repo-path: arithmetic
      revision: v2.0
      path: libs/arithmetic
  self:
    path: manifest
```

以上只展示一个条目的重构形式；实际练习保留 app、guide、组和扩展声明。先给原清单加入 remotes/defaults，只删除 arithmetic 与 guide 中显式的 `url`，让它们使用默认 remote；app 层次不同，仍保留显式的 `../../remotes/app`。arithmetic 保留自己的 v2 以覆盖缺省 v1。用 `west list -a -f "{name}: {url} @ {revision} -> {path}"` 比较修改前后结果，再 `west manifest --validate`。地址组成是前缀加 repo-path，未写 repo-path 时使用项目 name；本地 path 不参与地址字符串拼接，但本地相对 url 的解析会受项目所在层次影响。

本地相对地址是为了离线练习，真实远端的地址前缀常为团队托管服务地址，不依赖本地层次。练习完成后还原为原来的直接 url 写法，方便下一节复制 guide 条目。官方字段依据：[Manifest Files](https://docs.zephyrproject.org/latest/develop/west/manifest.html#manifest-files)。

## 3.3 观察配置覆盖，不改全局偏好

**system、global、local** 是 west 的三个配置作用域，分别对应机器、当前用户、当前工作区。相同配置键按 local 高于 global 高于 system 合并。`west config` 读取默认展示合并结果，写入默认落在 local；教程仍显式写 `--local`，让副作用范围可见。

```text
west config -l
west config --local -l
west config --local color.ui false
west config color.ui
west config --local -d color.ui
```

`color.ui` 控制文字颜色，写入 false 后查询为 false；删除后读取可能来自用户配置，也可能返回“未设置”。删除设置和设置为空是不同动作，未设置也不等于工具损坏。

如果希望观察真实覆盖而不触碰用户文件，用 Bash 子 shell 隔离临时变量：

```bash
(
  export WEST_CONFIG_GLOBAL=.west/lab-global.ini
  west config --global color.ui true
  west config --local color.ui false
  west config color.ui
  west config --local -d color.ui
  west config color.ui
)
```

两个读取应依次为 false、true。前提是 local 的 `color.ui` 是本节刚建的临时项；已有个人设置时先记下并恢复。`WEST_CONFIG_GLOBAL` 是配置文件位置的环境变量，不是更高优先级的 color 值。结束后可删除 `.west/lab-global.ini`，用户原配置未被写入。

官方对照：[West Configuration Files](https://docs.zephyrproject.org/latest/develop/west/config.html#west-configuration-files)以及当前版本 `west config -h` 的文件位置覆盖说明。

## 3.4 启用、停用与一次性分组

**项目组（project group）** 是清单中附在项目上的标签；**group-filter** 是启用或停用组的规则。它只控制相应 west 操作的活动项目集合，不删除磁盘目录，也不控制 C/C++ 的编译选项。

本例 guide 的 `groups: [docs]` 把它加入 docs 组，清单的 `group-filter: [-docs]` 默认停用。先预测当前磁盘上有没有该目录，再执行：

```text
west list -a -f "{name}: {active} [{cloned}]"
west config --local manifest.group-filter +docs
west list -f "{name}: {active} [{cloned}]"
west update
west config --local manifest.group-filter -- -docs
west list -a -f "{name}: {active} [{cloned}]"
```

启用后 guide 变成活动项目，但在 update 前仍可能尚未克隆；update 后出现 `docs/guide/`。停用后它仍留在磁盘，但默认项目遍历通常不再选择它。`--` 使 `-docs` 按值传递，避免被当成命令选项。

一个项目在多个组中，只要有启用组就可能仍活动；没有组的项目不因此被关掉。west 1.5 还有按项目名称匹配的 `manifest.project-filter`，会进一步改变活动状态。理解组规则时先检查 `west config -l` 是否有这种覆盖，不要只看一个 YAML 行。

恢复本地默认，再只对一次 update 启用组：

```text
west config --local -d manifest.group-filter
west update --group-filter=+docs
west list -a -f "{name}: {active} [{cloned}]"
```

最后一次 list 按持久配置判定 guide 为 inactive，即使刚刚更新过它；一次性选项没有改写默认值。官方对照：[Project Groups](https://docs.zephyrproject.org/latest/develop/west/manifest.html#project-groups)。

## 3.5 将可选项目移入另一个清单

项目越来越多时，**导入（manifest import）** 用来合并另一份清单。它不是在当前目录任意搜索 YAML 文件；谁声明导入决定相对路径和读取版本。

在 `manifest/extra.yml` 新建以下文件，保持原先 guide 的相对 url：

```yaml
manifest:
  projects:
    - name: guide
      url: ../../../remotes/guide
      revision: v1.0
      path: docs/guide
      groups: [docs]
```

然后从主清单 projects 中移除原 guide 条目，在已有 `self` 中加入 `import: extra.yml`，保留已有 path 和 west-commands。这不是额外复制一份项目定义，而是移动同一个定义。

```yaml
self:
  path: manifest
  west-commands: west-commands.yml
  import: extra.yml
```

在 workspace 执行：

```text
west manifest --validate
west manifest --resolve -o ../resolved-with-import.yml
west list -a -f "{name}: {path}"
```

结果仍只有一份 guide，展开清单能看到它。修改顶层清单仓库中 `extra.yml` 的工作树内容，下一次解析就可观察；不需要为这种本地文件拆分去联网。把导入文件名临时写错会报找不到文件，恢复原值后重新 validate 即可。

来自普通项目的导入有不同版本边界。例如项目条目写 `import: west.yml`，west 从该项目最近同步的 manifest-rev 所对应的 Git 内容读取清单，而不是随意采用该项目工作树里未提交的改动。项目导入用于复用上游配套依赖；缺少该项目时先整体 `west update`，由它建立解析所需数据。顶层直接定义可以覆盖导入中的同名项目，但涉及多层导入时先查看展开结果，不依赖猜测文件顺序。

官方对照：[Manifest Imports](https://docs.zephyrproject.org/latest/develop/west/manifest.html#manifest-imports)。分组和导入的组合会改变有效项目集合，发布时应记录实际展开结果和本地过滤规则。

## 3.6 从普通项目导入并验证读取版本

继续沿上一节已有文件操作，做一个不用联网的上游导入实验。先把 `manifest/extra.yml` 复制到 `../remotes/app/west.yml`，它将成为应用源仓库随版本发布的清单；再从顶层 `self` 中删除刚添加的 `import: extra.yml`。顶层 projects 仍不直接定义 guide，避免重复定义掩盖观察结果。

用 `cp manifest/extra.yml ../remotes/app/west.yml`，然后两者共用：

```text
git -C ../remotes/app add west.yml
git -C ../remotes/app -c user.name="Learning Lab" -c user.email="learning@example.invalid" -c commit.gpgsign=false commit -m "Publish an imported guide manifest"
git -C ../remotes/app rev-parse HEAD
```

把输出的完整提交标识复制到顶层清单 app 条目的 revision，并在同一个条目新增 `import: west.yml`。保留该条目的 name/url/path，或前面已验证等价的 remote 写法。执行：

```text
west update
west manifest --resolve -o ../resolved-project-import.yml
west list -a -f "{name}: {path}"
git -C app show manifest-rev:west.yml
```

展开结果仍包含 guide；`git show` 显示的正是 app 同步基线里的导入文件。接下来只将消费副本 `app/west.yml` 暂时改为 `manifest: {projects: []}`，再执行 `west list -a`：guide 应仍存在。因为普通项目导入读取的是 Git 中 manifest-rev 的内容，不是这个未提交文件。

完成后只恢复本节故意修改的消费副本文件：`git -C app restore west.yml`。清单源仓库中的新提交可以保留；后续修改上游导入清单也应沿“修改源文件→提交→顶层接受新 revision→整体 update”的链路。普通项目导入尚未取得时，validate/resolve 可能缺少解析材料，这时先 update，而不是把所有解析错误都归为 YAML 缩进。

## 3.7 配置更改的验收方法

每次只改变一个维度：字段变化后先 validate，再 list/resolve 观察声明，最后需要时 update 并核对实际 Git 提交。清单能解析、项目被选中、源码已获取、应用可运行，是四项不同证据。

挑战：把 guide 同时加入 `docs` 与新组 `examples`，只禁用 docs 时预测活动状态；再禁用两个组。参考答案：若没有其他覆盖，第一种仍活动，第二种不活动。完成后恢复 `[docs]`，删除临时 local 过滤项，保留清单拆分或用 Git 审查后还原；不要删掉含开发修改的仓库来“修复”配置。
