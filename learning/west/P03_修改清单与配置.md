# 3. 修改清单与配置

上一章结束时，原工作区的 app 使用第一版，arithmetic 已回到第二版同步基线；开发备注留在自己的分支，replay 证明冻结文件可以重建已接受的版本组合。我们已经能够回答“应用配哪版库”，现在还要决定“哪些仓库需要参加当前工作”。

材料中有一个 guide 文档仓库。团队希望普通开发者只取得应用和库，写文档的同事则额外取得 guide。如果把它当成所有人必需的依赖，就失去了这个选择；如果每个人随意手工 clone，又难以共同维护文档的来源和版本。因此需要在团队清单中声明它，同时允许本机决定是否使用。

本章先把 guide 作为可选成员写入清单，弄清字段决定什么、本地配置又能改变什么，再实际启用它。组合关系清楚后，把同一份声明拆到其他文件，并比较由顶层工作树读取和由项目版本读取的两种导入。每次只改变一个条件，以便从结果判断究竟是哪份输入起了作用。

## 3.1 给团队清单增加一个可选成员

继续在最初的 `textbook-01/workspace/` 操作，工具环境保持激活，replay 不参与本章。guide 已由第一章的生成器放在源仓库目录中，但还没有写进当前清单。我们先把它的地址、版本和位置纳入团队管理，再声明默认不使用它。保存原清单后，用下面的完整版本写入 manifest/west.yml：

```bash
cp manifest/west.yml ../before-config.yml
cat > manifest/west.yml <<'YAML'
manifest:
  version: "1.2"
  group-filter: [-docs]
  projects:
    - name: app
      url: ../../remotes/app
      revision: v1.0
      path: app
    - name: arithmetic
      url: ../../../remotes/arithmetic
      revision: v2.0
      path: libs/arithmetic
    - name: guide
      url: ../../../remotes/guide
      revision: v1.0
      path: docs/guide
      groups: [docs]
  self:
    path: manifest
YAML
west manifest --validate
west list -a -f "{name}: {active} [{cloned}]"
```

新增 guide 的地址和版本含义与前章相同。`groups: [docs]` 给它一个名为 docs 的 **项目组（project group）** 标签；`group-filter: [-docs]` 则让这个组默认停用。这样 guide 的配套信息仍归团队清单维护，但没有自动成为当前需要获取的项目。

这里的 **活动（active）** 表示项目被当前选择规则纳入默认操作范围，和是否已经克隆是两回事。`list -a` 中的 `-a` 要求连不活动的项目也列出来，所以应能看见 guide 处于 inactive、not-cloned；app 与 arithmetic 则仍活动且已克隆。后面还会用“先启用、再同步、最后停用”的实验逐步改变这两个状态。

团队的默认值现在写在 YAML 清单中。若一个人只想在本机启用 guide，他需要改的是自己的配置，而不是把全队的默认值改掉。第一章已经见过 `.west/config`，它使用类似 **INI** 的分区配置格式；INI 是格式名称，不是 west 专属语言。把已经接触过的文件并排看，就能区分各自负责的事情：

| 位置 | 所有者与用途 | 改完怎样生效 |
| --- | --- | --- |
| `manifest/west.yml` | 团队维护的仓库集合、版本、组与导入 | 下一次 west 解析读取；获取/切换项目仍需 update |
| `.west/config` | 本机工作区配置，如清单定位与组过滤 | 后续 west 调用读取，不自动提交到团队仓库 |
| 各项目的 `.git/config` | Git 的获取地址、分支上游等 | Git 执行时读取；不等于 west 清单本身 |

例如要把所有人使用的算术库升级，改 manifest/west.yml 并提交；只想让当前实验下载文档，改 .west/config 的本地筛选；想查看 Git 实际采用的获取地址，查项目的 .git/config。第三种文件中的地址不代替团队清单声明，west 后续同步还会依据清单处理项目。

可以把它理解为三次读取：west 先读本地配置来定位清单，再读清单确定项目集合及版本，最后 Git 根据获取动作处理仓库。排错时先判断错误在哪次读取发生，而不是因为这些文件都有“地址”就随意修改其中一份。

## 3.2 把清单字段变成可修改的选择

现在已经区分“团队声明”和“本地配置”的存放位置。先把注意力留在团队清单上：一个文件里同时有版本、地址和目录，修改其中某个字段究竟会影响哪一步？下面沿用 app、arithmetic 和 guide 的现有值，先判断字段的作用，再做一次不改变结果的清单重写。

| 字段 | 当前实例 | 修改时必须一起考虑的事实 |
| --- | --- | --- |
| `manifest.version` | 字符串 `"1.2"` | 声明受支持的清单格式需求，不是应用版本；只能用已定义的格式版本 |
| `projects[].name` | `arithmetic` | west 命令选择项目的标识，保持唯一 |
| `projects[].url` | `../../../remotes/arithmetic` | 本地获取来源，相对于消费项目目录；换镜像也应核对提交 |
| `projects[].path` | `libs/arithmetic` | 工作区内的本地位置；变化后应用搜索路径也可能要改 |
| `projects[].revision` | `v2.0` | 希望取得的 Git 版本，更新后再检查 HEAD |
| `self.path` | `manifest` | 清单仓库的声明位置；已有工作区实际定位仍看 `manifest.path` |

表中的 HEAD 沿用上一章的含义，表示实际检出的提交；revision 仍是期望版本。`self` 描述的是顶层清单仓库，不是普通依赖条目。仅改 `self.path` 不会把已有目录搬家；改项目 `path` 也不意味着 west 自动帮你迁移并清理旧目录的本地修改。路径变更应在新工作区验证，明确保存和清理旧数据。

当十几个项目都托管在同一个组织下面时，每条 url 都重复写相同前缀，换服务地址就容易漏改。清单中的 **remote** 可以把这个地址前缀命名，项目只引用它。**defaults** 为没有单独指定值的项目提供缺省选择。**repo-path** 则说明这个项目前缀之后接哪个仓库路径；省略时采用项目 name。

下面先只展示 arithmetic 这一项的重构结构，帮助看清字段关系，不能直接覆盖含有其他项目的完整清单：

```yaml
manifest:
  version: "1.2"
  remotes:
    - name: local-lab
      url-base: ../../../remotes
  defaults:
    remote: local-lab
    revision: v1.0
  projects:
    - name: arithmetic
      repo-path: arithmetic
      revision: v2.0
      path: libs/arithmetic
  self:
    path: manifest
```

先算出它应产生什么：default remote 选择 local-lab，前缀 ../../../remotes 加上 repo-path arithmetic，得到 ../../../remotes/arithmetic；默认版本是 v1.0，但项目明确写了 v2.0，所以最终仍选第二版。path 仍是 libs/arithmetic，不参与地址字符串拼接。

实际编辑前先记录所有项目的有效值：

```bash
west list -a -f "{name}: {url} @ {revision} -> {path}"
```

`-a` 包含停用的 guide，否则会漏查它。保留三个项目和现有组设置，给原清单加入上面 remotes/defaults 两段，只删除 arithmetic 与 guide 的显式 url，让它们使用默认 remote。arithmetic 保留 v2.0；guide 的版本仍为 v1.0。app 的消费目录较浅，来源地址仍需显式保留 ../../remotes/app，不能套用另外两个项目的三级相对前缀。

再次执行相同的 list，地址、版本与位置应该与编辑前相同，再运行 west manifest --validate。这次练习应只改变声明的写法，没有改变最终要获取的内容。如果地址变了，应先纠正字段关系，再执行 update；不要用同步失败来代替事先读懂配置。

本地相对地址是为了离线练习，真实远端的地址前缀常为团队托管服务地址，不依赖本地层次。练习完成后还原为原来的直接 url 写法，后面的导入实验便能单独移动 guide 条目，无须一并搬动默认地址定义。官方字段依据：[Manifest Files](https://docs.zephyrproject.org/latest/develop/west/manifest.html#manifest-files)。

## 3.3 观察配置覆盖，不改全局偏好

上一节改变了团队声明的写法，却保留了相同的有效地址和版本。现在转到个人设置这一侧：guide 应默认停用，但本机需要时可以启用。要判断自己的设置是否真的生效，先得知道 west 会从哪些配置文件读取同一个键。

同一个人可能同时维护几个工作区，他的颜色偏好可以共用，但某个工作区的特殊设置应只影响自身。west 提供 **system、global、local** 三个配置作用域，分别对应机器、当前用户、当前工作区。相同键按 local 高于 global 高于 system 合并。

先用控制文字颜色的 color.ui 练习这个规则，暂时不改 guide 的选择。这样，观察到的变化就只来自配置覆盖。前两条都是查询：不加作用域时看合并设置，加 --local 时只看本工作区文件。确认 local 中没有原有 color.ui 后再继续；如果已有值，记录它并在实验后恢复。

```bash
west config -l
west config --local -l
west config --local color.ui false
west config color.ui
west config --local -d color.ui
```

这里 `-l` 是列出配置项，与 init -l 的“本地清单”不是同一个含义。`west config --local color.ui false` 是写入，因为键后带了值；`west config color.ui` 是查询，因为只有键。`-d` 删除指定作用域内的键。删除后其他来源的值可能重新露出来，也可能没有任何设置，因此“删除”不能理解为“设成 false”。

如果希望观察真实覆盖而不触碰用户文件，可以使用 WEST_CONFIG_GLOBAL 环境变量指定一个临时的用户级配置文件。下面用 Bash 子 shell 限制这个变量的影响范围：

```bash
(
  export WEST_CONFIG_GLOBAL=.west/lab-global.ini
  west config --global color.ui true
  west config --local color.ui false
  west config color.ui
  west config --local -d color.ui
  west config color.ui
)
```

括号创建子 shell，export 使里面启动的 west 进程都看到临时变量。WEST_CONFIG_GLOBAL 指定“用户级配置文件从哪里读写”，因此本次 --global 写到实验文件，而不是用户真正的配置；它不是直接指定一个更高优先级的颜色值。

第一次读应为 false：local 遮住了临时 global 的 true。删除 local 项后再读应为 true：低一层的值仍然存在。括号结束后临时变量不影响外面的 Bash，用户原配置未被写入。实验文件 .west/lab-global.ini 可自行清理；若开始时 local 有个人值，此时恢复它。这次对照说明配置覆盖应当按来源判断，不能只看最近打开的文件。

官方对照：[West Configuration Files](https://docs.zephyrproject.org/latest/develop/west/config.html#west-configuration-files)以及当前版本 `west config -h` 的文件位置覆盖说明。

## 3.4 启用、停用与一次性分组

颜色实验已经说明，本地设置能改变后续 west 调用看到的有效值，而且不必写入用户真正的全局文件。现在把这个方法用于章首的 guide：保留团队清单默认停用 docs 的规则，只在当前工作区追加启用选择。

这里要同时看两层合并：首先，配置作用域决定有效的 `manifest.group-filter` 配置值；然后，这个过滤值追加到清单的 group-filter 后面，参与项目选择。因此本地的 +docs 可以重新启用清单默认停用的 docs，而清单原文件仍保持不变。

本例 guide 的 `groups: [docs]` 把它加入 docs 组，清单的 `group-filter: [-docs]` 默认停用。先预测当前磁盘上有没有该目录，再执行：

```bash
west list -a -f "{name}: {active} [{cloned}]"
west config --local manifest.group-filter +docs
west list -f "{name}: {active} [{cloned}]"
```

第一条先看默认状态：guide 通常显示 inactive [not-cloned]。写入 +docs 后再次 list，它应变为 active [not-cloned]，表示已经活动但尚未下载。若前面已单独下载过 guide，则本来就会显示 [cloned]，不必为了模仿输出删除它。这里 list 用单词表示状态；下一章自定义报告里的布尔输出才采用 True/False。

guide 已变成活动项目，但 not-cloned 说明目录尚未取得。执行默认 update 后，它才会与其他活动项目一起同步。随后只把本地选择改成停用，再观察已经下载的目录会不会消失：

```bash
west update
west config --local manifest.group-filter -- -docs
west list -a -f "{name}: {active} [{cloned}]"
```

update 后应出现 docs/guide。设置 -docs 后，最后的 list 应同时显示 guide 不活动、却已克隆。规则改变的是后续默认操作选择哪些项目，并不表示要删除已获取的数据，也不直接改变 C/C++ 编译选项。`--` 表示命令选项到此结束，让后面的 -docs 被当成配置值，避免被误当成选项。

一个项目在多个组中，只要有启用组就可能仍活动；没有组的项目不因此被关掉。west 1.5 还有按项目名称匹配的 `manifest.project-filter`，会进一步改变活动状态。理解组规则时先检查 `west config -l` 是否有这种覆盖，不要只看一个 YAML 行。

本地配置适合持续写文档的工作。如果只是临时同步一次资料，则没有必要让以后的命令都启用 docs。删除刚写入的本地过滤项，再通过单次 update 的参数表达这次需要：

```bash
west config --local -d manifest.group-filter
west update --group-filter=+docs
west list -a -f "{name}: {active} [{cloned}]"
```

最后一次 list 按持久配置判定 guide 为 inactive，即使刚刚更新过它；一次性选项没有改写默认值。官方对照：[Project Groups](https://docs.zephyrproject.org/latest/develop/west/manifest.html#project-groups)。

## 3.5 将可选项目移入另一个清单

guide 的选择已经恢复为默认停用，已克隆的目录仍在磁盘上。现在不再改变谁参加同步，而是改变这份声明的维护方式：如果文档项目逐渐增多，维护者希望把它们写在单独文件中，west 仍需把这些文件读成同一套项目集合。

**导入（manifest import）** 用来合并另一份清单。先练最简单的情况：文件仍归顶层 manifest 仓库维护，只把 guide 的定义从主文件移出去，没有新增 Git 仓库，也没有改变 guide 的版本。

在 `manifest/extra.yml` 新建以下文件，保持原先 guide 的相对 url：

```yaml
manifest:
  projects:
    - name: guide
      url: ../../../remotes/guide
      revision: v1.0
      path: docs/guide
      groups: [docs]
```

然后从主清单 projects 中移除原 guide 条目，在已有 `self` 中加入 `import: extra.yml`，保留已有 path。这不是额外复制一份项目定义，而是移动同一个定义。

```yaml
self:
  path: manifest
  import: extra.yml
```

在 workspace 执行：

```bash
west manifest --validate
west manifest --resolve -o ../resolved-with-import.yml
west list -a -f "{name}: {path}"
```

validate 检查组合后的声明；resolve 把导入展开写入指定文件；list 列出最终集合。结果应仍只有一份 guide，且与拆分前采用相同地址、版本和位置。这说明拆文件是维护方式的变化，不应顺带改变依赖关系。

self.import 的文件名相对顶层清单仓库根目录，因此这里读取 manifest/extra.yml，不是 workspace/extra.yml。它读取该仓库当前工作树中的文件，保存后下一次解析即可观察，不必先提交或联网。把文件名暂时写成 missing.yml，validate 应失败；普通输出可能只说清单不可用，此时执行 `west -vv manifest --validate`，用详细日志确认缺少的是导入文件 missing.yml。恢复 extra.yml 后应重新通过。这个失败发生在读取清单阶段，还没有进入项目的 Git 获取过程。

目前 extra.yml 和主清单属于同一个仓库，保存工作树文件就能改变下一次解析。若这份配套声明由 app 团队随应用版本发布，顶层维护者便不应靠手工复制文件来保持一致。下一节把同一份 guide 定义放进 app 的源历史，观察“清单属于哪个版本”如何影响读取结果。

官方对照：[Manifest Imports](https://docs.zephyrproject.org/latest/develop/west/manifest.html#manifest-imports)。分组和导入的组合会改变有效项目集合，发布时应记录实际展开结果和本地过滤规则。

## 3.6 从普通项目导入并验证读取版本

沿用刚才拆出的 guide 声明，这次让 app 团队来维护它：app 的源仓库提交一份 west.yml，顶层清单接受这个新的 app 版本时，再从 app 导入其中的项目。这称为普通项目导入。文件格式没有变，变化的是声明的拥有者以及选择内容的依据。

对普通项目导入，west 读取该项目 **manifest-rev 所对应提交中的文件**，而不是消费副本当前工作树中的文件。这样顶层选定某版 app 时，就能得到那一版随附的依赖要求。下面先让这条正常路径成立，再故意改消费副本，检验这个边界。

继续沿上一节文件操作。先把 manifest/extra.yml 复制为源仓库 ../remotes/app/west.yml；再从顶层 self 中删除刚加的 import: extra.yml。顶层 projects 也仍不直接定义 guide，避免其他定义覆盖本实验。此处先修改 remotes/app，是在模拟上游作者发布内容，而不是修改 workspace/app 消费副本。

在原 workspace 执行：

```bash
cp manifest/extra.yml ../remotes/app/west.yml
git -C ../remotes/app add west.yml
git -C ../remotes/app -c user.name="Learning Lab" -c user.email="learning@example.invalid" -c commit.gpgsign=false commit -m "Publish an imported guide manifest"
git -C ../remotes/app rev-parse HEAD
```

把输出的完整提交标识复制到顶层清单 app 条目的 revision，并在同一个条目新增 `import: west.yml`。保留该条目的 name/url/path，或前面已验证等价的 remote 写法。执行：

```bash
west update
west manifest --resolve -o ../resolved-project-import.yml
west list -a -f "{name}: {path}"
git -C app show manifest-rev:west.yml
```

update 获取新 app 提交，也为后续解析提供导入材料。git show 的 `manifest-rev:west.yml` 表示读取该提交中的文件，而非磁盘当前文件。它应显示包含 guide 的内容，resolve 和 list 也应包含 guide。guide 仍带 docs 组，顶层仍默认停用 docs；把定义移到别的仓库并没有自动启用它。

再故意只修改消费副本的工作树文件，然后比较两种读取：

```bash
printf '%s\n' 'manifest: {projects: []}' > app/west.yml
cat app/west.yml
git -C app show manifest-rev:west.yml
west list -a
git -C app restore west.yml
```

cat 看到空项目列表，git show 却仍看到已提交的 guide，west list 也应保留 guide。这说明普通项目导入读取的是 manifest-rev 对应的 Git 内容，不是当前工作树文件；与 self.import 的读取边界确实不同。最后 restore 只撤销本实验刚对 app/west.yml 做的修改。若未按步骤从干净文件开始，不应直接覆盖自己原有的编辑。

app 源仓库中的新提交可以保留；后续修改上游导入清单也应沿“修改源文件→提交→顶层接受新 revision→整体 update”的链路。普通项目导入尚未取得时，validate/resolve 可能缺少解析材料，这时先整体 update，让它取得提供清单的项目，而不是把所有解析错误都归为 YAML 缩进。

本实验特意让 guide 只在导入文件中出现，以免另一份定义遮住观察结果。实际清单允许顶层直接定义覆盖普通项目导入中的同名项目；多层导入的优先关系更复杂，修改后要看 resolve 的有效结果。声明来自哪里、使用哪个版本、合并后留下哪一项，是三个需要分别确认的问题。

## 3.7 配置更改的验收方法

两种导入都观察过以后，可以把本章的判断连起来：先确认 west 读取哪份文件及哪个版本，再看合并后的项目是否活动，最后确认源码和应用行为。通常先 validate，再用 list/resolve 观察声明，需要获取或切换时才 update；刚引入普通项目导入而材料不足时，先整体 update 补齐它所需的数据。清单能解析、项目被选中、源码已获取、应用可运行，分别证明流程中的不同一步。

接下来的练习重新聚焦组选择，不再改变导入版本。先把本章开头的完整直接定义版本写回 manifest/west.yml：app v1.0、arithmetic v2.0、guide v1.0，默认 -docs，不带 import。extra.yml 和 app 源仓库中的实验提交可以保留，但不再参与当前解析。

在这份直接定义清单中，把 guide 的 groups 临时改为 `[docs, examples]`。先保留 `group-filter: [-docs]`，用 `west list -a -f "{name}: {active} [{cloned}]"` 观察；再把过滤改成 `[-docs, -examples]`，重复查询。试着在执行前预测两次 active 状态，并判断 cloned 是否需要变化。

核对依据是：没有额外配置覆盖时，一个组仍启用就足以让 guide 活动，所以第一次活动、第二次不活动。这里只改选择规则，没有获取或删除目录，cloned 不随之改变。完成后把 groups 恢复为 `[docs]`，group-filter 恢复为 `[-docs]`，并删除自己添加的临时 local 过滤项。再执行下面命令，为下一章留下确定的起点：

```bash
west update
west list -a -f "{name}: {active} [{cloned}]"
python app/main.py
```

app/arithmetic 应活动并已同步到 v1.0/v2.0，guide 不活动；guide 已经下载的目录仍然存在，应用仍输出 5。若状态不同，先用 west config -l 核对来源。我们现在已经能人工判断哪些项目应当存在，下一章把这个判断写成可重复执行的命令，让遗漏依赖时有明确的失败返回。
