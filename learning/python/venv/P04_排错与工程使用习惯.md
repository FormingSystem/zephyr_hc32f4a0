# 4. 排错与工程使用习惯

安装提示成功，程序却仍然导入失败，这两件事并不矛盾。安装时可能用了 A，运行时用了 B；也可能解释器确实是 A，却从当前目录读到了一个同名文件。本章用证据区分这些情况，故意制造并恢复一次失败，最后学习怎样让自己修改的包源码及时进入运行结果。

## 4.1 用同一个解释器提问

当前位置：仓库根目录。A 已按 P02 安装 v1。先固定使用 A 的路径，避免排错过程中又无意换了解释器；Linux/macOS 按准备章把 Scripts/python.exe 换为 bin/python。

```bash
build/learning-tools/venv/a/Scripts/python.exe -c "import sys; print(sys.executable); print(sys.prefix); print(sys.base_prefix)"
build/learning-tools/venv/a/Scripts/python.exe -m pip --version
build/learning-tools/venv/a/Scripts/python.exe -m pip show lab-greeting
```

第一条输出解释器文件、当前环境根目录、基础 Python 根目录。前两个应对应 A，后两个前缀应不同，说明确实在虚拟环境中。第二条输出 pip 版本及其文件位置，应也落在 A 中；否则你调查的安装器和执行者不是同一组。第三条用安装名称 lab-greeting 查询版本及 Location，确认 A 中存在第一版的安装记录。

有安装记录还不够，接着询问 Python 实际导入了谁：

```bash
build/learning-tools/venv/a/Scripts/python.exe -c "import lab_greeting; print(lab_greeting.__file__)"
build/learning-tools/venv/a/Scripts/python.exe -m pip check
```

这里用导入名 lab_greeting，而不是带连字符的安装名。`__file__` 给出这一次导入选中的文件；正常应落在 A 的 site-packages 中。pip check 则检查包声明之间的依赖关系。它不检查每次 import 选中了哪个文件，因此“pip check 成功”不能排除同名文件遮蔽。下一节就制造这种情况。

**导入路径（import path）** 是 Python 在解释器启动后查找模块的一组目录，保存在 sys.path 中。这与第一章的 PATH 是两次不同的查找：Bash 先通过 PATH 找到要启动的程序，Python 启动后再通过 sys.path 查模块。这里使用 `-c` 执行短代码时，当前工作目录会进入模块搜索路径。**PYTHONPATH** 环境变量还可额外加入搜索目录，venv 不保证清除它；因此环境里的包即使正确，仍可能被前面的同名文件遮住。

## 4.2 故意制造一次遮蔽

我们不改 A 中的安装，只准备一个包含同名文件的新工作目录。仍从仓库根目录执行：

UCRT64 Bash：

```bash
mkdir -p build/learning-tools/venv/shadow
printf '%s\n' "print('local shadow module')" > build/learning-tools/venv/shadow/lab_greeting.py
(cd build/learning-tools/venv/shadow && ../a/Scripts/python.exe -c "import lab_greeting; print(lab_greeting.__file__)")
(cd build/learning-tools/venv/shadow && ../a/Scripts/python.exe -c "from lab_greeting import greet")
echo $?
```

mkdir 的 `-p` 会按需创建父目录。printf 写入的文件只会打印文字，没有定义 greet。括号让 cd 在 Bash 子 shell 内生效，括号结束后外层仍在仓库根目录；`&&` 保证只有切换目录成功才运行后面的程序。此时 ../a 是从 shadow 出发计算的解释器路径。

第一次导入应打印 local shadow module，随后显示 shadow 中的文件路径。第二次仍选中这个文件，但它没有 greet，于是应报 ImportError，echo 显示非零退出码。故障发生在“选中了错误的模块文件”，与是否安装了 lab-greeting 是两个问题。

把遮蔽文件改成不与包同名的名称，再在相同目录重试：

```bash
mv build/learning-tools/venv/shadow/lab_greeting.py build/learning-tools/venv/shadow/local_example.py
(cd build/learning-tools/venv/shadow && ../a/Scripts/python.exe -c "import lab_greeting; print(lab_greeting.__file__); print(lab_greeting.greet())")
```

现在应重新指向 A 的 site-packages，并输出第一版问候语。没有重新安装却恢复了功能，说明刚才的定位成立。实际项目遇到类似问题时也先检查导入文件，再决定是否需要重装。清理只涉及本例生成的 shadow 目录。

官方对照：[Python 模块搜索路径](https://docs.python.org/3.12/tutorial/modules.html#the-module-search-path)，带着“为什么当前目录优先”阅读。

## 4.3 把常见症状变成定位步骤

表中的 `python` 是解释器命令，`pip` 是安装器命令，`setuptools` 是构建后端工具名称，`ensurepip` 是 Python 随附的 pip 引导模块名称。先区分执行者、安装器和构建工具，才能把错误分派到正确的一层。

| 现象 | 优先检查 | 恢复动作与边界 |
| --- | --- | --- |
| 找不到 `python` 或 `pip` | 实际解释器路径是否存在 | 用完整路径，确认基础 Python 安装；不靠随机重装解决 |
| 安装成功却找不到模块 | `sys.executable` 与 `pip --version` 是否同环境 | 用运行程序的解释器执行 `-m pip`；再检查安装名和导入名 |
| 环境解释器提示基础路径失效 | 基础 Python 是否被卸载、环境是否被移动 | 按新解释器重建，不手改一串绝对路径 |
| 提示 `externally-managed-environment` | 是否正在修改发行版管理的系统 Python | 为项目建环境，再在环境中安装；无需破坏系统包管理 |
| 新环境没有 `setuptools` | Python 版本与项目构建需求 | 3.12 的该现象正常，按构建声明准备后端 |
| 没有 `ensurepip`/venv 组件 | 所选 Python 的来源 | 安装匹配发行版组件，或使用包含该模块的受支持发行版 |
| 提示没有匹配版本 | 包名、版本、索引、Python 版本和平台 | 查发布支持范围；旧包没有新 Python wheel 时可能需编译或换兼容版本 |
| 命令行正常，编辑器运行失败 | 编辑器选择的解释器 | 把项目解释器设为同一个环境路径，再用观察程序核对 |

编辑器的运行/调试配置可以选择自己的 Python 解释器，不一定沿用另一个终端的激活状态。这与嵌入式工程中终端和编辑器可能选中不同工具链类似；不要只看状态栏文字，用程序输出确认。

## 4.4 自己改包时使用可编辑安装

上一章从 wheel 安装到 A 后，A 运行的是安装进环境的代码。直接修改教材里的 package_v1 源码，并不会自动替换 A 中的那份安装结果。若你正在开发这个包，每改一行纯 Python 代码都重新构建并安装，会打断调试过程。

**可编辑安装（editable install）** 为此建立环境与开发目录的关联，让导入读取开发目录中的代码。它仍然是一次安装：需要包的构建声明和安装元信息，并非随便把目录加到某个搜索路径即可代替。下面另外建立 dev 环境，与已验证的 A 分开。

当前位置：仓库根目录。复制 `labs/package_v1` 到 `build/learning-tools/venv/edit-src`，避免覆盖正式教材。UCRT64 Bash：

```bash
cp -R learning/python/venv/labs/package_v1 build/learning-tools/venv/edit-src
py -3.12 -m venv build/learning-tools/venv/dev
build/learning-tools/venv/dev/Scripts/python.exe -m pip install setuptools==80.9.0
build/learning-tools/venv/dev/Scripts/python.exe -m pip install --no-build-isolation -e ./build/learning-tools/venv/edit-src
build/learning-tools/venv/dev/Scripts/python.exe -c "import lab_greeting; print(lab_greeting.__file__); print(lab_greeting.greet())"
```

确保 edit-src 原先不存在，避免 cp -R 把 package_v1 再嵌套复制进去。`-e` 表示可编辑安装，后面的目录应直接包含 pyproject.toml。`--no-build-isolation` 让构建使用 dev 中已有的后端，因此前一条才先安装项目声明的 setuptools 版本；它不是“无需构建后端”的开关。首次安装 setuptools 可能访问网络。

输出文件位置应在 edit-src/src/lab_greeting 中，而不是 dev 的普通包复制目录。现在用编辑器打开复制品 `build/learning-tools/venv/edit-src/src/lab_greeting/__init__.py`，只把返回字符串里的 from v1 改成 from edited，保存。重新启动两个解释器进行对比：

```bash
build/learning-tools/venv/dev/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/a/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
```

dev 应输出 from edited，A 仍输出 from v1。这说明 dev 读取开发目录，A 使用之前安装的 wheel，两种用法各有目的。这里每次启动新 Python 进程，避免已经导入的模块被长期运行的进程缓存。若改的是包依赖、入口命令等元信息，或需要编译的扩展代码，仍可能需要重新安装或构建，不能把本例纯 Python 文件的即时生效推广到所有修改。

执行 Dev 的 `-m pip uninstall lab-greeting` 会解除该环境安装关系，不删除 `edit-src` 的源码。清理时保存自己的修改，再移除 dev 环境和复制品。[pip 本地项目安装](https://pip.pypa.io/en/stable/topics/local-project-installs/#editable-installs)给出可编辑模式与常规安装的行为边界。

## 4.5 常见工程约定与选择依据

一个独立项目通常对应一个环境，源码和环境分开；环境路径、Python 版本、依赖安装与测试入口写入项目文档。运行脚本和自动化优先明确指定解释器，交互终端则可以激活后使用短命令。升级先在新环境验证，再更新依赖记录和测试结果，保留回退组合。

**pipx** 是为独立 Python 命令行工具创建独立环境并暴露命令的工具名称，适合一个工具供多个项目使用；**uv** 是提供 Python 项目和包管理能力的工具名称；**Conda** 是能够管理 Python 及其他二进制依赖的环境工具名称。这些工具的工作范围不同：只需要理解包隔离且愿意管理依赖记录时，venv 加 pip 就能完成任务；需要统一锁定、解释器管理或复杂本地库时，再根据团队要求评估额外工具。这里是按职责作选择，没有要求项目迁移工具。

官方进一步阅读：[pipx 的工具隔离](https://pipx.pypa.io/stable/)、[uv 项目环境](https://docs.astral.sh/uv/concepts/projects/layout/)、[Conda 环境管理](https://docs.conda.io/projects/conda/en/stable/user-guide/tasks/manage-environments.html)。venv 自身不提供跨 Python 版本安装、完整依赖锁定或系统库隔离。

综合验收：另选一个项目目录，创建新环境，用本地需求文件安装 v1，输出解释器位置、包位置与问候语；重开终端且不激活，再用完整路径运行一次。若这四步都能解释，就已经掌握可迁移的模型，而不仅是记住 `activate`。
