# 1. 创建并认识虚拟环境

假设你维护两个嵌入式项目，它们都有一个 Python 写的固件处理工具。旧项目用某个库的第一版，新项目需要第二版。你已经把两个项目放在不同文件夹，却发现给新项目升级库以后，旧项目也不能正常运行了。

问题出在一个容易忽略的地方：**源码放在哪里，与运行它的 Python 从哪里找库，是两件事。** 进入旧项目文件夹，并不会自动把 Python 切换成“旧项目专用版本”。本章从这个问题出发，弄清虚拟环境究竟改变了什么，再亲手创建两个环境。

命令使用 UCRT64 Bash 和 Windows Python 3.12；先完成[实验准备](../../P00_实验准备.md)。本章从仓库根目录操作，生成文件放在 build/learning-tools/venv。想先连续做完一轮，可用[实训手册](labs/README.md)，它有独立目录，不能混用两条路线的路径。

## 1.1 为什么换了项目目录，包仍会互相影响

先看一条最普通的运行命令。下面是用来理解关系的示意，firmware_tool.py 不是本仓库的实验文件：

```text
python firmware_tool.py
```

这条命令先选择一个叫 python 的程序，再让它执行后面的文件。这个执行 Python 代码的程序叫**解释器（interpreter）**。脚本调用外部库时，解释器会按自己的搜索规则找代码；它并不会因为脚本属于另一个 Git 仓库，就自动换一套已经安装的库。

假设两次运行最终选中的都是同一套 Python，库也都装在它的同一个安装位置：

```text
旧项目的脚本 ──→ 同一套 Python ──→ 同一个第三方包目录
新项目的脚本 ──→ 同一套 Python ──→ 同一个第三方包目录
```

此时安装第二版通常会替换该位置里的第一版。旧项目的源码一行没变，下一次运行却读到了新库，因此行为变了。真正需要分开的是“运行入口和包安装位置”，仅复制项目文件夹没有解决这件事。

可以为每个项目各装一整套 Python，但如果它们使用相同的 Python 版本，只是第三方库不同，这样做就重复了很多基础设施。Python 提供的**虚拟环境（virtual environment）**允许在现有 Python 的基础上，为不同项目建立独立的第三方包安装位置。

```text
基础 Python 3.12
  ├─ 创建环境 A：A 的解释器入口 ──→ A 的第三方包目录
  └─ 创建环境 B：B 的解释器入口 ──→ B 的第三方包目录
```

之后给 A 安装第一版、给 B 安装第二版，分别从 A/B 的入口运行脚本，就能使用不同的库。这里的“虚拟”不表示启动了另一台电脑：两个环境仍使用同一个操作系统，也仍能访问当前用户有权限访问的文件。它解决依赖安装隔离，不是限制程序权限的安全沙箱。

## 1.2 读懂创建命令，再建立 A 和 B

**venv** 是 Python 标准库中的模块名称，负责创建虚拟环境。模块可以先理解成一份可供 Python 使用的功能代码；**标准库**是随 Python 一起提供的这些功能，不用额外下载 venv。

在仓库根目录执行：

```bash
py -3.12 -m venv build/learning-tools/venv/a build/learning-tools/venv/b
```

从左向右读这条命令：`py -3.12` 用 Windows 启动器选择 Python 3.12；`-m venv` 让这份 Python 运行 venv 模块；最后两个路径告诉 venv 在哪里分别建立环境。这是在创建两个环境，不是创建一个包含两个项目的环境。

成功时可以没有输出。若 a/b 已经存在，重跑会复用目录，不会自动清掉你上次装过的包。首次练习应使用新目录；复练时先保存旧数据，再换一个统一的新目录名，不对未知目录使用清空选项。

现在检查两个入口能否运行：

```bash
build/learning-tools/venv/a/Scripts/python.exe --version
build/learning-tools/venv/b/Scripts/python.exe --version
```

两者都应报告 Python 3.12.x。版本相同是正常的：我们要隔离第三方包，不是把 Python 3.12 变成两个不同语言版本。Windows Python 创建的入口位于 Scripts，即使在 Bash 中运行也一样；Linux/macOS 通常使用 bin/python，具体替换见准备章。

以后看到这两类命令，应先判断它们操作哪一层：`py -3.12 -m venv ...` 使用基础 Python **创建环境**；`a/Scripts/python.exe ...` 使用已经创建的 A **运行程序**。安装依赖是另一项操作，由下一章的 pip 完成。

对照 [venv 的创建说明](https://docs.python.org/3.12/library/venv.html#creating-virtual-environments)，重点核对最后的路径参数和生成目录，先不急着使用全部高级选项。

## 1.3 环境究竟生成了什么

打开 A 的配置：

```bash
cat build/learning-tools/venv/a/pyvenv.cfg
```

cat 只读取文件。pyvenv.cfg 是环境配置文件名，Windows 环境的关键结构如下，省略无关文件：

```text
 a/
   pyvenv.cfg           记录环境与基础 Python 的关系
   Scripts/python.exe  从这个入口运行，使用 A 的环境
   Lib/site-packages/  A 安装第三方包的位置
```

配置中的 home 指向创建环境所用的基础 Python；include-system-site-packages 通常为 false，表示默认不把基础安装的第三方包目录开放给 A。**site-packages** 是这类包安装目录的约定名称，不是你的业务源码目录。

这也解释了两个工程习惯。第一，源码不要放进 .venv：环境应能删掉重建，源码却需要长期维护。第二，不要把环境目录复制给同事当作安装方法：配置、启动脚本可能关联原位置，基础 Python 和平台也可能不同。同事应使用依赖说明重建环境，第三章会实际验证。

现实项目常把自己的环境目录叫 `.venv`，只是命名惯例。venv 是创建工具的模块名，.venv 是你选择的目录名；本章的 a/b 与 .venv 没有本质区别。

## 1.4 不看提示符，怎样确认正在使用 A

目前我们没有执行任何“激活”命令，A 的解释器却已经能运行。用仓库附带的只读观察程序检查原因：

```bash
build/learning-tools/venv/a/Scripts/python.exe learning/python/venv/labs/inspect_environment.py
```

前半段选择 A 的解释器，后半段是要执行的脚本。观察脚本不安装包、不修改环境，只输出解释器报告的身份信息。输出采用 JSON（JavaScript Object Notation，一种数据表示格式），其中 true 表示真、null 表示没有值。

先看 executable 字段，它应指向 a/Scripts/python.exe。这回答“到底是谁执行了脚本”，比终端提示符是否出现 `(a)` 更直接。

再看 prefix 与 base_prefix 字段。prefix 指当前环境根目录，应是 a；base_prefix 指基础 Python 的目录，应与 a 不同。观察程序把两者是否不同写成 is_venv；本次应为 true，表示当前进程使用虚拟环境。

最后看 VIRTUAL_ENV。它是激活脚本设置的环境变量，若当前终端没有激活环境，值可以是 null。**没有这个变量，不妨碍你明确指定 A 的入口运行。** 环境身份应看实际解释器和前缀，不能只看激活变量。

这些关系比记住输出中的盘符有用：目录可以随机器变化，但 executable 属于 A、prefix 不等于 base_prefix 的判断仍然成立。

## 1.5 激活究竟替我们省了哪一步

一直输入完整的相对路径有些长，所以交互终端希望用短命令 python。问题随之出现：电脑上可能有多份 python，短名字该对应哪一份？

Bash 会按命令解析规则寻找程序，**PATH** 环境变量提供一组供它查找的目录。激活 A 的主要作用，就是把 A 的程序目录放到搜索顺序前面。于是没有显式指定路径的 python 通常会先找到 A。

在同一个终端、仓库根目录执行：

```bash
source build/learning-tools/venv/a/Scripts/activate
command -v python
python learning/python/venv/labs/inspect_environment.py
```

source 在当前 Bash 中执行激活文件，所以它对 PATH 的修改留在当前终端。command -v 查询短命令会解析到哪里；最后的观察程序应仍显示 A，只是 VIRTUAL_ENV 现在有值了。激活没有复制源码，也没有把先前运行的别的进程改成 A。

先预测下面的结果，再执行：

```bash
build/learning-tools/venv/b/Scripts/python.exe learning/python/venv/labs/inspect_environment.py
```

解释器应是 B。因为你已经写明 B 的文件位置，不需要再让 PATH 决定。这是“选择程序”和“方便输入”之间的区别。环境变量仍可能保留 A 的激活信息，因此再一次证明它不是运行身份的唯一依据。

结束交互选择：

```bash
deactivate
```

deactivate 是激活时加入的 shell 函数，它恢复当前终端设置。A/B 的目录和包没有被删除。新终端有自己的状态，需要重新激活；自动化任务为了减少这种隐含条件，常直接指定环境解释器路径。若结果不符，用 `type -a python` 列出候选，再用观察程序确认实际入口。

官方 [How venvs work](https://docs.python.org/3.12/library/venv.html#how-venvs-work)也将前缀判断与激活区分。阅读时对照刚才 A 激活、B 执行的反例。

## 1.6 哪些选项现在用得上，哪些会改变隔离条件

默认创建方式足够完成本系列实验。以后确有需要，再按目的选择选项：

| 想改变什么 | 创建时的选项 | 改变后的含义 |
| --- | --- | --- |
| 终端显示的名字 | `--prompt reader-a` | 只改提示文字，不改变 Python 版本或包来源 |
| 让环境也能看到基础安装的第三方包 | `--system-site-packages` | 放宽可见范围，实验不再是默认的独立包集合 |
| 不预先放入 pip 安装器 | `--without-pip` | 环境能运行 Python，但还没有通常用于装包的工具 |

若没有 pip，可以对该环境的解释器运行 `-m ensurepip --upgrade`。ensurepip 是 Python 随附的安装器引导模块，使用随发行版提供的资源。Python 3.12 的新环境不再默认含 setuptools 打包工具，下一章会在需要打包时单独准备，而不是把它当作创建失败。

现在应能解释：两个目录为何不足以隔离依赖；两个环境为何能使用同一 Python 版本；激活为何可省略；退出为何不删除文件。清理前退出环境、离开目标目录并保存源码，只删除已确认可再生的环境。下一章将真正安装同名包的两个版本，验证隔离是否影响程序结果。
