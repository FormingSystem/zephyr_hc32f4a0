# 1. 创建并认识虚拟环境

假设一个旧项目只能使用某个库的第一版，新项目需要第二版。把两版都装进同一个 Python 的默认位置，后一次安装通常会替换前一次。项目目录分开了，安装位置却仍然相同。我们需要把“哪份 Python 在运行、它从哪里找包”一起区分开。本章先建立两个空环境，下一章再用真实安装验证。

## 1.1 环境到底隔离什么

**解释器（interpreter）** 是执行 Python 代码的程序。**模块（module）** 是可导入的代码单元，例如一个 `.py` 文件；**导入包（import package）** 把多个模块组织在一个名称下。后文用 **分发包（distribution package）** 指供安装器安装的项目，它的安装名称不一定等于导入名称。

**虚拟环境（virtual environment）** 是一组与某个基础 Python 关联的目录和配置，拥有自己的第三方包安装位置。**venv** 是创建它的标准库模块名；**pip** 是安装分发包的工具名。二者分工：先用 venv 准备位置，再用 pip 安装依赖。

在本实验中，“基础 Python → 创建 A/B → 分别安装包 → 启动 A/B 的解释器”构成完整关系。A 和 B 默认不共享第三方安装目录，但仍依赖创建它们的基础 Python，也共享操作系统和文件访问权限。虚拟环境不能限制恶意代码访问文件，不是安全沙箱。

**标准库（standard library）** 是 Python 随附的常用模块，如本实验的 `sys`、`json`；无须单独用 pip 安装。创建环境不会自动获得你的全部业务依赖。

官方对照：[Python 3.12 venv](https://docs.python.org/3.12/library/venv.html#creating-virtual-environments)，可核对创建命令及生成目录。下面用本仓库输出观察这些对象。

## 1.2 创建 A 和 B

当前位置：仓库根目录。A/B 是教学名字；真实项目常把环境命名为 `.venv`。

UCRT64 Bash：

```bash
py -3.12 -m venv build/learning-tools/venv/a build/learning-tools/venv/b
build/learning-tools/venv/a/Scripts/python.exe --version
build/learning-tools/venv/b/Scripts/python.exe --version
build/learning-tools/venv/a/Scripts/python.exe learning/python/venv/labs/inspect_environment.py
```

首次创建通常耗时几秒，成功时可以没有输出。如果已经存在同名目录，不要以为重跑就清空了旧包；换新的目录名，或按清理规则删除已确认可丢弃的环境后重建。

观察程序输出的字段：`executable` 是真正运行的可执行文件；`prefix` 是当前环境根目录；`base_prefix` 是基础 Python 的位置；`is_venv` 来自两种前缀是否不同。`VIRTUAL_ENV` 是激活脚本设置的环境变量名称，观察程序也显示它；它没有值不代表解释器一定在环境之外。路径因机器而变，关键关系应为：

```text
executable: .../build/learning-tools/venv/a/.../python
prefix: .../build/learning-tools/venv/a
base_prefix: 基础 Python 安装位置
is_venv: true
VIRTUAL_ENV: null（在没有激活环境的终端直接执行时）
```

输出采用 **JSON（JavaScript Object Notation，数据表示格式）**；`null` 表示没有值。最后一行是关键反例：没有“激活”，仍然在虚拟环境中运行。

## 1.3 激活只是让短命令更方便

**PATH** 是 shell 查找命令时依次搜索的目录列表。输入 `python` 时，shell 按命令解析规则找到程序；激活脚本把环境的可执行目录放到 PATH 前面，并通常改变提示符。它没有复制项目，也没有启动后台虚拟机。

在仓库根目录激活 A。UCRT64 Bash：

```bash
source build/learning-tools/venv/a/Scripts/activate
command -v python
python learning/python/venv/labs/inspect_environment.py
deactivate
```

激活后实际解释器仍是 A，但 `VIRTUAL_ENV` 这个激活脚本设置的环境变量现在有值。`deactivate` 是激活时添加的退出函数：恢复当前 shell 的相关设置，既不卸载包也不删除目录。新窗口需要重新激活；自动脚本可一直使用完整路径。

主线直接调用环境解释器时不依赖激活。激活后仍用 `type -a python` 和实际解释器输出确认选择结果。

预测题：激活 A 后执行 B 的完整路径，谁运行？答案仍是 B。命令已经明确指定文件，PATH 不再替你选 A。可亲手把观察命令的 路径中的 `/a/` 改为 `/b/` 验证。

官方对照：[How venvs work](https://docs.python.org/3.12/library/venv.html#how-venvs-work)，区分运行时前缀与激活变量。

## 1.4 查看生成的文件，解释退出与删除

**pyvenv.cfg** 是环境配置文件名。用 `cat build/learning-tools/venv/a/pyvenv.cfg` 查看。`home` 记录基础解释器位置，`include-system-site-packages` 决定是否允许看到基础安装的包目录。

Windows 在 `Scripts/` 放启动程序，在 `Lib/site-packages/` 放安装的包；Linux/macOS 通常分别使用 `bin/` 和 `lib/pythonX.Y/site-packages/`。**site-packages** 是 Python 使用的第三方包目录名称；具体位置以观察程序为准。

创建时可加 `--prompt reader-a` 自定义提示符名；这只是显示名称。`--system-site-packages` 会放宽包可见性，不适合本次隔离实验；`--without-pip` 不引导安装 pip，之后可对环境解释器执行 `-m ensurepip --upgrade`。`ensurepip` 是 Python 随附的 pip 引导模块，它使用随 Python 提供的资源。Python 3.12 新环境不再默认包含 setuptools，下一章会显式准备构建工具。

不把虚拟环境复制到另一台机器的原因是：脚本和配置可能记录绝对路径，基础 Python 与平台也可能不同。应保存依赖说明后重建。清理 A/B 前先退出环境，确认它们只有可再生包而无源码，再删除对应目录；不要使用 `venv --clear` 指向含有项目源码的目录。

验收：你应能在不看提示符的情况下，用实际路径和前缀判断环境身份。下一章让 A/B 安装同名包，验证目录隔离是否真的影响程序输出。
