# 2. 安装包并验证版本隔离

上一章已经创建两个虚拟环境，也证明不激活仍可使用它们。现在还缺一项证据：同一个包安装不同版本，是否真的互不影响？本章把一个简单问候程序分别装进 A 和 B，从版本、文件位置和实际输出三个角度验证。

**虚拟环境（virtual environment）** 在这里指独立的 Python 包安装目录和关联解释器；**pip** 是包安装工具的名称。以下命令始终使用环境解释器运行 pip，使“安装者”和“执行者”保持一致。

## 2.1 看懂最小教学包

打开 [第一版 pyproject.toml](labs/package_v1/pyproject.toml) 和 [第一版代码](labs/package_v1/src/lab_greeting/__init__.py)。**pyproject.toml** 是 Python 项目配置文件名，使用 **TOML（Tom's Obvious Minimal Language，配置文件格式）**：方括号是配置分区，等号左右是名称和值。

本例只做一件事：调用 `greet()` 返回 `hello reader from v1`；第二版返回 `hello reader from v2`。`from lab_greeting import greet` 从已安装的包中导入该函数。本章只需要这条导入关系，不展开 Python 语法教学。

**分发包（distribution package）** 是安装单位，名字为 `lab-greeting`；**导入包（import package）** 是代码中的名称，为 `lab_greeting`。连字符与下划线不能随意互换到 Python 导入语句中。`src/` 是源码目录，`__init__.py` 使这个目录成为普通导入包，并提供本例函数。

配置中的 `[project]` 描述名称、版本和 Python 版本要求；`[build-system]` 说明谁把源码变成可安装文件；`[tool.setuptools.packages.find]` 告诉本例的构建工具去 `src/` 找包。**setuptools** 是构建工具名称，**构建后端（build backend）** 是执行打包工作的组件，本例指定 `setuptools.build_meta`。这里的构建依赖与“程序运行时依赖”是两个列表，本例不需要其他运行时包。

官方对照：[Writing your pyproject.toml](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#declaring-the-build-backend)。阅读时重点看构建依赖和项目元信息属于不同分区。

## 2.2 先产生安装文件

**wheel** 是 Python 可安装归档格式的名称，文件后缀为 `.whl`；本例的 **wheelhouse** 只是存放这些文件的目录名，不是一种额外服务。先构建后安装，可以清楚看见“源码→分发文件→环境目录”的路径。

当前位置：仓库根目录。A/B 已按第一章建立。先为构建单独创建 `builder` 环境，让业务环境只有教学包。UCRT64 Bash：

```bash
mkdir -p build/learning-tools/venv
cp -R learning/python/venv/labs/package_v1 build/learning-tools/venv/package_v1
cp -R learning/python/venv/labs/package_v2 build/learning-tools/venv/package_v2
py -3.12 -m venv build/learning-tools/venv/builder
build/learning-tools/venv/builder/Scripts/python.exe -m pip install setuptools==80.9.0
build/learning-tools/venv/builder/Scripts/python.exe -m pip wheel --no-deps --no-build-isolation --wheel-dir build/learning-tools/venv/wheelhouse ./build/learning-tools/venv/package_v1
build/learning-tools/venv/builder/Scripts/python.exe -m pip wheel --no-deps --no-build-isolation --wheel-dir build/learning-tools/venv/wheelhouse ./build/learning-tools/venv/package_v2
ls build/learning-tools/venv/wheelhouse
```

复制前确认目标 package_v1/package_v2 尚不存在；重新练习可换实验目录名，避免重复复制造成嵌套。应得到 `lab_greeting-1.0.0-py3-none-any.whl` 与 `lab_greeting-2.0.0-py3-none-any.whl`。本例是纯 Python 包，所以文件名表示适用于 Python 3、没有特定二进制接口与平台限制；带本地编译代码的包可能不能跨机器使用同一个 wheel。

`--wheel-dir` 指定产物目录；`--no-deps` 不继续构建运行依赖，本例确实没有运行依赖。`--no-build-isolation` 表示使用 builder 里已经准备好的后端，省去临时构建环境。它不负责安装后端；漏掉前面的 setuptools 安装会失败。普通项目可以不加该选项，让 pip 建立临时构建环境并安装 `[build-system]` 的依赖；这里显式准备工具是为了后续离线练习。

## 2.3 给 A 和 B 安装不同版本

**包索引（package index）** 是查询分发包下载位置的服务；公共服务常用名称 **PyPI（Python Package Index）**。本例不发布包，仅使用刚才生成的本地文件。`--no-index` 禁止查询索引；`--find-links` 提供搜索安装文件的目录；`==` 要求准确版本。

UCRT64 Bash：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==1.0.0
build/learning-tools/venv/b/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==2.0.0
build/learning-tools/venv/a/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/b/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
```

两个输出依次为 `hello reader from v1`、`hello reader from v2`。仅仅看到安装成功不能证明隔离；必须分别启动两个解释器确认输出。

如果出现 `No matching distribution found`，意为没有找到满足要求的安装文件。检查 wheelhouse 的位置、构建是否成功和版本拼写；不要直接去掉 `--no-index`，否则改变了实验的包来源。

## 2.4 查询位置、升级与卸载

以下表中 `PY` 是说明用占位符，不要原样粘贴。换成 `build/learning-tools/venv/a/Scripts/python.exe`；B 则把路径中的 `a` 改成 `b`。

| 命令 | 作用和应观察的结果 |
| --- | --- |
| `PY -m pip --version` | 显示 pip 的版本与安装目录，应属于 A |
| `PY -m pip list` | 查询已安装的分发包，应含 `lab-greeting 1.0.0` |
| `PY -m pip show lab-greeting` | 查看版本、依赖和 `Location` 安装位置 |
| `PY -c "import lab_greeting; print(lab_greeting.__file__)"` | 查看这次实际导入的代码文件 |
| `PY -m pip check` | 检查已声明依赖是否兼容，本例应无损坏要求 |
| `PY -m pip uninstall lab-greeting` | 询问后卸载该环境中的包，不删除教材源码 |

`__file__` 是模块属性名，指向实际导入文件。安装位置与导入位置相互核对，可以发现当前目录下同名代码抢先被导入的情况。`pip check` 只检查分发包声明关系，不执行你的业务测试。

把 A 升级到第二版的完整命令：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse --upgrade lab-greeting==2.0.0
build/learning-tools/venv/a/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/a/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==1.0.0
```

Linux/macOS 按准备章将解释器路径换成 `bin/python`。最后一条恢复 A 第一版，为下一章准备。固定版本安装既可以升级也可以降级；不固定版本的 `--upgrade` 可能选择另一个版本，因此团队升级要检查变更并运行测试。

失败实验：卸载 B 的 `lab-greeting` 后重新导入，预期出现 `ModuleNotFoundError`（找不到模块），但 A 仍应正常输出 v1。随后重新执行 B 的安装命令恢复。这个“B 失败而 A 成功”的反例比只观察成功更能说明隔离范围。

## 2.5 修改挑战与清理

不修改原始教学包，复制 `package_v2` 到 `build/learning-tools/venv/package_v3`，将版本改为 `3.0.0`，把问候语改为 `from v3`；沿同一流程构建并安装到 B。预测 A 是否变化，再运行验证。参考答案：A 保持 v1，因为修改和安装都没有写入 A 的包目录。

保留 wheelhouse 后，A/B 可随时重建。清理时删除实验环境、wheelhouse 与自己复制的源码目录即可；原始 `labs/` 不删。构建工具可能在源码旁生成 `build/` 和 `*.egg-info/`，它们是被忽略的打包产物，不是手写源代码。
