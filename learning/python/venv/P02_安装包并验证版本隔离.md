# 2. 安装包并验证版本隔离

上一章创建了 A/B，并能选择由谁执行程序。但环境刚创建好时，只有基础运行能力，并没有自动装入应用需要的所有第三方库。就像能启动编译器不等于已经拿到某个工程的依赖库一样，我们还要把所需代码准备到正确的位置。

本章始终追踪一个问题：同一份应用调用同名函数，为什么 A 输出 v1、B 输出 v2？我们先看被安装的是什么，再看它如何进入环境，最后检查实际调用来自哪里。所有命令仍从仓库根目录执行，沿用上一章的 build/learning-tools/venv/a 和 b。

## 2.1 看懂最小教学包

先看应用将要执行的代码：

```python
from lab_greeting import greet
print(greet())
```

第一行让 Python 找到名为 lab_greeting 的代码，再取出其中的 greet 函数；第二行调用并打印结果。这里没有写“第一版”或“第二版”，所以版本选择并不发生在这两行代码里，而发生在解释器能找到哪一份 lab_greeting 上。

教材提供两份源码。第一版的 greet 返回 `hello reader from v1`，第二版返回 `hello reader from v2`。这个差异故意很小，使我们只观察工具如何选包，不把业务逻辑混进来。代码在各自 src/lab_greeting/__init__.py 中；src 是本例的源码目录，__init__.py 让 lab_greeting 成为一个普通的 **Python 包（package）**，可按名称导入。

接着看安装者需要的信息。它不能只复制某个碰巧叫 src 的目录，还需要知道安装名称、版本、代码位置和打包方式。这些信息写在 [pyproject.toml](labs/package_v1/pyproject.toml)，它是 Python 项目配置文件，使用 TOML（Tom's Obvious Minimal Language）格式，方括号划分配置区域。

本例配置让工具做三项决定：project 区域给出分发名称 lab-greeting 和版本 1.0.0；tool.setuptools.packages.find 让工具到 src 中找包；build-system 指定负责生成安装文件的工具。负责安装交付的整体称为**分发包（distribution package）**，代码里导入的则是**导入包（import package）**。两种名称不保证一致，本例用连字符的 lab-greeting 安装，用下划线的 lab_greeting 导入。

最后才需要认识 **setuptools**：它是本例选择的打包工具。pip 将打包任务交给的组件叫**构建后端（build backend）**，本例配置为 setuptools.build_meta。这个依赖只为“做出安装包”服务，问候函数运行时并不调用 setuptools。先分清打包时和运行时，下一节为什么单建 builder 就容易理解了。

查看[官方 pyproject 指南](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#declaring-the-build-backend)时，可对应寻找“谁打包”和“项目叫什么”两个区域，不必先背下全部配置字段。

## 2.2 先产生安装文件

拿到源码以后，可以让工具边构建边安装；这里把两步拆开，让中间产物能看见。**wheel** 是 Python 的可安装归档格式，后缀为 .whl。本章的 wheelhouse 只是保存这些文件的目录名称，没有后台服务。

整条过程是“包的源码→打包工具→wheel 文件→pip 安装→某个环境的包目录”。**pip** 是安装工具名称；它也提供 wheel 子命令来组织构建，但真正如何打包由前面指定的后端完成。builder 只准备打包工具，A/B 只装应用需要的问候包，便于稍后观察依赖记录。

当前位置：仓库根目录。A/B 已按第一章建立。先为构建单独创建 `builder` 环境，让业务环境只有教学包。UCRT64 Bash：

```bash
mkdir -p build/learning-tools/venv
cp -R learning/python/venv/labs/package_v1 build/learning-tools/venv/package_v1
cp -R learning/python/venv/labs/package_v2 build/learning-tools/venv/package_v2
py -3.12 -m venv build/learning-tools/venv/builder
build/learning-tools/venv/builder/Scripts/python.exe -m pip install setuptools==80.9.0
build/learning-tools/venv/builder/Scripts/python.exe -m pip wheel --no-deps --no-build-isolation --wheel-dir build/learning-tools/venv/wheelhouse ./build/learning-tools/venv/package_v1
build/learning-tools/venv/builder/Scripts/python.exe -m pip wheel --no-deps --no-build-isolation --wheel-dir build/learning-tools/venv/wheelhouse ./build/learning-tools/venv/package_v2
ls build/learning-tools/venv/wheelhouse
```

复制前确认目标 package_v1/package_v2 尚不存在；重新练习可换实验目录名，避免重复复制造成嵌套。应得到 `lab_greeting-1.0.0-py3-none-any.whl` 与 `lab_greeting-2.0.0-py3-none-any.whl`。本例是纯 Python 包，所以文件名表示适用于 Python 3、没有特定二进制接口与平台限制；带本地编译代码的包可能不能跨机器使用同一个 wheel。

先看前三步：mkdir 准备产物目录，cp -R 复制教学源码，venv 创建 builder。打包可能在源码旁生成元数据，所以操作复制品，保留教材原件。随后 builder 的 pip install 安装 setuptools，固定到本次验证过的 80.9.0。

再从第一条 wheel 命令看数据流：末尾的 ./build/.../package_v1 是输入源码；--wheel-dir 后面是产物目录；--no-deps 表示不继续构建它的运行依赖，本例确实没有这种依赖。第二条对 v2 做相同的事，最后 ls 查看两份产物。

最容易误读的是 --no-build-isolation。它说“使用当前 builder 里已经有的后端”，并没有说“请帮我装后端”。省掉前面的 setuptools 安装会失败。普通工程可以不加它，让 pip 另建临时构建环境并按 build-system 准备后端；本例主动准备后端，是为了看清并复用后续离线流程。

## 2.3 给 A 和 B 安装不同版本

现在有两份安装文件，还没有把它们放进 A/B。安装时必须同时回答两个问题：要哪个版本，从哪里取得它？

平时 pip 可以查询在线的**包索引（package index）**；PyPI（Python Package Index）是常用公共服务。本例已经有本地文件，因此 --no-index 禁止查询在线索引，--find-links 指定本地候选目录。`lab-greeting==1.0.0` 再从候选中要求准确版本。目录里同时放着 v1/v2，不代表两个版本都会进入同一环境。

UCRT64 Bash：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==1.0.0
build/learning-tools/venv/b/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==2.0.0
build/learning-tools/venv/a/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/b/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
```

先执行两条安装，再执行两条调用。输出应依次为 `hello reader from v1`、`hello reader from v2`。调用代码完全一样，改变的是最左边的解释器路径：A 从 A 的包目录取得第一版，B 从 B 的包目录取得第二版。正是这一对照，把第一章的目录关系变成了运行证据。

如果出现 `No matching distribution found`，意为没有找到满足要求的安装文件。检查 wheelhouse 的位置、构建是否成功和版本拼写；不要直接去掉 `--no-index`，否则改变了实验的包来源。

## 2.4 查询位置、升级与卸载

如果输出不对，先问“装进去了什么”，再问“运行时真正读了什么”：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m pip list
build/learning-tools/venv/a/Scripts/python.exe -m pip show lab-greeting
build/learning-tools/venv/a/Scripts/python.exe -c "import lab_greeting; print(lab_greeting.__file__)"
```

list 列出已安装的分发包，应该看到 1.0.0；show 显示该包的版本、依赖和 Location 安装位置；第三条不再问安装记录，而是实际导入并输出模块属性 __file__。它应指向 A 包目录里的代码。这三个观察逐渐缩小范围，不是同一结果的三种写法。

若 show 正确而 __file__ 指向别处，可能是同名源码抢先被导入，第四章会制造并解释这个错误。此时反复安装没有针对实际原因。

把 A 升级到第二版的完整命令：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse --upgrade lab-greeting==2.0.0
build/learning-tools/venv/a/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/a/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==1.0.0
```

Linux/macOS 按准备章将解释器路径换成 `bin/python`。最后一条恢复 A 第一版，为下一章准备。固定版本安装既可以升级也可以降级；不固定版本的 `--upgrade` 可能选择另一个版本，因此团队升级要检查变更并运行测试。

再验证隔离的边界：只卸载 B 的包，A 会不会跟着坏？

```bash
build/learning-tools/venv/b/Scripts/python.exe -m pip uninstall -y lab-greeting
build/learning-tools/venv/b/Scripts/python.exe -c "import lab_greeting"
echo $?
build/learning-tools/venv/a/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/b/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse lab-greeting==2.0.0
```

uninstall 删除指定环境中的安装；-y 为这个明确的教学操作跳过交互确认。B 导入应故意失败，报 ModuleNotFoundError，echo 显示非零退出码；A 仍输出 v1。最后重新安装 B，恢复本章原状态。源码和 wheelhouse 没有被卸载，所以能够恢复。

## 2.5 安装成功以后，还要验证应用接受它

安装器能验证声明的依赖要求，却不知道你的程序想要怎样的输出。因此 `pip check` 成功不能替代应用测试。使用仓库已经提供的测试模板，把这个区别做成反例：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m unittest discover -s learning/python/venv/labs/application/tests -v
build/learning-tools/venv/b/Scripts/python.exe -m pip check
build/learning-tools/venv/b/Scripts/python.exe -m unittest discover -s learning/python/venv/labs/application/tests -v
echo $?
```

unittest 是 Python 标准库测试框架；discover 搜索测试文件，-s 给出目录，-v 逐项报告。模板里的两条 assertEqual 断言要求默认名字和 board 名字都输出 v1，这代表旧应用的要求，而不是“任何安装的版本都应该对”。

A 应两项通过。B 的 pip check 应报告没有损坏的依赖关系，但应用测试应故意两项失败，因为 v2 输出不符合旧要求。你现在可以区分三层：包安装成功、Python 导入成功、业务行为满足要求。完整复制和改错过程也见[实训第 5 节](<labs/README.md#5. 同一个应用，在 A 通过，在 B 失败>)。

## 2.6 把方法用于自己的包

不修改原始教学包，复制 `package_v2` 到 `build/learning-tools/venv/package_v3`，将版本改为 `3.0.0`，把问候语改为 `from v3`；沿同一流程构建并安装到 B。预测 A 是否变化，再运行验证。参考答案：A 保持 v1，因为修改和安装都没有写入 A 的包目录。

保留 wheelhouse 后，A/B 可随时重建。清理时删除实验环境、wheelhouse 与自己复制的源码目录即可；原始 `labs/` 不删。构建工具可能在源码旁生成 `build/` 和 `*.egg-info/`，它们是被忽略的打包产物，不是手写源代码。
