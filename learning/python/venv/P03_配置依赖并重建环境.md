# 3. 配置依赖并重建环境

A 已能运行上一章的问候程序。现在同事拿到程序源码，却在导入 lab_greeting 时失败：源码写明了“我要使用这个模块”，并没有把那个模块自动安装到同事的 Python 中。

直接发送 A 目录看起来省事，但第一章已看到环境会引用本机基础 Python，启动脚本也可能记录原位置。我们应交付可重建它的材料：使用什么 Python、安装什么包、从哪里获得这些包，以及怎样验证安装后的程序。本章逐步把这几项分开保存，再用全新的 C 环境证明材料足够。

## 3.1 需求文件不是环境备份

先回看程序中的 `from lab_greeting import greet`：缺少这个包，程序就不能按预期工作。我们把这种需要的其他包称为 **依赖（dependency）**。上一章手工输入过 lab-greeting==1.0.0。把同样的要求写进文本文件，就不必让每个同事重新凭记忆输入。

本例 [requirements-v1.txt](labs/requirements-v1.txt) 只有一行：

```text
lab-greeting==1.0.0
```

这样的文本叫 **requirements 文件**，pip 用 `-r 文件路径` 读取它。文件名不必固定，但团队通常保留 requirements 这个名字以便识别。`==` 要求准确版本；写成 `>=1,<2` 则允许一个范围。范围表达了兼容意图，但半年后出现符合范围的新版本，重新安装时可能选到不同结果。

程序直接使用 lab-greeting，所以它是直接依赖。如果 lab-greeting 又需要另一个包，后者就是传递依赖。本例教学包没有其他运行依赖，因此只需这一行；复杂应用只固定直接依赖，还不足以固定整个组合。

如果环境已有许多包，不想手工抄版本，可以用 pip 的 **freeze** 子命令输出当前安装记录。注意它回答的是“现在装着什么”，不是“程序真正需要什么”：临时装来排错的包也可能被记进去。应先检查结果，再把它作为交付材料。它也不会运行程序、记录基础 Python 的安装包或打包操作系统库。

官方对照：[pip freeze](https://pip.pypa.io/en/stable/cli/pip_freeze/#description)，注意其记录当前安装状态的边界。本例使用简单快照就能验证重建；真实应用还需要记录 Python、平台和包来源。

## 3.2 保存快照并创建 C

当前位置：仓库根目录。确保 P02 末尾已把 A 恢复为第一版。UCRT64 Bash：

```bash
build/learning-tools/venv/a/Scripts/python.exe -m pip freeze > build/learning-tools/venv/requirements.txt
cat build/learning-tools/venv/requirements.txt
```

`-m pip` 让 A 的解释器运行自己的 pip，因此快照来自 A。Bash 的 `>` 把输出写入指定文件，文件已存在时会覆盖；cat 立即显示文件内容，避免在没有审查的情况下继续安装。在本次 Python 3.12/pip 25.0.1 基线中应只看到 lab-greeting==1.0.0；pip 自身默认不在该版本的 freeze 结果中。

再创建新的 C。C 原先不应存在，否则 venv 可能复用旧目录，实验就不能证明“从空环境重建”。

```bash
py -3.12 -m venv build/learning-tools/venv/c
build/learning-tools/venv/c/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse -r build/learning-tools/venv/requirements.txt
```

这次 install 没有直接写包名：`-r` 让 pip 从快照取得名称和版本，`--no-index` 禁止查询包索引，`--find-links` 指向上一章实际构建的 wheel 文件目录。需求文件负责“要哪个版本”，wheelhouse 负责“提供那个版本的文件”，二者缺一不可。只有名称和版本却拿不到包文件，仍无法安装。

最后分别检查运行行为和包声明：

```bash
build/learning-tools/venv/c/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
build/learning-tools/venv/c/Scripts/python.exe -m pip check
```

C 应输出 hello reader from v1，pip check 应报告没有损坏的依赖要求。第一条证明这个调用的行为正确；第二条只检查已安装包声明的依赖是否满足。上一章的业务测试还可以继续在 C 上运行，它检查的范围比这一句问候语更具体。这些证据说明本例能够重建，并不说明任意平台上的所有程序都会相同。

如果快照出现本机绝对路径，常见原因是当初直接从某个本地路径安装，或使用可编辑安装。检查并区分本机开发引用与发布需求，不能原样称为可跨机器复制的清单。

## 3.3 体验约束与安装要求的差别

假设团队确认第二版暂时不兼容，但不想修改各个项目的需求文件，希望统一增加“所有人暂时不要装到 2”的限制。此时可以提供 **constraints 文件**：它是选版本时额外施加的限制，不会主动要求安装其中的包。

先创建约束，再故意给出冲突请求。继续在仓库根目录使用 C：

```bash
printf '%s\n' 'lab-greeting<2' > build/learning-tools/venv/constraints.txt
build/learning-tools/venv/c/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse -c build/learning-tools/venv/constraints.txt lab-greeting==2.0.0
echo $?
```

printf 把引号中的一行写入文件；引号也避免 Bash 把 `<` 当成输入重定向。`-c` 表示读取约束，与 `-r` 的“读取安装要求”不同。pip 同时收到“等于 2.0.0”与“小于 2”，不存在能满足两者的版本，因而应报告冲突并返回非零退出码；echo 显示的是紧邻上一条命令的退出码。

恢复办法应针对矛盾本身：本例业务要求仍是第一版，因此把请求恢复为 1.0.0，不需要更换下载镜像。

```bash
build/learning-tools/venv/c/Scripts/python.exe -m pip install --no-index --find-links build/learning-tools/venv/wheelhouse -c build/learning-tools/venv/constraints.txt lab-greeting==1.0.0
build/learning-tools/venv/c/Scripts/python.exe -c "from lab_greeting import greet; print(greet())"
```

第一版满足限制，应该安装成功或提示已经满足，问候语仍来自 v1。本例冲突在解析阶段就被拒绝，原第一版仍在；不要据此把所有安装失败都概括为“不会改变环境”。也可以只在一个空环境运行带 `-c` 却没有包名和 `-r` 的 install：它不会替你安装约束里的包，而会提示缺少安装要求。

官方对照：[Constraints Files](https://pip.pypa.io/en/stable/user_guide/#constraints-files)，重点核对“只约束、不触发安装”。

## 3.4 配置为什么会被覆盖

前面的文件解决了“装什么”。换到网络慢的环境，还可能需要改变“等多久”；使用团队包仓库时，需要改变“去哪里查找”。这些是 pip 安装器的选项，不是应用依赖，通常不写进包版本快照。

先考虑影响范围：只为 C 调整超时，就不该让其他项目一起变化。**配置作用域（configuration scope）** 表示设置影响的范围。pip 可以读取系统、用户和当前虚拟环境配置文件，还接受环境变量和命令行选项。判断最终值时要同时查这些来源，而不是找到一个配置文件就认为它必然生效。

在 C 上操作，避免改用户全局设置。UCRT64 Bash：

```bash
build/learning-tools/venv/c/Scripts/python.exe -m pip config debug
build/learning-tools/venv/c/Scripts/python.exe -m pip config --site set global.timeout 30
build/learning-tools/venv/c/Scripts/python.exe -m pip config --site get global.timeout
build/learning-tools/venv/c/Scripts/python.exe -m pip config list
```

Linux/macOS 只需替换解释器路径。`--site` 表示当前环境的配置文件；Windows 通常是环境根的 `pip.ini`，POSIX 系统通常是 `pip.conf`。这里 `global.timeout` 的 `global` 是文件中的“所有 pip 子命令通用”分区名，**不表示修改用户全局文件**，写入位置由 `--site` 决定。

debug 先显示 pip 检查哪些文件以及文件是否存在。set 将值写入 C 的配置；get 应读到 30，证明写入成功。list 列出读取到的设置。接着临时添加环境变量，观察同一个选项出现新的来源：

```bash
PIP_TIMEOUT=5 build/learning-tools/venv/c/Scripts/python.exe -m pip config list
build/learning-tools/venv/c/Scripts/python.exe -m pip config --site unset global.timeout
```

PIP_TIMEOUT 是 pip 识别的超时环境变量。list 中通常同时能看到配置文件的 global.timeout 和来自环境变量的 :env:.timeout；该输出列举来源，不是一次实际网络等待测量。对这个选项，命令行优先于环境变量，环境变量优先于配置文件。因此即使文件仍是 30，本次调用应采用 5。文件内部还有命令专属分区等规则，遇到复杂配置先用 debug 和 list 查来源。

Bash 行首赋值只影响这次 pip 子进程，结束后外层终端原有值保持不变。第二条 unset 撤销刚写入 C 的设置；原来其他来源的值仍可能存在。若只想临时改变一次安装，也可在 install 命令中添加 `--timeout 10`，无需永久写文件。

需要私有索引时，把团队提供的地址用于 `python -m pip install --index-url URL 包名`；其中 `URL` 是说明用占位符，必须替换真实地址。环境配置可使用 `pip config --site set global.index-url 地址`，随后用 `config debug` 和 `config list` 核对。不要把带口令的地址提交到仓库，也不要把禁用证书校验当作常规连接方案。

官方对照：[pip Configuration](https://pip.pypa.io/en/stable/topics/configuration/#precedence-override-order)。阅读顺序是先看文件位置，再看覆盖顺序；不是搜索到某个配置文件就假定它最终生效。

## 3.5 把实验迁移到团队工作

同事重建时需要的是可共享的输入：源码、项目元信息、经过审查的依赖记录，以及能访问的包来源。环境目录是根据这些输入在每台机器上生成的结果，通常不提交 Git。这样项目搬家时重建环境即可，不必修补旧环境中的机器路径。

应用通常要交付已经测试过的依赖组合，所以更关心准确复现；供其他项目安装的库则要声明兼容范围，避免无理由地强迫所有使用者采用某一个版本，并测试支持范围的边界。**锁文件（lock file）** 通常用于记录工具解析后的完整依赖结果；其跨平台、哈希和重建保证取决于具体工具与格式。freeze 是当前安装快照，不能仅靠改名为 lock 就获得这些保证。

**持续集成（Continuous Integration，CI）** 是在代码变化后自动执行安装和测试的流程。给 CI 指定解释器版本，创建新环境，按声明安装并运行测试，比复用开发机残留环境更容易发现缺失依赖。下面是流程示意，`应用测试命令` 需要替换成项目实际入口，不是可执行命令：

```text
选择 Python 版本 → 创建新环境 → 按需求安装 → pip check → 应用测试命令
```

离线交付可以先在兼容平台用 `pip download -r requirements.txt -d wheelhouse` 下载依赖，再在目标环境用 `--no-index --find-links` 安装。有些下载结果是源码分发，仍需构建依赖和编译器；准备纯 wheel 集合时可用 `--only-binary=:all:` 让缺少 wheel 的包提前报错。版本号不能固定文件内容，高要求交付还应保存分发文件及哈希，并学习 `--require-hashes` 的完整依赖要求。[可重复安装说明](https://pip.pypa.io/en/stable/topics/repeatable-installs/)解释了从版本固定到文件校验的不同强度。

本例的挑战是删除可丢弃的 C，换目录 D 重建，不参考 A 中的文件，只使用基础 Python、wheelhouse 与需求文件。成功标准是输出 v1 且 `pip check` 通过。完成后可删除 C/D 和临时约束文件，保留需求文件作为学习记录。
