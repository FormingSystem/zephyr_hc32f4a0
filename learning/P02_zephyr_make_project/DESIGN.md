# 第1章\_Zephyr 工程入门专题设计

本文件规定专题的读者起点、章节分工和维护边界。只保留现行设计；章节入口见[大纲](大纲.md)，不在这里追加逐轮修改日志。

## 1.1\_读者起点与完成目标

读者已有 C/C++ 和嵌入式开发基础，但尚未掌握 Zephyr 的工程组织、依赖管理和构建规则。专题从“为什么选择 Zephyr”进入，逐步到达“能够组织并维护自己的应用与硬件支持”，不要求读者先懂 west、CMake 或设备树。

贯穿实践先使用官方 `hello_world` 应用与 `mps2/an386` 目标，建立可复查的构建基线，再加入普通模块、新增板和 HC32 适配。已有目标用于分离环境问题与移植问题，不能用它的构建成功替代 HC32 实板验证。

读完后，读者应能根据项目需求判断选型条件，定位应用和硬件支持文件，按允许的来源准备配套依赖，选择应用与目标完成构建，找到实际产物，并能区分配置、编译、模拟运行和实板验证各自证明了什么。

P010 §10.1.2 并列呈现 [west 工作区](assets/p010-board-target-selection.svg)和[直接 CMake 构建](assets/p010-cmake-target-selection.svg)的两棵命令树。两图沿用相同的应用和板目标，CMake 图另示本地模块的接入。[west 命令的枝线式对照稿](assets/p010-board-target-mindmap.svg)保留供版式比较。

工程映射图从当前实验的具体输入开始。讲配置命令时，在树根写出原命令和工作目录，将独立参数向下分支，每支连到实际读取的文件或字段，再给出相应的观察结果。讲模块登记时也可以从声明开始，例如由 `hc32_port/zephyr/module.yml` 的三个搜索根分别找到板、SoC 和设备树。两条路线的对应分支保持相同读序。审图时任选一个参数向下找到工程文件，再从一项产物反查输入。涉及发送顺序、异常抢占或周期长短的图，分别检验调用关系和时间轴。

## 1.2\_章节安排与承接关系

章节以组建工程时的选择为顺序。首次使用工具时交代它接收什么、为工程产生什么；用一项真实配置或一小段源码说明选择怎样生效。工具实现、生成宏的展开与完整排错记录按需查阅。

| 阅读阶段 | 章节 | 本阶段完成的认识与实践 | 这样安排的原因 |
| --- | --- | --- | --- |
| 决定是否采用 | P001 | 认识实时操作系统、Zephyr 的收益与采用成本 | 先理解选择理由，再投入环境准备 |
| 准备可用材料 | P002—P005 | 选择环境，准备主机工具、Python、SDK 和源码依赖 | 将工具安装、依赖取得与工程发现分开核验 |
| 对照源码建立工程全景 | P006 | 打开已有应用与硬件支持文件，区分主仓、模块和待生成的构建输出 | 读者已取得源码与依赖，此时再把概念映射到实际目录 |
| 完成首次构建 | P008 | 选择应用与硬件，找到单板固件 | P007 供编写 CMake 目标时参考，多镜像作为扩展实验 |
| 理解 west 构建入口 | P009 | 对照同一工作区和应用，解释扩展加载及构建调用 | 已见过底层过程后，再理解工具怎样组织它 |
| 追踪配置与排错 | P010—P012 | 从目标找到源文件，追踪驱动和输入发现，按缓存与失败阶段定位问题 | 将已有构建结果作为证据，避免孤立罗列机制 |
| 扩展自己的工程 | P013—P015 | 先接入普通模块，再接入厂商源码与适配，最后新增板和芯片支持 | 先验证模块接入，再增加硬件适配的复杂度 |
| 连接镜像与运行 | P016 | 解释内存放置、Cortex-M 启动、初始化与资源验证 | 把编译成功后的执行条件补成闭环，区分静态产物与运行证据 |

west 的完整讲解放在 P009，但不能让前面的命令成为黑盒。P002/P003 在准备处解释工具的必要用途，P005 就地解释清单、初始化和依赖获取；P006 对照已经存在的目录回收这些关系。P009 再从实际操作和产物展开机制，不要求读者提前跨章补齐第一条命令的背景。

章节顺序同时受概念和材料依赖约束：P001 不要求源码或工具；P002 的入口是所选主机与终端准备条件，出口是主源码；P003/P004 按 Windows 路线补齐工具，Linux 在自身 P002 完成；P005 的出口是匹配模块；P006 消费这些现有文件，但不把尚未构建的 build 目录当作已存在；P008 生成固件后，后章才分析实际产物与运行。新增章节不得只因“先建立全景”而前移实现细节。

P004 只承担 SDK 安装与发现方式的准备，不在模块尚未齐全时要求配置完整应用。显式 SDK、独立 ARM 工具链及缓存证据的额外对照实验集中在 [SDK 选择与构建证据](reference/SDK选择与构建证据.md)，由 P008 首次构建后的入口引出；核心首次构建仍在 P008 正文完成。

P010 从应用目录里的选板命令开始，经板与 SoC 关系讲到控制台，用发送一个字符解释设备对象与驱动如何配合。详细选源和实例展开保存在源码实验中。P011、P012 分别在需要改变构建输入和排查失败时使用。

## 1.3\_环境路线与内容边界

环境、网络和源码形态是不同选择条件，分别交代，再组合成可执行路线。不能把“有 Git 历史”当成“可以连接 GitHub”，也不能把“不能连接 GitHub”当成“不能使用 Git 或 west”。

| 选择条件 | 正文组织方式 |
| --- | --- |
| 主机系统与终端 | P002 分 Linux Bash、Windows PowerShell、Windows UCRT64 Bash 三篇；P003 补齐 UCRT64 的主机工具与 Python，P004 安装 Windows SDK，Linux 在自己的环境章完成对应准备 |
| 允许访问的来源 | P005 区分官方仓库、内部 Git/制品库与完全离线材料；已有材料先核验，不无条件重复下载 |
| 源码的取得形态 | Git 克隆与源码归档都要核对配套修订和模块；不以恢复 Git 历史作为本地编译的前提 |
| 构建入口 | P008 先以直接 CMake 说明输入与产物，P009 用 west 对照同一过程；构建入口与联网下载能力分别解释 |

三种环境的首次构建在 P008 汇合，后续深入实验默认采用明确标注的 UCRT64 路线。终端命令使用对应的路径语法；跨到 Windows 原生程序时，在交接处解释路径转换与读取者。实验目录标识不随章节编号迁移。

组件关系统一按职责解释：`arch/` 提供 CPU 架构共用支持，`soc/` 接入具体芯片或处理器系统，`boards/` 描述板级资源并提供相关工具配置。启动和链接可能跨层协作；驱动与厂商 HAL/DDL 各有职责；模块是源码包装与接入方式，不是另一层硬件。P006 建立关系，P010 用实际文件验证，P014/P015 再说明新增与复用范围。

环境讲解按 Linux 与 Windows 两类主机组织，Windows 的 PowerShell/UCRT64 为终端子路线。Linux 必须给出 Make 与 Ninja 的实际选择和独立输出目录；Windows 必须区分工具跨平台能力、CMake 生成器支持与 Zephyr 官方支持范围，不把缺少 mingw32-make 当成官方采用 Ninja 的已知原因。

本专题还承担 Linux 内核学习的构建基础：P007 建立生成器与执行器的分工，P008 完成 Linux Make 构建、两类主机的 menuconfig 操作及 Kbuild 对照，P009 解释 west 默认值与覆盖，P012 处理切换生成器和配置保存边界。Linux Kbuild 的 Makefile 来自内核源码，不是 CMake 生成物；不把 Zephyr 的 BOARD、SDK 或 prj.conf 当成内核构建接口。

## 1.4\_正文写法与篇幅安排

每个操作先交代正在处理哪份工程、对象在哪里、此时是否应存在，再给动作、参数含义和观察结果。解释使用代码原名与块内行号、配置文件与键、输出字段或图中节点定位；切换终端、应用或构建目录时重新说明输入和结果归属。

跨章前提在使用处用简短引用链接到准备小节，优先补链接，不重复讲解或堆前置清单；命令索引同样可返回对应正文。

术语在首次需要时解释，参数在实际使用处解释。章节间用尚未解决的问题衔接，不按审稿意见的到达顺序追加问答，也不让表格、命令清单或外链替代必要的因果说明。

长章按完整实践决定是否拆分：P008 保留同一应用的环境对照与多镜像产物定位；P010 保留从文件选择到驱动调用的追踪；P012 保留缓存变化与故障定位；P014/P015 分别保留依赖接入和新增硬件的完整操作。后续若出现独立问题，应拆成可单独完成的单元并同步引用，不以保留长章为由继续追加无关内容。

图示按其任务区分职责关系、构建数据流、运行调用和启动顺序。关键关系先用短问题引出图，再沿图中的对象、颜色和箭头展开文字；不把图放在长篇解释末尾作为摘要。图应显示参与者、交接内容与结果，不能只把段落装进方框。简单操作顺序可用 Mermaid，复杂关系使用独立 SVG 文件，保存在 assets/，正文通过标准 Markdown 图片语法与相对路径引用。SVG 保留自然尺寸与 viewBox，避免依赖脚本、外部字体或阅读器专用代码围栏；同一图以 SVG 为唯一维护资产。原有照片与截图继续保留，放在对应操作和观察结果旁。每张图下就地解释颜色、箭头、适用配置及省略边界。

图中文字与正文保持相近的实际阅读尺度；没有宿主样式数据时，以 16 px 字号、800 px 正文列宽预览，主标签、辅助说明和图例默认均为 16 px。核对显示宽度与 viewBox 的比例，不能只检查源文件字号。复杂图优先重排和拆图，不靠放大画布或缩小文字容纳。图下按“名称(英文全称-中文)：作用”解释首次出现的硬件模块与缩写，区分片内模块和外接器件。架构演变保持同一场景和对象，时间对照保持同一工作量、单位与比例。

P001 的 RTOS 入门沿鼠标、键盘和显示屏的通信路径展开，先建立控制器、轮询与中断的认识，再用主循环伪代码、事件循环、定时器、线程现场及栈切换解释并发来源。软件响应时间与画面可见时间分别讨论；示意耗时不写成板级测量结果。1.2 随后区分采用调度内核与采用 Zephyr 开发平台：通过显示传输与参数保存说明驱动并发接入、系统服务及工程规则的复用价值，不把其他 RTOS 一概写成没有生态，也不把统一驱动接口等同于任意并发调用保证。

## 1.5\_维护与验收

修改先明确受影响的认识和操作，再检查前置章节、当前正文与后续使用处。结构变化同步大纲、标题锚点、命令附件和实际入链；设计变化直接改写本文件对应段落，不新增日期小节或保留相互冲突的“当前方案”。

验收分为三部分：

- **阅读与定位：** 隐藏聊天背景和外链后，正文仍能说明原因、对象、操作与结果；读者能找到所指文件和参数。
- **材料一致性：** 链接、编号、稳定 ID、命令附件和行号对应有效，示例版本与来源可核对。
- **实践证据：** 分别记录语法检查、实际构建、模拟运行和实板测试，未执行的步骤不能写成已验证。

评审、验证日志等过程记录保存在本机忽略目录，不进入正文和阅读导航。本文件只在目标、章节职责或维护规则改变时更新。
