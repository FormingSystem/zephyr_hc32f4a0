# 第1章\_模块与外部项目

原文：[Modules (External projects)](https://docs.zephyrproject.org/latest/develop/modules.html)。读取日期：2026-10-12，`latest`。

Zephyr 复用多个由外部维护的成熟项目，避免重复实现。在 Zephyr 构建系统中，这些需要接入构建与配置的项目称为**模块（Module）**。

要成为默认模块清单的候选，外部项目应在 Zephyr 之外拥有独立生命周期：独立仓库、贡献与维护流程以及发布过程。只为 Zephyr 编写的代码通常应进入 Zephyr 主树，而不是单独作为这种外部模块。

纳入默认清单的模块须提供项目 **技术指导委员会（Technical Steering Committee，TSC）**认可的功能，符合许可及贡献要求，并有承诺维护其代码的 Zephyr 开发者。常见类型包括调试器集成、芯片厂商**硬件抽象层（Hardware Abstraction Layer，HAL）**、密码库、文件系统、**进程间通信（Inter-Process Communication，IPC）**库。有些模块，尤其厂商 HAL，还引用可选的**二进制组件（Binary Blob）**。

本页说明官方模块政策及构建接入。这里的要求针对 Zephyr 官方模块体系；它不是要求读者立即建立新仓库、修改清单或同步当前工程。

<a id="modules-vs-projects"></a>

## 1.1\_模块与west项目

Zephyr 模块不等于 **west项目（West Project）**，模块本身也不强制依赖 west。但使用 west 时，构建系统可以借助它发现模块。

模块通常通过 `zephyr/module.yml` 告诉 Zephyr 如何接入仓库源码。west 项目则是 `west.yml` 清单 `projects:` 下的条目，负责工作区中的项目获取与版本管理。

很多 west 项目同时也是模块，但工具等不进入最终固件的项目可能不需要模块接入。构建系统可通过 west 或 CMake 变量 `ZEPHYR_MODULES` 取得模块列表。本页模块政策不自动适用于所有普通 west 项目。west 项目的清单结构见[项目条目说明](https://docs.zephyrproject.org/latest/develop/west/manifest.html#west-manifests-projects)。

> 译注：被 west 下载、被构建系统识别为模块、实际参与某个固件的编译，是不同阶段。后文也保留构建系统兼容旧式目录的发现规则，不能把本节对 `module.yml` 的概括当作唯一历史形式。

## 1.2\_官方模块仓库约定

默认清单中的模块仓库应符合以下要求：

1. 托管在 GitHub 的 `zephyrproject-rtos` 组织下。
2. 仓库根的 `zephyr/` 目录内有 `module.yml`。
3. 新仓库名使用小写字母与连字符，不用下划线；直接追踪外部 Git 项目的模块可沿用上游名字。现有不符合命名规则的仓库不必重命名。
4. 在 `zephyr/module.yml` 显式设置模块名。
5. 主分支默认名为 `zephyr`；针对特殊用途、如 **长期支持（Long-Term Support，LTS）**版本的分支，以 `zephyr_` 开头。
6. 存在上游仓库时保留其目录结构。不要求另设一个镜像上游主分支的 `master`，原文也不推荐，以免与应作为主分支的 `zephyr` 混淆。
7. 公开头文件的包含路径应以模块名开头，例如 MCUboot 的 `bootutil/bootutil.h` 以 `mcuboot/bootutil/bootutil.h` 对外提供。

## 1.3\_与上游同步

优先同步外部项目最新稳定发行版。如果取得重要修正必须使用开发分支尖端，也允许采用，但每次更新必须记录理由。

### 1.3.1\_允许操作的前提

模块主分支的改动，包括上游同步，只能通过**拉取请求（Pull Request，PR）**进入。PR 应能由 Zephyr **持续集成（Continuous Integration，CI）**验证，并能正常合并，例如使用 GitHub 的 **变基并合并（Rebase and Merge）**或**创建合并提交（Create a Merge Commit）**。

这样变更可以审查，下游历史持续增长，已有提交、标签等得到保留，也能对即将引入的改动运行 Git 风格、身份及许可证检查。禁止强制推送模块主分支。

### 1.3.2\_两种同步方式

| 方式 | 做法及取舍 |
| --- | --- |
| 上游差异快照 | 将上游变更形成一个快照提交，经 PR 提交到模块主分支，可用 Rebase and Merge 合并。方法简单、普遍适用，但不保留逐项上游历史。上游没有 Git 仓库时，这是唯一允许方式。 |
| 合并上游分支 | 先 Git merge 目标上游主分支或发行分支，再提交 PR，并使用 Create a Merge Commit 合并。适合上游有 Git 仓库的项目，保留上游原始提交标识，但下游会多出两个合并提交。 |

快照提交消息应写明上游项目地址、更新到的版本或标签、适用时的提交标识，以及更新原因。模块负责人选择同步方式后，应在该仓库一致采用。

## 1.4\_角色、维护与贡献

与上游同步需要明确谁负责审查、谁有合并权限，以及主树改动影响模块时由谁修复。以下规则将这些责任分配给仓库角色和改动提交者。

### 1.4.1\_角色职责

**管理员（Administrator）**管理仓库访问权限，例如按模块负责人请求添加协作者。管理员属于[项目角色](https://docs.zephyrproject.org/latest/project/project_roles.html#project-roles)中定义的 Administrators 团队，拥有模块 GitHub 仓库管理权限。

**模块代码负责人（Module Owner）**对仓库内容总体负责，需要组织代码审查，作为主分支 PR 的默认受理人，按需请求增加协作者，定期按既定方式同步上游，关注上游安全漏洞并在修复可用后及时纳入，还要在 Zephyr 发布说明中列出模块现存已知漏洞。模块负责人不一定是 Zephyr **维护者（Maintainer）**。

**合并者（Merger）**职责由 Zephyr 发布工程团队承担，有权并有责任将已批准的 PR 合并到模块主分支。

### 1.4.2\_保持与Zephyr主树兼容

Zephyr 的公共**应用程序编程接口（Application Programming Interface，API）**等变化可能要求修改模块。原改动提交者与模块负责人共同承担兼容维护责任。

提交者必须同时提交模块所需改动，使主树 PR 的 CI 及模块集成测试通过。负责人总体负责与主树同步和测试，除 CI 外还应不时开展更深入测试，并修复 PR CI 未发现的问题。

直接先向下游模块提交、尚未进入上游的改动应限于两类：适配 Zephyr 主树变化，或不能等待上游先合并的紧急修复，例如安全漏洞。若存在上游项目，重要设计或功能变化应优先直接提交上游，避免在下游形成大幅分叉。

### 1.4.3\_审查、清单与问题报告

模块遵守 Zephyr 通用贡献流程。PR 至少需要两份批准，其中包括受理人的批准，并且必须经过 Zephyr CI 验证。合并模块主分支时，应与 Zephyr 主树的相应清单更新配套。

模块仓库故意关闭独立 GitHub issue，以集中报告问题。模块缺陷或增强请求应在 [Zephyr 主仓库问题列表](https://github.com/zephyrproject-rtos/zephyr/issues)建立，按适用模块添加标签。可以建立问题用于追踪上游缺陷，但这类跟踪项不应影响原文所指的 [Zephyr 发布质量标准](https://docs.zephyrproject.org/latest/project/release_process.html#release-quality-criteria)。

## 1.5\_许可、文档、测试与退出维护

模块进入默认清单后，还需要持续满足许可、说明和集成测试要求。失去维护或不再符合要求时，则按弃用流程退出，而保留旧版本依赖的仓库。

### 1.5.1\_许可要求

模块源码文件应具有许可证头，除非模块的主许可证明确覆盖没有单独头部的文件。Zephyr 开发者仅在外部项目本来提供对应主许可证，且其为符合 **开放源代码促进会（Open Source Initiative，OSI）**要求的宽松许可证时，将其作为主许可证引入。

主许可证最好包含完整文本，而非只有 **软件包数据交换（Software Package Data Exchange，SPDX）**许可证标识。如果存在多个主许可证，必须明确每个文件适用哪一个。单文件许可证头优先于主许可证；任何新增内容都必须有许可覆盖。

Zephyr 推荐“文件头加主许可证”方式，但若上游通过单份或多份许可证采用自己的明确分配规则，也可在符合要求时接受并沿用。创建模块仓库时，应导入上游已有主许可证，并在 README 说明文件或 **YAML（YAML Ain't Markup Language，配置数据格式）**文件中说明默认许可。新增内容的 PR 必须启用 CI 许可证检查。

### 1.5.2\_必需文档

每个模块仓库必须有一份 **reStructuredText（RST，结构化文本标记格式）**的 `.rst` 文档，说明模块范围及目的、如何接入 Zephyr、仓库负责人、与上游同步的版本或提交信息，以及许可信息。这份文件是纳入模块的必要条件，内容应保持更新。

### 1.5.3\_集成测试

所有模块都应提供一定程度的**集成测试（Integration Testing）**，验证与 Zephyr 的接入能工作。可以在 Zephyr 主树放最小示例与测试，覆盖配置和基本 API 使用；模块 PR 中应由 Twister 构建并执行，例如在 QEMU 中运行。

候选新模块必须具有相应集成测试。厂商 HAL 会通过目标平台上的 Zephyr 构建及运行测试被间接覆盖，因此原文不要求它们另外提供集成测试。

集成测试不替代外部项目自己的功能验证。某些上游包含专为 Zephyr 编写的测试，这些可以纳入 Zephyr 测试框架，但并非强制。

### 1.5.4\_弃用与移除

缺少维护者、上游许可变化或代码过时等都可能导致**弃用（Deprecation）**。模块信息应标明弃用，构建系统使用它时应警告。经过两个 Zephyr 发行版后，可以从默认清单移除。

已移除模块的仓库仍应通过原始地址访问，因为旧版 Zephyr 仍依赖它们。

## 1.6\_构建系统怎样接入模块

`ZEPHYR_MODULES` 是 CMake 列表，记录模块根目录的完整位置。各模块用 `CMakeLists.txt` 说明如何构建，用 `Kconfig` 描述配置；构建系统通过 [`add_subdirectory()`](https://cmake.org/cmake/help/latest/command/add_subdirectory.html) 加入前者，并将后者接入 Kconfig 菜单树。

使用 west 时，构建系统可自动取得模块列表。希望保留自动发现结果并增加自己的模块时，设置 `EXTRA_ZEPHYR_MODULES` CMake 变量，或按环境约定在 [`.zephyrrc` 环境文件](https://docs.zephyrproject.org/latest/develop/env_vars.html#env-vars)中定义相应值。若环境变量、CMake 变量等多处都设置了它，最终附加列表合并各来源。

同名模块既来自 west 又来自 `EXTRA_ZEPHYR_MODULES` 时，附加列表中的自定义模块优先，适合临时换版本测试，而继续使用其他 west 模块。

> 译注：模块列表最终需要解析成完整目录，但公共说明不必写机器盘符。命令中可由当前位置、已有源码根变量或已定义模块根变量计算实际值。新增模块来源并不等于已经下载、识别或成功构建，还须具备后文所述真实文件。

若以 Zephyr 为清单仓库，希望持续为该工作区增加模块，也可以在 `submanifests` 目录添加 west 清单，详情见官方 [`submanifests/README.txt`](https://github.com/zephyrproject-rtos/zephyr/blob/main/submanifests/README.txt)。还可按后文手工指定列表；应用不需要模块时，也可完全不使用。

## 1.7\_module.yml名称与接入文件

模块通过 `zephyr/module.yml` 描述自身，使用前述 YAML 配置格式。

### 1.7.1\_稳定模块名

应显式写 `name`，避免模块名随用户目录名或 west 清单名字改变：

```yaml
name: <name>
```

CMake 中，`ZEPHYR_<MODULE_NAME>_MODULE_DIR` 表示模块根，`ZEPHYR_<MODULE_NAME>_CMAKE_DIR` 表示其接入用 `CMakeLists.txt` 所在目录。用于 CMake 和 Kconfig 变量时，模块名转大写，非字母数字字符变下划线，例如 `foo-bar` 对应 `ZEPHYR_FOO_BAR_MODULE_DIR`。

名为 `foo` 的模块可写：

```yaml
name: foo
```

未写 `name` 时使用模块目录名；例如 `<workspace>/modules/bar` 默认名为 `bar`。`foo`、`bar` 是示例名称，不是需要安装的模块。

### 1.7.2\_模块内部接入

`build.cmake` 指定包含接入 `CMakeLists.txt` 的目录，`build.kconfig` 指定 Kconfig 文件：

```yaml
build:
  cmake: <cmake-directory>
  kconfig: <directory>/Kconfig
```

二者均可省略，默认分别为 `zephyr` 与 `zephyr/Kconfig`。路径以模块根解析；若文件就在模块根，可写：

```yaml
build:
  cmake: .
  kconfig: Kconfig
```

### 1.7.3\_sysbuild接入

**系统构建（System Build，sysbuild）**使一个应用一次构建多个镜像。模块可以扩展它，例如增加自定义构建阶段或目标。专用接入文件使用：

```yaml
build:
  sysbuild-cmake: <cmake-directory>
  sysbuild-kconfig: <directory>/Kconfig
```

`sysbuild-cmake` 指向包含其 `CMakeLists.txt` 的目录，`sysbuild-kconfig` 指向其 Kconfig。文件位于模块 `sysbuild/` 目录时，例如：

```yaml
build:
  sysbuild-cmake: sysbuild
  sysbuild-kconfig: sysbuild/Kconfig
```

也可声明接入文件在外部 `MODULE_EXT_ROOT` 管理：

```yaml
build:
  sysbuild-cmake-ext: True
  sysbuild-kconfig-ext: True
```

这将接入描述放在模块仓库外部；具体查找关系见后面的外部集成说明。

## 1.8\_漏洞监测标识

若模块需要按外部项目身份追踪漏洞，例如它是其他仓库的分叉，可在 `security.external-references` 列出参考标识，支持 **通用平台枚举（Common Platform Enumeration，CPE）**与**软件包URL（Package URL，PURL）**。

```yaml
security:
  external-references:
    - <module-related-cpe>
    - <an-other-module-related-cpe>
    - <module-related-purl>
```

以密码与安全通信库 Mbed TLS 的模块为例，TLS 表示**传输层安全（Transport Layer Security）**协议：

```yaml
security:
  external-references:
    - cpe:2.3:a:arm:mbed_tls:3.5.2:*:*:*:*:*:*:*
    - pkg:github/Mbed-TLS/mbedtls@V3.5.2
```

CPE 字段须符合 **国家漏洞数据库（National Vulnerability Database，NVD）**提供的 CPE 2.3 模式；PURL 应符合原文引用的软件包 URL 规范。这里的版本标识供监测识别，不表示示例版本是当前推荐版本。

规范入口见 [CPE规范](https://csrc.nist.gov/projects/security-content-automation-protocol/specifications/cpe)与 [PURL规范](https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst)。

## 1.9\_构建期间的模块变量

模块被发现并按 `module.yml` 接入后，路径可由 CMake 与 Kconfig 变量读取。

> 译注：原文称有 `module.yml` 就会自动接入，这句话的前提是模块已经进入本次构建的发现范围；构建系统不会任意扫描整个磁盘。具体范围由 west 项目列表或显式 `ZEPHYR_MODULES` 等输入决定，详见后面的模块选择。

### 1.9.1\_普通Zephyr模块

两种配置系统都可访问 `ZEPHYR_<MODULE_NAME>_MODULE_DIR`。可用模块还自动生成 Kconfig 符号 `ZEPHYR_<MODULE_NAME>_MODULE`；声明二进制组件时，另生成 `ZEPHYR_<MODULE_NAME>_MODULE_BLOBS`，供其他配置表达依赖。

为了在缺少该模块时仍通过合规检查，原文推荐在 Zephyr 主树 `modules/` 下相应 Kconfig 中给这些符号提供默认定义。

CMake 的 `ZEPHYR_<MODULE_NAME>_CMAKE_DIR` 是实际加入构建的 `CMakeLists.txt` 所在目录；没有接入该文件时值为空。对于 `foo`，CMake 用 `${ZEPHYR_FOO_MODULE_DIR}`、`${ZEPHYR_FOO_CMAKE_DIR}`，Kconfig 用 `$(ZEPHYR_FOO_MODULE_DIR)`，注意语法不同。

变量还可检查模块是否存在：

```cmake
if(ZEPHYR_FOO_MODULE_DIR)
  # Do something if FOO exists.
endif()
```

Kconfig 可据模块根包含其他文件：

```kconfig
source "$(ZEPHYR_FOO_MODULE_DIR)/some/Kconfig"
```

处理每个模块 CMake 时，还提供当前对象变量：

| 变量 | 含义 |
| --- | --- |
| `ZEPHYR_CURRENT_MODULE_NAME` | 当前模块名。 |
| `ZEPHYR_CURRENT_MODULE_DIR` | 当前模块根目录。 |
| `ZEPHYR_CURRENT_CMAKE_DIR` | 当前模块接入 `CMakeLists.txt` 的目录。 |

这样模块脚本不必硬编码自己的名称，例如包含自身其他 CMake 文件：

```cmake
include(${ZEPHYR_CURRENT_MODULE_DIR}/cmake/code.cmake)
```

若模块首个 `CMakeLists.txt` 需要扩展上层 Zephyr 列表，先追加，再通过 **父作用域（Parent Scope）**传回。下面 `FOO_LIST` 是示例列表变量，`bar` 是示例元素，`PARENT_SCOPE` 是 CMake 设置上层变量的参数：

```cmake
list(APPEND FOO_LIST bar)
set(FOO_LIST ${FOO_LIST} PARENT_SCOPE)
```

实际用途之一是向 `SYSCALL_INCLUDE_DIRS` 增加目录，供**系统调用（System Call）**相关声明扫描。

### 1.9.2\_sysbuild模块变量

`SYSBUILD_CURRENT_MODULE_DIR` 指当前 sysbuild 模块根，CMake 中的 `SYSBUILD_CURRENT_CMAKE_DIR` 指接入文件所在目录，没有对应文件时为空。

CMake 使用 `${SYSBUILD_CURRENT_MODULE_DIR}` 及 `${SYSBUILD_CURRENT_CMAKE_DIR}`；Kconfig 使用 `$(SYSBUILD_CURRENT_MODULE_DIR)`。例如包含额外 Kconfig：

```kconfig
source "$(SYSBUILD_CURRENT_MODULE_DIR)/some/Kconfig"
```

或者包含 CMake 文件：

```cmake
include(${SYSBUILD_CURRENT_MODULE_DIR}/cmake/code.cmake)
```

模块首个 `CMakeLists.txt` 同样可以追加列表并传回父作用域：

```cmake
list(APPEND FOO_LIST bar)
set(FOO_LIST ${FOO_LIST} PARENT_SCOPE)
```

### 1.9.3\_sysbuild调用钩子

模块可定义 **构建钩子（Build Hook）**函数，让 sysbuild 在预定阶段调用：

| 函数形式 | 调用时机 |
| --- | --- |
| `<module-name>_pre_cmake(IMAGES <images>)` | 所有镜像开始 CMake 配置之前，对各模块调用。 |
| `<module-name>_post_cmake(IMAGES <images>)` | 所有镜像完成 CMake 配置之后。 |
| `<module-name>_pre_domains(IMAGES <images>)` | sysbuild 创建 domains YAML 之前。 |
| `<module-name>_post_domains(IMAGES <images>)` | domains YAML 创建之后。 |

`IMAGES` 后是本次将创建的 Zephyr 镜像列表。名为 `foo` 的模块若要在配置结束后处理，应定义 `foo_post_cmake()`；加载模块时提供的 `SYSBUILD_CURRENT_MODULE_NAME` 可以生成正确函数名：

```cmake
function(${SYSBUILD_CURRENT_MODULE_NAME}_post_cmake)
  cmake_parse_arguments(POST_CMAKE "" "" "IMAGES" ${ARGN})

  message("Invoking ${CMAKE_CURRENT_FUNCTION}. Images: ${POST_CMAKE_IMAGES}")
endfunction()
```

> 译注：`cmake_parse_arguments` 将参数解析到 `POST_CMAKE` 前缀变量，`POST_CMAKE_IMAGES` 是解析出的镜像列表；`ARGN` 是额外函数实参，`CMAKE_CURRENT_FUNCTION` 是当前函数名。这些钩子处于构建配置流程，不是固件运行时回调。

## 1.10\_模块依赖和处理顺序

模块可能需要其他模块存在，也可能因 CMake 目标依赖而要求在另一模块之后处理。通过 `build.depends` 声明：

```yaml
build:
  depends:
    - <module>
```

例如 `foo` 依赖 `bar`：

```yaml
name: foo
build:
  depends:
    - bar
```

这既要求 `bar` 存在，也保证先处理 `bar` 再处理 `foo`。

> 译注：声明构建依赖不会自行从网络下载缺失仓库，获取仍由 west 等依赖管理步骤完成。

## 1.11\_把接入文件放到模块外部

`MODULE_EXT_ROOT` 是 CMake 根目录列表，用于查找位于模块仓库之外的接入文件。

### 1.11.1\_Zephyr自带接入

Zephyr 对部分已知模块自带 CMake 与 Kconfig 文件，位于：

```text
<ZEPHYR_BASE>
└── modules
    └── <module_name>
        ├── CMakeLists.txt
        └── Kconfig
```

### 1.11.2\_自定义外部接入根

可以自行创建相同布局，为额外模块提供接入：

```text
<MODULE_EXT_ROOT>
└── modules
    ├── modules.cmake
    └── <module_name>
        ├── CMakeLists.txt
        └── Kconfig
```

然后在应用配置时通过 `-DMODULE_EXT_ROOT` 传入根目录列表。模块也可通过后面的 `build.settings.module_ext_root` 把自身相应位置加入列表。

Zephyr 源码根 `ZEPHYR_BASE` 总会以最低优先级加入，因此自定义根可以覆盖主树 `modules/<module_name>` 的接入实现。

`modules.cmake` 必须设置专有变量，告诉构建系统实际接入文件在哪：`ZEPHYR_<MODULE_NAME>_CMAKE_DIR` 是 CMake 文件目录，`ZEPHYR_<MODULE_NAME>_KCONFIG` 是 Kconfig 文件路径。

以 `foo` 为例，自行创建：

```text
<MODULE_EXT_ROOT>
└── modules
    ├── modules.cmake
    └── foo
        ├── CMakeLists.txt
        └── Kconfig
```

在其中 `modules.cmake` 写入：

```cmake
set(ZEPHYR_FOO_CMAKE_DIR ${CMAKE_CURRENT_LIST_DIR}/foo)
set(ZEPHYR_FOO_KCONFIG   ${CMAKE_CURRENT_LIST_DIR}/foo/Kconfig)
```

`CMAKE_CURRENT_LIST_DIR` 是当前脚本所在目录；这里由它拼出 `foo` 子目录，不绑定任何机器位置。

### 1.11.3\_模块声明使用外部接入

模块自己的 `zephyr/module.yml` 通过下列字段表明接入描述放在 `MODULE_EXT_ROOT`：

```yaml
build:
  cmake-ext: True
  kconfig-ext: True
```

模块仍提供自身源码和身份，外部根提供如何接入 Zephyr 的控制文件。Zephyr 仓库自身始终属于外部接入根之一。

## 1.12\_附加构建根目录

`build.settings` 可为构建系统增加其他搜索根，所有值均相对模块根解析：

| 字段 | 目录约定 |
| --- | --- |
| `board_root` | 额外板定义位于该根下的 `boards/`。 |
| `dts_root` | 额外架构或 SoC 相关设备树文件位于 `dts/`。 |
| `snippet_root` | **配置片段（Snippet）**的 `snippet.yml` 位于 `snippets/` 或其子目录。例如值为 `foo` 时搜索模块的 `foo/snippets/`。 |
| `soc_root` | 额外**片上系统（System on Chip，SoC）**定义位于 `soc/`。 |
| `arch_root` | 额外架构定义位于 `arch/`。 |
| `module_ext_root` | 外部模块接入文件按上一节的 `modules/` 布局提供。 |
| `sca_root` | **静态代码分析（Static Code Analysis，SCA）**工具实现在 `sca/<tool>/`，每个工具目录内有 `sca.cmake`。 |

例如以下 `module.yml` 设置：

```yaml
build:
  settings:
    board_root: .
    dts_root: .
    soc_root: .
    arch_root: .
    module_ext_root: .
```

对应目录结构为：

```text
<zephyr-module-root>
├── arch
├── boards
├── dts
├── modules
└── soc
```

> 译注：原文此处叙述偶写 `module.yaml`，本页实际发现入口及全部例子使用 `zephyr/module.yml`。根目录是搜索入口，不是让读者把所有定义直接写进根目录本身。 另外，原文表中 `sca_root` 的 `sca/<tool>` 少写了一层；[静态分析详细接入说明](../sca/P001_静态代码分析入口.md)及仓库 `cmake/modules/FindScaTools.cmake` 实际使用 `<sca_root>/cmake/sca/<tool>/sca.cmake`，自建目录应采用完整层级。

## 1.13\_Twister发现模块测试

`zephyr/module.yml` 可以列出样例、测试以及树外板目录，供测试运行器使用，例如：

```yaml
build:
  cmake: .
samples:
  - samples
tests:
  - tests
boards:
  - boards
```

这些 `samples`、`tests`、`boards` 是面向 Twister 的路径字段。仅填写它们不会使 Twister 自动测试模块；执行时仍需把路径加入命令行，例如先生成参数文件：

```sh
./scripts/zephyr_module.py --twister-out module_tests.args
if [ -s module_tests.args ]; then
    west twister +module_tests.args --outdir module_tests ...
fi
```

> 译注：原例在 Zephyr 源码根的 Bash 执行，`module_tests.args` 是 `scripts/zephyr_module.py` 生成的文件，`[ -s ... ]` 判断它存在且非空；Twister 的 `+文件名` 读取其中参数。末尾 `...` 代表实际额外选项，应替换或去掉，不是可直接执行的参数。`--outdir module_tests` 指生成测试产物目录。本次没有运行该脚本。

<a id="modules-bin-blobs"></a>

## 1.14\_二进制组件元数据

二进制组件必须归属一个 Zephyr 模块，元数据完整保存在 `module.yml` 的 `blobs` 中。可以通过 `west blobs` 获取；不用 west 时则自行下载并验证。

`blobs` 是映射列表，每项包含：

| 字段 | 含义 |
| --- | --- |
| `path` | 相对模块 `zephyr/blobs/` 的组件文件路径。 |
| `sha256` | 文件的 **256位安全哈希摘要（Secure Hash Algorithm 256，SHA-256）**，用于校验文件内容。 |
| `type` | 组件类型，当前限于 `img` 或 `lib`。 |
| `version` | 版本字符串。 |
| `license-path` | 相对模块根的许可证文件路径。 |
| `url` | 获取位置及相应协议；单个字符串或列表，列表中后续地址作为同一组件的下载回退来源。 |
| `description` | 人类可读描述。 |
| `doc-url` | 官方文档地址。 |

还可提供 `click-through`，表示下载前是否需要接受点击确认的许可；`size` 是字节大小，部分下载器可能要求；`fetcher` 指定下载方法，未设置时从 URL 推断。

组件类别和提交政策见官方 [二进制组件（Binary Blobs）](../contributing/P008_二进制文件.md#bin-blobs)，命令说明见 [west blobs](https://docs.zephyrproject.org/latest/develop/west/zephyr-cmds.html#west-blobs)。

> 译注：文件摘要验证、获取成功及使用许可是不同事项，不能相互代替。

## 1.15\_包管理器依赖与外部运行器

模块可以声明包管理器依赖，当前仅支持 Python 的 pip。`west packages <manager>` 列出 Zephyr 与支持此功能的已发现模块依赖，详细选项可查 `west help packages`。

`west packages pip` 默认列出需求文件；加 `--install` 且已激活**虚拟环境（Virtual Environment）**时安装。例如：

```yaml
package-managers:
  pip:
    requirement-files:
      - scripts/requirements-build.txt
      - scripts/requirements-doc.txt
```

这两个文件位于模块 `scripts/`，分别保存构建及文档依赖。格式见 [pip需求文件规范](https://pip.pypa.io/en/stable/reference/requirements-file-format/)。声明依赖、列出依赖和执行安装是不同动作。

如果模块中的树外板需要自定义烧录或调试**运行器（Runner）**，可声明 Python 文件：

```yaml
runners:
  - file: scripts/my-runner.py
```

执行 `west flash` 或 `west debug` 时导入这些文件，注册其中 `ZephyrBinaryRunner` 的子类。文件应由模块提供，相关接口见 [west运行器](../west/大纲.md)。

## 1.16\_选择本次构建使用的模块

模块元数据描述接入方式，但本次构建还需要确定从哪些模块根目录读取它。使用 west 自动发现、手工指定完整列表，以及完全不使用模块，分别对应下面三种情况。

### 1.16.1\_使用west发现

west 可用且没有提前设置 `ZEPHYR_MODULES` 时，构建系统运行 `west list` 取得项目路径，再逐项过滤：

1. 有 `zephyr/module.yml`：按其内容决定接入文件。
2. 没有该文件：检查 `zephyr/CMakeLists.txt` 与 `zephyr/Kconfig`，二者同时存在则作为旧式模块接入。
3. 都不满足：不是模块，不加入列表。

因此 west 项目列表是发现输入，元数据判定是筛选过程；工具项目不会因被下载就自动进入固件构建。

### 1.16.2\_手工指定

不用 west，或不希望用它发现模块时，可以自行指定 `ZEPHYR_MODULES`。列表中的每个目录仍须满足上述元数据或旧式双文件条件。

方法一，在 CMake 命令行设置：

```sh
cmake -DZEPHYR_MODULES=<path-to-module1>[;<path-to-module2>[...]] ...
```

> 译注：这是原文语法示意。尖括号和方括号代表替换项、可选项；实际传多个模块时，需保护 CMake 列表分号，避免被 Shell 当成命令分隔符，并使各项解析为实际模块根。它是替换完整发现列表，不是额外追加；只追加通常用 `EXTRA_ZEPHYR_MODULES`。

方法二，在应用顶层 `CMakeLists.txt` 中、`find_package(Zephyr ...)` 之前设置：

```cmake
set(ZEPHYR_MODULES <path-to-module1> <path-to-module2> [...])
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
```

`find_package` 会启动 Zephyr 包的构建配置，设置晚了就错过模块发现阶段。`REQUIRED` 表示找不到包应报错，`HINTS $ENV{ZEPHYR_BASE}` 从环境变量读取包搜索提示。

方法三，自行创建预加载 CMake 脚本，例如 `zephyr-modules.cmake`：

```cmake
# Put this in a file with a name like "zephyr-modules.cmake"
set(ZEPHYR_MODULES <path-to-module1> <path-to-module2>
  CACHE STRING "pre-cached modules")
```

在 CMake 命令行通过 `-C zephyr-modules.cmake` 预载缓存。这里 `CACHE STRING` 把列表保存为字符串缓存项；重新使用构建目录时，应考虑已有缓存值，不能把改动文件等同于旧缓存已自动失效。

### 1.16.3\_不使用模块

没有 west，也没有自行指定 `ZEPHYR_MODULES` 时，不加入额外模块。仍可构建不依赖外部仓库代码或配置项的应用。

## 1.17\_提交模块改动的协作流程

Zephyr 主树需要引用模块改动，才能在集成环境中验证。已合并内容可由提交哈希、标签或分支引用；尚在 PR 中的模块改动，则在清单的版本字段 `revision` 指向其 PR 引用。

为了避免把临时 PR 引用误合并进主树，主树 PR 应标为 **请勿合并（Do Not Merge，DNM）**，最好设为**草稿拉取请求（Draft Pull Request）**。原文说明草稿可减少审查就绪前的自动通知。模块先审查合并后，再由提交者或维护者把清单 `revision` 改成反映该改动的永久提交哈希。

多个模块之间有依赖时也使用同样流程，对每个相关模块分别修改清单引用。

<a id="submitting-new-modules"></a>

### 1.17.1\_提交新模块

先按官方 [外部代码提交与审查流程](../contributing/P012_外部组件贡献.md#external-src-process)取得 TSC 认可。项目团队创建并初始化仓库，将提交者加入协作者；若模块是上游 GitHub 项目的分叉，Zephyr 相关文件和差异维护在 `zephyr` 分支。

按贡献规则提交模块内容，再向主树 `west.yml` 加入：

```yaml
- name: <name of repository>
  path: <path to where the repository should be cloned>
  revision: <ref pointer to module pull request>
```

例如名为 `my_module` 的模块：

```yaml
- name: my_module
  path: modules/lib/my_module
  revision: pull/23/head
```

`pull/23/head` 指模块仓库的第 23 号 PR，不是版本号。模块审查合并后，必须换成模块仓库的实际提交哈希。

<a id="changes-to-existing-module"></a>

### 1.17.2\_修改已有模块

先向已有模块仓库提交 PR，遵守[贡献指南](../contributing/P002_贡献指南.md#contribute-guidelines)及[贡献者要求](../contributing/P003_贡献者职责.md#contributor-expectations)。再向 Zephyr 主树提交配套 PR，修改清单条目：

```yaml
- name: <name of repository>
  path: <path to where the repository should be cloned>
  revision: <ref pointer to module pull request>
```

对应例子仍是：

```yaml
- name: my_module
  path: modules/lib/my_module
  revision: pull/23/head
```

待模块改动合并，再把 PR 引用替换为最终提交哈希。这个流程保持模块仓库变更与主树清单验证相互关联；本译文没有创建、提交或合并任何 PR。
