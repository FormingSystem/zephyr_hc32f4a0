## 5.4\_源码跟踪译注

> 译注——使用入口与返回约定：应用通过所选C库的`<errno.h>`访问错误号；此处可见errno.h是Minimal C Library版本。errno宏展开为(*z_errno())，它是可读写的错误号存储位置，宏本身不会根据某次函数返回值自动更新。若具体接口约定直接返回-EINVAL等负错误码，应按该返回值处理；若约定失败返回-1并设置errno，应按该接口的失败条件读取errno。成功后不能假定errno自动清零，也不能把任意非零errno当作刚才调用失败的证据。

> 译注——编号与别名：保留本次最小C库所有数值及符号，不用主机系统错误号替换。例如这里ENOSYS为88、ETIMEDOUT为116；跨C库或主机交换错误信息时应按协议转换，不直接假定整数相同。EWOULDBLOCK直接别名到EAGAIN，但ENOTSUP为134、EOPNOTSUPP为95，两者在本头文件中不是同一数值。

> 译注——原文措辞：表中Not owner、No such context、Not enough core和Not a typewriter等历史描述按原文译出。core在此指内存，不是CPU核心数量；ENOTTY的打字机说法是历史终端措辞。EDOM原文写Argument too large，但不能由此推断它只适用于正向越界，具体数学函数应按自身定义域说明判断。列出错误号不代表Zephyr实现了该错误所涉及的全部POSIX或STREAMS功能。

> 译注——存储分支：z_errno()先检查CONFIG_LIBC_ERRNO，直接返回外部C库errno的地址；否则CONFIG_ERRNO_IN_TLS使用线程局部存储（Thread Local Storage，TLS）的z_errno_var；再否则声明为系统调用（System Call），由errno.c返回当前线程对应位置。用户空间（Userspace）分支使用userspace_local_data->errno_var，其他分支使用线程结构中的errno_var。不能把它理解为所有线程共享一个普通全局int。

> 译注——配置与边界：CONFIG_ERRNO默认启用；CONFIG_ERRNO_IN_TLS依赖ERRNO、THREAD_LOCAL_STORAGE且不使用LIBC_ERRNO，满足条件时默认启用，可避免用户空间访问该值所需的系统调用。内部头文件被单独放置是为了避免errno.h与kernel.h相互包含；应用不应据此绕过所选C库的公开入口。这里分析当前线程的存储实现，不把它推广为中断上下文可用性的保证。

> 译注——版权与版本：errno源码保留Wind River及加州大学董事会的版权文字、Berkeley软件许可说明和历史标记；不以中文文件的整体说明覆盖原有声明。本次源码浏览页的非注释内容与所下载头文件一致，本地源码链接用于跟踪，不能保证任意本地基线与滚动main相同。
