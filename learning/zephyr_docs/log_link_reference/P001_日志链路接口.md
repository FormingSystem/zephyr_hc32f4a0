## 1.6\_详细说明（Detailed Documentation）

<a id="ga9cf22f4fc8fb8c964396d6502fb20522"></a>

### `LOG_LINK_DEF`

```c
#define LOG_LINK_DEF ( _name, _api, _buf_wlen, _ctx )
```

```c
#include <zephyr/logging/log_link.h>
```

展开值（Value）：

```c
static uint32_t __aligned(Z_LOG_MSG_ALIGNMENT) _name##_buf32[_buf_wlen]; \
static const struct mpsc_pbuf_buffer_config _name##_mpsc_pbuf_config = { \
        .buf = (uint32_t *)_name##_buf32, \
        .size = _buf_wlen, \
        .notify_drop = z_log_notify_drop, \
        .get_wlen = log_msg_generic_get_wlen, \
        .flags = IS_ENABLED(CONFIG_LOG_MODE_OVERFLOW) ? \
                MPSC_PBUF_MODE_OVERWRITE : 0 \
}; \
COND_CODE_0(_buf_wlen, (), (static STRUCT_SECTION_ITERABLE(log_msg_ptr, \
                                                           _name##_log_msg_ptr);)) \
static STRUCT_SECTION_ITERABLE_ALTERNATE(log_mpsc_pbuf, \
                                         mpsc_pbuf_buffer, \
                                         _name##_log_mpsc_pbuf); \
static struct log_link_ctrl_blk _name##_ctrl_blk; \
static const STRUCT_SECTION_ITERABLE(log_link, _name) = \
{ \
        .api = &_api, \
        .name = STRINGIFY(_name), \
        .ctrl_blk = &_name##_ctrl_blk, \
        .ctx = _ctx, \
        .mpsc_pbuf = _buf_wlen ? &_name##_log_mpsc_pbuf : NULL, \
        .mpsc_pbuf_config = _buf_wlen ? &_name##_mpsc_pbuf_config : NULL \
}
```

创建日志链路实例。

_buf_len为正时，链路可以拥有专用消息缓冲区。此时，日志核心会尝试从全部可用缓冲区（默认缓冲区和各链路缓冲区）取得消息，并处理时间戳最早的一条，因此消息会按顺序处理。如果不要求严格排序，可以省略专用缓冲区，将_buf_len设为0。这样能提高内存利用率，但传给后端的消息可能无序。

**参数（Parameters）**

| 名称／方向 | 说明 |
| --- | --- |
| `_name` | 实例名称。 |
| `_api` | API列表，参阅log_link_api。 |
| `_buf_wlen` | 专用消息缓冲区的大小，以字（Word）为单位；为0时使用默认缓冲区。 |
| `_ctx` | 与链路关联的上下文，类型为void *。 |

### `log_link_activate()`

```c
int log_link_activate ( const struct log_link * link)
```

声明属性：`inline`、`static`。

```c
#include <zephyr/logging/log_link.h>
```

激活日志链路（Activate）。

此函数检查链路是否已初始化，并完成初始化过程。成功返回时，链路已就绪，日志域数量和日志源数量已取得，时间戳细节也已更新。

**参数（Parameters）**

| 名称／方向 | 说明 |
| --- | --- |
| `link` | 日志链路实例（Log Link Instance）。 |

**返回值（Return Values）**

| 名称／方向 | 说明 |
| --- | --- |
| `0` | 成功激活。 |
| `-EINPROGRESS` | 激活正在进行中。 |

### `log_link_initiate()`

```c

```

声明属性：`inline`、`static`。

```c

```

开始初始化日志链路（Initiate）。

此函数开始初始化链路。由于初始化过程可能耗时，为避免阻塞日志系统初始化，函数会在链路就绪之前返回。随后调用log_link_activate完成链路初始化。

| --- | --- |
| `link` | 日志链路实例（Log Link Instance）。 |
| `config` | 配置（Configuration）。 |

返回（Returns）：成功时为0，否则为错误码。

> 译注——源码核对：日志链路（Log Link）把远端域的消息引入本地日志核心；日志后端（Backend）负责消费并输出日志。两者使用不同的操作表和状态结构，不能因为都涉及传输就互换指针。

> 译注——源码核对：LOG_LINK_DEF的真实参数名为_buf_wlen，原说明正文使用_buf_len。源码为缓冲区声明uint32_t数组，容量单位是32位字而非字节；例如64个字对应256字节的消息存储，控制结构开销另计。原参数名差异保留并在这里说明。

> 译注——源码核对：专用缓冲区让日志核心能比较各缓冲区当前候选消息的时间戳；共享默认缓冲区有利于容量共用，但不提供同样的跨链路排序。这个机制本身不等于自动同步远端硬件时钟，也不能在不知道未来消息时无限等待以保证全局顺序。

> 译注——源码核对：initiate发起初始化，activate完成链路激活。包装函数直接调用操作表，不会为NULL操作指针自动提供空实现；具体传输必须实现所需操作。不要把initiate成功返回直接当成远端日志域已经可查询。

> 译注——源码核对：log_link_is_active返回整数状态码：已激活为0，进行中为-EINPROGRESS，不是true表示激活的布尔查询。当前实现检查domain_offset；日志管理层在activate成功后才分配并写入该偏移，因此不能只独立调用activate就推断管理层已完成登记。

> 译注——源码核对：这里的domain_id是链路内相对域编号，日志管理层另用domain_offset映射到系统视角。source_cnt按相对编号索引，当前内联函数没有在数组访问前检查编号范围，应使用已经取得且有效的域编号。

> 译注——源码核对：域名称查询的官方契约允许buf为NULL以取得长度，源名称查询则要求非NULL，当前包装函数会断言buf。length同时作为输入容量和输出实际名称长度；不能把一次返回后的值未经检查就当成缓冲区仍有那么大。具体传输仍需实现所声明的契约。

> 译注——源码核对：源码中的log_link_set_runtime_level对level执行非零断言，因此启用断言时传入LOG_LEVEL_NONE（0）会触发断言。原文没有列出此限制，译文保持原说明并单独标注当前实现；不可直接沿用其他日志控制接口可设0的用法。

> 译注——源码核对：接收消息与丢弃计数是两类独立回调。丢弃计数表示自上次通知以来的数量，不是已成功接收数量，也不是请求重发的队列。控制块的内部字段在官方类型页面被隐藏，源码可见内容与公共字段文档分别保留。
