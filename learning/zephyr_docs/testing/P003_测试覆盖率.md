# 第3章\_测试覆盖率

原文：[Generating coverage reports](https://docs.zephyrproject.org/latest/develop/test/coverage.html)。读取日期：2026-10-12，`latest`。

**代码覆盖率（Code Coverage）**报告帮助分析某个测试或应用执行了哪些代码。Zephyr 提供两条路线：在嵌入式目标或 **QEMU（机器模拟器项目）**上使用 gcov 集成，或为 **POSIX架构（Portable Operating System Interface Architecture）**构建原生应用，直接使用主机工具。

> 译注：覆盖表示代码被执行过，不等于行为已正确验证。下面保留官方命令与预期输出，本次没有运行测试或生成覆盖率报告。带 `$` 的行用它表示终端提示符，实际输入时去掉；终端命令采用 Bash 形式。

## 3.1\_嵌入式设备与QEMU

这条路线先让目标程序收集覆盖率计数，再把计数取回主机生成报告；设备能力、应用配置和主机工具都参与其中。

### 3.1.1\_工作原理

[gcov](https://gcc.gnu.org/onlinedocs/gcc/Gcov.html) 是与 **GNU编译器集合（GNU Compiler Collection，GCC）**配合使用的覆盖率工具，可分析程序并生成测试报告，帮助发现未经测试的代码路径和优化机会。

在 Zephyr 中，应用运行时的覆盖率计数保存在 **随机存取存储器（Random-Access Memory，RAM）**，而不是直接写入设备文件系统。原文概述称，收集和报告能力受到可用 RAM 限制，目前只为嵌入式目标的 QEMU 仿真启用。

### 3.1.2\_设备与应用两层配置

需要分别启用设备能力和应用覆盖率。gcov 的可用性依赖 RAM：例如 `frdm_k64f` 可以运行简单测试，但复杂用例在同时收集覆盖率时可能因内存不足崩溃。

设备支持在 `Kconfig.board` 中选择能力符号 `HAS_COVERAGE_SUPPORT`，生成的 Kconfig 配置项为 [CONFIG_HAS_COVERAGE_SUPPORT](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HAS_COVERAGE_SUPPORT)。具体测试应用再启用 [CONFIG_COVERAGE](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_COVERAGE)。

> 译注：原文同时保留了“当前仅QEMU”的概括与设备启用步骤，不能据此认定任意实板已支持。还应核对当前版本的板级能力、运行时转储通道和内存预算。Kconfig 文件中使用符号本名，`prj.conf` 中才使用 `CONFIG_` 前缀。

### 3.1.3\_单应用报告步骤

以下步骤生成一个应用的 **HTML（HyperText Markup Language，超文本标记语言）**覆盖率报告。先使用 `CONFIG_COVERAGE=y` 构建，并通过 `CONFIG_COVERAGE_DUMP` 启用转储：

```sh
west build -b mps2/an385 -- -DCONFIG_COVERAGE=y -DCONFIG_COVERAGE_DUMP=y
```

> 译注：原命令没有提供应用路径，要求当前位置或已有构建配置能确定应用。应在实际应用构建上下文执行；下面涉及 `scripts/` 的步骤则按 Zephyr 源码根定位，若工作目录不同，需使用正确相对路径。`mps2/an385` 是原文模拟板目标，不是本项目实板。

捕获模拟器输出到 `log.log`。覆盖率转储打印后，可能需要按 `Ctrl-A` 再按 `X` 结束模拟器，才能完成日志收集：

```sh
$ ninja -Cbuild run | tee log.log
```

从保存的日志生成 gcov 所需文件：

```sh
$ python3 scripts/gen_gcov_files.py -i log.log
```

> 译注：原文概括为由日志生成 `.gcda` 和 `.gcno`。通常 `.gcno` 是编译阶段产生的控制流说明文件，运行计数转储恢复为 `.gcda`；生成报告需要二者匹配。不要只保留日志就删除原构建目录中的 `.gcno`。

在 **软件开发工具包（Software Development Kit，SDK）**中查找对应架构的 gcov 程序，后面交给 gcovr：

```sh
$ find $ZEPHYR_SDK_INSTALL_DIR -iregex ".*gcov"
```

`ZEPHYR_SDK_INSTALL_DIR` 是当前 SDK 根环境变量。创建报告目录：

```sh
$ mkdir -p coverage-report
```

调用 **gcovr（gcov覆盖率汇总与报告工具）**生成报告：

```sh
$ gcovr -r $ZEPHYR_BASE . --html -o coverage-report/coverage.html --html-details --gcov-executable <gcov_path_in_SDK>
```

`ZEPHYR_BASE` 是当前 Zephyr 源码根环境变量；`<gcov_path_in_SDK>` 换成前面找到的、对应目标架构的程序路径。报告写入 `coverage-report/coverage.html`，并生成详细页面。

## 3.2\_POSIX架构的主机报告

针对 POSIX 架构构建时，使用主机原生工具生成一个可执行文件，其中包括应用、Zephyr 操作系统及基本硬件模拟。因此可以使用开发普通桌面程序时的覆盖率工具。

编译前设置 `CONFIG_COVERAGE`，运行应用后取得对应 `.gcda` 数据，并与构建阶段 `.gcno` 配合处理。例如：

```sh
west build -b native_sim samples/hello_world -- -DCONFIG_COVERAGE=y
```

运行程序，再用 **lcov（gcov覆盖率数据收集工具）**和其 HTML 生成器 `genhtml` 处理：

```sh
$ ./build/zephyr/zephyr.exe
# Press Ctrl+C to exit
$ lcov --capture --directory ./ --output-file lcov.info -q --rc lcov_branch_coverage=1
$ genhtml lcov.info --output-directory lcov_html -q --ignore-errors source --branch-coverage --highlight --legend
```

> 原文注意：需要支持中间文本格式的较新 lcov，至少1.14版，较新的 Linux 发行版通常提供。也可改用至少4.2版的 gcovr。

> 译注：`zephyr.exe` 是 native_sim 产物名称，扩展名不表示此流程可以在原生 Windows 直接运行；仍需遵守原生模拟目标的主机支持范围。报告生成目录 `lcov_html` 是工具输出，不是预先存在的源码目录。

## 3.3\_通过Twister生成

**Twister（Zephyr测试运行器）**可自动从已执行测试生成覆盖率报告，使用 `--coverage` 参数即可。例如：

```sh
$ west twister --coverage -p qemu_x86 -T tests/kernel
```

或者：

```sh
$ west twister --coverage -p native_sim -T tests/bluetooth
```

会产生 `twister-out/coverage/index.html` 报告，以及默认 gcovr 收集的 `twister-out/coverage.json` 数据。可通过 `--coverage-tool` 和 `--coverage-formats` 选择其他工具与格式。

若报告需同时包含 Zephyr 源码和仓库外的应用代码，在项目目录调用 Twister，并传入 `--coverage-basedir $ZEPHYR_BASE`：

```sh
$ west twister --coverage -p native_sim --coverage-basedir $ZEPHYR_BASE -T your_project_dir
```

`your_project_dir` 是待扫描测试应用位置，应按当前目录填写；应用布局见[应用开发](../application/P001_应用开发.md)。

> 原文注意：默认 gcovr 在过滤文件时假定路径已解析为真实位置。若环境中使用符号链接，应让 `ZEPHYR_BASE` 指向解析后的真实源码目录，或改用 `--coverage-tool lcov`，避免报告缺失部分文件。具体见 [gcovr符号链接过滤说明](https://gcovr.com/en/stable/guide/filters.html#filters-for-symlinks)。

单元测试使用主机工具链及不同板目标，命令为：

```sh
$ west twister --coverage -p unit_testing -T tests/unit
```

报告位置与其他测试相同；`unit_testing` 和 `native_sim` 的运行环境差异见[Ztest测试框架](P002_Ztest测试框架.md)。

## 3.4\_逐用例覆盖矩阵

默认按测试场景聚合覆盖率。若要追溯到单个 Ztest 用例，例如回答“哪些测试执行过 `foo.c` 的第X行”，使用 `--coverage-per-test`：

```sh
$ west twister -p mps2/an385 -T tests/kernel --coverage --coverage-tool lcov \
    --coverage-per-test
```

这会启用 Kconfig 选项 [CONFIG_ZTEST_COVERAGE_PER_TEST](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_COVERAGE_PER_TEST)，每个用例开始前复位 gcov 计数，结束后转储带测试标记的独立数据。

支持**半主机机制（Semihosting）**的平台，例如 QEMU 下的 Arm、RISC-V、Xtensa 目标中的相应配置，可把逐用例数据直接写到主机文件系统，避免大量串口输出；`mps2/an385` 是原文例子。其他平台退回串行控制台传输。

除通常的聚合报告，还生成：

- 各构建目录 `coverage/tests/` 下，每个测试一个 `<scenario>.<test>.info` **跟踪文件（Tracefile）**。
- `twister-out/coverage/test_matrix.json`，包含按行视图 `by_line`，结构为 `{file: {line: [tests]}}`；以及按测试视图 `by_test`，结构为 `{test: {file: [lines]}}`。

逐用例归属由矩阵及其仪表板呈现，不能从最终聚合 lcov 报告中保留同样粒度。聚合前，各测试实例的覆盖率先合为一个跟踪文件，因此结束时的报告工作量与实例数相关，而不是与全部用例数成正比。

> 原文注意：`--coverage-per-test` 要求使用 lcov，因为矩阵依赖 lcov 跟踪文件中的逐测试 `TN` 记录，gcovr 没有对应形式。这个参数还隐含启用 `--coverage`。

### 3.4.1\_矩阵可视化

官方独立脚本 [scripts/gen_test_matrix_dashboard.py](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/gen_test_matrix_dashboard.py) 可将已有 `test_matrix.json` 转成自包含的交互式 HTML 页面。脚本不依赖 Twister，可处理此前生成的矩阵：

```sh
$ scripts/gen_test_matrix_dashboard.py -i twister-out/coverage/test_matrix.json
```

输出 `twister-out/coverage/test_matrix.html`。页面按测试列出覆盖文件数、代码行数，以及其他测试未覆盖的独占行数，便于识别覆盖重复的测试或承担独有覆盖的测试；还可查看某测试涉及哪些文件，或反查特定文件与代码行由哪些测试覆盖。

> 译注：符号链接过滤说明改链至 gcovr 官方发布文档的对应小节；原 GitHub 源文件页的章节锚点未能定位。

## 3.5\_不同工具链的gcov选择

Twister 根据环境变量 `ZEPHYR_TOOLCHAIN_VARIANT` 决定 `--gcov-tool` 的默认值：

| 工具链变体 | 默认工具 |
| --- | --- |
| `host` | `gcov` |
| `llvm` | `llvm-cov gcov` |
| `zephyr` | `gcov` |

> 译注：表中是原文给出的工具名或调用形式，实际程序仍需与所用编译器和目标匹配。不要因主机也有 `gcov` 就直接替代 SDK 中对应架构的版本。逐用例矩阵是当前 `latest` 文档功能，使用旧版源码时先确认相应配置和脚本是否存在。
