# 第4章\_基准测试框架

原文：[Benchmarking Framework](https://docs.zephyrproject.org/latest/develop/test/benchmark.html)。读取日期：2026-10-12，`latest`。

**基准测试（Benchmarking）**通过重复执行指定操作，测量它的性能。Zephyr 的基准测试框架提供精确到周期的测量，自动收集数据、计算统计量，以统一方式评估 Zephyr 各部分的执行开销。

## 4.1\_框架概览与配置

框架帮助发现**性能退化（Performance Regression）**并优化**关键路径（Critical Path）**，也就是对整体性能有重要影响的执行路径。它提供与 Ztest 约定一致的**应用程序编程接口（Application Programming Interface，API）**宏，计算均值、标准差、标准误差及最小值、最大值，并通过**对照测试（Control Test）**估计测量框架自身的开销。

原文将**开销补偿（Overhead Compensation）**概括为：从报告的各项统计量减去对应对照开销，修正结果是实数，通常不对应某次单独测量。

> 译注：不能把这句话理解为从标准差和标准误差也直接减去同一个周期常数。对所有样本减去常数不会改变标准差；本仓库参照实现的 `subsys/testsuite/ztest/benchmark/src/benchmark.c` 也保留由样本方差计算出的标准差和标准误差，只对相应的周期开销指标作修正。具体指标以所用 Zephyr 版本的实现为准。

在待测应用的 Kconfig 配置中启用以下选项，例如加入应用的 `prj.conf`；这段是配置文件内容：

```kconfig
CONFIG_ZTEST=y
CONFIG_ZTEST_BENCHMARK=y
```

> 译注：本页翻译的是读取时的官方 `latest`。手动测量、预热、百分位数等较新功能，在本仓库较早的参照实现中未必存在。使用前核对目标源码中的头文件及 Kconfig，不把文档示例当作 HC32 实板已经验证的结果。

## 4.2\_定义套件与三种测量方式

**基准测试套件（Benchmark Suite）**将相关测试放在一起。先使用 `ZTEST_BENCHMARK_SUITE` 定义套件，再用相应宏添加单项测试，写法与普通 Ztest 套件类似。

以下代码来自测试源文件，`<test suite name>` 等尖括号部分是需要替换的占位说明，不能原样编译。`setup_fn` 是准备函数，`teardown_fn` 是清理函数。

```c
#include <zephyr/ztest.h>

ZTEST_BENCHMARK_SUITE(<test suite name>, <setup_fn>, <teardown_fn>);
```

### 4.2.1\_标准基准测试

**标准基准测试（Standard Benchmark）**按指定次数执行测试，测量消耗的周期数，适合观察关键路径的**中央处理器（Central Processing Unit，CPU）**执行开销，并定位 CPU 使用方面的瓶颈。它尤其适合执行时间较稳定、很少受**输入输出（Input/Output，I/O）**或**上下文切换（Context Switch）**影响的代码。上下文切换指处理器从一个执行上下文转到另一个执行上下文。下面用宏 `ZTEST_BENCHMARK` 声明指定样本数的测试。

```c
#include <zephyr/ztest.h>

ZTEST_BENCHMARK_SUITE(<suite name>, NULL, NULL);

ZTEST_BENCHMARK(<suite name>, <benchmark name>, <number of samples>, <setup_fn>, <teardown_fn>)
{
    /* Code to benchmark */
}
```

每个**样本（Sample）**对应一次被测执行：先调用准备函数，再执行测试函数，最后调用清理函数。按指定样本数重复这一过程；把准备、清理移出被测主体，有助于测量目标操作本身。

### 4.2.2\_定时基准测试

**定时基准测试（Timed Benchmark）**在指定时间窗口内运行测试。相较于只关心关键路径周期开销的标准测试，它适合执行时间变化较大、涉及 I/O、上下文切换等系统因素的工作。

```c
ZTEST_BENCHMARK_TIMED(<suite name>, <benchmark name>, <time in ms>, <setup_fn>, <teardown_fn>)
{
      /* Code to benchmark */
}
```

准备与清理函数各执行一次，被测函数在专用时间窗口内连续运行。这样得到的测量可以包含中断、上下文切换及其他后台任务带来的系统开销，更接近相应系统负载下的行为。`<time in ms>` 的单位为毫秒。

### 4.2.3\_手动基准测试

标准和定时测试由框架在**线程上下文（Thread Context）**中，围绕每次测试主体调用取得两个时间戳。有些测量的起止点处于不同上下文，例如触发中断到**中断服务程序（Interrupt Service Routine，ISR）**执行第一条指令的延迟，或 ISR 结束到被唤醒线程开始运行的延迟，不能直接用这种包围整个函数调用的方式表达。

**手动基准测试（Manual Benchmark）**通过宏 `ZTEST_BENCHMARK_MANUAL` 声明，仍由框架管理循环、准备和清理，但测试主体使用 `ztest_benchmark_start()` 与 `ztest_benchmark_end()` 指定被测区间。框架计算、报告的统计量与标准测试相同。

```c
ZTEST_BENCHMARK_MANUAL(<suite name>, <benchmark name>, <samples>, <setup_fn>, <teardown_fn>)
{
      prepare();

      ztest_benchmark_start();
      operation_under_test();
      ztest_benchmark_end();
}
```

上述两个函数只采集**时间戳（Timestamp）**，都可以在 ISR 中调用，因此区间起止点不必处于同一上下文。下例由 ISR 标记开始，回到线程后标记结束，用于表达中断到被唤醒线程的延迟测量。

```c
static void my_isr(const void *arg)
{
      ztest_benchmark_start();
}

ZTEST_BENCHMARK_MANUAL(<suite name>, isr_exit_latency, 1000, NULL, NULL)
{
      trigger_the_interrupt();

      ztest_benchmark_end();
}
```

> 译注：`prepare()`、`operation_under_test()`、`trigger_the_interrupt()` 是示意函数，需要测试自行提供。测量哪个中断、怎样触发、如何确保开始时间戳已经记录，取决于具体平台和测试设计；这不是直接复制即可运行的完整中断测试。

样本在测试主体返回后才计算。统计更新需要浮点运算，而并非每种架构都允许在 ISR 内进行浮点运算，因此计算留在中断上下文之外。如果某次迭代没有标记测量区间，它不贡献样本。

手动测试使用自己的对照测量。手动区间只包含界定区间的两个时间戳操作；标准采样测试的对照还包含间接调用测试主体的开销，后者不属于手动区间。若起止点位于不同上下文，其实际成本与这两种对照都不完全相同，任何一种对照都无法精确表达所有跨上下文情况。

**预热（Warmup）**的处理与标准采样测试相同：框架按 Kconfig 选项 `CONFIG_ZTEST_BENCHMARK_WARMUP` 额外执行测试主体，丢弃这些区间，并另行保留首次执行的冷启动成本。主体不需要区分预热和测量阶段，各次迭代执行相同的工作。

## 4.3\_理解标准测试结果

下面是标准测试的人类可读输出格式；尖括号内容表示实际输出值；`SE` 表示**标准误差（Standard Error）**，具体统计含义在下表解释：

```text
<suite name> ###############################################
<benchmark name> ===========================================
   Sample size:<number of samples>, total cycles: <total amount of cycles>
   Mean(u): <mean cycles per sample>
   Standard deviation(s): <cycles>
   Standard Error(SE): <cycles>
   Min: <cycles> (run #<sample number>)
   Max: <cycles> (run #<sample number>)
```

### 4.3.1\_统计指标与异常样本

| 指标 | 含义 |
| --- | --- |
| **均值（Mean，u）** | 每个样本平均消耗的周期数，表示执行开销的中心水平。 |
| **标准差（Standard Deviation，s）** | 各样本相对均值的波动程度；较小通常表示执行开销更一致。 |
| **标准误差（Standard Error，SE）** | 样本均值对总体均值的估计误差尺度，用于评估均值估计的统计可靠程度。 |
| **最小值与最大值（Minimum/Maximum，Min/Max）** | 观测到的最小、最大周期数，以及对应样本的编号。 |

> 译注：标准误差的解释依赖样本与统计模型的前提。较小的 SE 不证明每一次执行都接近均值，更不等于最坏执行时间的保证。

启用 [`CONFIG_ZTEST_BENCHMARK_OUTLIERS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_BENCHMARK_OUTLIERS) 后，人类可读报告用**离群样本（Outlier）**的数量和百分比替换标准误差这一行：它统计高于**中位数（Median）**且超出规定余量的样本，余量由 [`CONFIG_ZTEST_BENCHMARK_OUTLIER_MARGIN_DIV`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_BENCHMARK_OUTLIER_MARGIN_DIV) 控制。中位数是排序后位于中间位置的值。

设置余量是因为计数器的分辨率会让同一基准水平散布在几个计数值上；不留余量，就可能把约一半样本报告为离群点。延迟分布往往是稳定的基准水平加上少量受干扰执行，未必适合按单一随机总体理解。原文举例：一万次执行为 760 周期，一次为 1240 周期，标准误差约为 0.048；这个数字看似精确，却没有说明那次较慢执行。报告约万分之一、即 0.010% 的离群比例，更直接说明发生了什么。

该选项只改变人类可读报告，**逗号分隔值（Comma-Separated Values，CSV）**输出仍保留标准误差列，便于脚本按稳定列结构处理数据。

### 4.3.2\_预热与首次执行成本

基准测试依次经历准备、执行但不记录的预热迭代、正式采样三个阶段。[`CONFIG_ZTEST_BENCHMARK_WARMUP`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_BENCHMARK_WARMUP) 对同一镜像中的所有基准测试生效。

无论预热次数如何设置，第一次执行都不纳入正式样本。第一次执行时，**高速缓存（Cache）**、**分支预测器（Branch Predictor）**与**地址转换后备缓冲器（Translation Lookaside Buffer，TLB）**可能尚未形成后续执行所依赖的状态，执行时间可能比稳定运行时高一个数量级。缓存保存近期使用的数据或指令，分支预测器预测控制流，TLB 缓存地址转换结果；具体处理器未必具备全部这些部件。

框架单独报告这一次的**冷启动成本（Cold Cost）**，与后续的**稳态（Steady State）**开销分开。只在启动时执行一次的路径，更应关注首次成本；长期重复的路径则需要了解后续分布。

首次执行若同时计入稳态样本，会影响分布尾部的解释。原文用一万次样本的**最近秩（Nearest Rank）**百分位算法举例：p99.99 对应排序后第二大的值，用以强调首次执行与稳态尾部应分开分析。

> 译注：该例说明的是两类成本混在同一分布中的解释风险；一个冷启动样本是否恰好成为某个百分位值，还取决于其他样本的大小和采用的百分位定义，不能据此推导稳态最坏延迟。

增加预热并不总能提高微小测试的测量代表性。当整个操作成本与一次缓存未命中相当时，额外预热可能降低原文所说的测量准确性；样本足够多时，早期迭代对均值的影响也可能已很小。因此默认值零是起点。测试规模足以受缓存状态影响、目标明确是稳态开销时，再增加预热。

### 4.3.3\_延迟百分位数

均值和标准误差回答平均值估计得多精确，这对**吞吐量（Throughput）**有用；**延迟（Latency）**还需要知道个别操作可能慢到什么程度。实时系统关注的慢执行通常处于分布尾部。

启用 Kconfig 选项 [`CONFIG_ZTEST_BENCHMARK_PERCENTILES`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_BENCHMARK_PERCENTILES) 后，框架保留各次样本，在常规统计量之外报告 min、p50、p90、p99、p99.9、p99.99 和 max。**百分位数（Percentile）**表示排序分布中的位置，例如 p99 用于观察约 99% 样本所处范围的上界。CSV 模式下，标准采样测试和手动测试各增加一行以 `P` 为类型标识的百分位记录；列定义见 Kconfig 输出选项 [`CONFIG_ZTEST_BENCHMARK_OUTPUT_CSV`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_BENCHMARK_OUTPUT_CSV)。

原文以有负载系统的中断进入延迟为例：均值为 1264 周期、标准误差为 34，但未必有任何一次中断恰好花费 1264 周期；百分位数显示直到 p99 都是 1216 周期，尾部则达到 25184 周期。这两组描述揭示的性能特征不同。

百分位分辨率受样本数限制：p99 至少需要 100 个样本，p99.9 至少需要 1000 个，p99.99 至少需要 10000 个；样本更少时，相应结果退化为最大值。

样本缓冲区由 Kconfig 选项 [`CONFIG_ZTEST_BENCHMARK_MAX_SAMPLES`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST_BENCHMARK_MAX_SAMPLES) 指定条目数，每条占 8 字节，容量必须至少覆盖最大单项基准测试的样本数。缓冲区保存的是最先取得的样本，而不是从完整运行中随机抽取的代表样本；若只统计截断的前缀，会漏掉缓冲区填满后发生的慢执行。因此超出缓冲区容量时，框架不报告百分位数，并说明有多少样本未能保存。

对上述标准测试的周期指标，均值、最小值和最大值越低，通常表示执行越快；标准差和标准误差越低，通常表示波动更小或均值估计更稳定。仍需结合前述统计前提，不能仅靠一个较小数值证明实时性或功能正确性。

## 4.4\_理解定时测试结果

定时测试输出如下：

```text
<benchmark name> ===============================================
   Samples: <Number of samples executed during the benchmark>
   Total Time: <Gross execution time>
   Work Time: <Net execution time> ns (Net)
   Ops/Sec: <average operations per second>
   Cycles/Op: <average cycles per operation>
```

| 输出字段 | 解释 |
| --- | --- |
| `Samples` | 时间窗口内执行的样本数。 |
| `Total Time` | **总时间（Gross Execution Time）**，包含测试框架开销。 |
| `Work Time` | **净工作时间（Net Execution Time）**，扣除框架自身开销后的被测代码执行时间，示例以纳秒输出。 |
| `Ops/Sec` | **每秒操作数（Operations per Second）**，样本数除以用秒表示的净工作时间，反映吞吐量。 |
| `Cycles/Op` | **每次操作周期数（Cycles per Operation）**，净周期数除以样本数，反映 CPU 执行开销。 |

一般而言，`Ops/Sec` 越高、`Cycles/Op` 越低，性能越好。二者来自同一组底层测量，只是从不同角度表示性能，因此较高的每秒操作数通常对应较低的每次操作周期数。

## 4.5\_输出格式

默认输出是便于人阅读的详细文本。启用 `CONFIG_ZTEST_BENCHMARK_OUTPUT_CSV` 可改为 CSV，便于脚本导入、分析和生成报告；它保留相应统计指标，并使用适合自动处理的字段形式。

标准测试的 CSV 格式如下：

```text
S,<suite name>,<benchmark name>,<sample size>,<total cycles>,<mean>,<stddev>,<stderr>,<min>,<min sample>,<max>,<max sample>
```

定时测试的 CSV 格式如下：

```text
T,<suite name>,<benchmark name>,<samples>,<total time>,<work time>,<ops/sec>,<cycles/op>
```

`S` 与 `T` 区分上述两类记录；启用百分位数后的附加 `P` 记录按配置项说明解析，不应把每一行都当成相同列数。

## 4.6\_测量注意事项与接口参考

1. **测量噪声（Measurement Noise）**：基准测试对后台活动十分敏感。若目标是隔离被测代码的成本，应关闭不必要的后台任务及干扰计时的中断；若目标是特定负载下的行为，则保留并说明该负载条件。
2. **缓存预热（Cache Warming）**：首次执行可能因缓存未命中变慢。选择足够样本数，结合框架的冷启动成本与预热处理理解结果，避免用很小样本集代表稳定性能。
3. 使用准备、清理函数，把目标操作尽量与周边工作分开。若在被测主体中塞入大量准备或清理代码，可能显著扭曲短关键路径的测量。

完整宏和接口说明见 [Zephyr Benchmarking Framework](https://docs.zephyrproject.org/latest/doxygen/html/group__ztest__benchmark.html)。
