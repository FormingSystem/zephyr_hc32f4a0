# 第62章\_示例定义与准则

原文：[官方页面](https://docs.zephyrproject.org/latest/samples/sample_definition_and_criteria.html)。读取日期：2026-10-14；保存的latest页面及HTML摘要见[来源记录](../SOURCES.md)。

<a id="definition"></a>

## 62.1 定义（Definition）

示例（Sample）是简洁的Zephyr应用程序，用来清楚介绍一个或多个功能、子系统或模块，包括内核服务、驱动程序、协议等。示例应限制范围，只集中展示所介绍子系统或模块中有实质意义或必不可少的部分。

提交新功能时建议提供示例，但并非强制要求。

<a id="sample-criteria"></a>

## 62.2 示例准则（Sample Criteria）

<a id="samples-must-not-be-used-to-test-features-or-verify-platforms"></a>

### 62.2.1 示例不得用于测试功能或验证平台（1. Samples must not be used to test features or verify platforms）

- 示例的主要用途是为用户提供参考。
- 示例不得使用Zephyr测试框架：不得启用[`CONFIG_ZTEST`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZTEST)，也不得在示例中使用`zasserts`断言。
- 如果示例能够产生可验证的输出，应将输出与预期值比较，为示例自身提供一定程度的检查。详情参阅[测试运行器（Test Runner，Twister）](../twister/P001_Twister测试运行器.md#twister-script)。
- 成功运行示例虽然能够说明相关功能按预期工作，却不能取代提交到[tests/](https://github.com/zephyrproject-rtos/zephyr/blob/main/tests/)目录、具有完整覆盖率的专门测试。示例只检查自身能否构建，以及某些情况下是否按预期运行；所检查的是示例本身，而不是其依赖的子系统。

<a id="twister-should-be-able-to-build-every-sample"></a>

### 62.2.2 Twister应能够构建每个示例（2. Twister should be able to build every sample.）

每个示例都必须有YAML文件，参阅[测试运行器（Twister）](../twister/P001_Twister测试运行器.md#twister-script)。例如：

```yaml
tests:
  sample.kernel.cond_var:
    integration_platforms:
      - native_sim
    tags:
      - kernel
      - condition_variables
    harness: console
    harness_config:
      type: one_line
      regex:
        - ".*Waited and joined with 3 threads"
```

- 不要将测试标记为仅构建（Build only）。示例应能够在文档所列平台上构建并运行。使用`harness`选项跳过执行；原文说明，只有将测试执行器（Harness）设为`ztest`或`console`时，Twister才会尝试烧录并执行所生成的二进制文件。
- 示例默认配置必须放在`prj.conf`中，并应在所有支持的平台上正常工作。不要依赖YAML中的`extra_args`或`extra_configs`选项才能构建示例。
- 测试应验证示例的默认配置，以及README所说明的可选功能。不得用示例测试它所属子系统或模块的功能。
- 文档说明过、与示例及其运行有关的配置选项，可以通过YAML中的`extra_args`或`extra_configs`进行验证；基础配置仍应放在`prj.conf`中。
- 在适用的情况下，可使用`harness_config`的正则表达式（Regex）选项验证示例输出。
- 使用`platform_allow`将测试限制在实际验证过的平台上，并在README中列出这些平台。
- 存在时间或资源约束时，使用`integration_platforms`限制范围。理想情况下，通过拉取请求（Pull request）向Zephyr源码树提交变更时，选择一个平台就足以检查示例。
- 尽可能使示例通用；除非针对特定硬件，否则避免编写只能用于某个平台的示例。

> 译注——Twister版本差异：上述“仅`ztest`或`console`执行”的表述保留自原文。本次核对的官方`constants.py`已经列出`pytest`、`shell`、`robot`、`ctest`等更多受支持的Harness；`testinstance.py`还结合平台、运行器等条件判断可运行性。因此，不能按这句旧说明认定其他Harness一律不会运行，也不能仅凭名称在支持列表中就断定当前平台一定能够运行。

<a id="a-sample-should-provide-sufficient-coverage-of-a-subsystem-feature-or-module"></a>

### 62.2.3 示例应充分展示子系统、功能或模块（3. A sample should provide sufficient coverage of a subsystem, feature, or module.）

应当做到：

- 覆盖最常见、最重要的使用场景。
- 保持代码简单易读。原文示例链接：[samples/philosophers](https://github.com/zephyrproject-rtos/zephyr/blob/main/samples/philosophers)。

不应当做到：

- 不得用示例测试错误条件或边界情况。
- 示例不得写成单元测试（Unit test）。

> 译注——源码跟踪：对应的本地译文见[哲学家就餐示例](P030_哲学家就餐示例.md)；本仓库的[示例目录](../../../samples/philosophers/README.rst)使用相对路径，可随整个仓库迁移。

<a id="samples-must-be-documented"></a>

### 62.2.4 示例必须提供文档（4. Samples must be documented.）

- 示例目录中必须有`README.rst`，例如`samples/subsys/foo/README.rst`，清楚说明示例目的、硬件要求，以及适用情况下的预期输出。
- 确保能从`samples/index.rst`开始，沿示例文档层级访问该`README.rst`。

README模板应包含：概述（适用时）、软件／硬件要求、构建与运行说明，以及示例输出（适用时）。作为起点，可以参考[samples/kernel/condition_variables/condvar](https://github.com/zephyrproject-rtos/zephyr/blob/main/samples/kernel/condition_variables/condvar)。
