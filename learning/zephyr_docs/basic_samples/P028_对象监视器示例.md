# 第28章\_对象监视器示例

原文：[官方页面](https://docs.zephyrproject.org/latest/samples/kernel/object_monitor/README.html)。读取日期：2026-10-14；保存的latest页面及HTML摘要见[来源记录](../SOURCES.md)。

<a id="overview"></a>

## 28.1 概述（Overview）

本示例运行一个小型应用，并同时运行一个监视线程，利用[对象核心（Object Cores）](../kernel/P048_内核对象核心.md#object-cores-api)绘制系统中内核对象的实时表格。[对象核心示例](P027_对象核心示例.md#object_cores)逐步介绍这套设施，本示例则展示调试工具的典型用法：持续观察并非由监视器自己创建的对象。

应用是一个作业服务器（Job Server）：

- 传感器线程把采样值放入消息队列。
- 分派器启动短生命周期的作业线程，同时最多4个；每个作业都有一个在堆上分配的请求结构，其中嵌入信号量、互斥锁和定时器。
- 每个作业在各处理步骤中等待一个栈局部信号量，然后释放请求并退出。

因此，线程、请求及请求内嵌的对象不断出现和消失。监视器每秒刷新，打印以下内容：

- 每种类型的对象数量；因位于栈存储中而未登记的对象数`skipped`，这里是作业步骤信号量；因登记表已满而登记失败的计数`dropped`。
- 每个线程的状态，以及上一统计周期内的CPU占比。占比根据[`k_obj_core_stats_query()`](../object_core_reference/P002_对象核心统计接口.md#ga52afc700fb116acfaa4dd5e1ca49a782)返回的线程和内核运行时统计计算。
- 已启动、已结束和正在运行的作业数量。

如果把[`CONFIG_OBJ_CORE_MAX_DYNAMIC_OBJECTS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_OBJ_CORE_MAX_DYNAMIC_OBJECTS)降到运行时对象峰值以下，本例约为24个，登记表溢出时`dropped`列就会增长，但不影响应用运行。此后表格不再完整，因为存在不会被任何遍历报告的对象。

> 译注——两种丢弃：对象表的`dropped`统计登记失败；末行的`samples dropped`统计传感器消息入队失败，两者不是同一计数。当前实现用生成的数据模拟传感器，并不要求连接实际传感器。CPU列取相邻刷新间的周期增量，不是线程从启动以来的累计占比。

<a id="building-and-running"></a>

## 28.2 构建与运行（Building and Running）

可以按以下方式在QEMU上构建并执行：

> 译注——命令环境：在UCRT64 Bash或Linux Bash的Zephyr源码根目录执行，先准备命令中QEMU目标的工具链、模块和模拟器。构建成功后再运行；失败时先检查对应目标与依赖，不把下面的原文输出当作本次执行记录。

```sh
west build -b qemu_x86 samples/kernel/object_monitor
west build -t run
```

要为另一块开发板构建，把上面的`qemu_x86`替换为该板名称。在[native_sim](../native_reference/P004_Native_Simulator本机模拟器.md#native_sim)上，线程使用主机栈，因此示例启用[`CONFIG_ARCH_POSIX_UPDATE_STACK_INFO`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ARCH_POSIX_UPDATE_STACK_INFO)，以便内核识别栈存储中的对象。

监视器默认清屏并在原位置重绘。将`CONFIG_SAMPLE_MONITOR_CLEAR_SCREEN`设为`n`，可以让输出滚动；修改`CONFIG_SAMPLE_MONITOR_PERIOD_MS`可以调整刷新周期。

`tests.yaml`中的`sample.kernel.object_monitor.tracking`配置使用[`CONFIG_TRACING_OBJECT_TRACKING`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_TRACING_OBJECT_TRACKING)构建同一程序，通过跟踪子系统启用对象核心框架。

<a id="sample-output"></a>

### 28.2.1 示例输出（Sample Output）

```text
Object monitor   uptime 92.3s   refresh 181

  type           objects  skipped  dropped
  thread               6        0        0
  semaphore            2      801        0
  mutex                2        0        0
  timer                2        0        0
  message queue        1        0        0

  thread       address    state        cpu
  monitor      0x1105a0  running     0.5%
  idle         0x110500  ready      96.7%
  dispatcher   0x110160  sleeping    0.0%
  sensor       0x1100c0  sleeping    0.0%
  job-132      0x1103e0  pending     2.3%
  job-133      0x110340  pending     0.2%

  jobs: 133 started, 131 finished, 2 running; samples dropped: 23
```

这里有两个正在运行的作业，因此有两个请求，信号量、互斥锁和定时器的数量分别比静态对象数量多两个；除线程外，消息队列是唯一的静态对象。被跳过的801个信号量是此前各作业的步骤信号量，它们从未登记。

> 译注——刷新设置与原日志：当前示例Kconfig的默认刷新周期是1000 ms；原日志里的运行时间92.3秒、刷新181次不是默认周期的严格对应关系，可能来自不同配置或版本。保留原日志用于认识字段，不把这些数值当作固定运行结果。
