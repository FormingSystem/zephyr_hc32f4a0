# 第25章\_元中断优先级分派示例

原文：[官方页面](https://docs.zephyrproject.org/latest/samples/kernel/metairq_dispatch/README.html)。读取日期：2026-10-14；保存的latest页面及HTML摘要见[来源记录](../SOURCES.md)。

<a id="overview"></a>

## 25.1 概述（Overview）

本示例实现一个运行于元中断（Meta-IRQ）优先级的线程，在硬件中断服务程序（Interrupt Service Routine，ISR）结束时同步执行“下半部”（Bottom Half）风格的处理。它模拟一个产生消息的“设备”，消息需要分派到异步队列，再交给多个具有不同优先级的工作线程。设备ISR实际上只是定时器中断，它通过队列把消息交给Meta-IRQ线程，由后者完成分派。

每条消息都要求工作线程执行一段随机且不可忽略的处理工作。这样便形成突发负载（Bursty Load）：偶发的负载峰值需要抢占正在运行的线程，并推迟低优先级线程的调度。

消息带有时间戳，可以在几个位置计算逐条消息的延迟：

- 从ISR创建消息到Meta-IRQ线程接收并准备分派消息之间的周期时间。
- 从ISR到工作线程接收消息之间的时间。
- 工作线程处理消息实际经过的时间，与要求的处理时间作比较。这样可以衡量线程被抢占、未得到调度期间产生的开销。

结果中值得注意的现象如下：

- 如预期，高优先级，也就是优先级数值较小的线程，平均接收延迟和处理延迟更低。
- 协作式调度（Cooperative Scheduling）线程的处理延迟明显好于可抢占线程，因为它们只能被Meta-IRQ线程抢占。
- 由于排队和突发负载，无论优先级如何，所有工作线程都会出现与负载有关的延迟：CPU偶尔需要完成的工作多于可用时间。
- 但无论系统负载或线程配置如何，Meta-IRQ线程总在ISR之后立即运行。原文指出，它能够抢占所有其他线程，包括通常不能被抢占的协作式线程，因此在各种情况下都显示出可靠、恒定的延迟。

> 译注——结论范围：这里描述的是该示例中的线程调度对比。当前配置启用一个Meta-IRQ优先级，并把`CONFIG_MP_MAX_NUM_CPUS`设为1；源码使用`k_cycle_get_32()`测量周期数。不能将“立即”“恒定”解释为任意平台上的零延迟，或不受其他硬件中断、关中断区间及计时分辨率影响的时延保证。

<a id="requirements"></a>

## 25.2 要求（Requirements）

本示例应能在具备以下条件的Zephyr平台上正常运行：中断能够抢占运行中的线程，定时器驱动可用，日志输出可用。出于测量精度考虑，较高的定时器节拍频率能产生更好且更多的数据，理想值为10 kHz或更高。

注意，这个测试本质上是在测量线程抢占行为，因此未经修改不能用于`native_sim`平台。在该模拟环境中，线程只会在特定插桩点（Instrumentation Point），例如`k_busy_wait()`中自愿释放CPU时，才有机会被切换出去。

<a id="building-and-running"></a>

## 25.3 构建与运行（Building and Running）

可以按以下方式在`frdm_k64f`上构建并执行：

> 译注——命令环境：在UCRT64 Bash或Linux Bash的Zephyr源码根目录执行，先准备该板工具链、模块、烧录器和日志连接。构建成功后再烧录；构建失败先处理错误。不能把这一板目标和时序数据直接当作其他芯片的验证结果。

```sh
west build -b frdm_k64f samples/kernel/metairq_dispatch
west flash
```

要为另一块开发板构建，把上面的`frdm_k64f`替换为相应板名称。
