# 第20章\_多核数据包队列示例

原文：[官方页面](https://docs.zephyrproject.org/latest/samples/arch/smp/pktqueue/README.html)。读取日期：2026-10-14；保存的latest页面及HTML摘要见[来源记录](../SOURCES.md)。

<a id="overview"></a>

## 20.1 概述（Overview）

此示例应用实现互联网协议族中简化的网络层转发功能，本质上是IP首部验证（IP Header Validation）中的校验计算。原文参照RFC 1812《IPv4路由器要求》（Requirements for IP Version 4 Routers），原链接为[RFC 1812旧镜像](http://www.faqs.org/rfcs/rfc1812.html)。该应用用于提示微处理器在IP路由器系统中的潜在性能。

> 译注——原链接：2026-10-14检查时，旧镜像的HTTP请求返回400；可使用[RFC Editor正式来源](https://www.rfc-editor.org/rfc/rfc1812.html)阅读同一RFC。

应用开始时，初始化一个数据包首部数组，其大小由`SIZE_OF_QUEUE`定义。每个首部包含由`SIZE_OF_HEADER`指定长度的随机数据，并把计算得到的16位循环冗余校验（Cyclic Redundancy Check，CRC16）放入`CRC_BYTE_1`和`CRC_BYTE_2`定义的字段中。首部内容如下；保留原表跨列关系，每行表示32位。

> 译注——模拟负载与协议校验：当前实现用多项式`0x8005`计算CRC16；真正的IPv4首部校验和对16位字进行反码求和，再对结果取反，见[RFC 791第3.1节](https://www.rfc-editor.org/rfc/rfc791.html#section-3.1)；路由器校验要求见[RFC 1812第4.2.2.5节](https://www.rfc-editor.org/rfc/rfc1812.html#section-4.2.2.5)。因此这里是用于比较并行处理的模拟负载，不能直接当作完整、符合IPv4规范的转发实现。

随后，把首部存入多个“发送方”（Sender）队列，队列数由`QUEUE_NUM`定义。然后为每一对“发送方／接收方”（Sender／Receiver）队列创建一个线程，负责控制发送方队列的处理。

每个队列管理线程再创建由`THREADS_NUM`定义数量的工作线程。各工作线程首先从发送方队列取出首部，计算CRC；如果CRC正确，就把首部放入接收方队列。同一时刻，只允许一个线程访问某个发送方或接收方队列。

当每对队列中的所有首部都从发送方移到接收方后，与该队列对相关的线程执行结束。

在SMP系统上修改`CONFIG_MP_MAX_NUM_CPUS`，可以观察到使用更多核心时，完成计算任务所需的时间几乎按反比缩短。

还可以编辑示例源码，修改并行执行的队列对数量`QUEUE_NUM`、每对队列的线程数`THREADS_NUM`、每个队列中的首部数量`SIZE_OF_QUEUE`，以及以字节为单位的首部大小`SIZE_OF_HEADER`。

> 译注——源码对照：当前`THREADS_NUM`定义为`CONFIG_MP_MAX_NUM_CPUS + 1`，因此只修改核心配置也会改变工作线程数。每个发送／接收队列各有自己的互斥锁（Mutex），出入队在锁内进行，CRC计算在取出首部后进行。原文的扩展性描述不等同于排除了锁竞争或模拟器开销的固定加速保证。当前`queue_thread()`在发送队列计数变为0后递减`queues_remain`，主线程以此结束计时并检查接收队列；没有逐个等待工作线程退出。因此计时条件也应按所用源码版本核对，不能只依据概述推定同步过程。

## 20.2 构建与运行（Building and Running）

项目输出处理全部数据包首部所需的总时间，可以按以下方式在QEMU上构建并执行：

> 译注——命令环境：在UCRT64 Bash或Linux Bash的Zephyr源码根目录执行，先准备`qemu_x86_64`所需工具链、模块及QEMU。确认构建成功后再运行；构建或启动失败时先检查报错所指的目标配置和模拟器，不把示例输出当作已运行证据。

```sh
west build -b qemu_x86_64 samples/arch/smp/pktqueue
west build -t run
```
