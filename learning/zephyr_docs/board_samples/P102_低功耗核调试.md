# 第102章\_低功耗核调试（Debug ULP）

原文：[官方页面](https://docs.zephyrproject.org/latest/samples/boards/espressif/ulp/lp_core/debug_ulp/README.html)。快照读取日期：2026-10-15；来源摘要见[来源记录](../SOURCES.md)。

[在 GitHub 浏览源码（Browse source code on GitHub）](https://github.com/zephyrproject-rtos/zephyr/blob/main//samples/boards/espressif/ulp/lp_core/debug_ulp/README.rst/..)

<a id="overview"></a>

## 102.1 概述（Overview）

本示例演示如何为低功耗核（Low-Power Core，LP Core）构建、烧录并调试一个简单应用。

示例还提供一个自定义 `gdbinit` 文件，由 GDB 加载以设置调试环境。该文件连接远端 OpenOCD 服务器，加载低功耗核应用的符号（Symbols），并设置初始断点（Breakpoint）。

> 译注——调试连接与路径：gdbinit 连接 :3333，执行 monitor reset halt、刷新寄存器缓存，加载 build/debug_ulp_lpcore/zephyr/zephyr.elf，并以 thb do_things 设置临时硬件断点。GDB 的工作目录须与这些相对路径匹配，默认是在 Zephyr 源码根且使用该处 build。若换了构建目录，命令中的 HP ELF 和 gdbinit 中的 LP ELF 都要同步调整；读取符号并不等于重新烧录镜像。

<a id="limitations"></a>

## 102.2 限制（Limitations）

1. 当前不支持在高性能核（High-Performance Core，HP Core）或低功耗核进入任意睡眠模式时进行调试，因此可调试的场景受到限制。

2. 调试低功耗核时禁用操作系统支持，因而无法查看系统中运行的任务。取而代之的是两个分别代表高性能核和低功耗核的线程，原文称为 HP（‘esp32c6.cpu0’）和 LP（‘esp32c6.cpu1’）：

> 译注——线程视图：这里“线程”是调试器对两个处理器核的表示，不能当作 Zephyr 的两个应用线程。原文叙述中的名字与日志中的 esp32c6.hp.cpu0／esp32c6.lp.cpu 不同，以当前 OpenOCD 与 GDB 实际显示的目标名为准。

```text
(gdb) info thread
  Id   Target Id                                                                Frame
  1    Thread 1 "esp32c6.hp.cpu0" (Name: esp32c6.hp.cpu0, state: debug-request) arch_irq_unlock (key=8) at zephyr/include/zephyr/arch/riscv/arch.h:259
* 2    Thread 2 "esp32c6.lp.cpu" (Name: esp32c6.lp.cpu, state: breakpoint)      do_things (max=1000000000) at zephyr/samples/boards/espressif/ulp/lp_core/debug_ulp/remote/src/main.c:28
```

3. 在 GDB 中设置硬件断点（Hardware breakpoint）时，会同时在两个核上设置，因此可用硬件断点数量受低功耗核支持的数量限制；ESP32-C6 为两个。

<a id="sysbuild"></a>

## 102.3 多镜像系统构建（Sysbuild）

Sysbuild 负责为低功耗核目标构建 `remote` 目录中的应用。构建与烧录顺序如下：

> 译注——镜像与顺序：sysbuild.cmake 创建 debug_ulp_lpcore 子应用，并规定 LP 镜像在 HP 镜像之后烧录；只有 SB_CONFIG_BOOTLOADER_MCUBOOT 启用时，才追加先烧 MCUboot 的依赖。因此上面的三项顺序不是要求每次都启用 MCUboot。HP 启动加载器会从 slot0_lpcore_partition 读取 LP 镜像，缺少该镜像时会报错。

构建顺序：

- MCUboot 引导程序（Bootloader）

- 低功耗核应用（LP Core application）

- 高性能核应用（HP Core application）

烧录顺序：

- MCUboot 引导程序（Bootloader）

- 高性能核应用（HP Core application）

- 低功耗核应用（LP Core application）

<a id="building-and-flashing"></a>

## 102.4 构建与烧录（Building and Flashing）

> 译注——执行前提：在读者的 Zephyr 源码根目录，用 UCRT64 Bash 或 Linux Bash 执行主机命令；先按[入门指南](../getting_started/大纲.md)准备工具、模块、RISC-V 工具链和 ESP32-C6 板。--sysbuild 会构建 HP 主应用及 remote 中的 LP 子应用；烧录使用同一构建目录。提示符和输出日志不作为命令粘贴；本次未构建、烧录、调试或连接设备。

按以下命令构建示例代码：

```text
west build -b esp32c6_devkitc/esp32c6/hpcore --sysbuild samples/boards/espressif/ulp/lp_core/debug_ulp
```

使用以下命令将其烧录到设备：

```text
west build -b esp32c6_devkitc/esp32c6/hpcore --sysbuild samples/boards/espressif/ulp/lp_core/debug_ulp
west flash
```

<a id="debugging"></a>

## 102.5 调试（Debugging）

将 USB 线连接到 ESP32-C6 DevKitC 开发板的 USB 端口。

<a id="id2"></a>

ESP32-C6 模块需要尚未合入上游的 OpenOCD 补丁。Espressif 维护了自己的项目分支；可从 [OpenOCD ESP32](https://github.com/espressif/openocd-esp32/releases) [1] 获取定制版本。 相关链接：[［1］](#id1)。

在一个终端实例中运行 Espressif 的 OpenOCD：

> 译注——工具占位符：下面的 <path/to/openocd-esp32> 与 <path/to/zephyr/sdk> 需要替换为读者实际工具位置，可使用相对于当前源码根的目录；不要把尖括号占位符直接交给 Shell。路径含空格时将整个可执行文件路径用引号包住。SDK 的目录布局随发行包变化，先找到实际的 riscv64-zephyr-elf-gdb，并确认 OpenOCD 提供 board/esp32c6-lpcore-builtin.cfg。OpenOCD 保持运行，另开终端启动 GDB。

```text
<path/to/openocd-esp32>/bin/openocd -f board/esp32c6-lpcore-builtin.cfg
```

等待控制台出现以下输出：

```text
Info : Listening on port 3333 for gdb connections
```

在另一个终端实例中运行 GDB：

```text
<path/to/zephyr/sdk>/riscv64-zephyr-elf/bin/riscv64-zephyr-elf-gdb -x samples/boards/espressif/ulp/lp_core/debug_ulp/gdbinit build/debug_ulp/zephyr/zephyr.elf
```

应显示以下输出：

```text
[esp32c6.hp.cpu0] Reset cause (24) - (JTAG CPU reset)
add symbol table from file "build/debug_ulp_lpcore/zephyr/zephyr.elf"
Hardware assisted breakpoint 1 at 0x500000ec: file zephyr/samples/boards/espressif/ulp/lp_core/debug_ulp/remote/src/main.c, line 28.
(gdb)
```

从此处开始，可使用 GDB 命令调试应用。执行 `continue` 命令后，低功耗核应用会停在指定断点：

```text
(gdb) continue
Continuing.
[Switching to Thread 2]

Thread 2 "esp32c6.lp.cpu" hit Temporary breakpoint 1, do_things (max=1000000000) at zephyr/samples/boards/espressif/ulp/lp_core/debug_ulp/remote/src/main.c:28
28                      for (int i = 0; i < max; i++) {
(gdb)
```

应用执行到 `abort()` 函数时会自动中断。

> 译注——故障触发位置：remote/src/main.c 的 do_crash() 先向空指针地址写入，再调用 abort()；实际可能先因无效写入进入异常，不能保证一定执行到 abort。示例覆盖 ulp_lp_core_panic_handler()，调用 esp_cpu_dbgr_break() 让调试器停下。本次没有运行这段故障演示。
