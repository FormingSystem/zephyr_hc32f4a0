# 第1章\_Zephyr应用开发

原文：[Application Development](https://docs.zephyrproject.org/latest/develop/application/index.html)。读取日期：2026-10-12，`latest`。

本页原文约定：应用目录 `<app>` 类似 `<home>/zephyrproject/app`，构建目录为 `<app>/build`。Linux/macOS 的 `<home>` 相当于 `~`，Windows 则为 `%userprofile%`。把应用放在工作区 `<home>/zephyrproject` 内，更容易使用 `west build` 等命令；正确设置 `ZEPHYR_BASE` 后，也可以放在其他位置。

> 译注：上述路径是官方示例布局。已有工作区无需重新初始化；只有选择新建独立工作区时才执行相应的 `west init`。以下命令以主机工具、Python 环境、Zephyr 模块和目标工具链已准备好为前提。

## 1.1\_概述

Zephyr 构建系统基于 CMake，以应用为中心。应用发起 Zephyr 源码构建，控制自身与 Zephyr 的配置、编译过程，最终把二者链接成一个二进制映像。

主 `zephyr` 仓库包含 Zephyr 源码、配置和构建系统。通常旁边还安装了若干[外部模块](https://docs.zephyrproject.org/latest/develop/modules.html)，用于集成第三方代码。应用目录中的文件把 Zephyr、模块与应用连接起来，并保存应用专用配置及源码。一个简单应用可以具有如下结构：

```text
<app>
├── CMakeLists.txt
├── app.overlay
├── prj.conf
├── VERSION
└── src
    └── main.c
```

- `CMakeLists.txt` 告诉构建系统其他应用文件的位置，并把应用接入 Zephyr 的 CMake 构建系统，从而使用板专用配置、真实或模拟硬件的运行与调试等功能。
- `app.overlay` 是设备树覆盖文件，指定应用针对板基础设备树的修改，通常用于配置应用所使用的硬件。构建系统默认查找它，也会查找其他默认文件，并允许增加更多 overlay。详见[设备树](https://docs.zephyrproject.org/latest/build/dts/index.html)。
- `prj.conf` 是 Kconfig 配置片段，为一个或多个选项设置应用专用值，与其他设置合并生成最终配置，通常用于选择软件功能。它是默认查找的片段之一，也可以指定其他片段。
- `VERSION` 是包含若干版本字段的文本文件，可管理应用生命周期，并在映像签名时自动提供版本。详见[应用版本管理](https://docs.zephyrproject.org/latest/build/version/index.html)。
- `main.c` 是源码文件。应用可以包含 C、C++ 或汇编文件，Zephyr 习惯把它们放在 `<app>/src` 中。

定义应用后，由 CMake 生成单独的构建目录，再编译应用和 Zephyr 并链接出可运行的映像。最方便的入口是 `west build`，也可直接调用 CMake。Zephyr 不支持在源码目录中直接生成构建产物的 in-tree 构建；构建目录必须与源码目录分开。

## 1.2\_应用类型

按 `<app>` 所在位置区分三种应用：仓库应用位于 `zephyr` 仓库内；工作区应用位于安装 Zephyr 的 west 工作区内、但在 `zephyr` 仓库外；独立应用位于工作区外。构建系统如何支持它们，见 [Zephyr CMake Package](https://docs.zephyrproject.org/latest/build/zephyr_cmake_package.html)。

### 1.2.1\_Zephyr仓库应用

例如官方 Hello World 示例：

```text
zephyrproject/
├─── .west/
│    └─── config
└─── zephyr/
     ├── arch/
     ├── boards/
     ├── cmake/
     ├── samples/
     │    ├── hello_world/
     │    └── ...
     ├── tests/
     └── ...
```

### 1.2.2\_Zephyr工作区应用

下例的 `applications/app` 位于同一工作区，而不在 Zephyr 仓库中：

```text
zephyrproject/
├─── .west/
│    └─── config
├─── zephyr/
├─── bootloader/
├─── modules/
├─── tools/
├─── <vendor/private-repositories>/
└─── applications/
     └── app/
```

### 1.2.3\_Zephyr独立应用

下例的 `app` 位于工作区之外：

```text
<home>/
├─── zephyrproject/
│     ├─── .west/
│     │    └─── config
│     ├── zephyr/
│     ├── bootloader/
│     ├── modules/
│     └── ...
│
└─── app/
     ├── CMakeLists.txt
     ├── prj.conf
     └── src/
         └── main.c
```

## 1.3\_创建应用

可以采用参考工作区应用，也可以手工创建。

### 1.3.1\_使用参考工作区应用

官方 [example-application](https://github.com/zephyrproject-rtos/example-application) 仓库是推荐的参考，展示自定义开发板移植、设备树绑定、设备驱动、包括 Twister 的持续集成设置，以及自定义 west 扩展命令。

在已有工作区中使用它，进入工作区顶层后克隆：

```sh
cd <home>/zephyrproject
git clone https://github.com/zephyrproject-rtos/example-application my-app
```

`my-app` 目录名可以自行更换。进入该目录后调整文件；因为它属于已有工作区，可直接使用 west 构建、烧录和调试命令。

### 1.3.2\_用参考应用创建定制发行环境

该仓库也能作为定制 Zephyr 软件组合的起点：去掉不需要的模块，添加自己的仓库，用自己的版本替换上游仓库，并与他人共享协作。它包含 `west.yml`，因此也能作为 west 清单仓库。

仅在**新建独立工作区**时，执行原文步骤：

```sh
cd <home>
mkdir my-workspace
cd my-workspace
git clone https://github.com/zephyrproject-rtos/example-application my-manifest-repo
west init -l my-manifest-repo
```

这创建采用 [T2 拓扑](../west/P004_工作区.md)的工作区，清单仓库为 `my-manifest-repo`；两个目录名均可更换。克隆后的内容最初与参考仓库一致，随后可修改 `my-manifest-repo/west.yml`，按需增删仓库或调整版本。详见[清单导入](https://docs.zephyrproject.org/latest/develop/west/manifest.html#manifest-imports)，其他文件也按需求修改。

准备好清单后执行：

```text
west update
```

所需项目获取完成后即可使用工作区。如果把清单仓库发布到 `https://git.example.com/my-manifest-repo`，其他人可以建立匹配环境：

```sh
west init -m https://git.example.com/my-manifest-repo my-workspace
cd my-workspace
west update
```

之后通过向所用仓库推送修改，以及更新清单中的仓库集合和版本继续协作。


### 1.3.3\_手工创建应用

也可从零建立基本应用目录，不过从参考应用或[官方示例](https://docs.zephyrproject.org/latest/samples/index.html)开始通常更容易。

在选定父目录的 Unix shell 或 Windows `cmd.exe` 中创建应用目录：

```sh
mkdir app
```

原文警告：应用或 Zephyr 所在完整路径的任何部分含空格，都不受支持。例如路径片段 `YourName/app` 不含空格，而 `Your Name/app` 含空格。

> 译注：这里将原文的盘符路径改为相对路径片段，仅说明空格差异；检查时仍须检查整个实际路径，包括这些片段之前的父目录。

建立源码子目录：

```sh
cd app
mkdir src
```

把应用源码放入 `src`。以下假定读者自行创建了 `src/main.c`。在应用根新建 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr)
project(my_zephyr_app)

target_sources(app PRIVATE src/main.c)
```

`cmake_minimum_required()` 是 CMake 的要求，Zephyr 包中也会调用；CMake 版本低于任一处要求都将报错。`find_package(Zephyr)` 加载 Zephyr 构建系统，创建 `app` 目标，把 `Zephyr-Kernel` 定义为 CMake 项目，并启用 C、CXX、ASM。

`project(my_zephyr_app)` 定义应用项目，必须在 `find_package(Zephyr)` 后调用，以免干扰 `project(Zephyr-Kernel)`。`target_sources()` 把源码加入已创建的 `app` 目标，也必须在包加载后调用；可添加多个文件。

随后至少创建一个 Kconfig 片段，通常叫 `prj.conf`，写入应用所需选项；不需要额外设置时也创建空文件。按需要创建设备树 overlay，通常是 `app.overlay`，详见[设置 overlay](https://docs.zephyrproject.org/latest/build/dts/howtos.html#set-devicetree-overlays)。最后补充 Twister 配置、CI 文件、文档等其他材料。

## 1.4\_重要构建变量

`BOARD`、`CONF_FILE`、`DTC_OVERLAY_FILE` 可通过三种方式提供，优先级依次为命令行 `-D`、环境变量、应用 `CMakeLists.txt` 中的 `set()`。多个 overlay 路径应引用，如 `"file1.overlay;file2.overlay"`。已有 `BOARD` 缓存另有保护规则，见下一节。

| 变量 | 作用 |
| --- | --- |
| `ZEPHYR_BASE` | Zephyr 根位置；`find_package(Zephyr)` 自动写入 CMake 缓存，也可通过环境变量要求使用指定安装，包调用写法见下一节 |
| `BOARD` | 选择开发板及其默认配置；已有板见[板与扩展板列表](https://docs.zephyrproject.org/latest/boards/index.html)，新增支持见[板级移植](https://docs.zephyrproject.org/latest/hardware/porting/board_porting.html) |
| `CONF_FILE` | 一个或多个 Kconfig 配置片段，以空格或分号分隔，用来覆盖默认配置值；详见[初始配置](https://docs.zephyrproject.org/latest/build/kconfig/setting.html#the-initial-configuration) |
| `EXTRA_CONF_FILE` | 额外 Kconfig 片段，同样支持空格或分号；保留 `CONF_FILE` 默认选择，再追加设置 |
| `DTC_OVERLAY_FILE` | 一个或多个设备树 overlay，以分号分隔 |
| `EXTRA_DTC_OVERLAY_FILE` | 额外 overlay，以分号分隔；保留默认 overlay 选择再追加 |
| `SHIELD` | 选择[扩展板](https://docs.zephyrproject.org/latest/hardware/porting/shields.html) |
| `ZEPHYR_MODULES` | 包含模块目录绝对路径的 CMake 列表。设置它会替换 west 自动发现结果，因此必须列出要使用的全部模块 |
| `EXTRA_ZEPHYR_MODULES` | 与上述路径列表类似，但追加到 west 发现的模块集合，而非替换 |
| `FILE_SUFFIX` | Kconfig 片段和设备树 overlay 文件名的可选后缀；带后缀的文件不存在时退回无后缀文件 |
| `KCONFIG_WARNING_AS_ERROR` | 把每个 Kconfig 警告当作错误，包括默认只打印的警告；见[警告处理](https://docs.zephyrproject.org/latest/build/kconfig/setting.html#kconfig-warning-as-error) |

可使用 [Zephyr Build Configuration CMake 包](https://docs.zephyrproject.org/latest/build/zephyr_cmake_package.html)共享这些变量的公共设置。

## 1.5\_应用CMakeLists.txt

每个应用必须有 `CMakeLists.txt`，它是构建系统入口。最终 `zephyr.elf` 包含应用和内核库。下面的配置应按先后顺序安排。

### 1.5.1\_在加载Zephyr前选择板和配置

若应用只面向一个板，可设置：

```cmake
set(BOARD qemu_x86)
```

构建系统按顺序选择 `BOARD`，找到后停止：已有 CMake 缓存中的值优先，防止在同一个已配置目录悄悄换板；其次是命令行 `-DBOARD=YOUR_BOARD`（直接或通过 west）；再次是环境变量；最后才使用应用 `CMakeLists.txt` 的设置。

使用非默认 Kconfig 片段时，设置 `CONF_FILE`。多个路径可用空格、分号或 CMake 列表组合：

```cmake
set(CONF_FILE "fragment_file1.conf")
list(APPEND CONF_FILE "fragment_file2.conf")
```

使用设备树 overlay 时，可能还需要设置 `DTC_OVERLAY_FILE`。

### 1.5.2\_定义应用自己的Kconfig选项

若应用需要定义新的配置选项，在 `CMakeLists.txt` 同目录创建 `Kconfig`。仅为现有 Zephyr 选项赋值时，用前述 `CONF_FILE` 片段即可，不必新建选项。不同构建配置为自定义选项赋不同值属于更进阶的用法。

原文的文件结构如下，代码注释保留便于逐行对照：

```kconfig
# SPDX-License-Identifier: Apache-2.0

mainmenu "Your Application Name"

# Your application configuration options go here

# Sources Kconfig.zephyr in the Zephyr root directory.
#
# Note: All 'source' statements work relative to the Zephyr root directory (due
# to the $srctree environment variable being set to $ZEPHYR_BASE). If you want
# to 'source' relative to the current Kconfig file instead, use 'rsource' (or a
# path relative to the Zephyr root).
source "Kconfig.zephyr"
```

自定义选项放在标注的位置，最后加载 Zephyr 根目录的 `Kconfig.zephyr`。由于 `srctree` 环境变量设为 `ZEPHYR_BASE`，`source` 的相对路径从 Zephyr 根解析；若想相对于当前 Kconfig 文件，用 `rsource`，或自己写相对于 Zephyr 根的路径。

`source` 语句中的环境变量直接展开，无需用 `option env="ZEPHYR_BASE"` 定义中转符号。如果仍使用这种符号，必须与环境变量同名。详见 [Kconfig 扩展](https://docs.zephyrproject.org/latest/build/kconfig/extensions.html)。应用目录的 `Kconfig` 会自动发现；也可用绝对路径设置 `KCONFIG_ROOT`，指向其他位置。

### 1.5.3\_加载Zephyr、添加源码和合并HEX

完成前面的设置后，加载 Zephyr 并声明应用项目：

```cmake
find_package(Zephyr)
project(my_zephyr_app)
```

若要明确支持通过环境变量强制选择安装位置，可使用 `find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})`；Zephyr 所有示例均支持该环境变量。随后添加源码：

```cmake
target_sources(app PRIVATE src/main.c)
```

原文的简短组合示例为：

```cmake
set(BOARD qemu_x86)

find_package(Zephyr)
project(my_zephyr_app)

target_sources(app PRIVATE src/main.c)
```

> 译注：这个片段聚焦配置顺序；新建完整文件时仍保留上一节的 `cmake_minimum_required()`，不要因这里省略而删除它。

CMake 全局属性 `HEX_FILES_TO_MERGE` 可结合 Kconfig 和 CMake 配置，把外部构建的 HEX 与应用生成的 HEX 合并。例如：

```cmake
set_property(GLOBAL APPEND PROPERTY HEX_FILES_TO_MERGE
    ${app_bootloader_hex}
    ${PROJECT_BINARY_DIR}/${KERNEL_HEX_NAME}
    ${app_provision_hex})
```

这里用到的外部 HEX 路径变量须由应用配置提供。

### 1.5.4\_CMakeCache.txt

CMake 使用 `CMakeCache.txt` 在多次运行间持久保存字符串键值，包括编译/构建选项和依赖库路径。在空构建目录首次运行 CMake 时生成该文件。详见 [CMake Cache](https://cmake.org/cmake/help/book/mastering-cmake/chapter/CMake%20Cache.html)。

## 1.6\_应用配置

应用配置决定使用哪些软件功能和硬件设置，下面分别说明文件查找位置、配置内容和变体文件选择。

### 1.6.1\_配置目录与Kconfig

除通过 `CONF_FILE`、`EXTRA_CONF_FILE`、`DTC_OVERLAY_FILE`、`EXTRA_DTC_OVERLAY_FILE` 等参数明确给出绝对路径的文件外，Zephyr 从应用配置目录取配置。目录由 `APPLICATION_CONFIG_DIR` 确定：用户通过 `-DAPPLICATION_CONFIG_DIR=<path>` 指定，或在 `find_package(Zephyr)` 之前设置时，采用该目录；否则采用应用源码目录。

配置通常写在 `prj.conf`，例如启用 C++：

```kconfig
CONFIG_CPP=y
```

已有示例是很好的起点。详细规则见[设置 Kconfig 值](https://docs.zephyrproject.org/latest/build/kconfig/setting.html)，其中还说明了初始配置的来源；全部选项见 [Kconfig 搜索](https://docs.zephyrproject.org/latest/kconfig.html)，安全相关检查见[加固工具](../security/P005_安全加固工具.md#hardening)。计划新增选项时也应阅读 Kconfig 的其他章节。

### 1.6.2\_实验功能与设备树overlay

仍处于开发早期的功能在 Kconfig 标题中标为 `[EXPERIMENTAL]`。启用以下设置后，CMake 配置时会警告已启用的实验功能：

```kconfig
CONFIG_WARN_EXPERIMENTAL=y
```

例如同时启用实验选项 `CONFIG_FOO` 时显示：

```text
warning: Experimental symbol FOO is enabled.
```

设备树 overlay 的使用方法见[设置 overlay](https://docs.zephyrproject.org/latest/build/dts/howtos.html#set-devicetree-overlays)。

### 1.6.3\_文件后缀

同一代码库可能对应多种产品或构建变体，需要不同 Kconfig 和设备树设置。`FILE_SUFFIX` 自动为 Kconfig 片段和板 overlay 文件名增加后缀；如果带后缀文件不存在，则回退到无后缀名称。

原文示例布局：

```text
<app>
├── CMakeLists.txt
├── prj.conf
├── prj_mouse.conf
├── boards
│   ├── native_sim.overlay
│   └── qemu_cortex_m3_mouse.overlay
└── src
    └── main.c
```

| 目标板 | `FILE_SUFFIX` | 选中的Kconfig片段 | 选中的应用overlay |
| --- | --- | --- | --- |
| `native_sim` | 未定义 | `prj.conf` | `boards/native_sim.overlay` |
| `qemu_cortex_m3` | 未定义 | `prj.conf` | 无 |
| `native_sim` | `mouse` | `prj_mouse.conf` | 缺少带后缀文件，回退到 `boards/native_sim.overlay` |
| `qemu_cortex_m3` | `mouse` | `prj_mouse.conf` | `boards/qemu_cortex_m3_mouse.overlay` |

## 1.7\_应用源码与第三方库

应用专用源码通常放在 `src`；文件很多时可以按需要建立多层子目录。应用符号名称不得使用内核保留的前缀，详见[命名约定](https://github.com/zephyrproject-rtos/zephyr/wiki/Naming-Conventions)。

第三方库可以在 `src` 外构建，但库与应用必须采用相同的**应用二进制接口（Application Binary Interface，ABI）**。多数架构的 ABI 受编译选项控制，双方必须共享相关标志；适配代码也可能需要访问 Zephyr 内核头文件。

为帮助集成，Zephyr 在 `cmake/modules/extensions.cmake` 中定义并说明了一组 `zephyr_get_<type>_<format>` 函数，让应用构建脚本取得 Zephyr 编译选项。常需导出给第三方构建系统的变量包括 `CMAKE_C_COMPILER`、`CMAKE_AR`、`ARCH`、`BOARD` 以及标识 Zephyr 内核版本的变量。官方 `samples/application_development/external_lib` 展示其中部分能力。

## 1.8\_构建应用

构建系统把应用的全部组成部分编译、链接为一个可在真实或模拟硬件上运行的映像。过程分为两步：先由 `cmake` 及选定的生成器生成构建系统，再运行相应的底层工具编译源码、生成映像。west 在背后调用 CMake 和 Ninja/Make，也可手动调用它们。

Linux/macOS 可使用 Make 或 Ninja；原文规定 Windows 使用 Ninja，不支持 Make。本章默认展示 Ninja，`west build` 默认也使用它。

### 1.8.1\_从Zephyr根构建示例

使用 west：

```sh
# From the root of the zephyr repository
west build -b reel_board samples/hello_world
```

等价的 CMake/Ninja 流程：

```sh
# From the root of the zephyr repository
# Use cmake to configure a Ninja-based buildsystem:
cmake -Bbuild -GNinja -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
ninja -Cbuild
```

Linux/macOS 改用 Make 时，west 单次构建可追加 `-- -G"Unix Makefiles"`；要改变默认值，可执行 `west config build.generator "Unix Makefiles"`。原文直接调用 CMake 的对应写法为：

```sh
# From the root of the zephyr repository
# Use cmake to configure a Make-based buildsystem:
cmake -Bbuild -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
make -Cbuild
```

> 译注：该 Make 示例依赖主机 CMake 的默认生成器为 Unix Makefiles。若已设置其他生成器，应显式增加 `-G"Unix Makefiles"` 并使用新的构建目录；不要对已有 Ninja 缓存直接切换生成器。

### 1.8.2\_从应用目录构建

进入 `<app>`，把 `<board>` 替换为实际目标：

```text
west build -b <board>
```

或者在新的构建目录使用 CMake/Ninja：

```sh
mkdir build && cd build

# Use cmake to configure a Ninja-based buildsystem:
cmake -GNinja -DBOARD=<board> ..

# Now run the build tool on the generated build system:
ninja
```

要选择另一配置片段，使用 `CONF_FILE`。west 写法：

```text
west build -b <board> -- -DCONF_FILE=prj.alternate.conf
```

CMake/Ninja 写法：

```sh
mkdir build && cd build
cmake -GNinja -DBOARD=<board> -DCONF_FILE=prj.alternate.conf ..
ninja
```

原文说明替代 `.conf` 的设置覆盖应用原有或默认配置。有关最终 `.config` 的合并和重新配置条件，仍以 Kconfig 配置规则为准。也可通过 `BOARD`、`CONF_FILE` 环境变量或 CMake `set()` 持久选择；west 还支持默认板设置。

> 译注：上述 west 和手动 CMake 是两条可选路线，不能把多次 `mkdir build && cd build` 当成连续步骤执行。复用已有目录时进入原构建目录增量构建；换板或生成器时采用新目录或经过确认的 pristine 操作。

### 1.8.3\_构建目录产物

Ninja 构建目录大致如下：

```text
<app>/build
├── build.ninja
├── CMakeCache.txt
├── CMakeFiles
├── cmake_install.cmake
├── rules.ninja
└── zephyr
```

`build.ninja` 描述应用构建；`zephyr` 子目录是生成系统的重要工作位置，存放多数生成文件。它不是包含 Zephyr 源码的根目录。

运行 Ninja 后，该子目录包含 `.config`（实际构建配置）、内核和应用的 `.o` / `.a` 文件，以及最终 `zephyr.elf`。也支持 `.hex`、`.bin` 等格式。每次更新配置时，上一个 `.config` 保存为 `.config.old`，方便比较。

### 1.8.4\_重新构建与清理

开发中经常构建、测试，有助于尽早定位问题。源码、`CMakeLists.txt` 或配置显著变化后，应重新构建验证。通常仅重建可能受变化影响的部分，因此比第一次构建快。

如果必要文件没有重新编译，可进入 `<app>/build` 强制清理。以下二选一，删除生成产物但保留当前 `.config`：

```text
west build -t clean
```

```text
ninja clean
```

要连配置等全部生成内容一起删除，使用以下二选一：

```text
west build -t pristine
```

```text
ninja pristine
```

west 还支持按条件自动 pristine，见[构建与调试](../west/P007_构建烧录与调试.md)。之后按通常流程重新构建。

### 1.8.5\_选择开发板硬件修订版

同一板的小幅硬件变化可用 revision 表达，避免复制整套板支持文件。把 `<board>` 或 `<board>/<qualifiers>` 换成 `<board>@<revision>` 或 `<board>@<revision>/<qualifiers>`：

```text
west build -b nrf9160dk@0.14.0/nrf9160/ns
```

手动流程：

```sh
mkdir build && cd build
cmake -GNinja -DBOARD=nrf9160dk@0.14.0/nrf9160/ns ..
ninja
```

支持哪些修订版以板文档为准。CMake 配置时会输出当前选择，例如：

```text
-- Board: plank, Revision: 1.5.0
```

## 1.9\_运行应用

应用映像可以运行于真实开发板，也可以运行于模拟硬件，所需目标和主机工具有所不同。

<a id="application-run-board"></a>

### 1.9.1\_在开发板运行

先构建应用，将板连接到主机（通常通过 **通用串行总线（Universal Serial Bus，USB）**），然后从 `<app>/build` 执行：

```text
west flash
```

构建系统结合板支持调用相应工具，写入二进制并启动运行。默认每次 flash 都重新构建并烧录。若板支持不完整，可能没有 flash 能力；遇到不支持错误时，应查该板文档给出的替代方法。Linux 上非 root 用户访问 USB 设备可能需要安装板专用 udev 规则，失败时也应查板文档。

<a id="application-run-qemu"></a>

### 1.9.2\_在模拟器运行

Zephyr 内置 QEMU 支持，可先于实板或替代实板进行程序测试。Windows 的额外准备见[入门之后](../getting_started/P003_入门之后.md)。先为 QEMU 板构建，例如 `qemu_x86` 模拟 x86，`qemu_cortex_m3` 模拟 Arm Cortex-M3；然后从构建目录选择一种运行命令：

```text
west build -t run
```

```text
ninja run
```

退出时按 `Ctrl+A`，再按 `X`，程序停止并回到终端。每次运行目标都会先重建再运行。安装 **软件开发工具包（Software Development Kit，SDK）** 时默认使用其 QEMU；若要使用其他版本，可设置环境变量 `QEMU_BIN_PATH` 指向所需 QEMU 的路径。也可在目标后追加模拟器名，如 `west build -t run_qemu` 或 `ninja run_qemu`。

> 译注：QEMU 成功只验证所选模拟平台，不构成本项目 HC32F4A0 实板验证。

## 1.10\_自定义开发板、SoC与设备树

目标尚未被 Zephyr 支持时，可在应用或独立仓库中加入定义，不必立即放入 Zephyr 源码树。树外目录结构与树内类似，方便后续向上游提交。应用或专用仓库可具有：

```text
boards/
soc/
CMakeLists.txt
prj.conf
README.rst
src/
```

其中板目录例如：

```text
.
├── boards
│   └── vendor
│       └── my_custom_board
│           ├── doc
│           │   └── img
│           └── support
└── src
```

`soc` 保存 **片上系统（System on Chip，SoC）** 代码；自定义板也可以使用 Zephyr 已支持的 SoC。

### 1.10.1\_开发板

`boards` 下用厂商名称作目录。提交上游时应匹配 `dts/bindings/vendor-prefixes.txt` 中的前缀；非厂商板使用 `others`。`doc/` 与 `support/` 在本地开发时可选，提交 Zephyr 时则需要相应文档与支持文件。

`my_custom_board` 内容应遵循板级指南。原页列出的文件和目录为：

```text
board.yml
my_custom_board_defconfig
my_custom_board.dts
my_custom_board.yaml
board.cmake
board.h
CMakeLists.txt
doc/
Kconfig.my_custom_board
Kconfig.defconfig
support/
```

结构建立后，通过 `BOARD_ROOT` 告诉 CMake 在哪里查找：

```text
west build -b <board name> -- -DBOARD_ROOT=<path to boards>
```

```sh
cmake -Bbuild -GNinja -DBOARD=<board name> -DBOARD_ROOT=<path to boards> .
ninja -Cbuild
```

这样使用自定义板配置，在应用的构建目录生成二进制。也可在 `find_package(Zephyr ...)` 之前设置 `BOARD_ROOT`。在 `CMakeLists.txt` 中设置时必须是绝对路径，例如 `list(APPEND BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-board-root>)`；命令行 `-D` 可以使用绝对或相对路径，相对路径以应用目录为基准。

sysbuild 情况下，`BOARD_ROOT` 必须在模块或 sysbuild 的 `CMakeLists.txt` 中定义，见[配置 sysbuild 内部状态](https://docs.zephyrproject.org/latest/build/sysbuild/index.html)。

> 译注：原页占位符 `<path to boards>` 容易被理解成 `boards` 自身。`BOARD_ROOT` 应指向**包含 `boards/` 的根目录**，不是板目录或 `boards/` 目录。上面的文件表也不是要求每种板创建所有可选文件；具体要求以目标 Zephyr 版本的板级移植指南为准。

### 1.10.2\_SoC定义

结构与 Zephyr 树内相似，例如：

```text
soc
└── st
    └── stm32
        ├── common
        └── stm32l0x
```

`soc/Kconfig` 创建顶层 SoC/**中央处理器（Central Processing Unit，CPU）**/Configuration Selection 菜单。通过 CMake 变量 `SOC_ROOT` 指定包含 SoC 支持的根目录列表，以分号分隔，可把树外定义加入菜单。按上述结构可增加：

```text
soc
└── st
    └── stm32
        └── stm32l0x
            ├── Kconfig
            ├── Kconfig.soc
            └── Kconfig.defconfig
```

这些 Kconfig 文件可以描述 SoC，也可以加载其他文件。例如：

```text
soc
└── st
    └── stm32
        ├── Kconfig.soc
        └── stm32l0x
            └── Kconfig.soc
```

在 `st/stm32/Kconfig.soc` 中写入：

```kconfig
rsource "*/Kconfig.soc"
```

完成结构后，通过 `SOC_ROOT` 和 `BOARD_ROOT` 指定自定义平台：

```text
west build -b <board name> -- -DSOC_ROOT=<path to soc> -DBOARD_ROOT=<path to boards>
```

```sh
cmake -Bbuild -GNinja -DBOARD=<board name> -DSOC_ROOT=<path to soc> -DBOARD_ROOT=<path to boards> .
ninja -Cbuild
```

这样使用自定义平台配置，在构建目录生成映像。模块也可以在 `zephyr/module.yml` 的[构建设置](https://docs.zephyrproject.org/latest/develop/modules.html#build-settings)中提供 `SOC_ROOT`。若在应用 `CMakeLists.txt` 中设置，应放在 `find_package(Zephyr ...)` 前并使用绝对路径：`list(APPEND SOC_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-soc-root>)`。命令行允许绝对或相对应用目录的路径。

> 译注：`SOC_ROOT` 指向包含 `soc/` 的根目录。原页这个 `list(APPEND ...)` 示例缺少末尾右括号，译文已补齐。

### 1.10.3\_设备树定义

默认在 `APPLICATION_SOURCE_DIR`、`BOARD_DIR`、`ZEPHYR_BASE` 查找设备树目录，也可以建立额外 `DTS_ROOT`。译注：这些分别是应用源码目录、板目录、Zephyr 根目录和额外设备树搜索根的 CMake 变量。额外根下面的目录结构为：

```text
include/
dts/common/
dts/arm/
dts/
dts/bindings/
```

`arm` 应替换为所需架构，每个目录都可选。`dts/bindings` 保存绑定，其余目录保存可被设备树源文件包含的文件。结构建立后，通过 CMake 缓存变量指定根目录：

```text
west build -b <board name> -- -DDTS_ROOT=<path to dts root>
```

```sh
cmake -Bbuild -GNinja -DBOARD=<board name> -DDTS_ROOT=<path to dts root> .
ninja -Cbuild
```

也可以在 `find_package(Zephyr ...)` 前设置变量。`CMakeLists.txt` 中必须提供绝对路径，如 `list(APPEND DTS_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-dts-root>)`；命令行支持绝对或相对于应用目录的路径。这里同样补齐了原页示例缺失的右括号。

设备树源码经过 C 预处理器，可包含 `DTS_ROOT` 中找到的文件，惯例上包含文件使用 `.dtsi` 扩展名。可通过 `DTS_EXTRA_CPPFLAGS` 控制预处理，例如定义宏：

```text
west build -b <board name> -- -DDTS_EXTRA_CPPFLAGS=-DTEST_ENABLE_FEATURE
```

```sh
cmake -Bbuild -GNinja -DBOARD=<board name> -DDTS_EXTRA_CPPFLAGS=-DTEST_ENABLE_FEATURE .
ninja -Cbuild
```
