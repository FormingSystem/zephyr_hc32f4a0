# 第7章\_C加加语言支持

原文：[C++ Language Support](https://docs.zephyrproject.org/latest/develop/languages/cpp/index.html)。读取日期：2026-10-12，`latest`。

**C++（基于C发展而来的通用、面向对象编程语言）**可用于 Zephyr 应用。本章说明启用方式、运行库支持范围，以及 C/C++ 共享头文件时需要遵守的兼容规则。

## 7.1\_启用C++

Zephyr 支持同时包含 C 和 C++ 的应用。使用 C++ 时，在应用配置中启用 Kconfig 选项 [CONFIG_CPP](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_CPP)。

工具链也必须包含受 Zephyr 构建系统支持的 C++ 编译器。**Zephyr软件开发工具包（Software Development Kit，SDK）**包含属于 **GNU编译器集合（GNU Compiler Collection，GCC）**的 GNU C++ 编译器；本页所述特性和可用性以使用 Zephyr SDK 为前提。

应用默认的 C++ 标准级别为 C++11，即构建系统给编译器传入相应语言选项。也可通过 Kconfig choice 选择其他级别，例如 [CONFIG_STD_CPP98](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_STD_CPP98)。Zephyr 支持并测试的最早版本为 C++98。

构建系统按源文件后缀选择编译器，`.cpp` 和 `.cxx` 文件使用 C++ 编译器，例如 `myCplusplusApp.cpp`。

C++ 标准要求 `main()` 返回 `int`；应定义为 `int main(void)` 或 `int main(int, char **)`。使用带参数的 `main` 需要 Kconfig 选项 `CONFIG_BOOTARGS`。虽然 Zephyr 忽略 `main` 的返回值，应用仍必须返回 `0`，非零值均保留。

> 原文注意：不要用 C++ 编写内核、驱动或系统初始化代码。

## 7.2\_语言特性

Zephyr 当前只提供 C++ 功能的一个子集。原文列出以下不支持项：

- **静态全局对象析构（Static Global Object Destruction）**。
- 依赖操作系统的 C++ 标准库类，例如 `std::thread`、`std::mutex`。

支持的功能包括但不限于：

| 功能 | 英文术语与作用 |
| --- | --- |
| 继承 | Inheritance，派生类复用与扩展基类。 |
| 虚函数 | Virtual Function，支持运行时多态调用。 |
| 虚函数表 | Virtual Table，虚调用所用的运行时表。 |
| 静态全局对象构造 | Static Global Object Constructor，建立全局对象初始状态。 |
| 动态对象管理 | Dynamic Object Management，`new`、`delete` 运算符。 |
| 异常 | Exception，通过抛出与捕获传递异常情况。 |
| 运行时类型信息 | Run-Time Type Information，RTTI。 |
| 标准模板库 | Standard Template Library，STL，提供容器等通用组件。 |

静态全局对象构造发生在驱动初始化之后、应用 `main()` 之前，这也是 C++ 使用范围限定在应用代码的原因。

需要异常支持时，在应用配置中启用 [CONFIG_CPP_EXCEPTIONS](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_CPP_EXCEPTIONS)。

> 译注：上表列出可提供的能力，不表示只启用 `CONFIG_CPP` 就自动包含全部运行库和特性。最小库与完整标准库的区别见下面两节。

## 7.3\_Zephyr最小C++库

**Zephyr最小C++库（Zephyr Minimal C++ Library）**位于 `lib/cpp/minimal`，提供支持基本语言功能所需的最小标准库子集和 **应用程序二进制接口（Application Binary Interface，ABI）**函数，包括：

- `new`、`delete` 运算符。
- **虚函数桩（Virtual Function Stub）**及虚函数表。
- 为全局构造函数服务的静态全局初始化机制。

它的范围严格限于基本语言支持，不实现 STL 类或函数。因此只适用于自行实现非标准类库、且不依赖 STL 组件的应用。

使用 `std::string`、`std::vector` 等 STL 组件的应用，必须启用 C++ 标准库支持。

## 7.4\_C++标准库

**C++标准库（C++ Standard Library）**是 ISO C++ 标准规定的类与函数集合，主要位于 `std` 命名空间。Zephyr 不以源码形式随附完整标准库，而允许链接 C++ 工具链中的预编译实现。

在应用配置的 [CONFIG_LIBCPP_IMPLEMENTATION](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LIBCPP_IMPLEMENTATION) 选择组中，选择适用于工具链的实现。

例如使用 Zephyr SDK 时，启用 [CONFIG_GLIBCXX_LIBCPP](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_GLIBCXX_LIBCPP)，构建系统会链接 **GNU C++库（GNU C++ Library，libstdc++）**的 `libstdc++.a`。原文称它是提供 ISO C++ 标准功能、包括 STL 的完整库实现。

本页列出的受支持标准库为：

| 实现 | Kconfig选项 |
| --- | --- |
| GNU C++ Library | `CONFIG_GLIBCXX_LIBCPP` |
| ARC MetaWare C++ Library | [CONFIG_ARCMWDT_LIBCPP](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ARCMWDT_LIBCPP) |

需要完整 C++ 库功能的 Zephyr 子系统，可在其配置中选择 [CONFIG_REQUIRES_FULL_LIBCPP](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_REQUIRES_FULL_LIBCPP)。如果用户没有明确选择某个标准库实现，它会自动选择兼容实现。

> 译注：工具链提供完整标准库不等于 Zephyr 已实现所有依赖操作系统的类；`std::thread`、`std::mutex` 等仍受本章前述限制。应区分“库中有接口”和“当前操作系统集成支持该接口”。

## 7.5\_共享头文件与语言不兼容

C 和 C++ 通过头文件共享数据结构、宏、静态函数等代码。二者有大量重叠，但仍是存在不兼容之处的不同语言，C 并不只是 C++ 的子集。

不同标准级别又增加一层复杂性：一种语言中的特性可能多年后才被另一种语言借鉴，且细节不同；编译器可能在标准正式发布前提供实验实现；标准中的歧义可能有不同解释；编译器缺陷又可能要求特定规避方式。很多项目通过限制工具链数量减少这种复杂性，Zephyr 没有采用这种限制方式。

这些问题对头文件影响尤其大。头文件不仅必须兼容两种语言，还会因间接包含、现实项目中的组织结构不足，进入大量不同源文件的编译过程，暴露于更多工具链和配置组合。

Zephyr 对代码风格、编译器警告、静态分析和标准符合性也有严格要求，例如 **MISRA（Motor Industry Software Reliability Association，汽车工业软件可靠性协会及其编程规范体系）**相关要求。多种约束叠加后，头文件编写会非常困难。

本节记录 Zephyr 场景中的头文件实践与经验；其中很多也适用于其他项目，但不能替代对语言标准、教材及其他参考资料的学习。

### 7.5.1\_兼容性测试

Zephyr 有较完善的测试与**持续集成（Continuous Integration，CI）**设施，用于建立覆盖基线、及早发现问题、执行规范，并控制配置组合的数量膨胀。

官方源码中的 `tests/lib/cpp/cxx/` 对这类检查很有用，其 `testcase.yaml` 可让 **Twister（Zephyr测试运行器）**快速遍历多个 `-std` 参数，例如 `-std=c++98`、`-std=c++11`。

要记住，未使用的宏不会被编译。

> 译注：仅包含头文件并编译成功，不代表头文件内每个宏展开后都兼容。测试应覆盖实际使用宏的上下文；本次没有运行上述测试。

### 7.5.2\_指定初始化器

初始化宏常放在头文件中，以减少重复代码。C99 允许按指定成员名初始化 `struct` 和 `union`，而不只是提供一串无成员名表达式。一些 GCC 版本甚至在 C90 模式下也以扩展方式支持它。

简单使用**指定初始化器（Designated Initializer）**时，它更易读、更灵活且不容易出错。但 C99 允许的形式非常宽松：可以不按成员顺序、重复指定成员、嵌套指定如 `.a.x =`、省略多种花括号，或混用指定形式与普通表达式。

二十年后，C++20 也加入指定初始化器，但限制更多，部分原因是 C++ 的 `struct` 本质上也是类。如 C++ 提案 P0329 及完整参考资料所述，不能混用指定与非指定初始化，指定成员必须按声明顺序出现，但可跳过成员。

这些新限制可能使同一个 GCC 在 `-std=c++17` 下能编译的代码，改为 `-std=c++20` 后失败。例如某些 GCC 在 C++17 及更早模式下允许混用 C 风格指定项与普通表达式，C++20 模式却不接受。

原文建议：为尽量兼容多种 C/C++ 工具链和标准，Zephyr 头文件中的指定初始化器应遵守全部 C++20 规则。C99 之前的非指定初始化方式兼容性更广，也允许使用；但指定形式更易读，是优先采用的代码风格。两种风格绝不能混用于同一个初始化器。

> 原文警告：编译成功并不代表兼容问题已结束。例如 C99 没有规定初始化表达式的求值顺序，而 C++20 是预期的从左到右；其他标准版本还可能不同。不确定时，不应依赖求值顺序。

### 7.5.3\_匿名联合体

**匿名联合体（Anonymous Union，也称Unnamed Union）**很早就存在于 C++，C 到 C11 才正式加入。两种语言仍有区别，例如 C 只支持把匿名联合体作为外层结构体或联合体的成员；空初始化列表 `{ }` 在 C++ 中一直可用，而 C 要到 C23 才支持。

匿名成员初始化可以采用指定表达式或普通表达式，花括号规则也不同。为获得最大可移植性，原文给出两条要求：

1. 不要用额外花括号包住指定初始化器。C++20 及之后版本会把这种形式视为在其他指定初始化项之间混入普通表达式，导致编译失败。
2. 要用花括号包住普通表达式。C 对匿名联合体的这种初始化形式有此要求；虽然 C 允许省略许多初始化花括号，这个特定情形不能据此省略。原文将“可能用于消除多种初始化形式的歧义”作为解释性推测。

一些早于 C11 的 GCC 版本支持某种匿名联合体扩展，却要求用花括号包住指定初始化器，与上述推荐冲突。可根据 `#ifdef __STDC_VERSION__` 做条件处理，示例见 Zephyr [提交c15f029a7108](https://github.com/zephyrproject-rtos/zephyr/commit/c15f029a7108)及[相关代码审查讨论](https://github.com/zephyrproject-rtos/zephyr/issues/41543)。

> 译注：`__STDC_VERSION__` 是 C 实现用于表示所遵循 C 标准版本的预定义宏。这里的条件处理服务于特定编译器与语言模式差异，不应把它直接当成完整的 C++ 版本探测方法。
