# 第5章\_设置子系统

原文：[Settings](https://docs.zephyrproject.org/latest/services/storage/settings/index.html)。读取日期：2026-10-12，`latest`。

**设置子系统（Settings）**让模块能够持久保存各设备的配置与运行状态。它在同一组 **应用程序编程接口（Application Programming Interface，API）** 后提供 **Flash循环缓冲区（Flash Circular Buffer，FCB）**、**非易失存储（Non-Volatile Storage，NVS）**、**Zephyr内存存储（Zephyr Memory Storage，ZMS）** 和文件系统等存储实现，使应用可以选择适当介质，并在需要变化时更换后端。Zephyr 多个组件使用它，用户应用也能同时使用。

设置项以键值对保存，字符串键通常按软件包和子树组织。例如 `id/serial` 表示 `id` 包中的 `serial` 配置项。原文还说明提供了键值与字符串类型之间转换的便捷例程。使用示例见 [Settings API](P086_设置子系统示例.md)。

> 译注：原文称设置项为“key-value pair strings”，但当前接口的值是带长度的二进制数据，并不限于字符串；本页示例也直接存储整数。键使用字符串路径。
>
> 原文注意：从 Zephyr 4.1 开始，非文件系统存储推荐使用 [NVS](P002_非易失存储NVS.md) 或 [ZMS](P006_Zephyr内存存储ZMS.md) 后端。

## 5.1\_子树处理器

一个设置子树通过处理器函数接收、提交和导出数据。动态处理器用 `settings_register()` 注册，静态处理器用 `SETTINGS_STATIC_HANDLER_DEFINE()` 定义。

| 处理器 | 调用时机与作用 |
| --- | --- |
| `h_get` | 运行时后端通过 `settings_runtime_get()` 按名称请求设置值时调用 |
| `h_set` | `settings_load()` 从持久存储加载值，或运行时后端调用 `settings_runtime_set()` 时调用 |
| `h_commit` | 全部设置加载完成后调用。当多个设置互相依赖、不宜单独立即生效时，可在这里统一应用 |
| `h_export` | 写出当前所有设置时调用，例如 `settings_save()` 保存设置，或向用户实现的后端传输设置 |

处理器还有提交优先级 `cprio`，用于安排 `h_commit` 的调用次序。比如一个子系统的提交过程初始化了其他提交过程需要的服务，就可使它优先执行。默认 `cprio = 0`，整数值越小优先级越高。动态处理器可用 `settings_register_with_cprio()` 指定，静态处理器可用 `SETTINGS_STATIC_HANDLER_DEFINE_WITH_CPRIO()` 指定。

## 5.2\_后端接口

后端负责从存储加载数据到处理器，或把处理器提供的数据保存到存储。支持加载的后端通过 `settings_src_register()` 注册，支持保存的后端通过 `settings_dst_register()` 注册；当前实现允许多个来源后端，但只允许一个目标后端。

| 后端函数 | 调用时机 |
| --- | --- |
| `csi_load` | `settings_load()` 从持久存储加载设置 |
| `csi_load_one` | `settings_load_one()` 只加载一个设置项 |
| `csi_get_val_len` | `settings_get_val_len()` 查询持久存储中的值长度 |
| `csi_save` | `settings_save_one()` 保存一个设置项 |
| `csi_save_start` | `settings_save()` 或 `settings_save_subtree()` 开始保存当前设置 |
| `csi_save_end` | 上述整体或子树保存完成 |

### 5.2.1\_Zephyr提供的后端

| 后端 | Kconfig 配置项 | 来源注册 | 目标注册 |
| --- | --- | --- | --- |
| Flash 循环缓冲区 | `CONFIG_SETTINGS_FCB` | `settings_fcb_src()` | `settings_fcb_dst()` |
| 文件系统中的文件 | `CONFIG_SETTINGS_FILE` | `settings_file_src()` | `settings_file_dst()` |
| NVS | `CONFIG_SETTINGS_NVS` | `settings_nvs_src()` | `settings_nvs_dst()` |
| ZMS | `CONFIG_SETTINGS_ZMS` | `settings_zms_src()` | `settings_zms_dst()` |

可以声明多个来源，`settings_load()` 会恢复所有来源的设置；写入目标只能有一个，`settings_save()`、`settings_save_one()` 都写入该目标。`settings_fcb_src()` 还会初始化 FCB 区域，因此必须先于 `settings_fcb_dst()` 调用。

ZMS 后端的特点是先对设置键求哈希，再写入持久存储。键数量较多时可能发生哈希冲突，具体取决于选用的哈希函数。该后端最多可处理 `2^n` 个冲突，`n` 由 `CONFIG_SETTINGS_ZMS_MAX_COLLISIONS_BITS` 指定。

### 5.2.2\_存储位置

FCB、NVS、ZMS 后端默认寻找 `label` 为 `storage` 的固定分区；可在设备树 `/chosen` 节点的 `zephyr,settings-partition` 属性中选择其他分区。文件后端的路径由 `CONFIG_SETTINGS_FILE_PATH` 指定。

## 5.3\_从持久存储加载

`settings_load()` 通过 `h_set` 把设置加载到易失性内存；全部加载结束后调用 `h_commit`，通知应用设置已取回。也可以通过 `settings_load_one()` 只加载一个条目，将数据直接放入指定缓冲区。

如果只想查询值的长度，可调用 `settings_get_val_len()`。例如应用需要动态分配缓冲区时，可以先查询长度，再通过 `settings_load_one()` 读取。

FCB 和文件后端可能保留记录历史，较新记录追加在较旧记录之后。从 Zephyr 2.1 开始，后端必须过滤所有旧版本，仅使用最新版本调用回调。

## 5.4\_保存与垃圾回收

`settings_save_one()` 使用后端实现把设置写入介质。`settings_save()` 则通过 `h_export` 在一次操作中导出多个数据项，并借助 `settings_save_one()` 存储。只有希望被 `settings_save()` 保存的键，才必须由 `h_export` 覆盖；单独保存键不要求实现它。

FCB 和文件后端只保存相对于当前最新值有变化的数据，所以应用无须自己检查是否变化。这意味着同一个键可能有多个历史赋值，只有最后一个是当前值。

当 FCB 存储已满，或文件占用过多空间时，后端执行垃圾回收，删除旧键值记录及不再需要的键删除记录。

## 5.5\_安全域设置

当前设置子系统不提供同一实例同时承担安全域和非安全域配置存储的方案。建议安全域使用独立实例；如有需要，可根据具体情况通过专用接口向非安全域提供数据。

## 5.6\_示例：设备配置

此例只实现 `h_set` 和 `h_export`。从存储恢复值或最初设置值时调用 `h_set`；`h_export` 通过 `storage_func()` 将值写入存储。用户也可以实现其他导出行为，例如输出到 shell 控制台。

```c
#define DEFAULT_FOO_VAL_VALUE 1

static int8 foo_val = DEFAULT_FOO_VAL_VALUE;

static int foo_settings_set(const char *name, size_t len,
                            settings_read_cb read_cb, void *cb_arg)
{
    const char *next;
    int rc;

    if (settings_name_steq(name, "bar", &next) && !next) {
        if (len != sizeof(foo_val)) {
            return -EINVAL;
        }

        rc = read_cb(cb_arg, &foo_val, sizeof(foo_val));
        if (rc >= 0) {
            /* key-value pair was properly read.
             * rc contains value length.
             */
            return 0;
        }
        /* read-out error */
        return rc;
    }

    return -ENOENT;
}

static int foo_settings_export(int (*storage_func)(const char *name,
                                                   const void *value,
                                                   size_t val_len))
{
    return storage_func("foo/bar", &foo_val, sizeof(foo_val));
}

struct settings_handler my_conf = {
    .name = "foo",
    .h_set = foo_settings_set,
    .h_export = foo_settings_export
};
```

> 译注：原文中的 `int8` 不是标准 C 的固定宽度整数类型；若项目没有自行定义该类型，应使用 `<stdint.h>` 中的 `int8_t` 等正确类型。示例保留原样。`read_cb()` 返回非负数只表示没有负错误码，完整读取还应检查返回长度是否等于期望长度；本例不能作为忽略短读的通用模板。

## 5.7\_示例：持久保存运行状态

此例只定义用于恢复数据的 `h_set`。主函数递增 `foo_val` 并保存最新值。重启时，初始化阶段调用 `settings_load()`，计数就能从重启前的数值继续。

```c
#include <zephyr/kernel.h>
#include <zephyr/sys/reboot.h>
#include <zephyr/settings/settings.h>
#include <zephyr/sys/printk.h>
#include <inttypes.h>

#define DEFAULT_FOO_VAL_VALUE 0

static uint8_t foo_val = DEFAULT_FOO_VAL_VALUE;

static int foo_settings_set(const char *name, size_t len,
                            settings_read_cb read_cb, void *cb_arg)
{
    const char *next;
    int rc;

    if (settings_name_steq(name, "bar", &next) && !next) {
        if (len != sizeof(foo_val)) {
            return -EINVAL;
        }

        rc = read_cb(cb_arg, &foo_val, sizeof(foo_val));
        if (rc >= 0) {
            return 0;
        }

        return rc;
    }


    return -ENOENT;
}

struct settings_handler my_conf = {
    .name = "foo",
    .h_set = foo_settings_set
};

int main(void)
{
    settings_subsys_init();
    settings_register(&my_conf);
    settings_load();

    foo_val++;
    settings_save_one("foo/bar", &foo_val, sizeof(foo_val));

    printk("foo: %d\n", foo_val);

    k_msleep(1000);
    sys_reboot(SYS_REBOOT_COLD);
}
```

> 译注：原例每次启动后等待一秒再冷重启，适合说明状态恢复过程，不是建议应用采用的常驻重启逻辑。`foo_val` 为八位无符号数，超过 255 会回绕；实际应用还应处理初始化、注册、加载、保存的返回值，并核对读取长度。连续重启写入也应纳入存储寿命估算。

## 5.8\_示例：自定义后端

启用 `CONFIG_SETTINGS_CUSTOM` 后，可以注册自定义后端处理器。下面展示接口结构和来源、目标注册过程：

```c
static int settings_custom_load(struct settings_store *cs,
                                const struct settings_load_arg *arg)
{
    //...
}

static int settings_custom_save(struct settings_store *cs, const char *name,
                                const char *value, size_t val_len)
{
    //...
}

/* custom backend interface */
static struct settings_store_itf settings_custom_itf = {
    .csi_load = settings_custom_load,
    .csi_save = settings_custom_save,
};

/* custom backend node */
static struct settings_store settings_custom_store = {
    .cs_itf = &settings_custom_itf
};

int settings_backend_init(void)
{
    /* register custom backend */
    settings_dst_register(&settings_custom_store);
    settings_src_register(&settings_custom_store);
    return 0;
}
```

> 译注：`settings_custom_load()` 和 `settings_custom_save()` 的函数体是待实现部分；需要补充实际存储操作和返回值。这段只演示注册结构，并未提供可用的存储实现。
