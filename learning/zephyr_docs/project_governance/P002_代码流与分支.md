# 第2章\_代码流与分支（Code Flow and Branches）

原文：[官方页面](https://docs.zephyrproject.org/latest/project/code_flow.html)。快照读取日期：2026-10-15；来源摘要见[来源记录](../SOURCES.md)。

<a id="introduction"></a>

## 2.1 引言（Introduction）

Zephyr Git 仓库有三类分支：

`main`（主开发分支）

包含最新的开发状态。

`collab-*`（协作分支）

用于共同开发新功能，准备就绪后引入 main。创建协作分支需要理由和 TSC 批准。分支应基于 main，开发的变更也应以主开发分支为目标。对于已发布版本，修复和新功能如获 TSC 批准，应通过回移拉取请求（Backport PR）引入。

`vx.y-branch`（维护分支）

跟踪基于主要发布版本的维护版本。

功能进入主线前，团队可在协作分支上独立开发子系统或功能，提升效率、缩短周转时间，并促进合作和沟通。

提交到协作分支的变更可以逐步演进和完善，之后再提交主线完成最终集成。

为复杂功能设置独立分支，有利于在引入正式项目之前深入讨论新增内容。

协作分支是临时性的，协作完成后应删除。申请分支的提案应包含：

- 明确将协作分支变更合回 main 的退出准则（Exit criteria）。

- 明确分支预期生命周期的时间表，建议以某个 Zephyr 发布版本为时间目标。延长时间需要 TSC 批准。

<a id="roles-and-responsibilities"></a>

## 2.2 角色与职责（Roles and Responsibilities）

协作分支负责人应承担以下职责：

- 使用项目提供的基础设施和工具，如 GitHub、Git。

- 协作分支的全部变更都应通过 GitHub PR 提交。

- 仅在基于 main 进行变基（Rebase）时，才允许强制推送（Force push）协作分支。

- 评审团队成员的变更，提交变更时请求分支负责人评审。

- 保持分支与上游同步，定期更新。

- 经常通过以下方式向上游提交变更：

  - GitHub 拉取请求：例如，本地分支尚未完成评审的情况，如单人维护的分支。

  - 合并请求（Merge request）：一组变更已在本地完成，并在协作分支上经过评审和测试时使用。

对应官方文档源码：[doc/project/code_flow.rst](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/doc/project/code_flow.rst)。

> 译注——分支规则的适用范围：本页描述官方协作分支（Collaboration branch）的维护流程。分支所有权、强制推送和删除等规则应按参与的上游分支约定理解，不是本中文文档对读者当前仓库的操作指令。

> 译注——源码跟踪：本仓库[对应源码](../../../doc/project/code_flow.rst)可用于对照，版本可能与网页不同。本批仅翻译和核对文档，未执行Git工作流、构建、发布或连接设备。
