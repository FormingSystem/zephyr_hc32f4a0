# 第4章\_代码文档（Code Documentation）

原文：[官方页面](https://docs.zephyrproject.org/latest/project/documentation.html)。快照读取日期：2026-10-15；来源摘要见[来源记录](../SOURCES.md)。

<a id="api-documentation"></a>

## 4.1 API 文档（API Documentation）

完善的 API 文档能改善开发体验，也是 API 成功的重要条件。Zephyr 使用通用工具 Doxygen 编写 API 文档。它可生成 HTML 在线浏览页面，也可为其他工具提供输入，以便从带文档注释的源码生成参考手册。Zephyr 在线文档生成过程尤其使用 Doxygen XML 输出作为输入。

<a id="reference-to-requirements"></a>

## 4.2 引用需求（Reference to Requirements）

API 文档大多描述需求或声明功能的实现，并可追溯到相应功能。项目以 API 文档为主要接口，将实现追溯到文档化的功能；使用 Doxygen 原生需求追溯命令 `@satisfies` 和 `@verifies`，引用在其他位置的需求目录中维护的需求。

<a id="test-documentation"></a>

## 4.3 测试文档（Test Documentation）

为说明每项测试做什么、验证哪种功能，也使用相同工具在同一环境中记录测试代码，为所有单元测试和集成测试生成文档。测试文档通过链接被验证的 API 或功能，并引用原始需求，建立关联。

<a id="documentation-guidelines"></a>

## 4.4 文档指南（Documentation Guidelines）

<a id="test-code"></a>

### 4.4.1 测试代码（Test Code）

项目采用多种测试方法，最常见的是 [Ztest 框架](../testing/P002_Ztest测试框架.md#test-framework)。测试文档只应写在测试入口函数（通常以 test_ 开头）及 Ztest 直接调用的函数上。这些测试会出现在报告中，使用其名称和标识最便于识别，并从需求追溯到测试。

测试文档不应干扰实际 API 文档，应采用独立结构避免混淆。通过统一命名和明确结构，可将其归入独立模块，并在解析测试数据、生成追溯报告时唯一识别。规则如下：

- 全部测试代码文档都应归入 Doxygen 的 `all_tests` 分组。

- 全部测试文档都应位于名称以 tests_ 为前缀的 Doxygen 分组下。

> 译注——命名差异：上方规则要求分组名称以 `tests_` 开头，但下方官方示例使用 `kernel_semaphore_tests`。这里保留两者，避免在翻译中自行改写示例；新增测试应核对所用源码版本的文档规则与相邻测试。

<a id="documenting-a-requirement"></a>

### 4.4.2 记录需求（Documenting a Requirement）

使用 Doxygen 的 `@requirement` 命令记录需求，参数是唯一标识符及可选标题。Doxygen 将需求汇总到一页，并允许其他位置通过标识引用。应为需求使用专用注释块，通常维护在需求目录中：

```text
/**
* @requirement ZEPH-015 (Give a semaphore)
*
* The kernel shall provide a mechanism to give a semaphore, increasing its
* count up to its configured maximum.
*/
```

此处的标识符，例如 `ZEPH-015`，与下方 `@satisfies` 和 `@verifies` 引用的标识相同，从而把实现和测试关联到需求。

> 译注——需求示例含义：Give a semaphore 表示释放信号量（Semaphore）；英文需求要求内核提供增加信号量计数的机制，计数最高达到已配置的上限。需求标识 `ZEPH-015` 与 Doxygen 命令均按原例保留。

Doxygen 的 `@verifies` 表示某项测试验证一条需求：

```text
/**
* @brief Tests for the Semaphore kernel object
* @defgroup kernel_semaphore_tests Semaphore
* @ingroup all_tests
* @{
*/

...
/**
* @brief A brief description of the tests
* Some details about the test
* more details
*
* @verifies ZEPH-015
*/
void test_sema_thread2thread(void)
{
...
}
...

/**
* @}
*/
```

使用 Doxygen 的 `@satisfies` 描述实现或代码片段如何满足需求，以获取相应覆盖关系：

> 译注——测试注释含义：上方示例为“信号量内核对象的测试”，建立名为 Semaphore 的分组，并归入 `all_tests`；brief 和后续占位文字分别要求测试简介与细节。`@verifies` 声明测试与需求的追溯关系，不能单凭这条注释判断测试已执行通过。

```text
/**
* @brief Give a semaphore.
*
* This routine gives @a sem, unless the semaphore is already at its maximum
* permitted count.
*
* @note Can be called by ISRs.
*
* @param sem Address of the semaphore.
*
* @satisfies ZEPH-015
*/
__syscall void k_sem_give(struct k_sem *sem);
```

生成追溯矩阵前，需先构建文档，尤其是 Doxygen XML 输出：

> 译注——API 注释含义：上方 `k_sem_give()` 释放参数 `sem` 指向的信号量，除非其计数已达到允许的最大值；ISR 表示中断服务例程（Interrupt Service Routine），注释说明该函数可由 ISR 调用。`@satisfies` 是实现与需求的文档关联，不代替运行验证。

```text
$ make doxygen
```

> 译注——构建位置与前提：上面的 `$` 是终端提示符，不属于命令。该示例应在已按[官方文档构建说明](https://docs.zephyrproject.org/latest/contribute/documentation/index.html)完成依赖安装和 CMake 配置、且选择 Makefiles 生成器的文档构建目录内，用 UCRT64 Bash 或 Linux Bash 执行；不能直接假定翻译目录存在 Makefile。官方 [doc/CMakeLists.txt](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/doc/CMakeLists.txt)定义 `doxygen` 目标。本仓库可从[对应构建源码](../../../doc/CMakeLists.txt)追踪，版本可能不同。成功后检查构建日志及生成的 Doxygen 输出；若没有 Makefile 或工具报错，先返回依赖和生成器配置步骤。本次仅核对示例，未执行构建。

解析生成的 Doxygen XML 数据，生成可追溯矩阵（Traceability matrix）。

对应官方文档源码：[doc/project/documentation.rst](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/doc/project/documentation.rst)。
