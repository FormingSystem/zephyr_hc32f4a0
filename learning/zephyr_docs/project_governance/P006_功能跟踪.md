# 第6章\_功能跟踪（Feature Tracking）

原文：[官方页面](https://docs.zephyrproject.org/latest/project/proposals.html)。快照读取日期：2026-10-15；来源摘要见[来源记录](../SOURCES.md)。

向 Zephyr 提议新事项时：

1. 先搜索[已有 Issue](https://github.com/zephyrproject-rtos/zephyr/issues)，确认是否已有人开展相关工作。

2. 如果没有，可创建适当类型的[新 Issue](https://github.com/zephyrproject-rtos/zephyr/issues/new/choose)，例如 Enhancement、RFC/Proposal 等。

若希望讨论或参与已有 Issue 的实现，应联系其受指派负责人。

注意（Note）

项目过去通过 [GitHub 标签](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels)跟踪功能工作，因此可能看到带 Feature 或 Enhancement 标签的旧 Issue。

新 Issue 不再使用这些旧标签，而应选择适当类型。例如，创建 Enhancement 类型的 Issue，而不是给新 Issue 添加 Enhancement 标签。

<a id="roadmap-and-release-plans"></a>

## 6.1 路线图与发布计划（Roadmap and Release Plans）

项目路线图和发布计划都很重要，但用途不同，不应混淆。路线图传达高层战略概览；发布计划是战术性文档，用于记录并跟踪计划纳入后续版本的功能。

- 路线图说明“为什么”，发布计划细化“做什么”。

- 发布计划通常覆盖数月，产品路线图可能覆盖一年或更久。

<a id="project-roadmap"></a>

### 6.1.1 项目路线图（Project Roadmap）

项目路线图应以高层、可视化方式概括战略目标与预期。

良好的路线图可以向现有及潜在利益相关方清楚展示计划，帮助吸引新成员；团队和社区也可在开发过程中持续参照，以确认仍按计划推进。

因此，路线图应仅包含战略层细节、主要主题、大型功能项（Epic）和目标。

<a id="release-plans"></a>

### 6.1.2 发布计划（Release Plans）

将路线图的高层战略转换为可执行计划时，就需要发布计划，明确某个版本或里程碑必须包含的具体功能、改进和修复。

发布计划传达下一次或随后几次发布拟包含的功能与改进，更接近项目执行计划：将大型设想拆为较小项目，便于社区和主要利益相关方推进。

对应官方文档源码：[doc/project/proposals.rst](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/doc/project/proposals.rst)。

> 译注——跟踪方式：本页按官方快照保留 Feature、Enhancement 等 Issue 类型与分类用语。GitHub 类型、标签（Label）、指派（Assignment）和评审批准（Approval）是不同对象；文档不同页面的历史写法不意味着当前界面中每一种字段都仍以同样形式存在。

> 译注——源码跟踪：本仓库[对应源码](../../../doc/project/proposals.rst)可用于对照，版本可能与网页不同。本批仅翻译和核对文档，未执行Git工作流、构建、发布或连接设备。
