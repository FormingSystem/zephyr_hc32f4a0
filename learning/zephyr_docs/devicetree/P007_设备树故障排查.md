# 第7章\_设备树故障排查

原文：[Troubleshooting devicetree](https://docs.zephyrproject.org/latest/build/dts/troubleshooting.html)。读取日期：2026-10-12，`latest`。

本页介绍修复设备树相关代码问题的方法；其他操作说明见[设备树操作指南](P006_设备树操作指南.md)。以下 `<build>` 均指应用的构建目录，示例地址与开发板不代表 HC32 硬件事实。

## 7.1\_先排除旧构建产物

原文强调先用 pristine 构建目录重试，再进行其他排查。用法见[west 构建](../west/P007_构建烧录与调试.md)，也可以彻底移除旧构建目录后重建。

设备树输出在 CMake 配置阶段生成，输入变化不一定总能触发正确的重新生成，因此这条通用建议对设备树特别适用。

> 译注：只清理已核实的应用构建目录，不删除源码或 `.west`。本次只翻译操作说明，没有执行清理。

## 7.2\_诊断工具与头文件

可选诊断工具 DT Doctor 能协助定位设备树问题，构建时向 CMake 传入 `-DZEPHYR_SCA_VARIANT=dtdoctor` 启用；详见[设备树诊断](https://docs.zephyrproject.org/latest/develop/sca/dtdoctor.html)。

还要确保显式包含设备树头文件。与 Kconfig 符号不同，`devicetree.h` 必须通过 include 引入。其他 Zephyr **应用程序编程接口（Application Programming Interface，API）** 头文件可能间接包含它，但不保证如此。

> 译注：当前通常写 `#include <zephyr/devicetree.h>`；不要依赖其他头文件碰巧间接包含。

## 7.3\_undefined reference to __device_dts_ord_N

这通常发生在类似代码：

```c
const struct device *dev = DEVICE_DT_GET(NODE_ID);
```

`NODE_ID` 是有效节点标识符，但没有驱动为它创建 `struct device`，因此链接时找不到请求的对象。应确认两件事：节点为 `status = "okay";`（未写 status 也视为 okay）；负责创建设备对象的驱动已经通过 Kconfig 启用并编入应用。

### 7.3.1\_确认节点启用

先取链接错误中的数字 `<N>`，到 `<build>/zephyr/include/generated/zephyr/devicetree_generated.h` 顶部节点列表中查找。例如序号 15 对应 `/soc/i2c@deadbeef`：

```text
/*
 * Generated by gen_defines.py
 *
 * DTS input file:
 *   zephyr.dts.pre
 *
 * Directories with bindings:
 *   $ZEPHYR_BASE/dts/bindings
 *
 * Node dependency ordering (ordinal and path):
 *   0   /
 *   1   /aliases
[...]
 *   15  /soc/i2c@deadbeef
[...]
```

再到最终合并树 `<build>/zephyr/zephyr.dts` 找这个节点。若仍为 disabled，例如：

```dts
i2c0: i2c@deadbeef {
        status = "disabled";
};
```

在 overlay 中启用：

```dts
&i2c0 {
        status = "okay";
};
```

然后 pristine 重建，再确认最终 `zephyr.dts` 已出现 `status = "okay";`。

### 7.3.2\_确认驱动编入应用

从节点 `compatible` 开始，找到负责该 compatible 并创建 `struct device` 的驱动。不熟悉设备对象分配过程时，可参考[设备驱动模型](https://docs.zephyrproject.org/latest/kernel/drivers/index.html)以及原文链接的 ZDS 2021 演讲“A deep dive into the Zephyr 2.5 device model”（可从[原页](https://docs.zephyrproject.org/latest/build/dts/troubleshooting.html)进入）。

原文说明尚无完整文档逐项映射全部驱动和 compatible，因此需要查源码：先进入 `drivers` 下与设备 API 对应的子目录，再阅读相关文件，判断是否已有驱动。

常见线索是 `DT_DRV_COMPAT`：把 compatible 转小写并把特殊字符换为下划线。例如 `vnd,foo-device` 可对应：

```c
#define DT_DRV_COMPAT vnd_foo_device
```

但并非所有驱动都定义这个宏，搜索不到不能直接断定没有驱动。确认 compatible 正确仍没有实现时，需要编写驱动，这超出本页范围。

继续前例，若节点为：

```dts
i2c0: i2c@deadbeef {
        compatible = "nordic,nrf-twim";
        status = "okay";
};
```

应在 `drivers/i2c` 找处理 `nordic,nrf-twim` 的 `i2c_nrfx_twim.c`。即使没有 `DT_DRV_COMPAT`，文件名也可提供线索。接着查看该子目录 `CMakeLists.txt` 中决定是否编译文件的条件，例如：

```cmake
zephyr_library_sources_ifdef(CONFIG_NRFX_TWIM       i2c_nrfx_twim.c)
```

这表示 `<build>/zephyr/.config` 必须有 `CONFIG_NRFX_TWIM=y`。如果没有，应判断怎样满足其条件；很多驱动会在节点启用后自动启用。也有情况需在应用 `prj.conf` 加入：

```kconfig
CONFIG_FOO=y
```

`CONFIG_FOO` 代表 CMake 实际检查的驱动选项，不能原样照抄。随后 pristine 重建。若还有未满足的 Kconfig 依赖，必须先满足它们，详见定义该选项的 Kconfig 文件及[配置值设置](../kconfig/P003_设置配置值.md)。

## 7.4\_确认名字所处的语言

C/C++ 设备树 API 参数要使用小写，并将特殊字符转为下划线，这是生成头文件采用的 C token 形式。overlay 则是 **设备树源文件（Devicetree Source，DTS）** 片段，必须保留 DTS 本身的节点名和属性名。

例如读取 `/soc/i2c@12340000` 的 `clock-frequency`，原文 C 示例为：

```c
/*
 * foo.c: lowercase-and-underscores names
 */

/* Don't do this: */
#define MY_CLOCK_FREQ DT_PROP(DT_PATH(soc, i2c@1234000), clock-frequency)
/*                                           ^               ^
 *                                        @ should be _     - should be _  */

/* Do this instead: */
#define MY_CLOCK_FREQ DT_PROP(DT_PATH(soc, i2c_1234000), clock_frequency)
/*                                           ^               ^           */
```

> 译注：原文示例比说明中的地址少一个 0。若节点确实为 `i2c@12340000`，正确完整写法应为 `DT_PROP(DT_PATH(soc, i2c_12340000), clock_frequency)`；字符替换不能改变地址数字。

overlay 中则相反：

```dts
/*
 * foo.overlay: DTS names with special characters, etc.
 */

/* Don't do this; you'll get devicetree errors. */
&{/soc/i2c_12340000/} {
     clock_frequency = <115200>;
};

/* Do this instead. Overlays are just DTS fragments. */
&{/soc/i2c@12340000/} {
     clock-frequency = <115200>;
};
```

这里的两组错误/正确写法是对照，不是要求把它们一起加入工程。

## 7.5\_查看预处理输出

启用 `CONFIG_COMPILER_SAVE_TEMPS` 保存预处理结果。例如用 west 构建 Hello World：

```text
west build -b BOARD samples/hello_world -- -DCONFIG_COMPILER_SAVE_TEMPS=y
```

`BOARD` 替换为目标板。每个 `foo.c` 会在构建目录生成对应 `foo.c.i`，可查宏最终展开内容。在 Linux/macOS 查找 `main.c.i` 的原文终端示例：

```console
$ find build -name main.c.i
build/CMakeFiles/app.dir/src/main.c.i
```

打开前先格式化通常更容易读，例如原地格式化这个生成文件：

```text
clang-format -i build/CMakeFiles/app.dir/src/main.c.i
```

然后在编辑器中检查最终 C 代码。这里只改生成的预处理输出，不是修改应用源文件。

## 7.6\_减少宏展开错误输出

复杂设备树宏有多层展开，编译器可能为每一层输出信息，导致日志很长。关闭 `CONFIG_COMPILER_TRACK_MACRO_EXPANSION` 通常可把每个错误缩减为一条信息：

```text
west build -b BOARD samples/hello_world -- -DCONFIG_COMPILER_TRACK_MACRO_EXPANSION=n
```

## 7.7\_验证节点与属性

读取属性时报编译错误，应先验证节点标识符和属性。例如：

```c
int baud_rate = DT_PROP(DT_NODELABEL(my_serial), current_speed);
```

加入以下检查后重新编译：

```c
#if !DT_NODE_EXISTS(DT_NODELABEL(my_serial))
#error "whoops"
#endif
```

如果出现 `whoops`，标识符没有指向有效节点；先检查最终树和生成头文件。没有该错误时，继续确认名称转换是否正确、属性是否存在、节点是否匹配绑定、绑定是否定义该属性。

## 7.8\_缺失绑定与实例API问题

绑定说明见[官方绑定指南](https://docs.zephyrproject.org/latest/build/dts/bindings.html)，内置绑定见[绑定索引](https://docs.zephyrproject.org/latest/build/dts/api/bindings.html)。节点没有匹配绑定时，可能没写 compatible，也可能其值没有对应绑定；先排除名称拼错。在 DTS 中应是 `"vnd,some-device"` 形式，不能误用 C 宏形式。绑定位于 `zephyr/dts` 之外时，可能需设置 `DTS_ROOT`，见[应用树外设备树接入](../application/P001_应用开发.md)。

使用 `DT_INST_PROP()` 等实例 API 时，必须先把 `DT_DRV_COMPAT` 定义为所需 compatible 的小写下划线形式，详见[驱动实例化](P006_设备树操作指南.md)。
