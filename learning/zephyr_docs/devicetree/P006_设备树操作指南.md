# 第6章\_设备树操作指南

原文：[Devicetree HOWTOs](https://docs.zephyrproject.org/latest/build/dts/howtos.html)。读取日期：2026-10-12，`latest`。

本页给出完成设备树相关任务的逐步建议；问题定位见[设备树故障排查](https://docs.zephyrproject.org/latest/build/dts/troubleshooting.html)。

> 译注：命令在已准备好模块和工具链的实验源码根执行，`<board>` 等占位符须替换。下面 **通用异步收发器（Universal Asynchronous Receiver-Transmitter，UART）**、**串行外设接口（Serial Peripheral Interface，SPI）**、**集成电路间总线（Inter-Integrated Circuit，I2C）** 地址和节点均是官方示例，不是本项目 HC32 硬件定义。驱动代码是说明接口的骨架，包含未实现函数和占位类型，不应当作可直接编译的完整驱动。本页明确标出了原文代码中的不一致。

<a id="get-devicetree-outputs"></a>

## 6.1\_取得最终设备树和生成头文件

板的 `BOARD.dts` 通过 `#include` 引入公共定义，至少包括 **片上系统（System on Chip，SoC）** 的 `.dtsi`。可以逐个打开 `dts/<ARCH>/<vendor>/<soc>.dtsi` 等文件查看，但耗时较多。若只想看板最终的设备树，构建应用后打开构建目录的 `zephyr.dts`。

用 Hello World 可以查看没有额外应用 overlay 修改的基础树。例如在 Zephyr 源码根为 Cortex-M3 QEMU 板运行：

```sh
# --cmake-only here just forces CMake to run, skipping the
# build process to save time.
west build -b qemu_cortex_m3 samples/hello_world --cmake-only
```

`--cmake-only` 只执行 CMake，跳过编译以节省时间；可替换为实际开发板。配置输出会指出输入和生成文件，原文输出示例如下：

```text
-- Found BOARD.dts: .../zephyr/boards/arm/qemu_cortex_m3/qemu_cortex_m3.dts
-- Generated zephyr.dts: .../zephyr/build/zephyr/zephyr.dts
-- Generated devicetree_generated.h: .../zephyr/build/zephyr/include/generated/zephyr/devicetree_generated.h
```

`zephyr.dts` 是最终 **设备树源文件（Devicetree Source，DTS）**，`devicetree_generated.h` 是对应生成头文件，详情见[输入输出](P004_输入与输出文件.md)。原文输出中的 `boards/arm/...` 属于旧目录示例，实际位置以本次 CMake 输出为准。

## 6.2\_从节点取得struct device

应用经常需要从设备树节点取得驱动层 `struct device`。例如希望取得下列 `serial@40002000` 的设备对象：

```dts
/ {
        soc {
                serial0: serial@40002000 {
                        status = "okay";
                        current-speed = <115200>;
                        /* ... */
                };
        };

        aliases {
                my-serial = &serial0;
        };

        chosen {
                zephyr,console = &serial0;
        };
};
```

先建立节点标识符，下列四种写法按需要选择一种，不是连续重复定义：

```c
/* Option 1: by node label */
#define MY_SERIAL DT_NODELABEL(serial0)

/* Option 2: by alias */
#define MY_SERIAL DT_ALIAS(my_serial)

/* Option 3: by chosen node */
#define MY_SERIAL DT_CHOSEN(zephyr_console)

/* Option 4: by path */
#define MY_SERIAL DT_PATH(soc, serial_40002000)
```

它们分别按节点标签、别名、chosen 属性和路径定位同一节点。取得标识符后，一种方式是 `DEVICE_DT_GET`：

```c
const struct device *const uart_dev = DEVICE_DT_GET(MY_SERIAL);

if (!device_is_ready(uart_dev)) {
        /* Not ready, do not use */
        return -ENODEV;
}
```

还有 `DEVICE_DT_GET_OR_NULL`、`DEVICE_DT_GET_ONE`、`DEVICE_DT_GET_ANY` 等变体。这种方式在构建时确定设备指针，不付出运行时查找代价，适合把指针保存在配置数据里。但设备可能尚未初始化或初始化失败，所以传入任何设备 **应用程序编程接口（Application Programming Interface，API）** 前必须检查 ready 状态。

某些场景在构建时无法知道设备，例如 shell 命令由用户输入设备名，此时可在运行时查找：

```c
const char *dev_name = /* TODO: insert device name from user */;
const struct device *uart_dev = device_get_binding(dev_name);
```

`device_get_binding()` 会替读者检查设备状态。取得指针后，可调用 `uart_configure()` 等 UART API；其他设备也采用类似方式，但必须使用正确类别的 API。

遇到问题先确认节点启用。原文的条件编译示例如下：

```c
#define MY_SERIAL DT_NODELABEL(my_serial)

#if DT_NODE_HAS_STATUS(MY_SERIAL, okay)
const struct device *const uart_dev = DEVICE_DT_GET(MY_SERIAL);
#else
#error "Node is disabled"
#endif
```

> 译注：这一段原文把节点标签换成了 `my_serial`，与本节开头的 `serial0` 不一致。若沿用开头 DTS，应把第一行改为 `#define MY_SERIAL DT_NODELABEL(serial0)`；若使用别名则是 `DT_ALIAS(my_serial)`。不能把节点标签和别名混作同一个参数。

出现 `#error` 时应检查节点并启用。代码可能编译成功但链接报错：

```text
...undefined reference to `__device_dts_ord_N'
collect2: error: ld returned 1 exit status
```

这通常意味着 Kconfig 阻止对应驱动编译，引用的设备对象没有定义。成功编译链接后，还应检查初始化状态：

```c
if (!device_is_ready(uart_dev)) {
     printk("Device not ready\n");
}
```

不 ready 往往表示驱动初始化失败，可启用日志或调试初始化代码。运行时 `device_get_binding()` 返回 `NULL` 则可能是设备不存在，也可能是初始化失败。

## 6.3\_查找节点绑定

绑定是 YAML 文件，定义节点允许的内容，因此必须能找到所用节点的绑定。先生成设备树和头文件；打开生成头文件，开头注释列出依赖顺序中的节点：

```c
/*
 * [...]
 * Nodes in dependency order (ordinal and path):
 *   0   /
 *   1   /aliases
 *   2   /chosen
 *   3   /flash@0
 *   4   /memory@20000000
 *          (etc.)
 * [...]
 */
```

记下目标路径，如 `/flash@0`，再在同一文件搜索该节点输出。如果匹配到绑定，会看到：

```c
/*
 * Devicetree node:
 *   /flash@0
 *
 * Binding (compatible = soc-nv-flash):
 *   $ZEPHYR_BASE/dts/bindings/mtd/soc-nv-flash.yaml
 * [...]
 */
```

找不到时，按[缺失绑定排查](https://docs.zephyrproject.org/latest/build/dts/troubleshooting.html)继续定位。

## 6.4\_选择overlay文件

`DTC_OVERLAY_FILE` 是以空格或分号分隔的 overlay 列表，多文件按列出顺序经 C 预处理器包含。引用模块内文件时，可以转义模块目录变量，如 `\${ZEPHYR_<module>_MODULE_DIR}/<path-to>/dts.overlay`。

可以显式指定所需的全部文件，west 传参方式见[构建与调试](../west/P007_构建烧录与调试.md)。未设置 `DTC_OVERLAY_FILE` 时，构建系统在应用配置目录依次查找：

1. `socs/<SOC>_<BOARD_QUALIFIERS>.overlay` 存在则加入。
2. `boards/<BOARD>.overlay` 存在则追加。
3. 使用板 revision 且 `boards/<BOARD>_<revision>.overlay` 存在则追加。
4. 前三步已找到至少一个文件，就停止查找并使用这些文件。
5. 否则若 `<BOARD>.overlay` 存在，就使用它并停止。
6. 否则若 `app.overlay` 存在，就使用它。

还可通过 `EXTRA_DTC_OVERLAY_FILE` 追加文件，而保留上述自动选择流程。额外列表排在 `DTC_OVERLAY_FILE` 后，因此覆盖优先级更高。

除显式给出的绝对路径外，文件从应用配置目录读取，目录定义见[应用开发](../application/P001_应用开发.md)。使用 shield 也会增加 overlay。`DTC_OVERLAY_FILE` 的值存入 CMake 缓存，后续构建继续使用；配置阶段会打印实际选中的文件：

```text
-- Found devicetree overlay: .../some/file.overlay
```

## 6.5\_用overlay修改节点

先按上一节把 overlay 纳入构建。若 `BOARD.dts` 包含：

```dts
/ {
        soc {
                serial0: serial@40002000 {
                        status = "okay";
                        current-speed = <115200>;
                        /* ... */
                };
        };
};
```

下面两种覆盖 `current-speed` 的写法等价，后续采用节点标签方式：

```dts
/* Option 1 */
&serial0 {
     current-speed = <9600>;
};

/* Option 2 */
&{/soc/serial@40002000} {
     current-speed = <9600>;
};
```

别名是 `/aliases` 的属性，可这样增加：

```dts
/ {
     aliases {
             my-serial = &serial0;
     };
};
```

chosen 的写法类似：

```dts
/ {
     chosen {
             zephyr,console = &serial0;
     };
};
```

删除属性如下。原本存在的布尔属性要设为假，也采用删除方式：

```dts
&serial0 {
     /delete-property/ some-unwanted-property;
};
```

还可以给已有总线增加子节点，原文 SPI/I2C 示例为：

```dts
/* SPI device example */
&spi1 {
     my_spi_device: temp-sensor@0 {
             compatible = "...";
             label = "TEMP_SENSOR_0";
             /* reg is the chip select number, if needed;
              * If present, it must match the node's unit address. */
             reg = <0>;
             /* Configure other SPI device properties as needed.
              * Find your device's DT binding for details. */
             spi-max-frequency = <DT_FREQ_M(4)>;
     };
};

/* I2C device example */
&i2c2 {
     my_i2c_device: touchscreen@76 {
             compatible = "...";
             label = "TOUCHSCREEN";
             /* reg is the I2C device address.
              * It must match the node's unit address. */
             reg = <76>;
             /* Configure other I2C device properties as needed.
              * Find your device's DT binding for details. */
     };
};
```

SPI 的 `reg` 表示需要时使用的片选编号，必须匹配单元地址；其余属性依设备绑定配置。I2C 的 `reg` 是总线地址，也应匹配节点单元地址。其他总线采用同样步骤：在总线下创建子节点，按其绑定设置属性。

> 译注：上述 I2C 原例存在进制不一致：`touchscreen@76` 的单元地址按十六进制解释，但 `<76>` 是十进制。若目标地址确为 `0x76`，应写 `reg = <0x76>;`；若是十进制 76，则节点地址应为 `@4c`。此外，新绑定不推荐使用 `label` 属性，见[语法与结构](P003_语法与结构.md)；这里保留原例以便核对。`compatible = "..."` 必须换成实际绑定，使用 `DT_FREQ_M` 还需相应定义可见。

存在匹配 `my_spi_device` 和 `my_i2c_device` compatible 的驱动时，可以通过 Kconfig 启用，取得新加**外设节点**的 `struct device`，再使用对应 API。译文把原文此处的“bus node”明确为示例实际新增的外设子节点。

## 6.6\_用设备树API编写驱动

支持设备树的驱动，应为每个匹配其 compatible（或相关 compatible 集合）且 `status = "okay"` 的节点创建一个 `struct device`。

首先为硬件编写绑定，可参考类似驱动的现有绑定。最小骨架可以是：

```yaml
description: <Human-readable description of your binding>
compatible: "foo-company,bar-device"
include: base.yaml
```

description 填写便于人阅读的说明。绑定完成后，驱动 C 文件可找出所需 enabled 节点，为每个节点创建设备对象，方式分为实例编号和节点标签两种。

原文提出两条共同原则：设备名称按节点的 `label` 属性设置，便于用户取得对象；初始配置尽量来自设备树属性，便于通过 overlay 改变。

> 译注：原文关于设备名依赖 `label` 的表述是旧惯例，与当前不推荐新加 label 的说明不同。新驱动使用下面的 `DEVICE_DT_DEFINE` / `DEVICE_DT_INST_DEFINE` 以及当前版本的设备命名规则，不应为满足旧句子强加 label。编译期按节点取得设备也不需要 label 属性。

以下假定已经实现设备专用数据、配置和 API，原文骨架为：

```c
/* my_driver.c */
#include <zephyr/drivers/some_api.h>

/* Define data (RAM) and configuration (ROM) structures: */
struct my_dev_data {
     /* per-device values to store in RAM */
};
struct my_dev_cfg {
     uint32_t freq; /* Just an example: initial clock frequency in Hz */
     /* other configuration to store in ROM */
};

/* Implement driver API functions (drivers/some_api.h callbacks): */
static int my_driver_api_func1(const struct device *dev, uint32_t *foo) { /* ... */ }
static int my_driver_api_func2(const struct device *dev, uint64_t bar) { /* ... */ }

static struct some_api my_api_funcs = {
     .func1 = my_driver_api_func1,
     .func2 = my_driver_api_func2,
};
```

`my_dev_data` 保存各设备的 **随机存取存储器（Random Access Memory，RAM）** 数据，`my_dev_cfg` 保存 **只读存储器（Read-Only Memory，ROM）** 配置，例中的 `freq` 是以 Hz 表示的初始时钟频率；API 回调通过 `my_api_funcs` 关联。

### 6.6.1\_方式一：实例编号

条件允许时优先采用基于实例的 API，但它要求该驱动 compatible 对应的节点可以等同处理，不必识别各自是哪一个硬件实例。

先在 C 文件靠前位置（例如 include 之后）定义 `DT_DRV_COMPAT`。DTS 中的 `"vnd,my-device"` 转为小写下划线形式：

```c
/*
 * Put this near the top of the file. After the includes is a good place.
 * (Note that you can therefore run "git grep DT_DRV_COMPAT drivers" in
 * the zephyr Git repository to look for example drivers using this style).
 */
#define DT_DRV_COMPAT vnd_my_device
```

这里不能带引号或特殊字符，特殊字符转成下划线。在定义 `my_api_funcs` 后增加实例化宏，原文为：

```c
/*
 * This instantiation macro is named "CREATE_MY_DEVICE".
 * Its "inst" argument is an arbitrary instance number.
 *
 * Put this near the end of the file, e.g. after defining "my_api_funcs".
 */
#define CREATE_MY_DEVICE(inst)                                       \
     static struct my_dev_data my_data_##inst = {                    \
             /* initialize RAM values as needed, e.g.: */            \
             .freq = DT_INST_PROP(inst, clock_frequency),            \
     };                                                              \
     static const struct my_dev_cfg my_cfg_##inst = {                \
             /* initialize ROM values as needed. */                  \
     };                                                              \
     DEVICE_DT_INST_DEFINE(inst,                                     \
                           my_dev_init_function,                     \
                           NULL,                                     \
                           &my_data_##inst,                          \
                           &my_cfg_##inst,                           \
                           MY_DEV_INIT_LEVEL, MY_DEV_INIT_PRIORITY,  \
                           &my_api_funcs);
```

> 译注：原例把 `.freq` 初始化写进 `my_dev_data`，但上面的字段定义在 `my_dev_cfg`，两者不一致。按所给结构使用时，应把 `.freq = DT_INST_PROP(inst, clock_frequency),` 移到 `my_cfg_##inst` 初始化块；RAM 块按实际运行数据初始化。以下节点标签方案也有同一原文问题。绑定还必须声明 `clock-frequency`，并提供实际初始化函数、级别、优先级及 API 类型。

`DT_INST_PROP` 和 `DEVICE_DT_INST_DEFINE` 从 `DT_DRV_COMPAT` 对应节点的实例 `inst` 取数据和创建设备。最后把宏交给：

```c
/* Call the device creation macro for each instance: */
DT_INST_FOREACH_STATUS_OKAY(CREATE_MY_DEVICE)
```

每个匹配且启用的节点会调用一次 `CREATE_MY_DEVICE`。`DT_INST_FOREACH_STATUS_OKAY` 不会替宏展开追加分号，因此实例化宏必须以分号或函数定义结束，才能正确连续生成多个设备。

### 6.6.2\_方式二：节点标签

某些驱动无法把各实例等同处理，例如厂商 HAL 针对不同 IP 块提供不同接口。此时用 `DT_NODELABEL` 定位 SoC 外设节点，再用通用 API 读取数据。

SoC 的 DTSI 应给支持的 IP 块定义 `mydevice0`、`mydevice1` 等标签：

```dts
/ {
        soc {
                mydevice0: dev@0 {
                        compatible = "vnd,my-device";
                };
                mydevice1: dev@1 {
                        compatible = "vnd,my-device";
                };
        };
};
```

驱动由标签识别具体节点：

```c
/*
 * This is a convenience macro for creating a node identifier for
 * the relevant devices. An example use is MYDEV(0) to refer to
 * the node with label "mydevice0".
 */
#define MYDEV(idx) DT_NODELABEL(mydevice ## idx)

/*
 * Define your instantiation macro; "idx" is a number like 0 for mydevice0
 * or 1 for mydevice1. It uses MYDEV() to create the node label from the
 * index.
 */
#define CREATE_MY_DEVICE(idx)                                        \
     static struct my_dev_data my_data_##idx = {                     \
             /* initialize RAM values as needed, e.g.: */            \
             .freq = DT_PROP(MYDEV(idx), clock_frequency),           \
     };                                                              \
     static const struct my_dev_cfg my_cfg_##idx = { /* ... */ };    \
     DEVICE_DT_DEFINE(MYDEV(idx),                                    \
                     my_dev_init_function,                           \
                     NULL,                                           \
                     &my_data_##idx,                                 \
                     &my_cfg_##idx,                                  \
                     MY_DEV_INIT_LEVEL, MY_DEV_INIT_PRIORITY,        \
                     &my_api_funcs)
```

`MYDEV(0)` 取得 `mydevice0` 标识符，随后通过 `DT_PROP`、`DEVICE_DT_DEFINE` 获取节点数据并创建设备。原例 `.freq` 初始化所属结构的修正方法见上一小节。

最后手工检查每个节点是否启用并实例化：

```c
#if DT_NODE_HAS_STATUS(DT_NODELABEL(mydevice0), okay)
CREATE_MY_DEVICE(0)
#endif

#if DT_NODE_HAS_STATUS(DT_NODELABEL(mydevice1), okay)
CREATE_MY_DEVICE(1)
#endif
```

因为没有 `DT_INST_FOREACH_STATUS_OKAY()`，作者必须根据支持的 SoC 外设集合，为每个可能的节点安排 `CREATE_MY_DEVICE()`。

## 6.7\_设备之间的依赖

一个设备可能需要另一个设备的指针，例如传感器需要 SPI 控制器。绑定应尽可能支持 `devicetree.h` 中的硬件专用 API。总线设备的绑定应包含对应公共文件，如 `dts/bindings/spi/spi-device.yaml`，提供该总线设备通用定义。这样可用 `DT_BUS` 取得总线节点标识符，再按前文方式取得总线的 `struct device`。现有绑定和驱动可以作为参考。

## 6.8\_应用依赖板专用硬件时

要使同一应用代码不改动地运行于多板，可用设备树别名指定硬件相关部分，[LED 闪烁示例](../getting_started/P004_LED闪烁示例.md)就采用这种方式。具体选择放在 `BOARD.dts` 或 overlay 中。
