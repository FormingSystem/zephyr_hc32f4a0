# 第14章\_设备树设计目标

原文：[Design goals](https://docs.zephyrproject.org/latest/build/dts/design.html)。读取日期：2026-10-12，`latest`。

Zephyr 对**设备树（Devicetree）**的使用随时间发生了较大变化，后续仍会演进。本页说明总体设计目标、这些目标如何影响源码，以及原文列出的尚待改进方向。

## 14.1\_硬件信息只维护一份来源

Zephyr 内置驱动和示例应用，应从设备树取得可配置的硬件描述。这样，同一硬件的信息不必在驱动、应用及其他工具中分别维护。

具体要求包括：

- 新驱动通过设备树**应用程序编程接口（Application Programming Interface，API）**确定创建哪些设备对象，见[驱动实例创建方法](https://docs.zephyrproject.org/latest/build/dts/howtos.html#dt-create-devices)。
- 树内示例使用**别名（Alias）**，从同类多个通用设备中选择本次构建使用的设备。例如 [Blinky示例](https://docs.zephyrproject.org/latest/samples/basic/blinky/README.html#blinky)用别名选择闪烁的发光二极管。别名与选择节点的语法见[对应章节](https://docs.zephyrproject.org/latest/build/dts/intro-syntax-structure.html#dt-alias-chosen)。
- 新**片上系统（System on Chip，SoC）**的启动引脚复用及引脚配置，应由基于设备树的 **引脚控制（Pin Control，pinctrl）**驱动完成。

原文列出的待改进工作是：

- **Twister测试运行器（Twister Test Runner）**使用板的 `board.yaml` 判定硬件支持，未来应改从设备树取得。
- 一些旧驱动用 Kconfig 决定启用哪些 `compatible` 实例，应改用设备树**覆盖文件（Overlay）**。
- 板文档中手工维护的硬件支持表，应从板级设备树生成。
- 运行时确定 `struct device` 设备对象之间的关系，例如设备电源管理依赖，应利用设备树信息。

> 译注：这些是所读取原文对演进方向的说明，不是本次对整个源码现状逐项进行的完成度审计；不能将“待改进”直接理解为所有当前版本都仍缺少同一机制。

## 14.2\_保持与其他系统的源码兼容

Zephyr 设备树工具基于通用层，目标是与 Linux 内核等其他设备树使用者互操作。Zephyr 的绑定语言可以支持自身特有属性，但不应表达仅属于 Zephyr 的关系。

具体分层为：

- `dtlib.py` 是设备树源码解析器，与 [设备树编译器（Devicetree Compiler，dtc）](https://git.kernel.org/pub/scm/utils/dtc/dtc.git/about/)双向源码兼容：两者能读取对方的输出。
- `edtlib.py` 是扩展的 dtlib 库，提供中断、总线等通用元素的高层视图，不应包含 Zephyr 特有功能。
- 只有建立在 `edtlib.py` 之上的高层脚本 `gen_defines.py` 包含 Zephyr 特有知识及功能。

脚本职责见[输入输出与脚本说明](https://docs.zephyrproject.org/latest/build/dts/intro-input-output.html#dt-scripts)。

原文指出的剩余工作包括：Zephyr 使用自己的绑定语法，Linux 的 dtschema 尚不能满足全部需求，但应尽量对齐其可表达内容；当前绑定语言的灵活性不足，不能支持 Linux 的全部绑定；Zephyr 与 Linux 尚未进行设备树源码共享。

> 译注：dtschema 是设备树模式校验工具体系的名称。这里区分“通用解析语法可兼容”与“绑定表达和实际源码可直接共享”，前者不自动保证后两者。

## 14.3\_同一硬件由多种软件接口使用

一个硬件单元可通过不同 Zephyr API 使用时，设备树应把硬件身份与驱动、子系统使用各实例的方式分开。

建模原则如下：

1. `compatible` 聚焦设备的编程模型，不应仅为了选择软件 API 就改变它。硬件接口在架构上确实不同，例如使用不同寄存器块时，可以使用不同 `compatible`。
2. 对全系统只选一个实例的功能，用 `/chosen` 表达**单实例选择（Singleton Selection）**。系统定时器、控制台或熵源等功能，即使其他相同硬件实例用于不同 API，也应使用平台无关的选择属性。
3. 在正确层级保存选择。芯片固定特征写在 SoC `.dtsi`；随板、产品或应用变化的内容写在板 `.dts` 或覆盖文件。
4. 若同一硬件的不同用途有不同必需属性、子节点或总线语义，不必强制共用一个绑定模式；可采用不同 `compatible`，或者将设备建模为**多功能设备（Multi-Function Device）**。

Zephyr 选择属性参考见 [Zephyr特有chosen节点](https://docs.zephyrproject.org/latest/build/dts/api/api.html#devicetree-zephyr-chosen-nodes)。

## 14.4\_用chosen选择系统定时器

系统定时器是全系统单实例功能。`zephyr,system-timer` 属性选择由哪一个硬件定时器提供，其余相同实例仍可服务于其他 API。

例如两个相同的低功耗定时器 LPTMR 实例可共用同一 `compatible`：

```dts
lptmr1: timer@44300000 {
    compatible = "nxp,lptmr";
    reg = <0x44300000 0x1000>;
    /* ... */
};

lptmr2: timer@424d0000 {
    compatible = "nxp,lptmr";
    reg = <0x424d0000 0x1000>;
    /* ... */
};
```

集成层再选择具体实例：

```dts
/ {
    chosen {
        zephyr,system-timer = &lptmr1;
    };
};
```

系统定时器驱动据 `/chosen` 的选择绑定对应实例，计数器驱动跳过这个实例并使用剩余实例。

> 译注：这两个代码块是官方设备树片段，寄存器地址属于示例硬件，不能用于 HC32。原文“驱动绑定到 `/chosen` 节点”在这里应理解为按该节点引用选择硬件；`/chosen` 本身不是上面具有寄存器地址的定时器节点。是否由特定驱动实现跳过行为，应核对该版本驱动，不能仅因写入属性就假定任意驱动都会执行。
