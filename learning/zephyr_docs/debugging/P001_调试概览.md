# 第1章\_调试概览

原文：[Debugging](https://docs.zephyrproject.org/latest/develop/debug/index.html)。读取日期：2026-10-12，`latest`。

## 1.1\_应用调试

本节是使用 **QEMU（开源机器模拟器的项目名）**调试应用的快速上手参考，多数内容也见 [QEMU 手册](https://wiki.qemu.org/Main_Page)与 [GNU调试器（GNU Debugger，GDB）手册](https://www.gnu.org/software/gdb)。这里汇集便于配置环境的快捷方法、环境变量和参数。

最简单的方式是让 QEMU 在开发主机上提供本地 **GDB服务器（GDB Server）**，再用 GDB 连接。服务器负责控制模拟目标，客户端负责提供断点、单步和变量查看等交互。

调试需要 **可执行与可链接格式（Executable and Linkable Format，ELF）**二进制镜像。构建系统在构建目录生成它，默认名称为 `zephyr.elf`，可通过 Kconfig 配置项 `CONFIG_KERNEL_BIN_NAME` 更改。

### 1.1.1\_启动GDB服务器

以下使用常见的 **传输控制协议（Transmission Control Protocol，TCP）**端口 `1234`，也可以改为适合当前开发环境的端口。各种方式都会在启动时暂停模拟处理器，并让 GDB 服务器等待连接。

直接运行 QEMU：

```sh
qemu -s -S <image>
```

`-S` 表示启动时不立即运行 **中央处理器（Central Processing Unit，CPU）**，可在 QEMU 监视器中输入 `c` 继续；`-s` 是 `-gdb tcp::1234` 的简写，在 TCP 1234 端口启动服务器。

> 译注：`qemu` 与 `<image>` 是原文的概括写法。实际执行文件通常区分架构，还需要匹配模拟机型及镜像加载参数；在 Zephyr 应用中优先使用以下构建目标取得相应板级参数。

通过 Ninja 启动：在应用构建目录执行：

```sh
ninja debugserver
```

QEMU 把控制台输出写到 CMake 变量 `${QEMU_PIPE}` 指定路径，通常为构建目录中的 `qemu-fifo`。可在运行时使用 `tail -f qemu-fifo` 查看。

通过 west 启动：在项目根目录执行：

```sh
west build -t debugserver_qemu
```

此方式把 QEMU 控制台输出写到调用 west 的终端。

### 1.1.2\_配置监听设备

Kconfig 配置项 `CONFIG_QEMU_GDBSERVER_LISTEN_DEV` 控制监听设备，可以是 TCP 端口，也可以是字符设备路径。GDB 9.0 及更新版本还支持 **Unix域套接字（Unix Domain Socket）**，即同一主机内基于路径寻址的通信端点。

未设置该选项时，QEMU 调用中没有 `-s` 或 `-gdb` 参数；可通过 shell 环境变量 `QEMU_EXTRA_FLAGS` 提供自己的监听配置。

### 1.1.3\_连接GDB客户端

启动 GDB 并执行。下例中的 `ZEPHYR_BASE` 是 Zephyr 源码目录的占位名称：

```text
$ path/to/gdb path/to/zephyr.elf
(gdb) target remote localhost:1234
(gdb) dir ZEPHYR_BASE
```

将 `ZEPHYR_BASE` 替换为当前系统中的实际 Zephyr 源码目录。

> 译注：`dir` 用来添加源文件搜索目录。原例中的 `ZEPHYR_BASE` 是待替换文本，不表示 GDB 自动把它展开为同名环境变量。`path/to/gdb` 与 `path/to/zephyr.elf` 也需按当前执行目录填写正确相对路径。

可通过本地 `.gdbinit` 文件在每次启动 GDB 时初始化配置。该文件通常放在用户主目录，也可配置 GDB 从其他位置加载，例如当前启动目录。对应配置：

```text
target remote localhost:1234
dir ZEPHYR_BASE
```

### 1.1.4\_其他界面

GDB 提供基于 curses 的**文本用户界面（Text User Interface，TUI）**，可在启动时加入 `--tui`，或在 GDB 中执行 `tui enable`。

> 原文注意：开发主机上的 GDB 可能不支持 `--tui`。请使用与构建工具链相匹配的 **软件开发工具包（Software Development Kit，SDK）**所提供的 GDB。

下列命令使用 GDB 的图形前端 **DDD（Data Display Debugger，数据可视化调试器）**，从本例的 `zephyr.elf` 加载符号表：

```sh
ddd --gdb --debugger "gdb zephyr.elf"
```

这些方法最终都会运行 GDB。具体命令名称取决于所用工具链和交叉开发工具。系统不一定默认安装 DDD，应按操作系统说明安装；例如 Ubuntu 使用 `sudo apt-get install ddd`。

### 1.1.5\_开始调试

按上述方式连接后，应用停在系统启动处。此时可以设置断点、单步执行，操作方式与直接在 GDB 中调试本机应用相似。

> 原文注意：这里 GDB 不会直接显示目标系统的控制台输出。连接后执行继续运行，应用虽然开始执行，GDB 窗口却可能没有新输出；应按前述 QEMU 启动方式查看对应控制台。

## 1.2\_使用Eclipse调试

CMake 可生成可导入 **集成开发环境（Integrated Development Environment，IDE）**的项目描述，使 Eclipse 能进行图形调试。GNU MCU Eclipse 插件提供使用 pyOCD、SEGGER J-Link 和 OpenOCD 调试 Arm 工程的机制。

以下原教程演示在 Windows 上通过 Eclipse 和 pyOCD 调试 Zephyr，假定已安装 GCC Arm Embedded 工具链和 pyOCD。

> 译注：Eclipse 是 IDE 名称；**GNU编译器集合（GNU Compiler Collection，GCC）**提供编译工具；pyOCD 是基于 Python 的调试工具项目；**开放片上调试器（Open On-Chip Debugger，OpenOCD）**提供调试服务；J-Link 是 SEGGER 的探针与工具产品系列。本节包含旧插件名称、旧 Eclipse 下载页和旧 CMake 生成器写法，作为原文版本的流程保留。使用前应确认当前 Eclipse 插件与 `cmake --help` 所列生成器是否支持它们，不以本页代替当前版本安装验证。

### 1.2.1\_配置Eclipse环境

1. 下载并安装 [Eclipse IDE for C/C++ Developers](https://www.eclipse.org/downloads/packages/eclipse-ide-cc-developers/oxygen2)。
2. 打开 **Window → Eclipse Marketplace…（窗口→插件市场）**，搜索 `GNU MCU Eclipse` 并安装匹配结果。原插件说明见 [GNU MCU Eclipse](https://gnu-mcu-eclipse.github.io/plugins/install/)。
3. 打开 **Window → Preferences（窗口→首选项）**，进入 MCU，配置 **Global pyOCD Path（全局 pyOCD 路径）**。

### 1.2.2\_生成并导入工程

先按 [GNU Arm Embedded](../toolchains/P004_GNUArmEmbedded.md) 配置工具链，再进入 Zephyr 源码树外的目录构建应用。原文 Windows 示例为：

```bat
# On Windows
cd %userprofile%
```

> 原文注意：如果构建目录位于源码目录之下，CMake 会警告：构建目录是源码目录的子目录，Eclipse 对此支持不佳，强烈建议采用与源码目录并列的构建目录。

使用 CMake 配置，并通过 Ninja 构建。这里通过 `-G"Eclipse CDT4 - Ninja"` 选择不同的生成器，除普通 Ninja 构建文件外，还会生成 Eclipse `.project` 描述文件。

使用 west：

```sh
west build -b frdm_k64f samples/synchronization -- -G"Eclipse CDT4 - Ninja"
```

使用 CMake 与 Ninja；`-DBOARD` 是为 CMake 变量 `BOARD` 赋值的参数：

```sh
cmake -Bbuild -GNinja -DBOARD=frdm_k64f -G"Eclipse CDT4 - Ninja" samples/synchronization
ninja -Cbuild
```

> 译注：原文切换到源码树外后，仍把应用写为 `samples/synchronization`，该相对路径未必存在；实际应填从当前目录到应用的正确相对路径。CMake 示例还同时给出 `-GNinja` 与另一个 `-G`，实际调用应只保留所需的一个生成器。`frdm_k64f` 是原例目标板，不是本项目板卡。

在 Eclipse 中打开 **File → Import…（文件→导入）**，选择 **Existing Projects into Workspace（已有工程导入工作区）**。在 **Select root directory（选择根目录）**中定位应用构建目录，勾选发现的工程，点击 **Finish（完成）**。

### 1.2.3\_创建调试配置

打开 **Run → Debug Configurations…（运行→调试配置）**，选择 **GDB PyOCD Debugging**，点击 **New（新建）**，配置如下字段。

| 标签页/分组 | 字段 | 原文设置 |
| --- | --- | --- |
| Main | Project | `my_zephyr_app@build` |
| Main | C/C++ Application | `zephyr/zephyr.elf` |
| Debugger / pyOCD Setup | Executable path | `$pyocd_path\$pyocd_executable` |
| Debugger / pyOCD Setup | Allocate console for semihosting | 不勾选 |
| Debugger / Board Setup | Bus speed | `8000000 Hz` |
| Debugger / Board Setup | Enable semihosting | 不勾选 |
| Debugger / GDB Client Setup | Executable path | 从 `GNUARMEMB_TOOLCHAIN_PATH` 所指安装目录选择 `bin/arm-none-eabi-gdb.exe` |
| SVD Path | File path | 相对于工作区顶层的 `modules/hal/nxp/mcux/devices/MK64F12/MK64F12.xml` |

> 原文注意：SVD 路径可选，用于向调试器提供**片上系统（System on Chip，SoC）**的内存映射寄存器地址与位字段。

> 译注：**系统视图描述（System View Description，SVD）**以机器可读形式描述寄存器；**半主机（Semihosting）**让目标程序通过调试器调用主机输入输出。原文 GDB 可执行文件的固定盘符示例改为从工具链根目录定位。表中 8 MHz、SVD 文件与项目名均属于原例，不能直接套到其他芯片。

点击 **Debug（调试）**开始会话。

### 1.2.4\_RTOS线程感知

[pyOCD v0.11.0](https://github.com/pyocd/pyOCD/releases/tag/v0.11.0) 及更新版本支持 Zephyr **实时操作系统感知（Real-Time Operating System Awareness，RTOS Awareness）**。它可与 Eclipse 的 GDB PyOCD Debugging 配合，应用需设置 Kconfig 配置项 `CONFIG_DEBUG_THREAD_INFO=y`。

> 译注：RTOS 感知让调试器识别内核线程及其状态，而不只显示当前处理器的寄存器。工具支持此功能与应用提供必要线程信息，是两个都要满足的条件。

## 1.3\_调试I2C通信

可记录应用执行的全部或部分 **集成电路间总线（Inter-Integrated Circuit，I2C）**事务。启用 Kconfig 配置项 `CONFIG_I2C_DUMP_MESSAGES`；由于内容通过 `LOG_DBG` 调试日志宏输出，还需启用 Kconfig 配置项 `CONFIG_I2C_LOG_LEVEL_DBG`。

原文示例输出：

```text
D: I2C msg: io_i2c_ctrl7_port0, addr=50
D:    W      len=01: 00
D:    R Sr P len=08:
D: contents:
D: 43 42 41 00 00 00 00 00 |CBA.....
```

首行表示本次事务的控制器和目标地址：控制器为 `io_i2c_ctrl7_port0`，目标地址为 `0x50`。

> 原文注意：地址、长度、内容均以十六进制表示，只是没有 `0x` 前缀。

后续各行包含发送和接收的消息。写消息内容始终显示，读消息内容是否显示取决于传给 `i2c_dump_msgs_rw()` 的参数。用户可调用该函数，`i2c_transfer()` 内部也会调用它，并启用读内容转储。

长度之前的缩写含义：

| 缩写 | 含义 |
| --- | --- |
| `W` | Write，写消息 |
| `R` | Read，读消息 |
| `Sr` | Restart，重复起始标志 |
| `P` | Stop，停止标志 |

本例先写入 `0x00`，表示要从 I2C 目标读取的寄存器地址，然后显示接收长度与读到的八个字节 `43 42 41 00 00 00 00 00`。内容同时以十六进制和 **美国信息交换标准码（American Standard Code for Information Interchange，ASCII）**字符表示，因此前三字节显示为 `CBA`。

### 1.3.1\_过滤转储内容

默认记录全部控制器与全部目标的 I2C 通信，可能使日志充满无关设备信息。启用 `CONFIG_I2C_DUMP_MESSAGES_ALLOWLIST` 可建立**允许列表（Allowlist）**，只记录选定目标。

列表由设备树配置，例如：

```devicetree
/ {
    i2c {
        display0: some-display@a {
            ...
        };
        sensor3: some-sensor@b {
            ...
        };
    };

    i2c-dump-allowlist {
        compatible = "zephyr,i2c-dump-allowlist";
        devices = <&display0>, <&sensor3>;
    };
};
```

过滤节点通过 `compatible = "zephyr,i2c-dump-allowlist"` 识别，`devices` 属性通过 **节点引用句柄（Phandle）**选择 I2C 总线上的设备。本例只显示 `display0` 与 `sensor3` 的通信。

> 译注：设备树中的 `...` 表示省略的板级属性；这是结构示意，不是可直接编译的完整覆盖文件。Phandle 用于引用另一个设备树节点，不是应用运行时的 C 指针。
