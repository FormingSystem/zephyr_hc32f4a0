# 第1章\_实时输入输出

原文：[Real Time I/O (RTIO)](https://docs.zephyrproject.org/latest/services/rtio/index.html)。读取日期：2026-10-12，`latest`。

**实时输入输出（Real Time I/O，RTIO）**为事件驱动的异步操作链提供框架。本页介绍它的**应用程序编程接口（Application Programming Interface，API）**、队列、执行器、输入输出设备及外设常见用法。

RTIO 的操作方式和接口借鉴 Linux `io_uring`，因为这种模型与硬件传输队列、**直接存储器访问（Direct Memory Access，DMA）**传输描述符列表较为契合。

官方队列关系图如下，图中提交侧描述要做的操作，完成侧返回结果：

![RTIO提交与完成队列关系，官方原图](images/rings.png)

## 1.1\_为什么需要异步操作描述

应用若要组织复杂的 DMA 或中断驱动操作，往往需要直接理解硬件。DMA 接口本身不了解其他 Zephyr 设备及它们之间的关系，导致音频、视频或传感器流处理依赖具体硬件知识，或者迫使上层了解本应由驱动处理的细节。

为了支持异步操作，尤其 DMA，需要描述“做什么”，而不只是由应用不断调用 C 函数和回调。通道优先级、成组传输等能力，也不只是一张简单描述列表就能充分表达。

底层使用 DMA 或中断，不应直接决定上层调用必须阻塞还是必须不阻塞。

## 1.2\_借鉴io_uring的队列模型

原文介绍 Linux `io_uring` 在内核与用户应用之间共享两个**无锁环形缓冲区（Lock-Free Ring Buffer）**：一个保存可链接、可批量提交的操作，另一个保存完成事件。多个操作可一起提交，原文用提交接口名 `io_uring_submit` 概括该动作；根据等待完成的操作数，提交过程也可以阻塞调用方。

这个模型适合 DMA 和中断驱动传输，因为异步操作序列可以对应硬件中的中断状态机，涉及总线控制器、DMA 控制器等多个硬件单元。

> 译注：这一节说明设计灵感，不表示 RTIO 与 Linux 的结构、系统调用或实现逐项相同，也不是要求在 Zephyr 应用中调用 `io_uring_submit`。

## 1.3\_提交队列与操作链

**提交队列（Submission Queue，SQ）**描述要执行的并发操作链，每个操作由**提交队列项（Submission Queue Entry，SQE）**表示。

以**串行外设接口（Serial Peripheral Interface，SPI）**先写寄存器地址再读取为例，操作序列可能是：

1. 使能片选。
2. 开启时钟。
3. 向 SPI 发送寄存器写入目标寄存器地址。
4. 将 SPI 接收寄存器的数据读入缓冲区。
5. 关闭时钟。
6. 取消片选。

链中任一步失败就应放弃后续操作。部分准备动作可以由设备抽象承担，例如“读或写”隐含设置时钟和片选；事务边界也需要表达。若读取足够大，还可能交给 DMA，此时驱动须了解该设备如何配置 DMA。

RTIO 通过 SQE 的标志连接操作，表明下一个 SQE 必须等待当前项。相同控制器和总线设备的片选、时钟行为，则封装到 **输入输出设备（I/O Device，iodev）**中。

针对同一 iodev 的多个操作会按给出的顺序尽早执行。如果两条链在不同位置需要同一设备，其中一条可能必须等待另一条。

## 1.4\_完成队列

**完成队列（Completion Queue，CQ）**保存**完成队列事件（Completion Queue Event，CQE）**。SQE 完成后，产生的 CQE 进入 CQ。

CQE 的总体顺序不一定等于 SQE 的提交顺序；但同一条 SQE 链会保证所需的执行顺序与失败传递。完成队列也是 `io_uring` 等系统接口已经采用的成熟设计。

> 译注：“并发链之间可能乱序完成”和“单条链内部遵守依赖”是两个不同层次；不能仅按第几个完成事件来猜它对应第几个独立请求。

## 1.5\_执行器与设备各自负责什么

RTIO 的**执行器（Executor）**是低开销的并发输入输出任务调度器。它按提交列表处理请求，并落实标志规定的行为，包括按序链、事务组以及持续产生结果的**多次完成请求（Multi-Shot Request）**。

把 SQE 转换为 CQE 则由实现 iodev 接口的对象负责。它接收提交请求，处理内部队列并产生完成结果；可把每个 iodev 看作独立的事件驱动对象，不断接收输入输出请求。

实现方法由 iodev 作者选择。例如可把整组操作转换成 DMA 描述符，让硬件承担大部分传输工作。

## 1.6\_取消操作并非保证成功

已经排队的操作可以请求取消，但不保证取消成功。若 SQE 尚未开始，调用 [`rtio_sqe_cancel()`](../rtio_core_reference/P001_RTIO公共接口.md#gac01252e55d2848b38c0ed77b71d600a7)可能使它不再运行；原文说明，已经开始运行的 SQE 会忽略取消请求。

> 译注：应用不能把“发出取消请求”当成“硬件已停止或缓冲区已可复用”。应遵守当前接口及设备实现的完成、生命周期规则。

## 1.7\_按需要取得内存池缓冲区

某些读请求事先不知道会产生多少数据，或者多个设备的数据频率不可预测。提前为每个在途请求绑定内存可能浪费空间，因此可以让 iodev 在需要接收时，从关联 RTIO **内存池（Memory Pool）**分配缓冲区。

宏 [`RTIO_DEFINE_WITH_MEMPOOL`](../rtio_core_reference/P001_RTIO公共接口.md#gae4c2a9384a9ae4ed16dff914b1184ca8)可定义含专用内存块池的上下文。下例提交、完成容量均为 4，池含 128 个块，每块 16 字节，按 4 字节对齐。代码中的 `SQ_SIZE`、`CQ_SIZE` 是队列容量宏，`MEM_BLK_COUNT`、`MEM_BLK_SIZE`、`MEM_BLK_ALIGN` 是内存块数量、大小和对齐宏：

```c
#include <zephyr/rtio/rtio.h>

#define SQ_SIZE       4
#define CQ_SIZE       4
#define MEM_BLK_COUNT 128
#define MEM_BLK_SIZE  16
#define MEM_BLK_ALIGN 4

RTIO_DEFINE_WITH_MEMPOOL(rtio_context,
    SQ_SIZE, CQ_SIZE, MEM_BLK_COUNT, MEM_BLK_SIZE, MEM_BLK_ALIGN);
```

### 1.7.1\_准备读请求和接收缓冲区

调用方把接收固定指针和长度的函数 [`rtio_sqe_prep_read()`](../rtio_core_reference/P001_RTIO公共接口.md#ga89c7cc2494e3dda50737f78f1a1376cf)换成函数 [`rtio_sqe_prep_read_with_pool()`](../rtio_core_reference/P001_RTIO公共接口.md#ga15c1f623658d27d300d1a31a6f3d6b9d)。

设备端不再直接从设备提交项结构 `rtio_iodev_sqe` 取缓冲区，而通过函数 [`rtio_sqe_rx_buf()`](../rtio_core_reference/P001_RTIO公共接口.md#gaab6843e2038d00a8354f57d7e2ffcf7e)取得指针与长度，从而兼容固定缓冲区与内存池。原例使用应用给出的长度宏 `MIN_BUF_LEN`、`DESIRED_BUF_LEN`，以及记录错误的日志宏 `LOG_ERR`：

```c
uint8_t *buf;
uint32_t buf_len;
int rc = rtio_sqe_rx_buff(iodev_sqe, MIN_BUF_LEN, DESIRED_BUF_LEN, &buf, &buf_len);

if (rc != 0) {
  LOG_ERR("Failed to get buffer of at least %u bytes", MIN_BUF_LEN);
  return;
}
```

> 译注：代码把函数名写成 `rtio_sqe_rx_buff`，比正文与当前头文件多一个 `f`，实际应核对并使用 `rtio_sqe_rx_buf`。`MIN_BUF_LEN`、`DESIRED_BUF_LEN` 是应用需要提供的最小和期望长度，`iodev_sqe` 是当前设备提交项；此片段不能脱离设备实现直接执行。非零返回值表示没有取得所需缓冲区。

### 1.7.2\_消费结果与释放缓冲区

消费者通过函数 [`rtio_cqe_get_mempool_buffer()`](../rtio_core_reference/P001_RTIO公共接口.md#gaedbf9386a36ed99baa290ef6c318ded1)从完成事件取得分配的缓冲区：

```c
uint8_t *buf;
uint32_t buf_len;
int rc = rtio_cqe_get_mempool_buffer(&rtio_context, &cqe, &buf, &buf_len);

if (rc != 0) {
  LOG_ERR("Failed to get mempool buffer");
  return rc;
}

/* Release the cqe events (note that the buffer is not released yet */
rtio_cqe_release_all(&rtio_context);

/* Do something with the memory */

/* Release the mempool buffer */
rtio_release_buffer(&rtio_context, buf);
```

> 译注：原片段的释放接口与当前仓库头文件不一致：`rtio_release_buffer` 需要上下文、缓冲区、长度三个参数，应包含 `buf_len`；当前提供逐项释放函数 `rtio_cqe_release`，未找到片段中的 `rtio_cqe_release_all`。应按实际取得的 CQE 对象及版本 API 释放，不能机械复制旧调用。释放完成队列项与归还数据缓冲区是两个动作，数据处理结束前不能提前归还缓冲区。原块完整保留作为原文对照，本次未编译运行。

## 1.8\_适合哪些应用

RTIO 适合并发或批量输入输出。驱动可以把同一 SPI 外设的多个请求转换成硬件命令队列或 DMA 描述符，更充分使用硬件能力。

每个 RTIO 上下文和 iodev 都有一定成本，应与“每个并发操作一个线程”或“每个外设自建队列和线程”比较；原文认为 RTIO 的成本更低。

## 1.9\_总线支持与工作队列回退

检查总线驱动接口是否实现 `iodev_submit`，可判断是否原生支持 RTIO。

**内部集成电路总线（Inter-Integrated Circuit，I2C）**提供默认回退实现。没有原生提交实现的驱动，可以借助 `i2c_iodev_submit_fallback` 将阻塞式 I2C 事务交给工作项执行。工作项池大小由 Kconfig 配置项 [`CONFIG_RTIO_WORKQ_POOL_ITEMS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_RTIO_WORKQ_POOL_ITEMS)控制。

> 译注：原文先泛称“总线”，随后给出的是 I2C 专用回退函数。不能据此推断所有总线均使用这个函数；回退也不代表底层事务已经变成原生 DMA 异步实现。
