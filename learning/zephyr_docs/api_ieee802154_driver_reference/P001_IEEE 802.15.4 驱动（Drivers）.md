# 第1章\_IEEE 802.15.4 驱动（Drivers）

原文：[官方页面](https://docs.zephyrproject.org/latest/doxygen/html/group__ieee802154__driver.html)。读取日期：2026-10-17；来源摘要见[来源记录](../SOURCES.md)。

IEEE 802.15.4 驱动 API

<a id="details"></a>

IEEE 802.15.4 驱动 API。自 1.0 起提供，版本 0.8.0。本 API 为原生 IEEE 802.15.4 二层（L2）协议栈和 OpenThread 协议栈提供厂商专用硬件、固件的统一表示。应用开发者不应直接调用本 API；它仅面向驱动维护者。IEEE 802.15.4 驱动 API 分为两部分：所有驱动都要实现的基础驱动 API（主要位于物理层，PHY），以及若干可选的媒体访问控制层（MAC）扩展点，用于把 MAC 层对性能或时序要求严格的处理卸载到驱动硬件或固件（“硬”MAC，hard MAC）。实现基础驱动 API 可确保与原生 L2 协议栈集成，并为 OpenThread 提供基础支持。视硬件而定，可能需要利用厂商专用硬件或固件的卸载功能，才能完全符合 Thread 协议或 IEEE 802.15.4 子协议的要求，例如足够快地发送确认（ACK）包，或者在时隙信道跳频（TSCH）及协调采样监听（CSL）子协议中精确定时发送／接收（TX/RX）。是否实现 MAC 层卸载扩展点，由各驱动维护者决定。上层在可行时应当（SHOULD）提供“软”MAC（soft MAC）回退实现。注意：本文所有章节、表格和图编号均引用 IEEE 802.15.4-2020 标准。

## 1.4\_IEEE 802.15.4-2020 第 15 节：HRP UWB 物理层（PHY）

对于 HRP UWB，符号周期（Symbol Period）由前导码符号周期（Preamble Symbol Period，T_psym）推导；参见第 11.3 节表 11-1 和第 15.2.5 节表 15-4，IEEE 802.15.4z 第 15.1 节也确认了这一点。不能仅依据信道页（Channel Page）和信道（Channel）在这些周期之间进行选择，还必须知道平均脉冲重复频率（Mean Pulse Repetition Frequency）。参见 MCPS-DATA.request 原语的 UwbPrf 参数，即第 8.3.2 节表 8-88，以及 HRP-ERDEV 长度为 91 的码的前导码参数，即 IEEE 802.15.4z 第 15.2.6.2 节表 15-7b。

**枚举值（Enumerators）**

**`IEEE802154_CONFIG_AUTO_ACK_FPB`**

指示驱动应如何设置针对数据请求（Data Request）的 ACK 响应中的帧待处理位（Frame Pending Bit）。启用时，驱动应根据 `IEEE802154_CONFIG_ACK_FPB` 配置提供的信息以及指定的 FPB 地址匹配模式决定是否置位；否则应将此位置为 1（参见第 6.7.3 节）。注意：需要 `IEEE802154_HW_TX_RX_ACK` 能力，可在接口的任意运行状态下使用。

指示是否针对指定地址设置 ACK 的帧待处理位（Frame Pending Bit）。未提供地址（即传入 `NULL` 指针）而禁用该位时，应对所有已启用地址禁用它。注意：需要 `IEEE802154_HW_TX_RX_ACK` 能力，可在接口的任意运行状态下使用。

**`IEEE802154_CONFIG_PAN_COORDINATOR`**

指示设备是否为个域网协调器（PAN Coordinator）。这会影响数据包过滤。注意：可在接口的任意运行状态下使用。

**`IEEE802154_CONFIG_PROMISCUOUS`**

启用／禁用混杂模式（Promiscuous Mode）。注意：可在接口的任意运行状态下使用。

**`IEEE802154_CONFIG_EVENT_HANDLER`**

指定新的 IEEE 802.15.4 驱动事件处理函数。将处理函数指定为 `NULL` 会禁用事件通知。注意：可在接口的任意运行状态下使用。

**`IEEE802154_CONFIG_MAC_KEYS`**

对支持发送安全卸载（Transmit Security Offloading）的驱动，更新 MAC 密钥、密钥索引及每个密钥的帧计数器；参见第 9.5 节及表 9-9、表 9-10。如果帧计数器（在每密钥帧计数器选项为 `true` 时）未严格大于与同一密钥关联的当前帧计数器，则必须拒绝（SHALL NOT）此密钥配置；参见第 8.2.2 节、第 9.2.4 节 g/h) 及第 9.4.3 节。注意：需要 `IEEE802154_HW_TX_SEC` 能力，可在接口的任意运行状态下使用。

**`IEEE802154_CONFIG_FRAME_COUNTER`**

对支持发送安全卸载的驱动，设置与接口关联的当前 MAC 帧计数器值；参见第 9.5 节、表 9-8 中的 `secFrameCounter`。警告：如果帧计数器未严格大于与接口关联的当前值，则不得（MUST NOT）接受该值；参见第 8.2.2 节、第 9.2.4 节 g/h) 及第 9.4.3 节。否则，帧计数器提供的重放保护（Replay Protection）可能遭到破坏。如果配置的帧计数器不符合此要求，驱动必须（SHALL）返回 `-EINVAL`。注意：需要 `IEEE802154_HW_TX_SEC` 能力，可在接口的任意运行状态下使用。

**`IEEE802154_CONFIG_FRAME_COUNTER_IF_LARGER`**

仅当提供的值大于当前值时，才设置当前 MAC 帧计数器。注意：需要 `IEEE802154_HW_TX_SEC` 能力，可在接口的任意运行状态下使用。警告：此配置选项与 `IEEE802154_CONFIG_FRAME_COUNTER` 重复，不符合 #61227 规定的要求，因此将来会被弃用。

**`IEEE802154_CONFIG_RX_SLOT`**

设置或取消无线接收窗口（RX Slot，接收时隙）。它可用于任何预定接收，例如 Zigbee GP 设备、CSL、TSCH 等。接收时隙的 `start` 和 `duration` 参数以网络子系统的本地时钟为基准。如果 `start` 为 -1，则必须（SHALL）立即取消之前配置的任何接收时隙。如果 `start` 是过去的任意时刻（包括 0），或者 `duration` 为零，则接收器必须持续关闭，直到删除时隙或将其重新配置为未来的起始时刻。如果配置时先前时隙仍处于已调度状态，则必须取消先前时隙，改为调度新时隙。驱动处于“DOWN”状态时可以（MAY）编程设置接收时隙。如果调用 `start()` 时已配置任意过去或未来的时隙，则必须将接口置为“UP”状态，但不得启动接收器。驱动必须负责在时隙前后自主、异步且自动地启动／停止接收器。除非其他已编程事件要求驱动不能挂起，否则必须在时隙即将开始前恢复供电，并在时隙结束后再次挂起。驱动必须在时隙之前切换至编程指定的信道，并在时隙之后切回通过 `set_channel()` 设置的信道。如果到达起始时刻时驱动接口处于“DOWN”状态，则不得执行该时隙，接收器必须保持关闭。如果配置时驱动处于“UP”状态，必须立即关闭接收器，并且可以异步地进入尽可能低功耗的模式，直到时隙开始。如果删除时隙时驱动处于“UP”状态，则必须立即启用接收器；在这种情况下，`configure()` 返回之前，接收器必须（MUST）已准备好接收数据包。这意味着设置接收时隙会隐式地将 MAC PIB 属性 `macRxOnWhenIdle` 设为 `false`，而删除时隙会隐式地将其设为 `true`（参见第 8.4.3.1 节、表 8-94）。注意：需要 `IEEE802154_HW_RXTIME` 能力，可在接口的任意运行状态下使用。Thread 1.2 的协调采样监听（Coordinated Sampled Listening）功能需要此能力，参见 Thread 规范 1.2.0 第 3.2.6.3 章。

**`IEEE802154_CONFIG_CSL_PERIOD`**

启用或禁用设备作为协调采样监听（CSL）接收器的功能，并配置其 CSL 周期。

以 10 个符号周期为单位配置 CSL 周期。值大于零时，如果驱动支持 CSL，则启用 CSL，设备开始作为 CSL 接收器工作。设为零会禁用设备的 CSL。如果驱动不支持 CSL，配置调用必须（SHALL）返回 `-ENOTSUP`。

参见第 7.4.2.3 节以及第 8.4.3.6 节、表 8-104 中的 `macCslPeriod`。

注意：标准把 CSL 接收器称为“CSL 协调器”（CSL Coordinator，即“协调 CSL 协议时序”，参见第 6.12.2.2 节），容易引起混淆。通常，CSL 协调器并非同时也是 IEEE 802.15.4 全功能设备（FFD）协调器或 PAN 协调器，而是简单的精简功能设备（RFD）终端；可对照第 5.1、5.3、5.5 和 6.1 节概述的设备角色。为避免混淆，本文倾向于把 CSL 协调器（通常为 RFD 终端）称为“CSL 接收器”（CSL Receiver），把 CSL 对端设备（通常为 FFD 协调器或 PAN 协调器）称为“CSL 发送器”（CSL Transmitter）。另请注意，目前不支持第 6.12.2.4.4 节规定的、利用 CSL 唤醒帧进行的非同步发送。

为了将 CSL 接收器定时卸载给驱动，上层必须（SHALL）按如下方式组合多个配置选项：

1. 使用适当预填充的 CSL 信息元素（IE）调用一次 `IEEE802154_CONFIG_ENH_ACK_HEADER_IE`，CSL 相位可设为任意值或保持未初始化。驱动必须（SHALL）在运行时即时插入 CSL 相位，如下面步骤 2 所述。添加短地址和扩展地址，可告知驱动必须向哪个特定 CSL 接收器插入 CSL IE。若不提供地址，则一旦启用 CSL，就会在所有增强型 ACK 帧中插入 CSL IE。必须先完成此配置，之后才能通过设置大于零的 CSL 周期启用 CSL。

配置 `IEEE802154_CONFIG_EXPECTED_RX_TIME`，紧接着配置 `IEEE802154_CONFIG_CSL_PERIOD`。为防止竞争条件（Race Condition），上层必须（SHALL）确保在这两次调用期间以及两次调用之间接收器均未启用（例如利用之前配置的接收时隙），同时也不得发送帧。

预期接收时间必须（SHALL）指向过去或未来任意一个 CSL 信道采样窗口中，理想定时接收帧的帧起始定界符（SFD）结束时刻。也就是说，该帧的“SFD 结束”恰好在该 CSL 信道采样窗口内本地预测的时刻到达。

驱动必须（SHALL）根据给定的预期接收时间，按如下方式推导 CSL 锚点（Anchor Point）和 CSL 相位：

```text
cslAnchorPointNs = last expected RX time
                   + PHY-specific PHR duration in ns

startOfMhrNs = start of MHR of the frame containing the
               CSL IE relative to the local network clock

cslPhase = (startOfMhrNs - cslAnchorPointNs)
           / (10 * PHY specific symbol period in ns)
           % cslPeriod
```

驱动必须（SHALL）在步骤 1 配置的信息元素（IE）中设置 CSL 相位；若目标地址符合该 IE 的地址过滤器，则在发送增强型 ACK 帧时即时插入此 IE。

定期使用 `IEEE802154_CONFIG_RX_SLOT`，在每个 CSL 信道采样窗口开始前足够早地调度该窗口。窗口大小必须（SHALL）按照标准要求，考虑相对于 CSL 发送器的时钟漂移和调度不确定性，从而保证合法接收帧至少整个同步头（SHR）都能落在采样窗口内。

为此，最后配置的预期接收时间加上整数个 CSL 周期后，必须（SHALL）指向接收时隙内的一个固定偏移位置（不一定是中心）：

```text
expectedRxTimeNs_N = last expected RX time
    + N * (cslPeriod * 10 * PHY-specific symbol period in ns)

expectedRxTimeNs_N - rxSlot_N.start == const for all N
```

配置的 CSL 周期大于零时，驱动应当（SHOULD）据此验证每个接收时隙中的预期接收时间偏移。如果发现偏移随时隙变化，驱动应当记录差异，但仍必须（SHALL）接受并调度该接收时隙，返回零表示成功，以容忍上层轻微的实现或舍入误差。

配置并启动 CSL 接收器：

```text
ENH_ACK_HEADER_IE
   |
   | EXPECTED_RX_TIME (end of SFD of a perfectly timed RX frame
   |    |              in any past or future channel sample)
   |    |
   |    | CSL_PERIOD (>0)            RX_SLOT
   |    |    |                          |
   v    v    v                          v
-----------------------------------------------[-CSL channel sample ]----+
                                    ^                                    |
                                    |                                    |
                                    +--------------------- loop ---------+
```

在接收器上禁用 CSL：

```text
CSL_PERIOD (=0)
   |
```

**`IEEE802154_CONFIG_EXPECTED_RX_TIME`**

配置预期接收帧到达的时间点。

配置相对于网络子系统本地时钟、分辨率为纳秒的时间点：假设本地与远端网络时钟完全同步，且天线之间的距离为零，接收帧的 SFD 结束位置预期将在这一时刻到达本地天线。该位置也就是 SHR 结束、PHR 开始的位置；对于具有 RDEV 或 ERDEV 能力的 PHY，则为测距标记（RMARKER）。

此参数可以（MAY）用于将对时序敏感的时分多址（TDMA）协议（如 TSCH、包括 DSME 在内的信标使能 PAN）、低能耗协议（如 CSL、RIT）或测距协议（到达时间差，TDoA）的部分处理卸载给驱动。在这些协议中，介质访问受到严格控制，因此能够在明确界定的时间窗口内预测帧的到达时间。本功能通常与 `IEEE802154_CONFIG_RX_SLOT` 配合使用，但这并非强制要求。

“预期接收时间”（Expected RX Time）的含义可以（MAY）根据协议上下文略有不同：

CSL 相位（即距下一次预期 CSL 发送的时间）或锚点时间（即任意“CSL 相位为零”的时刻），必须（SHALL）通过将 PHY 头部时长加到预期接收时间上推导，从而计算 CSL 协议要求的“MAC 头部起始”（Start of MHR，即“MAC 的第一个符号”，参见第 6.12.2.1 节）；可对照 `IEEE802154_CONFIG_CSL_PERIOD`。

在时隙信道跳频（TSCH）中，预期接收时间可以（MAY）设为 `macTsRxOffset + macTsRxWait / 2`。随后必须（SHALL）以预期接收时间减去实际到达时间戳来计算时间校正量；参见第 6.5.4.3 节。

在测距应用中，可以（MAY）在驱动内部，将实际测距标记（RMARKER）时间戳与假设已同步的测距帧发送时刻进行比较，以计算到达时间差（TDOA）；参见 IEEE 802.15.4z。

对于周期性协议（例如 CSL 信道采样、单个 PAN 的周期性信标、周期性测距“blink”信号），可以提供过去或未来任意时刻的单个时间戳，再通过加减接收周期的整数倍推导其他预期时间戳。可参见本 API 中的 CSL 文档。

此外，驱动可以（MAY）利用此参数，通过推导与同一分布式网络时钟的远端表示相关的同步时刻，校准该时钟的本地表示，类似精确时间协议（PTP）的做法。

注意：可在接口的任意运行状态下使用。Thread 1.2 的协调采样监听（Coordinated Sampled Listening）功能需要此能力，参见 Thread 规范 1.2.0 第 3.2.6.3 章。

**`IEEE802154_CONFIG_ENH_ACK_HEADER_IE`**

添加一个头部信息元素（Header IE）：当给定的目标地址过滤器匹配时，将其插入驱动生成的增强型 ACK 帧。

实现 `IEEE802154_HW_RX_TX_ACK` 能力的驱动会自主生成 ACK 帧。设置此配置后，驱动需在生成增强型 ACK 帧时，根据标准的适用条件插入给定的预配置头部 IE。其他所有帧类型的信息元素必须（SHALL）由 L2 提供。

在下列情况下，驱动应返回 `-ENOTSUP`：

- 不支持 `IEEE802154_HW_RX_TX_ACK`。
- 不支持头部 IE 插入。
- 无法即时插入给定 IE 元素 ID 所要求的运行时字段（参见下方列表）。

下列增强型 ACK 头部信息元素（括号中为元素 ID）需要即时插入定时信息，因此驱动必须拒绝它们，或者明确支持并解析它们：

- CSL 信息元素（CSL IE，`0x1a`）。
- 会合时间信息元素（Rendezvous Time IE，`0x1d`）。
- 时间校正信息元素（Time Correction IE，`0x1e`）。

接受此配置选项的驱动必须（SHALL）针对每个待发送的增强型 ACK 帧检查已配置的 IE 列表，根据元素 ID 选择适用于所接收帧的 IE，即时插入所需运行时信息，并将选中的 IE 加入增强型 ACK 帧的 MAC 头部。

支持增强型 ACK 头部 IE 插入的驱动，必须（SHALL）按照标准要求自主插入头部终止信息元素（Header Termination IE）。

L2 可以（MAY）提供目标短地址和扩展地址，用于过滤哪些设备的帧应包含给定 IE。将短地址设为广播地址、扩展地址设为 `NULL` 时，会在所有 ACK 帧中插入该 IE，但若针对某个目标设备还存在更具体的过滤器，则优先使用该过滤器；前者属于回退配置（Fallback Configuration）。L2 必须（SHALL）确保两个地址字段要么都设为有效设备地址，要么都不指定。

此配置类型可使用不同的元素 ID 和／或地址调用多次。驱动必须（SHALL）保存所有已配置的 IE／地址组合；若无法保存更多配置，则返回 `-ENOMEM`。

配置头部 IE 时，若元素 ID 和地址过滤器已存在，必须（SHALL）覆盖先前配置。这意味着不支持同一头部 IE／地址组合重复出现。

配置已有的元素 ID／地址过滤器组合时，若将头部 IE 的长度字段设为零，必须（SHALL）删除该配置。未提供地址时，必须删除回退配置。

为某个地址过滤器配置头部 IE 时，若将头部 IE 指针设为 `NULL`，必须（SHALL）删除该地址过滤器的全部头部 IE。未提供地址时，必须删除所有头部 IE 配置，包括但不限于回退配置。

若要删除的配置此前并不存在，则必须（SHALL）忽略该调用。只要长度字段为零，驱动就不得（MUST NOT）访问内容字段。

L2 必须（SHALL）通过合并地址过滤器、删除不再需要的配置，尽量减少驱动保存 IE 配置所需的空间。

注意：需要 `IEEE802154_HW_RX_TX_ACK` 能力，可在接口的任意运行状态下使用。目前仅支持头部信息元素（Header IE），将来可能变化。Thread 1.2 的协调采样监听（Coordinated Sampled Listening）功能需要此能力，参见 Thread 规范 1.2.0 第 3.2.6.3 章。Thread 1.2 的链路度量（Link Metrics）功能也需要此能力，参见该规范第 4.11.3.3 章。

### `ieee802154_phy_channel_page`

```c
enum ieee802154_phy_channel_page
```

```c
#include <zephyr/net/ieee802154_radio.h>
```

PHY 信道页（Channel Pages），参见第 10.1.3 节。

设备驱动必须至少支持一种 IEEE 802.15.4 PHY 所要求的强制信道页、频段和信道。

信道页和编号的分配规则经过了标准多个版本的演变，文档说明并不十分清晰。因此，下面补充信道页及信道编号的一些特殊之处：

- 2006 年版标准定义了只读的 PHY PIB 属性 `phyChannelsSupported`，以位图（Bitmap）表示信道页／信道编号组合。后来信道数量增加，超出了位图能表示的范围，因此后续版本删除了此属性。这就是这里决定采用信道页与信道范围的组合来表示受支持信道的原因。
- 2020 年版标准明确规定了 13 个信道页，但原则上最多可以支持 32 页。2006 年版标准对此有明确的强制要求。后续标准则通过字段规范隐含此要求，例如 MAC PIB 属性 `macChannelPage`（第 8.4.3.4 节、表 8-100），或 SRM 协议使用的信道页字段（参见第 8.2.26.5 节）。
- 幅移键控（ASK）PHY（信道页 1）在 2015 年版标准中被弃用。2020 年版标准对信道页 1 是同时消失，还是现在应解释为 O-QPSK，表述有些含糊（参见第 10.1.3.3 节）。Zephyr 通过弃用信道页 1 来消除这一歧义。
- 标准未明确为某些 PHY 指定信道页，即 GFSK、RS-GFSK、CMB 和 TASK PHY。这些 PHY 都比较新；在没有驱动需要实现它们之前，暂不纳入本列表。

### `ieee802154_handle_ack()`

```c
enum net_verdict ieee802154_handle_ack ( struct net_if * iface, struct net_pkt * pkt )
```

声明属性：`extern`。

```c
#include <zephyr/net/ieee802154_radio.h>
```

IEEE 802.15.4 驱动调用二层（L2）的确认处理回调（ACK Handling Callback）；驱动收到 ACK 数据包时必须调用它。

IEEE 802.15.4 标准规定了在 L2（MAC）层处理 ACK 的通用流程。因此，L2 协议栈必须为此回调提供快速、可复用的通用实现，供驱动收到 ACK 数据包时调用。

注意：本函数属于 Zephyr 802.15.4 协议栈中从驱动到 L2 的“控制反转”（Inversion of Control）适配 API，所有 IEEE 802.15.4 L2 协议栈都必须实现它。

**参数（Parameters）**

| 名称／方向 | 说明 |
| --- | --- |
| `iface` | 指向接收到数据包的网络接口的有效指针。 |
| `pkt` | 指向待检查数据包的有效指针。 |

**返回（Returns）**：返回值：如果 L2 处理该 ACK 数据包，则返回 `NET_OK`；否则返回 `NET_CONTINUE` 或 `NET_DROP`。

**警告（Warning）**：警告：与网络协议栈中其他返回 `net_verdict` 的函数不同，即使本函数返回 `NET_OK`，也不会解除该数据包的引用（Unref）。
