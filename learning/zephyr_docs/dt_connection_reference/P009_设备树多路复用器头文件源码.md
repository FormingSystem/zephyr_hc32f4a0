## 9.2\_可见注释译文（Comments）

1. 版权：SPDX-FileCopyrightText: 2026 NXP。Apache-2.0许可证原文保留。

2. 为DT_FOREACH_PHA_CELL_BY_IDX_SEP生成一个单元值的辅助宏。

3. 句柄数组属性索引idx处元素的单元数量。

4. mux-controls内部存储标识符的生成宏。

5. mux-states内部存储标识符的生成宏。

6. 前N-1个单元组成寻址部分，索引N-1处的单元是状态。cells[]只保存寻址部分，使内嵌mux_control与从mux-controls生成的对象具有相同形态。末尾状态按位置，即最后一个参数，写入mux_state.state，而不按名称提取；因此后端可以按硬件需要将末尾单元命名为state、input、source等。GET_ARGS_FIRST_N(N, x0, x1, ..., xK)保留前N个实参，与NUM_VA_ARGS_LESS_1(...)组合后取得除最后一项之外的全部实参，恰好得到mux-states描述符的寻址部分。GET_ARG_N的索引从1开始，因此对K个单元调用GET_ARG_N(K, ...)会取得最后一项，即状态值。只有一个单元的mux-states仅有末尾状态，没有寻址部分，cells数组在逻辑上为空（len == 0）；底层占位存储差异见译注。

7. 结束头文件包含保护ZEPHYR_INCLUDE_DEVICETREE_MUX_H_。

## 9.4\_源码跟踪译注

> 译注——三种指针：DEV_GET系列取得控制器struct device指针，CONTROL_GET取得预先定义的struct mux_control地址，STATE_GET取得预先定义的struct mux_state地址。配置对象不包含同义的设备指针；应用须把匹配同一控制器的设备与配置配对传给mux_control_set或mux_state_apply，并自行检查设备就绪。GET不会自动创建对象或切换硬件通路。

> 译注——先定义再取地址：SPEC_DEFINE_BY_IDX／BY_NAME在drivers/mux.h中生成static const存储，应在文件作用域对同一消费节点及索引只定义一次；随后GET引用生成的标识符。SPEC_DEFINE_ALL对mux-states每项调用定义宏，因此也需要完整结构定义所在的drivers/mux.h；不能在同一翻译单元再为相同条目重复定义。开发者自定义的entries数组形状由消费方决定。

> 译注——寻址单元与状态：mux-controls的单元全部属于寻址信息；mux-states前N-1个单元属于寻址，最后一个单元按位置写入state，不强制名为state。只有一个单元时逻辑寻址长度为0；当前drivers/mux.h实际以{0}保留一个底层占位元素，因此源码注释中的“数组为空”应理解为len为0，并不代表零字节物理存储。状态描述符仍须至少有末尾状态单元。

> 译注——原例注释：channel 5／channel 7分别为通道5／通道7；entry 0表示通道5、状态2，entry 1表示通道7、状态3。s0->control->cells[0] == 5与s0->state == 2分别说明寻址首单元和默认状态。&mux0／&mux1注释表示所引用控制器，C代码实际取得Zephyr设备对象地址，不是对DTS标签直接做C取地址。

> 译注——名称与运行边界：mux-control-names和mux-state-names分别为两种属性条目提供名称，BY_NAME先换算条目索引再取对象。实例版本的inst指消费节点实例。带...和vendor,demux的片段是示意，不代表所需驱动、绑定和对象已存在；只有后续运行时调用才应用状态。

> 译注——版本边界：本次四份设备树头文件、MUX驱动头文件、gen_defines.py和edtlib.py登记摘要；四份源码浏览页的非注释代码与对应头文件一致。滚动main与本仓库参照基线不自动视为同版本；本批未编译示例、构建固件、采样、配置MUX或执行硬件实验。
