# 第10章\_二进制描述符

原文：[官方页面](https://docs.zephyrproject.org/latest/services/binary_descriptors/index.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 10.1\_概述

二进制描述符（Binary Descriptors）是保存可执行二进制文件信息的常量数据对象。与普通常量不同，它们链接到二进制中已知的偏移（Offset），因此同一设备上的另一个映像（Image）或主机工具也能访问。适合作为描述符的信息包括内核版本、应用版本、构建时间、编译器版本、环境变量以及编译主机名称等。

原文把创建宏概称为 `DEFINE_BINDESC_*`，例如：

```c
#include <zephyr/bindesc.h>

BINDESC_STR_DEFINE(my_string, 2, "Hello world!"); // Unique ID is 2
```

代码注释译文：唯一标识（Unique ID）为 `2`。随后可这样访问 `my_string`：

```c
printk("my_string: %s\n", BINDESC_GET_STR(my_string));
```

也可通过 `west bindesc` 读取：

```console
$ west bindesc custom_search STR 2 build/zephyr/zephyr.bin
"Hello world!"
```

译注：实际宏名如代码所示，为 `BINDESC_STR_DEFINE()` 等 `BINDESC_*_DEFINE` 形式；原文开头的 `DEFINE_BINDESC_*` 不是当前头文件提供的宏族名称。上述 `west` 命令在主机的 Zephyr 源码根目录执行，前提是目标映像已生成；输出字符串是从文件读取，不必运行目标固件。

## 10.2\_内部格式

二进制描述符由标签—长度—值（Tag, Length, Value，TLV）头部实现，并链接到映像内已知偏移。偏移可因架构而异，但通常尽量靠近映像起始位置。

对于必须以向量表（Vector Table）开头的架构，例如 ARM，描述符位于向量表之后；复位向量（Reset Vector）指向描述符后面的代码段（Text Section）起点。对于映像必须以可执行代码开头的架构，例如 x86，会在开头注入跳转指令，跳过紧随其后的描述符。

每个标签是 16 位无符号整数：最高半字节（Nibble，即 4 位）表示类型，目前为无符号整数、字符串或字节序列；剩余位表示 ID。每个描述符的 ID 应全局唯一。例如应用版本字符串的 ID 是 `0x800`，字符串类型为 `0x1`，合成标签为 `0x1800`。长度字段也是 16 位数字，表示数据的字节数；数据字段存放实际描述符值。

所有描述符数值，包括魔数（Magic）、标签和无符号整数，均按 SoC 本机字节序（Native Endianness）存放。`west bindesc` 默认按小端序（Little Endian）解释；映像来自大端序（Big Endian）SoC 时，应传入相应选项。

描述符头以魔数 `0xb9863e5a7ea46046` 开始，后接 TLV 项，并以 `DESCRIPTORS_END`（`0xffff`）标签结束。标签始终按 32 位对齐；上一项的值长度未对齐时，以零填充（Padding）保证下一标签对齐。

前面的字符串示例在小端 SoC 内存中呈现如下：

```text
 46 60 a4 7e 5a 3e 86 b9 02 10  0d 00  48 65 6c 6c 6f 20 77 6f 72 6c 64 21 00 00 00 00 ff ff 00 00
|         magic         | tag |length| H  e  l  l  o     w  o  r  l  d  !    |   pad  |    end    |
```

图中文字依次为魔数、标签、长度、字符串值、填充和结束项。译注：字符串长度 `0x000d` 包括末尾空字符；它后面的3个零字节用于对齐。32位对齐意味着4字节边界，不是每项必须长32字节。主机工具的大端参数为 `-b`／`--big-endian`，应按具体子命令帮助使用。

## 10.3\_用法与标准标签

描述符始终用 `BINDESC_*_DEFINE` 宏创建。任意字符串或整数都可作为值，并指定 ID；但建议遵循 `include/zephyr/bindesc.h` 中的标准标签（Standard Tags），这样有三个好处：

- `west bindesc` 能识别描述符含义，输出有意义的标签名。
- 不同来源的应用可以保持一致。
- 描述符生成实现可以贡献到上游，见下一节的标准描述符。

用标准标签定义描述符时，直接使用 `bindesc.h` 提供的标识：

```c
#include <zephyr/bindesc.h>

BINDESC_STR_DEFINE(app_version, BINDESC_ID_APP_VERSION_STRING, "1.2.3");
```

## 10.4\_标准描述符

构建时间、内核版本、主机信息等描述符较容易按统一方式实现，因此可由 Zephyr 上游提供，再通过 Kconfig 启用，无需每位用户重新实现。例如，要加入构建日期和时间字符串，启用：

```kconfig
# Enable binary descriptors
CONFIG_BINDESC=y

# Enable definition of binary descriptors
CONFIG_BINDESC_DEFINE=y

# Enable default build time binary descriptors
CONFIG_BINDESC_DEFINE_BUILD_TIME=y
CONFIG_BINDESC_BUILD_DATE_TIME_STRING=y
```

配置注释依次表示：启用二进制描述符、启用描述符定义、启用默认构建时间描述符；最后一项选择日期与时间字符串。

标准描述符分配在 `0x800-0xfff`，为用户保留 `0x000-0x7ff`，以避免 ID 冲突。详情见相应 Kconfig 符号帮助。按约定，描述符名称是去掉 `CONFIG_BINDESC_` 前缀后的 Kconfig 名称，再转成小写。例如 `CONFIG_BINDESC_KERNEL_VERSION_STRING` 生成的描述符可用 `BINDESC_GET_STR(kernel_version_string)` 访问。

## 10.5\_读取描述符

应用也可以读取并解析描述符，无论是自身映像还是另一个映像。提供三种后端（Backend）：

| 后端 | 读取方式及边界 |
| --- | --- |
| RAM | 描述符已被引导加载程序（Bootloader）等复制到RAM时，从所在缓冲区读取 |
| 内存映射闪存（Memory-mapped Flash） | 映像所在闪存可通过程序地址空间访问时，直接读取；RAM占用最少，但不能用于未映射闪存。原文出于安全考虑，不建议用此方式读取引导加载程序的描述符 |
| Flash | 通过闪存API逐项读取到内部缓冲区，并在数据仍位于该缓冲区时交给调用方 |

读取总开关为 [`CONFIG_BINDESC_READ`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_BINDESC_READ)。以上三种后端分别由 [`CONFIG_BINDESC_READ_RAM`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_BINDESC_READ_RAM)、[`CONFIG_BINDESC_READ_MEMORY_MAPPED_FLASH`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_BINDESC_READ_MEMORY_MAPPED_FLASH) 和 [`CONFIG_BINDESC_READ_FLASH`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_BINDESC_READ_FLASH) 启用。

首先初始化描述符句柄（Handle），原文代码如下：

```c
struct bindesc_handle handle;

/* Assume buffer holds a copy of the descriptors */
bindesc_open_ram(&handle, buffer);
```

注释译文：假定 `buffer` 保存描述符的一份副本。

> 译注——当前接口差异：官方原始头文件的签名已为 `int bindesc_open_ram(struct bindesc_handle *handle, const uint8_t *address, size_t max_size);`。原文两参数调用缺少 `max_size`，应提供真实可用缓冲区大小；只有 `buffer` 是当前作用域内实际数组时，`sizeof(buffer)` 才能表示其容量，指针的 `sizeof` 不能代替容量。打开操作返回成功后才能继续查询。

只有 `bindesc_open_*` 需要关心后端；其余 API 与数据位置无关。初始化句柄后，可按原文查询：

```c
char *version;
bindesc_find_str(&handle, BINDESC_ID_KERNEL_VERSION_STRING, &version);
printk("Kernel version: %s\n", version);
```

> 译注——只读结果与返回值：当前 `bindesc_find_str()` 接收 `const char **result`，因此输出变量应为 `const char *version`，并应先检查函数返回值，再打印或使用字符串。Flash后端的返回指针指向内部缓冲区，下次调用描述符API可能使结果失效，应立即使用或复制。原文代码为简化演示省略了这些检查，不能将它直接当作完整错误处理范例。
