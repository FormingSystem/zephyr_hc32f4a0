# 第2章\_资源管理

原文：[官方页面](https://docs.zephyrproject.org/latest/services/resource_management/index.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 2.1\_资源管理

多种场景需要在运行时协调多个客户端（Client）对资源的使用，例如电源轨（Power Rail）、时钟（Clock）、其他外设以及只有开关两种状态的设备电源管理（Binary Device Power Management）。在多线程系统中正确管理一个设备的多个使用者很复杂，尤其是状态转换可能异步完成，因此适合提供共享实现。

Zephyr 为多种协调策略提供管理器（Manager）。这些管理器嵌入服务（Service）内部，由服务使用它们完成具体功能。本页介绍[开关管理器（On-Off Manager）](#on-off-manager)。

## 2.2\_开关管理器

开关管理器允许任意数量的客户端使用一个具有二值状态的服务。典型应用是电源轨、时钟以及二值设备电源管理。

管理器具有以下特征：

- 稳定状态（Stable State）为关闭（Off）、开启（On）和错误（Error）。服务总是从关闭状态开始，也可能正处于向某个状态转换的过程中。
- 核心操作是请求（Request，添加依赖）和释放（Release，移除依赖）。辅助操作包括复位（Reset，清除错误状态）与取消（Cancel，从进行中的转换取回客户端数据）。服务依据发起这些操作的函数调用管理状态。
- 收到第一个客户端请求时，服务从关闭转换为开启。
- 收到最后一个客户端释放时，服务从开启转换为关闭。
- 每个服务的配置提供实施“关闭到开启”“开启到关闭”的函数，还可选择提供“错误到关闭”的函数。线程上下文（Thread Context）和中断上下文（Interrupt Context）都必须能够发起这些转换。
- 请求与复位使用[异步通知（Asynchronous Notifications）](P010_异步通知.md)，以异步方式执行。两种操作均可取消，但取消不影响正在进行的状态转换。
- 服务正在转换为关闭时，开启请求可以排队。成功关闭后，若上下文允许，服务会立即重新开启；启动完成时通知等待的客户端。

请求会进行引用计数（Reference Counting），但不会逐个跟踪。这意味着客户端要自行记录请求是否已被接受，并且只有先前请求已成功完成，才应发起释放。误用 API 可能让仍在活动的客户端失去资源；管理器不保存哪些具体客户端已获准使用服务的记录。

执行转换时的失败会被记录，在管理器复位前禁止继续请求或释放。发现错误时，等待中的请求会收到通知并被取消。

转换操作的完成通知通过[异步通知](P010_异步通知.md)提供。

客户端或其他组件若希望跟踪所有服务状态变化，包括开始关闭和进入错误状态，可以通过 `onoff_monitor_register()` 注册监视器（Monitor），接收状态转换通知。状态变化通知先于与新状态关联的完成通知发出。

**原文注意（Note）**：一个通用 API 可能由多个驱动实现，而常见情况是异步操作；开关客户端结构体（On-Off Client Structure）可能适合作为此类通用 API 的方案。对于能够保证状态转换同步完成、且不依赖调用上下文的驱动，可以使用 [`onoff_sync_service`](P022_同步开关服务结构.md) 及配套 API，代替 [`onoff_manager`](P020_开关管理器结构.md)，只需牺牲少量功能，主要是不支持监视器 API。
