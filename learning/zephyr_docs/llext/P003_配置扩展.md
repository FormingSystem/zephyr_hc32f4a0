## 3.1\_哈佛架构（Harvard Architecture）

本章说明LLEXT子系统可用的Kconfig选项。

[`CONFIG_HARVARD`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HARVARD)表示架构使用分离的指令存储器（Instruction Memory）和数据存储器（Data Memory）。此选项不是由LLEXT子系统定义的Kconfig项，而应由开发板或SoC定义并选择，以通知LLEXT启用哈佛架构支持。开发板或SoC还必须实现[`arch_is_instr_mem()`](https://docs.zephyrproject.org/latest/doxygen/html/group__instr__mem.html#ga61c79df57849b7e914cd33e0de4316a3)。

<a id="heap-size"></a>

## 3.2\_堆大小（Heap Size）

LLEXT需要为扩展相关数据分配堆（Heap）。使用静态堆时，由[`CONFIG_LLEXT_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_SIZE)控制其大小，单位为千字节（Kilobytes）。

在哈佛架构开发板上，LLEXT堆分为指令存储器堆和数据存储器堆，分别由以下选项控制：

| 配置项 | 含义 |
| --- | --- |
| [`CONFIG_LLEXT_INSTR_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_INSTR_HEAP_SIZE) | 指令存储器中LLEXT堆的大小，单位为千字节。 |
| [`CONFIG_LLEXT_DATA_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_DATA_HEAP_SIZE) | 数据存储器中LLEXT堆的大小，单位为千字节。 |

也可以通过[`CONFIG_LLEXT_HEAP_DYNAMIC`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_DYNAMIC)配置动态堆（Dynamic Heap）。有些应用需要将扩展加载到启动时尚不存在、不能静态分配的内存中。启用此选项后，由应用负责分配LLEXT堆，不再静态分配。

应用必须调用[`llext_heap_init()`](P011_扩展管理API.md#ga1fa344ade4911a259e7b8ded51241d13)，指定用作LLEXT堆的缓冲区，否则无法加载LLEXT模块。不再需要LLEXT功能时，应调用[`llext_heap_uninit()`](P011_扩展管理API.md#gab20e01c13bdb344978a0fb9b5bd8531d)，将缓冲区控制权交还应用。

> 注意：启用用户态（User Mode）时，堆必须足够大，以允许按架构要求的对齐方式分配扩展各节（Sections）。

> 注意：哈佛架构上的应用必须调用[`llext_heap_init_harvard()`](P011_扩展管理API.md#gad78c7504f824d86471c2ca94b6e1c82c)。

LLEXT堆默认以[`k_heap`](../heap_reference/P002_内核堆结构.md)作为底层数据结构。对于非元数据部分，即扩展内存区域（Extension Regions），可以在[`CONFIG_LLEXT_HEAP_MANAGEMENT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MANAGEMENT)中选择[`CONFIG_LLEXT_HEAP_MEMBLK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MEMBLK)，改用[`sys_mem_blocks_t`](../memblocks_reference/P001_内存块分配公共接口.md#ga5748df756d2f9aa10fddf2f39bf8a074)。

| 配置项 | 含义 |
| --- | --- |
| [`CONFIG_LLEXT_HEAP_MANAGEMENT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MANAGEMENT) | 选择用于在LLEXT堆中保存扩展区域的内存管理API。此选择不影响LLEXT元数据（Metadata），元数据始终由[`k_heap`](../heap_reference/P002_内核堆结构.md)管理。 |
| [`CONFIG_LLEXT_HEAP_MEMBLK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MEMBLK) | 使用[`sys_mem_blocks_t`](../memblocks_reference/P001_内存块分配公共接口.md#ga5748df756d2f9aa10fddf2f39bf8a074)管理扩展区域。每个区域至少分配一个块，必须谨慎选择块大小，确保区域满足对齐要求。 |

> 注意：[`CONFIG_LLEXT_HEAP_MEMBLK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MEMBLK)不支持[`CONFIG_LLEXT_HEAP_DYNAMIC`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_DYNAMIC)。

此时堆分为两部分，大小由以下选项控制：

| 配置项 | 含义 |
| --- | --- |
| [`CONFIG_LLEXT_EXT_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXT_HEAP_SIZE) | 扩展各节可使用的堆大小，单位为千字节。原文要求其为[`CONFIG_LLEXT_HEAP_MEMBLK_BLOCK_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MEMBLK_BLOCK_SIZE)的倍数。若选择[`CONFIG_HARVARD`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HARVARD)，则由[`CONFIG_LLEXT_INSTR_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_INSTR_HEAP_SIZE)和[`CONFIG_LLEXT_DATA_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_DATA_HEAP_SIZE)替代。 |
| [`CONFIG_LLEXT_METADATA_HEAP_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_METADATA_HEAP_SIZE) | LLEXT元数据可使用的堆大小，单位为千字节。 |

另由[`CONFIG_LLEXT_HEAP_MEMBLK_BLOCK_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MEMBLK_BLOCK_SIZE)控制[`sys_mem_blocks_t`](../memblocks_reference/P001_内存块分配公共接口.md#ga5748df756d2f9aa10fddf2f39bf8a074)堆的块大小，单位为字节（Bytes）。启用内存管理单元（Memory Management Unit，MMU）或内存保护单元（Memory Protection Unit，MPU）时，块大小必须等于`LLEXT_PAGE_SIZE`或为其倍数；同时还必须等于扩展区域所需最大对齐值或为其倍数。如果启用[`CONFIG_MPU_REQUIRES_POWER_OF_TWO_ALIGNMENT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_MPU_REQUIRES_POWER_OF_TWO_ALIGNMENT)且区域很大，可能需要不合理地增大块大小才能满足对齐要求。

> 译注：上面两项大小使用不同单位。核对倍数关系时，应先将堆的千字节容量换算到与块大小相同的字节单位；原选项名称和单位均照原文保留。

<a id="heap-placement"></a>

## 3.3\_堆的放置位置（Heap Placement）

LLEXT堆使用自定义节。非哈佛架构的堆节为`.llext_heap`；若选择[`CONFIG_LLEXT_HEAP_MEMBLK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_HEAP_MEMBLK)，则为`.llext_metadata_heap`和`.llext_ext_heap`。这些节在`include/zephyr/linker/common-noinit.ld`中放在`.noinit`各节附近。如果使用的链接脚本没有包含该文件，就需要手动放置这些非哈佛架构堆节。一种方法是在链接脚本的`.noinit`各节之后包含`snippets-noinit.ld`：

```c
/* Located in generated directory. This file is populated by the
 * zephyr_linker_sources() CMake function.
 */
#include <snippets-noinit.ld>
```

代码注释说明：文件位于生成目录，由CMake函数`zephyr_linker_sources()`填充。

在开发板、SoC或架构的`CMakeFiles.txt`中，将文件添加为链接器源文件（Linker Source）：

```cmake
zephyr_linker_sources(NOINIT snippets-noinit.ld)
```

然后在`CMakeFiles.txt`所在目录创建名为`noinit.ld`的文件：

```c
#if defined(CONFIG_LLEXT) && !defined(CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT)
*(.llext_heap)
*(.llext_ext_heap)
*(.llext_metadata_heap)
#endif /* CONFIG_LLEXT && !CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT */
```

> 译注：以上保留原文文件名和代码，但存在两处不一致：常规CMake入口应为`CMakeLists.txt`，原文写成了`CMakeFiles.txt`；创建的是`noinit.ld`，示例调用却传入`snippets-noinit.ld`。按[仓库中的zephyr_linker_sources实现](../../../cmake/modules/extensions.cmake)，`snippets-noinit.ld`是构建时生成的包含汇总文件，参数应指向实际源片段。若源片段确实命名为`noinit.ld`，应注册`zephyr_linker_sources(NOINIT noinit.ld)`，并在链接脚本中包含生成的`snippets-noinit.ld`。不要照原文拼写另造CMake入口文件；实际使用前核对所用Zephyr版本。

对于ARC，哈佛架构的指令和数据堆节`.llext_instr_heap`、`.llext_data_heap`已经在架构层分别放入相应存储器。对于采用哈佛架构的非ARC开发板，需要手动放置这两个节。

> 警告：如果加载和链接扩展时，`.llext_instr_heap`所在指令存储器不可写，LLEXT将无法加载扩展。

也可以使用自定义链接脚本指定位置。[`CONFIG_CUSTOM_LINKER_SCRIPT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_CUSTOM_LINKER_SCRIPT)指定替代开发板默认脚本的链接脚本路径。由于内核可能要求特定布局或区域，脚本必须基于Zephyr提供的版本。这适用于应用需要添加节、又希望避免修改Zephyr脚本的场景。

使用自定义链接脚本时，可能需要覆盖默认放置规则。例如，仍包含`include/zephyr/linker/common-noinit.ld`，但希望把堆放到其他位置。此时选择[`CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_CUSTOM_HEAP_PLACEMENT)，移除链接脚本中LLEXT堆节的默认放置规则，由用户自行安排。

<a id="word-granular-access-instruction-memory-heap"></a>

## 3.4\_按字粒度访问的指令存储器堆

按字粒度访问的指令存储器（Word Granular Access Instruction Memory）可以按字节寻址，但只能使用字大小、对齐的加载与存储操作访问。目前，LLEXT仅在Xtensa架构上支持将指令堆放入这种存储器；其他架构的支持可在未来按需求加入。

Xtensa SoC或开发板除选择[`CONFIG_HARVARD`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HARVARD)外，还必须选择[`CONFIG_ARCH_HAS_WORD_GRANULAR_ACCESS_INSTR_MEM`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ARCH_HAS_WORD_GRANULAR_ACCESS_INSTR_MEM)。该选项启用对可按字节寻址、按字粒度访问的指令存储器的支持。

若堆仍使用默认数据结构[`k_heap`](../heap_reference/P002_内核堆结构.md)，还需启用[`CONFIG_SYS_HEAP_BIG_ONLY`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_SYS_HEAP_BIG_ONLY)。它只针对大堆优化代码，能够容纳任意堆大小，但对小堆的内存利用不够高效。若未启用，指令堆初始化期间会出现非对齐或窄访问（Unaligned and Narrow Accesses）。

随后按前一节说明，将LLEXT指令堆放入该存储器。SoC或开发板除[`arch_is_instr_mem()`](https://docs.zephyrproject.org/latest/doxygen/html/group__instr__mem.html#ga61c79df57849b7e914cd33e0de4316a3)外，还必须实现[`arch_memcpy_to_instr()`](https://docs.zephyrproject.org/latest/doxygen/html/group__instr__mem.html#ga506986b790b95fca0423e4c47690b1fe)和[`arch_memcpy_from_instr()`](https://docs.zephyrproject.org/latest/doxygen/html/group__instr__mem.html#ga03af01659004f2d96438b948f8c065a9)。字粒度访问库中的`memcpy_to_word_granular()`、`memcpy_from_word_granular()`可能有助于实现。

ELF缓冲区可以放在RAM中。加载时，LLEXT会强制将代码区域（Text Region）放到指令堆，使其可执行，即使ELF缓冲区本身可写也如此。加载和链接期间访问代码区域时，会遵守字粒度访问限制。

> 警告：指令堆位于这种存储器中时，只能使用缓冲区加载器[`llext_buf_loader`](P021_缓冲区加载器.md)加载ELF。

扩展自身有责任保证后续对指令存储器的访问也满足这些限制。

如果仍发生加载／存储异常，可通过[`CONFIG_XTENSA_EMULATE_UNSUPPORTED_UNSIGNED_LOAD_STORE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_XTENSA_EMULATE_UNSUPPORTED_UNSIGNED_LOAD_STORE)启用Xtensa无符号加载／存储异常处理程序。当无符号指令触发不支持的加载／存储异常时，该处理程序使用受支持的字大小、对齐操作代为执行。目前不支持超长指令字（Very Long Instruction Word，VLIW）。

如选项描述所述，还必须禁用VLIW，因为启用VLIW会使编译器生成有符号加载／存储指令。[`CONFIG_COMPILER_CODEGEN_VLIW_DISABLED`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_COMPILER_CODEGEN_VLIW_DISABLED)明确要求编译器绝不生成VLIW指令。

<a id="elf-object-type"></a>

## 3.5\_ELF对象类型（ELF Object Type）

LLEXT支持不同类型的扩展，通过以下Kconfig选项选择：

| 配置项 | 含义 |
| --- | --- |
| [`CONFIG_LLEXT_TYPE_ELF_OBJECT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_TYPE_ELF_OBJECT) | 构建并使用可重定位文件（Relocatable File）作为对象类型，一次编译器调用生成目标文件。 |
| [`CONFIG_LLEXT_TYPE_ELF_RELOCATABLE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_TYPE_ELF_RELOCATABLE) | 构建并使用可重定位、部分链接（Partially Linked）的文件。链接器将多个目标文件合并为一个。 |
| [`CONFIG_LLEXT_TYPE_ELF_SHAREDLIB`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_TYPE_ELF_SHAREDLIB) | 构建并使用共享库（Shared Library）。通过标准链接流程，将多个目标文件生成共享库。 |

> 注意：共享库方式目前不支持ARM架构。

<a id="minimize-allocations"></a>

## 3.6\_减少内存分配（Minimize Allocations）

LLEXT默认采用定位／读取（Seek/Read）抽象，将所有数据复制到分配的内存中，以便从任何存储介质加载扩展。如果数据已经位于RAM缓冲区中，可能无须再次复制。

[`CONFIG_LLEXT_STORAGE_WRITABLE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_STORAGE_WRITABLE)允许直接引用ELF缓冲区中的节数据加载扩展，以减少内存占用。它要求ELF加载器支持窥视（`peek`）功能，例如[`llext_buf_loader`](P021_缓冲区加载器.md)。

> 警告：应用必须保证加载所用缓冲区一直保留到扩展卸载完成。

> 注意：链接阶段会直接修改缓冲区内容。扩展卸载后，必须重新装入缓冲区内容，才能再次将它用于[`llext_load()`](P011_扩展管理API.md#ga0a4c3db30bc3ec7aa8a9b0e076af7157)。

## 3.7\_符号分组（Symbol Groups）

所有LLEXT符号都属于一个分组。各组是否纳入导出符号表（Exported Symbol Table），由对应Kconfig符号控制。使用[`EXPORT_GROUP_SYMBOL`](P015_导出符号API.md#gad7e83af3c134d5eaabd1e1fad6689947)和[`EXPORT_GROUP_SYMBOL_NAMED`](P015_导出符号API.md#ga2da450c08c6b3dc8ebcf2f9d3f783006)将符号导出到指定分组。例如，将`memcpy`导出到`LIBC`组：

```c
EXPORT_GROUP_SYMBOL(LIBC, memcpy);
```

组名可自行定义，但必须全部大写。C代码中使用的每个分组，都必须有以下形式的Kconfig符号：

```kconfig
config LLEXT_EXPORT_SYMBOL_GROUP_{GROUP_NAME}
   bool "Export all symbols from the {GROUP_NAME} group"
```

代码中的提示文本含义是“导出`{GROUP_NAME}`分组的全部符号”。

通过[`EXPORT_SYMBOL`](P015_导出符号API.md#ga0188531646d69e784eccf85bd4fb34aa)或[`EXPORT_SYMBOL_NAMED`](P015_导出符号API.md#ga9822b90952597e6acd993999a7228aa1)声明、没有显式指定分组的符号，默认属于`UNASSIGNED`组。是否包含该组由[`CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_UNASSIGNED`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_UNASSIGNED)控制。

Zephyr目前定义的LLEXT符号分组如下：

| 组名（Group Name） | Kconfig符号 | 说明 |
| --- | --- | --- |
| `UNASSIGNED` | [`CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_UNASSIGNED`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_UNASSIGNED) | 未显式分组的符号。 |
| `SYSCALL` | [`CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_SYSCALL`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_SYSCALL) | Zephyr内核系统调用。 |
| `LIBC` | [`CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_LIBC`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_LIBC) | C标准库函数，例如[`memcpy()`](https://docs.zephyrproject.org/latest/doxygen/html/string_8h.html#af0f01bffcd16daa9143f6014d10a25ad)。 |
| `DEVICE` | [`CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_DEVICE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXPORT_SYMBOL_GROUP_DEVICE) | 设备树设备（Devicetree Devices）。 |

<a id="using-slid-for-symbol-lookups"></a>

## 3.8\_使用SLID查找符号

加载扩展时，LLEXT必须查找扩展引用的、位于主应用中的全部符号地址。因此，主二进制程序包含LLEXT专用符号表，每个向扩展导出的符号都有一条“符号名到地址”的映射，加载时由LLEXT链接器查询。字符串比较使该过程较慢，导出符号增加后，符号表也可能占用较大空间。

[`CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID)对Zephyr二进制程序及所有正在构建的扩展增加处理步骤：将符号表中的每个字符串转换为指针大小的哈希值，称为符号链接标识符（Symbol Link Identifier，SLID），并保存在二进制程序中。

整数比较替代字符串比较，可加快符号查找。采用SLID链接后，二进制程序也不再需要保存符号名称，符号表大小可显著减小。

> 注意：此选项目前与LLEXT EDK不兼容。

> 注意：主程序与扩展不能使用不同的选项值。例如，主程序使用`CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID=y`构建时，禁止加载使用`CONFIG_LLEXT_EXPORT_BUILTINS_BY_SLID=n`编译的扩展。
