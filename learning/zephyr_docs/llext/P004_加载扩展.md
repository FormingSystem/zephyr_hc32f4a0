# 第4章\_加载扩展

原文：[官方页面](https://docs.zephyrproject.org/latest/services/llext/load.html)。本次读取日期：2026-10-14；基线为保存的`latest`页面，HTML摘要见[来源记录](../SOURCES.md)。

<a id="loading-extensions"></a>

<a id="loading-an-extension"></a>

## 4.1\_加载扩展（Loading an Extension）

构建完成并取得ELF文件后，可以通过LLEXT API将扩展加载到Zephyr应用。该API可将扩展装入内存、访问其符号并调用其中的函数。

加载扩展可使用[`llext_loader`](P025_扩展加载器上下文.md)的任意实现。加载器包含一组函数指针，用于读取ELF数据，同时提供[`llext_load()`](P011_扩展管理API.md#ga0a4c3db30bc3ec7aa8a9b0e076af7157)需要的最小上下文内存。已经提供的加载器包括：

- [`llext_buf_loader`](P021_缓冲区加载器.md)：从可寻址内存中包含ELF的缓冲区读取。可使用[`LLEXT_TEMPORARY_BUF_LOADER`](P014_ELF加载器API.md#ga8485b4dfecbd2eff3e21b5958d5e8699)、[`LLEXT_PERSISTENT_BUF_LOADER`](P014_ELF加载器API.md#ga2c2214bcf1506f1209476619e42114b3)或[`LLEXT_WRITABLE_BUF_LOADER`](P014_ELF加载器API.md#gac726727897e02bca0bf5d32f4c66be55)宏，向LLEXT表明缓冲区类型。
- [`llext_fs_loader`](P023_文件系统加载器.md)：从文件系统中的文件读取。使用[`LLEXT_FS_LOADER`](P014_ELF加载器API.md#ga25a394fb7f7f93cfe3ab92d8ed4a6bff)宏创建加载器时，必须提供文件路径。
- [`llext_semihost_loader`](P026_半主机加载器.md)：通过半主机机制（Semihosting）读取主机文件系统中的文件。使用[`LLEXT_SEMIHOST_LOADER`](P014_ELF加载器API.md#ga28c2ad64c0b54fdea6130916ca35aec5)宏创建加载器时，必须提供文件路径。

调用[`llext_load()`](P011_扩展管理API.md#ga0a4c3db30bc3ec7aa8a9b0e076af7157)并传入扩展名称和已配置的加载器。调用成功后，扩展已装入内存，可以使用。

> 注意：启用用户态（User Mode）时，扩展不会自动加入任何用户内存域（User Memory Domain）。必须调用[`llext_add_domain()`](P011_扩展管理API.md#ga64b13edf15b7c233b49c9c8edff884e6)，才能从用户态访问。

<a id="initializing-and-cleaning-up-the-extension"></a>

## 4.2\_初始化与清理扩展

扩展可能定义若干初始化函数，必须在加载之后、使用其中任何函数之前调用。例如，C++等语言提供对象构造函数（Constructors）。类似地，也可能有必须在卸载前调用的清理函数（Cleanup Functions）。

LLEXT通过[`llext_bringup()`](P011_扩展管理API.md#ga01c0c23dba5ff1aa9da42c7895cc7fab)调用ELF文件`.preinit_array`和`.init_array`节中列出的函数，通过[`llext_teardown()`](P011_扩展管理API.md#gae061bb6100ad394fcaca7751ff3dadba)调用`.fini_array`中的函数。这些API兼容用户态，可从内核上下文（Kernel Context）或用户上下文（User Context）调用。

> 重要：这些函数执行的代码完全由ELF文件内容决定。如果ELF来源不可信，可能带来安全影响。

扩展需要专用线程时，可用[`llext_bootstrap()`](P011_扩展管理API.md#ga809f7a7976b4436dad31aa03d9ea3729)减少重复代码。其函数签名与[`k_thread_create()`](../thread_core_reference/P001_线程公共接口.md#gad5b0bff3102f1656089f5875d999a367)兼容，会先调用[`llext_bringup()`](P011_扩展管理API.md#ga01c0c23dba5ff1aa9da42c7895cc7fab)，再在同一上下文中调用用户指定的函数，最后在返回前调用[`llext_teardown()`](P011_扩展管理API.md#gae061bb6100ad394fcaca7751ff3dadba)。

<a id="accessing-code-and-data"></a>

## 4.3\_访问代码与数据

主应用通过[`llext_find_sym()`](P011_扩展管理API.md#gac0982fad15a62723a5cad3f7edd6ba3e)取得导出符号的地址，与新加载的扩展交互。返回的`void *`可转换为适当类型后使用。

[`llext_call_fn()`](P011_扩展管理API.md#gad50ad281c70093da99851723fc6af470)提供调用无参数函数的包装接口（Wrapper）。

需要直接访问扩展内存区域的高级用户，可参阅[`llext_get_section_info()`](P013_ELF检查API.md#ga23121962662f057da004ac1c527716e3)及其他LLEXT检查API（Inspection APIs）。

<a id="cleaning-up-after-use"></a>

## 4.4\_使用后的清理

不再需要扩展时，必须调用[`llext_unload()`](P011_扩展管理API.md#gad3df7ed4d436846504c0047166eb929e)释放它使用的内存。调用完成后，之前取得的指向扩展符号的全部指针都失效。

<a id="troubleshooting"></a>

## 4.5\_故障排查（Troubleshooting）

该功能仍在持续开发，可能出现问题。链接会修改二进制代码，因此发生错误时，结果难以预测。常见问题包括：

- [`llext_find_sym()`](P011_扩展管理API.md#gac0982fad15a62723a5cad3f7edd6ba3e)返回无效地址。
- 扩展中定义的常量和变量没有预期值。
- 调用扩展函数触发硬故障（Hard Fault），或函数返回后，主应用内存被破坏。

遇到这些情况，可以尝试以下方法定位问题：

1. 确认`CONFIG_LLEXT_LOG_LEVEL`设为`DEBUG`，收集调用[`llext_load()`](P011_扩展管理API.md#ga0a4c3db30bc3ec7aa8a9b0e076af7157)时的日志。
2. 如果可行，禁用MMU／MPU内存保护，观察行为是否变化。
3. 尽量将扩展简化到能够复现问题的最少代码。
4. 使用调试器（Debugger）检查内存和寄存器，进一步分析。详见[调试扩展](P005_调试扩展.md)。

如果问题仍然存在，请在官方GitHub仓库提交问题（Issue），并包含上述全部信息。
