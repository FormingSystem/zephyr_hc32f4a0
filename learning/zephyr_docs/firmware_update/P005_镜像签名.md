# 第5章\_镜像签名

原文：[Signing Binaries](https://docs.zephyrproject.org/latest/build/signing/index.html)。读取日期：2026-10-12，`latest`。

本页说明通过 CMake 构建逻辑自动为二进制文件生成**数字签名（Digital Signature）**。另一种方式是独立执行 `west sign`，见[官方west签名说明](https://docs.zephyrproject.org/latest/develop/west/sign.html#west-sign)。

## 5.1\_MCUboot与imgtool

Zephyr 构建系统专门支持用 [imgtool](https://pypi.org/project/imgtool/) 为 [MCUboot](https://mcuboot.com/) 生成签名镜像。设置相应 Kconfig 后，可把构建与签名作为同一次流程，随后 `west flash` 使用签名后的二进制文件。

下面原例构建并烧录 MCUboot 和由它**链式加载（Chain-loading）**的 Hello World 应用。当前位置是[入门指南](../getting_started/P002_入门指南.md)所用工作区根，源码位于其下 `zephyr/`；环境、west、工具链和所需模块应已准备完成。这是原例布局，不要求已有实验工程重新初始化。

```sh
west build -b YOUR_BOARD zephyr/samples/hello_world --sysbuild -d build-hello-signed -- \
     -DSB_CONFIG_BOOTLOADER_MCUBOOT=y

west flash -d build-hello-signed
```

将占位符 `YOUR_BOARD` 替换为实际板目标。反斜杠换行形式面向 Bash 一类终端；Windows 使用已配置的 Bash，或在相应终端将构建命令合成一行。`--sysbuild` 启用**多镜像系统构建（System Build，sysbuild）**，`-d` 把构建结果放入相对目录 `build-hello-signed`，`--` 后的 `-D` 设置 CMake 配置输入。第二条命令会实际烧录设备。

原例使用 MCUboot 自带、不安全的开发测试密钥。应用目录可以换成任何可由 MCUboot 加载的应用，例如[简单管理协议（Simple Management Protocol，SMP）服务器示例](P022_SMP服务器示例.md)。相关配置为：

| Kconfig 配置项 | 作用 |
| --- | --- |
| [`SB_CONFIG_BOOTLOADER_MCUBOOT`](https://docs.zephyrproject.org/latest/kconfig.html#SB_CONFIG_BOOTLOADER_MCUBOOT) | 将应用构建为由 MCUboot 加载，并在系统构建中加入引导程序。 |
| [`SB_CONFIG_BOOT_SIGNATURE_KEY_FILE`](https://docs.zephyrproject.org/latest/kconfig.html#SB_CONFIG_BOOT_SIGNATURE_KEY_FILE) | 选择签名密钥文件，或逗号分隔的文件列表。 |
| [`CONFIG_MCUBOOT_EXTRA_IMGTOOL_ARGS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_MCUBOOT_EXTRA_IMGTOOL_ARGS) | 传给 imgtool 的附加命令行参数。 |
| [`CONFIG_MCUBOOT_GENERATE_CONFIRMED_IMAGE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_MCUBOOT_GENERATE_CONFIRMED_IMAGE) | 额外生成已确认镜像；某些生产烧录场景比默认可用于**空中升级（Over-the-Air Update，OTA）**的镜像更适合使用它。 |

使用密钥列表时，MCUboot 嵌入每个密钥的公钥部分，并接受其中任一公钥可验证的镜像；第一项同时用于给应用签名，后续项必须是相同签名类型、仅含公钥的 **PEM文本封装（Privacy-Enhanced Mail，PEM）**文件，满足 imgtool 要求。端到端的模拟示例见 [MCUboot多密钥测试](https://github.com/zephyrproject-rtos/zephyr/blob/main/tests/boot/mcuboot_multiple_keys)。

原文建议：Windows 遇到 Access denied（拒绝访问）时，在所用 Python 环境执行 `pip3 install imgtool`，再用干净构建目录重试。

## 5.2\_启动输出与烧录器支持

如果所选 **运行器（Runner）**使用 imgtool 支持的镜像格式，烧录后设备串口可能显示如下原文输出：

```text
*** Booting Zephyr OS build zephyr-v2.3.0-2310-gcebac69c8ae1  ***
[00:00:00.004,669] <inf> mcuboot: Starting bootloader
[00:00:00.011,169] <inf> mcuboot: Primary image: magic=unset, swap_type=0x1, copy_done=0x3, image_ok=0x3
[00:00:00.021,636] <inf> mcuboot: Boot source: none
[00:00:00.027,374] <inf> mcuboot: Swap type: none
[00:00:00.115,142] <inf> mcuboot: Bootloader chainload address offset: 0xc000
[00:00:00.123,168] <inf> mcuboot: Jumping to the first image slot
*** Booting Zephyr OS build zephyr-v2.3.0-2310-gcebac69c8ae1  ***
Hello World! nrf52840dk_nrf52840
```

输出先显示 MCUboot 启动、检查主镜像和交换状态，再跳到第一个镜像槽，最后打印应用的 Hello World。旧版本字符串、板名和链式加载偏移均是原例内容，不是本次硬件验证结果。

功能是否可用取决于 [west运行器](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html#west-runner)。原文列出 nrfjprog 和 pyocd 运行器支持上述流程；其他运行器如需增加支持，可向上游提交补丁或问题报告。

> 译注：这只是运行器功能说明，不表示当前板已经具备正确分区或安全引导。若构建找不到模块/密钥，返回依赖与配置检查；若启动不成功，先核对烧录格式、偏移和控制台，而不能仅看到烧录工具返回成功就判定签名启动通过。

## 5.3\_签名密钥传到哪些镜像

系统构建使用 `SB_CONFIG_BOOT_SIGNATURE_KEY_FILE` 选密钥，并把值传给两个镜像：

- 应用镜像得到配置项 [`CONFIG_MCUBOOT_SIGNATURE_KEY_FILE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_MCUBOOT_SIGNATURE_KEY_FILE)，由 imgtool 用于签名。
- MCUboot 镜像得到配置项 `CONFIG_BOOT_SIGNATURE_KEY_FILE`，将其公钥部分编入引导程序，以验证签名。

**原文警告：**默认文件（例如 `root-ec-p256.pem`）是随每份 Zephyr/MCUboot 源码一起公开的开发密钥，只适合开发测试。其他用途应生成自己的密钥，并避免把私钥放进自己无法控制的仓库或构建目录。

## 5.4\_密钥文件的路径解析

配置值先经 CMake 命令 `string(CONFIGURE)` 处理，其中 `${VARIABLE}` 形式的引用按当时可用的 CMake 变量展开。展开后若为绝对路径，直接使用；若为相对路径，各镜像独立查找：

| 镜像 | 相对路径查找顺序 |
| --- | --- |
| 应用 | 先 `APPLICATION_CONFIG_DIR`，再 west 工作区顶层 `WEST_TOPDIR`。 |
| MCUboot | 先 `APPLICATION_CONFIG_DIR`，再 MCUboot 模块目录。 |

变量 `APPLICATION_CONFIG_DIR` 是相应镜像的应用配置目录，`WEST_TOPDIR` 是 west 工作区根。**原文警告：**两幅镜像解析基准不同，同一裸相对路径可能指向不同文件并导致构建失败，应使用明确锚定的路径。

原文推荐以变量 `${APP_DIR}`（主应用源码目录）锚定，让两幅镜像找到同一文件。这样无需在文档里写入个人盘符或主机绝对位置：

```kconfig
# sysbuild.conf
SB_CONFIG_BOOT_SIGNATURE_KEY_FILE="${APP_DIR}/keys/my-signing-key.pem"
```

> 译注：该设置写入应用的 `sysbuild.conf`，`${APP_DIR}` 保持字面形式，由 CMake 展开，不是让 shell 提前替换。例中的私钥文件必须由应用所有者事先提供；本次未生成、复制或提交密钥。

同样的路径规则适用于可选加密密钥配置项 [`CONFIG_MCUBOOT_ENCRYPTION_KEY_FILE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_MCUBOOT_ENCRYPTION_KEY_FILE)。签名与加密是不同用途，不能仅凭文件路径相同就推断两者已经配置。

## 5.5\_扩展或替换签名脚本

可以扩展或替换参与烧录流程的签名脚本，增加功能或采用其他签名机制。默认启用 MCUboot 时，由 Zephyr 的 `cmake/mcuboot.cmake` 加入构建后的签名生成命令。

选择优先级为：sysbuild 设置优先，其次是 Zephyr 目标属性，最后是默认 MCUboot 脚本。可在系统构建范围用 `-D<target>_SIGNING_SCRIPT` 为特定镜像设置脚本，或用 `-DSIGNING_SCRIPT` 为所有镜像设置脚本。原例为：

```sh
west build -b <board> <application> -DSIGNING_SCRIPT=<file>
```

> 译注：`<board>`、`<application>`、`<file>` 是待替换占位符，不应把尖括号原样交给 shell。若按本节使用 sysbuild，还需启用该模式；从新的构建目录传 CMake 设置时可采用 `west build --sysbuild -b <board> <application> -- -DSIGNING_SCRIPT=<file>` 的结构，其中脚本必须真实存在，路径基准须按实际脚本加载位置核对，可用 CMake 变量锚定。原例省略了这些上下文。

下面的条件使用 Kconfig 配置项 `CONFIG_BOOTLOADER_MCUBOOT` 判断是否启用 MCUboot 兼容模式，`PROPERTIES` 是设置目标属性的 CMake 关键字。另一种方式是在模块中设置 CMake 目标 `zephyr_property_target` 的属性 `SIGNING_SCRIPT`。变量 `${CMAKE_CURRENT_LIST_DIR}` 指当前 CMake 文件所在目录：

```cmake
if(CONFIG_BOOTLOADER_MCUBOOT)
  set_target_properties(zephyr_property_target PROPERTIES SIGNING_SCRIPT ${CMAKE_CURRENT_LIST_DIR}/custom_signing.cmake)
endif()
```

启用 MCUboot 签名支持时，这会包含自定义 CMake 文件而非默认签名文件。可以参考 Zephyr 的基础 MCUboot 签名脚本扩展默认行为。所引用的 `custom_signing.cmake` 必须实际提供；仅设置属性不会创建脚本。

本次没有运行构建、签名、密钥生成或烧录，也没有把原文预期输出当作实测记录。
