# 第4章\_安全需求（Safety Requirements）

原文：[官方页面](https://docs.zephyrproject.org/latest/safety/safety_requirements/safety_requirements.html)。快照读取日期：2026-10-15；来源摘要见[来源记录](../SOURCES.md)。

<a id="introduction"></a>

## 4.1 引言（Introduction）

安全委员会牵头收集反映实际实现状态的需求，遵循项目安全工作的 3s 路线。目标不是通过新增需求来申请项目尚未提供的新功能。 相关链接：[3s 路线（Route 3s）](P002_Zephyr功能安全概述.md#general-safety-scope)。

需求保存在独立仓库：[需求仓库（Requirement repository）](https://github.com/zephyrproject-rtos/reqmgmt)。

当前渲染后的内容可在 [Zephyr 项目需求（Zephyr Project Requirements）](https://zephyrproject-rtos.github.io/reqmgmt/)页面查看。

<a id="objectives-of-requirements-management-in-the-zephyr-project"></a>

## 4.2 Zephyr 项目需求管理的目标

在开发及记录已实现或预期功能时，有效的需求管理（Requirements Management）可以确保 RTOS 实现预定用途、在约束下可靠运行，并能方便地与硬件平台、嵌入式软件栈及应用软件层集成。

需求管理以结构化方法，在系统生命周期中收集、组织并追溯利益相关方的需要和期望。现有[项目文档](https://docs.zephyrproject.org/latest/index.html)侧重内核功能、API 配置选项和模块行为等实现细节。这些内容对开发者不可或缺，但仅依赖低层文档，可能导致理解碎片化、追溯受限，以及最终系统扩展或认证困难。

为改善理解，并为产品负责人、软件架构师、质量管理、安全管理和评估人员等非编码角色提供价值，项目还需要描述整体功能、结构和实现约束的高层需求。

<a id="guideline-to-requirements-management"></a>

## 4.3 需求管理指南（Guideline to Requirements Management）

以下说明需求仓库的规则，以及新增需求时对结构和语法的期望。

注意：这些规则用于需求仓库，其内容不像面向 Zephyr 用户的文档那样采用 .rst 编写。编写项目文档的规范请参阅[文档指南（Documentation Guidelines）](../contributing/P010_文档编写指南.md#doc-guidelines)。

<a id="scope"></a>

### 4.3.1 范围（Scope）

需求的初始范围是内核（Kernel）功能。也欢迎非内核功能需求，但目前并非重点。

<a id="managing-zephyr-requirements-structure-tools-and-grammar"></a>

### 4.3.2 管理 Zephyr 需求：结构、工具与语法

<a id="levels-of-requirements-in-the-repository"></a>

#### 4.3.2.1 仓库中的需求层级（Levels of requirements）

安全工作组评估了用需求补充现有低层描述的方法，在现有文档结构之上建立两级需求：最高层是系统需求（System Requirements），定义 Zephyr RTOS 整体能力；下一层是软件需求（Software Requirements），将系统层期望细化为各组件的详细规格。

系统需求（System Requirements）

系统需求描述 Zephyr RTOS（此处的“系统”）的行为，从高层说明功能和约束，不深入功能细节。

系统需求用于概览 Zephyr RTOS 当前已实现的特性。

这些需求从功能、性能和接口角度说明 RTOS 必须实现的目标，例如确定性任务调度、中断处理延迟、内存占用上限及行业标准符合性。系统需求是设计决策与确认准则的基础。

编写者若已了解 Zephyr 项目，或熟悉 RTOS 特有的需求和约束，将有助于创建这些需求。

软件需求（Software Requirements）

软件需求位于系统需求之下，将系统层需求细化为组件级规格，覆盖调度器、内存管理器和进程间通信机制等模块。

软件需求描述各组件的行为、接口和约束，确保它们共同实现系统目标；定义功能必须执行的具体动作和行为，使每条需求都能通过测试、分析和／或检查验证。

这一层仍应保持实现无关（Implementation-free）。实现说明应放在文档中；若尚未存在，应作为需求创建工作的另一项任务补充。

<a id="requirements-management-toolchain"></a>

#### 4.3.2.2 需求管理工具链（Requirements Management Toolchain）

<a id="requirement-repository"></a>

##### 4.3.2.2.1 需求仓库（Requirement Repository）：

需求仓库体现 Zephyr 的结构化需求管理方法，目前重点是目标安全认证范围，但并不限于此范围。 相关链接：[需求仓库（Requirement repository）](https://github.com/zephyrproject-rtos/reqmgmt)。

使用正常的 GitHub 分支与 PR 工作流。当前由安全工作组成员评审 PR，合入至少需要以下角色之一批准：Zephyr 安全经理（Safety Manager）、安全主席（Safety Chair）或安全架构师（Safety Architect）。

<a id="requirement-tooling"></a>

##### 4.3.2.2.2 需求工具（Requirement Tooling）：

项目使用 [StrictDoc](https://strictdoc.readthedocs.io/en/stable/) 编写、关联需求，并渲染可浏览的 .html 版本。

StrictDoc 是轻量级开源工具，用于编写、浏览和导出结构化需求，支持层次结构、可追溯关系及便于评审的 HTML 导出。

需求采用 StrictDoc 自己的 Markdown 语法编写。

> 译注——文件格式：这里保留原文“Markdown”表述，但后文示例实际是 StrictDoc 的结构化需求语法，使用 `.sdoc` 文件、字段和 `.sgra` 语法定义。不要把它当作普通 Markdown 文件直接改名；具体格式由所用 StrictDoc 版本和需求仓库语法决定。

偏好所见即所得（What You See Is What You Get，WYSIWYG）编辑的读者，也可以通过 StrictDoc 本地服务器编辑其 HTML 界面中的需求。

工具链设置方法见[需求管理入门（Getting started with Requirements Management）](P007_需求管理入门.md#getting-started-with-safety-requirements)。

<a id="verification-of-requirements"></a>

##### 4.3.2.2.3 需求验证（Verification of Requirements）：

新增或修改的需求，即需求仓库 PR 中的内容，必须经过评审验证。评审意见可直接记录在 PR 评论中。评审既要考虑技术正确性，也要检查需求是否符合规定的形式准则。

检查项和形式要求详见[安全需求检查清单（Safety Requirements Checklist）](P005_安全需求检查清单.md#safety-requirements-checklist)。Zephyr 项目的测试必须评估实际实现是否符合需求描述的功能。

<a id="glossary-of-requirements-grammar-elements"></a>

#### 4.3.2.3 需求语法要素词汇表（Glossary of Requirements Grammar Elements）

所有需求必须使用规定的语法：

<a id="id2"></a>

**StrictDoc 需求结构**

| 属性（Property） | 说明（Description） |
| --- | --- |
| UID（唯一标识符） | 用于识别需求的唯一 ID，由 StrictDoc 自动分配。 |
| STATUS（状态） | 描述需求状态：Draft（草稿）、Approved（已批准）、Retired（已退役）。 |
| TYPE（类型） | Functional（功能性）、Non-functional（非功能性）。 |
| COMPONENT（组件） | 应实现该需求的组件。 |
| REFERENCE（引用） | 引用父需求和／或子需求。 |
| TITLE（标题） | 能描述需求的标题，应简短、明确。 |
| STATEMENT（陈述） | 需求的描述。 |
| USER_STORY（用户故事） | 描述需求的用户故事；可选，仅在能为需求陈述提供额外价值时添加。 |

<a id="requirement-uid-unique-identifier-handling"></a>

#### 4.3.2.4 需求唯一标识符（UID）的处理

[StrictDoc](https://strictdoc.readthedocs.io/en/stable/) 负责管理每条需求的唯一标识符（Unique Identifier，UID），操作步骤如下：

1. 新建需求时，不添加 UID 值和 UID 字段。

2. 完成新需求编写后，执行 `strictDoc manage auto-uid .`。

> 译注——命令大小写与 UID 写法：原文此处写成 `strictDoc`，而入门页和当前[官方需求仓库 README](https://raw.githubusercontent.com/zephyrproject-rtos/reqmgmt/main/README.md)使用小写 `strictdoc`。本节要求新需求不填写 UID 字段，创建示例页则要求 `UID: TBD`，两处存在差异。不要据此批量改写已有 UID；新需求应按所用版本规则生成并检查结果，示例差异另见[创建首条需求](P008_创建首条RTOS需求.md)。

3. 如有需要，使用新分配的 UID 建立需求之间的链接。

完成后即可创建 PR。CI 会检查 UID 是否有效、有无重复；出现重复时，需要变基（Rebase）并重新执行以上步骤。

<a id="consistency"></a>

#### 4.3.2.5 一致性（Consistency）

所有需求的语言和用词应保持一致，见[语法（Syntax）](#syntax)。

也建议阅读已有需求及 PR 讨论，了解在该项目语境中怎样编写更合适。 相关链接：[需求仓库（Requirement repository）](https://github.com/zephyrproject-rtos/reqmgmt)。

<a id="pull-request-requirement-repository"></a>

#### 4.3.2.6 需求仓库的拉取请求（Pull Request）

- 遵循 Zephyr 项目的[贡献指南（Contribution Guidelines）](../contributing/P002_贡献指南.md#contribute-guidelines)。

  - 前提是相应规则适用于需求仓库。

- 避免在大型提交中混合琐碎变更和实质变更。

- 避免在同一提交中既移动需求又修改需求。

<a id="characteristics-of-a-good-requirement"></a>

#### 4.3.2.7 良好需求的特征（Characteristics of a good requirement）

- 无歧义（Unambiguous）。

- 可验证（Verifiable），例如功能需求可通过测试验证。

- 清晰（Clear）：简洁、简短、简单、精确。

- 正确（Correct）。

- 易理解（Understandable）。

- 可行（Feasible）：现实、能够实现。

- 独立（Independent）。

- 原子性（Atomic）。

- 必要（Necessary）。

- 实现无关（Implementation-free）：保持抽象。

<a id="characteristics-of-a-set-of-requirements"></a>

#### 4.3.2.8 一组需求的特征

- 完整（Complete）。

- 一致（Consistent）。

- 无冗余（Non-redundant）。

<a id="syntax"></a>

### 4.3.3 语法（Syntax）

- 建议使用公认的需求句式。

  - [EARS](https://alistairmavin.com/ears/) 是良好的参考，尤其适合不熟悉需求编写的读者。

  - 也接受其他格式，只要满足上述需求特征。
