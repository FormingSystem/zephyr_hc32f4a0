# 第49章\_作用域清理

原文：[Scope-based Cleanup Helpers](https://docs.zephyrproject.org/latest/kernel/cleanup.html)。读取日期：2026-10-12，`latest`。

清理辅助接口让变量离开**作用域（Scope）**时自动清理资源，类似 C++ 的 RAII（Resource Acquisition Is Initialization，资源获取即初始化）或 Go 的 `defer`。它利用编译器的 `__cleanup` 属性，确保作用域退出时执行清理代码，减少资源泄漏与重复错误处理。

需要启用 `CONFIG_SCOPE_CLEANUP_HELPERS`。典型用途包括自动释放互斥量或信号量、释放动态分配的内存、覆盖包括提前返回在内的退出路径，以及减少重复清理代码。

原文警告：工具链不支持 `__cleanup` 属性时，接口不可用。因此这些接口仅供用户应用使用，不用于内核本身或其他子系统。

## 49.1\_核心概念

接口包含三种抽象：作用域变量在声明时执行初始化，离开作用域时执行退出函数；作用域守卫是特殊的作用域变量，在初始化时获取锁或资源，退出时释放；作用域延后操作只登记退出时执行的函数，不在初始化时获取资源，类似 `defer`。

> 译注：本页“用户应用”与用户模式不是同义词，不能据此推断所有底层资源接口都可从非特权线程调用。自动清理也依赖正常的语言作用域退出，不是断电、**中央处理器（Central Processing Unit，CPU）** 致命故障或强行终止线程后的资源恢复保证。

## 49.2\_定义作用域类型

以下宏为初始化、退出、获取和释放动作生成对应包装，调用时再绑定具体资源。

### 49.2.1\_自定义作用域变量

用 `SCOPE_VAR_DEFINE` 定义带初始化与退出动作的变量类型，再用 `scope_var` 声明变量。退出表达式中的 `_T` 表示被清理变量的值。

```c
static inline struct flash_area *flash_area_init(int area_id)
{
    struct flash_area *fa;

    if (flash_area_open(area_id, &fa) < 0) {
        return NULL;
    }

    return fa;
}

static inline void flash_area_exit(struct flash_area *fa)
{
    if (fa != NULL) {
        flash_area_close(fa);
    }
}

// Define the scoped variable type
SCOPE_VAR_DEFINE(flash_area, struct flash_area *, flash_area_exit(_T),
                 flash_area_init(area_id), int area_id);

static int some_function(void)
{
    // Declare 'fa' with automatic cleanup
    scope_var(flash_area, fa)(PARTITION_ID(storage_partition));
    if (fa == NULL) {
        return -EINVAL;  // Exit function is still called
    }

    // Use fa normally
    printk("Has driver: %d\n", flash_area_has_driver(fa));

    // No need to manually close - exit function is called automatically
    return 0;
}
```

即使打开 Flash 区域失败、`fa == NULL` 并提前返回，退出函数仍会调用，因此示例退出函数显式检查空指针。

> 译注：原例 Flash 区域指针未加 `const`。本地核对的 `flash_area_open(uint8_t id, const struct flash_area **fa)` 要求指向只读区域描述符的指针，实际封装应统一使用相容类型；`PARTITION_ID(storage_partition)` 也需由项目提供有效定义。原文示例保留，不视作已经编译通过。

### 49.2.2\_作用域守卫

用 `SCOPE_GUARD_DEFINE` 定义获取和释放动作。下列互斥量守卫已由 `<zephyr/cleanup/kernel.h>` 提供；`scope_guard(k_mutex)` 获取锁并持有至当前包围作用域结束：

```c
// Example guard definition (already provided by <zephyr/cleanup/kernel.h>)
SCOPE_GUARD_DEFINE(k_mutex, struct k_mutex *,
                   (void)k_mutex_lock(_T, K_FOREVER),
                   (void)k_mutex_unlock(_T));

static K_MUTEX_DEFINE(lock);

void critical_section(void)
{
    scope_guard(k_mutex)(&lock);

    // Lock is held here
    // Perform critical operations

    // Lock is automatically released when guard goes out of scope
}
```

### 49.2.3\_紧随代码块的守卫

`scoped_guard` 仅绑定紧随其后的花括号代码块，一离开该块就释放资源，而 `scope_guard` 持有至外层作用域结束。这样可把短临界区与锁对象写在一起：

```c
static K_MUTEX_DEFINE(lock);

void worker(void)
{
    // ... work that does not need the lock ...

    scoped_guard(k_mutex, &lock) {
        // lock held only inside these braces
    }
    // lock released here

    // ... more work without the lock held ...
}
```

代码块恰好执行一次，任何退出方式，包括 `break`、`return` 和向外跳转的 `goto`，都会释放锁。特别注意：这里的 `continue` 也离开该块，行为像 `break`，不会重新执行代码块。

### 49.2.4\_条件守卫

原文前述普通守卫以 `K_FOREVER` 阻塞获取锁。要表示可能失败的获取，例如 `K_NO_WAIT` 尝试锁，使用 `SCOPE_COND_GUARD_DEFINE` 与 `scoped_cond_guard`。

获取表达式用于判断成功；失败时守卫保存 `NULL`，执行指定失败语句，并跳过代码块。以下 `k_mutex_try` 守卫也已由 `<zephyr/cleanup/kernel.h>` 提供：

```c
// Example guard definition (already provided by <zephyr/cleanup/kernel.h>)
SCOPE_COND_GUARD_DEFINE(k_mutex_try, struct k_mutex *,
                        k_mutex_lock(_T, K_NO_WAIT) == 0,
                        (void)k_mutex_unlock(_T));

static K_MUTEX_DEFINE(lock);

int try_critical_section(void)
{
    scoped_cond_guard(k_mutex_try, return -EBUSY, &lock) {
        // runs only if the lock was acquired
        // released automatically when the block is exited
    }

    return 0;
}
```

失败语句可以是 `break`、`return -EBUSY`，也可以用 `{}` 静默跳过代码块。

> 译注：普通宏本身执行开发者给定的获取表达式；“总会获取成功、以 `K_FOREVER` 等待”描述的是这里的锁守卫用法。自定义获取操作若可能失败，应设计为条件守卫，不能忽略错误后仍按成功路径释放。

### 49.2.5\_作用域延后操作

`SCOPE_DEFER_DEFINE` 为退出时执行的清理函数定义包装，`scope_defer` 在当前作用域登记操作：

```c
// Define a defer for a custom cleanup function
static void cleanup_resources(void)
{
    // Cleanup code here
}

SCOPE_DEFER_DEFINE(cleanup_resources);

void some_function(void)
{
    scope_defer(cleanup_resources)();

    // Do work...

    // cleanup_resources() is called automatically
}
```

函数有参数时，在定义中声明参数类型，登记时提供值。以下 `k_free` 包装已经由 `<zephyr/cleanup/kernel.h>` 提供：

```c
// Example deferred k_free (already provided by <zephyr/cleanup/kernel.h>)
SCOPE_DEFER_DEFINE(k_free, void *);

void allocate_and_use(void)
{
    void *ptr = k_malloc(100);
    scope_defer(k_free)(ptr);

    // Use ptr...

    // k_free(ptr) is called automatically
}
```

> 译注：原例未检查 `k_malloc()` 结果；实际使用 `ptr` 前仍必须检查分配是否成功。自动释放不代替分配错误处理。

## 49.3\_清理顺序与作用域规则

清理按声明的逆序执行，即**后进先出（Last In, First Out，LIFO）**，符合资源嵌套的自然顺序。下面先获得互斥量，再登记内存释放，因此退出时先释放内存，再解锁：

```c
{
    scope_guard(k_mutex)(&lock);           // Acquired first
    void *ptr = k_malloc(100);
    scope_defer(k_free)(ptr);              // Registered second

    // Do work...

}  // ptr is freed first, then mutex is unlocked
```

清理在变量离开作用域时发生，包括到达代码块末尾、提前 `return`、循环中的 `break` / `continue` 导致离开该变量作用域，以及 `goto` 跳出作用域。下面展示提前返回与正常返回都释放锁：

```c
void example_with_early_exit(struct k_mutex *lock)
{
    scope_guard(k_mutex)(lock);

    if (error_condition) {
        return;  // Guard cleanup happens here
    }

    // Normal path

}  // Guard cleanup also happens here
```
