# 第7章\_工作队列线程

原文：[Workqueue Threads](https://docs.zephyrproject.org/latest/kernel/services/threads/workqueue.html)。读取日期：2026-10-12，`latest`。

**工作队列（Workqueue）**是使用专用线程、按先进先出顺序处理工作项的内核对象。线程逐项调用工作项指定的处理函数。**中断服务例程（Interrupt Service Routine，ISR）** 或高优先级线程常用它把不紧急的工作交给较低优先级线程，避免干扰时间敏感处理。

队列数量仅受可用 **随机存取存储器（Random Access Memory，RAM）** 等资源限制，通过内存地址引用。每个队列包含待处理项列表及处理线程，线程可配置为协作或可抢占优先级。原文说明工作项之间会主动 yield，避免协作队列饿死其他线程；相关行为还受后文所列配置控制。

使用前需初始化空队列并启动线程。线程持续存在，没有工作时休眠。

## 7.1\_工作项生命周期

每个工作项通过地址引用，并关联一个处理函数。处理函数唯一参数是工作项自身地址；工作项还保存内部状态。初始化时记录函数并标为未挂起。

线程或 ISR 提交后，工作项进入 `K_WORK_QUEUED` 状态并追加到队尾。队列线程处理完前面的项后取出它并调用函数。实际等待时间取决于队列线程优先级及前面工作量，可能很短，也可能很长。

可延迟项还可处于 `K_WORK_DELAYED`；执行中为 `K_WORK_RUNNING`；若已经执行后又有人请求取消，可能同时为 `K_WORK_CANCELING`。

这些状态可以并存，例如一个项正在执行、因 `k_work_cancel_sync()` 被标为取消中、已经再次排队，并且还安排了未来向同一或其他队列提交。`k_work_is_pending()`、`k_work_busy_get()` 用于查询挂起或忙状态，但只是瞬时快照。

处理函数可以使用线程可用的内核 **应用程序编程接口（Application Programming Interface，API）**，但阻塞操作必须谨慎：当前函数不结束，队列就不能处理后续项。

若不需要参数可以忽略；需要附加数据时，把 `k_work` 嵌入更大结构，再用 `CONTAINER_OF` 从传入地址找回外层结构。

通常工作项只初始化一次，每次需要工作就提交。已经排队的项再次提交不会改变队列位置，也不会额外执行一次。处理函数可以重新提交自身，因为执行时已不在待处理队列；这样可分阶段完成工作，给其他项机会。

**忙碌工作项不得重新初始化。** 工作项正在被处理时，处理函数需要的附加信息也不得未经同步就修改，应等其完成。

## 7.2\_可延迟工作

线程或 ISR 可以安排未来再提交，而非立即排队。可延迟项包含普通工作项，并增加提交时间及目标队列信息。

初始化和安排使用专用 API。内核先等待超时，到期后才把普通工作项放入目标队列，随后仍按普通队列顺序处理；因此“延迟到期”不等于“处理函数立即开始”。

处理函数接收的仍是底层 `struct k_work *`。不要直接依赖 `k_work_delayable` 的内部布局，应先转换，再找外层上下文：

```c
static void work_handler(struct k_work *work)
{
        struct k_work_delayable *dwork = k_work_delayable_from_work(work);
        struct work_context *ctx = CONTAINER_OF(dwork, struct work_context,
                                                timed_work);
        ...
```

> 译注：原文片段在省略号后没有展示函数结束的 `}`；实际代码须补齐，并定义包含 `timed_work` 成员的 `work_context`。

## 7.3\_事件触发工作

`k_work_poll_submit()` 安排由 [Polling API 事件](https://docs.zephyrproject.org/latest/kernel/services/polling.html)触发的工作：资源可用、poll 信号产生或超时后，调用用户处理函数。与 `k_poll()` 不同，它不需要应用专门占一个线程等待或主动轮询。

触发项在普通工作项之外保存 poll 事件数组指针及数组长度。提交时开始观察这些事件对应的内核对象；至少一个对象发生所关注的状态变化后，将工作项放入目标队列，按普通方式执行。

从提交到执行或取消的完整生命周期内，工作项和事件数组都必须保持有效，不能修改。

线程或 ISR 只能在它仍等待 poll 事件时取消。成功取消后停止观察，不再执行该工作；超过这个阶段则不能按这种方式取消。

## 7.4\_系统工作队列与自定义队列

内核提供系统工作队列，供应用和内核代码共享；只有应用使用相关功能时才需要它。

额外队列有显著内存成本，应只在系统队列无法满足要求时创建。例如新工作会阻塞并不可接受地拖慢其他系统工作，这时独立队列有理由存在。

系统队列默认使用最低协作优先级，因此处理其工作先于所有可抢占线程。把系统队列改为可抢占优先级有风险，因为驱动和子系统可能隐式依赖协作上下文；低优先级任务可考虑使用独立低优先级队列。

### 7.4.1\_定义并启动队列

定义 `struct k_work_q`、线程栈，并清零队列或调用 `k_work_queue_init()`，最后调用 `k_work_queue_start()`。栈应使用适当栈宏，这里按原例采用 `K_THREAD_STACK_DEFINE`：

```c
#define MY_STACK_SIZE 512
#define MY_PRIORITY 5

K_THREAD_STACK_DEFINE(my_stack_area, MY_STACK_SIZE);

struct k_work_q my_work_q;

k_work_queue_init(&my_work_q);

k_work_queue_start(&my_work_q, my_stack_area,
                   K_THREAD_STACK_SIZEOF(my_stack_area), MY_PRIORITY,
                   NULL);
```

最后的可选参数还可控制队列身份及部分线程重调度行为，详见 API。

### 7.4.2\_排空与禁止新提交

`k_work_queue_drain()` 阻塞调用者直到队列没有待处理项。排空期间，来自队列线程自身的重新提交仍被接受，其他线程或 ISR 的提交被拒绝。

还可让排空后继续保持禁止提交（plugged），便于调用者执行额外操作。`k_work_queue_unplug()` 解除这种限制。

排空不改变可延迟项的计时和调度。但如果其到期时队列仍 plugged，这次提交会静默失败，不能假设排空动作同时取消或保留了全部延迟工作。

## 7.5\_提交普通工作项

定义 `struct k_work` 后调用 `k_work_init()`，或用 `K_WORK_DEFINE` 在编译期初始化。`k_work_submit()` 提交到系统队列，`k_work_submit_to_queue()` 提交到指定队列。

以下把 ISR 中错误信息的打印交给系统线程。如果它已经排队，ISR 再次提交不会为第二次错误新增打印任务：

```c
struct device_info {
    struct k_work work;
    char name[16]
} my_device;

void my_isr(void *arg)
{
    ...
    if (error detected) {
        k_work_submit(&my_device.work);
    }
    ...
}

void print_error(struct k_work *item)
{
    struct device_info *the_device =
        CONTAINER_OF(item, struct device_info, work);
    printk("Got error on device %s\n", the_device->name);
}

/* initialize name info for a device */
strcpy(my_device.name, "FOO_dev");

/* initialize work item for printing device's error messages */
k_work_init(&my_device.work, print_error);

/* install my_isr() as interrupt handler for the device (not shown) */
...
```

> 译注：原文 `char name[16]` 后缺少分号；`error detected` 和省略号是示意，初始化语句应放入实际函数。这里用固定设备名演示找回外层结构，不表示多个错误事件都会被逐一保存。

相关状态和同步接口如下：

| 接口 | 作用 |
| --- | --- |
| `k_work_busy_get()` | 返回状态标志快照；零表示没有被安排、排队、执行或仍由队列内部引用。 |
| `k_work_is_pending()` | 检查是否仍处于待处理的相关状态。原文在此概括为已安排、排队或执行。 |
| `k_work_flush()` | 在线程中等待工作完成；未挂起则立即返回。 |
| `k_work_cancel()` | 尝试阻止执行，不一定能成功，可从 ISR 调用。 |
| `k_work_cancel_sync()` | 在线程中等待取消/执行收尾；已成功取消或本来无需取消时立即返回。可在 ISR 发起异步取消后，用它确认真正结束。 |

## 7.6\_安排可延迟工作

定义 `struct k_work_delayable` 并用 `k_work_init_delayable()` 初始化。核心选择是：新事件到来时，是否延长原期限。例如从 **通用异步收发器（Universal Asynchronous Receiver-Transmitter，UART）** 收集键盘字符：

- `k_work_schedule()` 或 `k_work_schedule_for_queue()` 保持第一次安排的期限。延迟未结束前重复调用不改变提交时间，适合“从第一份未处理数据到达起，最多再等一段时间”。
- `k_work_reschedule()` 或 `k_work_reschedule_for_queue()` 无条件替换未完成延迟，必要时也替换目标队列，适合“从最后一份未处理数据到达起，再等一段时间”。

原先没有安排时，两者效果相同。延迟为 `K_NO_WAIT` 时等同直接提交，不再等最小超时；但 `schedule()` 遇到尚未结束的既有延迟，仍保持原安排。

处理函数可用 `k_work_delayable_from_work()` 找回可延迟对象。对应操作包括 `k_work_delayable_busy_get()`、`k_work_delayable_is_pending()`、`k_work_flush_delayable()`、`k_work_cancel_delayable()` 和 `k_work_cancel_delayable_sync()`。

## 7.7\_等待工作完成或取消

普通和可延迟项的状态都可从任意上下文查询，但查询不能代替同步。在线程上下文需要等到确定状态时，使用 `k_work_flush()`、`k_work_cancel_sync()`、`k_work_cancel_delayable_sync()`。

这些接口需要 `struct k_work_sync` 对象提供内部同步存储，应用不应检查其内部成员。若代码要支持 `CONFIG_KERNEL_COHERENCE` 架构，该同步对象不应分配在线程栈上。

## 7.8\_避免数据竞争

有些数据天然通过线程安全通道传递，例如其他线程放入 `k_queue`、工作线程取出。但通常还需保护共享标志或由 ISR 写入、工作函数读取的对象。

简单标志可使用原子操作，复杂情况可用自旋锁、信号量或互斥锁。若锁可能让线程睡眠，工作线程阻塞会饿住其他项，而后者可能正是释放锁所需的处理。因此工作函数应优先采用不等待的获取路径：

```c
static void work_handler(struct work *work)
{
        struct work_context *parent = CONTAINER_OF(work, struct work_context,
                                                   work_item);

        if (k_mutex_lock(&parent->lock, K_NO_WAIT) != 0) {
                /* NB: Submit will fail if the work item is being cancelled. */
                (void)k_work_submit(work);
                return;
        }

        /* do stuff under lock */
        k_mutex_unlock(&parent->lock);
        /* do stuff without lock */
}
```

> 译注：原文参数类型写成 `struct work *`，实际工作项类型应为 `struct k_work *`。

如果锁由比工作队列更低优先级的线程持有，立即重新提交可能持续抢占它，使持锁线程永远无法释放。需要这种重试模式时，优先用可延迟工作，并设置非零重试间隔，让持锁线程有机会运行。

工作函数内的重新提交可能因正在取消而失败。通常可以接受，因为函数返回后取消完成；若业务不能接受，则必须另行通知应用工作没有完成。

工作项内部操作有自己的锁，仅为 submit/schedule 无须再加外锁。即使外部受锁状态用于禁止继续提交，只要工作函数最终会加锁检查该状态并决定是否处理，再提交本身仍可安全。

但若处理函数因拿不到锁而重新安排延迟，还需要独立可安全访问的取消状态，例如应用/驱动发起取消时设置原子标志，以防已经取消的工作在新期限到来后又被重新提交。

## 7.9\_检查返回结果

应检查工作队列操作是否达到预期。提交可能因工作正在取消或队列不接收新项而失败；若忽略，依赖处理函数推进的子系统可能不再响应。

异步取消返回时，处理函数可能仍在执行。这时立即修改其共享状态会形成竞争。Zephyr 中曾有多种问题来自忽略操作结果。

确实可以忽略某个失败时，应同时显式强转为 `void`，并用注释说明失败后的安全行为。例如：

```c
/* If this fails, the work handler will check pub->active and
 * exit without transmitting.
 */
(void)k_work_cancel_delayable(&pub->timer);
```

该例说明取消失败时处理函数会检查 `pub->active` 并不发送数据。但后续代码仍须保护共享状态，因为不能据此断言工作线程已经停止访问它。

## 7.10\_不要先查状态再决定是否提交

队列 API 已设计为可从多个线程和中断安全调用。外部先检查状态再决定动作，很容易新增竞争。

新工作到来时直接提交，不要用 `k_work_is_pending()`、`k_work_busy_get()` 或 `k_work_delayable_remaining_get()` 的快照“优化”。返回 busy 后状态可能立刻改变；返回不忙时，其他上下文也可能已经提交；延迟为零也不代表工作不在队列中或没有执行。

通常应在受保护的共享状态中保存“是否真的有工作”这一条件，由处理函数检查并完成处理或清理。这样可以把清理路径集中到处理函数，而不是在每个提交位置处理取消和资源回收。

少数可安全使用 pending 快照的情况，是已经确定检查期间绝无其他提交者，例如持有保护提交条件的锁，并据此省去不必要的 flush 或同步取消。

## 7.11\_用途与配置

系统队列适合把复杂中断后处理交给共享线程，既及时推进工作，又不妨碍后续中断响应，也免去应用自行创建管理额外线程。

相关配置为 `CONFIG_SYSTEM_WORKQUEUE_STACK_SIZE`、`CONFIG_SYSTEM_WORKQUEUE_PRIORITY`、`CONFIG_SYSTEM_WORKQUEUE_NO_YIELD`。完整接口见[官方 Work Queue APIs](https://docs.zephyrproject.org/latest/doxygen/html/group__workqueue__apis.html)。
