# 第40章\_用户模式内核对象

原文：[Kernel Objects](https://docs.zephyrproject.org/latest/kernel/usermode/kernelobjects.html)。读取日期：2026-10-12，`latest`。

## 40.1\_对象类别与不透明性

**内核对象（Kernel Object）**包括三类：信号量、线程、管道等核心对象；用 `K_THREAD_STACK_DEFINE()` 声明、元素为 `z_thread_stack_element` 的线程栈；属于已知子系统的设备实例 `const struct device`。已知对象与驱动子系统集合由 [`include/zephyr/sys/kobject.h`](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/sys/kobject.h) 中的 `k_objects` 定义。

内核对象对用户线程是不透明的。用户线程可把对象地址传给接口，但不能直接解引用内部字段，否则会触发内存保护故障。对象须位于用户不能直接访问的内存中。

用户操作经系统调用完成，处理函数检查地址是否对应有效对象，以及调用线程是否具有权限。

对象权限还具有“引用”的意义，影响会分配临时缓冲区的对象和运行时动态对象。对象失去全部引用后，可能调用其清理函数释放运行时缓冲区；若对象本身动态分配，还会释放对象存储。

## 40.2\_对象放置

仅监督线程使用的对象可以位于二进制中任意合适位置，甚至声明在栈上；但仍不能放到用户可直接访问的区域，以防篡改。

静态对象若要让用户线程经系统调用使用，必须满足以下条件：

- 构建时以顶层全局对象声明，使其出现在 **可执行与可链接格式（Executable and Linkable Format，ELF）** 符号信息中；允许 `static` 作用域，也允许数组元素或嵌入其他结构体。`scripts/build/gen_kobject_list.py` 扫描 ELF，把地址纳入对象元数据表。
- 位于内核保留内存，不可处于用户可访问分区。
- 该存储必须专供这个对象，不能把内核对象放在 union 中与其他成员复用。

被找到却不满足条件的对象，不会进入用户传入指针的验证表。排查漏登记时，可用脚本 `--verbose` 或构建系统详细输出观察扫描结果。

## 40.3\_动态对象

启用 `CONFIG_DYNAMIC_OBJECTS` 后，`k_object_alloc()` 可从调用线程资源池在运行时创建对象。释放有两种途径：监督线程调用 `k_object_free()` 强制释放；或当所有线程都失去该对象权限、引用数为 0 时自动释放。

用户线程可用 `k_object_release()` 放弃自己的权限，线程终止时权限也会清除。监督线程还可用 `k_object_access_revoke()` 撤销别人的权限。

由于权限同时参与引用计数，监督线程即使不受访问控制限制，也应对正在使用的动态对象取得权限，避免对象因其他引用消失而自动释放。

### 40.3.1\_实现细节

对象生成脚本解析 ELF 中的 DWARF 调试信息，寻找符合放置规则的对象结构或数组，并通过 gperf 生成完美哈希表。系统调用拿到一个地址后，可用常量时间查找判断它是不是合法静态对象。

设备实例都使用 `struct device`，还需按其 **应用程序编程接口（Application Programming Interface，API）** 指针识别子系统，避免把传感器对象错误交给 **通用异步收发器（Universal Asynchronous Receiver-Transmitter，UART）** 接口等操作。

对象地址映射到 `z_object` 元数据，包含权限位图、`k_objects` 类型、初始化/公开状态标志，以及含义随对象类型变化的 `z_object_data` 附加数据。

原文说明线程数值 ID 用于索引权限位图，位图容量由 `CONFIG_MAX_THREAD_BYTES` 控制，容量不足会使构建失败。动态对象则放在运行时红黑树中，验证时与静态 gperf 表配合使用。

> 译注：原文“所有线程 ID 都在构建时分配”的措辞主要描述静态元数据基础，不能据此否定本页已经说明的动态对象/线程能力；运行时分配与可用 ID 上限应以目标实现为准。

## 40.4\_监督线程的权限

监督线程能访问任意内核对象，但仍跟踪其权限。除了动态对象引用计数外，还有两个用途：调用 `k_thread_user_mode_enter()` 降到用户模式后，保留此前授予的权限；创建带 `K_INHERIT_PERMS` 的子线程时，子线程继承父线程权限，除了父线程对象本身。

## 40.5\_用户线程的授权与撤销

新用户线程默认只对自身线程对象有权限，其他对象需显式或隐式授权。

`K_INHERIT_PERMS` 让创建的线程继承父线程对象权限集合，但不继承父线程对象。`k_object_access_grant()` 可向另一线程授予单个对象；便利接口 `k_thread_access_grant()` 接收多个对象指针并逐个授权。

授权时，目标线程与被授权对象无需已初始化。若授权者处于用户模式，则必须同时拥有被授权对象与目标线程对象权限；监督模式授权者不受该限制。

监督线程可通过 `k_object_access_all_grant()` 把对象设为公开，使当前及未来全部线程都可使用。原文强调此后应假定任何不可信或被攻破的代码都能操作它，必须谨慎选择。

静态 `K_THREAD_DEFINE()` 线程可以配合 `K_THREAD_ACCESS_GRANT()` 在启动时授予一组对象权限。

`k_object_access_revoke()` 撤销授权，只供监督线程使用；用户线程可用 `k_object_release()` 放弃自己的权限。

`k_object_access_revoke_others()` 撤销除调用者之外所有线程的权限，也清除此前设置的公开状态。它适合重置曾授予不可信线程、而该线程可能又转授他人的对象权限。

监督线程试图为未被内核跟踪的对象设置权限时，操作无效果；用户线程做同样操作会触发致命错误。通过 `k_object_alloc()` 分配时，调用者自动得到新对象权限。

## 40.6\_初始化状态

对象未初始化时，大部分操作会失败，须先执行相应 init。静态初始化宏（如 `K_SEM_DEFINE`）声明的对象，在构建状态信息中已标记初始化；设备对象在内核启动阶段运行其初始化函数后被视为已初始化。

若通过私有静态初始化器初始化对象，监督线程还须在适当时机调用 `k_object_init()`，否则用户访问时仍可能被认为未初始化。这较少见，通常是对象嵌入大结构并静态初始化的情况：

```c
struct foo {
    struct k_sem sem;
    ...
};

struct foo my_foo = {
    .sem = Z_SEM_INITIALIZER(my_foo.sem, 0, 1),
    ...
};

...
k_object_init(&my_foo.sem);
...
```

> 译注：这里的 `k_object_init()` 标记对象跟踪状态，不能代替具体对象类型本身所需的数据初始化。示例前面已经用专用初始化器设置嵌入信号量。

## 40.7\_新增对象类型

实现新内核功能或驱动子系统时，可能需要新增可跟踪对象类型。

核心对象：在 `scripts/build/gen_kobject_list.py` 的 `kobjects` 列表中加入结构体名称，满足规则的实例随后会被扫描跟踪。

驱动子系统：设备仍是 `struct device`，按 API 结构区分；在同一脚本的 `subsystems` 列表加入新 API 结构名称，随后可识别该子系统实例。

## 40.8\_配置与接口

原文相关配置列为 `CONFIG_USERSPACE`、`CONFIG_MAX_THREAD_BYTES`，动态对象一节另要求 `CONFIG_DYNAMIC_OBJECTS`。完整接口见[User Mode APIs](https://docs.zephyrproject.org/latest/doxygen/html/group__usermode__apis.html)。
