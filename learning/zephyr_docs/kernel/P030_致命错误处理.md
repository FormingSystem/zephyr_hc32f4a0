# 第30章\_致命错误处理

原文：[Fatal Errors](https://docs.zephyrproject.org/latest/kernel/services/other/fatal.html)。读取日期：2026-10-12，`latest`。

## 30.1\_源码主动触发的错误

Zephyr 提供构建时检查、条件编译的运行时断言，以及主动调用的 panic、oops 等错误检测或处理机制。`ZASSERT()` 和旧的 `__ASSERT()` 运行时断言失败会触发**致命错误（Fatal Error）**，配置与具体接口见[断言](P031_断言.md)。

### 30.1.1\_内核oops

`k_oops()` 主动触发软件致命错误，用于表示应用逻辑遇到不可恢复情况，原因码为 `K_ERR_KERNEL_OOPS`。

### 30.1.2\_内核panic

`k_panic()` 表示 Zephyr 内核本身已处于不可恢复状态。遇到 panic 后，`k_sys_fatal_error_handler()` 实现不应返回，因为整个系统需要复位。

用户模式线程不允许调用 `k_panic()`；若这样做，会转为 kernel oops。正常内核 panic 的原因码为 `K_ERR_KERNEL_PANIC`。

## 30.2\_异常

硬件中断和处理器异常也可能进入致命错误处理，具体原因如下。

### 30.2.1\_杂散中断

若某中断线没有通过 `IRQ_CONNECT()` 或 `irq_connect_dynamic()` 安装处理函数，处理器却收到该线的硬件中断，内核会报告 `K_ERR_SPURIOUS_IRQ`。

> 译注：原文将该原因码写成 `K_ERR_SPURIOUS_IRQ()`，它是错误原因标识，不是需要调用的函数。

### 30.2.2\_线程栈溢出

线程压入的数据超出栈缓冲区容量时，内核可能检测到并报告 `K_ERR_STACK_CHK_FAIL`。

用户模式下，线程无权写入栈缓冲区外没有权限的相邻内存，溢出由内存保护硬件捕获；原文强调不会因此破坏该线程原本无权写入的区域。

监督模式线程，或未启用 `CONFIG_USERSPACE` 时，能否捕获取决于配置。某些架构支持 `CONFIG_HW_STACK_PROTECTION`，可检测监督模式栈溢出，也包括替用户线程执行系统调用的阶段。通常通过专用处理器功能，或紧邻栈的 **内存管理单元（Memory Management Unit，MMU）**/**内存保护单元（Memory Protection Unit，MPU）** 只读保护区实现。检测到溢出不等于保证没有其他数据破坏，应视为影响整个系统健康的严重情况。

缺少内存管理硬件时，可启用 `CONFIG_STACK_SENTINEL`，定期检查栈末尾哨兵值是否被改写。它不需要硬件，但不能阻止数据损坏；检查通常在中断退出时进行，可能在实际溢出一段时间之后才发现。

`CONFIG_STACK_CANARIES` 启用 GCC 栈金丝雀机制：编译器在函数栈帧中放入启动时随机生成的值，函数退出时检查是否被覆盖。失败则调用 `__stack_chk_fail()`，Zephyr 实现由此触发栈相关致命错误。它表示当前函数栈帧被破坏，不必然意味着整个线程栈已超出边界。

默认所有线程共享启动时生成的一个金丝雀值。启用 `CONFIG_STACK_CANARIES_TLS` 后，值存入[线程局部存储](P033_线程局部存储.md)，每个线程拥有自己的值，以额外的每线程初始化开销换取更难预测的位置和值。

`CONFIG_STACK_POINTER_RANDOM` 是补充加固措施，在线程创建时随机偏移初始栈指针，形成有限的地址布局随机化，让栈帧位置不再固定。代价是每个线程的可用栈最多减少所配置的字节数。

### 30.2.3\_其他异常

其他未处理的处理器异常报告 `K_ERR_CPU_EXCEPTION`。

## 30.3\_致命错误策略

`k_sys_fatal_error_handler()` 决定遇到致命错误后采取什么策略。默认弱链接实现先调用 `LOG_PANIC()` 输出所有待处理日志，再用 `k_fatal_halt()` 无条件停止系统。

应用可覆盖该函数实现自定义策略。若处理函数返回，故障线程会被终止，其余系统继续运行；具体约束见[致命错误 API](../fatal_irq_reference/P001_致命错误处理接口.md)。

> 译注：返回并继续执行不是所有错误都适用的恢复保证；尤其前文所述 kernel panic 不允许按这种方式继续，栈损坏等情况也必须判断系统状态是否仍可靠。
