# 第11章\_互斥量

原文：[Mutexes](https://docs.zephyrproject.org/latest/kernel/services/synchronization/mutexes.html)。读取日期：2026-10-12，`latest`。

**互斥量（Mutex）**是实现传统可重入互斥锁的内核对象。它保证对相关硬件或软件资源的互斥访问，使多个线程能够安全共享资源。

## 11.1\_概念与生命周期

互斥量数量只受可用内存等资源限制，每个对象通过内存地址引用。它有两个关键属性：加锁计数记录拥有者重复加锁的次数，0 表示未锁定；拥有者线程标识当前锁定它的线程。

使用前必须初始化互斥量，将加锁计数设为 0。线程使用共享资源前，应锁定对应互斥量以取得独占访问权。如果锁由其他线程持有，请求者可以选择等待解锁。

获得锁后，线程可以按需使用资源。不过应尽可能缩短持锁时间，减少对其他需要该资源的线程的影响。不再需要资源时，必须解锁，让其他线程能够访问。

互斥量仍被锁定或还有线程等待时，**不得释放对象或复用其内存**。动态分配对象中内嵌的互斥量必须在释放对象前解锁，否则拥有者还会追踪已经不属于该对象的内存。

可以有多个线程等待同一个已锁定互斥量。锁变为可用后，优先由最高优先级线程获得；同优先级时，由等待最久者获得。

互斥量不用于**中断服务例程（Interrupt Service Routine，ISR）**。

## 11.2\_可重入加锁

线程可以再次锁定自己已经持有的互斥量。这样，当执行到一段需要访问共享资源的代码时，不必要求该线程此前一定已加锁或一定未加锁。

重复加锁后，必须执行相同次数的解锁，互斥量才会完全释放并允许其他线程取得。

## 11.3\_优先级继承

持有互斥量的线程可以获得优先级继承：如果更高优先级线程开始等待该锁，内核会暂时提高拥有者优先级，使它能按等待者的优先级执行，尽快完成工作并释放锁。锁释放后，恢复过程会考虑线程其余持锁情况。

Kconfig 选项 `CONFIG_PRIORITY_CEILING` 限制继承所能提升到的最高优先级。原文当前默认值 `-128` 表示不施加额外限制；若设为与空闲线程相同或更低的优先级，就禁用继承提升。

线程第一次因互斥量被提升时，其提升前优先级保存在自身对象中；它持有的每个互斥量也在每线程链表中跟踪。更高优先级线程等待时，内核调整拥有者优先级。拥有者释放一个锁，或高优先级等待者超时后，内核重新扫描它仍持有的互斥量，按其中仍在等待的最高优先级重新计算；若没有等待者，就回到线程原始优先级。因此，按照当前原文描述，无论以何种顺序释放多个锁，都能正确恢复。

如果拥有者本身也在等待另一个互斥量，优先级提升会沿拥有关系链继续传播，使阻碍该等待者前进的线程依次得到提升。每次加锁尝试所遍历的链长度有实现定义的上限；超出上限的拥有者保持原优先级，直到后续加锁尝试再次遍历到它们。

> 译注：这里忠实保留读取时 `latest` 页面的多锁重算与继承链传播行为。旧版 Zephyr 的互斥量实现及限制可能不同，不能把本节当作所有历史版本的保证。具体优先级数值仍按目标构建的线程优先级配置解释。

## 11.4\_定义互斥量

使用 `struct k_mutex` 类型定义，再调用 `k_mutex_init()` 初始化：

```c
struct k_mutex my_mutex;

k_mutex_init(&my_mutex);
```

也可使用 `K_MUTEX_DEFINE` 宏在编译时定义并初始化，效果相同：

```c
K_MUTEX_DEFINE(my_mutex);
```

## 11.5\_加锁与解锁

调用 `k_mutex_lock()` 加锁。下面在锁被其他线程持有时无限等待：

```c
k_mutex_lock(&my_mutex, K_FOREVER);
```

下面最多等待 100 毫秒；未获得锁时输出警告：

```c
if (k_mutex_lock(&my_mutex, K_MSEC(100)) == 0) {
    /* mutex successfully locked */
} else {
    printf("Cannot lock XYZ display\n");
}
```

当前线程用 `k_mutex_unlock()` 释放它此前取得的锁：

```c
k_mutex_unlock(&my_mutex);
```

## 11.6\_用途、配置与接口

互斥量用于提供资源的独占访问，例如保护一个物理设备。相关配置为前述 `CONFIG_PRIORITY_CEILING`。完整接口见[Mutex APIs](../synchronization_reference/P006_互斥量公共接口.md)。

相关[哲学家就餐示例](../basic_samples/P030_哲学家就餐示例.md#dining-philosophers)使用 Zephyr 内核服务实现该同步问题的一种解法。

## 11.7\_Futex与用户模式互斥量

`k_futex` 是尽量减少内核参与的轻量互斥原语。无竞争操作只依赖共享内存的原子访问。它不是内核对象，不使用内核对象权限管理；对象位于用户内存，任何对该内存有读写权限的线程都能使用。详见[FUTEX APIs](../userspace_sync_reference/P001_Futex公共接口.md)。

`sys_mutex` 行为几乎与 `k_mutex` 一样，同时允许实例放在用户内存中。未启用用户模式时，它的行为与 `k_mutex` 相同。详见[用户模式互斥量 API](../userspace_sync_reference/P003_用户模式互斥量公共接口.md)。

> 译注——当前用户模式实现：本次官方源码中的sys_mutex加锁／解锁仍通过内核接口操作关联的k_mutex；头文件所说的无竞争原子快速路径是未来增强。CONFIG_USERSPACE下sys_mutex_init本身不创建底层对象。完整条件分支及地址识别规则见[用户模式互斥量参考](../userspace_sync_reference/P003_用户模式互斥量公共接口.md)。
