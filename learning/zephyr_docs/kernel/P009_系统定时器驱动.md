# 第9章\_系统定时器驱动

原文：[System Timer Drivers](https://docs.zephyrproject.org/latest/kernel/services/timing/system_timer_drivers.html)。读取日期：2026-10-12，`latest`。

本页说明内核的**计时节拍（Tick）**记账与产生这些 tick 的硬件驱动之间的接口。内核侧的记账方式及应用可见行为见[内核计时](P008_内核计时.md)。tick 是内核计时单位，**硬件计数周期（Cycle）**则是硬件时间源的计数单位，两者不能直接互换。

> 译注：以下按当前官网完整翻译，包含统一时钟锁、空闲钩子与通用 tickless 核心等接口。采用这些设计前应核对目标 Zephyr 版本中的声明与实现；本文不表示 F 盘仓库已经包含或移植了全部新接口。

## 9.1\_定时器驱动的基本职责

内核 tick 层的计时由定时器驱动推动，其接口相对简单。

驱动通过 `sys_clock_announce()` 向内核报告新增 tick，参数为自上一次报告或系统启动以来经过的完整 tick 数。报告可以发生在任何时刻，但在中断延迟等因素允许的范围内，应尽量靠近 tick 边界，而不是落在 tick 中途。最关键的是长期计数正确，相对其他计数器和现实时间的偏差尽量小。

驱动提供 `sys_clock_set_timeout()`，供内核告知：最多还可经过多少 tick，就必须收到报告以触发已经注册的超时。可以提前报告，只要计数正确；晚于期限则会错过事件。传入值相对当前时刻，但这不免除驱动保持长期 tick 速率稳定的责任。简单实现若错误地把不足一个 tick 的余量重置，会引起时钟漂移。

驱动还提供 `sys_clock_elapsed()`，返回从最近一次 `sys_clock_announce()` 起，按实际时间已经经过多少 tick。内核用它检查新到达的超时请求是否已经到期。

## 9.2\_没有超时与进入低功耗空闲

驱动可以实现可选函数 `sys_clock_no_timeout()`。当超时队列为空且启用 Kconfig 选项 `CONFIG_SYSTEM_CLOCK_SLOPPY_IDLE` 时，内核用它代替 `sys_clock_set_timeout()`。此时没有即将到来的 tick 报告要求，系统不要求精确维护运行时间，驱动可采取节省资源的措施。下一次 `sys_clock_set_timeout()` 恢复正常操作；它不同于 `sys_clock_disable()`，不是拆除或关闭驱动。

这里**不得停止定时器计数器**。`sys_clock_cycle_get_32()` 和 `sys_clock_cycle_get_64()` 必须继续递增，好像该钩子没有被调用一样。

超时队列为空时，处理器仍可能运行就绪线程或响应中断。线程和**中断服务例程（Interrupt Service Routine，ISR）**仍可能调用 `k_cycle_get_32()`、`k_busy_wait()`。因此通常可以屏蔽定时器中断，但直接门控其时钟很可能不行；具体可行措施取决于硬件。

若未实现该钩子，内核向 `sys_clock_set_timeout()` 请求其能表达的最长等待，即 `UINT32_MAX` 个 tick。数值上它对应这里历史使用的 `K_TICKS_FOREVER`，因此未迁移的驱动仍能处理这一“无截止期限”信号。

驱动也可以实现 `sys_clock_idle_enter()`。电源管理路径在处理器即将进入低功耗空闲时，用它替代 `sys_clock_set_timeout()`；参数为到下次预期唤醒的 tick 数，若没有唤醒期限且允许运行时间记账漂移，则传 `SYS_CLOCK_IDLE_FOREVER`。

需要切换到低功耗唤醒定时器或重新配置硬件以便睡眠的驱动，应在这里处理。收到 `SYS_CLOCK_IDLE_FOREVER` 后，可以停止自己的时间基准。这比 `sys_clock_no_timeout()` 的权限更大，因为处理器即将休眠，并保证返回时调用 `sys_clock_idle_exit()`。只有发起调用的处理器进入空闲；多个处理器共享时间基准时，必须等最后一个处理器进入空闲后才能停止时钟。

若没有该钩子，内核仍调用 `sys_clock_set_timeout()`，把已弃用的 `idle` 参数设为 `true`，兼容仍依赖该参数处理低功耗的驱动。

三类入口对应以下四种状态：

| 系统状态 | 没有待处理超时 | 有待处理超时 |
| --- | --- | --- |
| 运行 | `sys_clock_no_timeout()` | `sys_clock_set_timeout(ticks)` |
| 空闲 | `sys_clock_idle_enter(SYS_CLOCK_IDLE_FOREVER)` | `sys_clock_idle_enter(ticks)` |

未启用 `CONFIG_SYSTEM_CLOCK_SLOPPY_IDLE` 时，不会出现左列：内核会维持一个合成截止期限，以保证运行时间准确，驱动只看到右列情形。

## 9.3\_定时器驱动锁

内核通过 `sys_clock_lock()`、`sys_clock_unlock()` 提供统一定时器锁。它同时保护内核 tick 记账状态（`curr_tick`、超时队列），以及必须与之保持一致的驱动私有状态，例如硬件周期计数器的基准值。

维护内部状态的驱动应在 ISR 开始时获得该锁，更新硬件状态，再把锁 key 交给 `sys_clock_announce_locked()`；后者会接管并消耗该 key。这样，驱动周期基准与内核 `curr_tick` 始终在同一把锁下更新，避免分开使用两把锁时的竞态。这对**对称多处理（Symmetric Multiprocessing，SMP）**尤其重要；在单处理器（Uniprocessor，UP）上，高优先级 ISR 需要一致实时基准时也可能遇到同类问题。

内核调用驱动的 `sys_clock_set_timeout()`、`sys_clock_elapsed()` 时，总是已经持有此锁。

为兼容旧驱动，`sys_clock_announce()` 仍保留，并在内部获取锁。新驱动和迁移后的驱动应优先使用 `sys_clock_lock()` 配合 `sys_clock_announce_locked()` 的模式。

## 9.4\_周期 tick 与无周期 tick

上述接口自然适用于无周期 tick（tickless）内核：依赖可编程硬件计数器产生不规则中断，仅为已注册事件接收和处理定时器中断。传统固定 tick 驱动也很容易实现：

1. 按操作系统 tick 频率定期接收中断，每次调用 `sys_clock_announce(1)`。
2. 可以忽略 `sys_clock_set_timeout()` 请求，因为无论有无超时，每个 tick 都会被报告。
3. `sys_clock_elapsed()` 可始终返回 0，因为该简单模型下若已经经过完整 tick，就应该收到相应中断，而不会再有额外未报告的完整 tick。

> 译注：第三点是原文所述简单周期驱动模型的条件，不可据此忽略实际硬件的长时间屏蔽中断、丢失中断或多 tick 累积问题。驱动仍须满足前述长期计时正确的职责。

## 9.5\_SMP细节

多处理器环境通常不改变接口。内核会同步内部访问并尽量缩小临界区，但还需注意以下事项。

- Zephyr 不规定由哪个处理器服务定时器中断。把全部定时器中断交给一个处理器并不违法，虽然某些情况下并不理想。已有 SMP 架构采用对称定时器驱动。
- 驱动层必须在全局同步 `sys_clock_announce()`。内核不按处理器分别追踪 tick。两个定时器中断几乎同时发生时，只能有一个报告当前新增 tick 数；另一个若没有新 tick，可以报告 0。由于时间片要求，不能简单跳过报告调用，参见[内核计时](P008_内核计时.md)。
- 有些硬件使用全局定时器，有些使用每处理器计数器。处理器之间的计数器同步等复杂性由驱动负责，内核不代为管理。
- 内核通过 `sys_clock_set_timeout()` 向每个处理器传回相同的下一次超时值。因此默认每个事件会使各处理器几乎同时收到定时器中断，但只能有一个向 `sys_clock_announce()` 传非零新增 tick。这能降低异常 ISR 或中断锁延误超时的概率，适合时间敏感应用，却也可能产生性能成本；优化仍由驱动负责。

## 9.6\_通用tickless核心

周期到 tick 的换算、报告基准、对齐 tick 的截止时间计算、计数器回绕与范围处理，在各 tickless 驱动中几乎相同。重复手写这些逻辑经常产生错误。[`drivers/timer/system_timer_generic.h`](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/timer/system_timer_generic.h) 将它们集中实现。

这是**实现头文件**，不是只有声明的头文件：包含后会定义 `sys_clock_set_timeout()`、`sys_clock_elapsed()` 和 `sys_clock_cycle_get_32()` / `sys_clock_cycle_get_64()`。多个候选驱动都可以基于它实现，每个驱动在提供所需宏和基本操作后包含一次。一次构建只编译一个系统定时器驱动，因此这些定义只落地一次。驱动本身只处理 cycle，通用核心负责 tick。

不论硬件计数器有多宽，核心默认生成两种周期读取函数，包括 64 位版本；报告基准本身为 64 位，未使用的函数由链接器去除。驱动是否选择 `CONFIG_TIMER_HAS_64BIT_CYCLE_COUNTER` 仍由自身决定。该选项表示 64 位读取成本较低，或至少不高于 32 位读取，因此优先窄读取没有优势。

使用 `TIMER_CORE_COUNTER_NONATOMIC` 时，两种读取都经过时钟锁，符合该条件；若硬件是小于 64 位的原子计数器，只有 64 位读取要上锁，32 位读取仍可无锁。

驱动必须提供两个基本操作：读取硬件周期的 `timer_driver_cycle_get()`，以及根据后端选择的定时设置函数 `timer_driver_set_compare()` 或 `timer_driver_set_reload()`。ISR 先确认/清除硬件中断，再调用 `timer_core_announce()`；初始化时先连接 **中断请求（Interrupt Request，IRQ）**，再调用 `timer_core_init()`；SMP 的 `smp_timer_init()` 调用 `timer_core_smp_prime()`。

## 9.7\_选择硬件后端

下列宏必须恰好选择一个，用于描述硬件工作方式：

| 宏 | 含义 |
| --- | --- |
| `TIMER_CORE_BACKEND_COMPARE_ORDERED` | 绝对比较器，有序匹配；计数达到或超过比较值就产生中断。因此写入已经过去的截止值会立即触发。可用范围是计数器计数跨度的一半。 |
| `TIMER_CORE_BACKEND_COMPARE_EXACT` | 绝对比较器，仅相等时匹配；若写入时计数已越过比较值，将错过整个计数周期。核心用带校验的循环写比较器，驱动不必自行设定最小延迟下限。 |
| `TIMER_CORE_BACKEND_RELOAD` | 相对延迟，适用于递减计数器及比较匹配后复位的周期计数器。假定自动重装，因此固定 tick 内核可从初始化设置的值自由运行。 |

## 9.8\_可选宏

只有默认设置不适合硬件时才定义下列宏。

`TIMER_CORE_CYCLES_PER_SEC` 指定计数器频率，单位 Hz，默认内核系统时钟频率。计数器分频或使用独立固定速率时需要设置。核心由它推导 `TIMER_CORE_CYC_PER_TICK`；驱动可读取后者进行硬件配置，例如设置初始化时的单 tick 周期，但不得自行定义它。

`TIMER_CORE_CYCLES_PER_SEC_RUNTIME` 表示上面的频率是变量而非编译常量，例如从时钟控制器读取或初始化时计算。核心会预先计算一次每 tick 周期数，而不依赖编译器折叠除法。调用 `timer_core_init()` 前，该变量必须已有最终值。

`TIMER_CORE_COUNTER_WIDTH` 指定 `timer_driver_cycle_get()` 返回计数的有效位宽，最多 64 位，默认本机寄存器宽度。若硬件宽度不同，必须显式指定。例如 32 位处理器上的真实 64 位计数器若继承默认 32 位掩码，会丢失超过 `2^32` 周期的时间跨度。核心对每个差值按此位宽取掩码，窄计数器可直接读原始值，无须驱动用软件扩展。

`TIMER_CORE_COUNTER_NONMONOTONIC` 表示读取值可能短暂小于此前观察值，例如 QEMU SMP 的全局计时器。核心把倒退读数视为没有时间流逝，而不是巨大的向前跳变。

`TIMER_CORE_COUNTER_NONATOMIC` 表示 `timer_driver_cycle_get()` 不是单次原子读取，而是从 ISR 也会修改的状态合成计数。核心会在时钟锁下读取。

`TIMER_CORE_HAVE_CYCLE_GET_32`、`TIMER_CORE_HAVE_CYCLE_GET_64` 表示相应入口由驱动自行定义，核心不生成，适用于需要缩放的计数器。包含头文件后可用 `timer_core_cycle_get()` 取得计数器自身时钟域的完整宽度计数，再进行缩放。

若驱动设置 `TIMER_CORE_CYCLES_PER_SEC`，必须自行提供 32 位入口：独立速率计数器的原始值不能直接作为内核周期使用。此时核心也不生成 64 位入口，因为它同样属于驱动声明的外部时钟域；需要 64 位入口时也应自行实现。

`TIMER_CORE_ALARM_MAX_CYCLES` 只表示定时设置操作能表达的最大硬件值。默认覆盖 `TIMER_CORE_COUNTER_WIDTH` 的全部计数跨度，因为告警与计数器通常是同一硬件。比较/重装寄存器更窄或告警由独立硬件承担时需另外设置。

这个宏只描述硬件容量，不应预扣安全余量。核心自行根据计数器宽度限制：设置时刻距上次报告最多为半个计数跨度；使用 `TIMER_CORE_COUNTER_NONMONOTONIC` 时最多四分之一，使延迟报告仍可经掩码正确解出差值。硬件容量与核心限制中较小者生效。

`TIMER_CORE_ALARM_MIN_CYCLES` 是重装周期下限，仅用于 `TIMER_CORE_BACKEND_RELOAD`，默认 1 个 cycle。

`TIMER_CORE_ALARM_LEAD_CYCLES` 是比较值必须领先当前计数多少 cycle 才能捕获匹配，仅用于 `TIMER_CORE_BACKEND_COMPARE_EXACT`，默认 1，即只要写入时计数仍小于比较值就能触发。若写操作需先跨入计数器时钟域，距离过近会丢失匹配，应提高此值。

新 tickless 驱动应基于该头文件实现，避免重新实现 tick 记账。头文件对各宏和基本操作有完整说明。驱动入口的正式声明见[时钟 API](../timer_reference/P086_系统时钟公共接口.md)。
