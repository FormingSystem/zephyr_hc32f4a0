# 第1章\_中断

原文：[Interrupts](https://docs.zephyrproject.org/latest/kernel/services/interrupts.html)。读取日期：2026-10-12，`latest`。

**中断服务例程（Interrupt Service Routine，ISR）**是响应硬件或软件中断而异步执行的函数。它通常抢占当前线程，以较低延迟响应事件；只有全部 ISR 工作完成后，线程执行才能恢复。

## 1.1\_基本概念

在硬件允许的范围内，可以定义任意数量的 ISR，数量最终受可用 **随机存取存储器（Random Access Memory，RAM）** 等资源限制。每个 ISR 有四项关键属性：触发它的**中断请求（Interrupt Request，IRQ）**信号、IRQ 优先级、处理函数，以及传给函数的参数。

中断描述符表（IDT）或向量表把中断源与 ISR 关联。基本模型中，一个 IRQ 同一时刻关联一个 ISR；多个 ISR 可以复用处理函数，通过不同参数区分中断来源。这适合一个设备产生多类中断，或多个同类设备使用共同处理代码的情况。

内核为未使用的 IDT 表项安排默认 ISR；意外中断触发时，它会产生致命系统错误。

内核支持中断嵌套。高优先级中断可抢占正在运行的低优先级 ISR；高优先级处理结束后，低优先级 ISR 继续。ISR 在内核中断上下文执行，使用专用中断栈，某些架构可能有多个中断栈。启用嵌套时，栈容量必须覆盖多层 ISR 同时占用的空间。

许多内核 **应用程序编程接口（Application Programming Interface，API）** 只能在线程中调用。如果一个函数可能同时从线程和 ISR 调用，可用 `k_is_in_isr()` 判断当前上下文并选择相应行为。

> 译注：后文共享中断功能通过一个分发入口调用多个客户 ISR，因此不能把这里的基本模型理解为 Zephyr 完全禁止多个驱动共享 IRQ。

## 1.2\_多级中断控制

平台可以级联中断控制器，扩展本来有限的中断线。子控制器把多个硬件中断源汇聚成一条线，再接入父控制器。

支持级联控制器时，应启用 `CONFIG_MULTI_LEVEL_INTERRUPTS`，并按硬件配置 `CONFIG_2ND_LEVEL_INTERRUPTS`、`CONFIG_3RD_LEVEL_INTERRUPTS`。

Zephyr 用唯一的 32 位中断号编码级联路径，以找到正确 ISR。默认每级占一个字节，这种编码可表示最多四级。原文图示如下：

```text
          9                           2       0
┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
│   │   │ ╷ │   │   │   │   │ A │   │ ╷ │   │   │               (LEVEL 1)
└───┴───┴─│─┴───┴───┴───┴───┴───┴───┴─│─┴───┴───┘
          └─────────────────┐         └─────────────────────┐
      5                     v                               v
┌───┬───┬───┬───┬───┬───┬───┐   ┌───┬───┬───┬───┬───┬───┬───┐
│   │ ╷ │   │ C │   │   │   │   │   │   │   │   │ B │   │   │   (LEVEL 2)
└───┴─│─┴───┴───┴───┴───┴───┘   └───┴───┴───┴───┴───┴───┴───┘
      └─────────────────────┐
                            v
┌───┬───┬───┬───┬───┬───┬───┐
│   │   │   │   │ D │   │   │                                   (LEVEL 3)
└───┴───┴───┴───┴───┴───┴───┘
```

图中每个格子代表一条中断线，从最右边的 `0` 开始编号：

- 第一级有 12 条线；第 2、9 号线接子控制器，设备 A 接第 4 号线。
- 一个第二级控制器的第 5 号线接第三级控制器，设备 C 接第 3 号线。
- 另一个第二级控制器没有下级，设备 B 接第 2 号线。
- 第三级控制器的设备 D 接第 2 号线。

四个设备的编码为：

```text
A -> 0x00000004
B -> 0x00000302
C -> 0x00000409
D -> 0x00030609
```

第二级及以后，每级编码值比实际线号加 `1`，因为 `0` 用来表示该级不存在。D 的路径是第三级 `2` → 第二级 `5` → 第一级 `9`，编码后依次是 `3`、`6`、`9`，所以得到 `0x00030609`。

## 1.3\_防止被中断

线程执行时间敏感操作或临界区时，可能需要暂时阻止 ISR。IRQ 锁用于暂时禁止中断处理，并允许嵌套获取；调用方不必先知道锁是否已经生效。加锁多少次，就必须相应解锁多少次，之后才能恢复中断处理。

**持有 IRQ 锁时不得休眠，只能调用允许 ISR 使用的 `isr-ok` 函数。**

也可以只禁用某个 IRQ，使其信号到来时暂不执行对应 ISR，之后再启用。禁用 IRQ 的效果不只影响发起操作的线程：系统中其他线程也不会被这个已禁用 IRQ 对应的 ISR 抢占。

> 译注：IRQ 锁的具体作用范围取决于架构与内核实现。不要把单核上下文中的表述当作多核共享数据的完整互斥方案；多核同步还需采用相应锁机制。

### 1.3.1\_零延迟中断

IRQ 锁会增加某些中断的响应延迟。为满足严格低延迟需求，内核允许某些中断运行在 IRQ 锁无法屏蔽的优先级，这称为零延迟中断。

需要启用 `CONFIG_ZERO_LATENCY_IRQS`，并在 `IRQ_DIRECT_CONNECT` 中传入 `IRQ_ZERO_LATENCY`。这种中断必须声明为直接 ISR，因为普通 ISR 会访问内核；其中不得使用 `ISR_DIRECT_PM`。有些架构也支持同时具有直接和动态属性的 ISR，见后文。

零延迟 ISR 应直接处理硬件，不与内核代码交互。对它而言，所有内核 API 都应视为行为未定义；若应用仍调用，正确性须由应用直接验证。它不得修改正常 Zephyr 上下文中内核 API 会检查的数据，也不能产生需要同步处理的异常，例如内核 panic。

系统电源管理在恢复期间可能保持普通中断锁定，但零延迟 IRQ 不受此顺序约束，可能在挂起/恢复逻辑期间、恢复记账及 **片上系统（System on Chip，SoC）**/设备硬件恢复完成前就执行。因此，ISR 必须能够在电源管理唤醒过程中安全运行；否则应在系统状态不允许时屏蔽或禁用其来源。可参考[设备电源策略约束](https://docs.zephyrproject.org/latest/services/pm/device.html#pm-device-constraint)，在可能产生零延迟 IRQ 的设备路径活动期间排除不安全电源状态。

零延迟中断按架构提供支持；原文当前列出的实现是 Arm Cortex-M。为了减少 Flash 访问延迟，还可以把 ISR 及所有相关符号迁移到 RAM。

> 译注：“零延迟”是指不受上述普通 IRQ 锁造成的屏蔽延迟，并不意味着物理响应时间为零。仍应考虑处理器进入中断、存储访问和更高优先级活动等因素。

## 1.4\_把耗时工作交给线程

ISR 应快速执行，使系统响应可预测。若处理耗时，应把部分或全部工作交给线程，尽快恢复内核响应其他中断的能力。

可以通过 **先进先出（First In, First Out，FIFO）**、**后进先出（Last In, First Out，LIFO）**、信号量等内核对象通知辅助线程，也可以把工作项提交给[系统工作队列线程](https://docs.zephyrproject.org/latest/kernel/services/threads/workqueue.html)。

通常 ISR 结束后，只需一次上下文切换就能进入处理线程，因此工作几乎可以立刻继续。但是否立即运行仍取决于调度：当前协作线程或其他更高优先级线程可能先执行。

## 1.5\_共享中断线

部分硬件的不同功能块共用同一 IRQ。例如第 17 号线既可能表示 **直接内存访问（Direct Memory Access，DMA）** 传输完成，也可能表示数字音频接口控制器 FIFO 达到水位。以往可用特殊逻辑或 `shared_irq` 控制器解决，但这不容易扩展。

启用 `CONFIG_SHARED_INTERRUPTS` 后，可以让内核统一处理。当通过 `IRQ_CONNECT` 或 `irq_connect_dynamic()` 在同一 IRQ 上注册第二组“ISR + 参数”时，该线变为共享；以后每次触发，原有和新增处理函数都会被调用。

每个使用者称为一个客户（client）。单条线允许的最多客户数由 `CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS` 控制。共享对调用者透明，仍按普通方式注册。

同时启用共享与动态中断后，可通过 `irq_disconnect_dynamic()` 动态断开 ISR。断开后，该 IRQ 再次触发就不会调用被移除的处理函数。

共享中断支持会明显增加二进制体积，应按实际需要启用。

## 1.6\_定义普通ISR

普通 ISR 通过 `IRQ_CONNECT` 连接，并通过 `irq_enable()` 启用。

原文说明，`irq_enable()`、`irq_lock()` 等不带前缀的名字属于历史拼写，新代码应使用对应的 `k_irq_enable()`、`k_irq_lock()` 等带命名空间的接口；旧名称仍受支持。下面保留原文代码。

`IRQ_CONNECT()` 不是 C 函数，内部包含内联汇编等构建机制；全部参数必须在构建期已知。多实例驱动因此可能需要为每个实例定义独立配置函数。

```c
#define MY_DEV_IRQ  24       /* device uses IRQ 24 */
#define MY_DEV_PRIO  2       /* device uses interrupt priority 2 */
/* argument passed to my_isr(), in this case a pointer to the device */
#define MY_ISR_ARG  DEVICE_GET(my_device)
#define MY_IRQ_FLAGS 0       /* IRQ flags */

void my_isr(void *arg)
{
   ... /* ISR code */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_ISR_ARG, MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}
```

> 译注：原文称通过此宏“在运行时定义 ISR”，但其含义不是允许全部参数在运行时任意计算。连接表信息在构建期生成，优先级设置等动作可能在运行时执行，详见后面的实现说明。

若必须运行时决定参数，可使用 `irq_connect_dynamic()`，调用形式与宏相同：

```c
void my_isr_installer(void)
{
   ...
   irq_connect_dynamic(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_ISR_ARG,
                       MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}
```

动态中断需要 `CONFIG_DYNAMIC_INTERRUPTS`。原文在这里说“目前不支持移除或重新配置动态中断”。

> 译注：这句话与本页后面的动态断开功能不一致。本页同时明确给出在共享/动态支持条件下调用 `irq_disconnect_dynamic()` 的方案；因此不能将其理解为所有配置均绝对禁止移除。应以目标架构、实际配置和接口支持为准。

## 1.7\_定义直接ISR

普通中断带有一些开销，某些低延迟场合无法接受，包括：

- 查找 ISR 参数并传入函数。
- 启用电源管理且系统原先空闲时，先从低功耗状态恢复硬件，再执行 ISR；这一过程可能耗时。
- 某些架构由硬件切换中断栈，另一些需要软件完成。
- 中断处理后执行可能触发重新调度的内核逻辑。

零延迟中断必须采用直接 ISR，避免普通路径对内核的访问。

直接中断使用 `IRQ_DIRECT_CONNECT` 安装，处理函数用 `ISR_DIRECT_DECLARE` 声明。这种方式有额外实现约束、功能也更少，细节见相应宏定义。只有选择 `CONFIG_ARCH_HAS_DIRECT_INTERRUPTS` 的架构支持；在其他架构使用这两个宏会构建失败。

示例：

```c
#define MY_DEV_IRQ  24       /* device uses IRQ 24 */
#define MY_DEV_PRIO  2       /* device uses interrupt priority 2 */
#define MY_IRQ_FLAGS 0       /* IRQ flags */

ISR_DIRECT_DECLARE(my_isr)
{
   do_stuff();
   /* PM done after servicing interrupt for best latency. This cannot be
   used for zero-latency IRQs because it accesses kernel data. */
   ISR_DIRECT_PM();
   /* Ask the kernel to check if scheduling decision should be made. If the
   ISR is for a zero-latency IRQ then the return value must always be 0. */
   return 1;
}

void my_isr_installer(void)
{
   ...
   IRQ_DIRECT_CONNECT(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}
```

示例在完成硬件处理后才执行 `ISR_DIRECT_PM()`，以缩短处理延迟；该宏访问内核数据，不能用于零延迟 IRQ。返回 `1` 表示请求内核检查是否需要调度；若是零延迟 IRQ，必须始终返回 `0`。

动态直接中断的支持也依赖架构。原文列出的 Arm Cortex-M 实现通过 `ARM_IRQ_DIRECT_DYNAMIC_CONNECT` 声明同时具有动态和直接属性的中断。

### 1.7.1\_在RAM中执行ISR

为了极低延迟，可把 ISR 与向量表搬到 RAM，避免 Flash 访问延迟。`CONFIG_SRAM_VECTOR_TABLE`、`CONFIG_SRAM_SW_ISR_TABLE` 可将对应表放在 RAM，再通过[代码和数据重定位](https://docs.zephyrproject.org/latest/kernel/code-relocation.html)将 ISR 及关联符号迁入 RAM。

## 1.8\_共享与动态断开的代码

以下两个 ISR 使用同一 IRQ：

```c
#define MY_DEV_IRQ 24               /* device uses INTID 24 */
#define MY_DEV_IRQ_PRIO 2           /* device uses interrupt priority 2 */
/*  this argument may be anything */
#define MY_FST_ISR_ARG INT_TO_POINTER(1)
/*  this argument may be anything */
#define MY_SND_ISR_ARG INT_TO_POINTER(2)
#define MY_IRQ_FLAGS 0              /* IRQ flags */

void my_first_isr(void *arg)
{
   ... /* some magic happens here */
}

void my_second_isr(void *arg)
{
   ... /* even more magic happens here */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_second_isr, MY_SND_ISR_ARG, MY_IRQ_FLAGS);
   ...
}
```

普通 `IRQ_CONNECT` 的构建期常量限制仍适用。未启用 `CONFIG_SHARED_INTERRUPTS` 会报构建错误；启用后，第 24 号 IRQ 每次触发都会调用两个 ISR。若 `CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS` 小于此处的客户数 `2`，也会构建失败。

启用动态中断后，`irq_connect_dynamic()` 可以在运行时加入共享客户；超过配置的最大客户数会触发断言失败。

### 1.8.1\_动态断开ISR

原文再次定义两个共享 ISR，然后在运行时移除其中一个：

```c
#define MY_DEV_IRQ 24               /* device uses INTID 24 */
#define MY_DEV_IRQ_PRIO 2           /* device uses interrupt priority 2 */
/*  this argument may be anything */
#define MY_FST_ISR_ARG INT_TO_POINTER(1)
/*  this argument may be anything */
#define MY_SND_ISR_ARG INT_TO_POINTER(2)
#define MY_IRQ_FLAGS 0              /* IRQ flags */

void my_first_isr(void *arg)
{
   ... /* some magic happens here */
}

void my_second_isr(void *arg)
{
   ... /* even more magic happens here */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_second_isr, MY_SND_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

void my_isr_uninstaller(void)
{
   ...
   irq_disconnect_dynamic(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   ...
}
```

这次 `irq_disconnect_dynamic()` 会使第 24 号 IRQ 退出共享状态，效果相当于第一次 `IRQ_CONNECT` 从未发生。必须启用 `CONFIG_DYNAMIC_INTERRUPTS`，否则会出现链接错误；同时还需满足前述共享功能的配置条件。

> 译注：原文引导句称“第二个 ISR 被断开”，但实际代码传入 `my_first_isr` 和 `MY_FST_ISR_ARG`，后文也说第一次连接被移除。因此本例实际断开的是第一个 ISR，保留第二个。

## 1.9\_中断表构建机制

中断表由专用构建工具生成。本节先说明除 x86 外的通用机制，x86 另有专节。

调用 `IRQ_CONNECT` 会声明 `struct _isr_list` 实例，并放入特殊的 `.intList` 段。它仅存在于中间构建产物，供 Zephyr 脚本生成中断表，最终镜像会移除此段。

脚本可以采用不同解析器：

- **默认 C 数组方式**：直接从 `.intList` 读取处理函数和参数地址，生成 C 数组。兼容性较广，但要求生成数组后代码地址不再变化；否则数组中的地址可能失效。这限制了链接时优化（LTO）的使用。
- **局部 ISR 声明方式**：在调用 `IRQ_CONNECT` 的源文件中就声明各表项，放入合成的唯一命名段，再把段名记入 `.intList`。脚本生成链接片段，把这些段放到正确位置。支持范围受架构和工具链限制，但保留链接器可见的对象关系，因此可支持 LTO。

### 1.9.1\_C数组方式

原文将它列为 Zephyr 架构的默认配置，x86 的特殊处理见后文。每次连接会产生以下记录：

```c
struct _isr_list {
    /** IRQ line number */
    int32_t irq;
    /** Flags for this IRQ, see ISR_FLAG_* definitions */
    int32_t flags;
    /** ISR to call */
    void *func;
    /** Parameter for non-direct IRQs */
    void *param;
};
```

Zephyr 分两阶段构建。第一阶段的 `${ZEPHYR_PREBUILT_EXECUTABLE}.elf` 中，`.intList` 记录前带一个头部：

```c
struct {
    void *spurious_irq_handler;
    void *sw_irq_handler;
    uint32_t num_isrs;
    uint32_t num_vectors;
    struct _isr_list isrs[];  <- of size num_isrs
};
```

> 译注：`<- of size num_isrs` 是原文对数组长度的行内说明，不是合法 C 代码，应读作“大小为 num_isrs”。

`gen_isr_tables.py` 从中间 **可执行与可链接格式（Executable and Linkable Format，ELF）** 读取头部及记录，生成定义向量表和软件 ISR 表的 C 文件，再编译并链接到最终应用。

中断优先级不编码在这些表中；`IRQ_CONNECT` 还有运行时部分，会把所需优先级写入中断控制器。某些架构不支持中断优先级，此时该参数被忽略。

### 1.9.2\_向量表

启用 `CONFIG_GEN_IRQ_VECTOR_TABLE` 时生成向量表。**中央处理器（Central Processing Unit，CPU）** 原生使用此函数指针数组，第 `n` 项对应 IRQ `n` 的入口：

- `IRQ_DIRECT_CONNECT` 声明的直接中断：保存实际处理函数。
- `IRQ_CONNECT` 声明的普通中断：保存公共软件 IRQ 入口，由它完成内核中断记账并从软件 ISR 表查找处理函数及参数。
- 未配置中断：保存意外中断处理入口，执行时产生致命系统错误。

某些架构所有中断共用入口，不支持向量表，应关闭该选项。某些架构在前几个向量保留系统异常，并另行定义它们，此时须通过 `CONFIG_GEN_IRQ_START_VECTOR` 调整索引起点。

### 1.9.3\_软件ISR表与共享表

软件 ISR 表是以下结构的数组：

```c
struct _isr_table_entry {
    void *arg;
    void (*isr)(void *);
};
```

公共软件 IRQ 入口从中断控制器读取活动中断号，以它索引表项，再调用相应 ISR 并传入参数。

共享软件 ISR 表则是以下结构的数组：

```c
struct z_shared_isr_table_entry {
    struct _isr_table_entry clients[CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS];
    size_t client_num;
};
```

该表记录每条线的客户。IRQ 变成共享时，`z_shared_isr()` 会替换 `_sw_isr_table` 中原来的处理函数；它遍历客户列表并依次调用各 ISR。

## 1.10\_局部声明与链接脚本方式

这种方式在 `IRQ_CONNECT` 所在位置直接创建将组成中断表的元素，再通过自动生成的链接脚本安排内存位置，因此称为局部 ISR 声明。

启用选项是 `CONFIG_ISR_TABLES_LOCAL_DECLARATION`。如果架构和工具链支持，`CONFIG_ISR_TABLES_LOCAL_DECLARATION_SUPPORTED` 会被设置；具体支持范围见该配置项。

调用 `IRQ_CONNECT` 或 `IRQ_DIRECT_CONNECT` 会在 `.intList` 段中声明：

```c
struct _isr_list_sname {
    /** IRQ line number */
    int32_t irq;
    /** Flags for this IRQ, see ISR_FLAG_* definitions */
    int32_t flags;
    /** The section name */
    const char sname[];
};
```

段名放在柔性数组成员中，所以已初始化记录的大小随名称长度变化。脚本在构建时使用整个记录，取得放置中断表项所需信息。

此外，`IRQ_CONNECT` 还生成实际软件 ISR 表项：

```c
struct _isr_table_entry {
    const void *arg;
    void (*isr)(const void *);
};
```

它被放入 `_isr_list_sname` 指定名字的段中。`IRQ_DIRECT_CONNECT` 产生什么内容取决于架构，可以是指向 ISR 的变量：

```c
static uintptr_t <unique name> = ((uintptr_t)func);
```

也可以是执行跳转的裸函数：

```c
static void <unique name>(void)
{
    __asm(ARCH_IRQ_VECTOR_JUMP_CODE(func));
}
```

生成的变量或函数同样进入记录中的指定段。

> 译注：原文此节开头偶尔写 `.isrList`，实际前后使用的是 `.intList`；另有一句把长度变化说成取决于“结构名”，这里应理解为记录中保存的段名长度。`<unique name>` 是待生成唯一标识符的占位，不是合法 C 名称。

### 1.10.1\_脚本生成的文件

中断表生成脚本产生三个文件：

| 文件 | 作用 |
| --- | --- |
| `isr_tables.c` | 为普通、直接及已启用的共享中断生成应用尚未定义的必要结构；应用已定义的部分用注释指明位置。 |
| `isr_tables_vt.ld` | 放在目标架构要求的向量表位置，安排向量项。 |
| `isr_tables_swi.ld` | 安排软件 ISR 表元素；单独提供是因为该表可能按配置放在可写或只读段。 |

## 1.11\_x86的特殊机制

x86 的向量表称为中断描述符表（IDT），布局须遵循处理器文档。`arch/x86/gen_idt.py` 利用 `.intList` 生成它。

在基于 APIC 的系统中，向量索引不等于 IRQ 线号。前 32 个向量留给 CPU 异常，其余直到索引 255 按每 16 个一组映射到优先级。例如优先级 0 使用 32—47，优先级 1 使用 48—63，以此类推。工具按请求优先级在对应区间查找空闲向量并安装处理入口。

x86 进入中断或异常时，没有可靠通用办法直接判断刚才触发的是哪个向量，因此不使用按 IRQ 线索引的软件 ISR 表。`IRQ_CONNECT` 改为生成一个小汇编入口，它把 ISR 和参数传给公共 `_interrupt_enter()`。IDT 保存该汇编入口的地址；直接中断则把无参数 ISR 直接放入 IDT。

当向量位置表示优先级时，中断控制器还需知道 IRQ 线对应哪个向量。`arch/x86/gen_idt.py` 另外生成 `_irq_to_interrupt_vector` 数组，运行时由 `IRQ_CONNECT` 用于配置 IRQ 到向量的关联。

动态中断需要构建时生成每个 4 字节的动态入口桩，每个使用中的动态中断占一个。数量由 `CONFIG_X86_DYNAMIC_IRQ_STUBS` 控制。入口桩压入唯一标识，再用它从动态连接时填充的表中查找处理函数与参数。

## 1.12\_扩展每级中断数量

多级编码默认每级使用 8 位掩码。当单个聚合控制器需要支持超过 255 个中断时，可以调整各级位数；各级合计必须不超过 32 位，保证编码仍放在一个 32 位整数中。

在 `Kconfig.multilevel` 中覆盖默认的 `8`：第一级使用 `CONFIG_1ST_LEVEL_INTERRUPT_BITS`，第二级使用 `CONFIG_2ND_LEVEL_INTERRUPT_BITS`，第三级使用 `CONFIG_3RD_LEVEL_INTERRUPT_BITS`。

这些配置决定生成中断值、判断层级以及转换层级时使用的掩码长度和移位量。相关逻辑见 `irq_multilevel.h`。

## 1.13\_推荐用途、配置与参考

需要快速响应，且能快速完成、不发生阻塞的处理，适合普通或直接 ISR。耗时或需要阻塞的部分应交给线程，方法见前述工作下放部分。

通用相关配置为 `CONFIG_ISR_STACK_SIZE`，此外还有架构及设备专用配置。完整接口见[官方 Interrupt Service Routine APIs](../fatal_irq_reference/P007_中断服务接口.md)。
