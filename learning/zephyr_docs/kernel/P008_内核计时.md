# 第8章\_内核计时

原文：[Kernel Timing](https://docs.zephyrproject.org/latest/kernel/services/timing/clocks.html)。读取日期：2026-10-12，`latest`。

Zephyr 提供可扩展的**计时框架（Timing Framework）**，利用不同精度的硬件时间源记录并跟踪定时事件。

## 8.1\_时间单位

应用通常用毫秒、微秒等实际时间单位，含义明确且可移植，但不一定与底层硬件精度完全匹配。

`k_cycle_get_32()`、`k_cycle_get_64()` 提供周期计数。设计目标是暴露操作系统能够提供的最快计数器，例如 **中央处理器（Central Processing Unit，CPU）** 周期计数器，并使读取成本很低；对精度敏感的代码可以轮询它。

计数频率通过 `sys_clock_hw_cycles_per_sec()` 获取。多数平台在运行期为常量，对应 `CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC`，整个系统生命周期固定。若平台的系统定时器频率可变，该函数返回当前值，应用不得假设频率永远不变。

### 8.1.1\_运行时系统定时器频率

有些平台从硬件探测时钟速率，或在启动后改变定时器频率，因此需要运行时频率支持。能够改变活动频率的平台必须启用 `CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE`，并在完成硬件时钟变更后调用 `z_sys_clock_hw_cycles_per_sec_update()`。

若驱动缓存周期数/tick 等派生常量，或频率变化后要重新编程硬件，应由定时器驱动提供该函数的覆盖实现。默认实现只更新保存的频率值。

该配置只维护一个全局系统定时器频率，不适用于各 CPU 可能观察到不同定时器频率的按 CPU 调频方案。启用后，频率查询和单位转换使用当前运行值。

### 8.1.2\_内核tick

内核用 tick 记录运行时间与超时，不跟踪小数 tick；在实际可行范围内，中断应落在 tick 边界。速率由 `CONFIG_SYS_CLOCK_TICKS_PER_SEC` 配置。

原文给出的典型量级是：支持任意超时编程的硬件平台约 10 kHz，软件仿真平台和旧驱动常采用 100 Hz。这是常见配置背景，不代表每个平台的固定默认值。

## 8.2\_单位转换

转换库覆盖 `ms`、`us`、`tick`、`cyc` 之间的各种组合，并提供向下取整 `floor`、向上取整 `ceil` 和四舍五入到最近单位 `near`，输出可选 32 或 64 位。

例如 `k_ms_to_ticks_ceil32()` 把毫秒转成向上取整的 tick，返回 32 位结果；`k_cyc_to_us_floor64()` 把周期数转成向下取整的微秒，保留 64 位精度。

多数平台各频率成整数比例、结果又能放入一个机器字时，转换通常只需 2—4 个操作，只在确有需要时使用更高精度计算。完整列表见 **应用程序编程接口（Application Programming Interface，API）** 参考。

## 8.3\_系统运行时间

`k_uptime_get()` 返回启动以来的毫秒数，通常是可移植应用的首选。内核实际用 64 位 tick 维护时间；愿意自行转换的精密计时应用可以调用 `k_uptime_ticks()`。

`k_uptime_delta()` 返回参考时刻到当前的间隔，并把参考值更新为当前运行时间，便于下一次继续测量。

## 8.4\_超时对象与时间基准

许多 API 有超时参数：信号量或队列等待超过期限后可报错返回；定时器使用 duration 和 period；可延迟工作指定何时提交到工作队列。

它们都使用不透明结构 `k_timeout_t`，必须由内核宏构造，常见的 `K_MSEC()` 表示从当前时间起若干毫秒。

相对超时中的“当前时间”依上下文而定：

- 在超时回调中安排另一个超时时，以当前触发事件原本应当到期的精确时刻为基准，即使真实时间已经稍晚。这样回调之间可以保持精确偏移，周期运行不累积漂移。
- 应用上下文中，以内核接收该超时值时的 `k_uptime_ticks()` 为基准。

> 译注：原文把 `k_timer_init()` 到期回调和 `k_work_init_delayable()` 的工作处理函数都列为第一类例子，但延迟工作的用户处理函数通常在线程中、排队后才执行，不等同于内部超时回调。不要据此认为在普通 work handler 中重新安排相对超时会自动保持原定到期基准。本地超时实现按当前 CPU 是否正在通告超时区分时间基准，工作函数由队列线程调用；具体周期需求可采用绝对期限并核对目标版本。

其他构造宏包括 `K_NSEC()`、`K_USEC()`、`K_TICKS()`、`K_CYC()`，分别按纳秒、微秒、tick 和周期指定。`k_timeout_t` 精度可配置；原文将默认描述为 32 位，长时间运行且对计时敏感的应用应考虑 64 位，避免非 tick 单位大数值的复杂回绕语义。

也可以使用启动以来的绝对时刻，例如 `K_TIMEOUT_ABS_MS()` 在 uptime 达到指定毫秒数时到期，还有纳秒、微秒、周期和 tick 变体。

## 8.5\_超时队列内部机制

所有内核超时事件由一个全局事件队列管理。请求方提供到期回调及嵌入自身数据结构的 `struct _timeout` 跟踪对象，例如等待机制或线程结构中的成员。

各种单位在入队时只转换一次为 tick，内核不会反复跨单位转换，因此无论事件多少或等待多长，都以 tick 粒度保持精度。

通过 `CONFIG_TIMEOUT_BACKEND` 在构建期选择队列数据结构。通告路径、**对称多处理（Symmetric Multiprocessing，SMP）** 重入及相对/绝对超时规则是共享前端，各后端只提供队列实现，便于按负载选择。

默认后端为 `CONFIG_TIMEOUT_BACKEND_DLIST`：按到期顺序排列的双向链表，每项记录相对前驱的 tick 差值，插入复杂度 O(N)。少量超时时成本低，但大量挂起项下扩展性较差。

原文另外列出四个**实验性**后端：

| 后端 | 性能与约束 |
| --- | --- |
| `CONFIG_TIMEOUT_BACKEND_MINHEAP` | 按绝对到期时间排序的二叉最小堆，插入删除 O(log N)。需要 `CONFIG_TIMEOUT_64BIT`；容量由 `CONFIG_TIMEOUT_HEAP_MAX_ENTRIES` 固定，溢出为致命错误；不保留同 tick 到期顺序。 |
| `CONFIG_TIMEOUT_BACKEND_WHEEL` | 分层时间轮，近期事件插入删除 O(1)，远期进入有序溢出列表。每事件及静态内存开销最大；不保留同 tick 顺序；下一超时估计受轮周期限制，会周期性唤醒无周期节拍空闲 CPU，增加功耗。 |
| `CONFIG_TIMEOUT_BACKEND_BUCKET` | 单层分桶差值链表，时间轮的简化形式。由 `CONFIG_TIMEOUT_BUCKET_LISTS` 调整近期窗口，窗口内插入 O(1)，远期进入有序溢出列表。需要 64 位 tick，保留同 tick 顺序且不增加空闲唤醒成本。 |
| `CONFIG_TIMEOUT_BACKEND_SKIPLIST` | 按绝对到期排序的 Pugh 跳表，期望插入删除 O(log N)，无固定容量限制，同 tick 按 **先进先出（First In, First Out，FIFO）**。需要 64 位 tick；每事件保存 `CONFIG_TIMEOUT_SKIPLIST_MAX_LEVEL` 个前向指针，**随机存取存储器（Random Access Memory，RAM）** 高于差值链表或最小堆。 |

非默认后端面向同时存在大量超时、尤其近期密集超时的系统。多数应用仍适合默认差值链表。

> 译注：这些后端和选项按本次 `latest` 页面翻译。旧版 Zephyr 未必提供，不能直接套用到任意发行版。

## 8.6\_定时器驱动与时间片

tick 层面的内核计时由系统定时器驱动推进，接口及锁约束见[系统定时器驱动](https://docs.zephyrproject.org/latest/kernel/services/timing/system_timer_drivers.html)。

计时子系统还给调度器提供时间片计数。线程时间片不是全局到期事件，在 SMP 上要按 CPU 分别跟踪，所以不能直接当作普通超时值处理。

若没有额外硬件，Zephyr 会复用系统定时器驱动。当前 CPU 运行受时间片限制的线程时，传给 `sys_clock_set_timeout()` 的值可能被缩短到早于全局队列中下一个超时，以便按时轮换。

## 8.7\_保留毫秒接口的子系统

子系统可以继续接收普通毫秒值，内部按自己的方式处理，只在传入内核时用 `K_MSEC()` 转换。这便于移植，但无法充分利用更高精度构造和绝对超时等能力；简单需求下仍可接受。

特殊值需要处理：`K_FOREVER` 已不是整数，不能直接传给旧毫秒整数接口，应另定义整数标记表示永远等待。`K_NO_WAIT` 同样有类型差异，但其含义一直是零等待，可自然映射为整数 `0`。

## 8.8\_使用原生k_timeout_t的子系统

接收等待期限的接口最好直接使用内核超时类型。但它是不透明结构，不能像整数一样随意检查或减去已经经过的时间。比较特殊值可用 `K_TIMEOUT_EQ()`，例如判断是否为 `K_FOREVER`。

旧式循环可能这样在每次等待后扣减毫秒：

```c
void my_wait_for_event(struct my_subsys *obj, int32_t timeout_in_ms)
{
    while (true) {
        uint32_t start = k_uptime_get_32();

        if (is_event_complete(obj)) {
            return;
        }

        /* Wait for notification of state change */
        k_sem_take(obj->sem, timeout_in_ms);

        /* Subtract elapsed time */
        timeout_in_ms -= (k_uptime_get_32() - start);
    }
}
```

> 译注：这是说明需要迁移的旧接口反例，不是当前 `k_sem_take()` 的正确调用；该函数现在需要 `k_timeout_t`。示例也未完整处理超时终止及数值下溢，不能直接用于实际等待逻辑。

应先用 `sys_timepoint_calc()` 把期限变成基于 uptime tick 的到期时间点，再用 `sys_timepoint_timeout()` 得到剩余超时：

```c
void my_wait_for_event(struct my_subsys *obj, k_timeout_t timeout)
{
    /* Compute the end time from the timeout */
    k_timepoint_t end = sys_timepoint_calc(timeout);

    do {
        if (is_event_complete(obj)) {
            return;
        }

        /* Update timeout with remaining time */
        timeout = sys_timepoint_timeout(end);

        /* Wait for notification of state change */
        k_sem_take(obj->sem, timeout);
    } while (!K_TIMEOUT_EQ(timeout, K_NO_WAIT));
}
```

`sys_timepoint_calc()` 支持 `K_FOREVER`、`K_NO_WAIT`，也同样支持绝对和相对超时。逆向转换可能返回这两个特殊值；时间点已过去时也返回 `K_NO_WAIT`。简单查询可用 `sys_timepoint_expired()`。

相对期限仍需要“当前时间”基准。因此必须尽量在用户把超时交给子系统时，同步且只调用一次 `sys_timepoint_calc()`。不要先长时间保存相对超时再转换，也不要在每次循环中重新计算截止点，否则会不断推迟期限。
