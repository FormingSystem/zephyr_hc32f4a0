# 第27章\_架构移植指南

原文：[Architecture Porting Guide](https://docs.zephyrproject.org/latest/hardware/porting/arch.html)。读取日期：2026-10-12，`latest`。

当 Zephyr 需要运行于尚不支持的**指令集架构（Instruction Set Architecture，ISA）**或**应用二进制接口（Application Binary Interface，ABI）**时，就需要架构移植。已有例子包括使用 System V ABI 的 x86_32、使用 Thumb2 与 Arm 嵌入式 ABI（aeabi）的 ARMv7-M，以及 ARCv2。

架构的 Kconfig 方案与开发板类似，配置方法见[设置配置值](../kconfig/P003_设置配置值.md)。架构移植主要包括以下工作：

- 必需：复位后的早期启动、中断异常处理、上下文切换、线程创建与终止、架构相关工具函数、工具链和链接脚本。
- 设备驱动：通常中断控制器与系统时钟绑定架构，其中一部分必需，其他可选。
- **中央处理器（Central Processing Unit，CPU）** 空闲与电源管理：部分可选，但通常非常需要。
- 故障管理：提供架构相关调试信息和致命错误处理，部分可选。
- 内存管理与映射、栈对象的硬件保护要求、用户模式线程及远程调试 GDB stub。

> 译注：已有 Cortex-M 架构上的 HC32 **片上系统（System on Chip，SoC）**/开发板移植，不等于重新实现整套 ISA 移植。本章供理解底层职责与排查边界使用。

## 27.1\_早期启动

早期启动把系统从复位状态带到可执行 C 代码、进入通用内核初始化的状态。多数架构所需步骤很少，也有架构需要额外准备。

通用步骤是建立初始栈；XIP 内核将有初值数据从 **只读存储器（Read-Only Memory，ROM）** 复制到 **随机存取存储器（Random Access Memory，RAM）**；没有 **可执行与可链接格式（Executable and Linkable Format，ELF）** 加载器时清零 BSS；跳到 `z_cstart()`。后者负责从启动时的临时上下文切换到主线程。

架构特定工作例如：x86_32 从实模式进入 32 位保护模式、修复引导程序遗留的段寄存器；Cortex-M3/4 初始化开发板看门狗，切换 MSP 到 PSP，并以适当方式替代直接进入 `z_swap()`，防止启动竞态；ARCv2 建立快速中断 FIRQ 与常规 **中断请求（Interrupt Request，IRQ）** 处理。

### 27.1.1\_启动钩子

Zephyr 的 [include/zephyr/platform/hooks.h](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/platform/hooks.h) 定义了在精确时点运行 SoC/开发板代码的钩子。多数由通用代码调用，但早期阶段的钩子需由架构实现负责。

原文给出的顺序是：

1. 从名称匹配 `CONFIG_KERNEL_ENTRY` 的架构入口开始。
2. 若启用 `CONFIG_INIT_ARCH_HW_AT_BOOT`，立即重新初始化架构状态。
3. 调用 `soc_early_reset_hook()`。
4. 为后续步骤建立初始栈。
5. 执行架构相关的挂起到 RAM 恢复逻辑。若依据 `CONFIG_PM_S2RAM` 等状态判定正在恢复，不再执行后面的常规启动。
6. 调用 `soc_reset_hook()`，再执行架构汇编准备。
7. 调用架构 C 函数 `z_prep_c()`，它立即调用 `soc_prep_hook()`。
8. 执行其余架构 C 初始化，调用 `z_cstart()`，转入架构无关代码。

调用 `soc_early_reset_hook()` 前不必建立有效栈，且该钩子允许在返回前改写栈指针；调用者不能假定原栈指针保持不变。

架构有多个栈指针时，返回型钩子只允许改写当前可直接访问的主栈指针，不得读取或修改其他辅助栈指针。这允许架构代码预先设置其他模式的栈。

例如 Cortex-A 各执行模式有自己的 `sp_mode`，当前处于模式 M 时，普通 `sp` 对应 `sp_M`。钩子可改 `sp_M`，不能读写其他模式栈指针。

钩子也可以不返回、完全接管系统。此时不受上述返回约束，可以访问全部栈指针，但剩余启动流程显然也不再执行。

## 27.2\_中断与异常

设备用中断通知 CPU 处理工作；执行中出现不能按正常指令流处理的情况则产生异常。两者都转入处理程序，中断处理程序通常称 **中断服务例程（Interrupt Service Routine，ISR）**。ISR 工作往往与设备有关；异常处理通常由核心内核提供。

除了处理程序自身任务，内核入口还需要保存当前上下文，必要时退出省电状态并唤醒设备，从无 tick 空闲退出时更新运行时间；处理结束后决定是否切换线程，并恢复选中的上下文。

各架构在概念上相同，但保存寄存器、具体指令和异常编号不同，因此需要架构专用的中断/异常入口桩。

原文给出的 ISR 签名是：

```c
void (*isr)(void *parameter)
```

硬件通常没有统一的参数传递方式，常用两种实现：一种在入口桩内通过架构机制安置参数，常见于 x86；另一种用独立表保存 ISR 和参数，真实向量表统一进入分派器，运行时识别当前中断号后查表，Arm 和 ARC 常借 `CONFIG_GEN_ISR_TABLES` 实现。

例子可查看 x86 的 `_interrupt_enter()`、Arm 的 `_isr_wrapper()`，以及 [ARC 中断封装实现](https://github.com/zephyrproject-rtos/zephyr/blob/main/arch/arc/core/isr_wrapper.S)。

架构还必须实现中断锁 `irq_lock()` / `irq_unlock()`、构建时连接 `IRQ_CONNECT()`、适用时的 `irq_priority_set()`，以及 `irq_enable()` / `irq_disable()`。

`IRQ_CONNECT` 借汇编或链接脚本技巧在构建时建立连接，以减少启动工作和代码体积。

向量表应为每个可能发生的异常或中断提供处理程序。最简单可自旋，但原文强烈建议至少打印调试信息，以便定位除零、无效内存访问或意外中断。可参考 [Cortex-M 故障处理](https://github.com/zephyrproject-rtos/zephyr/blob/main/arch/arm/core/cortex_m/fault.c)。

## 27.3\_线程上下文切换

内核决定调度哪个协作或抢占线程，架构负责实际切换方法。Zephyr 有两套互斥接口：启用 `CONFIG_USE_SWITCH` 使用推荐的 `arch_switch`；关闭时使用 `arch_swap`。新架构实现其中一种即可，但 **对称多处理（Symmetric Multiprocessing，SMP）** 必须使用 `arch_switch`。

切换可能发生在线程阻塞等待资源、释放资源使高优先级线程就绪、中断唤醒高优先级线程、线程运行结束，或线程发生致命异常并退出运行集合时。抢占还要求当前线程可被抢占。

### 27.3.1\_协作与抢占路径

协作切换由线程主动让出，或等待不可用对象而阻塞。抢占切换由 ISR 或线程执行某操作，使更高优先级线程获得运行机会，例如释放它等待的对象。

原文说明协作线程运行时不会被其他普通线程夺走控制权。

> 译注：这不表示协作线程不会被硬件中断打断，也不覆盖具有特殊语义的 meta-IRQ 线程；具体规则见[调度](../kernel/P005_调度与CPU空闲.md)。

协作切换通过内核 `z_swap` 或变体进入相应架构切换函数；到达该层后不再判断要不要切换，切换必须发生。32 位 x86 的 `arch_swap` 也可用于中断退出切换，但 Cortex-M 和 ARCv2 并不这样实现，不能视为通则。

原文解释，因为 `z_swap` 通过协作函数调用进入，ABI 规定需由调用者保留的寄存器已由调用路径处理，无须再全部保存进 `k_thread`。

抢占切换发生在 ISR 退出桩：x86 的 `_interrupt_enter` 处理程序返回后、Arm 的 `z_arm_exc_exit` / `z_arm_int_exit`，以及 ARCv2 的 `_firq_exit` / `_rirq_exit`。

### 27.3.2\_中断退出的选择

只在退出最外层、非嵌套中断时判断切换。启用 `CONFIG_USE_SWITCH` 时，退出代码调用 `z_get_next_switch_handle()`，返回该句柄标识的线程上下文。否则读取就绪队列缓存线程：与当前线程不同则切换，相同则不切换。

这些判断虽简单，却至关重要；错误实现会导致内核异常运行，常表现为栈损坏引起的难解释崩溃。

## 27.4\_线程创建、终止与TLS

创建线程时，要构造能被切换路径按正常保存上下文恢复的初始栈帧。原文将架构例程称为 `_new_thread`。

新线程 PC 不直接设成应用入口，而设成包装例程 `_thread_entry`，把应用入口作为第一参数交给它；寄存器和栈的具体安排由 ABI 决定。

> 译注：这些是旧符号名。本地 Cortex-M 实现使用 `arch_new_thread()` 和 `z_thread_entry`；移植应核对当前内核到架构接口，不能仅按旧名新增函数。

线程终止有通用实现，但某些架构需要专用处理。例如 Cortex-M 因致命异常终止线程时，还必须退出处理程序模式，而正常入口返回时不需要。原文要求按需提供架构版本的终止处理并选择 `CONFIG_ARCH_HAS_THREAD_ABORT`，可参考 Cortex-M Kconfig。

### 27.4.1\_线程局部存储

支持 TLS 需要完成四项工作：

1. 实现 `arch_tls_stack_setup()`，按工具链要求建立栈中的 TLS 区域。`z_tls_data_size()` 返回变量本身所需大小，不含架构/工具链附加数据；`z_tls_copy()` 只准备线程局部变量内容，不处理那些附加数据。
2. 切换时从新线程 `struct k_thread.tls` 取得 TLS 区域地址，写入工具链与架构约定的寄存器或其他位置。
3. 在架构 Kconfig 中加入 `select ARCH_HAS_THREAD_LOCAL_STORAGE`。
4. 运行 `tests/kernel/threads/tls` 验证新实现。

## 27.5\_必需设备驱动

内核所需硬件很少：理论上只要中断控制器即可，不一定需要系统时钟。但实际运行多数内核测试需要时钟，这两类设备通常与架构绑定，因此属于移植工作。

### 27.5.1\_中断控制器

不同架构的控制器与编号规则差异很大。原文以 x86 的中断描述符表 IDT 及不同中断控制器为例，并称向量位置决定优先级；Cortex-M 的 NVIC 属于架构定义，不需要额外独立 IDT，硬件 IRQ 优先级按条目编程，与向量位置无直接关系。

> 译注：x86 优先级还取决于实际中断控制器及其配置，不能把 IDT 位置概述推广到所有 x86 中断来源。

ARCv2 的中断单元也属于架构，类似 NVIC，但异常号与中断号一一对应，例如异常 1 就是 IRQ1，设备中断从 16 开始；Arm 中 IRQ0 对应异常 16，异常 1 可按编号差表示为 IRQ-15。这些差异使控制器实现很少能跨架构共享。

### 27.5.2\_系统时钟与串口控制台

x86 有 APIC 定时器和 HPET，Cortex-M 有 SysTick，ARCv2 有 timer0/1。内核超时在系统时钟驱动 ISR 上下文处理。

另一个虽非必需却极有价值的设备是简单的轮询、只输出串口驱动，用来发送 `printk` / `printf` 调试信息。也可启用 `CONFIG_RAM_CONSOLE`，将输出写入环形内存缓冲区，由调试器读取。

## 27.6\_工具函数、空闲与故障

现代 CPU 可用少量指令或无锁方式实现一些常用操作，架构移植需要提供这些基础能力。

### 27.6.1\_工具函数

有硬件原子指令时，可通过 `CONFIG_ATOMIC_OPERATIONS_ARCH` 选择架构实现；没有时可用 `CONFIG_ATOMIC_OPERATIONS_C`，由通用实现把中断锁包在普通操作外。

查找最低/最高置位位也需要实现；没有指令时可用通用 C。允许使用编译器内建函数，但必须注意所需编译器屏障。

### 27.6.2\_CPU空闲与省电

必须提供 `arch_cpu_idle()` 与 `arch_cpu_atomic_idle()`。前者可在适当解除中断锁后执行省电指令，例如 x86 `hlt`、Arm `wfi` / `wfe`、ARC `sleep`。

普通空闲适合不在意“进入休眠前先被中断”的循环，例如单线程系统初始化后只剩空循环，或内核空闲线程。原子空闲则必须原子地重新允许中断并进入省电，适合单线程系统某些真实应用等待场景。

通常应把 CPU 空闲交给空闲线程，应用只有特殊情形才直接使用。原文允许最低限度的实现仅解除中断锁并执行 NOP，但强烈建议真正实现省电路径。

> 译注：必须遵守目标 **应用程序编程接口（Application Programming Interface，API）** 的中断键和原子性合同；不应把“解除中断后执行 NOP”的最低限度退化行为作为完整低功耗功能宣称。多线程同步等待应优先使用相应内核对象。

### 27.6.3\_故障与链接

未处理的 CPU 异常需要调用 `z_fatal_error()`，输出架构无关信息并进入可覆盖的系统致命错误策略。原文将策略函数写为 `k_sys_fatal_error()`，默认行为是锁中断后永久自旋，也可以由应用选择支持的关机等策略。

> 译注：本地声明使用 `k_sys_fatal_error_handler()`；完整规则见[致命错误处理](../kernel/P030_致命错误处理.md)，不要混用旧符号。

工具链支持需加入构建系统，可能在 `include/zephyr/toolchain/gcc.h` 增加架构定义。每架构还需要链接脚本，可复用其他架构的多数段，但有自身特殊部分，原文举例 Arm 的 SCB 段和 x86 的 IDT 段。

## 27.7\_内存管理与映射

目标平台使用分页且要求驱动映射 I/O 区域时，启用 `CONFIG_MMU`，并实现 `arch_mem_map()`、`arch_mem_unmap()` 与 `arch_page_phys_get()`。

## 27.8\_栈对象布局

硬件内存保护会影响栈对象创建。所有架构都要定义 `ARCH_STACK_PTR_ALIGN`，满足 CPU 与 ABI 的组合要求，常见为 4、8 或 16 字节。

栈分两种：`K_KERNEL_STACK_DEFINE()` 等定义的内核栈只承载监督线程或中断异常，通常对齐较宽松、保留数据较少，不预留特权提升栈；普通线程栈还可承载用户线程，因此通常更大。关闭 `CONFIG_USERSPACE` 时两者等价。

### 27.8.1\_对齐、保留区与运行时扣除

架构可定义栈对象对齐、非缓冲区保留数据大小，以及为用户模式向上调整栈大小的宏。原文列出的默认规则是：`ARCH_KERNEL_STACK_RESERVED` 与 `ARCH_THREAD_STACK_RESERVED` 默认无保留；`ARCH_KERNEL_STACK_OBJ_ALIGN` 与 `ARCH_THREAD_STACK_OBJ_ALIGN` 默认按 `ARCH_STACK_PTR_ALIGN` 对齐；栈大小默认向上取整到同一粒度。

> 译注：原文在默认规则处将大小宏写成 `ARCH_THREAD_STACK_SIZE_ALIGN`，后文和本地头文件使用的是 `ARCH_THREAD_STACK_SIZE_ADJUST()`。应按当前接口实现大小调整。

创建栈的宏都基于这些定义。栈对象前部为保留内存，后部为实际栈缓冲区；某些边界构建时确定，另一些依线程上下文在运行时确定。

架构可能在运行时从缓冲区扣除一部分区域，而非始终在构建时预留，或在已有保留区之外补充，例如 Arm FPU。扣除结果由 `thread.stack_info.start` 跟踪。`start` 与 `size` 描述的区域必须可完整授予用户线程访问；`delta` 用于从栈末尾计算初始栈指针，考虑 TLS 数据和地址空间布局随机化（ASLR）偏移。

```text
+---------------------+ <- thread.stack_obj
| Reserved Memory     | } K_(THREAD|KERNEL)_STACK_RESERVED
+---------------------+
| Carved-out memory   |
|.....................| <- thread.stack_info.start
| Unused stack buffer |
|                     |
|.....................| <- thread's current stack pointer
| Used stack buffer   |
|                     |
|.....................| <- Initial stack pointer. Computable
| ASLR Random offset  |      with thread.stack_info.delta
+---------------------| <- thread.userspace_local_data
| Thread-local data   |
+---------------------+ <- thread.stack_info.start + thread.stack_info.size
```

图中依次是保留内存、动态扣除区、未用/已用栈、随机偏移和线程局部数据。Zephyr 原文说明目前不支持向高地址增长的栈。没有内存保护时，默认布局即可。

### 27.8.2\_硬件栈溢出检测

`CONFIG_HW_STACK_PROTECTION` 使用硬件使监督模式栈溢出产生致命错误，平台必须具备能力并选择 `CONFIG_ARCH_HAS_STACK_PROTECTION`。

检测不意味着系统状态仍可靠：溢出可能发生在关键数据结构修改途中；有限保护区也可能被大跨度越界跳过，先破坏邻近数据再被检测。任何监督模式溢出，包括系统调用期间的溢出，都应视为致命错误，不能假定内核完好。

该配置与 `CONFIG_USERSPACE` 正交。用户模式栈越界从内核角度可以隔离处理，无须依赖此监督栈保护开关。

支持两类实现：专用 CPU 界限寄存器，例如 Arm SPLIM，可采用默认布局；或在栈缓冲区前放只读保护区域，写入时产生异常。

后者需要把 `ARCH_KERNEL_STACK_RESERVED` 设为保护区域最小大小，原文以多数 Arm **内存保护单元（Memory Protection Unit，MPU）** 的 32 字节为例，并设置对应 `ARCH_KERNEL_STACK_OBJ_ALIGN`。**内存管理单元（Memory Management Unit，MMU）** 系统不应为保护区占用实际 RAM，而应在映射中保留一个不存在的虚拟页；栈对象仍按页大小对齐和取整。

```text
+-----------------------------+ <- thread.stack_obj
| Guard reserved memory       | } K_KERNEL_STACK_RESERVED
+-----------------------------+
| Guard carve-out             |
|.............................| <- thread.stack_info.start
| Stack buffer                |
.                             .
```

内核栈的动态保护区扣除应尽量避免，主要有两种必要情况：同一栈以后可能用于用户线程，而用户栈不需要原先的监督保护；或保护大小随上下文变化。例如 Arm 延迟浮点压栈可能一次大幅减小 SP 却暂不写内存，跨过最小保护区。此时可只对使用浮点的线程额外扣除较大区域，而非所有栈都无条件预留。

### 27.8.3\_用户模式新增要求

用户线程需要不可访问的固定大小特权栈，大小为 `CONFIG_PRIVILEGED_STACK_SIZE`，供内核处理系统调用；需要保护时还要在此前放保护区，必要时支持动态扣除。

保护硬件必须能精确覆盖 `thread.stack_info` 所描述的用户栈缓冲区。因此 `ARCH_THREAD_STACK_SIZE_ADJUST()` 要按硬件粒度向上调整大小，`ARCH_THREAD_STACK_OBJ_ALIGN()` 也要相应对齐。

旧 MPU 常要求区域大小是 2 的幂、并按自身大小对齐，由 `CONFIG_MPU_REQUIRES_POWER_OF_TWO_ALIGNMENT` 表示。无论何种情况，`thread.stack_info` 必须始终准确指向可授予用户访问的部分。

### 27.8.4\_不要求2的幂的区域

无需 2 的幂对齐时，`K_THREAD_STACK_RESERVED` 可容纳特权栈，布局例如：

```text
+------------------------------+ <- thread.stack_obj
| Other platform data          |
+------------------------------+
| Guard region (if enabled)    |
+------------------------------+
| Guard carve-out (if needed)  |
|..............................|
| Privilege elevation stack    |
+------------------------------| <- thread.stack_obj +
| Stack buffer                 |      K_THREAD_STACK_RESERVED =
.                              .      thread.stack_info.start
```

创建线程时把保护区及必要扣除区设置为只读。对监督线程，特权提升区域也可作为额外栈空间，溢出最终触及保护区；对用户线程，只授予后面的用户栈缓冲区权限，前后的区域均不可访问。用户溢出会触及不可访问的特权栈，系统调用栈溢出则触及保护区。

MMU 系统无需物理保护区：特权栈映射到内核空间，用户栈映射到用户空间，各自下方留不存在的虚拟保护页。

保护区之前可以放其他平台数据，但若能放在 `thread.arch` 就不建议如此。`ARCH_THREAD_STACK_RESERVED` 必须涵盖这些数据、特权栈和保护区，并使其后能立即放置满足硬件对齐的用户栈映射。

### 27.8.5\_要求2的幂的区域

为紧凑安排内存，线程栈对象必须按相同的 2 的幂大小及边界对齐，不带固定保留区。保护区全部从缓冲区动态扣除，特权栈分配在别处。

原文要求 `ARCH_THREAD_STACK_SIZE_ADJUST()` 与 `ARCH_THREAD_STACK_OBJ_ALIGN()` 使用 `Z_POW2_CEIL()`，`K_THREAD_STACK_RESERVED` 为 0。

启用 `CONFIG_GEN_PRIV_STACKS` 后，为系统发现的每个线程栈生成对应固定大小内核特权栈。运行时根据线程栈地址通过 `z_priv_stack_find()` 快速查找，特权栈布局与其他内核专用栈相同：

```text
+-----------------------------+ <- z_priv_stack_find(thread.stack_obj)
| Reserved memory             | } K_KERNEL_STACK_RESERVED
+-----------------------------+
| Guard carve-out (if needed) |
|.............................|
| Privilege elevation stack   |
|                             |
+-----------------------------+ <- z_priv_stack_find(thread.stack_obj) +
                                     K_KERNEL_STACK_RESERVED +
                                     CONFIG_PRIVILEGED_STACK_SIZE

+-----------------------------+ <- thread.stack_obj
| MPU guard carve-out         |
| (supervisor mode only)      |
|.............................| <- thread.stack_info.start
| Stack buffer                |
.                             .
```

线程栈对象中的保护扣除只在监督模式时使用。线程降为用户模式后，不再使用这块监督保护区，整个对象作为用户栈缓冲区，并相应更新 `thread.stack_info`。

## 27.9\_用户模式线程

架构选择 `CONFIG_ARCH_HAS_USERSPACE`，并实现以下内核到架构接口：

| 接口 | 职责 |
| --- | --- |
| `arch_buffer_validate()` | 验证当前线程对指定内存范围的访问权限。 |
| `arch_user_mode_enter()` | 不可逆地把监督线程降为用户模式，并清理栈内容。 |
| `arch_syscall_oops()` | 系统调用参数验证失败时生成 oops，报告位置应表现为用户线程调用系统调用的位置。 |
| `arch_syscall_invoke0()` 至 `arch_syscall_invoke6()` | 按参数数量发起系统调用，提升特权时通过寄存器传参。 |
| `arch_is_user_context()` | CPU 当前处于用户模式时返回非零。 |
| `arch_mem_domain_max_partitions_get()` | 报告内存域最大分区数；MPU 受区域数约束，原文称 MMU 无此硬件区域数限制。 |

> 译注：MMU 不受同样的少量 MPU 区域限制，并不表示页表、地址空间和软件配置没有资源上限。

某些架构在内存域操作时，需要同步更新软件管理结构或其他 CPU 的寄存器。此时选择 `CONFIG_ARCH_MEM_DOMAIN_SYNCHRONOUS_API`，实现 `arch_mem_domain_thread_add()`、`arch_mem_domain_thread_remove()`、`arch_mem_domain_partition_add()`、`arch_mem_domain_partition_remove()`；这在 MMU 系统较常见，MPU 系统较少见。

还必须处理：新建带 `K_USER` 的线程以用户模式运行；切换时撤销旧线程栈用户权限并授予新线程栈权限，切换相应内存域；为每线程提供用户永不可访问、足以处理任何系统调用的固定大小特权栈。

建立软件中断或其他特权提升机制，与架构调用入口配合。根据调用 ID 在 `_k_syscall_table` 查找处理程序，非法 ID 转入 `K_SYSCALL_BAD`。返回用户模式前必须防止内核寄存器状态泄漏。

## 27.10\_GDB调试桩

新架构支持远程 GDB stub，需要上下文保存、入口出口、寄存器操作、断点及可访问内存描述。

### 27.10.1\_上下文与入口

在 `include/zephyr/arch/<arch>/gdbstub.h` 定义 `struct gdb_ctx`，至少包含名为 `exception` 的 `unsigned int` 字段，表示异常原因；其他成员按架构需要增加。

进入 `z_gdb_main_loop()` 前必须设置 `exception`，并传入上下文指针，该指针继续传给其他调试桩函数。

若通过中断响应断点，要实现相应 ISR 作为入口。入口保存原执行上下文，再进入命令主循环；退出恢复上下文，使程序可像没有断点一样继续运行。

### 27.10.2\_初始化、继续与单步

`arch_gdb_init()` 初始化上下文、连接调试中断等，并通过架构手段暂停执行，以允许启动阶段连接 GDB。

`arch_gdb_continue()` 对应 GDB 的 `c` / `continue`，继续运行；`arch_gdb_step()` 对应 `si` / `stepi`，执行一条机器指令后回到调试提示。

### 27.10.3\_寄存器读写

调试桩运行在目标上，不能把用户要求修改的寄存器立即写进正在运行调试桩的硬件上下文。应把被调试线程寄存器先保存，读写操作只修改副本，恢复目标线程时才写回硬件。

- `arch_gdb_reg_readall()`：收集 `g/G` 数据包所需寄存器，布局由架构和 GDB 协议决定。多数架构必须返回正确长度，否则 GDB 会终止会话。
- `arch_gdb_reg_writeall()`：把 GDB 发来的 `G` 包值写入待恢复的寄存器副本。
- `arch_gdb_reg_readone()`：读取单个寄存器值返回 GDB。
- `arch_gdb_reg_writeone()`：按 GDB 给定值修改单个寄存器副本。

### 27.10.4\_断点与内存区域

`arch_gdb_add_breakpoint()` / `arch_gdb_remove_breakpoint()` 管理架构断点。软件断点类型为 0，GDB 通常自行把目标指令替换为陷入指令，命中后恢复，因此架构通常无须额外实现。

代码在不可运行时修改的 ROM/Flash 中，则需要类型 1 的硬件断点；具体配置见架构资料。架构不支持硬件断点时可以不实现，GDB 会依赖软件断点。

某些内存区域不可访问时，应定义 `gdb_mem_region` 类型数组 `gdb_mem_region_array`，描述允许访问的范围。每项包含 `start`、`end`、`attributes` 和 `alignment`：属性为 `GDB_MEM_REGION_RO` 或 `GDB_MEM_REGION_RW`；无需对齐、可逐字节访问时 `alignment` 设为 0。
