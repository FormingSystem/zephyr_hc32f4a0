# 第2章\_核心转储

原文：[Core Dump](https://docs.zephyrproject.org/latest/services/debugging/coredump.html)。读取日期：2026-10-12，`latest`。

**核心转储（Core Dump）**模块导出 **中央处理器（Central Processing Unit，CPU）** 寄存器和内存内容，供离线调试。发生致命错误时调用该模块，按启用的后端输出或保存数据。

## 2.1\_配置

通过 `DEBUG_COREDUMP` 启用模块。输出后端选项如下：

| 选项 | 作用 |
| --- | --- |
| `DEBUG_COREDUMP_BACKEND_LOGGING` | 通过日志模块输出 |
| `DEBUG_COREDUMP_BACKEND_LOGGING_UDP` | 日志后端并可选用原始 UDP 传输；对端由 `DEBUG_COREDUMP_LOGGING_UDP_HOST` 字符串指定，经 `net_ipaddr_parse()` 解析，支持 IPv4/IPv6 和可选端口，省略端口时为 UDP 17777 |
| `DEBUG_COREDUMP_BACKEND_FLASH_PARTITION` | 保存到 Flash 分区 |
| `DEBUG_COREDUMP_BACKEND_NULL` | 其他后端无法启用时的回退，所有输出丢弃 |

UDP 收集端使用 [coredump_udp_receiver.py](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/coredump/coredump_udp_receiver.py) 生成二进制文件，再交给 [coredump_gdbserver.py](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/coredump/coredump_gdbserver.py)。

内存转储范围有三种选择：

| 选项 | 范围 |
| --- | --- |
| `DEBUG_COREDUMP_MEMORY_DUMP_MIN` | 仅异常线程栈、线程结构及支持调试器回溯栈所需的最少其他数据；只在确实要求最小转储时使用 |
| `DEBUG_COREDUMP_MEMORY_DUMP_THREADS` | 所有线程的结构、栈和调试线程所需数据 |
| `DEBUG_COREDUMP_MEMORY_DUMP_LINKER_RAM` | `_image_ram_start[]` 与 `_image_ram_end[]` 之间的区域，至少包含 data、noinit 和 BSS；这是默认选择 |

即使选择最小范围，也可以通过一个或多个[核心转储设备](https://docs.zephyrproject.org/latest/hardware/peripherals/coredump.html#coredump-device-api)加入额外内存。

> 译注：本节沿用原文 Kconfig 符号名。在 `prj.conf` 等配置片段中赋值时，使用相应 `CONFIG_` 前缀，例如 `CONFIG_DEBUG_COREDUMP=y`。

## 2.2\_使用流程

模块在致命错误时保存的数据可以交给专门的 GDB 服务器，再让 GDB 或兼容调试器以远程目标方式连接，检查寄存器、内存和栈。通常按下列步骤操作：

1. 按所用后端取得设备转储；日志后端就收集日志输出。
2. 转换为服务器可解析的二进制格式。串口日志使用 [coredump_serial_log_parser.py](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/coredump/coredump_serial_log_parser.py)；UDP 后端在收集主机运行接收脚本，重组为相同原始二进制格式。
3. 将转储二进制与 Zephyr **可执行与可链接格式（Executable and Linkable Format，ELF）** 文件传给 `scripts/coredump/coredump_gdbserver.py`，启动服务器；也可从 GDB 内启动。
4. 启动与目标架构对应的调试器。

> 原文注意：Intel ADSP CAVS 15–25 平台在 `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` 时，应使用 **软件开发工具包（Software Development Kit，SDK）** 的 `xtensa-intel_apl_adsp` 工具链调试器。
>
> 译注：ELF 应来自生成该转储的同一次固件构建，否则符号、地址和栈解析可能不匹配。离线转储只包含故障时收集的数据，并不代表仍连接着运行中的设备。

Flash 分区后端需要在设备树中定义分区：

```dts
&flash0 {
   partitions {
      coredump_partition: partition@255000 {
         label = "coredump-partition";
         reg = <0x255000 DT_SIZE_K(4)>;
      };
   };
};
```

> 译注：`0x255000` 和四 KiB 仅为原文示例，实际分区必须适合目标 Flash 容量、擦除布局与镜像安排；这里没有为 HC32 分配实际转储区域。

```shell

./scripts/coredump/coredump_gdbserver.py build/zephyr/zephyr.elf coredump.bin
```

```shell
<path to SDK>/x86_64-zephyr-elf/bin/x86_64-zephyr-elf-gdb build/zephyr/zephyr.elf
```

## 2.4\_从GDB内部启动服务器

`target remote |` 可以直接启动专用服务器，无须额外 shell。先启动 GDB：

```shell
<path to SDK>/x86_64-zephyr-elf/bin/x86_64-zephyr-elf-gdb build/zephyr/zephyr.elf
```

再以 `--pipe` 启动服务器：

```text
(gdb) target remote | ./scripts/coredump/coredump_gdbserver.py --pipe build/zephyr/zephyr.elf coredump.bin
```

## 2.5\_文件格式

转储二进制由一个文件头、一个架构专用块、零或一个线程元数据块，以及多个内存块组成。以下头部中的所有数值采用小端序。

### 2.5.1\_文件头

| 字段 | 数据类型 | 说明 |
| --- | --- | --- |
| ID | `char[2]` | 文件标识字符 `Z`、`E` |
| Header version | `uint16_t` | 头部版本；结构变化时递增，使解析器能够拒绝不兼容旧版而非错误解析 |
| Target code | `uint16_t` | 架构或 **片上系统（System on Chip，SoC）** 目标编码，选择正确的寄存器块解析器 |
| Pointer size | `uint8_t` | 指针位宽的二进制指数，例如三十二位为 5、六十四位为 6，用于解析内存地址 |
| Flags | `uint8_t` | 标志；原页未进一步说明 |
| Fatal error reason | `unsigned int` | 致命错误原因，与 [include/zephyr/fatal.h](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/fatal.h) 中 `enum k_fatal_error_reason` 一致 |

> 译注：原文把 Pointer size 写作 `uintptr_t` 大小的 2 次幂形式；结合其 5/6 示例，这里明确为位宽指数，不是直接记录四/八字节。

### 2.5.2\_架构专用块

该块存储 CPU 寄存器等目标专有信息：

| 字段 | 数据类型 | 说明 |
| --- | --- | --- |
| ID | `char` | `A` 表示架构专用块 |
| Header version | `uint16_t` | 块版本，由相应目标解析器解释 |
| Number of bytes | `uint16_t` | 头部之后的目标数据字节数 |
| Register byte stream | `uint8_t[]` | 目标架构专用数据；格式由目标实现决定，仅由其解析器处理 |

### 2.5.3\_线程元数据块

该块存储调试线程所需数据：

| 字段 | 数据类型 | 说明 |
| --- | --- | --- |
| ID | `char` | `T` 表示线程元数据块 |
| Header version | `uint16_t` | 头部版本；结构改变需递增，以防错误解析旧格式 |
| Number of bytes | `uint16_t` | 头部之后的数据流长度 |
| Byte stream | `uint8_t[]` | 调试线程所需数据 |

### 2.5.4\_内存块

每个内存块包含区域起止地址及内容：

| 字段 | 数据类型 | 说明 |
| --- | --- | --- |
| ID | `char` | `M` 表示内存块 |
| Header version | `uint16_t` | 头部版本；结构改变需递增 |
| Start address | `uintptr_t` | 内存区域起始地址 |
| End address | `uintptr_t` | 内存区域结束地址 |
| Memory byte stream | `uint8_t[]` | 起止地址之间的内存内容 |

## 2.6\_增加新目标

架构专用块需要目标对应的转储函数和解析器，新增目标按以下过程实现：

1. 在 [include/zephyr/debug/coredump.h](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/debug/coredump.h) 的 `enum coredump_tgt_code` 中增加编码。
2. 实现 `arch_coredump_tgt_code_get()`，返回新编码。
3. 实现 `arch_coredump_info_dump()`，构造架构专用块，并调用 `coredump_buffer_output()` 输出到后端。
4. 在 `scripts/coredump/gdbstubs/` 增加解析器，继承 `gdbstubs.gdbstub.GdbStub`。在 `__init__` 中把异常对应的 GDB 信号保存到 `self.gdb_signal`；解析 `self.logfile.get_arch_data()`，格式必须与第三步生成的块一致；实现抽象方法 `handle_register_group_read_packet`，返回 GDB 预期的寄存器组，具体格式查 GDB 对该目标的代码与文档。对于 `g` 包未覆盖的寄存器，可另实现 `handle_register_single_read_packet`。
5. 扩展 [gdbstubs/__init__.py](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/coredump/gdbstubs/__init__.py) 中的 `get_gdbstub()`，返回新增实现。
