# 第4章\_west工作区

原文：[Workspaces](https://docs.zephyrproject.org/latest/develop/west/workspaces.html)。读取日期：2026-10-12，`latest`。本页进一步解释基本概念中介绍的 west 工作区。

## 4.1\_manifest-rev分支

west 在每个项目中创建并控制名为 `manifest-rev` 的 Git 分支。它指向最后一次执行 `west update` 时，清单为该项目指定的修订。其他工作区管理命令可以用它表示最近更新所对应的上游修订；该分支也使清单能够直接以 SHA 指定项目修订。

虽然它是普通 Git 分支，west 会在下一次更新时重建或重置它。因此自行检出、修改它是危险的：手工添加到这个分支的提交可能在下次 `west update` 时丢失。应使用另一个名字创建自己的分支，然后在需要时将该分支变基到新的 `manifest-rev`，或者把 `manifest-rev` 合入自己的分支。

west 不会在清单仓库中创建 `manifest-rev`，因为它不管理清单仓库的分支与修订。

## 4.2\_refs/west引用

west 还为自己保留项目本地仓库中所有以 `refs/west/` 开头的 Git 引用，例如 `refs/west/foo`。与 `manifest-rev` 不同，它们不是普通分支。其行为属于实现细节，使用者不应依赖这些引用一定存在或具有某种固定行为。

## 4.3\_在Git仓库中开发

west 项目就是普通 Git 仓库。默认情况下，west 只创建和更新 `manifest-rev` 与 `refs/west/` 下的引用。你创建的分支由你自己管理；只有显式请求 `west update --rebase`，west 才会对它们进行变基。

这也解释了普通 `west update` 为什么留下游离 `HEAD`：它检出新的 `manifest-rev` 所指修订，并让你的分支保持原位。设计原因见[west update 的 detached HEAD 说明](https://docs.zephyrproject.org/latest/develop/west/why.html)。

Zephyr 模块与 west 项目不同，虽然很多 west 项目也是模块。下面的 Git 流程适用于所有 west 项目，不论它是否属于 Zephyr 模块。

有本地改动时，可以采用下列流程：

1. 在项目仓库创建分支，并像平常一样提交修改：

```text
git -C <repository-path> switch --create <your-branch>
```

2. 在工作区内更新，并查看发生了什么变化：

```text
west update --rebase
west compare
```

此时保持你的分支为当前分支，并将它变基到新的 `manifest-rev`。这是 west 修改你自己的分支的时机；有冲突时命令失败，按普通 Git 方法解决。

3. 如果不希望 west 进行变基，普通 `west update` 会切离你的分支，除非由此引起 Git 冲突。另一个选项是 `west update --keep-descendants`；原文将其描述为一个不会失败的第三种分支处理选择。具体见 `west update --help` 中的 `checked out branch behavior` 选项组及[命令说明](https://docs.zephyrproject.org/latest/develop/west/built-in.html#west-update)。

> 译注：“不会失败”应放在当前分支处理策略的语境中理解，不能据此断言网络获取、磁盘读写等其他步骤不会失败。

### 4.3.1\_不要在游离HEAD上直接提交

不要直接在 `west update` 留下的游离 `HEAD` 上提交。Git 会提醒这些提交无法从任何分支到达，以后可能被垃圾回收。应为工作建立分支，或使用专为无分支工作设计的其他 Git 客户端，例如 [JJ](https://www.jj-vcs.dev/)。

## 4.4\_私有仓库

west 可以获取私有仓库，这并不需要 west 特有的功能。

当项目的 `manifest-rev` 需要指向新取得的提交时，`west update` 实质上会执行 `git fetch YOUR_PROJECT_URL`。确保获取成功是当前 Git 环境的职责。

可以手动输入认证信息，也可使用 [Git 内置凭据助手](https://git-scm.com/docs/gitcredentials)。Git 已经提供凭据管理，因此无须另设 west 专用机制。

### 4.4.1\_通过HTTPS获取

原文描述：Windows 上较新的 Git，在默认安装下首次从 GitHub 获取时会打开图形窗口要求认证，并保存凭据供后续使用，因此完成首次认证后通常可以免去重复输入。

一般也可以使用 Git 的 `store` 凭据助手把凭据保存在磁盘，详见 [git-credential-store](https://git-scm.com/docs/git-credential-store)。以下是原文的独立选择，不能把它们当作全部必做步骤。

对工作区中的所有仓库设置：

```text
west forall -c "git config credential.helper store"
```

仅对 `foo` 和 `bar` 项目设置：

```text
west forall -c "git config credential.helper store" foo bar
```

对当前用户全局设置：

```text
git config --global credential.helper store
```

原文还介绍 GitHub 个人访问令牌（Personal Access Token，PAT）作为账户密码的替代，并指出双因素认证可能要求使用令牌；即使未启用双因素认证，令牌也可能优于存储账户明文密码。其凭据存储示例为：

```bash
# 原文示例：GH_TOKEN 代表事先取得的令牌；不是实际凭据。
echo "https://x-access-token:$GH_TOKEN@github.com" >> ~/.git-credentials
```

> 译注：`store` 会将凭据以明文保存在磁盘；以上保留上游示例，不是当前项目必做配置，也没有在本机执行。GitHub 的实际认证方式应按其[个人访问令牌文档](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)选择，不能把这份页面的历史“账户密码”表述理解为现行 Git HTTPS 登录步骤。

不希望把凭据写入文件系统时，可通过 [git-credential-cache](https://git-scm.com/docs/git-credential-cache)暂存在内存。

如果已经配置 SSH，还可用 Git 的 URL 重写，让 GitHub 的 HTTPS URL 改走 SSH：

```bash
# 修改当前用户的 Git 全局 URL 重写规则；适用于希望统一走 SSH 的场景。
git config --global url."git@github.com:".insteadOf "https://github.com/"
```

### 4.4.2\_通过SSH获取

SSH 密钥没有口令时，获取通常可直接工作。密钥带口令时，可以使用 ssh-agent，避免每次手工输入。GitHub 的配置及密钥生成见[使用 SSH 连接 GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh)。

## 4.5\_项目位置

项目可以位于工作区内部任何位置，但不能“逃出”工作区。项目既不必都放在清单仓库的子目录，也不必都直接位于 topdir 下；路径只需位于工作区内。

可以自行把工作区内的项目目录替换成指向计算机其他位置的符号链接，但 west 不会替你完成这件事。

## 4.6\_受支持的拓扑

下面是 west 支持的三种源码组织示例。

### 4.6.1\_T1：以Zephyr为中心的星形拓扑

Zephyr 仓库是中心仓库，并在自己的 `west.yml` 中指定模块。可类比为以 Zephyr 为主项目的 Git 子模块组织。

这是默认布局，主线上游 Zephyr 和前文的工作区示例采用这种方式。

### 4.6.2\_T2：以应用为中心的星形拓扑

适合围绕单个应用开发的场景。应用仓库成为中心，并在 `west.yml` 中列出构建所需项目，包括 Zephyr 和其他模块。可类比为应用是 Git 主项目，而 Zephyr 和其他项目是子模块。

```text
west-workspace/
├── application/             # 清单仓库，west 创建后不修改其内容
│   ├── CMakeLists.txt
│   ├── prj.conf
│   ├── src/
│   │   └── main.c
│   └── west.yml             # 主清单，可含导入及覆盖项
├── modules/
│   └── lib/
│       └── zcbor/           # 来自主清单或导入清单的 Git 项目
└── zephyr/                  # Git 项目
    └── west.yml             # 可以较低优先级部分导入，或完全忽略
                            # 只可导入 manifest-rev 修订中的版本
```

从 west 0.7 起可使用清单导入。例如在 `application/west.yml` 中导入 Zephyr v2.5.0 及其模块：

```yaml
# T2 清单示例；这是应用清单文件内容，不是替换 Zephyr 的官方 west.yml。
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v2.5.0
      import: true
  self:
    path: application
```

采用 `import` 仍可以有选择地覆盖个别 Zephyr 模块，见[清单导入示例](https://docs.zephyrproject.org/latest/develop/west/manifest.html)。

另一种达到相同目的的方法，是把 Zephyr 清单内容复制到应用清单，并加上 Zephyr 项目自身的条目：

```yaml
# 与上例等价，但 Zephyr 模块由应用清单手工维护。
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
  defaults:
    remote: zephyrproject-rtos
  projects:
    - name: zephyr
      revision: v2.5.0
      west-commands: scripts/west-commands.yml
    - name: net-tools
      revision: some-sha-goes-here
      path: tools/net-tools
    # ... 在这里列出其他 Zephyr 模块 ...
  self:
    path: application
```

`west-commands` 用于发现构建、烧录、调试等 Zephyr 扩展；使用 `import` 时不必显式添加。

导入的主要优势是无须单独跟踪每个被导入项目的修订：模块版本自动来自对应 Zephyr 修订中的 `west.yml`，不必手工复制和维护。

> 译注：两段均为原文的旧版本清单示例；占位修订必须替换为实际修订才可使用。它们用于解释应用仓库的组织方式，不要求新建、覆盖或修改当前实验源码中的官方 `west.yml`。

### 4.6.3\_T3：森林拓扑

适合支持多个独立应用，或者没有单一“中心”代码仓库的下游发行版。专用清单仓库不包含 Zephyr 源码，其他项目处于同一层级；可类比 Google repo 管理的源码发行。

```text
west-workspace/
├── app1/                    # Git 项目
│   ├── CMakeLists.txt
│   ├── prj.conf
│   └── src/
│       └── main.c
├── app2/                    # Git 项目
│   ├── CMakeLists.txt
│   ├── prj.conf
│   └── src/
│       └── main.c
├── manifest-repo/           # 清单仓库，west 创建后不修改其内容
│   └── west.yml             # 主清单，可含导入和覆盖项
├── modules/
│   └── lib/
│       └── zcbor/           # 来自主清单或导入清单的项目
└── zephyr/                  # Git 项目
    └── west.yml             # 可按较低优先级导入或忽略
                            # 只能导入 manifest-rev 中的版本
```

下面的 `manifest-repo/west.yml` 导入 Zephyr v2.5.0 及其模块，然后加入 `app1`、`app2`：

```yaml
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
    - name: your-git-server
      url-base: https://git.example.com/your-company
  defaults:
    remote: your-git-server
  projects:
    - name: zephyr
      remote: zephyrproject-rtos
      revision: v2.5.0
      import: true
    - name: app1
      revision: SOME_SHA_OR_BRANCH_OR_TAG
    - name: app2
      revision: ANOTHER_SHA_OR_BRANCH_OR_TAG
  self:
    path: manifest-repo
```

同样可以参照 T2 手工复制 Zephyr 的项目清单，但也会有同样的手工维护负担。

## 4.7\_不受支持：顶层目录本身也是Git仓库

有些使用者希望工作区顶层本身是 Git 仓库，例如：

```text
my-workspace/                # 工作区顶层目录
├── .git/                    # 把整个工作区纳入一个 Git 仓库
├── .west/                   # 标识工作区顶层
└── [ ... other projects ...]
```

这不是官方支持的拓扑。west 的设计假定工作区 topdir 本身不是 Git 仓库。你可能让某种类似配置满足自己的目标，但未来 west 的变更可能破坏它。
