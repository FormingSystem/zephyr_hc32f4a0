# 第7章\_使用west构建、烧录与调试

原文：[Building, Flashing and Debugging](https://docs.zephyrproject.org/latest/develop/west/build-flash-debug.html)。读取日期：2026-10-12，`latest`。本章连同原页的 runner Python API 一并翻译。

Zephyr 提供 west 扩展命令，用于构建、烧录及调试程序，包括 `build`、`flash`、`debug`、`debugserver`、`rtt` 和 `attach`。板级维护者如何接入这些命令，见[板级移植指南](https://docs.zephyrproject.org/latest/hardware/porting/board_porting.html#flash-and-debug-support)。

> 译注：以下命令以已有 Zephyr 工作区、所需模块和工具链为前提。构建操作在应用目录、源码根或明确指定的构建目录进行；烧录还要求目标板和对应主机工具可用。按实际目标与工具支持情况选择示例中的组合，路径相对于自己使用的源码或构建目录解析。本章没有执行构建或硬件操作。

## 7.1\_构建：west build

运行 `west build -h` 可查看帮助。默认行为适合增量构建：若当前目录已经是构建目录，或包含名为 `build` 的构建目录，west 直接在该目录继续构建；否则，它把当前目录作为应用源码目录，创建构建目录并开始构建。

### 7.1.1\_基本用法与开发板选择

在包含应用 `CMakeLists.txt` 的源码根执行：

```text
west build -b <BOARD>
```

`<BOARD>` 与直接调用 CMake 时 `-DBOARD` 的值相同；`west boards` 可列出开发板。第一次构建时，west 调用 CMake 建立构建系统，默认使用 `build` 目录。再次调用则进行增量构建，除非有需要重新配置的变化或显式使用 `--cmake`，否则不重新运行 CMake。

已有构建目录中的板名称记录在 CMake 缓存里，不必每次传 `--board`。新构建的选择顺序为：命令行 `--board`、环境变量 `BOARD`、west 配置项 `build.board`。

强制重新运行 CMake：

```text
west build -c
```

设定默认开发板：

```text
west config build.board reel_board
```

通过 [sysbuild](https://docs.zephyrproject.org/latest/build/sysbuild/index.html) 可以构建多个 domain，每个 domain 对应一个独立的 Zephyr 构建系统；这些映像可用于单板或多板。传入 `--sysbuild` 启用，或用 `build.sysbuild` 配置默认启用；`--no-sysbuild` 可针对一次调用关闭。默认通过顶层构建目录构建全部 domain，也可选择一个 domain。

### 7.1.2\_指定源码、输出目录与构建目标

在源码目录外构建，显式给出应用路径：

```text
west build -b <BOARD> path/to/source/directory
```

指定构建目录，`--build-dir` 也可写成 `-d`：

```text
west build -b <BOARD> --build-dir path/to/build/directory
```

也可设置目录格式，减少不同应用和开发板共用缓存的情况：

```text
west config build.dir-fmt "build/{board}/{app}"
```

此时运行 `west build -b reel_board samples/hello_world`，默认目录是 `build/reel_board/hello_world`。各占位符含义见本节末配置表。

用 `-t` 或 `--target` 执行特定构建目标。例如构建后在 QEMU 中运行：

```text
west build -b qemu_x86 -t run samples/hello_world
```

列出当前构建系统支持的目标：

```text
west build -t help
```

清空构建目录的文件：

```text
west build -t pristine
```

> 译注：`pristine` 是清理构建产物的操作。执行前核对 `-d` 或自动发现的构建目录，不要把源码目录当作构建目录。

### 7.1.3\_干净构建与详细输出

pristine 构建会先把目录恢复到类似新建目录的状态。`--pristine=always` 或 `-p=always` 每次清理，单独 `-p` 等同于 always：

```text
west build -p -b reel_board samples/hello_world
west build -p=always -b reel_board samples/hello_world
```

默认构建不会自动为每一种过期缓存情况执行 pristine。`--pristine=auto` 会在一些能够识别的情形中清理，例如应用或开发板发生变化。也可以配置 `build.pristine` 为 `always`、`never` 或 `auto`。

需要查看构建实际执行的命令时，使用 west 的全局详细输出选项；它位于 `build` 前：

```text
west -v build -b reel_board samples/hello_world
```

### 7.1.4\_向CMake传递参数

`--` 之后的参数交给 CMake。只要提供这些额外参数，west 就会重新运行 CMake；已有目录仍可增量编译，但重新配置会花一些时间。首次配置后，仅继续构建可用 `west build -d <build-dir>`。

例如选择 Unix Makefiles 生成器，或同时启用详细 Makefile 输出：

```text
west build -b reel_board -- -G'Unix Makefiles'
west build -b reel_board -- -G'Unix Makefiles' -DCMAKE_VERBOSE_MAKEFILE=ON
```

只写一个 `--`，其后所有参数都属于 CMake。设置设备树 overlay 或额外 Kconfig 配置文件：

```text
west build -b reel_board -- -DDTC_OVERLAY_FILE=enable-modem.overlay
west build -- -DEXTRA_CONF_FILE=file.conf
```

如果每次配置都需要相同参数，可用 `build.cmake-args` 保存。其内容按 shell 参数规则拆分，在运行 CMake 时传入；它不会使每一次增量构建都强制重新配置。修改后若已有缓存仍保留旧状态，应重新配置或使用干净构建，使新配置生效。

```text
west config build.cmake-args -- -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
west config build.cmake-args -- -DCMAKE_VERBOSE_MAKEFILE=ON
west config build.cmake-args -- "-DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_VERBOSE_MAKEFILE=ON"
```

此处 `--` 防止 `west config` 把以 `-D` 开头的值当作自身选项。上面三条是不同配置示例，后一次设置会替换前一次值。

另一种方式是自行创建 `~/my-cache.cmake`，内容为：

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON CACHE BOOL "")
set(CMAKE_VERBOSE_MAKEFILE ON CACHE BOOL "")
```

然后配置：

```text
west config build.cmake-args "-C ~/my-cache.cmake"
```

### 7.1.5\_向底层构建工具传参、选择domain与片段

`-o` 或 `--build-opt` 向 Ninja（默认）或 Make 传递参数。例如让 Ninja 解释为什么需要重新构建，或让 Make 在发生错误后继续其他可构建部分：

```text
west build -o=-dexplain
west build -o=--keep-going
```

等号把以连字符开头的值绑定给 `-o`，避免被当成 west 参数。Ninja 默认并行使用可用处理器，而 Make 默认单任务；可显式指定并行数：

```text
west build -o=-j4
```

只构建特定 sysbuild domain，或查询该 domain 的目标：

```text
west build --sysbuild --domain hello_world
west build --sysbuild --domain hello_world --target help
```

构建时如何应用命名配置片段，见[使用 snippets](https://docs.zephyrproject.org/latest/build/snippets/using.html#using-snippets)。

### 7.1.6\_构建配置选项

配置读写方式见[west 配置](P003_配置.md)。

| 选项 | 类型、默认值与含义 |
| --- | --- |
| `build.board` | 字符串；命令行和环境变量均未指定开发板时使用 |
| `build.board_warn` | 布尔值，默认 `true`；设为 `false` 关闭相关开发板提示 |
| `build.cmake-args` | 字符串；每次调用 CMake 时使用的额外参数，按 shell 参数规则拆分 |
| `build.dir-fmt` | 字符串，默认 `build`；默认构建目录格式 |
| `build.generator` | 字符串，默认 `Ninja`；CMake 生成器 |
| `build.guess-dir` | 字符串，默认 `never`；控制 flash/debug 等命令是否尝试猜测构建目录；不猜测且无法确定时应通过 `-d` 提供 |
| `build.pristine` | 默认 `never`；可选 `auto` 或 `always`，控制自动清理行为 |
| `build.sysbuild` | 布尔值，默认 `false`；默认是否使用 sysbuild |

`build.dir-fmt` 支持以下替换字段：

| 字段 | 含义 |
| --- | --- |
| `{west_topdir}` | west 工作区顶层的绝对路径 |
| `{board}` | 所选开发板名称 |
| `{source_dir}` | 源码目录相对于当前工作目录的路径；当前目录就是源码目录时为空；Windows 下源码与当前目录不在同一驱动器时也为空。未给源码路径时采用当前目录。例如在 `<west_topdir>/app1` 中执行 `west build ../app`，该值为 `../app` |
| `{source_dir_workspace}` | 源码在工作区内时，相对于工作区顶层的路径；否则相对于文件系统根（Windows 为所在驱动器根）的路径。上例的工作区相对路径为 `app` |
| `{app}` | 源码目录的末级名称，即应用名称 |

> 译注：原页 `source_dir_workspace` 段末的示例误写了 `source_dir` 字段名；这里按段落讨论的工作区相对路径解释，避免与上一行的 `../app` 混淆。

## 7.2\_烧录：west flash

在 Zephyr 构建目录内执行：

```text
west flash
```

默认先重新构建，再把程序写入开发板。也可以从其他位置显式指定目录：

```text
west flash --build-dir path/to/build/directory
```

`-d` 是 `--build-dir` 的简写。未指定时先查找 `build`，再检查当前目录；配置 `build.dir-fmt` 可改变默认构建目录位置。

### 7.2.1\_选择runner

如果板级集成支持多个烧录程序，使用 `--runner` 或 `-r` 覆盖默认值。例如板默认使用 pyOCD，但也支持 J-Link：

```text
west flash --runner jlink
```

默认 runner 可在 CMake 配置阶段通过 `BOARD_FLASH_RUNNER` 和 `BOARD_DEBUG_RUNNER` 选择。烧录示例：

```text
west build [...] -- -DBOARD_FLASH_RUNNER=jlink
```

> 译注：`[...]` 表示应填写的其他构建参数，不能原样复制执行。

`west flash -H` 可列出烧录 runner；在构建目录内运行，或加 `--build-dir`，还能看到当前开发板的信息。

### 7.2.2\_覆盖配置和runner专用参数

构建系统保存了板目录、映像路径等默认配置。可以在一次命令中覆盖其中某项，其他项继续使用默认值。例如 runner 使用 Intel HEX 文件时：

```text
west flash --hex-file path/to/some/other.hex
```

所有 runner 共用的覆盖选项见 `west flash -h`。各 runner 还可提供专用选项，如在写入前擦除目标可寻址 Flash 的 `--erase`。

查看板支持的 runner、全部选项及用法：

```text
west flash --context
```

`--context` 可写成大写 `-H`；它会重新执行构建，确保显示的信息与当前配置一致。在构建目录之外运行 `west flash -H` 只列出 runner。查看某个 runner 的选项：

```text
west flash -H -r jlink
```

### 7.2.3\_多个domain与配置项

遇到 sysbuild 目录时，默认按 sysbuild 指定顺序烧录全部 domain。只选择一个：

```text
west flash --domain hello_world
```

`flash.rebuild` 是布尔配置项，默认 `true`；设为 `false` 后，`west flash` 不先重新构建。

## 7.3\_调试：west debug与west debugserver

在构建目录执行 `west debug`，连接目标后进入加载了符号信息的 GDB 控制台；执行 `west debugserver` 则启动供 IDE 或其他调试器连接的本地调试服务：

```text
west debug
west debugserver
```

两者是按需要选择的不同操作，也可明确指定构建目录：

```text
west debug --build-dir path/to/build/directory
west debugserver --build-dir path/to/build/directory
```

构建目录查找规则与 `west flash` 相同。

### 7.3.1\_runner选择和参数覆盖

开发板支持多种工具时，可选择 J-Link 等 runner：

```text
west debug --runner jlink
west debugserver --runner jlink
```

`west debug -H` 列出支持调试的 runner；提供构建目录时显示该板的附加信息。CMake 缓存中的默认值包括板目录和包含符号表的程序文件等。假定 runner 使用 **可执行与可链接格式（Executable and Linkable Format，ELF）**，可只替换程序文件：

```text
west debug --elf-file path/to/some/other.elf
west debugserver --elf-file path/to/some/other.elf
```

`west debug -h` 列出通用覆盖参数。runner 可能有额外选项，例如调试服务的网络端口。查看完整上下文：

```text
west debug --context
```

`west debugserver --context` 输出相同信息。缩写是大写 `-H`，并且会重新构建以更新信息。在构建目录外只列出 runner；可指定名称查询其用法：

```text
west debug -H -r jlink
```

### 7.3.2\_多domain调试

一次 `west debug` 只能调试一个 domain。检测到 sysbuild 目录时，默认调试 sysbuild 指定的 `default` domain，它通常对应传入的应用源码目录：

```text
west build --sysbuild path/to/source/directory
```

例如使用 sysbuild 构建同时包含 MCUboot 的 Hello World 时，`hello_world` 是默认 domain：

```text
west build --sysbuild samples/hello_world
```

调试该应用，可选下面任一写法：

```text
west debug
west debug --domain hello_world
```

调试 MCUboot 则必须明确选择：

```text
west debug --domain mcuboot
```

> 译注：这里说明已配置 MCUboot 的 sysbuild 工程如何选择调试对象；`--sysbuild` 本身并不意味着已经启用 MCUboot。

`debug.rebuild` 和 `debugserver.rebuild` 都是默认 `true` 的布尔配置项；分别设为 `false` 可跳过对应命令执行前的重新构建。

## 7.4\_烧录和调试runner

这些命令使用 Python 包装各种[烧录与调试主机工具](https://docs.zephyrproject.org/latest/develop/flash_debug/index.html)。包装代码位于官方 [`scripts/west_commands/runners`](https://github.com/zephyrproject-rtos/zephyr/tree/main/scripts/west_commands/runners)，每种包装称作一个 runner，可支持烧录、调试或二者。

核心抽象是 `runners.core` 中的 `ZephyrBinaryRunner` 抽象类。当前可用的 runner 集合由已经导入的子类决定；具体实现位于 `runners.nrfjprog`、`runners.openocd` 等子模块。

## 7.5\_运行Robot Framework测试：west robot

`west robot -h` 提供帮助。当前命令只支持使用 `renode-test` 的 runner；这个工具在 Renode 中运行 Robot 测试，也可以通过增加 runner 扩展命令。

从 Zephyr 构建目录运行测试套件：

```text
west robot --runner=renode-robot --testsuite path/to/testsuite.robot
```

这会执行 `testsuite.robot` 中的所有测试，显示 Robot Framework 输出。向 Renode 传入额外参数，例如同时显示 Renode 日志：

```text
west robot --runner=renode-robot --testsuite path/to/testsuite.robot --renode-robot-arg="--show-log"
```

> 译注：原文说明段写成复数 `--renode-robot-args`，示例为单数 `--renode-robot-arg`；此处保留示例的单数参数，并把网页排版产生的长横线和弯引号恢复为 ASCII 命令字符。本仓库 `scripts/west_commands/runners/renode-robot.py` 的参数声明也使用单数，但该本地核对不等于官网与本地源码版本完全一致。以正在使用的版本的 `--context` 帮助为准。

查看 runner 的选项及用法：

```text
west robot --runner=renode-robot --context
```

查看 `renode-test` 自身支持的全部选项：

```text
west robot --runner=renode-robot --renode-robot-help
```

## 7.6\_模拟开发板：west simulate

当前只有使用 Renode 的 runner，可通过新增 runner 扩展。在构建目录运行：

```text
west simulate --runner=renode
```

这会启动 Renode，采用当前平台的默认 `.resc` 脚本配置模拟，默认加载 `zephyr.elf`。之后在 Renode Monitor 中输入 `start` 或 `s` 开始运行，也可通过 runner 直接传入命令：

```text
west simulate --runner=renode --renode-command start
```

向 Renode 本身传参，例如在控制台运行而非另开窗口：

```text
west simulate --runner=renode --renode-arg="--console"
```

后续即可按通常方式使用 Renode 的控制台或窗口界面，详见 [Renode 文档](https://docs.renode.io/)。以上两条同样恢复了原网页的命令字符排版。

查看 runner 选项和 Renode 自身选项：

```text
west simulate --runner=renode --context
west simulate --runner=renode --renode-help
```

## 7.7\_树外runner与开发入口

[Zephyr 模块](https://docs.zephyrproject.org/latest/develop/modules.html)可以在 `module.yml` 中登记 Python 文件，使外部 runner 被发现。自定义类应继承 `ZephyrBinaryRunner`，实现所有抽象方法。

原文注释指出：支持自定义树外 runner，使 `runners.core` 成为公共 **应用程序编程接口（Application Programming Interface，API）** 的组成部分；不向后兼容的改变必须经历[弃用流程](https://docs.zephyrproject.org/latest/develop/api/api_lifecycle.html)。

开发者可实现 runner，为新的烧录或调试方式提供支持。提交到 Zephyr 上游时，应把实现加入新建或已有的 `runners` 模块，并从 `runners/__init__.py` 导入。官方 [`scripts/west_commands/tests`](https://github.com/zephyrproject-rtos/zephyr/tree/main/scripts/west_commands/tests) 为 runner 包及其具体类提供单元测试；增加 runner 时应增加测试，破坏已有用例会使上游 PR 的 CI 失败。

接下来的参考说明核心 `ZephyrBinaryRunner` 及辅助类；它们属于实现烧录与调试能力时使用的核心接口。

## 7.8\_runner辅助类型参考

这些类型分别提供构建配置、能力声明、运行配置，以及程序和网络端口等辅助处理；下一节的 runner 核心类会使用它们。

### 7.8.1\_BuildConfiguration与SysbuildConfiguration

`class runners.core.BuildConfiguration(build_dir: str)` 提供对构建时配置的访问。可像字典一样读取 `object['CONFIG_FOO']` 或 `object.get('CONFIG_FOO')`；Kconfig 值从 `.config` 解析，设备树通过 `object.edt` 暴露 edtlib API。

- 属性 `edt`：返回表示设备树的 EDT；第一次访问时延迟加载，后续使用缓存。
- `getboolean(option)`：选项明确为 `y` 或 `n` 时返回相应布尔值；否则返回 `False`。

`class runners.core.SysbuildConfiguration(build_dir: str)` 提供 sysbuild 配置访问；同样支持 `object['SB_CONFIG_FOO']` 和 `object.get('SB_CONFIG_FOO')`，Kconfig 值从 `.config` 解析。

### 7.8.2\_其他辅助类型

原文只列出下列两个类型的签名，没有附加语义说明：

```python
class runners.core.DeprecatedAction(option_strings, dest, nargs=None, const=None, default=None, type=None, choices=None, required=False, help=None, metavar=None)
class runners.core.FileType(*values)
```

`exception runners.core.MissingProgram(program)` 是 `FileNotFoundError` 的子类，表示缺少某个执行所需的程序依赖。与父类没有显著行为差异，作用是明确指出缺少的是必需程序；`filename` 属性包含缺失的程序。

`class runners.core.NetworkPortHelper` 用于处理本地 IP 网络端口。`get_unused_ports(starting_from)` 接收一个期望端口的可迭代对象，按原顺序返回可用端口：期望端口空闲就沿用，否则向后寻找下一个空闲端口。检查与真正使用之间端口仍可能被占用，调用者必须处理绑定失败。

## 7.9\_ZephyrBinaryRunner参考

`class runners.core.ZephyrBinaryRunner(cfg: RunnerConfig)` 是二进制 runner（烧录器、调试器）的抽象父类。

原文类说明保留如下提醒：该类自加入以来 API 变化较少，但不被视为稳定的 Zephyr API，可能在不预先通知的情况下改变。

> 译注：这条自动生成的类说明与前面树外 runner 段落“公共 API、不兼容变更须弃用”的说法存在张力。两处原意均保留；实际扩展开发应固定使用的 Zephyr 版本，核对该版本源码及发布说明，不能据此推断跨版本绝对兼容。

除少数例外外，Zephyr 支持的开发板应提供通用烧录与调试方式。烧录是把固件持久写入设备；调试是让主机上的断点调试器和程序加载器连接目标。构建系统管理四个顶层操作：

- `flash`：把已配置的二进制写入开发板，启动目标执行，然后返回。
- `debug`：通过调试协议连接，写入 Flash，加载当前二进制的符号表并进入调试器，直到调试器退出才返回。
- `debugserver`：通过板专用协议连接，复位并暂停目标，使用户能够连接调试服务并使用二进制符号表。
- `attach`：通过调试协议连接，加载符号表并进入调试器，等待其退出；此操作不写入 Flash。

每个子类简称 runner，具有 `pyocd` 等名称，并声明支持的命令。开发板如 `nrf52dk/nrf52832` 向构建系统声明兼容 runner 及其配置。构建系统把足够的信息写入构建目录，使 `create()` 能通过命令行参数解析接口创建 runner；也可以直接实例化子类。

实现自定义 runner 的步骤为：定义子类并实现抽象方法，必要时覆盖 `capabilities()`；确保定义类的 Python 模块已导入（例如修改包的 `__init__.py`，否则 `get_runners()` 无法发现）；在板的 `board.cmake` 中向构建系统提供 runner 名称。

附加建议：

- 依赖非标准库模块时捕获 `ImportError`，把缺失依赖的报错延迟到需要使用该 runner 时以 `RuntimeError` 给出，避免影响不使用它的用户。
- 需要 `input()` 等交互时，在类方法 `create()` 中完成，而非 `do_run()`。这样构造完成后就具备执行所需信息，也避免非命令行调用途径意外触发输入。
- 通过 `self.logger` 使用 Python 标准日志 API；日志器名称为 `runner.<your-runner-name()>`。

命令行接口由共用 `add_parser()` 和其调用的专用 `do_add_parser()` 建立，采用 argparse；`create()` 结合 `RunnerConfig` 和解析后的参数创建实例。构造器应接收执行所需的值，实际执行通过 `run()` 进入。

### 7.9.3\_文件、地址、程序发现及帮助接口

`ensure_output(output_type: str) -> None` 确认 `self.cfg` 中指定类型的产物存在。例如 `ensure_output('bin')` 要求 `self.cfg.bin_file` 已定义且文件存在；否则报错。`output_type` 是表示输出类型的字符串。

静态方法 `flash_address_from_build_conf(build_conf: BuildConfiguration)` 按以下规则取得烧录地址：若 `CONFIG_FLASH_USES_MAPPED_PARTITION=y`，返回设备树 `zephyr,code-partition` 节点的 `reg` 地址；否则，若 `CONFIG_HAS_FLASH_LOAD_OFFSET=n`，返回 `CONFIG_FLASH_BASE_ADDRESS`；其余情况返回 `CONFIG_FLASH_BASE_ADDRESS + CONFIG_FLASH_LOAD_OFFSET`。

静态方法 `get_flash_address(args: Namespace, build_conf: BuildConfiguration, default: int = 0) -> int` 在 `args.dt_flash` 为真时调用上述地址计算函数，否则返回传入的默认地址。

`get_rtt_address() -> int | None` 提取 RTT 控制块地址；已提供 `args.rtt_address` 时直接使用，否则尝试从 ELF 查找 RTT 块，找不到返回 `None`。静态方法 `sram_address_from_build_conf(build_conf: BuildConfiguration)` 返回 SRAM 地址。

静态方法 `gdb_ex_args(commands: list[str] | None) -> list[str]` 把 GDB 命令变成 `'-ex', <command>` 参数对，命令内容原样传递。

静态方法 `require(program: str, path: str | None = None) -> str` 在继续前确认程序已安装。`program` 可以是名称或二进制路径；绝对路径指向现存程序时直接成功，否则按名称在给定的 `path`（PATH 字符串）中查找，未提供时使用系统 PATH。找到返回路径，否则抛出 `MissingProgram`。

静态方法 `normalize_chip(name: str) -> str` 规范化芯片名称，使匹配忽略大小写与连字符差异。

静态方法 `resolve_port_by_chip(detect_func, target, logger, priority_vids=None)` 探测串口并返回第一个芯片名称与规范化 `target` 匹配的设备路径，未找到返回 `None`：

- `detect_func` 接收端口设备路径，返回该端口报告的芯片名称，无法识别时返回 `None`；该函数负责打开和关闭端口。
- `target` 是用于匹配的规范化芯片名称。
- `logger` 用于进度和诊断日志。
- `priority_vids` 可选，列出优先探测的 **通用串行总线（Universal Serial Bus，USB）** VID，以避免复位无关的串口适配器。

类方法 `dev_id_help() -> str`、`extload_help() -> str` 和 `tool_opt_help() -> str` 分别返回 `--dev-id`、`--extload` 和 `--tool-opt` 的 argparse 帮助文字。

## 7.10\_手动烧录与调试

不使用 west 时，可在构建目录查找生成的二进制。具体名称取决于板级集成，通常有 `zephyr/zephyr.elf`、`zephyr/zephyr.hex` 等。可以用其他工具把它们写入开发板，也可用于调试，例如从 ELF 读取符号表。

默认情况下，west 在烧录和调试前重新构建。这也可以通过 Zephyr 构建系统的通常目标完成；west 正是通过这些目标实现重新构建的。
