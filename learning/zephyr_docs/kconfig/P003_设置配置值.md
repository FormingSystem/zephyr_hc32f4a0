# 第3章\_设置Kconfig配置值

原文：[Setting Kconfig configuration values](https://docs.zephyrproject.org/latest/build/kconfig/setting.html)。读取日期：2026-10-12，`latest`。

应用开发时可以在 menuconfig 或 guiconfig 中试验配置，本章说明如何永久保存设置。所有选项可在 [Kconfig 搜索页](https://docs.zephyrproject.org/latest/kconfig.html)查询；修改 Kconfig 定义前，建议先读[技巧与最佳实践](https://docs.zephyrproject.org/latest/build/kconfig/tips.html)。

## 3.1\_可见与不可见符号

可见符号定义了 prompt（提示文字），因而能在交互界面中显示，也能在配置文件中设置。例如：

```kconfig
config FPU
   bool "Support floating point operations"
   depends on HAS_FPU
```

它在 menuconfig 中显示为可切换条目：

```text
[ ] Support floating point operations
```

不可见符号没有提示文字，不出现在通常的交互界面中，用户无法直接控制值，而是由默认值或其他符号决定。例如：

```kconfig
config CPU_HAS_FPU
   bool
   help
     This symbol is y if the CPU has a hardware floating point unit.
```

这里的帮助说明 **中央处理器（Central Processing Unit，CPU）** 有硬件浮点单元时该符号为 `y`；它由其他符号的 `select CPU_HAS_FPU` 启用。

## 3.2\_配置文件中的赋值

可见符号可在配置文件中赋值。初始配置通常由板的 `*_defconfig` 和应用 `prj.conf` 合并而来。语法为：

```text
CONFIG_<symbol name>=<value>
```

等号两侧不能有空格。布尔值分别用 `y`、`n` 启用或禁用，例如：

```kconfig
CONFIG_FPU=y
```

也可以用以下特殊注释形式把布尔值设为 `n`：

```kconfig
# CONFIG_SOME_OTHER_BOOL is not set
```

构建目录 `zephyr/.config` 使用这种形式。它因历史兼容原因保留：Kconfig 配置可以当作 Makefile 解析（Zephyr 不采用这种方式），让 `n` 对应未设置变量能简化 Make 中的判断。

字符串、整数和注释示例：

```kconfig
CONFIG_SOME_STRING="cool value"
CONFIG_SOME_INT=123
```

```kconfig
# This is a comment
```

只有符号依赖得到满足，配置中的赋值才会生效；否则会给出警告。可在交互界面按 `/` 搜索符号，查看依赖，或查官方 Kconfig 搜索页。

## 3.3\_初始配置如何形成

应用初始配置合并以下三类输入：板专用 `boards/<VENDOR>/<BOARD>/<BOARD>_defconfig`、以 `CONFIG_` 开头的 CMake 缓存项，以及应用配置。

应用配置由一个或多个 Kconfig fragment（配置片段）合并，默认使用 `prj.conf`。原页按以下规则说明选择过程：

1. 设置了 `CONF_FILE` 时，合并其中列出的文件。可在 `find_package(Zephyr)` 前于 `CMakeLists.txt` 设置，也可直接或通过 west 传 `-DCONF_FILE=<conf file(s)>`，或从 CMake 缓存取得。
2. 否则，若应用配置目录有 `boards/<BOARD>.conf`，将它与 `prj.conf` 合并。
3. 原文接着以“否则”描述板修订版：若使用 revision 且有 `boards/<BOARD>_<revision>.conf`，则把它与 `prj.conf`、`boards/<BOARD>.conf` 合并。
4. 否则采用应用配置目录中的 `prj.conf`；不存在则报致命错误。

> 译注：原文第 2、3 条的“否则”表达不够严谨，不能据此推断存在普通板片段时一定跳过 revision 文件。此处保留两条列举的合并对象；实际选中文件应以所用版本的 CMake 配置输出和生成 `.config` 为准。

应用还可提供 **片上系统（System on Chip，SoC）** 片段 `socs/<SOC>_<BOARD_QUALIFIERS>.conf`。存在时，它在主项目配置之后、所有板配置片段之前应用。

除 `CONF_FILE`、`EXTRA_CONF_FILE`、`DTC_OVERLAY_FILE`、`EXTRA_DTC_OVERLAY_FILE` 中给出的绝对路径外，配置文件均从应用配置目录读取。若在应用 `CMakeLists.txt` 中引用模块里的文件，可转义模块目录变量，例如 `\${ZEPHYR_<module>_MODULE_DIR}/<path-to>/<file>`。配置目录的定义见[应用开发](../application/P001_应用开发.md)。

同一符号同时出现在板 defconfig 和应用配置中时，应用值优先。合并结果保存在构建目录 `zephyr/.config`。只要它存在且比板和应用配置文件都新，构建系统优先复用它，不重新合并；交互配置界面修改的也是这个文件。

## 3.4\_把警告当作错误

某些警告默认中止构建，例如对未定义符号赋值；另一些只打印，例如重复赋值，或因依赖未满足而忽略赋值。要让全部警告都视为错误，在配置时设置：

```text
west build -b <board> <app> -- -DKCONFIG_WARNING_AS_ERROR=y
```

这适用于 CI，因为被静默忽略的设置往往是错误。变量通过 `zephyr_get()` 读取，也能作为环境变量或通过 [Zephyr Build Configuration CMake 包](https://docs.zephyrproject.org/latest/build/zephyr_cmake_package.html#cmake-build-config-package)提供。

## 3.5\_让一个符号跟随另一个符号

符号可把另一个符号的值作为默认值。应用或子系统希望保留本地命名、避免直接依赖公共名称，或希望两者能独立配置时，这很有用。例如公共设置 `FOO_STRING` 与子系统设置 `SUB_FOO_STRING`：

```kconfig
config FOO_STRING
        string "Foo"
        default "foo"

config SUB_FOO_STRING
        string "Sub-foo"
        default FOO_STRING
```

默认时二者相同，但仍允许用户分别配置。也可以去掉跟随符号的提示文字，使其不可见，从而保持同步，除非通过 defconfig 定义改变它的值：

```kconfig
config FOO_STRING
        string "Foo"
        default "foo"

config SUB_FOO_STRING
        string
        default FOO_STRING
        help
          Hidden symbol which follows FOO_STRING
          Can be changed through *.defconfig files.
```

最后的帮助文字说明：这是跟随 `FOO_STRING` 的隐藏符号，可通过 `*.defconfig` 文件改变。

## 3.6\_配置不可见符号

调整开发板默认配置时，可能要设置不可见符号。这应在 `boards/<VENDOR>/<BOARD>/Kconfig.defconfig` 中完成，它是普通 Kconfig 定义文件。`.config` 中对不可见符号的赋值不起作用，所以两种文件的区别不只是组织习惯。

此方法利用同一符号可在多处定义的能力。假定基础定义为：

```kconfig
config FOO_WIDTH
    int
```

要让某板默认使用 32，在 `Kconfig.defconfig` 扩展定义：

```kconfig
if BOARD_MY_BOARD

config FOO_WIDTH
    default 32

endif
```

基础定义已经给出 `int` 类型，不必重复。类型只在基础位置定义通常更好，原因见[常用 Kconfig 简写](https://docs.zephyrproject.org/latest/build/kconfig/tips.html)。

`Kconfig.defconfig` 中的默认值比基础定义优先，因为这些文件先被包含。Kconfig 选择第一个条件满足的 `default`；没有条件等价于 `if y`。外层顶层 `if` 条件会传播到属性，因此上例等价于 `default 32 if BOARD_MY_BOARD`。

### 3.6.1\_多处定义会如何影响依赖

多处定义各自构成同名符号的独立定义，不能把新增依赖理解为向前一处追加限制；只要任一处定义允许，符号就可能可用。因此不能通过重复定义使依赖更严格。下例满足 `DEP1` 或 `DEP2` 任一个就足够，不要求二者同时满足：

```kconfig
config FOO
   ...
   depends on DEP1

config FOO
   ...
   depends on DEP2
```

没有显式依赖的定义同样遵守这个规则。下面的第二处没有限制，会使 `FOO` 无论 `DEP1` 如何都默认启用：

```kconfig
config FOO
   bool "FOO"
   depends on DEP1

config FOO
   default y
```

如果仅需追加默认值、不改变其他行为，可用 [`configdefault` 扩展](https://docs.zephyrproject.org/latest/build/kconfig/extensions.html)避免弱化依赖。修改 `Kconfig.defconfig` 后，应在交互界面检查直接依赖；通常需要重复基础定义的依赖条件以维持约束。

### 3.6.2\_为什么需要Kconfig.defconfig

一个原因是避免把板的固定设置变成用户可以在交互界面随意修改的选项。如果所有板配置都用 `<BOARD>_defconfig` 设置，符号就都必须可见，因为该文件中的赋值对不可见符号无效。这会使界面繁杂难懂，也更容易形成无效配置。面对固定硬件设置时，还应判断是否更适合放进设备树。

## 3.7\_配置choice

有两种方式选择互斥配置：

第一种是在配置片段中把一个 choice 成员设为 `y`，其他成员自动为 `n`。多个成员被设为 `y` 时，仅最后一个生效，因此应用 `prj.conf` 可以覆盖板 defconfig 的选择。

第二种是在 `Kconfig.defconfig` 修改 choice 的默认项。与普通符号相似，需要多处定义；为此 choice 必须有名字。基础定义示例：

```kconfig
choice FOO
    bool "Foo choice"
    default B

config A
    bool "A"

config B
    bool "B"

endchoice
```

把 `FOO` 默认选项改成 `A`，在 `Kconfig.defconfig` 增加：

```kconfig
choice FOO
    default A
endchoice
```

choice 的依赖可能不满足时，应采用第二种方式；这样是在规定“当用户使该 choice 可见时采用什么默认选择”。
