# 第25章\_分组管理

原文：[官方页面](https://docs.zephyrproject.org/latest/services/connectivity/networking/api/net_pkt.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 25.1\_概览与架构（Overview and Architectural Notes）

网络分组（Network Packet）是协议栈处理的主要数据。`net_pkt` 结构保存分组对象，提供读写能力，并携带网络核心需要的元数据（Metadata）。本页用 `net_pkt` 指代这种对象，结构及相关 API 定义在 [`include/zephyr/net/net_pkt.h`](../../../include/zephyr/net/net_pkt.h)。

协议栈中有发送（TX）与接收（RX）两条分组路径；在两条路径上，每个分组都从头到尾访问，更具体地说，是从协议头（Header）依次访问到载荷（Payload）。

## 25.2\_并发与线程安全（Concurrency and Thread Safety）

`net_pkt` 及其 API **不是线程安全的**。协议栈采用严格的独占所有权（Exclusive Ownership）模型：分组在任何时刻只归一个线程或执行上下文所有。

并发主要通过三种方式管理：

- **通过 FIFO 转移所有权**：常见生命周期是在隔离的执行上下文间传递分组，例如从 RX 驱动线程交给 IP 协议栈。一旦入队，发送方放弃自己的引用与访问权。
- **浅克隆（Shallow Cloning）**：某层需要保留分组，例如 TCP 留作重传，同时另一层还要处理它时，使用 `net_pkt_shallow_clone()` 创建新的包装对象，共享底层只读数据。数据缓冲区自身的引用计数是线程安全的。
- **粗粒度协议锁（Coarse-Grained Protocol Lock）**：有意保留在内存队列中的分组，由更高层子系统锁保护，例如连接互斥锁。

`struct net_pkt` 的 `atomic_ref` 用于内存生命周期管理，防止释放后使用（Use-After-Free），并非允许并发修改对象的锁。

> 译注：这里“放弃引用”描述所有权移交，不是要求在每次成功入队后机械调用 [`net_pkt_unref()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga893d1660fd18ad5842224fda78466099)。是否释放额外引用须遵守实际队列／调用 API 的所有权约定；移交中的分组仍必须保持有效。

## 25.3\_内存管理（Memory Management）

### 25.3.1\_分配分组（Allocation）

全部 `net_pkt` 来自预先定义的 `struct net_pkt` 对象池（Pool），可通过以下宏定义：

```c
NET_PKT_SLAB_DEFINE(name, count)
```

通常无需自行定义，因为核心已经为 TX 和 RX 各提供一个池。分配原始分组对象：

```c
pkt = net_pkt_alloc(timeout);
```

没有数据缓冲区和必要元数据的原始对象尚不能用于实际处理，至少需要关联将要发送或已经收到该分组的网络接口。常用辅助函数是：

```c
pkt = net_pkt_alloc_on_iface(iface, timeout);
```

还可以同时分配对象与数据缓冲区：

```c
pkt = net_pkt_alloc_with_buffer(iface, size, family, proto, timeout);
```

缓冲区的分配规则如下。

### 25.3.2\_分配缓冲区（Buffer Allocation）

`net_pkt` 不自行定义数据缓冲区，而是使用 [`net_buf`](https://docs.zephyrproject.org/latest/doxygen/html/structnet__buf.html)，见[网络缓冲区（Network Buffers）](P005_网络缓冲区.md#net-buf-interface)。它将网络相关的分配和操作规则封装起来，因此大部分时候不需要直接操作底层缓冲区。

分配缓冲区前，分组至少应设置网络接口。此时即使还不知道地址族（Address Family），也可以调用：

```c
net_pkt_alloc_buffer(pkt, size, proto, timeout);
```

不知道协议时，`proto` 可以是 `0`，因为没有 `IPPROTO_UNSPEC`。也可使用前面的 [`net_pkt_alloc_with_buffer()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga4ea4f0897e5fe4dfaf7ceca5f18f1702) 一次完成分组及缓冲区分配，这是最常用的分配器。

分配器结合接口、地址族与协议判断请求大小：从接口获取最大传输单元（Maximum Transmission Unit，MTU），在地址族与协议均已指定时估算头部空间。若请求及头部能够容纳在 MTU 内，则分配请求大小加上需要的头部空间；否则缩小载荷，使头部与载荷合计不超出限制。

原文以 MTU 为 `1500` 字节的以太网接口举例：

```c
pkt = net_pkt_alloc_with_buffer(iface, 800, NET_AF_INET4, IPPROTO_UDP, K_FOREVER);
```

这会为新分组申请 `800 + 20 + 8` 字节，额外的 `20` 和 `8` 分别是 IPv4、UDP 头部。相对地：

```c
pkt = net_pkt_alloc_with_buffer(iface, 1600, NET_AF_INET4, IPPROTO_UDP, K_FOREVER);
```

原文说明上例只分配 `1500` 字节，其中 `20 + 8` 字节用于头部，不能用于载荷。

接收路径尚不知道地址族与协议时：

```c
pkt = net_pkt_rx_alloc_with_buffer(iface, 800, AF_UNSPEC, 0, K_FOREVER);
```

分配 `800` 字节，不额外预留协议头空间；而：

```c
pkt = net_pkt_rx_alloc_with_buffer(iface, 1600, AF_UNSPEC, 0, K_FOREVER);
```

原文说明会分配 `1514` 字节，即 MTU 加以太网头部。

> 源码跟踪译注：原例中的 `NET_AF_INET4` 在本次官方 `net_ip.h` 中没有定义，IPv4 地址族定义为 `NET_AF_INET`；采用该头文件时应修正此名称。类型定义可对照 [`net_ip.h`](../../../include/zephyr/net/net_ip.h)。这些数字是原文特定以太网场景的计算示例，不能当作所有配置的固定结果。当前 [`net_pkt.c`](../../../subsys/net/ip/net_pkt.c) 的 `pkt_buffer_length()` 还考虑 IPv4／IPv6 分片配置、最小 IP MTU，以及未知地址族时的 `NET_ETH_MAX_HDR_SIZE`；启用 VLAN 等配置也会影响以太网头部上限。示例还省略了分配失败判断，实际程序必须检查返回值。上述原代码未改写为本仓库测试结果。

可再次调用 [`net_pkt_alloc_buffer()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#gae31b4afd510bce346f7d00a9ec5d190d) 增加空间；它考虑已有缓冲区，并在地址族有效时结合 `proto` 计算头部需求。新增缓冲区追加到现有链尾，不插入头部。这种用法较少见，通常应在开始时就确定所需大小。

### 25.3.3\_释放分组（Deallocation）

每个分组都有引用计数（Reference Count），分配时为 `1`。[`net_pkt_ref()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga4e83d4f60b46db8f57798c0e96d6cd7a) 增加引用，[`net_pkt_unref()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga893d1660fd18ad5842224fda78466099) 减少引用；降到 `0` 时，也释放对数据缓冲区的引用，并将分组对象自动归还空闲的 `net_pkt_slabs`。

若分组对象释放后仍需使用它的数据缓冲区，必须在最后一次 `net_pkt_unref` 前，为整个 [`net_buf`](https://docs.zephyrproject.org/latest/doxygen/html/structnet__buf.html) 链额外持有引用，见[网络缓冲区说明](P005_网络缓冲区.md#net-buf-interface)。

## 25.4\_基本读写（Read and Write Access）

访问分组缓冲区有两种方式：基本读写，以及下一节更推荐的数据访问（Data Access）。分组可能分散在多个 [`net_buf`](https://docs.zephyrproject.org/latest/doxygen/html/structnet__buf.html) 中，单个缓冲区的 API 难以处理这种情况；`net_pkt` API 隐藏了非连续访问的复杂性。

每个分组内部维护游标（Cursor），全部读写操作都会改变它。长度参数是**必须读写的精确长度**，不是上限；无法完成指定长度时，操作失败。

有写入（Write）和覆盖（Overwrite）两种模式：写入会改变缓冲区有效数据长度（Length），覆盖只能发生在已有有效数据范围内，不改变长度。长度不同于容量（Size）；无论什么模式都不能超出容量。新分配分组默认使用写入模式，游标位于缓冲区开头。

假设刚分配的缓冲区容量为 `500` 字节，此时有效长度是 `0`，可以检查：

```c
len = net_pkt_get_len(pkt);
```

写入 `8` 字节：

```c
net_pkt_write(pkt, data, 8);
```

有效长度变为 `8`。另有写单字节、大端序（Big-endian）`uint16_t` 和 `uint32_t` 的辅助函数：

```c
net_pkt_write_u8(pkt, &foo);
net_pkt_write_be16(pkt, &ba);
net_pkt_write_be32(pkt, &bar);
```

> 源码跟踪译注：原例传入 `&foo`、`&ba`、`&bar`，但当前 `net_pkt.h` 的三个写入函数第二参数分别是 `uint8_t`、`uint16_t`、`uint32_t` 数值，而不是指针。因此若这些变量分别具有对应整数类型，应传入 `foo`、`ba`、`bar`。下文长度变化是在成功按值写入 `1 + 2 + 4` 字节的前提下讨论，原错误写法仍保留供对照。

随后长度应为 `15`。此时游标在有效数据末尾，直接读取会失败。即使仍处于写入模式，也可先重置游标，读取已经写好的内容：

```c
net_pkt_cursor_init(pkt);
net_pkt_read(pkt, data, 15);
```

游标先回到开头，读出 `15` 字节后又来到末尾。要以相同字节填充一段区域，可用：

```c
net_pkt_memset(pkt, 0, 5);
```

此后长度为 `20`。通过 `net_pkt_set_overwrite()` 可随时切换模式。下面开启覆盖模式并将游标复位：

```c
net_pkt_set_overwrite(pkt, true);
net_pkt_cursor_init(pkt);
```

现在仍可使用相同操作函数，但访问范围限定为已有的 `20` 字节。

查询可用缓冲空间：

```c
net_pkt_available_buffer(pkt);
```

如果还要计入头部占用，查询可用载荷空间：

```c
net_pkt_available_payload_buffer(pkt, proto);
```

使用 [`net_pkt_skip()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga223a79baa1e740a53c4ed0f083d62185) 将游标移到已知位置。例如跳过 IP 头：

```c
net_pkt_cursor_init(pkt);
net_pkt_skip(pkt, net_pkt_ip_header_len(pkt));
```

## 25.5\_数据访问（Data Access）

基本读写 API 简单，但始终涉及从缓冲区复制数据或复制到缓冲区。协议头通常是大小已知的字段集合，使用对应结构直接访问更自然；若头部在连续内存中，将当前位置转换为结构指针还能避免额外复制、节约内存。

专门的数据访问 API 建立在前面的读写 API 上，可透明处理连续与非连续数据。用以下两个宏定义数据访问描述符（Data Access Descriptor）：

- `NET_PKT_DATA_ACCESS_DEFINE`：无法确定数据是否连续时使用。
- `NET_PKT_DATA_ACCESS_CONTIGUOUS_DEFINE`：已保证数据连续时使用。

以 IP 与 UDP 为例，IPv4、IPv6 基本头部位于 IP 分组开头，通常可容纳在 `128` 字节的 [`net_buf`](https://docs.zephyrproject.org/latest/doxygen/html/structnet__buf.html) 中，原文也指出可选择 `64` 字节。IPv4 示例：

```c
NET_PKT_DATA_ACCESS_CONTIGUOUS_DEFINE(ipv4_access, struct net_ipv4_hdr);
struct net_ipv4_hdr *ipv4_hdr;

ipv4_hdr = (struct net_ipv4_hdr *)net_pkt_get_data(pkt, &ipv4_access);
```

原文随后重复写道“`struct net_ipv4_hdr` 也同样适用”。译注：此处前面的例子已经是 IPv4；若用于 IPv6，应采用实际 IPv6 头部类型并确保其连续性，不能把文字重复当作类型可互换的依据。

UDP 头则可能跨越缓冲区，例如在 IPv6 场景中，因此使用不要求预先保证连续的描述符：

```c
NET_PKT_DATA_ACCESS_DEFINE(udp_access, struct net_udp_hdr);
struct net_udp_hdr *udp_hdr;

udp_hdr = (struct net_udp_hdr *)net_pkt_get_data(pkt, &udp_access);
```

此时游标仍指向请求数据的开头。在 RX 路径上，只读取而不修改头部时，需要将游标推进到数据之后，专用操作是：

```c
net_pkt_acknowledge_data(pkt, &ipv4_access);
```

TX 路径中头部字段已被修改时，使用：

```c
net_pkt_set_data(pkt, &ipv4_access);
```

数据连续时，[`net_pkt_set_data()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga98df84477b35e203b11029fc4ddec1cc) 相应推进游标；不连续时，则把修改后的数据写回并更新游标。RX 也可以调用它，但 [`net_pkt_acknowledge_data()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#gac7226cbfa2da28408f9691d375bc8f9f) 稍快，因为后者不关心连续性，直接通过 [`net_pkt_skip()`](https://docs.zephyrproject.org/latest/doxygen/html/group__net__pkt.html#ga223a79baa1e740a53c4ed0f083d62185) 推进游标。
