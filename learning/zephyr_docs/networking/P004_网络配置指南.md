# 第4章\_网络配置指南

原文：[官方页面](https://docs.zephyrproject.org/latest/services/connectivity/networking/net_config_guide.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

本文说明如何根据系统的可用资源，设置各类网络配置选项（Network Configuration Options）。

## 4.1\_网络缓冲区配置

网络缓冲区选项决定同一时刻能够发送或接收多少数据。

| 选项 | 作用 |
| --- | --- |
| [`CONFIG_NET_PKT_RX_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_PKT_RX_COUNT) | 同时能够接收的网络分组（Network Packet）数量上限。 |
| [`CONFIG_NET_PKT_TX_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_PKT_TX_COUNT) | 同时处于待发送状态的网络分组数量上限。 |
| [`CONFIG_NET_BUF_RX_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_BUF_RX_COUNT) | 为接收数据分配的网络缓冲区（Network Buffer）数量。 |

每个 `net_buf` 包含一个小型管理头，以及固定长度或可变长度的数据缓冲区。启用 [`CONFIG_NET_BUF_FIXED_DATA_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_BUF_FIXED_DATA_SIZE) 时，使用 [`CONFIG_NET_BUF_DATA_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_BUF_DATA_SIZE) 指定数据大小；这是默认配置，默认缓冲区大小为128字节。

[`CONFIG_NET_BUF_VARIABLE_DATA_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_BUF_VARIABLE_DATA_SIZE) 是实验性选项。此时每个 `net_buf` 的数据部分从内存池（Memory Pool）分配，可以按从网络收到的数据量分配。接收的数据放入 `net_buf` 数据部分。根据设备资源和期望的网络用途，可以用 [`CONFIG_NET_BUF_DATA_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_BUF_DATA_SIZE) 调整固定缓冲区大小；使用可变长度缓冲区时，则用 [`CONFIG_NET_PKT_BUF_RX_DATA_POOL_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_PKT_BUF_RX_DATA_POOL_SIZE) 和 [`CONFIG_NET_PKT_BUF_TX_DATA_POOL_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_PKT_BUF_TX_DATA_POOL_SIZE) 设置数据池大小。

对于固定长度数据缓冲区，可以按接收数据的特点调整数据部分大小，从而控制内存消耗。如果数据大小设为256字节，却只收到32字节的分组，那么每个分组会“浪费”224字节，因为剩余空间不能被利用。但数据大小也不宜过小，因为每个 `net_buf` 都有管理开销。综合这些因素，默认网络缓冲区大小设为128字节。

可变长度数据缓冲区的测试覆盖不如固定长度方案，因此仍标为实验性功能。它通过只分配网络数据所需的最少空间改善内存利用率，代价是从内存池动态分配所需的额外时间。

例如，以太网（Ethernet）的最大传输单元（Maximum Transmission Unit，MTU）为1500字节。原文说明：若要接收两个完整帧，应把 `net_pkt` 接收数量设为2，把 `net_buf` 接收数量设为 `(1500 / 128) * 2`，即24。使用 TCP 时需要更大的值，因为分组可能在交给应用之前先在内部排队。

> 译注：上述24的计算需要对每帧所需缓冲区数量向上取整，即 `ceil(1500 / 128) * 2 = 24`。原式省略取整；若照 C 整数除法计算，会得到22。此例只说明数据分段数量，实际池容量还要考虑协议和排队需求，不能把它当作所有以太网配置的完整内存预算。

[`CONFIG_NET_BUF_TX_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_BUF_TX_COUNT) 指定为发送数据分配的网络缓冲区数量，与接收缓冲区数量的设置类似，但用于发送方向。

## 4.2\_连接选项

[`CONFIG_NET_MAX_CONN`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MAX_CONN) 指定支持的网络连接端点（Connection Endpoint）数量。例如，每个 TCP 连接需要一个端点，每个监听中的 UDP 连接也需要一个端点；DHCP、DNS 等系统服务同样需要端点。运行时可通过网络 Shell 命令 `net conn` 查看连接信息。

[`CONFIG_NET_MAX_CONTEXTS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MAX_CONTEXTS) 指定分配的网络上下文（Network Context）数量。每个上下文描述监听或发送网络流量所用的网络五元组（Network 5-tuple）。系统中每个 BSD 套接字（BSD Socket）使用一个网络上下文。

## 4.3\_套接字选项

| 选项 | 作用与选择依据 |
| --- | --- |
| [`CONFIG_ZVFS_POLL_MAX`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZVFS_POLL_MAX) | 支持的 `poll()` 条目数量上限；根据系统需要轮询的 BSD 套接字数量选择。 |
| [`CONFIG_ZVFS_OPEN_MAX`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZVFS_OPEN_MAX) | 打开文件描述符（File Descriptor）的数量上限，包括文件、套接字、特殊设备等；根据创建的 BSD 套接字及其他描述符需求选择。 |
| [`CONFIG_ZVFS_EVENTFD_MAX`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ZVFS_EVENTFD_MAX) | ZVFS 的事件文件描述符（eventfd）数量上限。HTTP服务器、CoAP服务器、LwM2M引擎、PTP、SSH和套接字服务等子系统会分配 eventfd 唤醒其 poll 循环。各子系统通过 `CONFIG_ZVFS_EVENTFD_ADD_SIZE_*` 声明需求，实际数量取本选项与所有这些需求之和中的较大值。只有应用自己额外创建 eventfd 时，才需要显式设置此项。 |
| [`CONFIG_NET_SOCKETPAIR_BUFFER_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_SOCKETPAIR_BUFFER_SIZE) | 供 `socketpair()` 使用，指定内部中间缓冲区的字节数，限制两个 socketpair 端点之间可传递消息的大小。 |

## 4.4\_TLS选项

传输层安全（Transport Layer Security，TLS）及数据报传输层安全（Datagram Transport Layer Security，DTLS）的配置如下：

| 选项 | 作用 |
| --- | --- |
| [`CONFIG_NET_SOCKETS_TLS_MAX_CONTEXTS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_SOCKETS_TLS_MAX_CONTEXTS) | TLS／DTLS 上下文数量上限，每条连接需要一个。 |
| [`CONFIG_NET_SOCKETS_TLS_MAX_CREDENTIALS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_SOCKETS_TLS_MAX_CREDENTIALS) | 单个套接字可使用的 TLS／DTLS 凭据（Credential）数量上限。 |
| [`CONFIG_NET_SOCKETS_TLS_MAX_CIPHERSUITES`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_SOCKETS_TLS_MAX_CIPHERSUITES) | 通过套接字选项显式设置时，单个套接字可配置的密码套件（Cipher Suite）数量上限。默认情况下，系统中所有可用套件都可供套接字使用。 |
| [`CONFIG_NET_SOCKETS_TLS_MAX_APP_PROTOCOLS`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_SOCKETS_TLS_MAX_APP_PROTOCOLS) | 通过套接字选项显式设置的 TLS／DTLS 应用层协议（Application Layer Protocol）数量上限。默认不设置支持的应用层协议。 |
| [`CONFIG_NET_SOCKETS_TLS_MAX_CLIENT_SESSION_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_SOCKETS_TLS_MAX_CLIENT_SESSION_COUNT) | 为 TLS／DTLS 会话恢复（Session Resumption）保存的会话数量上限。 |
| [`CONFIG_TLS_MAX_CREDENTIALS_NUMBER`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_TLS_MAX_CREDENTIALS_NUMBER) | 可注册的 TLS 凭据数量上限；应足够大，使所有证书都能加载到凭据存储中。 |

## 4.5\_IPv4与IPv6选项

[`CONFIG_NET_IF_MAX_IPV4_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_IF_MAX_IPV4_COUNT) 指定系统中启用 IPv4 的网络接口数量上限。例如，有两个接口而只有一个使用 IPv4 地址，可设为1；若两个接口都可能使用 IPv4，则应设为2。

[`CONFIG_NET_IF_MAX_IPV6_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_IF_MAX_IPV6_COUNT) 指定 IPv6 网络接口数量上限，含义与 IPv4 的对应选项相同。

## 4.6\_TCP选项

### 4.6.1\_TIME_WAIT等待时间

[`CONFIG_NET_TCP_TIME_WAIT_DELAY`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TCP_TIME_WAIT_DELAY) 指定 TCP 在 `TIME_WAIT` 状态等待多久，单位为毫秒。为避免旧连接的延迟分组被误交给复用了相同本地／远端端口的新连接这一低概率问题，[RFC 793](https://www.rfc-editor.org/rfc/rfc793) 建议让已经关闭的旧连接保留在 `TIME_WAIT` 状态，持续 `2*MSL`。最大报文段生存期（Maximum Segment Lifetime，MSL）建议取2分钟，但 RFC 同时指出：这是工程选择，经验表明有必要时可以调整。

对于资源有限的系统，较大的 MSL 可能迅速耗尽资源，并带来相关拒绝服务（Denial of Service，DoS）攻击风险。同时，现代 TCP 协议栈使用随机、不重复的端口号和初始序列号，已显著缓解分组误投问题。因此 Zephyr 默认采用远低于该建议的1500毫秒。设为0会完全禁用 `TIME_WAIT` 状态。

### 4.6.2\_重传次数

[`CONFIG_NET_TCP_RETRY_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TCP_RETRY_COUNT) 指定 TCP 报文段（Segment）最大重传次数。原文给出以下公式，用于计算报文段为等待重传而被保留的时间，单位为毫秒：

$$
\sum_{n=0}^{\mathtt{NET\_TCP\_RETRY\_COUNT}} \bigg(1 \ll n\bigg)\times
\mathtt{NET\_TCP\_INIT\_RETRANSMISSION\_TIMEOUT}
$$

原文说明：默认值为9时，IP 协议栈最多尝试重传1分42秒，尽量接近 [RFC 1122](https://www.rfc-editor.org/rfc/rfc1122) 建议的最低值1分40秒。重传次数只用5位保存，所以接受范围为0至31，但强烈建议不要低于9。重传超时后，接收回调会得到 `-ETIMEDOUT` 错误码，并解除对上下文的引用（Dereference）。

> 译注：本轮官方 `Kconfig.tcp` 中初始重传超时默认为200毫秒。按上式含上限9求和，会得到 `200 * (2^10 - 1) = 204600` 毫秒，并非1分42秒；若求和到8才是102200毫秒。原公式和文字均保留，但不能将其不一致的数值直接当作当前实现的精确超时保证。实际行为还须核对所用版本、配置和重传计时逻辑；本轮未运行网络计时测试。

### 4.6.3\_发送和接收窗口

[`CONFIG_NET_TCP_MAX_SEND_WINDOW_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TCP_MAX_SEND_WINDOW_SIZE) 指定最大发送窗口（Send Window）大小。默认0表示让 TCP 协议栈按系统配置的网络缓冲区数量选择。如果存在多条活动 TCP 连接，可能需要降低此值，否则各连接排队的发送数据很容易耗尽 `net_buf` 池。

[`CONFIG_NET_TCP_MAX_RECV_WINDOW_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TCP_MAX_RECV_WINDOW_SIZE) 指定最大接收窗口（Receive Window）大小。增大它可能提升吞吐量，但也需要更多接收缓冲区才能高效工作。默认0表示由 TCP 协议栈根据配置的网络缓冲区数量选择。

### 4.6.4\_接收队列超时

[`CONFIG_NET_TCP_RECV_QUEUE_TIMEOUT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TCP_RECV_QUEUE_TIMEOUT) 指定接收数据的排队时间，单位为毫秒。收到乱序（Out-of-order）TCP 数据时会先排队；若在指定时间内仍无法交给应用，则丢弃。设为0禁用接收排队。

原文说明当前版本只保存连续数据，队列中不应有空洞。例如，正在等待序号（Sequence Number，SEQ）2时依次收到5、4、3、6，则把3、4、5、6按此顺序排队，收到2后交给应用；若收到5、4、3、7，则因缺少6而丢弃7。

## 4.7\_流量类别选项

接收和发送时都可以配置多个流量类别（Traffic Class）队列。每个队列由不同优先级的线程处理，分组按其优先级进入相应队列，从而得到不同处理时机。由于线程调度有延迟，实践中最快的发送方式是直接发送，不经过专用流量类别线程。因此原文说明：未启用用户空间时，[`CONFIG_NET_TC_TX_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TC_TX_COUNT) 默认0；启用用户空间时，最少有1个发送类别，因为用户空间应用没有足够权限直接交付消息。

接收侧建议至少有一个接收类别队列。设备驱动收到分组时通常处于中断请求（Interrupt Request，IRQ）上下文，不应直接向上层交付分组，而应放入流量类别队列。如果驱动接收分组时不处于 IRQ 上下文，则可将 [`CONFIG_NET_TC_RX_COUNT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_TC_RX_COUNT) 设为0。

> 译注：本轮官方 Kconfig 还在 USB 网络类以及 `NET_SHELL_REQUIRE_TX_THREAD` 等条件下将发送类别默认设为1；原文只按用户空间区分，未列全条件。架构指南中“默认一个发送队列”的叙述也应结合此配置理解。实际值以工程生成的配置为准。

## 4.8\_线程栈大小

启用网络的系统有多个网络专用线程。部分线程受功能配置控制，可按配置启用或禁用；每个线程栈大小都经过调整，以支持正常网络操作。

网络管理 API 默认使用专用线程。启用 [`CONFIG_NET_MGMT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MGMT) 和 [`CONFIG_NET_MGMT_EVENT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MGMT_EVENT) 后，此线程将网络管理事件交给已注册的监听者（Event Listener）。用户可注册回调，由 `net_mgmt` 线程在每次网络管理事件发生时调用。

默认事件线程栈较小，设计上希望回调只做很少的工作，以便尽快交付后续事件、避免丢失。原文称线程栈由 [`CONFIG_NET_MGMT_EVENT_QUEUE_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MGMT_EVENT_QUEUE_SIZE) 控制，并建议不要在回调中执行阻塞操作。可通过内核 Shell 的 `kernel threads` 命令观察网络线程栈使用情况。

> 译注：原文这里混淆了队列容量与线程栈大小。官方 `Kconfig.mgmt` 中，线程栈大小由 [`CONFIG_NET_MGMT_EVENT_STACK_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MGMT_EVENT_STACK_SIZE) 控制；[`CONFIG_NET_MGMT_EVENT_QUEUE_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NET_MGMT_EVENT_QUEUE_SIZE) 控制可排队的事件数量。修改队列容量不能替代扩大线程栈。上述源码核对依据的链接和摘要见[来源记录](../SOURCES.md)。
