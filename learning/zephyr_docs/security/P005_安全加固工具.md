# 第5章\_安全加固工具

原文：[官方页面](https://docs.zephyrproject.org/latest/security/hardening-tool.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 5.1\_安全加固（Hardening）

产品发布前，应尽可能确保软件安全。“加固（hardening）”就是增强系统安全性，使其能够抵御潜在威胁和漏洞的过程。

从总体上看，Zephyr 应用的加固分为两方面：

- 关闭可能导致安全漏洞的功能和编译选项。例如，确认没有使用“实验性（experimental）”功能，关闭断言（assertion）、命令行 shell 等常用于调试的功能。
- 启用能够改善安全性的可选功能，例如栈哨兵（stack sentinel）、硬件栈保护（hardware stack protection）等。其中一些功能依赖硬件。

Zephyr 提供了加固工具，将应用配置与加固数据库比较。该数据库中的建议由 Zephyr 安全工作组（Security Working Group）维护。工具读取构建目标的 Kconfig 选项，针对安全相关配置提出建议，并解释每项建议的理由。

<a id="usage"></a>

## 5.2\_使用方法（Usage）

使用 west：

```sh
# From the root of the zephyr repository
west build -b reel_board samples/hello_world
west build -t hardenconfig
```

使用 CMake 和 Ninja：

```sh
# From the root of the zephyr repository
# Use cmake to configure a Ninja-based buildsystem:
cmake -Bbuild -GNinja -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
ninja -Cbuild hardenconfig
```

> 译注——命令上下文：两个代码块是可选的两条官方操作路线，均从 Zephyr 源码仓库根目录执行。需先准备主机工具、Python 依赖、源码模块和匹配的工具链。原文注释分别为“从 Zephyr 仓库根目录开始”“用 CMake 配置基于 Ninja 的构建系统”“对生成的构建系统运行构建工具”。先完成配置或构建，再运行 `hardenconfig`；前一步失败时先解决错误。原例板名和路径照录，不代表本批已构建该目标。

输出应类似下面的表格。对可能导致安全漏洞的配置取值，工具给出推荐值，并说明该选项为何重要。

```text
Hardening report for profile: strict
+------------------------------+-----------+---------------+----------------+--------------------------------------------------+
| Name                         | Current   | Recommended   | Check result   | Rationale                                        |
+==============================+===========+===============+================+==================================================+
| CONFIG_BUILD_OUTPUT_STRIPPED | n         | y             | FAIL           | Produces a stripped copy of the ELF next to the  |
|                              |           |               |                | unstripped one, so a product that distributes or |
|                              |           |               |                | flashes the ELF itself ships no symbol names or  |
|                              |           |               |                | debug information for an attacker to work from.  |
|                              |           |               |                | Both files are built; deploying the stripped one |
|                              |           |               |                | remains the user's responsibility.               |
+------------------------------+-----------+---------------+----------------+--------------------------------------------------+
| CONFIG_STACK_SENTINEL        | n         | y             | FAIL           | Places a software sentinel value at the end of   |
|                              |           |               |                | each thread stack and checks it at context       |
|                              |           |               |                | switches, catching overflows on hardware without |
|                              |           |               |                | MPU/MMU stack protection.                        |
+------------------------------+-----------+---------------+----------------+--------------------------------------------------+
```

表头译文：`Name` 为名称，`Current` 为当前值，`Recommended` 为推荐值，`Check result` 为检查结果，`Rationale` 为理由；`FAIL` 表示不符合所选加固规则。`Hardening report for profile: strict` 表示“加固报告，采用 strict 配置档”。两项理由译文如下：

- `CONFIG_BUILD_OUTPUT_STRIPPED`：在未剥离的 ELF 旁生成一份已剥离副本。如果产品分发或烧写 ELF 本身，使用剥离副本可避免向攻击者暴露符号名称和调试信息。两个文件都会生成；确保部署剥离后的文件仍是使用者的责任。
- `CONFIG_STACK_SENTINEL`：在每个线程栈末尾放置软件哨兵值，并在上下文切换时检查，以便在没有内存保护单元（Memory Protection Unit，MPU）或内存管理单元（Memory Management Unit，MMU）栈保护的硬件上检测溢出。

对当前目标不适用的选项，例如无 MPU 的硬件上的 MPU 保护，或当前配置下没有可见提示的选项，默认不报告。

除了数据库规则，工具还会标出 Kconfig 本身标记为实验性、已弃用（deprecated）或不安全（not secure）的已启用选项，即选择了 [`CONFIG_EXPERIMENTAL`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_EXPERIMENTAL)、[`CONFIG_DEPRECATED`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_DEPRECATED) 或 [`CONFIG_NOT_SECURE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_NOT_SECURE) 的选项。

<a id="profiles"></a>

## 5.3\_配置档（Profiles）

建议按配置档分组。源码树内提供两个配置档：

| 配置档 | 适用检查范围 |
| --- | --- |
| `base` | 每次生产构建都应满足的基本加固要求：启用可用的内存保护和漏洞利用缓解功能，关闭本质上不安全的选项。 |
| `strict`，默认 | 包括 `base` 全部内容，并移除会扩大攻击面或泄露内部状态的调试、跟踪和可观测性功能，例如日志、shell 和断言。 |

某些产品确实需要保留其中一部分功能；如果属于这种情况，可改用 `base` 检查：

```sh
west build -t hardenconfig -- -DHARDENCONFIG_PROFILE=base
```

<a id="configuration-options"></a>

## 5.4\_配置选项（Configuration Options）

工具通过 CMake 缓存变量或同名环境变量控制。使用 `west build` 时，CMake 变量放在 `--` 后，如上例所示。

| 选项 | 作用 |
| --- | --- |
| `HARDENCONFIG_PROFILE` | 指定检查使用的加固配置档，默认为 `strict`。 |
| `HARDENCONFIG_SHOW_ALL` | 设置后，除失败项外，也列出通过和不适用的选项。 |
| `HARDENCONFIG_STRICT` | 设置后，只要任一检查失败就以非零状态码退出。可用于持续集成（Continuous Integration，CI）或发布流程的加固检查门禁。 |
| `HARDENCONFIG_JSON` | 指定额外输出 JSON 结果的文件，供脚本和仪表板读取。 |
| `HARDENCONFIG_EXTRA_SOURCES` | 用分号分隔的附加加固数据库文件列表，见后文。 |

<a id="the-hardening-database"></a>

## 5.5\_加固数据库（The Hardening Database）

数据库采用分散式组织：每条规则与被加固的代码放在一起，由对应代码的维护者审查。

- [`scripts/kconfig/hardening.yaml`](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/kconfig/hardening.yaml) 是安全工作组负责的中央文件，定义加固配置档，以及顶层 Kconfig 文件所定义符号的规则。
- 各 Kconfig 文件旁的 `hardening.yaml` 片段只包含规则，例如 [`subsys/bluetooth/hardening.yaml`](https://github.com/zephyrproject-rtos/zephyr/blob/main/subsys/bluetooth/hardening.yaml) 和 [`arch/x86/hardening.yaml`](https://github.com/zephyrproject-rtos/zephyr/blob/main/arch/x86/hardening.yaml)。工具会在 `arch/`、`boards/`、`drivers/`、`kernel/`、`lib/`、`modules/`、`share/`、`soc/` 和 `subsys/` 下自动发现片段。

在两个文件中重复定义同一符号会报错，在片段中定义配置档也会报错。

所有文件使用相同的 JSON 模式（schema）：[`scripts/schemas/hardening-schema.yaml`](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/schemas/hardening-schema.yaml)。每条规则以对应的 Kconfig 符号为键，建议一个精确值或整数约束：

```yaml
rules:
  BOOT_BANNER:
    value: n
    rationale: |
      The boot banner prints the exact Zephyr version to the console,
      letting anyone with console access fingerprint the firmware and
      match it against known vulnerabilities for that release.
    references: [CWE-200]

  STACK_POINTER_RANDOM:
    min: 100
    rationale: |
      Randomizing each thread's initial stack pointer makes stack
      addresses unpredictable. The offset is taken out of the thread's
      own stack, which keeps the recommended value small.
    references: [CWE-121]
```

原例的理由译文：

- `BOOT_BANNER`：启动横幅会向控制台输出精确的 Zephyr 版本，使任何能访问控制台的人都可以识别固件版本，并对应到该版本的已知漏洞。引用为 `CWE-200`。
- `STACK_POINTER_RANDOM`：随机化每个线程的初始栈指针，使栈地址不可预测。随机偏移取自线程自身的栈空间，因此推荐值保持较小。引用为 `CWE-121`。

贡献新规则时，将规则加入相关 Kconfig 文件旁的 `hardening.yaml`；若子系统尚无片段，则创建它。每条规则必须提供理由 `rationale`，由模式强制检查。CI 还验证所有文件是否能解析并满足模式、每条规则是否指向已有 Kconfig 符号且取值符合其类型、规则是否重复，以及是否存在疑似命名错误的片段文件，以防条目悄悄失效或未被加载。

理由是报告展示给读者的内容，会在较窄的列中换行，通常也是读者判断的主要依据。应以该功能为主语，用现在时的一两句话说明选项的安全后果。

| 推荐值形式 | 理由应说明的内容 |
| --- | --- |
| `value: n` | 启用该功能造成的暴露；相关时说明谁能够访问。例如：“详细调制解调器日志会转储与调制解调器交换的全部数据，其中可能包含 APN 设置、PIN 和服务器地址等凭据。” |
| `value: y` | 它能抵御什么攻击，或者关闭它会允许什么后果，选择更清楚的一种表达。 |
| `value: 0`、`min`、`max` | 其他取值会输出什么或无法阻止什么，以及边界值本身起什么作用。 |

不要这样写：

- **不要规定该选项属于哪种构建。** 由配置档决定产品是否接受某种后果。写“……泄露内部传输状态和地址”，而不是“……所以只能用于开发构建”。
- **不要声称无需后续动作就能实现尚不完整的效果。** 例如，选项可能只生成剥离后的二进制文件，确保实际部署它仍由使用者负责。
- **不要重复报告已有列。** 例如“0 会完全关闭随机化；建议至少 100 字节的随机偏移”，后半句已经属于 `Recommended` 列。
- **不要照搬另一条规则的措辞。** 同一报告中可能同时失败的两条规则，应有足够不同的说明，让读者能区分。

如果某个选项只有在另一条 `n` 规则已被违反时才能启用，并且另一条规则覆盖的配置档至少相同，就不要再给该选项添加 `n` 规则。例如，已经标出 [`CONFIG_SHELL`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_SHELL) 时，对 shell 命令模块的规则是冗余的，CI 会拒绝。仅仅通过 `select` 选择了某个被标记选项的上层选项，其规则并不冗余，因为它指出了使用者真正需要修改的选项。

规则不携带适用条件：依赖关系和硬件支持已经由 Kconfig 表达。当前目标不适用的建议会被报告为“不适用”，而不是失败。

<a id="extending-the-database-out-of-tree"></a>

## 5.6\_在源码树外扩展数据库（Extending the Database Out of Tree）

产品团队可以通过 `HARDENCONFIG_EXTRA_SOURCES`，在树内数据库之上叠加自己的建议。附加文件使用相同模式，可以定义新配置档（也可扩展树内配置档）、新增规则，以及覆盖树内规则。

重定义已有配置档会被拒绝，因此无论产品如何叠加规则，树内配置档仍保持本页所描述的含义。

```yaml
profiles:
  acme-production:
    extends: strict
    description: ACME product security policy.

rules:
  MY_VENDOR_DEBUG_INTERFACE:
    value: n
    profiles: [acme-production]
    rationale: |
      The vendor debug interface bypasses the product's authentication.
```

原例文字译文：`ACME product security policy.` 为“ACME 产品安全策略”；`The vendor debug interface bypasses the product's authentication.` 为“厂商调试接口会绕过产品的身份验证”。

```sh
west build -t hardenconfig -- \
  -DHARDENCONFIG_EXTRA_SOURCES=/path/to/acme-hardening.yaml \
  -DHARDENCONFIG_PROFILE=acme-production
```

> 译注：`/path/to/acme-hardening.yaml` 是官方原例的占位路径，不是应照抄的机器地址。附加 YAML 是产品团队自行提供的文件，必须先存在。相对路径的基准取决于实际执行工具的工作目录，不应误认为总是启动 west 的目录；源码跟踪说明见下文。本页保留原例以供对照，不要求读者固定仓库存放位置。

### 5.6.1\_译注：路径与配置的读取位置

本次读取的官方 [`cmake/modules/kconfig.cmake`](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/cmake/modules/kconfig.cmake) 先取得 `HARDENCONFIG_*` 设置，再作为环境变量传给加固目标，并将工作目录设置为 `${PROJECT_BINARY_DIR}/kconfig`。[`scripts/kconfig/hardenconfig.py`](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/scripts/kconfig/hardenconfig.py) 读取这些变量，把附加来源按分号拆开，再交给 [`hardeninglib.py`](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/scripts/kconfig/hardeninglib.py) 打开；该库不会自动把相对来源改为相对于启动 west 的目录。

若产品的附加规则保存在应用内自行创建的 `config/acme-hardening.yaml`，可以在应用已有 `CMakeLists.txt` 中、`find_package(Zephyr ...)` 之前，按应用目录推导文件位置。以下为本地补充示例，不属于上面的官方原例：

```cmake
# 应用 CMakeLists.txt；前提：已创建 config/acme-hardening.yaml。
# 在 find_package(Zephyr ...) 之前设置，让配置阶段读取。
set(HARDENCONFIG_EXTRA_SOURCES
    "${CMAKE_CURRENT_SOURCE_DIR}/config/acme-hardening.yaml"
    CACHE STRING "Product hardening database files")
```

文件名从当前应用目录推导，不包含作者的盘符或用户名。`CACHE` 设置保存在该构建目录的 `CMakeCache.txt`，普通 `set(... CACHE ...)` 不覆盖已有值；更改位置后需重新配置对应构建目录并更新该缓存项。直接使用环境变量时，其保存期限由设置环境变量的终端或主机环境决定。工具生成报告，不会自动替使用者修改应用 Kconfig 配置。

本仓库可通过相对链接查看[对应 CMake 文件](../../../cmake/modules/kconfig.cmake)和[对应加固脚本](../../../scripts/kconfig/hardenconfig.py)。网页和上游 main 持续变化，本仓库参照版本可能还没有本文的新增数据库文件或选项，不能仅因文件名相同就视为同版本实现。


对应官方文档源码：[doc/security/hardening-tool.rst](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/doc/security/hardening-tool.rst)。

本仓库的[对应源码](../../../doc/security/hardening-tool.rst)可用于跟踪，版本可能与网页不同；本批仅翻译和核对文档，没有执行固件构建、模拟运行或烧录。
