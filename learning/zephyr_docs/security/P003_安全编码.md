# 第3章\_安全编码

原文：[官方页面](https://docs.zephyrproject.org/latest/security/secure-coding.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 3.1\_背景

传统上，基于微控制器（microcontroller）的系统并未充分重视安全。人们通常认为它们孤立、与外界断开，而且难以接触，因此不容易受到攻击。物联网（Internet of Things，IoT）改变了这一点：运行在小型微控制器上的代码，如今经常能访问互联网，至少也会连接其他设备，而这些设备本身可能存在漏洞。考虑到这类设备往往部署数量庞大，失控的访问可能造成严重后果，见本页注释 1。

本文件说明 Zephyr 项目落实安全的要求和流程。所有提交的代码都应遵循这些原则。本文件的大量内容来自 [CIIBPB](P008_安全文献引用.md#ciibpb)。

<a id="introduction-and-scope"></a>

## 3.2\_简介与范围（Introduction and Scope）

本文件从安全角度说明 [Zephyr 项目](https://www.zephyrproject.org/)的指导原则，其中许多理念来自其他开源项目。

首先概述与 Zephyr 有关的安全设计；随后“安全开发知识”说明项目开发者应具备的基本能力，并提供其他安全资料的引用。如何编写安全软件的全部细节超出本文范围。该部分还说明至少一名主要开发者应具备的漏洞知识，这是后续审查流程所必需的。

随后介绍将变更合入 Zephyr 代码库的审查流程，以及项目如何处理安全敏感问题。最后说明本文档本身的修改方式。

## 3.3\_安全编码原则（Secure Coding）

要使 Zephyr 这样的开放软件系统具备安全性，必须遵循一组明确的设计标准。[SALT75](P008_安全文献引用.md#salt75) 定义了以下广泛接受的保护机制原则，用于预防安全违规并限制其影响。

1. **开放设计（Open Design）。** 广泛使用的系统无法长期隐藏其保护机制。因此，不应依赖秘密的、专门定制的安全手段，而应使用公开接受的密码算法及成熟的密码库。
2. **机制简约（Economy of Mechanism）。** 底层系统设计应尽可能简单、精小。Zephyr 可以通过模块化代码和抽象 API 等方式实现，参见 [PAUL09](P008_安全文献引用.md#paul09)。
3. **完全仲裁（Complete Mediation）。** 对每个对象和进程的每次访问，都必须先验证身份。应尽可能避免保存访问条件的机制。
4. **默认安全拒绝（Fail-Safe Defaults）。** 默认限制访问，只有满足系统保护方案定义的特定条件时才允许，例如身份验证成功后。服务的默认设置也应提供尽可能高的安全性，对应“默认安全（Secure by Default）”原则，参见 [MS12](P008_安全文献引用.md#ms12)。
5. **权限分离（Separation of Privilege）。** 只有同时满足两个或更多条件才授予访问权限。在 Zephyr 中，这可以包括拆分密钥（split keys），参见 [PAUL09](P008_安全文献引用.md#paul09)。
6. **最小权限（Least Privilege）。** 每个用户、程序和线程只获得完成任务所需的最小权限子集。这种正向安全模型（positive security model）旨在尽量缩小系统攻击面（attack surface）。
7. **最少共用机制（Least Common Mechanism）。** 多个用户或进程共用的机制，除非确有必要，不应共享。[SALT75](P008_安全文献引用.md#salt75) 的例子是：某个函数应实现为各用户分别执行的共享库，而不是所有用户共用的特权过程（supervisor procedure）。
8. **心理可接受性（Psychological Acceptability）。** 安全功能应便于开发者使用，才能确保其被采用并正确使用。

除这些通用原则外，安全实时操作系统（Real-Time Operating System，RTOS）的开发还应遵循以下要求。

**互补安全／纵深防御（Complementary Security / Defense in Depth）。** 不要只依赖一种威胁缓解方法。互补安全由底层平台承担部分威胁缓解；若平台不提供这些机制，或这些机制不可信，则应使用纵深防御，参见 [MS12](P008_安全文献引用.md#ms12)。

**不常用服务默认关闭（Less Commonly Used Services Off by Default）。** 为减少潜在攻击暴露面，较少使用的功能或服务不应默认启用；[MS12](P008_安全文献引用.md#ms12) 给出了 80% 的阈值。Zephyr 可以通过配置管理实现：每项功能和模块都表示为配置选项，必须显式启用。这样，不需要的功能、协议和驱动即可全部关闭。若底层选项和 API 已启用、应用却没有使用，应通知使用者。

**变更管理（Change Management）。** 为保证系统变更可追溯，每项变更应遵循指定流程，包括变更请求、影响分析、批准、实现和验证；各阶段提供相应文档。所有提交都应关联问题跟踪系统中的缺陷报告或变更请求；没有有效关联的提交应被拒绝。

<a id="secure-development-knowledge"></a>

## 3.4\_安全开发知识（Secure Development Knowledge）

<a id="secure-designer"></a>

### 3.4.1\_安全设计者（Secure Designer）

Zephyr 至少必须有一名主要开发者了解如何设计安全软件。这要求理解下列设计原则，其中包括 [SALT75](P008_安全文献引用.md#salt75) 的八项原则：

- **机制简约：** 在实际可行的范围内保持设计简单、精小，例如进行整体性的简化。
- **默认安全拒绝：** 访问决策默认拒绝，项目安装后的默认状态应安全。
- **完全仲裁：** 每次可能受限制的访问都必须检查权限，且检查不可绕过。
- **开放设计：** 安全机制不应依赖攻击者不了解设计，而应依赖密钥、密码等更容易保护和更换的信息。
- **权限分离：** 理想情况下，对重要对象的访问应取决于多个条件，使攻破一种保护机制不等于获得完全访问权。例如，同时要求密码与硬件令牌的多因素身份验证（multi-factor authentication），强于单因素验证。
- **最小权限：** 进程应以必需的最低权限运行。
- **最少共用机制：** 尽量减少多个用户共用、所有用户都依赖的机制，例如临时文件目录。
- **心理可接受性：** 人机界面必须易用；遵循“最少惊讶（least astonishment）”的设计有助于实现这一点。
- **有限攻击面（Limited Attack Surface）：** 限制攻击者能够尝试进入系统或提取数据的不同入口集合。
- **用允许列表验证输入（Input Validation with Allowlists）：** 接受输入前，通常应先检查有效性。使用只接受已知合法值的允许列表（allowlist），不要依赖试图列举已知非法值的阻止列表（blocklist）。

<a id="vulnerability-knowledge"></a>

### 3.4.2\_漏洞知识（Vulnerability Knowledge）

“主要开发者（primary developer）”是指熟悉项目代码库、有能力修改代码，并得到大多数项目参与者认可的人。他通常在过去一年内做出过多项贡献，包括代码、文档或回答问题。

通常符合以下情况的开发者会被视为主要开发者：发起了项目且离开项目未超过三年；有资格从私密漏洞报告渠道接收信息（若存在该渠道）；可以代表项目接受提交；或者负责最终软件发行。如果项目只有一名开发者，此人就是主要开发者。

至少一名主要开发者必须了解此类软件中容易导致漏洞的常见错误，并且针对每类错误，至少掌握一种防范或缓解方法。

视软件类型而定，例子包括 SQL 注入（SQL injection）、操作系统注入（OS injection）、典型缓冲区溢出（buffer overflow）、跨站脚本（cross-site scripting）、缺少身份验证（authentication）和缺少授权（authorization）。常用列表见 [CWE/SANS top 25](https://cwe.mitre.org/top25/) 或 [OWASP Top 10](https://owasp.org/www-project-top-ten/)。

非营利机构 OpenSecurityTraining2 提供面向 C/C++ 开发者的免费课程 [OST2_1001](https://ost2.fyi/Vulns1001)，教授如何预防、检测和缓解线性栈／堆缓冲区溢出、非线性越界写入、整数溢出及其他整数问题。后续课程 [OST2_1002](https://ost2.fyi/Vulns1002) 涵盖未初始化数据访问、竞态条件（race condition）、释放后使用（use-after-free）、类型混淆（type confusion）和信息泄露（information disclosure）漏洞。

<a id="zephyr-security-subcommittee"></a>

## 3.5\_Zephyr安全分委员会（Zephyr Security Subcommittee）

应设立 Zephyr 安全分委员会，负责落实本指南、监督审查并改进这些指导原则。该团队按照 Zephyr 项目章程建立。

<a id="code-review"></a>

## 3.6\_代码审查（Code Review）

Zephyr 应使用代码审查系统，所有变更都必须经过审查。每项变更至少由一名并非变更作者的主要开发者审查。审查者应基于一般安全知识判断变更是否影响系统安全；如果有影响，还应请具备漏洞知识的开发者或安全设计者审查。

这些人员中的任何一人，都应有权阻止变更合入主线，直到安全问题得到解决。

<a id="issues-and-bug-tracking"></a>

## 3.7\_问题与缺陷跟踪（Issues and Bug Tracking）

Zephyr 应有 [GitHub](https://www.github.com) 这样的跟踪系统，用于记录和跟踪系统中发现的缺陷。

安全问题通常比较敏感，因此跟踪系统应有标记安全问题的字段。设置后，该问题仅对 Zephyr 安全分委员会可见。还应有另一个字段，让委员会添加能够查看该问题的其他使用者。

这种披露禁限期（embargo），即限制可见性的时间，只能持续固定期限，默认期限由项目决定。不过，安全方面的考虑往往涉及 Zephyr 项目之外，因此可能需要延长期限；所需时间应在问题记录中明确注明。

安全分委员会至少每月审查一次问题列表，重点跟踪修复、判断是否需要通知或邀请外部相关方，以及决定何时解除禁限。不应通过自动化方式解除禁限，但也应避免对已解决问题作不必要的延迟。

> 译注：本节保留原页对问题跟踪系统字段和可见性的要求。具体的现行报告入口与安全公告流程参见本册[安全漏洞报告](P007_安全漏洞报告.md)；这里没有创建问题或发送报告。
