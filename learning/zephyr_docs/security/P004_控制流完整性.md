# 第4章\_控制流完整性

原文：[官方页面](https://docs.zephyrproject.org/latest/security/control-flow-integrity.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 4.1\_控制流完整性概念

控制流完整性（Control Flow Integrity，CFI）确保程序控制流沿预定路径运行，防止攻击者将执行转向恶意代码。它尤其适用于防御控制流劫持（control flow hijacking），例如面向返回编程（Return-Oriented Programming，ROP）和面向跳转编程（Jump-Oriented Programming，JOP）攻击。

CFI 在运行时验证控制流，确保函数调用和返回的目标合法。通常通过代码插桩（instrumentation）添加检查，验证执行是否遵循程序控制流图（control flow graph）规定的路径。

<a id="forward-and-return-edges"></a>

## 4.2\_前向边与返回边（Forward and Return Edges）

CFI 将控制流边分为两类：

- **前向边（forward edge）：** 从一个函数流向另一个函数，例如函数调用。通常检查调用目标是否是程序中的合法函数。
- **返回边（return edge）：** 从函数返回调用者。检查返回地址是否有效，且是否对应合法调用点。

前向边可以通过编译器插桩检查函数调用目标。返回边可以通过影子栈（shadow stack）或其他机制保证返回地址合法。

Zephyr 支持维护影子栈，通过 [`CONFIG_HW_SHADOW_STACK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HW_SHADOW_STACK) 启用。内核随后使用 [`K_THREAD_HW_SHADOW_STACK_DEFINE`](../thread_stack_reference/P001_线程栈接口.md#ga16eed4de8bbcf2132f0947844c3874b8) 等宏，并配合其他线程栈宏，为线程影子栈提供存储区域。应用通常只需启用 [`CONFIG_HW_SHADOW_STACK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HW_SHADOW_STACK) 及相关选项，例如 [`CONFIG_HW_SHADOW_STACK_PERCENTAGE_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HW_SHADOW_STACK_PERCENTAGE_SIZE) 和 [`CONFIG_HW_SHADOW_STACK_MIN_SIZE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HW_SHADOW_STACK_MIN_SIZE)，内核就会自动管理各线程的影子栈。

<a id="implementation-details"></a>

### 4.2.1\_实现细节（Implementation Details）

`K_THREAD_HW_SHADOW_STACK*` 系列宏仅对影子栈参数做最低限度的设置，随后调用架构专用的 `ARCH_THREAD_HW_SHADOW_STACK*` 宏完成实际设置。

<a id="hardware-support"></a>

## 4.3\_硬件支持（Hardware Support）

CFI 可以用软件实现，但硬件支持能显著提升效果和性能。Zephyr 当前支持 Intel 控制流强制执行技术（Control-flow Enforcement Technology，CET），提供基于硬件的 CFI 支持。

<a id="intel-cet"></a>

### 4.3.1\_Intel CET

Intel CET 是一组增强应用安全的硬件特性，包含两个主要部分：

- **影子栈（Shadow Stack）：** 为返回地址维护独立栈，防止返回地址被篡改。函数返回时，从影子栈弹出返回地址，与普通栈中的返回地址比较，为防止控制流劫持增加一层保护。
- **间接分支跟踪（Indirect Branch Tracking，IBT）：** 跟踪函数指针等间接分支，确保它们只跳转到代码中的合法位置，防止攻击者借助 ROP 等技术将执行重定向到任意代码。

这两项特性分别提供返回边和前向边验证。在支持的硬件上，用 [`CONFIG_HW_SHADOW_STACK`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_HW_SHADOW_STACK) 启用影子栈，用 [`CONFIG_X86_CET_IBT`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_X86_CET_IBT) 启用 IBT。

IBT 实际上由编译器实现，因此需要工具链支持。Zephyr SDK 的 x86 工具链可以构建支持 IBT 的应用，但其中的预编译产物，如 `libc` 和 `libgcc`，没有启用 IBT。C 库因此需要作为模块重新构建，例如通过 [`CONFIG_PICOLIBC_USE_MODULE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_PICOLIBC_USE_MODULE)；其他部分则需要定制工具链。

<a id="intel-cet-limitations"></a>

### 4.3.2\_Intel CET限制（Intel CET Limitations）

当前在后台创建的影子栈处于全局命名空间。因此，即使位于不同的编译单元（compilation unit），也不能重复使用线程栈名称。

<a id="arm-pointer-authentication-and-branch-target-identification"></a>

### 4.3.3\_ARM指针认证与分支目标识别

ARM 平台通过指针认证（Pointer Authentication，PAC）和分支目标识别（Branch Target Identification，BTI）提供硬件 CFI。Cortex-M 和 ARM64（Cortex-A/R）架构均有支持这些特性的版本：

- **PAC：** 使用密码签名保护返回地址和其他指针。返回地址压栈时，用各线程独有的密钥签名；返回前验证签名，确保地址未被篡改，从而防御 ROP。该能力见于 ARMv8.1-M Mainline（Cortex-M）以及 ARMv8.3-A 和后续 ARM64 架构。
- **BTI：** 用特殊的 BTI 落点（landing pad）指令标记合法的间接分支目标。处理器检查间接分支是否仅落到带 BTI 标记的有效目标，从而防御 JOP。该能力见于 ARMv8.1-M Mainline（Cortex-M）以及 ARMv8.5-A 和后续 ARM64 架构。

PAC 和 BTI 分别提供返回边和前向边验证，可通过 `ARM_PACBTI` 菜单启用。选项包括 [`CONFIG_ARM_PACBTI_STANDARD`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ARM_PACBTI_STANDARD)（同时启用 PAC 和 BTI）、[`CONFIG_ARM_PACBTI_PACRET`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ARM_PACBTI_PACRET)（仅 PAC）、[`CONFIG_ARM_PACBTI_BTI`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_ARM_PACBTI_BTI)（仅 BTI）及其他变体。二者既可独立使用，也可组合以提供完整控制流保护。

与 x86 CET IBT 一样，这些特性需要编译器支持和恰当的 C 库插桩。PAC 要求函数采用相应签名及验证指令；BTI 要求所有合法分支目标包含 BTI 落点指令。工具链附带的预编译 C 库通常没有这些插桩。

为支持 BTI，C 库必须使用 `-mbranch-protection` 参数编译，使所有函数都带有 BTI 落点。因此，只要选项启用了 BTI，就只能使用 [`CONFIG_MINIMAL_LIBC`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_MINIMAL_LIBC)，或者通过 [`CONFIG_PICOLIBC_USE_MODULE`](https://docs.zephyrproject.org/latest/kconfig.html#CONFIG_PICOLIBC_USE_MODULE) 作为模块构建的 picolibc。工具链附带的 Newlib 不支持与 BTI 搭配使用。

PAC 的要求相对宽松，因为它主要影响函数入口和退出序列（prologue/epilogue）；不过，为获得最佳安全效果，仍建议构建带 PAC 支持的 C 库。
