# 第6章\_读取与解码

原文：[Read and Decode](https://docs.zephyrproject.org/latest/hardware/peripherals/sensor/read_and_decode.html)。读取日期：2026-10-12，`latest`。

## 6.1\_接口与数据流

**读取与解码（Read and Decode）**是原文称正在迅速稳定的传感器**应用程序编程接口（Application Programming Interface，API）**。主要函数包括 [`sensor_read()`](https://docs.zephyrproject.org/latest/doxygen/html/group__sensor__interface.html#gace7f20e29b302e607ba274fe40a2c2bd)、[`sensor_read_async_mempool()`](https://docs.zephyrproject.org/latest/doxygen/html/group__sensor__interface.html#gaf53b015c47acab3c3acb4cb1d8ab827d)、[`sensor_get_decoder()`](https://docs.zephyrproject.org/latest/doxygen/html/group__sensor__interface.html#ga12db6fc43adce48d34c25c16fd2336a3) 和 [`sensor_decode()`](https://docs.zephyrproject.org/latest/doxygen/html/group__sensor__interface.html#ga018bca56056ae2558f9e45aeb2fa5f53)，分别用于读取、异步读取到内存池缓冲区、取得解码器和解码。

这些接口面向更多传感器类型和数据流，解决旧 [Fetch and Get](P004_获取与读取.md) 遇到的一些限制。读取函数先把设备编码数据放入调用方提供的缓冲区，解码器再把传感器特定编码转换成各通道的 [`q31_t`](https://docs.zephyrproject.org/latest/doxygen/html/group__math__dsp.html#gadc89a3547f5324b7b3b95adec3806bc0) 定点向量，以便进一步使用**数字信号处理（Digital Signal Processing，DSP）**函数，例如低通滤波、**快速傅里叶变换（Fast Fourier Transform，FFT）**和传感器融合。

读取的底层实现默认采用异步方式，利用**实时输入输出（Real-Time Input/Output，RTIO）**串接异步请求，或从一个调用上下文启动多个传感器的请求。

> 译注：底层异步不等于所有上层函数都非阻塞。`sensor_read()` 是阻塞包装；需要非阻塞提交应选择相应异步接口。定点结果还需结合对应数据结构的缩放信息理解，不能把整数直接当成物理量。

## 6.2\_相较旧接口的能力

新的数据流支持以下用法：

- 先取得原始数据，选择不解码、以后再解码，或交给另一处理器（例如手机）解码。
- 直接从中断处理程序发起读取，不必为这一步设专用线程和栈，也无需依赖带来可变延迟的工作队列；从单一中断、线程或工作队列上下文发起多个传感器的读取。
- 对同一设备提交多个读取请求，实现**乒乓双缓冲（Ping-Pong / Double Buffering）**。
- 组成完整传感器数据处理流程，从单个线程按**有向无环图（Directed Acyclic Graph，DAG）**的依赖顺序处理，并支持[传感子系统](../io_services/P002_传感子系统.md)中的软件虚拟传感器。
- 有可能预先配置**直接存储器访问（Direct Memory Access，DMA）**，由**通用输入输出（General-Purpose Input/Output，GPIO）**事件触发，使**中央处理器（Central Processing Unit，CPU）**无需逐次参与处理传感器缓冲区水位等事件。

旧接口在内存和触发处理方面的一些限制也得到改善：

- 触发器产生排队事件，而不是直接交给应用回调。
- 触发器可配置为自动获取数据，有可能让 GPIO 中断直接触发预先配置的 DMA 传输。
- 降低回调或上下文切换长时间屏蔽中断而漏事件的可能性。
- 通过**先进先出缓冲区（First-In, First-Out，FIFO）**触发器，将数据读入内存池分配的缓冲区，支持传感器硬件 FIFO。
- 传感器数据处理可在有内存保护的**用户态（User Mode）**线程中完成。
- 更好地支持同一种测量类型下的多个通道。

**原文注意：**要充分发挥这些能力，访问传感器的通信路径须支持 RTIO，通常意味着使用支持 RTIO 的**串行外设接口（Serial Peripheral Interface，SPI）**或 **I²C总线（Inter-Integrated Circuit，I2C）**驱动。

> 译注：从中断发起请求指非阻塞提交路径，不包括调用阻塞读取、等待完成或执行任意解码工作；原文中预编程 DMA 和自动流水处理也以驱动与硬件支持为条件。使用内存池时仍需规划队列深度、缓冲容量和错误处理，不能把降低漏事件风险理解为无限存储或必然不丢数据。

## 6.3\_轮询一个温度传感器

为所需通道实例化一个轮询用 **输入输出设备（I/O Device）**对象，其角色类似文件描述符；之后可请求阻塞或非阻塞读取，并按需把结果解码为定点数。

下面是原文的温度读取示例。宏 `DT_ALIAS` 解析设备树别名，宏 `DEVICE_DT_GET` 取得设备指针；示例宏 `TEMP_CHANNEL` 组合温度类型与索引。设备树别名 `temp0` 指向温度传感器；宏 `SENSOR_DT_READ_IODEV` 定义读取对象，宏 `RTIO_DEFINE` 定义提交和完成队列上下文。结构体 `sensor_q31_data` 保存解码后的结果，宏 `SENSOR_DECODER_DT_GET` 获取设备类型对应的解码器，宏 `SENSOR_DECODE_CONTEXT_INIT` 初始化解码上下文。枚举 `SENSOR_CHAN_AMBIENT_TEMP` 表示环境温度，索引 0 选择这一类型的第一个通道。结果格式宏 `PRIsensor_q31_data` 与参数宏 `PRIsensor_q31_data_arg` 配套打印，函数 `k_msleep(1)` 休眠一毫秒。

```c
/*
 * Copyright (c) 2024 Intel Corporation
 *
 * SPDX-License-Identifier: Apache-2.0
 */

#include <zephyr/drivers/sensor.h>

#define TEMP_CHANNEL {SENSOR_CHAN_AMBIENT_TEMP, 0}

const struct device *const temp0 = DEVICE_DT_GET(DT_ALIAS(temp0));

SENSOR_DT_READ_IODEV(temp_iodev, DT_ALIAS(temp0), TEMP_CHANNEL);
RTIO_DEFINE(temp_ctx, 1, 1);

int main(void)
{
	int rc;
	uint8_t buf[8];
	struct sensor_q31_data temp_data = {0};
	struct sensor_decode_context temp_decoder = SENSOR_DECODE_CONTEXT_INIT(
		SENSOR_DECODER_DT_GET(DT_ALIAS(temp0)), buf, SENSOR_CHAN_AMBIENT_TEMP, 0);

	while (1) {
		/* Blocking read */
		rc = sensor_read(temp_iodev, &temp_ctx, buf, sizeof(buf));

		if (rc != 0) {
			printk("sensor_read() failed %d\n", rc);
		}

		/* Decode the data into a single q31 */
		sensor_decode(&temp_decoder, &temp_data, 1);

		printk("Temperature " PRIsensor_q31_data "\n",
		       PRIsensor_q31_data_arg(temp_data, 0));

		k_msleep(1);
	}
}
```

> 译注：此原例并非已经编译通过的完整应用。按所核对的 `include/zephyr/drivers/sensor.h`，读取函数需要设备指针，应传 `&temp_iodev`；读取失败后不可继续解码旧缓冲区。解码会推进上下文的帧迭代位置，新一轮独立缓冲区应重新初始化或把 `fit` 置零，并检查解码返回值。固定 8 字节缓冲区是否足够，要看该设备编码格式；设备树别名、驱动支持、设备就绪和输出结构大小均须配套核对。

## 6.4\_同一线程读取多个传感器

一个线程可以并发启动多个传感器及其多个通道的异步请求，在各读取完成后再解码。下面原例使用两个温度传感器，每个有两个温度通道。

示例宏 `TEMP_CHANNELS` 列出两个通道，`NUM_SENSORS` 给出设备数量；示例宏 `TEMP_IODEV_SYM` 生成对象名，`TEMP_IODEV_PTR` 取得对象地址，`TEMP_ALIAS` 构造设备树别名，宏 `TEMP_DEFINE_IODEV` 为各设备展开读取对象；宏 `CONCAT` 拼接名称，宏 `LISTIFY` 按数量展开重复定义。宏 `RTIO_DEFINE_WITH_MEMPOOL` 创建带缓冲池的 RTIO 上下文。

函数 `sensor_read_async_mempool()` 提交请求，并把设备对象指针作为用户数据关联到完成结果。**完成队列项（Completion Queue Entry，CQE）**由结构体 `rtio_cqe` 表示：函数 `rtio_cqe_consume_block()` 等待完成项，函数 `rtio_cqe_get_mempool_buffer()` 获取其缓冲区，函数 `rtio_cqe_release()` 释放完成项；数据解码完成后，函数 `rtio_release_buffer()` 另行释放内存池缓冲区。这两种释放不能相互替代。

```c
/*
 * Copyright (c) 2024 Intel Corporation
 *
 * SPDX-License-Identifier: Apache-2.0
 */

#include <zephyr/drivers/sensor.h>

#define TEMP_CHANNELS				\
	{ SENSOR_CHAN_AMBIENT_TEMP, 0 },	\
	{ SENSOR_CHAN_AMBIENT_TEMP, 1 }
#define TEMP_ALIAS(id) DT_ALIAS(CONCAT(temp, id))
#define TEMP_IODEV_SYM(id) CONCAT(temp_iodev, id)
#define TEMP_IODEV_PTR(id) &TEMP_IODEV_SYM(id)
#define TEMP_DEFINE_IODEV(id)			\
	SENSOR_DT_READ_IODEV(			\
		TEMP_IODEV_SYM(id),		\
		TEMP_ALIAS(id),			\
		TEMP_CHANNELS			\
		);

#define NUM_SENSORS 2

LISTIFY(NUM_SENSORS, TEMP_DEFINE_IODEV, (;));

struct sensor_iodev *iodevs[NUM_SENSORS] = { LISTIFY(NUM_SENSORS, TEMP_IODEV_PTR, (,)) };

RTIO_DEFINE_WITH_MEMPOOL(temp_ctx, NUM_SENSORS, NUM_SENSORS, NUM_SENSORS, 8, sizeof(void *));

int main(void)
{
	int rc;
	uint32_t temp_frame_iter = 0;
	struct sensor_q31_data temp_data[2] = {0};
	struct sensor_decoder_api *decoder;
	struct rtio_cqe *cqe;
	uint8_t *buf;
	uint32_t buf_len;

	while (1) {
		/* Non-Blocking read for each sensor */
		for (int i = 0; i < NUM_SENSORS; i++) {
			rc = sensor_read_async_mempool(iodevs[i], &temp_ctx, iodevs[i]);

			if (rc != 0) {
				printk("sensor_read() failed %d\n", rc);
				return;
			}
		}

		/* Wait for read completions */
		for (int i = 0; i < NUM_SENSORS; i++) {
			cqe = rtio_cqe_consume_block(&temp_ctx);

			if (cqe->result != 0) {
				printk("async read failed %d\n", cqe->result);
				return;
			}

			/* Get the associated mempool buffer with the completion */
			rc = rtio_cqe_get_mempool_buffer(&temp_ctx, cqe, &buf, &buf_len);

			if (rc != 0) {
				printk("get mempool buffer failed %d\n", rc);
				return;
			}

			struct device *sensor = ((struct sensor_read_config *)
				((struct rtio_iodev *)cqe->userdata)->data)->sensor;

			/* Done with the completion event, release it */
			rtio_cqe_release(&temp_ctx, cqe);

			rc = sensor_get_decoder(sensor, &decoder);
			if (rc != 0) {
				printk("sensor_get_decoder failed %d\n", rc);
				return;
			}

			/* Frame iterators, one per channel we are decoding */
			uint32_t temp_fits[2] = { 0, 0 };

			decoder->decode(buf, {SENSOR_CHAN_AMBIENT_TEMP, 0},
					&temp_fits[0], 1, &temp_data[0]);
			decoder->decode(buf, {SENSOR_CHAN_AMBIENT_TEMP, 1},
					&temp_fits[1], 1, &temp_data[1]);

			/* Done with the buffer, release it */
			rtio_release_buffer(&temp_ctx, buf, buf_len);

			printk("Temperature for %s channel 0 " PRIsensor_q31_data ", channel 1 "
			    PRIsensor_q31_data "\n",
			    dev->name,
			    PRIsensor_q31_data_arg(temp_data[0], 0),
			    PRIsensor_q31_data_arg(temp_data[1], 0));
		}
	}

	k_msleep(1);
}
```

> 译注：原例还有明确的类型与语法差异，不能按原样当成可编译程序：当前头文件中 I/O 对象是 `struct rtio_iodev`，不是例中的 `struct sensor_iodev`；设备及解码器应保持接口要求的 `const` 限定。C 函数实参中的 `{SENSOR_CHAN_AMBIENT_TEMP, 0}` 需要改成有类型的复合字面量，例如 `(struct sensor_chan_spec){SENSOR_CHAN_AMBIENT_TEMP, 0}`。打印处 `dev` 未定义，应关联实际完成的 `sensor`；`int main()` 的错误分支不应只写无返回值的 `return;`，循环后的休眠也永远不会执行。

> 译注：每条错误路径都须处理已取得的完成项、缓冲区和其他未完成请求。只有提交成功的请求才应计入待完成数量；完成顺序不必等同于提交顺序，所以原例用完成项用户数据找回设备。以上说明依据本地接口核对，未把该本地版本等同于官网构建版本，也未在此执行并发采样。

## 6.5\_触发事件与流式读取

**流式读取（Streaming）**通过流 I/O 设备配置指定要捕获的触发器集合，以及事件发生时是否一起取得数据。例中的枚举 `SENSOR_STREAM_DATA_INCLUDE` 表示包含数据，`SENSOR_STREAM_DATA_NOP` 表示不为该事件额外请求数据；宏 `SENSOR_DT_STREAM_IODEV` 定义流对象。

函数 `sensor_stream()` 启动流，并可返回结构体 `rtio_sqe` 表示的请求句柄。解码器的函数成员 `get_frame_count` 取得某通道的帧数，`has_trigger` 判断缓冲区是否携带相应事件，`decode` 按帧迭代解码。示例拟同时处理数据就绪与轻敲事件。示例宏 `ACCEL_TRIGGERS` 列出触发配置；原文用枚举名 `SENSOR_TRIG_DRDY` 指数据就绪（下方说明版本差异），枚举 `SENSOR_TRIG_TAP` 指轻敲。`ACCEL_ALIAS`、`ACCEL_IODEV_SYM`、`ACCEL_IODEV_PTR`、`ACCEL_DEFINE_IODEV` 是应用示例宏，分别构造别名、对象名、地址和流对象定义。通道枚举 `SENSOR_CHAN_ACCEL_XYZ` 选择三轴加速度：

```c
/*
 * Copyright (c) 2024 Intel Corporation
 *
 * SPDX-License-Identifier: Apache-2.0
 */

#include <zephyr/drivers/sensor.h>

#define ACCEL_TRIGGERS						\
	{ SENSOR_TRIG_DRDY, SENSOR_STREAM_DATA_INCLUDE },	\
	{ SENSOR_TRIG_TAP, SENSOR_STREAM_DATA_NOP }
#define ACCEL_ALIAS(id) DT_ALIAS(CONCAT(accel, id))
#define ACCEL_IODEV_SYM(id) CONCAT(accel_iodev, id)
#define ACCEL_IODEV_PTR(id) &ACCEL_IODEV_SYM(id)
#define ACCEL_DEFINE_IODEV(id)					\
	SENSOR_DT_STREAM_IODEV(					\
		ACCEL_IODEV_SYM(id),				\
		ACCEL_ALIAS(id),				\
		ACCEL_TRIGGERS					\
		);

#define NUM_SENSORS 2

LISTIFY(NUM_SENSORS, ACCEL_DEFINE_IODEV, (;));

struct sensor_iodev *iodevs[NUM_SENSORS] = { LISTIFY(NUM_SENSORS, ACCEL_IODEV_PTR, (,)) };

RTIO_DEFINE_WITH_MEMPOOL(accel_ctx, NUM_SENSORS, NUM_SENSORS, NUM_SENSORS, 16, sizeof(void *));

int main(void)
{
	int rc;
	uint32_t accel_frame_iter = 0;
	struct sensor_three_axis_data accel_data[2] = {0};
	struct sensor_decoder_api *decoder;
	struct rtio_cqe *cqe;
	uint8_t *buf;
	uint32_t buf_len;
	struct rtio_sqe *handles[2];

	/* Start the streams */
	for (int i = 0; i < NUM_SENSORS; i++) {
		sensor_stream(iodevs[i], &accel_ctx, NULL, &handles[i]);
	}

	while (1) {
		cqe = rtio_cqe_consume_block(&accel_ctx);

		if (cqe->result != 0) {
			printk("async read failed %d\n", cqe->result);
			return;
		}

		rc = rtio_cqe_get_mempool_buffer(&accel_ctx, cqe, &buf, &buf_len);

		if (rc != 0) {
			printk("get mempool buffer failed %d\n", rc);
			return;
		}

		struct device *sensor = ((struct sensor_read_config *)
					 ((struct rtio_iodev *)cqe->userdata)->data)->sensor;

		rtio_cqe_release(&accel_ctx, cqe);

		rc = sensor_get_decoder(sensor, &decoder);

		if (rc != 0) {
			printk("sensor_get_decoder failed %d\n", rc);
			return;
		}

		/* Frame iterator values when data comes from a FIFO */
		uint32_t accel_fit = 0;

		/* Number of accelerometer data frames */
		uint32_t frame_count;

		rc = decoder->get_frame_count(buf, {SENSOR_CHAN_ACCEL_XYZ, 0},
					      &frame_count);
		if (rc != 0) {
			printk("sensor_get_decoder failed %d\n", rc);
			return;
		}

		/* If a tap has occurred lets print it out */
		if (decoder->has_trigger(buf, SENSOR_TRIG_TAP)) {
			printk("Tap! Sensor %s\n", dev->name);
		}

		/* Decode all available accelerometer sample frames */
		for (int i = 0; i < frame_count; i++) {
			decoder->decode(buf, {SENSOR_CHAN_ACCEL_XYZ, 0},
					accel_fit, 1, &accel_data);
			printk("Accel data for %s " PRIsensor_three_axis_data "\n",
			       dev->name,
			       PRIsensor_three_axis_data_arg(accel_data, 0));
		}

		rtio_release_buffer(&accel_ctx, buf, buf_len);
	}
}
```

> 译注：原例的 `SENSOR_TRIG_DRDY` 与所核对头文件不一致，该版本定义的是 `SENSOR_TRIG_DATA_READY`。更严重的是它向 `sensor_stream()` 传入 `NULL` 用户数据，后面却把 `cqe->userdata` 当成设备对象指针解引用；应为请求关联有效对象或采用另外经过验证的来源映射。应先检查启动结果，再等待相应完成事件。

> 译注：前节的 I/O 类型、`const`、未定义的 `dev`、裸花括号实参和 `return;` 问题也出现在这里。当前 `get_frame_count` 要求 `uint16_t *`，原例却提供 `uint32_t *`；`decode` 要求帧迭代器地址 `&accel_fit`，而不是其数值。`accel_data` 原声明为数组，后面的打印和解码写法却按单个结构体使用，须统一对象类型并配置足够空间。数据就绪帧、只有事件而无采样的帧及 FIFO 多帧结果应分别处理；每帧读取结果和解码返回值都要检查，并保证正确释放缓冲区。

本页完整保留三段原代码与原有版权署名，用于理解原文数据流。译注指出的修改仅是接口对照，未声称完成了这些片段的构建或实际传感器验证。
