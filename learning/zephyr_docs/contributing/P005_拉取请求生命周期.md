# 第5章\_拉取请求生命周期

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/pr_lifecycle_policy.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

本策略让开放的拉取请求（Pull Request，PR）集中在持续推进、并有现实合入途径的贡献上。

<a id="goals"></a>

## 5.1\_目标（Goals）

- 使贡献者和维护者能够有效管理开放的 PR。
- 优先把审查精力投入正在推进的修改。
- 明确草稿 PR 和无活动 PR 的预期。

<a id="scope"></a>

## 5.2\_适用范围（Scope）

适用于仓库中的全部 PR，包括草稿 PR。

<a id="definitions"></a>

## 5.3\_定义（Definitions）

| 术语 | 含义 |
| --- | --- |
| 活跃PR（Active Pull Request） | 有实质进展，例如新增提交、回应审查或更新以解决修改要求。 |
| 草稿PR（Draft Pull Request） | 为进行中的工作和早期反馈而创建。 |
| 停滞PR（Stalled Pull Request） | 在规定的无活动时间窗口内没有实质活动。 |
| 已关闭的无活动PR（Closed Inactive Pull Request） | 因无活动、已被替代或没有明确合入途径而关闭。 |

<a id="draft-pull-request-expectations"></a>

## 5.4\_草稿PR的要求（Draft Pull Request Expectations）

- 清楚描述问题、当前状态和已知缺口。
- 应在 **30 天**内转为可审查（ready-for-review）。
- 草稿连续 **30 天**无活动时，可以标为过时（stale）并发布提醒。
- 标记后再过 **7 天**仍没有实质进展，可以关闭。

<a id="ready-for-review-pull-request-expectations"></a>

## 5.5\_可审查PR的要求（Ready-for-Review Pull Request Expectations）

- 作者应在 **21 天**内回应审查反馈。
- 连续 **30 天**没有实质活动，可以标为 stale。
- stale 提醒后 **7 天**内没有实质更新，可以关闭。
- 阻塞性反馈超过 **45 天**仍未解决，且没有具体处理计划时，可以关闭。

<a id="what-counts-as-meaningful-activity"></a>

## 5.6\_什么算实质活动（What Counts as Meaningful Activity）

包括解决审查反馈的新提交、具体技术回应与跟进更新，以及对 PR 内容产生实质影响的重要修订。

通常不包括没有技术更新的单纯催促评论，或不涉及实质修改的简单变基（rebase）。

<a id="exceptions"></a>

## 5.7\_例外（Exceptions）

安全关键修复、阻塞发布的问题，以及明确等待外部依赖并链接了跟踪事项的 PR，可以不受自动关闭无活动 PR 的规则约束。即使获得豁免，仍需至少每 **30 天**更新一次状态。

<a id="superseded-pull-requests"></a>

## 5.8\_被替代的PR（Superseded Pull Requests）

工作被其他 PR 替代时，关闭旧 PR 并注明已被替代；链接替代 PR；添加简短总结评论以保留上下文。

<a id="reopening-closed-inactive-pull-requests"></a>

## 5.9\_重新打开已关闭的无活动PR（Reopening Closed Inactive Pull Requests）

因无活动而关闭是保持开放列表可管理的行政处理，并不表示拒绝这项贡献。

作者发布更新后的计划、先前的阻塞性反馈得到解决、维护者确认能够继续审查后，可以重新打开。项目鼓励贡献者在能够提供实质更新时随时重新打开 PR。

<a id="responsibilities"></a>

## 5.10\_职责（Responsibilities）

贡献者应保持 PR 描述最新、及时回应审查、在草稿具备可审查条件时转为可审查状态，并参阅[贡献者职责](P003_贡献者职责.md#contributor-expectations)获得更多指导。

维护者应一致地应用 stale 和关闭决策，提供清楚的阻塞性反馈，在关闭时明确理由及重新打开的途径，并参阅[维护者职责](https://docs.zephyrproject.org/latest/project/project_roles.html#maintainer)。
