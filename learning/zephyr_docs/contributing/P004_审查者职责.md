# 第4章\_审查者职责

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/reviewer_expectations.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 4.1\_审查者职责（Reviewer Expectations）

评论拉取请求（Pull Request，PR）时应尊重他人，详情见 Zephyr [行为准则（Code of Conduct）](https://github.com/zephyrproject-rtos/zephyr/blob/main/CODE_OF_CONDUCT.md)。

项目理解审查者和维护者精力有限。审查请求应按以下次序处理：

1. 与 [Zephyr 发布计划](https://github.com/orgs/zephyrproject-rtos/projects/13)有关的 PR，或在稳定阶段（首个候选发布版 RC1 之后）面向下一次发布的 PR。
2. 审查者自己提出了阻塞性修改要求的 PR。
3. 分配给自己、由自己担任领域维护者的 PR。
4. 其他 PR。

审查者应通过反馈以及与作者互动，努力使 PR 达到可合并状态。尽量一次给出整个 PR 的反馈，让贡献者能在下一次更新中一起处理全部意见。

允许部分审查，但必须评论说明已经审查的范围。有用的部分审查包括：特定领域，例如设备树（Devicetree）；影响 PR 可读性的代码风格；以及某个提交的修改要求会影响后续提交时，分别审查各提交。

不要通过要求新功能扩大 PR 范围，尤其是 PR 已有相应征求意见稿（Request for Comments，RFC）时。应把建议评论到 [RFC](P007_提案与征求意见稿.md#rfcs) 中；最小实现合入以后，多位贡献者更容易共同开发功能，这也能促进协作。

使用 “Request Changes”（请求修改）时，应把琐碎且不影响功能的要求标为 “Non-blocking”（不阻塞）。只剩不阻塞的修改时，应批准 PR。作者可决定是否处理全部不阻塞意见，但应以某种方式回应每一条评论，即使只是表情符号。

对于项目尚未写入文档、只是审查者个人不赞同的风格，可以提出不阻塞建议，但不能作为请求修改的理由。审查者可以先修正源码树中的潜在不一致，记录新规则或准则，再在审查中执行。

要求修改风格时，审查者应能指出项目文档中的对应准则、规则或理由。某些与具体改动密切相关的要求不受此限制，例如选择某种数据结构或锁原语（locking primitive）。

使用 “Request Changes” 时，必须清楚说明要求修改什么；要求应处于当前 PR 范围内，并符合项目贡献和风格规则。还必须能指出 PR 中触发该请求的具体问题。

不要为持续集成（Continuous Integration，CI）已经会自动捕获的问题再提出阻塞性修改请求，否则即使 CI 故障已经修复，PR 仍可能保持阻塞，无谓延迟合并。

审查者不得仅因技术或结构上的分歧关闭 PR。如果审查中无法解决修改要求，应使用 [PR 技术争议升级流程](P003_贡献者职责.md#pr-technical-escalation)寻找处理办法，其结果可能包括关闭 PR。

使用人工智能（Artificial Intelligence，AI）工具辅助审查代码或起草回复时：

- 审查者有责任跟进所用 AI 工具生成的评论，例如 GitHub Copilot。
- 不得把未经核实的大语言模型（Large Language Model，LLM）原始输出直接粘贴为 PR 评论。
- 所有 AI 反馈均须由人类审查者检查、验证并结合具体上下文处理；这位审查者对评论或审查意见的准确性和语气承担全部责任。
