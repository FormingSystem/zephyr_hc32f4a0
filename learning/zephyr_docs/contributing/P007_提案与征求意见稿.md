# 第7章\_提案与征求意见稿

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/proposals_and_rfcs.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

## 7.1\_提案与征求意见稿（Proposals and RFCs）

许多变更，包括缺陷修复和文档改进，可通过常规 GitHub 拉取请求（Pull Request，PR）工作流实现和审查。但另一些属于重大变更（substantial changes），需要先经过设计过程，在项目相关方之间形成共识。

征求意见稿（Request for Comments，RFC）流程为新功能进入项目提供一致、可控的路径。准备大幅修改 Zephyr 或其文档的贡献者和相关方，应考虑使用此流程。例如：

- 新增功能，扩展应用程序编程接口（Application Programming Interface，API）范围，并且引入时需要功能开关（feature flag）。
- 修改现有稳定 API。
- 删除已经随 Zephyr 发布的功能。
- 引入新的惯用方式或约定，即使不修改 Zephyr 自身代码。

RFC 让更多人在提案成为 Zephyr 一部分之前参与审视。即使看似显然的方案，在更广泛的相关人员提出意见后，也常能明显改进。它还能在功能设计阶段推动讨论，趁方案尚易改变、完整实现尚未完成，把重要约束纳入设计。

对于重大功能（Major Feature），先建立问题单并概述提案，以便讨论、协调工作、避免重复投入，也帮助贡献者把修改组织成项目能接受的形式。提供以下信息可提高问题单被及时处理的机会：

1. 提案概览（Overview of the Proposal）。
2. 动机或使用场景（Motivation or Use Case）。
3. 设计细节（Design Details）。
4. 替代方案（Alternatives）。
5. 测试策略（Test Strategy）。

某些变更不需要 RFC，但其理由和详细内容仍应写进 PR，例如：对成熟子系统的小型增强和修改；措辞调整、重新组织或重构；增加或删除警告；向现有子系统增加开发板、片上系统（System on Chip，SoC）或驱动等。

具体流程是创建带 [RFC 标签](https://docs.zephyrproject.org/latest/project/dev_env_and_tools.html#gh-labels)的 GitHub 问题单，充分记录提案。鼓励使用 [RFC 表单](https://github.com/zephyrproject-rtos/zephyr/issues/new?template=003_rfc-proposal.yml)，使提案采用项目参与者熟悉的模板。

与 PR 一样，如果存在分歧或意见数量不足以继续推进，RFC 可能需要在某次 [Zephyr 会议](https://github.com/zephyrproject-rtos/zephyr/wiki/Zephyr-Committee-and-Working-Groups)中讨论。应添加合适的标签，或纳入相应 GitHub 项目，以便下一次会议审议。
