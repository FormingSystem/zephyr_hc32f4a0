# 第8章\_二进制文件

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/bin_blobs.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

对于支持多种架构和集成电路（Integrated Circuit，IC）系列的操作系统，有些功能离不开以二进制形式分发的可执行代码。二进制专有文件（Binary Blob，简称 blob）是包含专有机器代码或二进制数据的文件，例如没有以开放源代码促进会（Open Source Initiative，OSI）认可的许可发布对应源码的文件。

Zephyr 内置机制支持下载和使用第三方 blob，但有下文所述的重要条件。本页全部信息仅适用于[上游原版 Zephyr（upstream / vanilla Zephyr）](https://github.com/zephyrproject-rtos/zephyr)。

Zephyr 分支或第三方发行版支持 blob 时没有这类限制，可能的许可兼容性问题除外。构建系统支持与 blob 有关的各种用途，包括链接库、向目标烧录镜像等。因此，无法满足本页要求时，用户仍可创建使用 blob 的 Zephyr 下游软件。

<a id="software-license"></a>

## 8.1\_软件许可（Software License）

大多数 blob 按专有许可分发，条款性质和条件可能差异很大。厂商须在提交 blob 时指定许可；下载和安装时，厂商可要求用户经过点击接受或其他类似最终用户许可协议（End-User License Agreement，EULA）的流程。

<a id="hosting"></a>

## 8.2\_托管（Hosting）

blob 必须由第三方基础设施在互联网上托管和管理，例如硬件厂商管理的 Git 仓库或 Web 服务器。Zephyr 项目不在自身 Git 仓库或其他位置托管 blob。

<a id="fetching-blobs"></a>

## 8.3\_获取二进制文件（Fetching Blobs）

使用 [`west blobs`](../west/P008_其他Zephyr扩展命令.md#west-blobs) 从官方第三方来源获取。blob 必须在各厂商维护的独立 Zephyr [模块仓库](../modules/P001_模块与外部项目.md#modules)中的 [`module.yml`](../modules/P001_模块与外部项目.md#modules-bin-blobs) 声明。因此，要把 blob 的引用加入上游 Zephyr 发行版，必须已有相应模块仓库，或在提交流程中创建它。

每个可下载的 blob 都必须在对应 [`module.yml`](../modules/P001_模块与外部项目.md#modules-bin-blobs) 中单独标识，声明包含：

- blob 的概括性描述。
- 版本信息。
- 厂商提供的文档引用。
- blob 的[类型](#bin-blobs-types)，必须属于允许的类型。
- 校验和，[`west blobs`](../west/P008_其他Zephyr扩展命令.md#west-blobs) 下载后会检查；这样可以复现结果，并在 blob 变化时用 Git 和 west 二分定位问题。
- 适用于 blob 的许可文本，或采用软件包数据交换（Software Package Data Exchange，SPDX）格式的许可文本引用。

字段的正式定义见[模块文档对应小节](../modules/P001_模块与外部项目.md#modules-bin-blobs)。[`west blobs`](../west/P008_其他Zephyr扩展命令.md#west-blobs) 可列出可用 blob 的元数据，也可获取用户所选模块的 blob。它只下载并保存二进制文件本身；配套代码，包括接口头文件，必须已在相应模块仓库中。

<a id="tainting"></a>

## 8.4\_污点标记（Tainting）

包含 blob 会给 Zephyr 构建加上污点标记（taint）。这一概念源自 [Linux 内核](https://www.kernel.org/doc/html/latest/admin-guide/tainted-kernels.html)；在 Zephyr 中，带标记的镜像表示它包含 blob。

以下方式会告知用户：

1. 一个或多个 `TAINT_BLOBS_*` Kconfig 选项设为 `y`。
2. 构建系统在配置阶段发出警告，可通过 Kconfig 关闭该警告。
3. `west spdx` 的输出包含污点状态。
4. 内核默认致命错误处理程序明确打印污点状态。
5. 启动横幅（boot banner）打印污点状态。

<a id="allowed-types"></a>
<a id="bin-blobs-types"></a>

## 8.5\_允许的类型（Allowed Types）

Zephyr 接受以下类型：

- **预编译库（Precompiled Libraries）**：以预编译形式分发的硬件支持库，通常针对片上系统（System on Chip，SoC）外设，例如无线外设支持库。
- **固件镜像（Firmware Images）**：次级处理器或中央处理器（Central Processing Unit，CPU）的可执行代码镜像，可以完整或部分提供；部分通常是差分或补丁数据，一般由主 CPU 复制到随机存取存储器（Random Access Memory，RAM）或 Flash。例如运行低功耗蓝牙（Bluetooth Low Energy，Bluetooth LE）控制器的核心固件。
- **其他二进制数据文件**：例如预训练神经网络模型数据。

不接受通过专有库提供与硬件无关的功能。例如，与硬件无关、按静态归档分发的专有 TCP/IP 协议栈会被拒绝。

类型符合要求并不意味着无条件接纳，仍可根据其他原因逐项拒绝，见下文预编译库专用要求。有分歧时，由技术指导委员会（Technical Steering Committee，TSC）裁定某个 blob 是否属于上述类型。

<a id="precompiled-library-specific-requirements"></a>

## 8.6\_预编译库专用要求（Precompiled Library-Specific Requirements）

以下要求专用于预编译库。提交者必须声明所提交的库符合要求；以后发现不符合时，项目可以从上游发行版移除相应 blob。

<a id="interface-header-files"></a>

### 8.6.1\_接口头文件（Interface Header Files）

库必须附带一个或多个定义接口的头文件，按 OSI 认可、非著佐权（non-copyleft）的许可分发。

<a id="allowed-dependencies"></a>

### 8.6.2\_允许的依赖（Allowed Dependencies）

本节约束库要求构建系统提供的外部符号（external symbols）。

- blob 不得直接依赖 Zephyr API。换言之，在完全没有 Zephyr 源码时，也必须能够构建该二进制文件。这样可保持松耦合和可维护性，因为 API 可能变化，而并非所有项目维护者都能修改 blob。
- 如果库需要 Zephyr 或一般实时操作系统（Real-Time Operating System，RTOS）提供的能力，可随库提供操作系统抽象层（OS Abstraction Layer），也称移植层（porting layer）。该层实现必须提供源码，按 OSI 认可的许可发布，并使用 Doxygen 编写文档。

<a id="toolchain-requirements"></a>

### 8.6.3\_工具链要求（Toolchain Requirements）

数据格式必须与 Zephyr 支持的某种工具链兼容，并能被该工具链链接，以保证可维护性和可用性。使用时允许需要专门的编译器或链接器选项，例如移植层所需选项，或静态归档要求的特定链接选项。

<a id="limited-scope"></a>

### 8.6.4\_范围限制（Limited Scope）

任意允许库 blob 可能削弱上游发行版的开源程度。极端例子是内核时钟驱动仅为 blob 的移植层，此时目标连启动都无法只依靠开源软件完成。

为降低风险，上游库 blob 的范围受到限制。项目维护者定义了一套开源测试，上游目标必须仅使用主线发行版及其模块中的开源软件通过。目前包含 `samples/philosophers` 和 `tests/kernel`。

测试范围可随时间扩大，目的是为所有获得上游支持的目标规定必须以开源软件支持的最小功能集合。发布团队可酌情移除无法通过这套测试的硬件目标支持。

<a id="support-and-maintenance"></a>

## 8.7\_支持与维护（Support and Maintenance）

项目不承担所贡献 blob 的维护与支持。因此，发布团队可逐案决定：需要 blob 才能复现、在 Zephyr GitHub 跟踪器报告的问题，可以不按缺陷处理，也可以按不属于 Zephyr 项目范围关闭。

这不表示未经调查就关闭。例如，问题可能暴露 Zephyr 代码路径中的缺陷，而缺少 blob 时很难或无法触发；维护者可以接纳并尝试解决。但维护者可能无法区分问题来自 Zephyr 还是 blob，也可能因没有硬件而无法复现，因此需要保留处理弹性。

blob 必须有指定维护者，及时回应用户问题并提供修复更新。为控制代码失养（bit-rot）、安全问题等风险，发布团队可因维护者响应或支持不足，随时从 `zephyr/west.yml` 移除引用 blob 的模块修订。提出集成 blob 的人必须承诺，在可预见的未来持续维护其集成。

项目用于构建、可选执行测试和示例以防止回归的持续集成（Continuous Integration，CI）基础设施 **不会下载 blob**。这同时适用于新 GitHub PR 触发的 CI 和其他定期执行的 CI。

<a id="submission-and-review-process"></a>
<a id="blobs-process"></a>

## 8.8\_提交与审查流程（Submission and Review Process）

通过标准 PR 工作流提交 blob 引用，不需要 TSC 批准。维护者和审查者负责确认提交满足[本页](#bin-blobs)规定的条件。

初次集成的 PR 必须说明 blob 及其提供的功能，并提供：

1. blob 来源。
2. 类型，例如预编译库或固件镜像。
3. 哪个 Zephyr 模块将引用它。
4. 功能的简短描述。
5. 是否依赖其他组件，若有则列出。
6. 分发采用的许可。

获得适当批准后即可集成；技术分歧使用标准 [PR 争议升级流程](P003_贡献者职责.md#pr-technical-escalation)处理。后续更新按[模块更新流程](../modules/P001_模块与外部项目.md#modules-changes)进行。
