# 第3章\_贡献者职责

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/contributor_expectations.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

Zephyr 鼓励[贡献者（Contributors）](https://docs.zephyrproject.org/latest/project/project_roles.html#contributor)把修改拆成较小的拉取请求（Pull Request，PR）。这样做有以下好处：

- 更快且更充分地得到审查。审查者多次抽出几分钟处理小修改，比一次留出大块时间审查大型 PR 更容易。
- 审查者或维护者不接受修改方向时，已经投入但最终无用的工作更少。
- 更容易变基（rebase）和合并（merge），因为小 PR 与源码树中其他改动发生冲突的概率更低。
- PR 破坏功能时，更容易撤销（revert）。

> 原文说明：本页不适用于草稿拉取请求（draft PR）。为测试或预览，草稿可以有任意大小、任意提交数量，也可以组合多个较小的 PR。草稿没有必须得到审查的预期；创建时就是草稿的 PR 默认不会通知任何人。

<a id="defining-smaller-prs"></a>

> 译注：这里说明草稿不受本页的小型 PR 和待审查质量要求约束；[PR 生命周期策略](P005_拉取请求生命周期.md)仍明确适用于草稿，不能据此认为草稿不受无活动处理规则约束。

## 3.1\_怎样定义较小的PR（Defining Smaller PRs）

- 一个较小的 PR 应包含一个自包含的逻辑修改。
- 增加大型新功能或应用程序编程接口（Application Programming Interface，API）时，一个 PR 只处理其中一部分；同时创建 [RFC 提案](P007_提案与征求意见稿.md#rfcs)，向审查者说明其他部分。
- 增加功能、修改功能尤其是改变 API 行为契约、或修复与硬件无关的缺陷时，PR 应包含测试或示例。缺陷测试应在未修复时失败、应用修复后通过。
- 功能代码变更影响到的文档必须同步更新。
- 引入新 API 时必须给出用法示例，为审查提供上下文，并避免提交无人使用的 API。

<a id="multiple-commits-on-a-single-pr"></a>

## 3.2\_一个PR中的多个提交（Multiple Commits on a Single PR）

项目还鼓励贡献者把 PR 拆成多个提交，但其中每个提交仍必须能够正常构建，并通过全部持续集成（Continuous Integration，CI）测试。

例如，扩展 API 时可以按以下具体修改拆分：

1. 引入新 API，包括共用的设备树绑定（Devicetree Bindings）。
2. 更新驱动 X，包括驱动专用设备树绑定。
3. 更新驱动 Y。
4. 增加新 API 的测试。
5. 增加使用该 API 的示例。
6. 更新文档。

<a id="large-changes"></a>

## 3.3\_大型变更（Large Changes）

大型变更必须提交 [RFC 提案](P007_提案与征求意见稿.md#rfcs)，描述完整范围及后续工作。RFC 为审查者提供必要上下文，使较小、渐进的 PR 能够逐步审查和合入；还应定义最小可用实现（minimum viable implementation）。

以下变更需要 RFC：新功能、新 API、[全源码树变更（Treewide Changes）](P002_贡献指南.md#treewide-changes)，以及其他适合通过 RFC 流程讨论的大型变更。维护者可以要求过大或过于复杂的 PR 先建立 RFC。

<a id="pr-requirements"></a>
<a id="id2"></a>

## 3.4\_PR要求（PR Requirements）

> 原文重点：达不到下列质量要求的 PR 较难获得审查者投入；审查者可以直接要求修改而不提供详细反馈。贡献者应在请求审查前自行检查修改，确保满足全部要求。

每个提交必须遵循[提交说明指南](P002_贡献指南.md#commit-guidelines)；不得包含修补提交（fixup commit）或合并提交（merge commit），详见[贡献工作流](P002_贡献指南.md#contribution-workflow)。PR 描述须说明变更内容及理由。全部文件必须满足[许可要求](P002_贡献指南.md#licensing-requirements)，代码须遵循[编码风格指南](../coding_style/P001_代码风格指南.md#coding-style)和[编码准则](P009_编码准则.md#coding-guidelines)。

PR 必须按[拉取请求合并准则](https://docs.zephyrproject.org/latest/project/release_process.html#merge-criteria)通过全部 CI 检查。若想在 CI 尚未通过时获得早期反馈，可以把 PR 标成草稿，并明确请求审查者反馈。

PR 中的提交应是清晰、便于审查的逻辑修改单元，并保持可二分定位性（bisectability）：

1. **独立而有意义的修改单元。** 增加功能、修复缺陷和重构应分别提交，避免把功能实现与无关重构混在一起。
2. **保持可二分定位性。** 每个提交都要构建成功并通过相关测试，使 `git bisect` 能有效定位引入问题的具体提交。
3. **压合开发中间过程。** 部分实现、临时文件、调试代码等中间修改，应在提交 PR 前压合（squash）或重写；去掉之后又改名的临时文件重命名，以及后续已经重写或大幅修改的代码等非最终产物。
4. **提交前整理历史。** 使用交互式变基 `git rebase -i`，把零碎、不完整的提交合为连贯单元；保持每个提交可二分定位，并在提高清晰度时正确保留作者署名。
5. **重命名和代码重写。** 开发后期发生重命名或重写时，压合或重写前面的提交，使其反映最终结构；避免冗余改名和部分重写，保持历史清楚且可二分定位。
6. **准确署名。** 整理历史时必须保证作者归属准确。
7. **可读、可审查的历史。** 最终历史应让未来维护者容易理解；各逻辑单元组成清晰、连贯的工作说明。

增加重要的新功能时，必须向自动测试套件加入测试。所有 API 函数都应有测试用例，也应测试 API 的行为契约；维护者和审查者可判断测试是否充分。以下是有效测试 API 的实践示例：

- [内核定时器测试](https://github.com/zephyrproject-rtos/zephyr/blob/main/tests/kernel/timer/timer_behavior)按代码行计算，为[内核定时器](https://github.com/zephyrproject-rtos/zephyr/blob/main/kernel/timer.c)提供约 85% 的覆盖率。
- 片外外设仿真器（emulator）可有效测试驱动 API。[电量计测试](https://github.com/zephyrproject-rtos/zephyr/blob/main/tests/drivers/fuel_gauge/sbs_gauge)使用[智能电池仿真器](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/fuel_gauge/sbs_gauge/emul_sbs_gauge.c)，覆盖[电量计 API](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/drivers/fuel_gauge.h)与[智能电池驱动](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/fuel_gauge/sbs_gauge/sbs_gauge.c)。
- Zephyr 的覆盖率报告可在 [Codecov](https://app.codecov.io/gh/zephyrproject-rtos/zephyr) 查看。

不兼容的 API 变更必须更新下一版本的发布说明，详细描述改动；标为实验性（experimental）的 API 不受此要求约束。API 发生变更还必须按版本规则增加 API 版本号。

新增或更新文档，使其反映 PR 引入的代码变化。文档须沿用现有页面的术语，并使用美式英语；图片须符合[图片规则](P010_文档编写指南.md#doc-images)，更多要求见[文档编写指南](P010_文档编写指南.md#doc-guidelines)。发布工程团队成员把 PR 合入 Zephyr 源码树之前，PR 还须满足全部[合并准则](https://docs.zephyrproject.org/latest/project/release_process.html#merge-criteria)。维护者可以要求拆成更小的 PR，并建立 RFC。

<a id="workflow-suggestions-that-help-reviewers"></a>

### 3.4.1\_有助于审查的工作流建议（Workflow Suggestions That Help Reviewers）

- 除非完全照审查者建议修改，否则作者不得自行解决并隐藏评论，应交由最初的审查者处理。Zephyr 不要求合并前解决全部评论；保留某些已讨论完的对话，有时有助于理解整体背景。
- 在 “Files changed”（文件变更）视图中使用绿色的 “Start Review”（开始审查）和 “Add Review”（添加审查）按钮回应；这样能把多条回复一起发布，减少给审查者发送的邮件。
- GitHub 没有实现 [git range-diff](https://git-scm.com/docs/git-range-diff)，因此尽量减少审查过程中的变基。如果必须变基，将其单独作为一次更新推送，不夹带上次推送后的其他修改；同时在 PR 中评论说明哪个提交是变基的结果。

<a id="getting-prs-reviewed"></a>

### 3.4.2\_推动PR获得审查（Getting PRs Reviewed）

Zephyr 社区成员的投入程度与优先事项各不相同，审查者和维护者可能无法立即处理 PR。

- 1 周没有活动后，在 PR 中评论提醒负责人（Assignee）或审查者。
- 2 周没有活动后，在 Discord 的 [#pr-help](https://discord.com/channels/720317445772017664/997527108844798012) 频道发消息并附 PR 链接。

<a id="pr-technical-escalation"></a>
<a id="id3"></a>

### 3.4.3\_PR技术争议升级（PR Technical Escalation）

贡献者不同意审查者的修改要求时，按以下流程解决技术分歧。升级前，先在 PR 中由负责人、维护者和审查者讨论；适用时，由负责人主持协调。

如果仍无进展，负责人（维护者）可撤销过时、无关或不切题的修改请求，但必须给审查者至少 **1 个工作日**，以便回应、重新考虑原请求或启动升级流程。负责人必须在 PR 中记录撤销审查的理由，并通知审查者。为留出回应和升级时间，负责人应通过暂不批准 PR 或设置 `DNM`（Do Not Merge，不合并）标签阻止合入。

审查过程的任何一方——负责人、审查者或原作者——都可启动升级：

1. 在 PR 上添加 `Architecture Review`（架构审查）标签，提交给[架构工作组（Architecture Working Group）](https://github.com/zephyrproject-rtos/zephyr/wiki/Architecture-Working-Group)。除每周处理此类问题的会议外，应请求时工作组也应安排线下异步审查，尤其是有人无法参加会议时。
2. 所有解决与升级途径都失败后，负责人可添加 `TSC` 标签，提交技术指导委员会（Technical Steering Committee，TSC）作出有约束力的决定。
3. 负责人应确保升级事项得到解决，并把结论记录在相关 GitHub PR 或问题单中。
