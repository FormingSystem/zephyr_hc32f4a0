# 第2章\_贡献指南

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/guidelines.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

作为开源项目，Zephyr 欢迎并鼓励社区直接提交补丁。在协作式开源环境中，采用统一的修改提交标准与方法，有助于减少活跃开发社区可能产生的混乱。

本页介绍怎样参与讨论、报告缺陷和增强需求，以及向项目提交补丁，使其更快被代码库接纳。

<a id="prerequisites"></a>

## 2.1\_前置条件（Prerequisites）

贡献者应熟悉 [Zephyr 项目网站](https://zephyrproject.org)介绍的配置、安装与使用方法，并按[入门指南（Getting Started Guide）](../getting_started/P002_入门指南.md#getting-started)准备开发环境。还应熟悉 Git、CMake 等常用开发工具，以及 GitHub 等平台。

如果尚未准备好，需要在 [GitHub](https://github.com) 创建免费账户，并在开发系统中安装 Git 工具。

> 原文说明：Zephyr 工作流支持 Linux、macOS 和 Windows 三大系统，但下文有些工具只能在 Linux 和 macOS 上使用。Windows 用户需要依靠提交拉取请求（Pull Request，PR）时自动运行的 GitHub Actions 持续集成（Continuous Integration，CI）服务执行这些工具。失败结果可在 PR 对话列表底部附近的工作流详情链接中查看，详见[持续集成](#continuous-integration)。

<a id="licensing-requirements"></a>

## 2.2\_许可（Licensing）

许可对开源项目非常重要，有助于保证软件继续按作者希望的条款提供。

Zephyr 采用 [Apache 2.0 许可证](https://github.com/zephyrproject-rtos/zephyr/blob/main/LICENSE)，全文位于[项目 GitHub 仓库](https://github.com/zephyrproject-rtos/zephyr)的 `LICENSE` 文件中，以兼顾开放贡献和用户使用软件的自由。Apache 2.0 是宽松式开源许可（permissive open-source license），允许使用、修改、分发和销售包含此许可软件的产品。更多说明可参阅 [为什么选择 Apache 2.0](https://www.zephyrproject.org/faqs/#1571346989065-9216c551-f523)和 [Apache 许可十大问题解答](https://www.whitesourcesoftware.com/whitesource-blog/top-10-apache-license-questions-answered/)。

许可说明版权持有人授予开发者哪些权利。贡献者必须充分理解并同意许可权利；版权持有人有时并非贡献者本人，例如贡献者代表公司完成工作时。

<a id="components-using-other-licenses"></a>

### 2.2.1\_采用其他许可的组件（Components Using Other Licenses）

Zephyr 导入或复用的某些组件采用其他许可，见[Zephyr 项目组件许可](https://docs.zephyrproject.org/latest/LICENSING.html#zephyr-licensing)。从其他项目向 Zephyr 操作系统导入非 Apache 2.0 许可的代码，必须充分理解具体情况并获得 Zephyr 管理委员会批准。

通过仔细审查潜在贡献，并对代码贡献执行[开发者来源证明（Developer Certificate of Origin，DCO）](#dco)流程，项目努力保证社区开发产品时不受专利或版权问题困扰。外部组件的贡献和审查流程详见[贡献外部组件](P012_外部组件贡献.md#external-contributions)。

<a id="copyright-and-license-notices"></a>
<a id="copyrights"></a>

### 2.2.2\_版权和许可声明（Copyright and License Notices）

Zephyr 采用 SPDX/REUSE 风格的文件头。应在每个文件顶部添加机器可读的版权声明和许可标识，使工具能够识别，例如使用 [REUSE 工具](https://github.com/fsfe/reuse-tool)的 [west spdx](../west/P008_其他Zephyr扩展命令.md#west-spdx)。SPDX 指软件包数据交换（Software Package Data Exchange）。

项目遵循 Linux 基金会版权声明的[社区最佳实践](https://www.linuxfoundation.org/blog/copyright-notices-in-open-source-software-projects/)，因此建议采用以下版权声明：

```text
SPDX-FileCopyrightText: Copyright The Zephyr Project Contributors
```

同时附上许可标识：

```text
SPDX-License-Identifier: Apache-2.0
```

使用文件自身的注释语法，把这两行放在文件最顶部。如果创作了实质性的原创内容，可以再为自己或所属组织增加一行声明。

<a id="developer-certification-of-origin-dco"></a>
<a id="dco"></a>

## 2.3\_开发者来源证明（Developer Certification of Origin，DCO）

为善意地确保许可条件得到满足，Zephyr 要求遵循 DCO 流程。每位开发者的每项贡献都附带这一证明；开发者在提交说明中加入 `Signed-off-by` 声明，即表示同意 DCO。

提交补丁意味着贡献者承诺有权按相关许可提交。以下保留原协议，也可在 [DCO 官方网站](https://developercertificate.org/)查看：

```text
Developer's Certificate of Origin 1.1

By making a contribution to this project, I certify that:

(a) The contribution was created in whole or in part by me and I
    have the right to submit it under the open source license
    indicated in the file; or

(b) The contribution is based upon previous work that, to the
    best of my knowledge, is covered under an appropriate open
    source license and I have the right under that license to
    submit that work with modifications, whether created in whole
    or in part by me, under the same open source license (unless
    I am permitted to submit under a different license), as
    Indicated in the file; or

(c) The contribution was provided directly to me by some other
    person who certified (a), (b) or (c) and I have not modified
    it.

(d) I understand and agree that this project and the contribution
    are public and that a record of the contribution (including
    all personal information I submit with it, including my
    sign-off) is maintained indefinitely and may be redistributed
    consistent with this project or the open source license(s)
    involved.
```

**协议译文——开发者来源证明1.1：** 向本项目作出贡献时，我证明：

- **(a)** 该贡献全部或部分由我创作，我有权按文件指明的开源许可提交；或者
- **(b)** 该贡献基于既有工作，据我所知，该工作采用适当的开源许可；我有权按该许可，将这项工作及其修改——无论修改全部还是部分由我完成——按文件所指明的相同开源许可提交，除非我获准使用不同许可；或者
- **(c)** 该贡献由其他人直接交给我，此人已证明符合 (a)、(b) 或 (c)，而我没有修改它。
- **(d)** 我理解并同意：本项目和贡献是公开的；贡献记录，包括我随贡献提交的全部个人信息和签署，将无限期保留，并可依照本项目或所涉及的开源许可再次分发。

<a id="dco-sign-off"></a>

### 2.3.1\_DCO签署（DCO Sign-Off）

DCO 的签署（sign-off）就是每个提交日志中的 `Signed-off-by:` 行，格式为：

```text
Signed-off-by: Your Name <your.email@example.com>
```

将 `Your Name` 替换为法定姓名，不得使用化名、网名或组织名称。将 `your.email@example.com` 替换为实际用于创作提交的邮箱；不允许 `you-id+your-username@users.noreply.github.com` 这类伪造或匿名邮箱。邮箱必须与提交作者邮箱一致，否则 CI 会失败。

使用 `git commit -s` 可自动向正文添加 `Signed-off-by:`。可参考 Zephyr Git 历史中的其他提交；姓名和邮箱配置见 [Git 设置](#git-setup)。如果修改他人创建的既有提交，必须加入自己的签署行，并保留已有签署行。

<a id="id1"></a>

## 2.4\_AI编程助手（AI Coding Assistants）

本节为使用人工智能（Artificial Intelligence，AI）工具和助手向 Zephyr 贡献的人提供指导。

<a id="licensing-and-legal-requirements"></a>

### 2.4.1\_许可与法律要求（Licensing and Legal Requirements）

所有贡献必须满足项目许可要求，并与 Zephyr 的许可兼容，例如 Apache-2.0；详情见[许可要求](#licensing-requirements)。

<a id="signed-off-by-and-developer-certificate-of-origin"></a>

### 2.4.2\_签署与来源证明（Signed-Off-By and Developer Certificate of Origin）

AI 代理不得添加 `Signed-off-by` 标签。只有人类能够依法作出 [DCO](#dco) 证明。人类提交者负责审查全部 AI 生成代码、确保许可合规、添加自己的 `Signed-off-by` 以证明 DCO，并对贡献承担全部责任。

<a id="usage-disclosure-and-attribution"></a>

### 2.4.3\_使用披露与归属（Usage Disclosure and Attribution）

AI 工具参与编写贡献时，适当注明其贡献有助于跟踪 AI 在开发过程中的作用。贡献应包含以下格式的 `Assisted-by:` 标签：

```text
Assisted-by: [Agent Name]:[Model Version] [Tool1] [Tool2]
```

`[Agent Name]` 是工具或框架名称，`[Model Version]` 是具体模型版本，`[Tool1] [Tool2]` 是可选的专用分析工具。不要列入 Git、GCC、make、编辑器等基本开发工具。例如：

```text
Assisted-by: Claude:claude-opus-4.6 coccinelle
```

> 译注：以上是 Zephyr 上游贡献规则的译文和原始格式示例，不改写本仓库既有的提交约定，也不表示本次已经添加签署或创建提交。

## 2.5\_源码树结构（Source Tree Structure）

克隆主仓库的方法见[获取 Zephyr 并安装 Python 依赖](../getting_started/P002_入门指南.md#get-the-code)。主源码树除了内核，还包含技术文档源码、示例、开发板配置和子系统测试，均欢迎开发者贡献与改进。理解源码树有助于定位具体功能的实现。

| 顶层文件 | 用途 |
| --- | --- |
| `CMakeLists.txt` | CMake 构建系统的顶层文件，包含构建 Zephyr 所需的大量逻辑。 |
| `Kconfig` | 顶层配置文件，引用同一目录下的 `Kconfig.zephyr`。详细说明见[Kconfig 手册](../kconfig/P001_配置系统概述.md#kconfig)。 |
| `west.yml` | [west 元工具](../west/P014_west官方总入口.md#west)的清单，列出 west 命令行工具管理的外部仓库。 |

顶层目录如下；它们可再包含本节未展开的一层或多层子目录。

| 目录 | 内容 |
| --- | --- |
| `arch` | 架构相关的内核与片上系统（System on Chip，SoC）代码。x86、ARM 等架构分别拥有子目录，其中又包含架构专用内核源码和私有 API 头文件子目录。 |
| `soc` | SoC 相关代码与配置。 |
| `boards` | 开发板相关代码与配置。 |
| `doc` | Zephyr 技术文档源码及生成[官方文档网站](https://docs.zephyrproject.org)的工具。 |
| `drivers` | 设备驱动。 |
| `dts` | [设备树（Devicetree）](../devicetree/P013_设备树文档入口.md#dt-guide)源码，用于描述不能自动发现的板级硬件细节。 |
| `include` | 公共应用程序编程接口（Application Programming Interface，API）的头文件，`lib` 中定义的接口除外。 |
| `kernel` | 与架构无关的内核代码。 |
| `lib` | 库代码，包括最小标准 C 库。 |
| `misc` | 不属于其他顶层目录的杂项代码。 |
| `samples` | 演示 Zephyr 功能用法的应用。 |
| `scripts` | 构建和测试 Zephyr 应用的程序及其他文件。 |
| `cmake` | 构建 Zephyr 所需的附加构建脚本。 |
| `subsys` | 子系统，包括 USB 设备协议栈、含蓝牙及其他协议栈的网络代码、文件系统，以及蓝牙主机与控制器。 |
| `tests` | 功能测试与基准测试。 |
| `share` | 与架构无关的附加数据，当前包含 Zephyr 的 CMake 包。 |

<a id="pull-requests-and-issues"></a>

## 2.6\_拉取请求和问题单（Pull Requests and Issues）

开始补丁前，先查[项目问题跟踪器](https://github.com/zephyrproject-rtos/zephyr/issues)，了解相关问题已有的报告。在 [开发邮件列表](https://lists.zephyrproject.org/g/devel)或 [Discord 服务器](https://chat.zephyrproject.org)讨论问题和拟议方案，可能遇到相同问题的人或有类似修改、增强想法的人。可以在开发邮件列表介绍想法，与社区讨论。

提交新问题前搜索已有或相关问题始终是好习惯。提交缺陷或功能请求后，分诊团队（triage team）通常会在几个工作日内审查并评论。GitHub 提供全部[开放的 PR](https://github.com/zephyrproject-rtos/zephyr/pulls)以及[问题单](https://github.com/zephyrproject-rtos/zephyr/issues)。

## 2.7\_Git设置（Git Setup）

项目需要知道贡献者的身份和联系方式。在 Git 配置中，将 `user.name` 设为完整姓名，将 `user.email` 设为邮箱。例如姓名为 `Zephyr Developer`、邮箱为 `z.developer@example.com` 时：

```bash
git config --global user.name "Zephyr Developer"
git config --global user.email "z.developer@example.com"
```

> 原文说明：`user.name` 必须是完整姓名，至少包括名和姓，不得使用化名或网名。Git 配置邮箱必须与签署邮箱一致，否则 PR 的 CI 会失败。如果准备在 GitHub 网页编辑提交，个人资料中的 `email address` 和 `name` 也应与 Git 的 `user.email` 和 `user.name` 一致。

> 译注：这里的姓名和邮箱均为官方示例占位内容；`--global` 写入当前用户的 Git 配置，实际贡献时使用自己的身份信息。本页没有执行配置命令。

<a id="pull-request-guidelines"></a>

## 2.8\_拉取请求指南（Pull Request Guidelines）

创建 PR 时遵循以下规则，以符合 Zephyr 标准并便于审查。不确定时，可用搜索过滤器和标签查找仓库中类似修改的现有 PR。

> 原文说明：GitHub 默认代码视图把制表符显示为 4 个字符宽，而 Zephyr 遵循[Linux 内核代码风格](https://kernel.org/doc/html/latest/process/coding-style.html#indentation)，采用 8 个字符宽。在 [GitHub 用户偏好](https://github.com/settings/appearance)中把制表符宽度设为 8 个空格，使显示与其他开发者一致。

<a id="commit-message-guidelines"></a>
<a id="commit-guidelines"></a>

### 2.8.1\_提交说明指南（Commit Message Guidelines）

修改以 Git 提交的形式交付，每个提交必须说明改了什么。可接受的格式为：

```text
[area]: [summary of change]

[Commit message body (must be non-empty)]

Signed-off-by: [Your Full Name] <[your.email@address]>
```

方括号中的内容，例如 `[like this]`，需按实际提交替换。完整示例：

```text
drivers: sensor: abcd1234: fix bus I/O error handling

The abcd1234 sensor driver is failing to check the flags field in
the response packet from the device which signals that an error
occurred. This can lead to reading invalid data from the response
buffer. Fix it by checking the flag and adding an error path.

Signed-off-by: Zephyr Developer <z.developer@example.com>
```

示例译文：标题为“驱动：传感器：abcd1234：修复总线输入输出错误处理”。正文说明驱动没有检查设备响应包中表示错误的标志字段，可能读取响应缓冲区中的无效数据，因此增加标志检查和错误处理路径。作者签署行保留其原始格式。

<a id="area-summary-of-change"></a>

#### (1)\_标题（[area]: [summary of change]）

标题必须只有一行、长度 **小于72个字符**，下一行必须完全空白。

`[area]` 通常标识修改的代码领域；跨多个领域时也可标识更广泛的上下文。示例：

- `doc: ...`：文档。
- `drivers: foo:`：foo 驱动。
- `Bluetooth: Shell:`：蓝牙 Shell。
- `net: ethernet:`：以太网相关网络代码。
- `dts:`：全源码树范围的设备树修改。
- `style:`：代码风格。

不确定时，可用 `git log FILE` 查看所改文件 `FILE` 的历史提交，参考已有标题。

`[summary of change]` 简述完成的修改，例如 `doc: update wiki references to new site` 表示更新指向新站点的 wiki 引用，`drivers: sensor: sensor_shell: fix channel name collision` 表示修复传感器 Shell 的通道名冲突。

<a id="commit-message-body"></a>

#### (2)\_提交说明正文（Commit Message Body）

> 原文警告：正文不得为空。即使改动很小，也必须给出有描述性的正文，否则 PR 的 CI 检查会失败。

正文须具体说明做了什么以及为何需要。只写 `"Fixes stuff"`（修了一些东西）会被拒绝。根据实际情况说明变更行为、所选方案的理由、作出的假设，以及证明有效的方法，例如运行了哪些测试。

每行通常不超过 **75 个字符**，长行用换行拆开；长 URL、邮箱地址等可例外。已接纳的示例见 GitHub [提交历史](https://github.com/zephyrproject-rtos/zephyr/commits/main)。

<a id="signed-off-by"></a>

#### (3)\_签署行（Signed-off-by: …）

> 原文提示：先完成 [Git 设置](#git-setup)，再用 `git commit -s` 按这些信息自动添加 `Signed-off-by:`。

出于开源许可要求，提交必须有以下签署行：

```text
Signed-off-by: [Your Full Name] <[your.email@address]>
```

姓名、邮箱与前例相同时为：

```text
Signed-off-by: Zephyr Developer <z.developer@example.com>
```

签署表示本人已经确认修改符合 [DCO](#dco)，因此须使用法定姓名，不得使用化名或网名。姓名和邮箱必须与 Git 提交的 `Author:` 字段一致。贡献者及审查者要求还见[贡献者职责](P003_贡献者职责.md#contributor-expectations)。

<a id="adding-links"></a>

#### (4)\_添加链接（Adding Links）

修改解决某个 GitHub 问题时，在 PR 描述中使用：

```text
Fixes zephyrproject-rtos/zephyr#[issue number]
```

仅对 Zephyr 项目的 PR，也可使用短形式：

```text
Fixes #[issue number]
```

将 `[issue number]` 换成实际编号，例如：

```text
Fixes zephyrproject-rtos/zephyr#1234
```

这样 PR 合并时会自动关闭该问题。为避免歧义，尤其是跨仓库时，应始终写完整仓库路径 `zephyrproject-rtos/zephyr`。提交说明也可使用相同格式。

链接相关问题、数据手册或技术参考手册等外部资源时，使用 `Link:` 标签：

```text
Link: https://github.com/zephyrproject-rtos/zephyr/issues/<issue number>
```

<a id="continuous-integration-ci"></a>
<a id="continuous-integration"></a>

### 2.8.2\_持续集成（Continuous Integration，CI）

每个 PR 都运行 CI，检查 Git 提交格式、代码风格、Twister 对多架构与多开发板的构建，以及验证文档变更的文档构建。

CI 在 GitHub Actions 上运行，使用[本地 CI 测试](#ci-tests)一节所述的相同工具。合并前必须全部通过，显示绿色的 “All checks have passed”（全部检查通过）。PR 创建时、以及每次增加提交更新时都会运行。

状态在 GitHub PR 页底部、审查状态下方显示，可能是 “All checks have passed” 或 “All checks have failed”（全部检查失败）。失败时点击 “Details”（详情），进入 GitHub Actions 结果汇总页；其中有各个构建的表格，再点失败的非绿色行，查看具体构建或测试。

<a id="running-ci-tests-locally"></a>
<a id="ci-tests"></a>

### 2.8.3\_在本地运行CI测试（Running CI Tests Locally）

<a id="check-compliance-py"></a>
<a id="id3"></a>

#### (1)\_合规检查（check\_compliance.py）

[`scripts/ci/check_compliance.py`](https://github.com/zephyrproject-rtos/zephyr/blob/main/scripts/ci/check_compliance.py) 用于检查代码是否符合 Zephyr 准则和实践，封装了代码检查器（linter）、格式化器（formatter）等多种工具。鼓励在创建 PR 前本地运行：

```bash
./scripts/ci/check_compliance.py -c <commit range>
```

默认并行执行，每个 CPU 一个工作进程。`-p N` 限制为 N 个进程，`-p 1` 顺序执行：

```bash
./scripts/ci/check_compliance.py -p 1 -c <commit range>
```

> 原文说明：Windows 尚未给 `.pl` 扩展名关联应用时，首次不指定解释器而运行 Perl 文件，会询问用什么程序打开。将默认应用设为 Strawberry Perl，默认可执行文件位于 `C:\Strawberry\perl\bin\perl.exe`。

> 译注——源码跟踪：本仓库的 [check_compliance.py](../../../scripts/ci/check_compliance.py) 中可查阅 `KeepSorted` 检查类；具体选项以所用 Zephyr 版本为准，网页 main 与本仓库参照源码不一定相同。

> 译注：上述安装位置是官方给出的 Strawberry Perl 默认路径，实际应选择自己已安装的解释器，不是本仓库的位置要求。命令中的 `<commit range>` 是待检查提交范围的占位符，应在 Zephyr 源码根执行检查。

<a id="keepsorted-check"></a>

##### 1)\_保持排序检查（KeepSorted Check）

KeepSorted 确保指定的代码、配置或文档块保持排序。用独占行的开始与结束标记包围内容，通常放在注释中：

```text
// zephyr-keep-sorted-start
option_a
option_b
option_c
// zephyr-keep-sorted-stop
```

<a id="keepsorted-marker-options"></a>

###### a)\_KeepSorted标记选项（KeepSorted Marker Options）

可在开始标记的同一行追加一个或多个选项：

- `re(regex_pattern)`：正则表达式模式，仅检查匹配的行，其余行忽略。例如检查 YAML 属性排序：

```yaml
# zephyr-keep-sorted-start re(^\s+\- name:)
projects:
  - name: application
    revision: main
  - name: library1
    revision: feature-branch
  - name: library2
    revision: main
# zephyr-keep-sorted-stop
```

- `strip(characters)`：比较前去除指定字符，适用于应忽略的可选前缀或后缀。例如去掉 YAML 字典键的引号：

```yaml
# zephyr-keep-sorted-start strip(":)
ACPI:
  status: odd fixes
"West project: acpica":
  status: odd fixes
# zephyr-keep-sorted-stop
```

其中 `status: odd fixes` 表示“维护状态：零星修复”；此示例关注键名的排序，原始键和值均保留。

- `nofold`：禁止折叠行。默认会把主行之后的缩进行连接在一起再比较；此选项禁用该行为并忽略缩进行。
- `ignorecase`：通过 Python 的 [`str.casefold`](https://docs.python.org/3/library/stdtypes.html#str.casefold) 忽略大小写，使同一块可混合大小写项目；省略时采用 Python 默认字符串排序。

同一标记行可以组合多个选项：

```rst
.. zephyr-keep-sorted-start re(^\* \w) ignorecase
* Shell
  Some important message about the shell.

* STM32
  Updates for this vendor.
.. zephyr-keep-sorted-stop
```

示例中的 `Some important message about the shell.` 意为“关于 Shell 的重要说明”，`Updates for this vendor.` 意为“此厂商的更新”；它们作为条目的缩进正文保留，排序对象是上方星号开头的项目。

<a id="twister"></a>

#### (2)\_测试运行器（twister）

> 原文说明：Twister 仅在 Linux 上得到完整支持；Windows 和 macOS 不能在所有目标设备上执行测试。

如果认为改动可能破坏测试，可以把 PR 作为草稿提交，让项目 CI 自动运行[测试运行器（Test Runner，Twister）](../twister/P001_Twister测试运行器.md#twister-script)。失败时，从 CI 日志查看怎样在本地重跑，例如：

```bash
west twister -p native_sim -s tests/drivers/build_all/sensor/drivers.sensor.generic_test
```

<a id="static-code-analysis"></a>
<a id="static-analysis"></a>

## 2.9\_静态代码分析（Static Code Analysis）

[Coverity Scan](https://scan.coverity.com/projects/zephyr) 是面向开源项目的免费静态分析服务，基于 Coverity 商业产品，可分析 C、C++ 和 Java。

静态分析不运行代码，而用抽象解释（abstract interpretation）了解控制流和数据流，跟踪程序可能经过的路径。例如，它知道 `malloc()` 分配的内存稍后应由 `free()` 释放，会沿分支和函数调用检查各种组合是否都释放内存。它可发现内存或文件描述符泄漏、空指针解引用、释放后使用（use after free）、未检查的返回值、死代码、缓冲区溢出、整数溢出、未初始化变量等问题。

结果在 Coverity Scan 网站查看，用户须自行创建账户，再到 Zephyr 项目页选择 “Add me to project”（把我加入项目）；新成员需要管理员批准。

原文说明 Zephyr 代码库按 `bi-weekly` 周期开展静态分析。工具发现的问题自动生成 GitHub 问题单，初始优先级与工具定义相同或等价，并分配给受影响代码的维护者，以明确责任并高效解决。

> 译注：英语 `bi-weekly` 可表示每两周一次或每周两次，原页未进一步限定，因此此处保留原词，避免给出未经证实的执行频率。

由静态分析、代码质量和软件安全领域人员组成的专门团队负责保障流程有效，核实问题得到正确分诊并及时解决。

<a id="workflow"></a>

### 2.9.1\_处理流程（Workflow）

分析 Coverity 报告后若确认是误报，将分类设为 “False positive”（误报）或 “Intentional”（有意如此），操作设为 “Ignore”（忽略），负责人设为自己，并评论说明理由。

随后在 Zephyr 的相关 GitHub 问题单补充详情；必须先在扫描服务网站完成上述处理，再关闭问题单。没有修复代码、也没有在扫描服务中忽略条目就关闭的问题，如果仍然存在，会自动重新打开。

## 2.10\_贡献工作流（Contribution Workflow）

项目鼓励小而受控的修改，以简化审查、合并和变基，并保持历史清楚。贡献时应尽可能提供变更信息，更新相关文档，并在提交前充分测试。

常用 GitHub 工作流结合 Git 命令行和浏览器操作。Git 完成任务的方法不止一种，以下是一种典型流程。

> 译注：以下命令属于官方工作流示例，前提是已经按入门指南取得源码并准备 Git 环境。`zephyrproject/zephyr`、分支名和远端名体现这套示例布局；`<your github id>`、提交编号、文件列表等必须按实际贡献替换。它们不绑定作者电脑的目录，也不是要求重命名已有工作区或直接改动当前仓库远端。

1. 在个人 GitHub 账户下[创建 Zephyr 分叉（Fork）](https://github.com/zephyrproject-rtos/zephyr)，即点击仓库页右上角 Fork 按钮。
> 译注：原文 Fork 链接的 `#fork-destination-box` 锚点在所核对的仓库页面中已不存在，因此链接改为同一官方仓库入口；使用页面上的 Fork 按钮。

2. 在开发电脑进入[获取源码时创建](../getting_started/P002_入门指南.md#get-the-code)的 `zephyr` 目录：

```bash
cd zephyrproject/zephyr
```

3. 将指向[上游仓库](https://github.com/zephyrproject-rtos/zephyr)的默认远端从 `origin` 重命名为 `upstream`：

```bash
git remote rename origin upstream
```

4. 添加个人分叉，命名为 `origin`：

```bash
git remote add origin https://github.com/<your github id>/zephyr
```

5. 检查远端：

```bash
git remote -v
```

预期输出类似下方；这是输出，不是要执行的命令：

```text
origin   https://github.com/<your github id>/zephyr (fetch)
origin   https://github.com/<your github id>/zephyr (push)
upstream https://github.com/zephyrproject-rtos/zephyr (fetch)
upstream https://github.com/zephyrproject-rtos/zephyr (push)
```

6. 从 `main` 创建主题分支（topic branch）。处理问题单时，建议分支名包含编号：

```bash
git switch main
git switch -c fix_comment_typo
```

某些子系统在不同于 `main` 的分支开发，检出时可能需明确分支：

```bash
git switch -c fix_out_of_date_patch origin/net
```

7. 修改、本地测试、再修改并测试；也参阅前面的 [twister](#twister) 小节。
8. 结果满意后，添加修改过的文件，开始 PR 提交流程：

```bash
git add [file(s) that changed, add -p if you want to be more specific]
```

这里方括号中的英文说明意为“发生修改的文件；若需更精确可加 `-p`”，不是字面文件名。查看尚未暂存文件：

```bash
git status
```

核对准备提交的内容：

```bash
git diff --cached
```

9. 在本地提交：

```bash
git commit -s
```

`-s` 自动添加 `Signed-off-by:`，表示同意 [DCO](#dco)。缺少此行会被拒绝；提交说明要求见[提交说明指南](#commit-guidelines)。

10. 将主题分支推送到个人 GitHub 分叉：

```bash
git push origin fix_comment_typo
```

11. 浏览器打开个人分叉，为刚处理的分支点击 “Compare & pull request”（比较并创建拉取请求）。检查差异，确认目标为 `main`；提交说明中的标题和正文也会出现。
12. 机器人依据仓库的 `MAINTAINERS` 文件分配建议审查者；项目成员还可选择其他审查者。
13. 点击提交按钮后，PR 等待审查。审查评论会触发邮件，也可在[PR 列表](https://github.com/zephyrproject-rtos/zephyr/pulls)查看。
14. 等待合入时，可以从 `main` 而非前一个主题分支创建另一个分支处理新问题：

```bash
git switch main
git switch -c fix_another_issue
```

再沿同一流程推进。

15. 审查者要求修改时，在开发仓库通过交互式变基修订相关提交：

```bash
git rebase -i <offending-commit-id>^
```

在编辑器中将 `pick` 改为 `edit`，选中要修改的提交；有多个提交时可针对某一个。删除整行会删除对应提交。随后编辑文件解决审查问题，再检查和测试。

准备好后继续：

```bash
git add [file(s)]
git rebase --continue
```

必要时更新提交说明，再推送：

```bash
git push --force origin fix_comment_typo
```

强制推送会更新原 PR，无需重新提交 PR。

16. 推送后检查 PR 是否有合并冲突。如有，在本地变基：

```bash
git fetch --all
git rebase --ignore-whitespace upstream/main
```

原文将 `--ignore-whitespace` 描述为阻止变基调用的 `git apply` 改变空白。解决冲突后再次推送：

```bash
git push --force origin fix_comment_typo
```

> 译注：原文对空白选项的描述过于绝对。[Git 官方说明](https://git-scm.com/docs/git-rebase#Documentation/git-rebase.txt---ignore-whitespace)指出，此选项在协调差异时忽略空白差异：apply 后端在补丁上下文中忽略空白变化；merge 后端把仅空白变化的行视为未变，可能丢弃仅修改空白的补丁块。不能据此认为所有空白都会原样保留。

> 原文说明：修订提交并强制推送是 Zephyr 推荐、在 GitHub 之外也常用的审查方式，但并非 GitHub 主要支持的模式。强制推送可能导致 “View Changes”（查看修改）只能查看最后一次修改，旧提交找不到；也不总能比较最后审查版本与最新提交版本。重写历史时，GitHub 只保证可访问最新版本。

CI 失败时，应修改代码并按上述变基方式修订提交；更多信息见[持续集成](#continuous-integration)。

<a id="contribution-tips"></a>
<a id="id5"></a>

### 2.10.1\_贡献技巧（Contribution Tips）

以下做法有助于加快 PR 审查和合入：

- 推送后续修改时，使用 [git-rebase](https://git-scm.com/docs/git-rebase#Documentation/git-rebase.txt---keep-base) 的 `--keep-base`。
- 在 PR 页面确认仍能无冲突合并。
- 标题清楚说明修复或增加什么。
- PR 必须有正文，补充提交内容的详情。
- 在 PR 正文引用所修复的问题单。
- 提交后立即观察早期 CI 结果，及时修复发现的问题。
- **1—2 小时**后回看全部 CI 状态，确认全部为绿色。
- 按审查要求修订并推送后，点击 “Re-request review”（重新请求审查）通知提出要求的人。

<a id="identifying-contribution-origin"></a>

### 2.10.2\_标明贡献来源（Identifying Contribution Origin）

新增文件时，要说明来源、署名和用途。Zephyr 原创文件的提交说明应包括下方内容；没有 `Origin` 标签时默认是 `Original`：

```text
Origin: Original
```

从[外部项目导入](P012_外部组件贡献.md#external-contributions)文件时，提交说明必须包含原项目、项目位置、该文件来源提交的 SHA 标识及用途。本地维护的导入示例：

```text
Origin: Contiki OS
License: BSD 3-Clause
URL: https://www.contiki-os.org/
commit: 853207acfdc6549b10eb3e44504b1a75ae1ad63a
Purpose: Introduction of networking stack.
```

其中 `Purpose: Introduction of networking stack.` 表示“用途：引入网络协议栈”；`Origin` 为原项目，`License` 为许可，`URL` 为项目网址，`commit` 为来源提交。

模块仓库中由外部维护的导入示例：

```text
Origin: Tiny Crypt
License: BSD 3-Clause
URL: https://github.com/01org/tinycrypt
commit: 08ded7f21529c39e5133688ffb93a9d0c94e5c6e
Purpose: Introduction of TinyCrypt
```

其中用途是“引入 TinyCrypt”，其他来源字段含义相同。

<a id="treewide-changes"></a>
<a id="id6"></a>

## 2.12\_全源码树变更（Treewide Changes）

这类变更影响广泛，因此有附加要求，以提高审查充分性和用户可见性。

<a id="definition-and-decision-making"></a>

### 2.12.1\_定义与决策（Definition and Decision Making）

全源码树变更指对 Zephyr API、编码实践或其他开发要求的修改，其影响要求整个 Zephyr 源码仓库相应修改，或可合理预期大量外部 Zephyr 软件需要相应修改。

定义必然带有非正式性质，因为具体判断可能依赖上下文并存在主观因素。维护者应审慎判断，优先考虑开发者体验。长期争议可提交技术指导委员会（Technical Steering Committee，TSC）解决，但不要过早升级。

<a id="requirements-for-treewide-changes"></a>

### 2.12.2\_全源码树变更要求（Requirements for Treewide Changes）

1. 对相应问题单和 PR 添加 `treewide` GitHub 标签。
2. 任何相关 PR 合并前，提案人必须建立 [RFC 问题单](https://github.com/zephyrproject-rtos/zephyr/issues/new?assignees=&labels=RFC&template=003_rfc-proposal.yml)，描述修改、理由和影响。
3. 合并前，[架构工作组（Architecture Working Group，WG）](https://github.com/zephyrproject-rtos/zephyr/wiki/Architecture-Working-Group)须将其纳入议程，讨论接纳还是拒绝；未形成共识时升级到 TSC。
4. 工作组须为每项全源码树变更规定 PR 合并程序，包括特定子系统的批准要求及额外审查时间。
5. 工作组接纳后、任何相关 PR 合并前，提案人必须向 [`devel@lists.zephyrproject.org`](mailto:devel%40lists.zephyrproject.org) 邮件列表通报 RFC。

<a id="examples"></a>

### 2.12.3\_示例（Examples）

过去的例子包括：弃用[日志 API](../observability/P001_日志.md#logging-api) 第 1 版、转向第 2 版，见提交 [262cc55609](https://github.com/zephyrproject-rtos/zephyr/commit/262cc55609b73ea61b5f999c6c6daaba20bc5240)；删除旧版[设备树绑定](../devicetree/P008_绑定概述.md#dt-bindings)语法的支持，见 [6bf761fc0a](https://github.com/zephyrproject-rtos/zephyr/commit/6bf761fc0a2811b037abec0c963d60b00c452acb)。

为广泛使用的 API 增加新版，同时继续支持旧版，不属于全源码树变更；但弃用或删除这类 API 属于。

<a id="specialized-driver-requirements"></a>

## 2.13\_专用驱动要求（Specialized Driver Requirements）

独立器件的驱动应尽可能使用 Zephyr 总线 API，例如串行外设接口（Serial Peripheral Interface，SPI）和集成电路间总线（Inter-Integrated Circuit，I2C），以便器件能用于任何厂商实现兼容总线的 SoC。

如果特定 SoC 系列的专用加速器使通用 API 在技术上无法发挥完整性能，可以为该系列增加专用实现路径；但驱动仍必须为其他 SoC 提供通过 Zephyr API 的常规路径。每个例外都必须由架构工作组批准，以核实合理性，并可能从中总结经验、推动改进。


对应官方文档源码：[doc/contribute/guidelines.rst](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/doc/contribute/guidelines.rst)。

> 译注——源码跟踪：本仓库的[对应源码](../../../doc/contribute/guidelines.rst)可用于跟踪，版本可能与网页不同；本批仅翻译和核对文档，没有执行固件构建、模拟运行或烧录。
