# 第9章\_编码准则

原文：[官方页面](https://docs.zephyrproject.org/latest/contribute/coding_guidelines/index.html)。读取日期：2026-10-14；保存的 latest 页面及 HTML 摘要见[来源记录](../SOURCES.md)。

<a id="main-rules"></a>

## 9.1\_主要规则（Main Rules）

编码准则以 MISRA-C 2012 为基础，采用其中一个子集。下表给出规则摘要、MISRA-C 参考以及其他标准的对应规则。MISRA 源自汽车工业软件可靠性协会（Motor Industry Software Reliability Association）；这里保留标准名称，表中的 `Dir` 指指令（Directive），`Rule` 指规则，CERT C 为对应的 C 安全编码参考。

原文说明：MISRA-C 严重程度及其他标准引用只供参考；表中列出的规则对 Zephyr **全部是必需的**，所有新代码都应遵守。

> 原文说明：现有维护者或协作者若无法通过雇主获得 MISRA-C 2012，项目可提供数量有限的副本。有需要者向 [`safety@lists.zephyrproject.org`](mailto:safety%40lists.zephyrproject.org) 发邮件，说明为何无法通过其他途径取得，以及取得后预期作出的贡献。安全委员会会审查所有请求。

## 9.2\_附加规则（Additional Rules）

<a id="rule-a-1-conditional-compilation"></a>

### 9.2.1\_规则A.1：条件编译（Conditional Compilation）

**严重程度：必需（Required）。**

头文件中的函数声明和结构体声明不得按条件编译。对于结构体定义内部的字段，可以按条件排除，以免支持的功能未启用时浪费内存。

理由：按编译选项排除头文件声明，可能使相应文档无法生成；声明缺失也会使代码不能用 `if (IS_ENABLED(CONFIG_FOO)) {}` 替代预处理条件语句，按选项改变执行路径。

<a id="coding-guideline-inclusive-language"></a>

### 9.2.2\_规则A.2：包容性语言（Inclusive Language）

**严重程度：必需（Required）。**

不得新增下表所列冒犯性术语的用法。适用范围包括但不限于源码、注释、文档和分支名。替代词可因领域或子系统不同而不同，但应尽可能跟随更新后的行业标准。

维护现有实现，或新增由 Zephyr 外部机构管理的行业标准实现时，可以例外。一旦更新后的标准可用或管理机构公开宣布新术语，建议尽快替换已有用语；没有适用规范时应立即替换。

| 原用语 | 可选替代用语及中文含义 |
| --- | --- |
| `{master,leader} / slave` | `{primary,main} / {secondary,replica}`（主要／主实例与次要／副本）；`{initiator,requester} / {target,responder}`（发起者／请求者与目标／响应者）；`{controller,host} / {device,worker,proxy,target}`（控制器／主机与设备／工作者／代理／目标）；`director / performer`（指挥者／执行者）；`central / peripheral`（中心设备／外围设备）。 |
| `blacklist / whitelist` | `denylist / allowlist`、`blocklist / allowlist`、`rejectlist / acceptlist`，分别表达拒绝／允许、阻止／允许、拒收／接收列表。 |
| `grandfather policy` | `legacy`（旧有、历史遗留）。 |
| `sanity` | `coherence`（一致性）、`confidence`（可信度）。 |

<a id="coding-guideline-libc-usage-restrictions-in-zephyr-kernel"></a>

### 9.2.3\_规则A.3：宏名称冲突（Macro Name Collisions）

**严重程度：必需（Required）。**

对于 `MIN`、`MAX`、`ARRAY_SIZE` 这类常用名称的宏，不得为避免与其他实现冲突而修改或保护其定义。特别是不得加前缀移入 Zephyr 专用命名空间，不得用 `#undef` 后重新定义，也不得用 `#ifndef` 条件排除。若与[模块](../modules/P001_模块与外部项目.md#modules)已有定义冲突，应修改模块本身，最好在其上游修改，或者修改 Zephyr 自己的分叉。

此规则适用于整个 Zephyr 项目，不受宏加入时间或当前树中名称影响。如果某宏名在多个知名开源项目中广泛使用，Zephyr 也应使用该名。“常用”的判断有主观、不可量化成分，但最终目标是给用户熟悉的宏。

模块之间冲突也适用：集成前应修改双方模块，采用各自模块专用的宏名。

理由：Zephyr 实时操作系统（Real-Time Operating System，RTOS）通过模块附带额外能力和依赖。模块通常是独立项目，宏名可能互相冲突或与 Zephyr 冲突。本页把 Zephyr 视为主项目，因此由它实现不带命名空间的版本；由于每个模块使用相应上游的分叉，可以修改模块中的宏实现来避开冲突。

<a id="rule-a-5-c-standard-library-usage-restrictions-in-zephyr-codebase"></a>

### 9.2.5\_规则A.5：Zephyr代码库的C标准库限制（C Standard Library Usage Restrictions in Zephyr Codebase）

**严重程度：必需（Required）。**

除本规则列出的豁免外，Zephyr 代码库使用的 C 标准库函数和宏，应限于 C11，且排除附录 K 的边界检查接口（Bounds-checking Interfaces）。

这里的“代码库”指提交到[Zephyr 主仓库](https://github.com/zephyrproject-rtos/zephyr)、准备在嵌入式目标上运行的全部源码，排除前述内核；不包括主机工具和[原生测试目标](../native_reference/P001_目录.md#boards-posix)专用代码。

> 译注：原文此处链接到“规则A.3：宏名称冲突”，但内核范围实际定义在上一节A.4。此处按该定义理解，记录原文交叉引用差异。

<a id="id44"></a>

以下非 C11 函数和宏获得豁免，可以使用：

| 函数或宏 | 来源标准 |
| --- | --- |
| [`gmtime_r()`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/gmtime_r.html) | POSIX.1-2001 |
| [`strnlen()`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/strlen.html) | POSIX.1-2008 |
| [`strtok_r()`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/strtok.html) | POSIX.1-2001 |


全部这些非标准接口必须在[公共C库](../languages/P003_C库公共代码.md#c-library-common)实现，以便所选标准库不提供时仍可使用。在满足此条件且有理由时，可增加其他常见标准库的非标准函数；但若有功能等价的标准函数，必须使用标准函数。

理由：Newlib、Picolibc 等库还提供 POSIX、Linux 等标准或事实标准对 ISO C 的扩展。C11 不要求工具链支持这些非标准接口，使用它们可能与自带标准库的第三方工具链不兼容。
