# 第3章\_编写配置片段

原文：[Writing Snippets](https://docs.zephyrproject.org/latest/build/snippets/writing.html)。读取日期：2026-10-12，`latest`。

本章说明如何编写**配置片段（Snippet）**，把需要一同使用的 Kconfig 设置、设备树覆盖和其他构建参数放到可复用的描述文件中。先了解文件结构和查找方式，再决定设置的应用顺序及开发板条件。

## 3.1\_基础结构

片段通过名为 `snippet.yml` 的 **YAML（YAML Ain’t Markup Language，结构化数据描述语言）**文件定义。文件包含片段名称和其他构建设置：

```yaml
name: snippet-name
# ... build system settings go here ...
```

构建设置写在本章后面介绍的其他键中。相同键下的设置可以组合，例如同时追加片段专属的**设备树覆盖文件（Devicetree Overlay）**和 `.conf` 配置文件：

```yaml
name: foo
append:
  EXTRA_DTC_OVERLAY_FILE: foo.overlay
  EXTRA_CONF_FILE: foo.conf
```

片段也可同时应用于**系统构建（System Build，Sysbuild）**及应用配置：

```yaml
name: foo
append:
  SB_EXTRA_CONF_FILE: sb.conf
  EXTRA_CONF_FILE: app.conf
```

> 译注：`name` 给出构建时选择的片段名，`append` 表示追加设置；`EXTRA_DTC_OVERLAY_FILE` 是附加设备树覆盖文件变量，`EXTRA_CONF_FILE` 是应用附加 Kconfig 文件变量，`SB_EXTRA_CONF_FILE` 是 Sysbuild 附加 Kconfig 文件变量。描述文件及其中引用的 `.overlay`、`.conf` 文件都由片段作者提供，不会因写下文件名而自动生成。

## 3.2\_避免名称冲突

在片段内编写设备树覆盖时，为节点标签、节点名等选择 `snippet_<name>` 或 `snippet-<name>` **命名空间（Namespace）**前缀，避免与其他配置冲突。

例如片段名为 `foo-bar` 时，可这样命名：

```devicetree
chosen {
        zephyr,baz = &snippet_foo_bar_dev;
};

snippet_foo_bar_dev: device@12345678 {
        /* ... */
};
```

> 译注：`snippet_foo_bar_dev` 是设备树节点标签，`&snippet_foo_bar_dev` 引用它；标签中的连字符转换为下划线。原例只展示相关片段，`/* ... */` 表示省略的属性，不是包含完整节点属性和根结构的可独立编译覆盖文件。

## 3.3\_片段查找位置

构建系统在以下位置查找片段。

### 3.3.1\_SNIPPET_ROOT搜索根

CMake 变量 `SNIPPET_ROOT` 包含片段搜索根目录，始终包括 Zephyr 仓库，因此官方 [snippets目录](https://github.com/zephyrproject-rtos/zephyr/blob/main/snippets/)始终是一个片段来源。可在 CMake 配置时手工加入其他目录；变量是以空格或分号分隔的目录列表。

对每个根目录，构建系统在它的 `snippets/` 子目录中寻找 `snippet.yml`。文件可以任意嵌套在这些子目录之下。

例如，若两个搜索根是当前工程布局中的 `foo` 与 `bar`，则相应搜索 `foo/snippets/` 与 `bar/snippets/`。

> 译注：原文用根目录下的两条绝对示例路径说明相同关系。这里改为相对目录示意，重点是每个搜索根下都追加 `snippets/`，不绑定读者机器的位置。实际传给 CMake 的相对根目录如何解析，应按调用时的工作目录和所用版本核对。

### 3.3.2\_模块提供的搜索根

任何在 `module.yml` 中提供 `snippet_root` 设置的[模块](https://docs.zephyrproject.org/latest/develop/modules.html#modules)，都可以提供片段。

例如，一个名为 `baz` 的 Zephyr 模块可以在 `module.yml` 中加入以下设置片段：

```yaml
settings:
  snippet_root: .
```

随后 `baz/snippets` 内的 `snippet.yml` 就会自动被发现，效果与把 `baz` 的目录加入 `SNIPPET_ROOT` 相同。

> 译注：`snippet_root` 是模块构建设置，不是片段名称。原例只显示 `settings` 子树；在完整 `module.yml` 中应按模块格式放到 `build.settings` 下，不能把局部示例误当成完整文件。`.` 相对于模块根，表示该根下的 `snippets/` 提供片段。

## 3.4\_处理顺序

片段按 CMake 变量 `SNIPPET` 中的顺序处理；使用 west 时，则按各个 `-S` 参数出现的顺序处理。

要先应用 `foo`、再应用 `bar`，CMake 示例：

```sh
cmake -Sapp -Bbuild -DSNIPPET="foo;bar" [...]
cmake --build build
```

等效 west 示例：

```sh
west build -S foo -S bar [...] app
```

多个片段设置同一配置时，最后处理的片段所设值进入最终配置。例如 `foo` 设置 `CONFIG_FOO=1`，`bar` 设置 `CONFIG_FOO=2`，上述顺序最终得到 `CONFIG_FOO=2`。这一原则同时适用于 Kconfig 配置片段 `.conf` 和设备树覆盖 `.overlay`。

> 译注：`CONFIG_FOO` 是原文假设存在的配置项；实际 Kconfig 值仍需符合类型、依赖和可见性等规则。处理顺序并不能让一个依赖不满足的选项强行生效。命令中的 `[...]` 表示省略参数，不能原样输入。

## 3.5\_设备树覆盖文件

下面的 `snippet.yml` 将 `foo.overlay` 追加到构建：

```yaml
name: foo
append:
  EXTRA_DTC_OVERLAY_FILE: foo.overlay
```

`foo.overlay` 路径相对于 `snippet.yml` 所在目录。多个覆盖文件可写成列表：

```yaml
name: foo
append:
  EXTRA_DTC_OVERLAY_FILE:
    - foo.overlay
    - bar.overlay
```

## 3.6\_应用Kconfig文件

下面的 `snippet.yml` 将 `foo.conf` 追加到应用构建：

```yaml
name: foo
append:
  EXTRA_CONF_FILE: foo.conf
```

路径同样相对于 `snippet.yml` 所在目录；多个 `.conf` 文件也可用列表提供。

## 3.7\_Sysbuild的Kconfig文件

下面的 `snippet.yml` 把 `foo.conf` 追加到 Sysbuild 配置：

```yaml
name: foo
append:
  SB_EXTRA_CONF_FILE: foo.conf
```

路径相对于 `snippet.yml` 所在目录，也支持多个 Sysbuild `.conf` 文件列表。

> 译注：应用配置与 Sysbuild 配置有不同的 Kconfig 命名空间；后者通常设置 `SB_CONFIG_` 前缀选项。见[系统构建](../sysbuild/P001_系统构建.md)。不要仅因后缀都是 `.conf` 就混用内容。

## 3.8\_设备树预处理参数

CMake 缓存变量 `DTS_EXTRA_CPPFLAGS` 保存额外的**设备树源码（Devicetree Source，DTS）**预处理选项。下面示例向构建追加一个宏定义：

```yaml
name: foo
append:
  DTS_EXTRA_CPPFLAGS: -DMY_DTS_CONFIGURE
```

这些标志可控制设备树文件中参与处理的内容。

> 译注：`-DMY_DTS_CONFIGURE` 是传给 **C预处理器（C Preprocessor，CPP）**的宏定义参数，宏名是此例自定的标识符。它服务于设备树预处理，不自动成为应用 C 源码的编译宏；实际设备树还需使用相应条件逻辑。

## 3.9\_特定开发板设置

可以编写仅适用于部分开发板的设置。这些设置会叠加到适用于全部开发板的公共片段设置之上。例如，普通应用同时具有 `prj.conf` 与 `boards/foo.conf` 时，为板 `foo` 构建会同时使用两者，而不是只使用后者；这里的叠加关系类似。

### 3.9.1\_按名称匹配

在 `boards` 键下列出开发板名称：

```yaml
name: ...
boards:
  bar: # settings for board "bar" go here
    append:
      EXTRA_DTC_OVERLAY_FILE: bar.overlay
  baz: # settings for board "baz" go here
    append:
      EXTRA_DTC_OVERLAY_FILE: baz.overlay
```

为板 `bar` 构建时加入 `bar.overlay`，为 `baz` 构建时加入 `baz.overlay`。原例 `name: ...` 仍需填写真实片段名称。

### 3.9.2\_按正则表达式匹配

把板名模式放在斜线 `/` 之间，可按 [CMake语法的正则表达式（Regular Expression）](https://cmake.org/cmake/help/latest/command/string.html#regex-specification)匹配；表达式必须匹配整个板名。

```yaml
name: foo
boards:
  /my_vendor_.*/:
    append:
      EXTRA_DTC_OVERLAY_FILE: my_vendor.overlay
```

上例为 `my_vendor_board1` 和 `my_vendor_board2` 加入 `my_vendor.overlay`，但不匹配 `another_vendor_board` 或 `x_my_vendor_board`。

### 3.9.3\_开发板修订版本

还支持**开发板修订版本（Board Revision）**专属配置，按顺序应用在公共文件之后：

```yaml
name: foo
boards:
  bar:
    append:
      # Base file will be applied first
      EXTRA_DTC_OVERLAY_FILE: first.overlay
    revisions:
      "0.7.0":
        append:
          # Will be applied on top of common board file
          EXTRA_DTC_OVERLAY_FILE: extra_0_7_0.overlay
```

板 `bar` 的全部修订版本都使用 `first.overlay`。构建 `bar@0.7.0` 时，再追加 `extra_0_7_0.overlay`；这使该修订可以在公共配置之上调整相关属性。
