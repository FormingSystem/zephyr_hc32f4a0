# 第2章\_地址总线与存储器映射

前一专题的 CPU 已经能够发出读取和写入，但还没有解释一个关键问题：同一颗芯片里同时存在程序存储器、数据存储器和 GPIO，CPU 怎样指定这次要找谁？答案涉及地址、地址译码和完成访问所需的总线协议。

本章先用一小块连续存储区建立地址模型，再把相同访问形式推广到外设。后一专题才把这些对象放进 H743 的真实地址地图，避免先背一串十六进制数。

<a id="4.1_地址表示位置，内容表示保存的值"></a>

## 2.1\_地址表示位置，内容表示保存的值

**地址（Address）** 是访问位置的编号。在本专题采用的字节寻址系统中，相邻地址对应相邻字节。设四个位置的内容如下：

![逐字节编号与一个四字节数之间的关系](../assets/p004-byte-addresses.svg)

图例：**蓝框是一字节存储位置，绿框是把四个字节按小端解释得到的数值，紫色表示访问起点**。图中每个格子都能被单独编号，四字节分组没有删除中间三个地址。

名称注释：`Byte（字节）：本例为 8 位。` `Word（字）：本篇 Arm 整数访问中指 32 位，即四字节；其他架构的术语约定需分别核对。`

| 地址 | 保存的一个字节 |
| --- | --- |
| `0x20000000` | `0x78` |
| `0x20000001` | `0x56` |
| `0x20000002` | `0x34` |
| `0x20000003` | `0x12` |

一个 32 位数占四个字节。把最低有效字节放在最低地址，称为**小端序（Little-Endian）**；按这种规则，上表保存的 32 位值是 `0x12345678`。H743 的处理器采用小端数据表示。若只从首地址读一个字节，则得到 `0x78`，不是整个 `0x12345678`。

**地址 `0x20000001` 完全存在。** 它不需要因为 CPU 是 32 位就变成 `0x20000004`。区别在于这次要从它开始访问几个字节：取一个字节，只需要它自己；取一个四字节对象，则会覆盖 `...01`、`...02`、`...03`、`...04`。对齐检查针对“起点与访问类型的组合”，不是判断地址这个数有没有资格存在。

“32 位处理器”也不表示每个地址只能保存 32 位。处理器的寄存器宽度、地址表示能力、访问宽度和总线数据宽度是不同维度；例如某条指令可以只访问一个字节，另一条访问一个 32 位字。

如果用 32 位表示字节地址，理论上可表示 `2^32` 个字节位置，即 4 GiB 的地址空间。**地址空间（Address Space）** 是可编号的范围，不等于芯片真的装有 4 GiB 存储器。许多范围可能未实现、保留或分配给外设。

<a id="4.2_寻址怎样把表达式变成实际访问地址"></a>

## 2.2\_寻址怎样把表达式变成实际访问地址

**寻址（Addressing）** 是确定指令的操作数在哪里，以及访问时使用哪个地址的过程。寄存器中的数、指令内的常数、寄存器指向的内存，是三种不同来源。先假设 r0=`0x24000000`、r2=2，比较下面几种表达：

![基址加元素偏移形成有效地址再访问目标](../assets/p004-effective-address.svg)

图例：**蓝色是地址计算用的数值，紫色是最终有效地址，绿色是读取的数据**。先算地址，再读该位置内容；得到地址不是已经得到数据。

名称注释：`Effective Address（有效地址）：本次内存操作最终使用的地址。` `Base（基址）：计算访问位置的起点。` `Offset（偏移）：在基址上增加的字节距离。`

表中的 MOV（Move，传送指令）复制数值，LDR（Load Register，加载寄存器指令）从地址取内容，LSL（Logical Shift Left，逻辑左移）参与计算偏移。先区分数值传送和内存访问，再比较方括号内的地址表达。

| 表达 | 实际动作 | 是否访问数据存储器 |
| --- | --- | --- |
| `MOV r1,#7` | 把常数 7 放入 r1 | 否 |
| `MOV r1,r0` | 复制 r0 的数值到 r1 | 否 |
| `LDR r1,[r0]` | 从地址 `0x24000000` 读取一个字 | 是 |
| `LDR r1,[r0,#4]` | 从地址 `0x24000004` 读取一个字 | 是 |
| `LDR r1,[r0,r2,LSL #2]` | 从 `r0+(r2×4)`，即 `0x24000008` 读取一个字 | 是 |

LSL（Logical Shift Left，逻辑左移）把位向左移动，这里移两位相当于在适用范围内乘 4。最后一个例子正好对应 32 位数组的第 2 号元素。C 的 `samples[2]` 先按元素大小计算偏移，CPU 执行的是算出的字节地址；硬件不认识源码中的数组名称。

Arm 还支持访问后更新基址等形式，例如 `LDR r1,[r0],#4` 先使用旧 r0，再令 r0 增加 4；`LDR r1,[r0,#4]` 使用加 4 后的位置，但不改变 r0。这个差别会在启动代码复制数据时直接出现。实际指令编码对寄存器和偏移范围有限制，不能把任意数学表达式塞进方括号。

练习：r0=`0x24000000`，数组元素是 `uint16_t`（16 位无符号整数，每个占两字节），第 3 号元素在哪里？答案是 `0x24000006`。索引是 3，字节偏移是 6；把偏移误写成 3，访问位置就变了。

<a id="4.3_一次总线访问必须带哪些信息"></a>

## 2.3\_一次总线访问必须带哪些信息

**总线（Bus）** 是连接多个部件并按协议传递访问请求与响应的互连。为完成一次写入，系统至少需要表达目标地址、写入数据以及访问性质；读取则要把目标内容作为响应返回。

![CPU 地址请求经过译码到存储器或 GPIO 的访问关系](../assets/p004-address-decode.svg)

图例：**蓝色箭头表示请求，绿色箭头表示读回数据或完成响应，紫色虚线表示地址选择**。这是事务关系图，未画出具体协议的全部信号。

名称注释：`SRAM（Static Random-Access Memory－静态随机存取存储器）：在供电期间保存可反复读写的数据。` `GPIO（General-Purpose Input/Output－通用输入输出）：提供外部引脚状态与控制接口。` `MMIO（Memory-Mapped Input/Output－存储器映射输入输出）：用地址空间中的访问操作控制外设。`

沿蓝线发起读取时，CPU 或其访问接口给出地址。**地址译码（Address Decoding）** 根据地址范围选择目标，目标再根据内部偏移选中具体位置。等目标能够给出数据，绿色路径才带回响应。若目标还没准备好，协议可以让事务等待；若访问非法或目标报告错误，也可能返回错误而引发处理器故障。

这个模型解释了“读一条寄存器语句为什么不一定一个周期结束”。程序发出访问，目标完成访问，中间有互连、桥接和目标时序。外设不必与 CPU 处于相同频率。不同目标还可能走不同接口，因而相同的 `LOAD` 形式可能有不同延迟。

<a id="4.4_为什么读写外设看起来像访问内存"></a>

## 2.4\_为什么读写外设看起来像访问内存

给 GPIO 的状态和控制接口分配地址后，CPU 就可以用加载、存储指令访问它们，这称为 MMIO。地址与普通存储器一样承担定位职责，但读写效果由外设定义。

普通 SRAM 位置通常可以“写入一个数，以后再读回”。外设寄存器则可能具有不同规则：某位反映实时输入，只能读；某位写 1 表示清除已经锁存的事件；某个写入口把数据推入发送队列，读取同一位置可能根本没有意义。

| 访问属性 | 软件动作 | 需要保持的认识 |
| --- | --- | --- |
| 只读状态 | 读取当前硬件提供的状态 | 写入通常不能改变它，具体后果查手册 |
| 普通读写配置 | 读出配置，再按允许的字段修改 | 保留位与生效条件仍须遵守 |
| 写 1 清除 | 给指定状态位写 1 | 写入值不是要保存的新状态，而是清除命令 |
| 写数据入口 | 写入待发送数据 | 写入可能启动硬件工作，重复写会产生重复动作 |

因此，`reg |= mask` 不是通用的“只改一位”工具。它实际执行读取、CPU 运算和写回；若寄存器采用写 1 清除语义，读到的其他置位状态也会被写回为 1，从而被一并清除。必须从访问属性选择动作，不能只凭 C 语法判断效果。

<a id="4.5_程序和变量为什么放在不同存储器"></a>

## 2.5\_程序和变量为什么放在不同存储器

断电后程序仍应保留，但运行中的计数、缓存和栈又需要频繁更新。不同存储技术承担了不同需求。

**闪存（Flash Memory）** 适合保存断电后仍要保留的固件和常量；它的擦除、编程有专门粒度和流程，不能把普通变量赋值直接当作可靠的 Flash 更新。**RAM（Random-Access Memory－随机存取存储器）** 中的“随机存取”指可按地址选择位置，不是随机数；SRAM 是其中一种实现，适合运行期变量，读写方便，但一般在失去供电后不能保持内容。“静态”是其存储电路类型名称，不表示断电不丢数据。

处理器还可能配置更近的高速存储，例如缓存和紧耦合存储。此时程序可见的地址不一定告诉我们访问最终经过哪一级；先按正确地址与权限完成访问，再根据具体芯片的路径解释性能。

从结构上看，**冯·诺依曼结构（Von Neumann Architecture）** 强调指令与数据共享存储/访问组织；**哈佛结构（Harvard Architecture）** 强调指令与数据通路分离。现代处理器可能在内部拆分取指与数据路径，同时仍让程序使用统一地址地图。H743 不能被简化成“程序只准在 Flash，数据只准在 SRAM”的两条绝对规则；访问权限和实际实现决定哪些地址可以取指、读写。

<a id="4.6_四字节对齐到底约束什么"></a>

## 2.6\_四字节对齐到底约束什么

一个四字节值从能被 4 整除的地址开始，称为**四字节对齐（4-byte Alignment）**。用数值判断就是 `address % 4 == 0`；因为 4 是 2 的平方，也等价于地址最低两位为 `00`。十六进制末位为 0、4、8、C 的地址满足此条件，末位为 1、2、3 等则不满足四字节对齐，但仍可能是合法的字节地址。

| 访问或布局要求 | 判断方式 | 例子 |
| --- | --- | --- |
| 字节访问的自然对齐 | 任意字节地址 | `...00`、`...01` 都成立 |
| 半字的自然对齐 | 地址能被 2 整除 | `...02` 成立，`...03` 不成立 |
| 字的自然对齐 | 地址能被 4 整除 | `...04` 成立，`...02` 不成立 |
| 函数公共接口的栈对齐 | 本例 Arm 调用约定要求 SP 能被 8 整除 | 比普通字访问更严格 |
| 向量表整体基址对齐 | 按核心与表的覆盖大小决定 | 不能只因每项四字节就推断基址只需四字节对齐 |

最后两行来自软件协作或核心表定位规则，不能都归结为“CPU 是 32 位”。第6专题会认识栈和堆，第7专题再用向量表把两种不同的对齐约束分开计算。

<a id="4.7_硬件为什么偏好自然对齐"></a>

## 2.7\_硬件为什么偏好自然对齐

先用一条每次处理四个字节的简化通路观察代价。它把字节划分为边界固定的组：`...00` 到 `...03` 一组，`...04` 到 `...07` 下一组。一个四字节数从 `...00` 开始，恰好在一组内；从 `...01` 开始，则横跨两组。

![四字节对齐与跨组访问的字节组合对比](../assets/p004-alignment-groups.svg)

图例：**蓝色是本次需要的字节，灰色是邻近但不属于本次对象的字节，紫色框表示教学通路中的固定四字节组，绿色表示组合结果**。上下是两种访问方案，不是两个 CPU 同时工作。

名称注释：`Alignment（对齐）：起始地址满足指定边界。` `Byte lane（字节通道）：宽数据通路中对应一个字节的位置。`

对齐的情况可以直接选取一组；跨组的情况可能需要取得两部分，再移位拼接，写入时也可能拆分并分别选择字节位置。这增加数据选择、访问组织和边界处理的成本。**这是解释成本的模型，不是 H743 每条 LDR 的固定总线拍数。** M7 还有缓存、不同宽度的内部接口、缓冲和多个存储目标，实际访问次数与延迟要看路径，不能把图中的两组直接报告为“两周期”。

硬件和指令对未对齐访问的支持不同。Cortex-M7 的部分普通加载/存储指令可在合适的普通存储区处理未对齐访问；也可以通过配置使其触发故障。LDM/STM（Load/Store Multiple，多寄存器加载/存储）、LDRD/STRD（Load/Store Register Doubleword，双字加载/存储）等有更严格的对齐要求，设备类型区域也不能任意做未对齐访问。**“处理器支持部分未对齐”不等于任意指针、任意指令、任意外设都合法。**

C 语言还要求指针满足所指对象类型的对齐条件。把 `bytes+1` 强转成 `uint32_t *` 并解引用，不会因一次硬件实验成功就成为可移植代码。需要从字节流解析整数时，可以逐字节组合，或在满足语言与库契约的前提下用复制方式取得对象；如果输入是 MMIO，还必须遵守外设允许的访问宽度，不能直接套普通 RAM 方法。

<a id="4.8_单字节在-32-位-cpu-上怎样读写"></a>

## 2.8\_单字节在 32 位 CPU 上怎样读写

32 位寄存器能容纳四个字节，并不要求每次都从内存取四个字节。下面三个自有函数的完整原件是 [access_width.c](../labs/access_width.c)。此处观察已生成的结果；第12专题安装工具后可以重新编译。

![单字节加载和存储在四字节分组中的选位关系](../assets/p004-byte-load-store.svg)

图例：**蓝色是选中的一个字节，灰色是保持不变的邻居，绿色是加载结果，橙色是存储值**。上下两步分别演示读与写，所有地址均按字节编号。

名称注释：`LDRB（Load Register Byte－加载字节）：读取一个字节并零扩展。` `STRB（Store Register Byte－存储字节）：只更新目标字节。` `Zero extension（零扩展）：高位补零，保留无符号数值。`

```c
#include <stdint.h>

uint32_t read_byte(const volatile uint8_t *bytes)
{
    return bytes[1];
}

uint32_t read_word(const volatile uint32_t *words)
{
    return words[1];
}

void write_byte(volatile uint8_t *bytes, uint8_t value)
{
    bytes[1] = value;
}
```

GNU Arm GCC 10.3.1 对 Cortex-M7、Thumb、`-O1` 生成：

```asm
read_byte:
    ldrb r0, [r0, #1]
    bx   lr
read_word:
    ldr  r0, [r0, #4]
    bx   lr
write_byte:
    strb r1, [r0, #1]
    bx   lr
```

这里首个指针参数进入 r0，写入函数的第二参数进入 r1，返回值使用 r0。**LDRB/STRB 的 B 是 Byte，表示字节访问**；LDRB 将无符号字节零扩展到 32 位寄存器，STRB 只把源寄存器低八位写到指定位置。若使用有符号字节并做符号扩展，编译器可能选择 LDRSB，不能把两种扩展都解释成“高位补零”。

手推一次：首地址处四字节为 `11 22 33 44`，r0 指向首地址。`read_byte` 访问 `+1`，返回 `0x00000022`；`write_byte` 写入 `0xAA` 后，四字节成为 `11 AA 33 44`。后者不要求 C 程序先读出完整字、修改、再写回全部四字节。总线通常有访问大小和字节选择规则，缓存填充也可能取得更大的块；这些内部行为不能被混成“LDRB 在软件语义上读取四字节”。对 MMIO，是否允许字节访问仍由该寄存器规定。

再看两个数组：`bytes[1]` 走 `+1`，`words[1]` 走 `+4`。**改变步长的是元素类型，改变加载宽度的是生成的指令，两者都不是由变量名称决定。**

<a id="4.9_结构体填充把对齐变成可见的布局"></a>

## 2.9\_结构体填充把对齐变成可见的布局

一条面板记录既有单字节状态，又有四字节计数。先把两个相邻记录展开，观察下一条记录从哪里开始。

![结构体数组通过填充保持每个计数字段对齐](../assets/p004-struct-padding.svg)

图例：**蓝色是一个字节的 state，灰色是填充，绿色是 count 的四个字节**。两行是同一数组中连续的两条记录，`+n` 都相对数组起点计算。

名称注释：`Padding（填充）：为满足布局约束而保留的间隔。` `Stride（步长）：相邻数组元素起点之间的字节距离。` `ABI（Application Binary Interface－应用二进制接口）：约定类型大小、对齐与二进制协作方式。`

设记录含 `uint8_t state` 和 `uint32_t count`。按本例 Arm ABI 的普通布局，state 在偏移 0，偏移 1–3 留作填充，count 在偏移 4，整体通常占八字节。编译器这样安排，使结构体数组中的下一个 count 仍能保持所需对齐；不是让 state 自身变成四字节类型。

如果协议线上规定只有五字节，就不能直接认定 `sizeof(record)==5`，更不能把内存对象原样发送当作通用序列化。紧凑布局会改变约束，字段访问可能需要不同代码；按协议逐字段编码能够明确字节序和宽度。第12专题的工具实验会用编译期断言验证这份普通布局。

数组也可以据此计算。若 `uint32_t samples[4]` 从 `0x24000000` 开始，每个元素四字节，则 `samples[2]` 位于 `0x24000008`。C 表达式中的 `samples+2` 按元素大小推进，不是把字节地址简单加 2。后面的汇编地址计算会把这种大小关系展开出来。

练习：若从 `0x20000001` 起连续四字节为 `11 22 33 44`，按小端解释的数是什么？是否因此可以断定任意四字节加载指令都能合法读取它？解答：数值布局对应 `0x44332211`；布局解释成立，不代表某条指令在该地址、该存储类型和当前配置下的访问合法。数据表示与访问约束要分别判断。

官方对照：[PM0253 Rev 6](https://www.st.com/resource/en/programming_manual/DM00237416.pdf) 的 **2.3 Memory model、3.3.5 Address alignment、3.4.2 LDR and STR, immediate offset** 分别用于查存储属性、未对齐限制与字节/半字/字访问。H743 哪个地址实际连接哪块存储器，要继续查芯片参考手册；C 对象布局和公共接口栈对齐见 [AAPCS32 的 Data types and alignment、The Stack](https://github.com/ARM-software/abi-aa/blob/2025Q1/aapcs32/aapcs32.rst)。
