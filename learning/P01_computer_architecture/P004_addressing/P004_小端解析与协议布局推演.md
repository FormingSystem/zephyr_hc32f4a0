拿同一组字节分别按字节、半字和字读取，再判断它能否直接当作协议结构体。

偏移按字节计数，访问宽度决定从起始位置取几个字节。小端编码把数值最低的八位放在最低地址，因此同样的起始地址可以读出不同宽度的结果。

<a id="section-1"></a>

## 4.1\_从字节表恢复数值

在纸上写八个字节 `11 22 33 44 55 66 77 88`，基址设为 `0x24000000`。分别求偏移 1 的字节、偏移 2 的半字和偏移 4 的字，按小端解释，答案依次是 `0x22`、`0x4433`、`0x88776655`。三个地址的自然对齐分别满足各自宽度要求。

若要从偏移 1 解析协议中的四字节小端整数，可以显式组合，避免把协议布局误当成 CPU 对象布局：

```c
#include <stdint.h>
uint32_t read_le32(const uint8_t *p)
{
    return (uint32_t)p[0] | ((uint32_t)p[1] << 8)
         | ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24);
}
```

前提是 p 后面至少有四个可读字节。先转无符号 32 位再移位，明确操作宽度；函数不检查缓冲区长度。把输入换成上述数组的偏移 1，应得到 `0x55443322`。优化器可能把这种逻辑合成为适合目标的访问，语义正确并不要求最终逐字节执行。

<a id="section-2"></a>

## 4.2\_为什么结构体不能直接当通信帧

对 `struct { uint8_t tag; uint32_t value; };`，常见 AAPCS32 布局中 value 在偏移 4，总大小 8。协议若要求 tag 紧挨 value，只需五字节。多出的填充服务于内存对象对齐，不属于协议。分别画出内存布局和协议布局，再编写逐字段编码，比直接发送 `sizeof(struct)` 更可移植。
