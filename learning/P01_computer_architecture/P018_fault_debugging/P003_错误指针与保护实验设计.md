从一个错误指针出发，先判断哪些访问会触发保护，再决定该用什么证据定位故障。

故障处理要回答三件事：哪条指令请求了什么访问、目标地址允许怎样访问、硬件实际记录了什么。只有把这三项对上，才能从一次异常追到程序中的错误。

<a id="section-1"></a>

## 3.1\_从一条错误指针推到检查顺序

教学案例：一条存储指令的基址寄存器意外为0。先不要断言一定触发某类故障，因为地址0的映射、写权限和目标响应都影响结果。正确分析依次确认指令宽度与有效地址、该地址的区域属性、故障分类状态、地址有效位和保存帧是否可靠。

若发现指针来自已经返回函数的局部对象，应修复对象寿命和接口。只把 MPU 配成允许写入，可能让故障消失却扩大破坏范围。保护用于让错误早暴露，不能代替正确的对象所有权。

<a id="section-2"></a>

## 3.2\_设计一个不误伤硬件的验证

设一段练习 RAM 允许特权代码读写，区域属性禁止取指，邻接区域禁止访问。假设 MPU 已启用，这两段属性确实覆盖相应地址，代码以特权运行。读取第一段中的字应成功；跨入后一段读取，预期产生数据访问违规；从第一段取指，预期产生指令访问违规。由此可见，读写权限与执行权限要分开判断。将推演变成实板实验前，须保留栈、向量表、故障处理代码和记录区所需权限。

记录使用的芯片修订、区域属性、访问指令与捕获状态。只把有效字段作为证据，不将一次 Fault 的截图推广成所有空指针都会产生相同故障。硬件实验结束恢复原保护配置，避免把故意故障的练习混入正常固件。
