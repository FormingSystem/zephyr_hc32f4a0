# 第3章\_从硬件机制走向RTOS：案例与推演

先读[关系与模型](P001_关系与模型.md)与[原理与实现](P002_原理与实现.md)。下面把已建立的对象放进具体输入，先预测再核对；纸面结果与真实芯片观察分别说明。

## 3.1\_比较同一批工作怎样安排

使用教学时间，暂忽略 ISR 与切换开销：显示计算需2 ms；鼠标报告在0.2 ms到达，需要0.1 ms处理；键盘报告在0.4 ms到达，需要0.1 ms处理。输入线程优先于显示线程，三者初始没有积压。

| 方案 | 唯一CPU的执行顺序 | 输入响应 |
| --- | --- | --- |
| 连续显示计算后再轮询 | 显示0—2，鼠标2—2.1，键盘2.1—2.2 | 鼠标等待1.8，键盘等待1.7 ms |
| 可抢占的事件线程 | 显示0—0.2，鼠标0.2—0.3，显示0.3—0.4，键盘0.4—0.5，显示0.5—2.2 | 理想化为到达即可开始，实机需加中断与调度延迟 |

两种方案有效 CPU 工作都是2.2 ms。第二种缩短输入排队，没有让计算量消失；显示被抢占的时间也必须从显示执行量中扣除。把显示计算拆成短小裸机状态机，同样能改善输入延迟，RTOS 额外提供保存调用现场与统一等待接口。

## 3.2\_把忙等改成阻塞

对照两种伪代码：`while (!new_report) {}` 会持续占用 CPU；`report = queue_receive_forever()` 应在队列为空时让线程进入阻塞状态。收到数据后处理一条，再回到接收；队列已有多条时则继续消费，不必等待下一 tick。

再加入容量为4的队列：若报告生产速率持续高于处理速率，RTOS 也无法避免积压。需要定义保留最新鼠标位置、保留全部按键边沿等不同策略。业务语义决定是否可以合并数据，调度不能替应用决定丢哪条。完成这套推演后，再进入 P02 选择 Zephyr 的现成内核、驱动与队列生态。
