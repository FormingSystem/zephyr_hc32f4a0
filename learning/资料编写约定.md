# 第1章\_Markdown\_与\_PPT\_的编写和同步约定

`learning` 的正文应让读者在明确前置条件后，独立阅读、操作并判断结果；PPT 应让读者跟随视频理解关键过程，做完实验后快速复习。两种材料对应同一期，内容深度不同。不能用“视频里演示过”或“PPT 有截图”省略 Markdown 的必要步骤，也不把正文整页复制到幻灯片。

## 1.1\_文件命名与对应关系

章节统一为 `P001_主题.md`，按专题内顺序编号，公共准备为 `P000_实验准备.md`。同一期 PPT 与 Markdown 使用相同文件主名，例如 `P003_SDK准备与编译器选型_Windows.md` 对应 `slides/P003_SDK准备与编译器选型_Windows.pptx`。三位编号可以容纳超过 100 期的资料。核心主题拆分后直接递增主序号，例如 P002、P003、P004；后续章节顺延，不使用 P002_01 这种二级文件编号。每章独立使用章号和小节号，MD/PPT、封面、页内引用、命令索引和重建入口一起更新。每模块写清前置输入、当前任务、完成产物与后续入口。

平台流程确实不同时使用 `_Windows`、`_Linux` 后缀，仍放在同一专题目录。共用原理章节不强制加平台后缀，但每段可执行命令必须标出实际终端。专题目录保持稳定，不因期数增减反复更名。章节号与视频期数按专题对应，不把不同专题的 P001 当作同一章。

`README.md` 是入口，`大纲.md` 组织阅读顺序；`labs/` 保存配套材料，`assets/` 保存正文图片与 Mermaid 源图，`slides/` 保存演示文稿。`DESIGN.md`、`REVIEW.md`、`VALIDATION.md` 和 `slides/*/src` 是维护材料，不承担读者实验的前置步骤。

已有稳定文档 ID 保持不变。元信息用 `engineering` 表示操作章节，`track` 表示大纲，`reference` 表示查阅材料；状态描述资料维护情况，不能代替安装、编译、模拟和实板的实际验证记录。

默认使用 UCRT64 Bash，保持 Linux 命令习惯。只有 Zephyr 官方明确采用 PowerShell 的 Windows 下载/安装步骤，以及 setup.cmd 等 Windows 专用脚本和其 Windows 管理操作，才切换到 PowerShell。普通下载、摘要校验、解压、版本检查、Python/venv 与 CMake 工程操作仍用 UCRT64，不能仅因调用 Windows 可执行程序就整段改成 PowerShell。Ubuntu 22.04 使用原生 Linux Bash。每段标明终端和目录，切换时重新进入目录，临时变量不互相继承。

## 1.2\_Markdown\_承担完整讲解与实验

章节先接住前文已经建立的认识，再说明本章的任务和完成后能观察到的结果。对连续教材，清楚写出依赖哪一章、需要保留什么产物即可；不要求每章从安装操作系统开始重复。

| 阅读时遇到的环节 | 正文应当提供的信息 |
| --- | --- |
| 开始操作 | 当前系统与终端、工作目录、已完成的前提、本章创建的文件 |
| 新概念或工具 | 先说明解决什么问题，再解释名称、职责、输入和输出 |
| 一段命令或配置 | 可复制的完整操作单元，紧接含义、预期输出与下一步依据 |
| 路径或变量 | 谁定义、在哪定义、指向什么；每次复用自定变量时提示来源与用途 |
| 一个阶段结束 | 怎样证明成功；出现什么现象应先停下检查 |
| 中断或失败 | 恢复工作目录和环境的步骤，错误原因、检查入口和恢复办法 |
| 章末交接 | 留给下一章的状态、关键复习问题和未执行的验证范围 |

Markdown 保留比 PPT 更完整的安装分支、版本依据、输出解释、排错过程和恢复命令。完整命令保存在正文，不能让读者拼接几张 PPT 截图才能执行。长命令按不可拆的操作单元分块，避免一次粘贴修改大量状态。

教学截图可以来自 PPT：抽取原图到 assets，并在正文说明图中的哪个对象是观察重点、版本或路径哪些只是示例。关键命令仍用文本提供。用户批注中的问题应在实际正文解决，原意见和落实位置保留在审阅记录。

## 1.3\_PPT\_承担重点讲解与复习

每页围绕一个需要解释的关系或关键动作组织内容，例如“芯片身份怎样落到 board/SoC”“清单怎样决定下载修订”“为什么激活 venv 后解释器路径变化”。图解、对照表和必要命令一起帮助读者理解；精细化是把一个问题讲透，不是缩小字体塞入更多正文。

PPT 与视频按 Markdown 的阶段推进，页面能定位到对应小节。Markdown 的“视频与复习对照”说明各组页面对应的实验阶段，不以易漂移的单页号承担唯一导航。页面增删后同步页码范围。

PPT 保留操作位置、必要前提和关键命令，完整安装分支、较长源码与排错表留在 Markdown。命令使用一个连续可编辑的代码区，按完整操作单元分拆；长命令提供明确可打开复制的纯文本文件及正文定位，不能以截图、碎片文本或省略号替代。每个文件首次使用时说明官方原有、外部下载、教程随附、自行创建或工具生成；下载阶段解释官方依据，优先采用官方支持的依赖工具，并讲清工具生成的目录与工程接入；网页用于查证，手动路线仅作为必要的补充。备注补充讲解线索和依据，不能只在备注里藏着正文执行所需的前提。屏幕上的截图与命令可以帮助复习，但都不能冒充实际验证结果。

### 1.3.1\_颜色用于区分对象

保留用户已有的语义配色，重排、重写和同步重建都不能把这些标注抹成单色。浅色 PPT 使用以下分类，正文、代码和图示中的同类对象保持一致：

| 对象 | 颜色 | 示例 |
| --- | --- | --- |
| 变量、参数与配置字段 | 深橙色 `#B84E00` | `BOARD`、`ZEPHYR_SDK_INSTALL_DIR`、`-D`、`cmake-ext` |
| 文件与路径 | 蓝色 `#0070C0` | `CMakeLists.txt`、`module.yml`、`samples/hello_world` |
| 接口函数 | 深绿色 `#087B3D` | `find_package`、`target_sources`、`zephyr_get` |
| 终端命令 | 紫色 `#A02B93` | `cmake`、`west`、`export` |

首次使用时提供小型图例，正文保持深色，只突出需要辨认的对象。按语境判断：`cmake` 可以指目录，也可以指终端程序；`Kconfig` 可以指配置系统，也可以指具体文件，不能仅凭同名批量上色。颜色不能替代文字说明，灰度阅读时也应知道对象是什么。

代码在原有连续文本框内按文字片段着色，不拆成零散文本框，不改变换行、引号和注释。上述色值用于浅色 PPT 画布，深色画布需成对核对前景与背景。Markdown 使用行内代码及带语言的代码块，跟随阅读器语法高亮，不插入固定 HTML 颜色；Mermaid 按下节同时检查明暗主题。

### 1.3.2\_行距与段间留白

PPT 正文、代码、表格和图内多行文字采用 1.2 倍行距，使用 PowerPoint 的“多倍 1.2”段落属性。段间留白单独设置，正文逻辑段落可从 12 pt 段后距起按页面校准，不插入空白段落撑版。代码的空行、缩进和换行必须保留。

调整后检查文字边界、文本框高度、图中节点留白、表格行高和页脚区域。保留现有字号与语义配色，需要时重排或按完整关系拆页，不能通过压回单倍行距或缩字号解决拥挤。封面、标题、单行阶段标签、来源链接、署名与页码保留系列版式。Markdown 行距由阅读器控制，不插入 HTML 或改全局主题来模拟 PPT 行距。

## 1.4\_用\_Mermaid\_标出阶段和关系

长实验先给一张阶段图，在阶段切换时突出当前位置；图中的名称、正文小节和 PPT 的阶段标记保持一致。已有连贯阶段图继续使用，不为满足形式在每段插一张新图。

```mermaid
flowchart LR
    A["阅读 MD<br/>理解前提与依据"] --> B["按 MD 做实验<br/>执行与观察"]
    B --> C["检查结果<br/>解释或排错"]
    C --> D["看 PPT 与视频<br/>复盘关键关系"]
    D --> E["回到 MD<br/>查细节并继续实验"]
```

图是另一种解释方式。箭头应表达状态变化、操作顺序或依赖关系，正文解释关键转折；不要用图取代必需的命令和因果说明。进入不同操作系统的分支前，先明确平台身份。

思维导图说明组成关系，流程图说明处理顺序，时序图说明谁调用谁、传入什么与返回什么。图前交代要回答的问题，图后解释关键连接；PPT 与 MD 使用一致的阶段和术语。不要把同一 CMake 进程内执行的脚本画成独立服务，也不要用图替代必要的因果解释。

正文 Mermaid 的背景和文字跟随阅读器主题。当前阶段用 `stroke` 和 `stroke-width` 强调，避免在 `style` 或 `classDef current` 中固定 `fill`、`color`，以免与阅读器的明暗主题混搭。配色修改后同时检查浅色和暗色渲染，尤其是高亮节点、HTML 标签与普通 SVG 文字。PPT 中固定画布的图片单独按其背景检查，不用正文主题规则替换它的完整配色。 Mermaid 思维导图默认分支色若不能保证文字对比度，可成对设置该图全部分支的填充与标签颜色，并在明暗背景下复核；不能只固定浅色底而让字体继续跟随暗主题。

## 1.5\_主线、参考与验证分开说明

工程准备专题是从零实验主线；`download_zephyr` 保留下载方案、机制对照和较早讨论，仍标为参考，尚未核验的方案不能包装成已经可执行的主线。内容较长不构成删减依据；必要时拆成有明确阅读目的的小节，保留原有信息与实验条件。

官方要求从所选源码、官方文档和发行记录取得；教程选择的 Python/west 补丁号、实验目录和 HAL 移植基线明确标为教程约定。更新 Zephyr 后重新查询依赖，而不是复制旧截图中的版本。

本地链接和语法检查只证明资料结构可用；包完整、工具可运行、配置成功、固件编译成功、模拟运行和实板运行分别记录。文档改动不得将历史验证结果自动升级成新环境实测通过。

## 1.6\_修改后同步哪些资料

正文改名或移动时，同时更新章节导航、大纲、学习中心、实验材料 README、PPT 正文及备注中的路径，以及可重建的 PPT 包源码。PPT 有用户手工修改时先保存并同步原生包，再改动，保留图片和批注。

维护检查在文档仓库根执行 `python learning/check_docs.py`；正式实验命令仍在正文指定的 G 盘实验目录执行。PPT 验证还包括页面渲染、正文与备注检查、媒体保留及同步重建。每次交付更新验证记录，Git 更新/同步策略继续按用户后续决定处理。
