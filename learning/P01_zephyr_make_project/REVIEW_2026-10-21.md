# 工程入门文档评审与改版记录

本次先评审、再修改 Markdown 和配套命令。PPT 按用户要求保留旧版，待正文审核后另行同步。编辑模式为内容重写，不是只调整空行和标题。修改基线为干净工作区提交 `2a5ad0c7133ce529ea703958f35e9b2293de760b`，原正文、截图、命令及批注可据此回查；不修改实验源码和硬件实现。

## 1. 评审发现

这组问题的共同原因是按材料和工具名称排列，而没有按读者已经获得的认识排列。分类本身不是错误；在当前问题尚未需要它时展开分类，才会打断推理。

## 2. 用户反馈与处理范围

1. “分为 linux、Windows PowerShell、UCRT；有 Git 历史和只能 ZIP 两种情况”：整理为三种主机终端乘两种源码获取路线。Git 元数据、GitHub 连通性、west 工作区是否存在分别核对，不能互相推定。
2. “各种莫名其妙的类型分辨，很多无关联的解释”：主线以源码、应用、目标、构建产物为连续对象；厂商包来源、驱动实现和高级接口留在负责该问题的后续章节。
3. “没有先做工程类型布局讲解；还不知道选应用、芯片、组合型号”：在所有安装和构建之前建立布局、板目标与端到端过程，随后用同一个 hello_world 实验落实。
4. 后续确认：“先完成 Markdown 和配套命令，PPT 标明旧版”；“我审核没有问题再同步 PPT”。本轮不重建、不改写 PPT 正文及其原生制作源。

## 3. 本次故障记录的证据裁决

附件记录用户在 UCRT64、ZIP 源码、Windows Python 环境下为 `mps2/an386` 生成了 ELF。本次只把它作为用户提供的构建记录，不冒称维护者重新实测了该机器。

- 407 是代理认证失败；其后的包版本匹配报错不足以证明 west 版本不存在。是否取消代理取决于网络是否支持直连，不能教读者一律删代理。
- `.venv` 提示符不能证明 CMake 使用了该 Python；检查实际解释器并在配置时固定它。
- 把 `$(cygpath ...)` 先赋给变量不会改变同一字符串的路径语义。真正需要核对的是 cmake 的运行时、参数内容、子进程收到的路径及缓存；`-a` 只负责绝对化，不能修复错用 MSYS CMake。
- 模块目录存在与本次模块发现成功不同；检查 `zephyr_modules.txt` 与 `Kconfig/Kconfig.modules`。不能关闭 Kconfig 警告掩盖缺少的模块定义。
- 附件使用了两处不同根目录的 CMSIS。教材必须允许明确填写既有位置，但新准备默认使用工作区下统一的模块位置；不把临时混合布局推广为要求。
- 清单声明两个 CMSIS 仓库不代表所有 Cortex-M 构建都使用两者的头文件。示例显式提供二者作为固定清单配套输入，实际启用情况再由生成配置和编译命令确认。
- DTC 安装及随后被检测到有记录；DTC 是否是某构建的致命前提须看配置行为，不能仅凭 Could NOT find 判定。
- Ccache 总表“已安装”与后文“无完整安装证据”矛盾，采用后者：安装状态待核验；它是可选缓存。
- Git 乱码与无 .git 引起的版本查询失败分别说明；仅补 locale 不能宣称已修好原生 Git 编码。
- 136/136、内存占用和工具补丁号只属于附件现场，不是所有版本的验收常量；ELF 生成也不是 HC32 实板验证。

## 4. 改版蓝图

主线：工程布局与构建全景 → 按主机准备源码 → 主机工具与 Python → SDK → 匹配的源码模块 → 原生 CMake → 选择应用与硬件目标并构建 → west 构建入口 → 驱动模型 → 输入发现 → 缓存和故障定位 → 普通组件 → HC32 外部模块 → 新增板与芯片实验。

认识依赖：先建立应用与 Zephyr 源码的关系，再解释 workspace 和模块；先知道板承载芯片、芯片包含处理器核，再解释 BOARD 限定；先知道配置生成规则、编译生成镜像，再解释缓存；多镜像在单镜像闭环后出现。Git/ZIP 是源码来源，Linux/PowerShell/UCRT 是运行环境，应用在何处是目录布局，SDK GNU/LLVM 是工具链选择，四者不混成一张“工程类型”表。

保留原有深入章节的有效内容与实验，调整到依赖已建立的位置。各章承担的新增认识、文件迁移、检查结果与未执行项在本目录 DESIGN.md、VALIDATION.md 中更新。原有截图和旧版 PPT 只作为历史参考，不沿用其页码宣称与新正文同步。
