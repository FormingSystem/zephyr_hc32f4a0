# 第6章\_源码依赖与离线准备

源码和编译工具已经就位，现在补齐源码之外的依赖。本章始终面向同一个组合：`samples/hello_world + mps2/an386`。不先讨论所有芯片和厂商库，只解决“这次缺什么、怎样得到匹配版本、怎样让构建找到它”。

本例的 Cortex-M 支持需要 **CMSIS-Core**，即 Arm 的 CMSIS 标准接口体系中面向处理器内核的头文件与接口。Zephyr 本版通过 `cmsis_6` 模块提供所需 Core 头。`modules/cmsis_6` 是主源码里的接入规则，工作区 `modules/hal/cmsis_6` 才是外部源码；两处目录名字相似，职责不同。当前规则可查 `modules/cmsis_6/CMakeLists.txt` 与 `soc/arm/mps2/soc.h`。本次不需要华大 HAL，HC32 接入留到 P014。

本例准备 `cmsis` 和 `cmsis_6` 两个配套项目，各自版本取自当前清单。Core 头文件来自其中的 cmsis_6，完整依赖准备仍包含二者；后面的自动获取命令、手动归档列表和 P008 的模块参数使用同一组材料。

P002 区分了硬件职责和源码包装：`arch/`、`soc/`、`boards/` 说明支持代码做什么，module 说明一包源码怎样接入。当前 MPS2 的架构、SoC、板和串口驱动支持已在主仓，仍会引用主仓外的 CMSIS 头文件。因此取得一个板目录，并不等于已经取得它依赖的全部源码；反过来，取得 CMSIS 或厂商 HAL 也不会自动补齐尚不存在的板和 SoC 支持。

Zephyr 把内核与通用构建规则放在主仓，把一部分外部库放在独立仓库。不同 Zephyr 修订可能要求不同的外部库修订，因此“有一个名叫 CMSIS 的文件夹”还不能证明配套。随源码提供的 `west.yml` 就记录这份源码预期使用的项目、版本和位置；它是依赖清单，不是已经下载好的依赖本身。

配套模块可以用 Git/west 按清单取得，也可以从归档取得，分别见 6.1 和 6.2。选择取决于已有材料和允许访问的来源：公司禁止连接 GitHub 时，仍可能允许内部 Git；一个来自 GitHub 的旧克隆，也可以在断网后继续本地构建。先判断缺少什么，再决定是否需要获取：

| 当前材料与访问条件 | 怎样使用本章 |
| --- | --- |
| 可以访问清单中的官方仓库，且缺少配套模块 | 按 6.1 查询清单，再从其中的地址取得模块 |
| 只允许内部 Git 或内部制品库 | 按 6.1 核对公司清单及内部仓库；归档交付按 6.2 核对，不能直接执行指向 GitHub 的下载 |
| 主源码、配套模块和主机工具已经齐全 | 直接做 6.3 的本地核验，随后进入 P008；不要求先 init 或 update |
| 完全离线，而且主机工具或 Python 包还不齐 | 除源码外，还要按 6.4 准备对应主机的安装材料 |

下面先解释 west 在这个过程中负责什么，再使用已有命令。P009 会在第一次构建成功后继续展开它的扩展与构建机制；本章把准备依赖所需的背景讲清，不要求读者先跳过去学完整个工具。

## 6.1\_Git 路线：让当前清单管理模块

如果希望由 west 管理依赖，就需要把当前源码与一份具体清单关联起来。本节先建立这个关系，再区分已有工作区和新初始化，最后只在确有需要时取得模块。已经有完整材料、准备直接指定模块路径的读者，可以理解这一关系后转到 6.3 核验。

### 6.1.1\_west 为什么要先知道工作区和清单

Git 管理一个仓库的版本；本例却需要把 Zephyr、cmsis 和 cmsis_6 按一组配套修订放在一起。west 是安装在项目 Python 环境里的管理工具，它读取清单，再调用 Git 取得各个项目。它不属于 GitHub，也不要求仓库一定托管在 GitHub；实际访问的地址由清单决定。

west 需要先知道“这次管理哪一组项目”。它用父目录里的 `.west/config` 标识一个工作区，配置中的 `manifest.path` 指向保存清单的目录，`manifest.file` 指定文件名，默认是 `west.yml`。保存这份文件的仓库称为**清单仓库（manifest repository）**；官方通常让 Zephyr 主仓兼任这个角色，公司也可以用独立的仓库维护清单。

由此可以把几个动作接起来：`west init` 建立工作区并选定清单；`west list` 读取清单，显示项目要求；`west update` 才根据要求取得或切换项目源码。稍后 CMake 还可以查询 west，找到这些项目在本机的位置，再检查其中的模块声明。**清单中的项目是仓库管理对象，Zephyr 模块是构建接入对象**；下载一个项目不等于它的全部代码都会进入当前固件。

先确认 west 使用的是哪份清单。west 从当前目录向上寻找工作区标记；电脑上有另一份 `.west` 时，短命令可能读到别的工作区。因此已有目录先查询，不无条件重新初始化。下面的查询只读取本地配置，不下载依赖。

以下两段按终端选择一个。Linux 使用其准备章的父目录 venv，UCRT64 使用源码根 venv：

```bash
# Linux Bash：~/zephyrproject/zephyr；或 UCRT64：/g/zephyr_practice/zephyr-main。
# 先在对应准备章激活 .venv，再进入该源码根。
python -m west topdir
python -m west config manifest.path
python -m west config manifest.file
```

```powershell
# Windows PowerShell；源码根；使用项目解释器，不依赖激活策略。
Set-Location -LiteralPath 'G:\zephyr_practice\zephyr-main'
& .\.venv\Scripts\python.exe -m west topdir
& .\.venv\Scripts\python.exe -m west config manifest.path
& .\.venv\Scripts\python.exe -m west config manifest.file
```

**对应所选终端查询块第 3—5 行：** `west topdir` 输出工作区根，`west config manifest.path` 输出清单仓库相对工作区根的目录，`west config manifest.file` 输出清单文件名。沿用官方清单时，第一项应为源码的父目录，第二项应为当前 `zephyr` 或 `zephyr-main`。公司独立清单仓库可能有另一个目录名，应与公司的工作区布局核对，不要求强行改成这两个名字。未显式设置 `manifest.file` 时，查询可能无值，默认文件名为 `west.yml`。若 topdir 已指向其他有效工作区，先检查它的配置，不删除 `.west`，也不覆盖配置来让输出“看起来一致”。

### 6.1.2\_初始化使用哪份清单，和清单从哪里下载是两件事

准备章中 Linux 从官方地址建立新工作区，Windows 分支则先取得主源码。走到这里，读者手里的材料因此可能不同：有人已经有 `.west/config`，有人只有包含 `west.yml` 的源码目录。前者复用已有工作区；后者若要使用 west 管理依赖，可以围绕这份本地清单建立工作区。

“自己做 init”并不意味着必须自己编写清单；“沿用官方清单”也不意味着每次初始化都要连接 GitHub。下面几种写法只说明参数关系，不是要依次执行的命令：

| 手里的清单来自哪里 | 初始化的含义 | 此时是否需要访问仓库服务器 |
| --- | --- | --- |
| 主源码已在本机，使用它自带的 west.yml | 在源码根使用 `west init -l .`；`-l` 表示使用本地清单目录 | 这一步不克隆清单仓库 |
| 公司已交付本地清单，或自己已经编写清单 | 用 `west init -l 清单目录`；文件名不是 west.yml 时另加 `--mf 文件名` | 这一步不克隆清单仓库，但文件必须已经存在 |
| 从官方或公司 Git 取得一份新的清单仓库 | 用 `west init -m 仓库地址 --mr 清单仓库修订 新工作区` | 需要访问 `-m` 指定的服务器；内部地址可以不经过 GitHub |

`--mr` 选择的是**清单仓库自身**的修订，模块修订仍由该版本清单的 `revision` 决定。省略 `-m` 的远程初始化默认使用官方 GitHub 仓库，所以不能在禁止 GitHub 的环境中照抄一条不带地址的远程 init。`-l` 也不是“离线下载”开关：它只省去克隆清单仓库，后续缺失模块仍要有可用来源。两种初始化都需要 west 及其要求的 Git 程序可用。

**仅在尚未初始化、当前源码是要使用的清单仓库时**，选择对应命令：

```bash
# Linux/UCRT64 Bash；当前源码根，已激活项目 .venv；确认上方没有可复用工作区。
python -m west init -l .
```

```powershell
# Windows PowerShell；G:\zephyr_practice\zephyr-main；仅未初始化时执行。
& .\.venv\Scripts\python.exe -m west init -l .
if ($LASTEXITCODE -ne 0) { throw '初始化失败；检查已有工作区，不继续 update' }
```

`-l` 复用本地清单仓库，创建父级的 west 配置；它不会替你下载模块。成功后重新查询 topdir、manifest.path 和 manifest.file。看到 Initialized 只表示这组项目的管理入口建立了，不表示 CMSIS、SDK 或 Python 依赖已经齐全。

公司只允许内部 Git 时，先看公司是否已经提供了适配内部地址的清单。有就复用它；没有时，已经齐全的本地材料仍可走 6.3 和 P008 的显式模块构建，不必为了编译临时设计一套公司清单。若要长期用 west 管理内部仓库，清单维护者需要为每个项目明确内部 URL、配套修订和本地路径，并确认服务器确实保存了对应提交。

这里尤其容易混淆的是：**把 Zephyr 主仓克隆地址改成内部地址，不会自动改掉它的 west.yml 中的模块地址。** 如果公司清单用 `import` 导入另一个仓库中的清单，导入的项目还会保留其各自的来源规则；顶层写了一个内部 remote，不等于所有导入项目都变成内部仓库。现阶段先核对公司交付的完整依赖来源。已有导入所需的本地 Git 对象时，可以让 west 展开查询；缺少导入对象而解析失败时，应从内部来源补齐，不能把失败当成允许连接 GitHub 的理由。P009 在已有工作区的基础上再解释清单复用、自己维护和导入之间的关系。

初始化参数的完整说明见本仓库官方译文[内置命令](../zephyr_docs/west/P011_内置命令.md)的 12.1 节 west init，清单字段和导入规则见[west 清单文件](../zephyr_docs/west/P013_west清单文件.md)。这里使用的是同一套机制，额外说明它怎样对应本专题的现有材料。

### 6.1.3\_先看项目来源，再决定是否获取

工作区正确以后，先只读查看本例的两个项目。这一步把“打算访问什么”显示出来；不要把查询和下载连成一条无条件执行的命令。

```bash
# Linux/UCRT64 Bash；同一源码根，项目 .venv 已激活；只读查询。
python -m west list cmsis cmsis_6 -f '{name} {url} {revision} {abspath}'
```

```powershell
# Windows PowerShell；G:\zephyr_practice\zephyr-main；只读查询。
& .\.venv\Scripts\python.exe -m west list cmsis cmsis_6 -f '{name} {url} {revision} {abspath}'
if ($LASTEXITCODE -ne 0) { throw '当前清单未解析成功，先检查清单和源码版本' }
```

**对应两种终端的 `list -f` 行：** 输出每行按 `{name} {url} {revision} {abspath}` 排列，依次是项目名、实际仓库地址、清单修订、在本机的绝对路径。先用第一列区分 `cmsis` 和 `cmsis_6`，再核对同一行的后三项。使用官方清单时通常会看到 GitHub 地址；使用公司清单时应看到对应的内部来源。已有材料版本匹配就直接进入 6.3。只有确实需要获取或调整版本，且这些地址允许访问、所需提交可取得时，才执行下一组更新命令；更新前先保存并审查模块的本地修改。

```bash
# Linux/UCRT64 Bash；同一源码根，项目 .venv 已激活。
# 已核对上一组 list 输出；仅在需要取得模块且允许访问这些地址时执行。
python -m west update cmsis cmsis_6
```

```powershell
# Windows PowerShell；G:\zephyr_practice\zephyr-main；使用项目解释器。
# 已核对上一组 list 输出；仅在需要取得模块且允许访问这些地址时执行。
& .\.venv\Scripts\python.exe -m west update cmsis cmsis_6
if ($LASTEXITCODE -ne 0) { throw '模块获取失败，保留日志，按网络或 Git 错误处理' }
```

`update` 按清单指定的修订取得源码，不等于更新到各模块最新分支，也不是每次编译前的必做动作。这里准备 `cmsis` 与 `cmsis_6` 两个配套仓库；本次 Cortex-M Core 的实际提供者仍由当前 Zephyr 规则确定。准备源码、发现模块和选入某份代码是三个阶段，不能从准备了两个仓库推断任意板都必须编译二者的全部代码。若当前清单没有其中某项，先核对该版本的模块规则，再调整准备列表。

下载后可对每个有 Git 元数据的模块执行 `git -C 模块目录 rev-parse HEAD`。清单固定提交号时，直接核对；使用标签或分支时，要核对它实际解析的提交。内部镜像若保留原提交，可与上游清单直接对照；公司若重新导入快照、提交号已经改变，则需要其交付记录说明对应的上游修订和补丁，不能仅凭文件夹同名声称版本匹配。Git 拉取不可用但可以获得可信归档时，进入下一节；不必补全主仓完整历史。

## 6.2\_ZIP 路线：从同一份清单取得匹配归档

上一节由 west 按清单调用 Git；这一节由读者从交付包中取得同一组文件。归档可以来自允许访问的官方站点，也可以来自公司内部制品库，后者是保存源码包、工具包等交付文件的服务。主源码本身可以仍是一个内部 Git 仓库；使用模块归档并不要求把主源码也变成 ZIP。

ZIP 包里有 `west.yml`，但没有因为这个文件存在就自动下载依赖。即使不运行 west，仍可把这份清单作为版本依据。先打开**正在实验的源码**里的清单，查 `cmsis` 和 `cmsis_6`。以下是字段形状示意，不是让你新建或替换清单：

```yaml
# 只读示意；revision 必须读取当前源码，不复制占位文本。
- name: cmsis_6
  repo-path: CMSIS_6
  revision: <当前清单中的提交或标签>
  path: modules/hal/cmsis_6
```

`name` 是清单项目名；`repo-path` 是仓库名，省略时通常用 name；`revision` 是配套修订；`path` 相对工作区根。URL 有显式 `url` 就使用它，否则按项目或默认 remote 的 `url-base` 与仓库名组成。官方这两个项目的仓库分别是 `zephyrproject-rtos/cmsis` 和 `zephyrproject-rtos/CMSIS_6`。不要把 `cmsis_6` 项目名直接拼成错误的 GitHub 仓库地址。

实际操作按以下顺序完成：

1. 在浏览器打开清单对应仓库，定位到 **revision 指定的提交或标签**，再下载该修订的 ZIP。也可以通过 GitHub 的 `https://github.com/组织/仓库/archive/提交号.zip` 取得固定修订归档；不能改用不断变化的 main。
2. 不允许连接 GitHub 时，从公司内部制品库或其他获准交付渠道取得这些配套归档及来源记录；允许通过另一台联网机器准备材料的环境，可在那里取得精确归档，再按交付流程转入。内部快照须能追溯对应修订及补丁；修改 pip 或 pacman 源不能改变 Git 仓库地址。
3. 把归档解压到工作区下的 `modules/hal`。归档通常自带 `仓库名-提交号/` 这一层，将真正含 `zephyr/module.yml` 的目录命名为 `cmsis` 或 `cmsis_6`。已有同名源码时先核对，不覆盖合并。
4. 保存下载来源和修订记录。ZIP 不带 .git，之后不能用 git rev-parse 证明它的上游提交；归档名和自己计算的摘要也不能独立证明来源，只能结合可信下载记录复查。

对于尚未建立固定目录的读者，本教程建议结果如下：

```text
zephyr_practice/                  Linux 对应 ~/zephyrproject
├── zephyr-main/                  Linux 对应 zephyr；主源码 ZIP 解压
│   ├── west.yml
│   └── samples/hello_world/
└── modules/hal/                  由读者解压配套归档建立
    ├── cmsis/zephyr/module.yml
    └── cmsis_6/
        ├── zephyr/module.yml
        └── CMSIS/Core/Include/core_cm4.h
```

这条路线不需要 `.west`，也不需要给 ZIP 补 .git。构建时用 `ZEPHYR_MODULES` 明确提供模块根目录，具体命令在 P008 三种终端的 ZIP 分支中完整给出。它的值是分号分隔的路径列表，整项必须作为一个参数传递。该输入接管本次模块列表，不是“在自动列表后顺手追加两个目录”。

已有材料可以保留原来的存放位置。例如 cmsis 在 `../modules/hal/cmsis`，cmsis_6 在源码内的 `modules/hal/cmsis_6`，只要版本匹配、关键文件齐全，就在构建参数里分别填入真实根目录。下文采用同级模块目录便于新建工作区；模块发现依赖实际路径和入口文件，不要求移动已有源码来匹配示例布局。

源码内 `cmake/modules/zephyr_module.cmake` 读取 `ZEPHYR_MODULES`，调用 `scripts/zephyr_module.py` 解析模块声明，再生成模块的 CMake/Kconfig 入口。目录被发现后，功能是否启用、源文件是否编译仍取决于配置。官方依据：[Modules without west](https://docs.zephyrproject.org/latest/develop/modules.html#using-modules-without-west)，仓库原件 `doc/develop/modules.rst`。

## 6.3\_先核验文件，再让配置过程确认发现结果

现在不论哪条获取路线，都应有匹配模块。已经由公司交付完整材料的读者也从这里继续：我们要确认构建输入在本机，而不是再次下载。以下文件核验不访问 GitHub，也不要求 `.west` 或模块的 `.git` 存在；版本是否匹配仍依据上一节的清单或交付记录，不能只凭文件存在判断。

先按自己的终端验证实际文件：

```bash
# Linux/UCRT64 Bash；源码根；以下采用上方统一模块布局。
test -f ../modules/hal/cmsis/zephyr/module.yml &&
test -f ../modules/hal/cmsis_6/zephyr/module.yml &&
test -f ../modules/hal/cmsis_6/CMSIS/Core/Include/core_cm4.h &&
printf '模块入口和本例 Core 头已存在；下一步仍须验证 CMake 发现结果。\n'
```

```powershell
# Windows PowerShell；源码根；采用上方统一模块布局。
Set-Location -LiteralPath 'G:\zephyr_practice\zephyr-main'
foreach ($file in @(
    '..\modules\hal\cmsis\zephyr\module.yml',
    '..\modules\hal\cmsis_6\zephyr\module.yml',
    '..\modules\hal\cmsis_6\CMSIS\Core\Include\core_cm4.h'
)) {
    if (-not (Test-Path -LiteralPath $file -PathType Leaf)) { throw "缺少 $file" }
}
'模块入口和本例 Core 头已存在；下一步仍须验证 CMake 发现结果。'
```

若只看到 `cmsis_6/CMSIS_6-提交号/zephyr/module.yml`，说明多套了一层解压目录；模块根应当是里面那一层。文件缺失时返回允许访问的依赖来源和解压步骤，不通过新建一个空 module.yml 让检查通过。

文件齐全后，P008 有两种模块发现方式。已有有效 west 工作区、清单及其导入内容均可在本地解析时，选 `route=west`，CMake 向 west 查询本地项目位置；它不会因此自动执行 update。只有源码目录，或希望明确指定模块时，选该章已有的 `route=zip`，由 `ZEPHYR_MODULES` 传入真实路径。这个教程变量沿用归档路线的名字，**内部 Git 克隆得到的模块同样可以使用它**，不检查有没有 Git 历史。

这就把准备与编译接起来了：先取得配套文件，再让 CMake 找到它们，最后编译。本例材料齐全时，这两种发现方式都可以不连接 GitHub；不把 init、update 或在线安装当作每次构建的前置动作。其他应用若在自己的构建脚本中另有下载行为，需要另外检查，不能把本例结论推广到所有工程。

当 P008 扩展到整板的多个芯片或镜像时，要对每个应用重复依赖核对，再准备它们的完整集合。两个 CMSIS 模块只是本次起点，新增芯片可能还需要厂商 HAL，加入引导程序也可能引入新的源码项目和工具。sysbuild 负责组织构建，不能替手动归档路线补齐这些缺件。

到这里先完成输入文件核验，还没有要求生成构建结果。后续执行 P008 的 CMake 配置并成功生成后，再到那条命令 `-B` 指定的目录读取 `zephyr_modules.txt`、`Kconfig/Kconfig.modules` 和 `compile_commands.json`。例如 UCRT64 的 `route=zip` 使用 `/g/zephyr_practice/zephyr-main/build/learning-tools/first-ucrt-zip`；前两份文件用于确认模块路径与配置入口，第三份用于核对编译命令中的头文件目录。其他终端和路线从各自 `-B` 目录读取同名记录，具体选择见 [P008 的产物检查](P008_选择应用与硬件目标并构建.md#firmware-formats)。

## 6.4\_完全离线还需要准备哪些东西

“不能连接 GitHub”“只能取得 ZIP”和“完全离线”不是相同条件。公司可能允许内部 Git、内部 Python 包索引和 SDK 制品库；也可能只交付一次完整安装材料。这几类服务提供的东西不同：内部 Git 能提供源码，不会自动提供 Python 包或编译工具。已有工具和包通过前面章节的检查，就不必为了沿着教程阅读而重装；确实缺少时再选择允许使用的安装来源。

完全离线的电脑必须提前带齐这些主机依赖，不能靠一条 pip install 或 Minimal SDK 的在线补装命令完成准备。下面的收集操作在允许联网的准备机上执行，离线机只使用后面的本地安装命令。

**步骤一，在联网准备机收集包。** 这台机器须与离线目标机使用相同操作系统及 Python 版本/架构，才能收集与当前源码要求匹配的 wheel 包。以下命令由项目 Python 执行，因此不另教 Python 语言；它只是运行 pip 这一包管理工具：

```bash
# 联网 Linux/UCRT64 Bash；当前源码根，匹配目标离线机的项目 venv 已激活。
# wheelhouse 为本次创建的包归档目录；Windows 只能拿匹配 Windows 的 wheel。
python -m pip download --only-binary=:all: --dest wheelhouse \
  -r scripts/requirements-base.txt "west==1.5.0"
```

```powershell
# 联网 Windows PowerShell；当前源码根，使用与离线机匹配的 Windows Python。
& .\.venv\Scripts\python.exe -m pip download --only-binary=:all: --dest wheelhouse -r scripts/requirements-base.txt 'west==1.5.0'
if ($LASTEXITCODE -ne 0) { throw '离线包集未准备完整；不要把部分下载当成成功' }
```

**对应两种终端的 `pip download` 命令：** `--dest wheelhouse` 指定收集目录，`--only-binary=:all:` 只接受 wheel 包；`-r scripts/requirements-base.txt` 读取这份源码的基础依赖，`west==1.5.0` 固定教程工具版本。若某个依赖没有匹配 wheel，命令会停止；需要在匹配环境制作 wheel 并验证，不能删掉依赖强行凑齐。

**步骤二，在离线目标机安装包。** 把完整 `wheelhouse` 转移到离线源码根，在目标机创建并使用自己的项目 venv，再按终端选择下面一块：

```bash
# 离线 Linux/UCRT64 Bash；源码根，项目 venv 已激活，wheelhouse 已转入。
python -m pip install --no-index --find-links=wheelhouse \
  -r scripts/requirements-base.txt "west==1.5.0" &&
python -m pip check
```

```powershell
# 离线 Windows PowerShell；源码根，wheelhouse 已转入。
& .\.venv\Scripts\python.exe -m pip install --no-index --find-links=wheelhouse -r scripts/requirements-base.txt 'west==1.5.0'
if ($LASTEXITCODE -ne 0) { throw '离线依赖安装失败' }
& .\.venv\Scripts\python.exe -m pip check
if ($LASTEXITCODE -ne 0) { throw '依赖关系检查失败' }
```

**对应本地安装块的 `pip install` 行：** `--no-index` 禁止访问包索引，`--find-links wheelhouse` 指定刚转入的本地目录；后面的 `pip check` 应报告 `No broken requirements found.`。venv 本身不跨机器直接复制。这里是本次基础构建依赖，其他应用或模块需要的 Python requirements 要一起纳入收集。SDK 应取得匹配主机的完整 GNU 包，或 Minimal 包加同版目标工具链归档；主机 CMake、Ninja、DTC 等也要有可用安装来源。

到这里，下载、版本核对和模块接入的关系已经清楚。先读 [P007 的配置与构建模型](P007_原生CMake与目标模型.md)，再到 [P008](P008_选择应用与硬件目标并构建.md)执行完整构建；工具模型已熟悉的读者可直接进入 P008。CMSIS 历史、厂商包与旧版 Git 兼容问题保留在[深入参考](reference/CMSIS来源与历史排错.md)，不是第一次构建的前置阅读。
