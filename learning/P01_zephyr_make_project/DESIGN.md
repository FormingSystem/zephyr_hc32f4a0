# 第1章\_Zephyr 工程入门专题设计

本文件规定专题的读者起点、章节分工和维护边界。只保留现行设计；章节入口见[大纲](大纲.md)，检查结果见[验证记录](VALIDATION.md)，不在这里追加逐轮修改日志。

## 1.1\_读者起点与完成目标

读者已有 C/C++ 和嵌入式开发基础，但尚未掌握 Zephyr 的工程组织、依赖管理和构建规则。专题从“为什么选择 Zephyr”进入，逐步到达“能够组织并维护自己的应用与硬件支持”，不要求读者先懂 west、CMake 或设备树。

贯穿实践先使用官方 `hello_world` 应用与 `mps2/an386` 目标，建立可复查的构建基线，再加入普通模块、新增板和 HC32 适配。已有目标用于分离环境问题与移植问题，不能用它的构建成功替代 HC32 实板验证。

读完后，读者应能根据项目需求判断选型条件，定位应用和硬件支持文件，按允许的来源准备配套依赖，选择应用与目标完成构建，找到实际产物，并能区分配置、编译、模拟运行和实板验证各自证明了什么。

## 1.2\_章节安排与承接关系

章节按读者需要作出的判断推进。前章建立后章的必要认识，后章用文件、操作或结果兑现前章的关系；详细目录只在大纲维护。

| 阅读阶段 | 章节 | 本阶段完成的认识与实践 | 这样安排的原因 |
| --- | --- | --- | --- |
| 决定是否采用 | P001 | 认识实时操作系统、Zephyr 的收益与采用成本 | 先理解选择理由，再投入环境准备 |
| 建立工程全景 | P002 | 区分应用、架构、芯片、板、驱动、模块和构建输出 | 先知道对象及其职责，再执行配置命令 |
| 准备可用材料 | P003—P006 | 选择环境，准备主机工具、Python、SDK 和源码依赖 | 将工具安装、依赖取得与工程发现分开核验 |
| 完成首次构建 | P007—P008 | 从普通 CMake 目标进入 Zephyr，选择应用与硬件，定位单应用及系统构建产物 | 先建立通用构建过程，再理解 Zephyr 的输入与组合 |
| 理解 west 构建入口 | P009 | 对照同一工作区和应用，解释扩展加载及构建调用 | 已见过底层过程后，再理解工具怎样组织它 |
| 追踪配置与排错 | P010—P012 | 从目标找到源文件，追踪驱动和输入发现，按缓存与失败阶段定位问题 | 将已有构建结果作为证据，避免孤立罗列机制 |
| 扩展自己的工程 | P013—P015 | 先接入普通模块，再接入厂商源码与适配，最后新增板和芯片支持 | 先验证模块接入，再增加硬件适配的复杂度 |

west 的完整讲解放在 P009，但不能让前面的命令成为黑盒。P002 先说明它为何管理多个仓库；P003/P004 区分安装工具与取得源码；P006 就地解释清单、初始化和依赖获取。P009 再从已经使用过的文件展开机制，不要求读者提前跨章补齐第一条命令的背景。

## 1.3\_环境路线与内容边界

环境、网络和源码形态是不同选择条件，分别交代，再组合成可执行路线。不能把“有 Git 历史”当成“可以连接 GitHub”，也不能把“不能连接 GitHub”当成“不能使用 Git 或 west”。

| 选择条件 | 正文组织方式 |
| --- | --- |
| 主机系统与终端 | P003 分 Linux Bash、Windows PowerShell、Windows UCRT64 Bash 三篇；P004 补齐 UCRT64 的主机工具与 Python，P005 安装 Windows SDK，Linux 在自己的环境章完成对应准备 |
| 允许访问的来源 | P006 区分官方仓库、内部 Git/制品库与完全离线材料；已有材料先核验，不无条件重复下载 |
| 源码的取得形态 | Git 克隆与源码归档都要核对配套修订和模块；不以恢复 Git 历史作为本地编译的前提 |
| 构建入口 | P008 先以直接 CMake 说明输入与产物，P009 用 west 对照同一过程；构建入口与联网下载能力分别解释 |

三种环境的首次构建在 P008 汇合，后续深入实验默认采用明确标注的 UCRT64 路线。终端命令使用对应的路径语法；跨到 Windows 原生程序时，在交接处解释路径转换与读取者。实验目录标识不随章节编号迁移。

组件关系统一按职责解释：`arch/` 提供 CPU 架构共用支持，`soc/` 接入具体芯片或处理器系统，`boards/` 描述板级资源并提供相关工具配置。启动和链接可能跨层协作；驱动与厂商 HAL/DDL 各有职责；模块是源码包装与接入方式，不是另一层硬件。P002 建立关系，P010 用实际文件验证，P014/P015 再说明新增与复用范围。

## 1.4\_正文写法与篇幅安排

每个操作先交代正在处理哪份工程、对象在哪里、此时是否应存在，再给动作、参数含义和观察结果。解释使用代码原名与块内行号、配置文件与键、输出字段或图中节点定位；切换终端、应用或构建目录时重新说明输入和结果归属。

术语在首次需要时解释，参数在实际使用处解释。章节间用尚未解决的问题衔接，不按审稿意见的到达顺序追加问答，也不让表格、命令清单或外链替代必要的因果说明。

长章按完整实践决定是否拆分：P008 保留同一应用的环境对照与多镜像产物定位；P010 保留从文件选择到驱动调用的追踪；P012 保留缓存变化与故障定位；P014/P015 分别保留依赖接入和新增硬件的完整操作。后续若出现独立问题，应拆成可单独完成的单元并同步引用，不以保留长章为由继续追加无关内容。

## 1.5\_维护与验收

修改先明确受影响的认识和操作，再检查前置章节、当前正文与后续使用处。结构变化同步大纲、标题锚点、命令附件和实际入链；设计变化直接改写本文件对应段落，不新增日期小节或保留相互冲突的“当前方案”。

验收分为三部分：

- **阅读与定位：** 隐藏聊天背景和外链后，正文仍能说明原因、对象、操作与结果；读者能找到所指文件和参数。
- **材料一致性：** 链接、编号、稳定 ID、命令附件和行号对应有效，示例版本与来源可核对。
- **实践证据：** 分别记录语法检查、实际构建、模拟运行和实板测试，未执行的步骤不能写成已验证。

具体检查结果进入 VALIDATION；项目交付状态进入移植状态记录。本文件只在目标、章节职责或维护规则改变时更新。
