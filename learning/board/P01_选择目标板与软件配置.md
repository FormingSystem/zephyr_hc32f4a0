# 1. 选择目标板与软件配置

## 1.1 为什么不能只选择 Cortex-M4

你知道芯片和 PCB，本章补齐 Zephyr 如何把它们变成构建输入。SoC 是芯片级支持，包含内核、存储器和外设；board 是具体板卡，描述装了哪个芯片、晶振和接线。相同 CPU 内核不代表相同外设地址和启动方式。

本工程目标 `uyup_rpi_a/hc32f4a0pitb` 中，前半段是板名，斜杠后是芯片限定项（qualifier），用于区分板卡上的 SoC/变体。不要拿供应商产品页的简称直接替换 BOARD。

先按[项目环境](../../project-docs/environment.md)配置工具，在仓库根目录执行：

```bash
source .venv/Scripts/activate
python scripts/project_env.py exec west boards
python scripts/project_env.py build
```

boards 枚举当前源码知道的板；实际限定项还需查看对应 board.yml。默认 build 选择本工程 HC32 板，不因接了某种探针就自动选芯片。

## 1.2 找到目标背后的文件

YAML（YAML Ain't Markup Language）是一种结构化文本格式，本章用它记录板元数据。
DTS（Devicetree Source，设备树源码）描述硬件连接；下面文件地图先确定职责，下一章再解释其语法。

| 位置 | 用途 | 什么时候改 |
| --- | --- | --- |
| boards/uyup/uyup_rpi_a/board.yml | 板与 SoC 关联、目标元数据 | 新板或新增受支持芯片变体 |
| boards/uyup/uyup_rpi_a/Kconfig.uyup_rpi_a | 板选择关联 | 建立新板的 Kconfig 入口 |
| uyup_rpi_a_hc32f4a0pitb_defconfig（同目录） | 板级默认软件选项 | 改板的共同默认能力 |
| uyup_rpi_a_hc32f4a0pitb.dts（同目录） | 实装器件、控制台、LED、接线 | PCB 适配 |
| uyup_rpi_a_hc32f4a0pitb.yaml（同目录） | Twister 使用的平台能力 | 测试选择与资源描述 |
| board.cmake（同目录） | 烧录/调试 runner 设置 | 接入受支持的板级工具 |
| soc/xhsc/hc32f4a0/ | SoC 选择、启动、时钟及底层集成 | 芯片系列移植 |
| dts/arm/xhsc/hc32f4a0*.dtsi | 芯片公共外设与封装限制 | 芯片描述层变化 |
| samples/bringup/prj.conf | 应用功能开关 | 此应用需要什么驱动与能力 |

board.yml 和同目录平台 yaml 用途不同，不要因为都是 YAML 就互相代替。确切硬件事实集中在[hardware.md](../../project-docs/hardware.md)，这里仅教你定位配置层。

选择另一块已支持板时先确认应用是否依赖特定外设/别名，再用独立构建目录试编译。选择当前未支持的芯片时，需要 SoC、DTS、启动和驱动等移植；改 BOARD 字符串不能创造硬件支持。

## 1.3 Kconfig 配置的是软件能力

Kconfig 定义选项类型、依赖和默认值；.conf 提供选择。例如 CONFIG_GPIO=y 请求 GPIO 支持，前提是芯片与驱动依赖满足。最终值由整个配置系统解析得出，不是把 prj.conf 原样复制。

板默认值与应用 prj.conf 合并，再可用 EXTRA_CONF_FILE 追加实验片段。输出位于 build 目录的 zephyr/.config；生成的 autoconf.h 供 C 代码判断。只读这些输出，不把手改生成文件作为持久配置。

若选项依赖不满足，赋 y 也可能不生效；若符号不存在，当前配置会告警并终止。先搜索定义：

```bash
rg -n "config DEBUG_OPTIMIZATIONS|config GPIO" Kconfig.zephyr drivers subsys
```

本源码使用 CONFIG_DEBUG_OPTIMIZATIONS=y 选择适合调试的优化。不要照旧资料加入未定义的 CONFIG_DEBUG_INFO。选项版本以当前受控源码为准。

## 1.4 用独立目录比较最终配置

下面沿用本工程应用，叠加教程配置；还同时选择下一章的 LED overlay，便于两章复用一次构建：

```bash
python scripts/project_env.py exec cmake -S samples/bringup -B build/learning-tools/pcb-green -G Ninja -DBOARD=uyup_rpi_a/hc32f4a0pitb -DEXTRA_CONF_FILE=../../learning/board/labs/debug.conf -DDTC_OVERLAY_FILE=../../learning/board/labs/green-led.overlay
python scripts/project_env.py exec cmake --build build/learning-tools/pcb-green
rg -n "CONFIG_DEBUG_OPTIMIZATIONS" build/learning-tools/pcb-green/zephyr/.config
```

两个附加文件的相对路径按应用目录 samples/bringup 解析，故使用 ../../，不是按 shell 根目录解析。-B 则相对当前 shell 工作目录。区分各参数的路径基准比给所有示例写绝对路径更重要。

预期配置文件中选项为 y，构建成功。需要交互查看选项可执行：

```bash
python scripts/project_env.py exec cmake --build build/learning-tools/pcb-green --target menuconfig
```

menuconfig 可帮助搜索选项与依赖；退出时保留你确认需要的选择，再把最小必要配置写回应用 .conf。不要整份复制生成配置，否则把大量默认值固定住，后续升级难以追踪。

## 1.5 改配置之前先判断层次

打开驱动开关属于 Kconfig；指定 LED 接在哪个 GPIO 属于设备树；将驱动源文件纳入构建属于 CMake；获取某个模块版本属于 Git/west。遇到失败，按相应层找输入与最终输出。

修改挑战：用新的 EXTRA_CONF_FILE 选择一个在当前源码确有定义且依赖满足的应用选项，记录原值、预期值、最终 .config 值，解释差异。不要通过修改板默认值解决仅一个应用的偏好。

清理仅涉及本章的 pcb-green 构建目录。完成标志是能由目标名找到板和 SoC 文件，能解释最终配置来源。[下一章：PCB 与设备树](P02_按PCB连接修改设备树.md)。

依据：[板级移植官方说明](https://docs.zephyrproject.org/latest/hardware/porting/board_porting.html)、[Kconfig 官方配置说明](https://docs.zephyrproject.org/latest/build/kconfig/setting.html)。
