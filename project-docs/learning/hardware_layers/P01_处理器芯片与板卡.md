# P01 处理器、芯片与板卡

前面的 C 语言学习已经把程序解释为“读取对象、计算、再写入对象”。
但是，当心跳程序请求翻转板上的蓝灯时，写了哪个对象才能改变灯的亮灭？
处理器名称相同的两块板，为什么不能直接互用固件？
本章用仓库已有示例闭合这两个问题，再检查一个“芯片内部有名称，实装封装却没有引脚”的反例。

**Zephyr** 是操作系统项目名称，**HC32F4A0PITB** 是目标芯片型号，
**UYUP-RPI-A-2.5** 是本项目开发板的型号；这些都是专名，不应互相代替。
`HC32` 是本章指代目标芯片系列的简称标识符，不是另一个处理器核名称。
本章只讲它们如何组合，以及程序怎样沿组合关系驱动一个输出。
异常入口、时钟配置和完整设备树语法分别留给后续专题。
读完后，应能从蓝灯的软件别名找到板卡连接、芯片端口、驱动入口和写寄存器的厂商函数，
并说明“找到写入语句”和“实板已经亮灯”分别需要什么证据。

## 1. 先让一条指令有地方执行

**处理器核（CPU core；CPU 为 Central Processing Unit，中央处理器）** 是执行指令的硬件单元。
它反复取指令、解释操作、读取输入并更新状态。C 函数经过编译后形成的机器指令，由它执行。
处理器核没有“名为蓝灯的 C 对象”；它最终只看到计算、分支和对地址的读写。

**指令集架构（Instruction Set Architecture，ISA）** 约定处理器能理解哪些指令以及它们的效果。
架构是一组约定，处理器核是遵循约定的具体实现，二者的关系类似文件格式与实现读写格式的软件。
同一架构允许有不同处理器核，不能仅凭兼容指令就推断外设地址也相同。

**Cortex-M4** 是 Arm 的处理器核产品名称。本工程相关源码还会出现 **Cortex-M4F**，
它标识本项目使用的带浮点处理能力的配置；浮点处理用于某类数值运算，不定义板上的连线。
其中 `M4F` 属于产品配置的后缀标识符，不是需要另编英文全称的接口缩写。
该身份来自本项目的[硬件依据](../../hardware.md#存储、中断与其他资源)和
[片上硬件描述](../../../dts/arm/xhsc/hc32f4a0.dtsi)，不是根据固件名称猜出来的。

现在可以解释第一层错误模型：“它们都是 Cortex-M4，所以写同一个地址能点同一盏灯”。
相同处理器核只给出了指令执行的共同基础。灯的控制器在哪里、使用哪个引脚，尚未进入这个模型。
要回答这些问题，必须把处理器核放回芯片。

## 2. 芯片把执行、存储与外设接到一起

**片上系统（System on Chip，SoC）** 是把处理器核、存储控制和外设等系统部件集成在一颗芯片上的组织方式。
**微控制器（Microcontroller Unit，MCU）** 是面向嵌入式控制的一类芯片；本项目目标就是这类器件。
Zephyr 的 SoC 支持目录描述目标芯片的集成方式，不能把目录里的 SoC 当成另一块外接硬件。

**外设（peripheral）** 是处理器之外负责特定输入输出任务的硬件单元。
本章使用的 **通用输入输出（General-Purpose Input/Output，GPIO）** 控制器，负责读取或驱动引脚电平。
处理器发出写操作，GPIO 控制器改变输出状态，引脚才可能向外部电路输出电平。
改变处理器寄存器中的普通计算结果，本身不会自动改变 GPIO。

这里的 **寄存器（register）** 有两种需要区分的语境。
处理器内部寄存器保存运算操作数和执行状态；外设寄存器则是芯片规定的控制和状态入口。
软件通过外设寄存器配置方向、设置输出或读取输入，寄存器的每一位含义由芯片规定。
同样是向一个地址写数字，普通内存可能只保存该数字，外设地址却可能触发硬件动作。

**地址空间（address space）** 是处理器能够区分和访问的地址集合。
**存储映射输入输出（Memory-Mapped Input/Output，MMIO）** 把外设寄存器放进这个地址空间，
使处理器能用内存访问指令与外设交互。地址映射的对象由芯片定义，不能随意当作数组存储。
例如，把外设翻转寄存器当成普通变量“读后加一”，可能改变完全不同的输出位。

**Flash** 是断电后仍能保留数据的非易失存储器类别名称，通常保存固件；
**静态随机存取存储器（Static Random-Access Memory，SRAM）** 用于运行中的对象和栈等数据。
它们与 GPIO 寄存器同处处理器地址空间，却有不同的访问效果、寿命和布局约束。
本板的实际地址和容量只在[存储记录](../../hardware.md#存储、中断与其他资源)维护；
这里的关键判断是“这个地址映射到什么对象”，而不是背一张地址表。

外设还可以产生 **异常（exception）**：处理器暂时转向规定的处理入口，完成处理后再继续原执行流。
由外设请求触发的中断是一类异常来源。当前心跳只主动写 GPIO，不需要 GPIO 中断。
因此，能点灯并不表示该外设的中断路由也完成了；本章的证据不能越过这个边界。

## 3. 封装和板卡决定输出能到哪里

芯片内部的一路输出，需要经过 **封装（package）** 才能成为可焊接的外部引脚。
芯片型号后缀所确定的封装，是查手册时的必要输入。某系列内部存在一个端口名，
不意味着该系列所有封装都把它引出。
**LQFP（Low-profile Quad Flat Package，薄型四边扁平封装）** 是封装类别，
后续数字描述该封装的引脚数量；本项目实装身份由[硬件依据](../../hardware.md)确认。

**开发板（development board）** 把芯片与电源、晶振、指示器和连接器焊接在电路板上。
板卡决定“芯片外部引脚接到了什么”，芯片手册决定“这个物理脚在该型号上有什么功能”。
这两项资料要用物理脚号对齐，不能只看原理图上的通用名称。
本板原理图使用兼容器件符号，因此这个区别直接影响移植是否正确。

**网络（net）** 是原理图中电气相连的一组连接点；同名网络通常用来表示不画连续导线的连接。
**未连接（Not Connected，NC）** 在本项目要求中还约束未引出的芯片功能：
对于实装芯片没有的引脚，软件不能假设那里存在可用连接。
“把不存在的引脚写成输入以免冲突”仍然在启用不存在的资源，不能替代排除它。

**发光二极管（Light-Emitting Diode，LED）** 是流过合适方向电流时发光的器件。
本章沿用硬件记录中“首次启动所需信号”表的蓝色指示灯，使用其已核对的连接和有效电平；
这里只抽取该例需要的事实，不新增另一张全板引脚表。
对应记录为[蓝灯连接依据](../../hardware.md#首次启动所需信号)。

此时可以按关系而不是名称画出系统：

```text
Arm 的指令约定
    ↓ 由具体处理器核实现
芯片内的 Cortex-M4 处理器核
    ↓ 发起对芯片地址空间的访问
HC32 内部 GPIO 控制器
    ↓ 通过实装封装引出的引脚
板卡导线、电阻和蓝灯
    ↓ 形成有方向的电流
可观察的亮灭
```

这张关系图解释谁包含谁以及谁驱动谁；它还没有说明软件如何选择这条连接。
同芯片不同板卡可以把输出接到不同器件，因此连接信息需要独立进入软件构建。
Zephyr 官方[板级移植指南](https://docs.zephyrproject.org/latest/hardware/porting/board_porting.html#hardware-support-hierarchy)
也按板卡、SoC 与处理器核组织支持；网页用于对照概念，项目行为以当前源码为准。

## 4. 把“蓝灯”变成构建时可以查找的描述

**设备树（devicetree）** 是描述硬件及其连接的数据组织方式。
它在这里提供“蓝灯接哪个控制器、哪个引脚、有效电平是什么”的信息；它不是执行翻转的程序。
**设备树源文件（Devicetree Source，DTS）** 保存人编写的硬件描述，
`.dtsi` 文件是可被其他设备树源文件包含的公共片段，扩展名表示文件角色。

下面片段中的 `GPIO_ACTIVE_LOW` 是低电平有效的配置宏，`LED3` 是板上蓝灯的器件编号名称。
当前板级源文件的以下片段来自仓库，省略了本轮不用的其他设备：

```dts
blue_led: led-0 {
    gpios = <&gpiod 10 GPIO_ACTIVE_LOW>;
    label = "LED3 blue";
};

aliases {
    led0 = &blue_led;
};
```

`blue_led` 是节点标签，允许其他位置引用该节点；`led-0` 是节点名。
`gpios` 是描述输出连接的属性：`&gpiod` 引用 D 端口控制器，`10` 是端口内的引脚索引，
`GPIO_ACTIVE_LOW` 是低电平有效的配置宏。
这里的 `10` 不是封装物理第十脚，物理脚号必须回到硬件记录查证。
`label` 是人可读的设备说明，不能据此决定实际连接。

`aliases` 是设备树中保存别名的节点；其中 `led0` 给应用提供稳定名字，
让应用不必把板上的端口号写死在 C 源码里。
**绑定描述（binding）** 是约束设备树属性如何填写的文件，
本控制器的绑定规定 GPIO 引用携带 `pin` 和 `flags` 两个值，分别表示引脚索引和配置标志。
控制器的 `port-index` 属性则表示芯片端口编号，D 端口取值为 3。

依据分别在[板级设备树](../../../boards/uyup/uyup_rpi_a/uyup_rpi_a_hc32f4a0pitb.dts)、
[芯片公共设备树](../../../dts/arm/xhsc/hc32f4a0.dtsi)和
[GPIO 绑定](../../../dts/bindings/gpio/xhsc,hc32-gpio.yaml)。
阅读时核对“应用别名 → 设备节点 → 控制器引用 → 端口属性”，而不是从文件名猜连接。
官方[设备树介绍](https://docs.zephyrproject.org/latest/build/dts/intro.html)可用于对照数据职责；
本例只解释这条连接用到的语法，合并规则在 T10 深化。

## 5. 一次翻转怎样从 C 请求到寄存器写入

**驱动（driver）** 是把通用设备请求翻译成某个硬件控制动作的软件。
**应用编程接口（Application Programming Interface，API）** 规定应用怎样提出请求并解释返回值。
本例应用使用 Zephyr 的 GPIO API，HC32 驱动接收请求，再调用厂商封装好的寄存器操作函数。

**硬件抽象层（Hardware Abstraction Layer，HAL）** 为具体硬件操作提供软件封装。
本仓库华大模块使用 **设备驱动库（Device Driver Library，DDL）** 的函数实现这些操作；
HAL 在这里表示集成层职责，DDL 是所集成库的名称，二者不是两个独立外设。
该层不能替应用证明板卡装配正确，只能按给定端口和引脚操作芯片。

已有[心跳应用](../../../samples/bringup/src/main.c)先用 `DT_ALIAS` 宏找到 `led0` 节点，
再用 `GPIO_DT_SPEC_GET` 宏产生一个 `gpio_dt_spec` 结构体。
该结构体把控制器设备指针、端口内引脚索引和设备树标志存到一起，
应用中的 `led` 对象保存它，后续配置和翻转都使用这个对象。
它是编译生成信息的承载者，不是灯的运行状态副本。

运行时先调用 `gpio_is_ready_dt` 函数确认控制器完成初始化，再调用
`gpio_pin_configure_dt` 函数设置方向和初始状态。
示例传入 `GPIO_OUTPUT_INACTIVE` 配置宏，意思是“输出，初始为逻辑未激活”。
“逻辑未激活”与“引脚拉低”不同：低有效灯的未激活状态需要高电平。
通用 GPIO 实现在进入硬件驱动前把有效电平与初值合并，得到物理输出要求。
具体处理可在[GPIO 公共接口](../../../include/zephyr/drivers/gpio.h)的初始化标志处理处核对。

初始化失败时，应用打印错误并把 `led_ready` 布尔变量置为假，后续不再翻转该输出。
该变量属于应用，表示是否继续尝试灯操作；它不是读取灯后得到的真实亮灭状态。
配置成功后，循环调用 `gpio_pin_toggle_dt` 函数，把同一引脚输出取反，随后等待再循环。
这是长期运行的板级示例，因此没有正常自动退出；本章实验只读源码，不启动这个无限循环。

请求在本项目内依次经过以下交接，每一行表示相邻两层的实际分工：

| 交接 | 接收什么 | 更新或返回什么 |
| --- | --- | --- |
| 应用调用 `gpio_pin_toggle_dt` | `led` 结构体中的设备和引脚 | 向公共接口请求翻转，取得返回值 |
| 公共接口定位设备 API | 控制器设备及单引脚位掩码 | 调用设备的 `port_toggle_bits` 操作 |
| `gpio_hc32_port_toggle_bits` 驱动函数 | 端口配置与待翻转的位掩码 | 先核对可用引脚，再调用厂商函数 |
| `GPIO_TogglePins` 厂商函数 | 端口索引和 16 位引脚掩码 | 通过目标端口的翻转寄存器执行写入 |
| GPIO 硬件与板卡电路 | 配置后的输出状态和实际接线 | 形成引脚电平及可能的灯亮灭，需要实板观察 |

**位掩码（bit mask）** 是用某一位表示某个对象是否被选中的整数。
本例端口内索引为 10，故单引脚掩码是 `1 << 10`，即十六进制 `0x0400`；
移位只选中一位，不能拿物理脚号直接代入。
驱动从设备配置中的 `port` 字段取得端口索引，从 `port_pin_mask` 字段取得允许访问的引脚集合。
这些字段描述控制器身份与限制，不保存灯的亮灭历史。

驱动的 `gpio_hc32_port_toggle_bits` 检查请求是否超出允许集合，
在临界区调用 `GPIO_TogglePins`，最后返回零表示这次驱动操作未报告错误。
临界区在此通过暂时屏蔽可屏蔽中断保护操作配对；它不能制造不存在的引脚，也不证明外部电平。
驱动代码见[HC32 GPIO 实现](../../../drivers/gpio/gpio_hc32.c)。

厂商代码的 `GPIO_TogglePins` 使用 `POTR_REG` 宏选择端口翻转寄存器，
`GPIO_REG_OFFSET` 是相邻端口寄存器的地址步长，`GPIO_POTR_BASE` 是 A 端口同类寄存器的基准地址。
宏按端口索引计算目标位置，再由 `SET_REG_BIT` 宏按传入位掩码执行寄存器读写表达式。
这些是代码标识符；本章不根据英文缩写猜寄存器完整名称，也不把该表达式宣传成无需保护的原子操作。
具体代码在[厂商 GPIO 实现](../../../modules/hal/xhsc/hc32_ddl/hc32f4a0/drivers/src/hc32_ll_gpio.c)。

从这一过程反推，改端口或有效电平时先改板级描述并核对电路；
改 HC32 写入方式时则需要检查驱动和厂商调用的行为，不能靠改应用别名达到目的。
“通用 API 能调用”只到软件契约这一层，“驱动返回成功”只到本次软件路径这一层，
引脚电压、输出电流和灯是否亮仍要实物测量补上。

## 6. 为什么不能把其他封装的引脚补进来

合理的旧模型是“该 GPIO 端口有 16 个编号，0 到 15 都能传给驱动”。
在所有引脚均引出的端口上，这个模型工作正常；它遗漏的是封装引出条件。
本板[旧模板冲突记录](../../hardware.md#旧模板中的时钟冲突)指出模板曾使用未引出的 PH14/PH15。
这不是一个换名字就能复用的配置，必须从可用集合中排除。

本项目使用两层限制。
第一层在型号专属设备树片段中用 `gpio-reserved-ranges` 属性描述保留范围，
每对数字表示“起始索引、连续数量”。因此 `<2 14>` 表示保留索引 2 到 15，
不能读成“只保留索引 2 和 14”。
第二层在 HC32 驱动初始化时检查 `package_pins` 数组，它保存该型号封装允许的端口位集合。
设备树扩大可用范围时，驱动会检查新集合是否仍是封装集合的子集。

这两层所解决的问题不同：设备树表达型号与应用配置，驱动保留封装硬限制。
它们仍不能判断“一个真实引脚已经被板上的晶振占用”等完整用途冲突，
所以“封装存在”只是允许继续核对的必要条件，不是随意接输出的充分条件。
本章不会启用被保留的端口，也不会修改晶振脚来试错。

## 7. 只读实验：验证连接和限制来自哪里

实验问题是：当前源码能否连出蓝灯的请求链，而且型号描述与驱动对 H 端口限制一致？
需要已经可以运行工程 Python 的主机，不需要插板，也不需要已有构建目录。
**Python** 是下面执行只读检查的语言名称，**PowerShell** 是承载多行命令的终端程序名称。
从仓库根目录执行；代码仅读取三个受控文件并在当前进程中计算掩码，不运行驱动。
输出中的 `PASS` 是本实验选用的成功标记字符串名称，只对应脚本中明确检查的条件。

```powershell
@'
from pathlib import Path
import re

root = Path.cwd()
board = (root / "boards/uyup/uyup_rpi_a/uyup_rpi_a_hc32f4a0pitb.dts").read_text()
package = (root / "dts/arm/xhsc/hc32f4a0pitb.dtsi").read_text()
driver = (root / "drivers/gpio/gpio_hc32.c").read_text()
led = re.search(r"blue_led:.*?gpios\s*=\s*<([^>]+)>", board, re.S)
reserved = re.search(r"&gpioh\s*\{.*?gpio-reserved-ranges\s*=\s*<(\d+)\s+(\d+)>", package, re.S)
table = re.search(r"package_pins\[\]\s*=\s*\{([^}]+)\}", driver, re.S)
assert led and reserved and table, "源码结构改变，请重新定位定义"
start, count = map(int, reserved.groups())
allowed = 0xFFFF & ~(((1 << count) - 1) << start)
masks = [int(value.strip().removesuffix("U"), 0)
         for value in table.group(1).split(",") if value.strip()]
assert allowed == masks[7], "型号描述与驱动的 H 端口限制不一致"
print("blue_led:", led.group(1).strip())
print(f"H allowed mask: 0x{allowed:04X}")
for pin in (1, 14):
    print(f"H{pin} in package mask:", bool(allowed & (1 << pin)))
print("PASS: package description agrees with driver mask")
'@ | python -B -
```

`-B` 是 Python 禁止写入字节码缓存的选项，末尾 `-` 表示从标准输入读取程序。
`re` 是 Python 正则匹配模块，负责从当前文本定位需要的定义；它不解析完整设备树语言。
`allowed` 是本实验根据保留区间计算的允许集合，`masks[7]` 是驱动数组的 H 端口项。
检查规则刻意限定于本次源码结构，结构改变时应停下来重新定位，不能把断言删除后继续宣称一致。

2026-09-10 在提交标识符为 `d79a7bff3115163d79e4462ed7044cb26ed6bc04` 的项目源码上执行，退出码为 0。


正常结果是设备树和驱动集合一致；反例是把“端口有 16 位”套到 H14 时，计算结果为假。
实验没有给芯片发送这个非法请求，因此不应把它写成“实板拒绝了 H14”。
H1 为真也仅表示封装集合中存在该引脚，不授权把它改成灯输出；板级用途仍须核对。

## 8. 迁移练习与验收边界

迁移练习：沿用同一方法追踪已有绿色指示灯。
先从硬件记录取连接依据，再从板级别名找节点、控制器、引脚索引和有效电平，
计算单引脚位掩码，最后判断哪些通用调用可以复用、哪些板级输入改变了。
该练习是读者任务，本次没有把绿色灯运行记成已验证。

进一步设想：保持处理器核不变，更换另一款芯片，应重新核对哪些层？

芯片地址、厂商驱动、封装引出和板卡连接都必须分别核对，不能靠“同为 Cortex-M4”直接沿用。
