# Zephyr 学习与实验路线

这套资料从“让一个程序有证据地运行起来”开始，逐步走到“能解释内核、移植驱动、定位故障并维护完整产品”。
Zephyr 是本工程采用的嵌入式操作系统项目名称。学习时同时保留两条线：一条在电脑上的模拟目标验证软件机制，
另一条把相同应用接到 HC32F4A0PITB 开发板，核对实际电路和时序。
HC32F4A0PITB 是芯片型号，HC32 是下文使用的芯片系列简称，两者不是需要展开英文全称的缩写。

默认你能看懂简单 C 函数；指针、结构体、编译和硬件基础会有专门补课专题。
不需要先买齐扩展模块，也不需要先读完所有内核源码。每次只完成一个可以解释、复现和验收的学习单元。

## 学习会经过哪些阶段

顺序按实际遇到的问题安排。早期先学会记录输出和检查返回值；完整调试和测试方法在后面深化，
并不是到最后才开始验证。阶段编号是阅读组织，不是必须一次学完的课时表。

| 阶段 | 由什么问题引出 | 阶段结束时能够完成什么 |
| --- | --- | --- |
| 01 准备知识与实验起点 | 我究竟在构建哪份程序，结果可靠吗？ | 固定版本、环境和第一份实验记录 |
| 02 应用、构建与配置 | 改了一行配置，为什么固件没有变化？ | 从输入配置追到生效文件和最终镜像 |
| 03 线程、中断与时间 | 程序等待时谁在运行，为什么没有准时醒来？ | 解释一次执行切换和一次超时唤醒 |
| 04 共享数据与异步任务 | 多项工作交错时，数据和资源怎样交接？ | 设计有容量、所有权和退出规则的数据通路 |
| 05 内存与执行边界 | 栈、缓冲区和权限为何会破坏看似正确的程序？ | 定量规划内存并复现受控失败 |
| 06 HC32 最小移植 | 从复位开始，怎样走到串口与指示灯？ | 将启动、时钟、引脚和驱动连成验收链 |
| 07 外设与数据搬运 | 轮询不够用时，如何接入外设事件和连续数据？ | 逐项实现并验证外设驱动 |
| 08 存储与持久化 | 断电以后，哪些数据必须完整留下来？ | 区分原始存储、参数保存和文件系统 |
| 09 调试、故障与性能 | 卡死、丢数据或变慢时，怎样用证据定位？ | 建立从症状到源码、状态和测量的调查过程 |
| 10 低功耗、安全与升级 | 长期运行、掉电和更新如何影响系统完整性？ | 设计唤醒、可信启动与可恢复升级的验证方案 |
| 11 通信与互联 | 一台设备怎样可靠地与其他设备和服务交换信息？ | 处理连接、超时、断线、重连和协议边界 |
| 12 传感、交互与数据处理 | 怎样把采集的数据变成用户可用的信息？ | 组合采样、处理、显示或音频链路 |
| 13 测试、扩展与维护 | 改完驱动、依赖或配置，怎样知道旧功能仍正确？ | 组织回归、依赖更新和可审查的交付 |
| 14 综合工程 | 各章知识怎样一起满足真实需求？ | 做出有资源预算、异常恢复和验收报告的完整项目 |

## 实验在哪里运行

“构建成功”只证明工具生成了程序，不能证明接线、实际时钟或外设运行正确。
因此每篇实验分别记录下面这些证据，不使用一个笼统的“通过”覆盖全部环境。
QEMU 是模拟器项目名称；`mps2/an386` 是本工程采用的模拟板目标标识，它不模拟 HC32 外设。

| 环境或证据 | 能回答什么 | 当前边界 |
| --- | --- | --- |
| 主机检查 | 配置、源码、链接布局和测试工具是否符合预期 | 不访问开发板 |
| QEMU 模拟器 | 在模拟处理器上运行程序，检查软件行为 | 项目已有 `mps2/an386` 的心跳回归记录；新增实验需逐个验证 |
| HC32 镜像构建 | 当前板级目标能否生成符合布局的程序 | 已有构建与镜像审计；实板运行仍待验收 |
| HC32 实板 | 引脚、晶振、外设和电气时序是否正确 | 按每项实验取得实际日志或测量证据 |
| 其他平台或扩展模块 | 当前板暂未具备的接口和系统能力 | 明确所需驱动、器件、工具和额外源码依赖后再启用 |

另一种官方目标 `native_sim` 把程序与内核构建为 Linux 主机程序，可用于后续软件测试；
它需要另外准备相应主机环境，不能把输出文件名 `zephyr.exe` 当作 Windows 原生支持的证明。
依据见[官方 native_sim 说明](https://docs.zephyrproject.org/latest/boards/native/native_sim/doc/index.html)。

## 每一篇怎样做深

专题从具体遭遇开始：先给出已有方案能够保证什么，再用一个反例暴露缺口。
随后解释参与者、状态、数据与执行顺序，给出最小正确用法，最后追到当前版本源码和可观察实验。
读者应当能够预测改变一个条件后的结果，并知道需要哪项证据来验证自己的预测。

学习主线围绕一个不断成长的“可诊断数据采集节点”：最初只输出心跳，随后接受按键或命令，
再增加数据队列、传感采样、持久化和远程传输。每一步保留小实验，不把所有功能塞进同一个越来越难定位的例程。

适用源码为本仓库固定的 Zephyr 4.4.99，准确提交见[源码基线](../source-baseline.md)。
在线官方文档用于辅助阅读，涉及接口与实现时以本仓库对应源码为准；相同版本字符串也可能对应不同开发提交。
板卡参数统一引用[硬件依据](../hardware.md)，实际完成度统一见[移植状态](../porting-status.md)。
