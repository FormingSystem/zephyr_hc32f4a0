# 从哪里开始学习 Zephyr

如果你已经打开工程，却不知道先看哪个目录，先从这篇开始。
今天的目标很具体：说清这个工程怎样产生一个可运行的程序，在电脑上完成一次软件实验，
再知道下一步该学什么。全部 88 个专题是一条长期路线，可以随着实际问题逐步进入。
阅读起点只要求能看懂简单 C 函数；指针、数组等基础由下文的 T02 补齐。

**Zephyr 是嵌入式操作系统项目的名称**。“嵌入式”表示程序运行在设备里，负责采集、控制或通信等任务；
操作系统提供组织程序执行、等待事件、共享数据和访问设备的基础能力。
本课程采用本仓库固定的 Zephyr 4.4.99 源码，具体来源见[源码基线](../source-baseline.md)。
下文先建立学习顺序，再带你使用已经存在的实验；不会要求先记住完整目录或全部接口。

## 1. 先知道自己要解决什么问题

可以把学习目标想成做一个小设备：定期采集一个数，收到操作时作出回应，同时输出当前状态。
开始只有一项工作时，一个反复执行的 C 循环就容易表达。
后来增加了等待、超时和几项工作之间的数据交接，你需要回答：谁正在运行，谁正在等，
等到条件满足后谁继续，交出去的数据在那时是否还有效。

Zephyr 提供处理这些问题的组织方式。**内核（kernel）**是其中管理执行、等待和协调的核心部分。
**线程（thread）**是内核管理的一条程序执行线，
有自己的执行位置和保存函数调用过程所需的空间；一条线程等待时，其他已具备运行条件的线程可以得到执行机会。
这不表示所有工作在同一时刻执行，也不表示使用线程之后就自动满足时间要求。
先在[程序如何运行](../P02_Zephyr如何组织程序运行.md)里观察等待，再在后续专题解释调度细节。

为了知道每次应该修改哪一层，先区分四种职责：

| 名称 | 在这个小设备里负责什么 |
| --- | --- |
| 应用（application） | 表达设备要做的事，例如处理一次采样、决定输出什么 |
| 内核（kernel） | 管理执行、等待、时间和程序之间的协调，线程是它管理的对象之一 |
| 设备驱动（device driver） | 把软件的设备操作接到某种硬件的实际访问方式 |
| 构建（build） | 让电脑上的工具把选定的源码、软件选项和硬件描述转换成目标程序 |

学习时反复用同一个问题检查自己：这次修改是在改变应用需求、运行组织、硬件访问，还是生成程序的输入？
如果暂时分不清，就先回到第一篇介绍定位，不必立即往内核实现深处搜索。
这些职责的完整项目位置在[认识这个工程](../P01_认识这个工程.md)中展开；
Zephyr 自身的定位也可对照仓库内的[官方介绍](../../doc/introduction/index.rst)。

## 2. 先读四篇介绍，再按需补齐六个基础专题

四篇介绍是一遍工程全景。首次阅读可以先关注程序走过哪些环节，遇到暂时不熟悉的具体语法，
带着问题进入后面的基础专题。每篇读完都做表中的一个小动作，用它判断自己是否抓住了主线。
其中 **HC32 是本项目所用芯片系列的名称**，属于型号专名；第四篇把学习过程接到实际芯片移植工作。

| 顺序 | 现在能读的文章 | 读完立即做什么 |
| --- | --- | --- |
| 第一步 | [P01 认识这个工程](../P01_认识这个工程.md) | 在目录里分别找到应用、内核、板卡描述和项目脚本 |
| 第二步 | [P02 Zephyr 如何组织程序运行](../P02_Zephyr如何组织程序运行.md) | 指出心跳程序在哪里等待，解释等待时为何可以执行其他工作 |
| 第三步 | [P03 从源码到固件](../P03_从源码到固件.md) | 把一个源文件、一个配置输入和生成的程序文件对应起来 |
| 第四步 | [P04 HC32 移植由哪些部分组成](../P04_HC32移植由哪些部分组成.md) | 说明增加一个外设功能时，哪些部分可能需要修改 |

随后进入六个详细基础专题。T01 等编号是课程索引，不是工具命令。
这一组已经有正文、步骤和实际核对记录；后续专题仍在建设。

| 顺序 | 详细专题 | 它补齐哪种学习能力 |
| --- | --- | --- |
| T01 | [版本、证据与官方资料](evidence/README.md) | 先确定正在读哪份源码，再区分文档约定、具体实现和实验观察 |
| T02 | [C 对象与生命期](c_lifetime/README.md) | 判断传递的是数据还是地址，知道数据何时仍可使用，处理容量和失败 |
| T03 | [从 C 到链接对象](compilation/README.md) | 解释源文件如何变成目标代码，识别缺少定义造成的链接失败 |

首次动手前读完 T05，并把 T06 放在旁边对照。当前完成度是 **四篇介绍加 T01—T06，详细专题 6/88**，
实际验证范围见[第一组验收记录](第一组验收记录.md)。

## 3. 第一次动手先完成一轮可检查的软件实验

这里的**主机（host）**就是运行编辑器和构建工具的电脑，**目标（target）**是生成的程序准备运行的环境。
**QEMU 是模拟器项目的名称**，它在电脑上模拟目标处理器和部分设备。
本实验使用的 `mps2/an386` 是模拟板目标标识；先用它学习软件行为，不需要接开发板。
模拟器没有本项目芯片的外设和真实电路，因此本节结果不能证明实板引脚、晶振或串口工作正确。

先打开仓库的[编辑器工作区](../../zephyr_hc32f4a0.code-workspace)。工作区文件告诉编辑器打开哪个项目目录、
怎样启动终端和工程任务；本项目只展示一个完整源码根目录。
以下命令使用 **PowerShell，它是本机执行这些开发命令的终端语言**。
终端应位于当前项目根目录，那里同时存在 `README.md`、`VERSION`、`scripts/` 和 `tests/`。
本机实际目录与已安装工具的位置，通过 [AGENTS.md 中的私人配置入口](../../AGENTS.md)核对。

先准备当前终端，再检查环境：

```powershell
. ./scripts/Enter-Environment.ps1
python scripts/project.py doctor
$LASTEXITCODE
```

第一行开头的点表示把脚本设置载入当前终端，因此后续命令能使用选定的工具与源码。
`python` 是启动 Python 解释器的命令；`scripts/project.py` 是本仓库的工程脚本路径，
`doctor` 子命令检查源码、工具和调试配置，不连接开发板。
`$LASTEXITCODE` 是 PowerShell 保存的上一条外部程序退出码；这里预期为 `0`。
退出码是程序交给调用方的整体结果，通常用零表示成功、非零表示失败。
若环境检查失败，先按 [T05](environment/README.md)处理对应原因；新电脑的安装步骤见[开发说明](../development.md)。

然后打开[实验源文件](../../tests/learning/first_evidence/src/main.c)，先看两个测试要判断什么。
**断言（assertion）**是在程序运行时检查某个条件，并在条件不成立时报告失败的检查动作。
这里第一个测试用 `10、20、30` 三个数，检查计算结果是否为 `60`；
第二个测试检查空输入被拒绝后，输出值仍保持原来的 `1234`。
先写下这两个预期，再执行：

```powershell
python scripts/learning/run.py test --app tests/learning/first_evidence --variant normal
$LASTEXITCODE
```

`scripts/learning/run.py` 是学习实验的入口路径。`test` 表示构建并运行，
`--app` 指定实验目录，`--variant normal` 把这组结果命名为 normal，方便分别保存不同实验条件。
这个入口的默认目标就是本节的模拟板。预期有 **2 个实际运行的用例、2 个通过，退出码为 0**。
终端中的 `Evidence` 是结果路径标签，它指向本次生成的证据记录。
记录采用 JSON 格式（JavaScript Object Notation，JavaScript 对象表示法），用带名字的字段保存命令、配置身份和结果。

看到程序有输出以后，还要确认上述用例数和退出码。构建结束、出现一行日志、用例被跳过，
都不能单独表示断言已经执行且通过。若报告没有实际运行用例，先检查报告和工具错误，
不要把“没有失败”推断成“测试成功”。

接下来按 [T06 的完整步骤](first_experiment/P01_从断言到实验结果.md)开启已有的故障配置：
测试把预期结果改成 `61`，实际计算仍为 `60`，应得到一个通过、一个失败以及非零退出码；
恢复正常配置后再次运行，应回到两个通过。
这是检验失败能否被观察到的练习，不需要制造越界访问或修改板卡时钟。
本节复用 T06 的实验，源码中的测试框架与各层结果交接也在那里解释。

完成这一轮时，你学会的是把输入、计算结果、检查条件和报告关联起来。
这还没有证明线程调度、外设驱动或所有错误输入都正确；新的问题需要新的实验。
保留本次命令、预期、实际结果和证据记录位置，再进入下一阶段。

## 4. 第一轮之后，专题应该怎样接着学

程序已经能运行，下一步自然会问：这个应用由哪些文件组成，换一块板或改一个选项为什么会改变结果？
这时进入 T07—T13 的应用、构建与配置组。
其中，**CMake 是描述构建关系的工具名称**，**Kconfig 是表达软件选项及依赖的配置系统名称**，
**设备树（devicetree）**是描述硬件设备和连接的结构化数据。
这一组分别解释“编哪些文件”“启用哪些能力”“目标上有哪些设备”，然后检查它们在生成结果中的落点。

等这些关系清楚后，再引入多项工作并行推进、等待和共享数据：

| 新出现的问题 | 继续进入的专题组 | 这一阶段的练习方向 |
| --- | --- | --- |
| 应用怎样组成，设置怎样进入程序？ | T07—T13 应用、构建与配置 | 改一个输入，找到对应的生成结果并解释变化 |
| 谁在运行，等待何时结束？ | T14—T20 线程、中断与时间 | 观察执行顺序、等待和超时，不用日志间距冒充精确时间 |
| 多项工作怎样共享数据？ | T21—T28 共享数据与异步任务 | 设计容量、交接规则和受控竞争实验 |
| 程序可用空间为何会耗尽或被破坏？ | T29—T33 内存与执行边界 | 检查调用空间、缓冲区、分配与访问边界 |
| 同一个应用怎样接到这块板？ | T34—T39 最小移植，接着 T40—T49 外设 | 把启动、设备描述、驱动和实板观察逐项对应 |

这些是接下来的学习与写作规划，T07—T88 的详细正文尚未交付。
后续还包括存储、故障定位、低功耗、升级、通信、数据处理、测试维护和综合工程；
完整的 **14 组、88 专题** 及各自目标在[专题蓝图](专题蓝图.md)。
已有相应基础时可以按蓝图的前置依赖进入需要的专题，不需要把高级通信或显示功能变成开始学习的条件。

贯穿项目会逐步从输出状态，发展到接收操作、采集数据、保存结果和传输信息。
每次新增一项需求都保留独立小实验，然后再组合到应用中，这样出错时能缩小排查范围。
实板是否具备所需驱动、哪个步骤已经测过，继续查[移植状态](../porting-status.md)。

## 5. 遇到具体问题时怎样使用现有资料

学习正文负责带你建立解释，官方材料用来核对约定，源码用来定位这份版本如何实现。
先提出一个可回答的问题，例如“这个等待函数会不会一直占着处理器”，再选择入口，
比从第一个文件开始逐行通读更容易形成可验证的结论。

| 此时的问题 | 使用什么材料 | 查阅后应留下什么 |
| --- | --- | --- |
| 我还不知道这个机制为什么出现 | 四篇介绍和已完成的详细专题 | 自己能复述的场景、问题和解决过程 |
| 我需要核对接口的使用条件 | `doc/` 中的官方文档与 `include/zephyr/` 中的接口声明 | 适用版本、调用条件和需要检查的返回结果 |
| 我需要知道这份实现实际走哪里 | `kernel/`、`drivers/` 等实现目录 | 与问题有关的配置分支、调用关系和下一处观察位置 |
| 我需要设计一个能推翻错误理解的实验 | `samples/`、`tests/` 和本课程实验 | 明确输入、预测、失败条件和实际运行记录 |

这些是仓库内目录名；它们的查阅入口按问题整理在[资料索引](资料索引.md)。
目录中存在某个上游示例，只能说明有参考代码，还要核对它需要的目标、驱动和依赖才能运行。
具体取证过程在 [T01](evidence/README.md)演示；首次入门不要求读完整个官方文档目录。

如果现在只选一个开始动作，就打开[认识这个工程](../P01_认识这个工程.md)，
读完后在自己的工作区里指出“应用在哪里、内核在哪里、构建入口在哪里”。
随后沿本页第二节继续阅读，再完成第三节的软件实验。
