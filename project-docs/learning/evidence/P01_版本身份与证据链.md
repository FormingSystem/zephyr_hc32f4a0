# 1. 版本身份与证据链

你已经知道，这个工程会把应用、操作系统和芯片支持一起构建成固件。
现在读到一篇教程说：“心跳程序调用休眠函数后，一秒钟再执行。”
如果你照着教程去找实现，却发现文件位置不同，应该相信网页、函数名字，还是手里的源码？

**Zephyr** 是本工程使用的嵌入式操作系统项目专名。
本章不要求先懂它的调度算法；我们只追问一个问题：怎样让关于程序的结论带有可核对的依据。
最后你会完成一张证据卡，说明研究了哪份代码、看到了什么、结论成立需要什么条件，以及还没有验证什么。

## 1.1 同一个工程为什么需要几种版本身份

**Git** 是记录文件变更历史的工具专名。一次**提交（commit）**保存一组文件状态和历史关系；
提交标识用一串十六进制字符表示。**HEAD** 是 Git 对当前检出位置的引用名称，
它告诉你当前工作从哪个提交出发，不表示未提交的文件与该提交完全相同。

本工程导入的是上游**源码快照（source snapshot）**：保留某个时刻的源文件，
随后在自己的 Git 历史中增加移植。**基线（baseline）**是用于比较变化的已记录起点。
因此，“本项目当前提交”和“导入时的上游提交”回答两个不同问题。

先考虑下面这个具体变化：你修改了应用的心跳周期，但尚未提交。
此时 HEAD 没变，实际构建输入已经变了。只记录 HEAD，另一个人就无法知道你测试的是哪个周期。
正确做法是同时记录项目提交和工作树差异；工作树是你现在编辑和构建的那组文件。

| 身份 | 当前工程如何取得 | 它能区分什么 |
| --- | --- | --- |
| 本项目提交 | `git rev-parse HEAD` 命令 | 已提交移植和工程内容的历史位置 |
| 未提交变化 | `git status --short`、`git diff HEAD` 命令 | 同一提交之上的实际编辑；新文件还需单独记录 |
| 上游起点 | 根目录的 dependencies.lock.json 文件 | 导入 Zephyr 及依赖模块时记录的来源提交 |
| 上游版本字符串 | 根目录的 VERSION 文件 | 版本系列和开发阶段，不能唯一标识每次开发提交 |
| 实际产物 | 构建生成的文件及其校验值 | 这次检查或运行的是哪份二进制文件 |

上表的文件名是项目约定，不是要求展开英文的技术缩写。
仓库的[源码基线说明](../../source-baseline.md)记录了快照导入策略与准确节点。
2026-09-10 本章核对时，项目起点为 `d79a7bff3115163d79e4462ed7044cb26ed6bc04`；
当时新增学习文件尚在工作树中，这个值不能单独代表包含新教程的完整状态。

### 1.1.1 为什么 4.4.99 不等于一个稳定发布包

版本字符串通常便于交流，但开发期间可以连续很多次提交都使用同一个字符串。
本工程 VERSION 写的是 4.4.99。上游在开发主线使用补丁号 99 标识下一版本的开发工作已经开始，
不能把它理解成“4.4 系列第 99 个正式修复版本”，也不能据此声称我们的移植已发布 4.4.99 产品版本。

官方对照是本地 [Release Process 的 Tagging 小节](../../../doc/project/release_process.rst)：
查找 `v[Major].[Minor].99`，看它描述的是主线开发标签还是正式发布标签。
这里的本地文本来自固定快照；网上的 latest 页面会继续变化，适合找资料方向，不能替代本地节点。

### 1.1.2 没有上游历史，为何仍能核对源码

Git 把文件内容保存为 **blob 对象**；blob 是 Git 的对象类型名称，表示文件内容，不保存提交关系。
`git hash-object` 命令计算这种内容对象的标识。
本工程保存了导入清单中的原始对象标识，即使没有导入上游提交历史，也能比较指定文件是否仍与导入内容一致。

这与 **SHA-256（Secure Hash Algorithm 256-bit，256 位安全散列算法）**文件校验不同。
后者直接对文件字节计算摘要，用于给实验产物和日志留下内容身份；不要把两种算法的输出互相比较。
校验相等支持“按该方法计算的内容一致”，不自动证明来源可信、逻辑正确或硬件运行成功。

本机实测：休眠接口和实现两个文件的 Git 内容对象标识均与导入清单相同。
同样在本项目查询上游提交对象会失败，因为导入策略本来就没有保留它。
“无法 git show 上游提交”与“源文件缺失”是两个不同现象，不能据前者要求重新导入整套上游历史。

## 1.2 一句话结论需要哪种证据

**接口契约（interface contract）**说明调用者需要满足什么条件，以及允许依赖什么结果。
**实现（implementation）**是当前版本怎样兑现契约的具体代码。
**观察（observation）**是某次实际运行或测量得到的结果。
三者相互支持，却不能相互冒充。

例如，接口允许一个等待中的执行任务在到期前被其他动作唤醒。
你运行一百次都没有观察到提前醒来，也不能否定接口允许这种路径。
反过来，源码里有处理提前唤醒的分支，也不能证明你的应用实际走过该分支。

| 证据种类 | 应带着什么问题看 | 常见越界推论 |
| --- | --- | --- |
| 官方接口说明 | 调用前提、参数单位、返回值和禁止上下文是什么 | 文档说能做，便认定当前板已接通 |
| 当前源码 | 实际调用了谁，配置选择了哪个分支 | 发现函数定义，便认定当前镜像包含并执行了它 |
| 官方样例 | 演示了哪种完整用法、依赖什么目标与配置 | 样例只演示成功路径，便认为没有失败情况 |
| 构建生成文件 | 最终启用了什么、源文件从哪里来、镜像如何布局 | 链接成功，便认为芯片已经运行 |
| 日志或测量 | 哪个输入在何种条件下产生了什么现象 | 一条打印正常，便认为全部机制已验证 |

因此，一张证据卡至少要把“问题、身份、契约、实现、配置、观察、限制”分开。
并非每张卡都必须包含硬件测量；没有执行的项目直接写未执行，比把预期日志当成结果更有用。

## 1.3 现场：心跳里的休眠是怎样找到实现的

**线程（thread）**是可以独立等待和继续执行的一条程序执行路径。
**休眠（sleep）**表示当前线程暂时停止参与正常执行，等待到期或被唤醒；
**忙等（busy wait）**则持续占用当前执行资源检查条件或消耗时间。
本章只区分这两个行为，不展开调度优先级和时间误差的完整机制。

在心跳应用中，函数标识符 **k_msleep** 表示按毫秒指定时长的线程休眠接口；
它不是函数名类似就能推断出的精确定时保证。
下面是[现有应用](../../../samples/bringup/src/main.c)中的裁剪现场，省略了设备初始化和输出：

```c
#define HEARTBEAT_INTERVAL_MS 1000

/* 每次完成工作后，请求当前线程休眠。 */
k_msleep(HEARTBEAT_INTERVAL_MS);
```

这里的 HEARTBEAT_INTERVAL_MS 是应用宏名称，值为 1000。
它既不包含此前工作的执行时间，也不保证到期后线程立刻获得运行机会。
仅凭这一行不能得出“输出间隔严格为一秒”的测量结论。

### 1.3.1 从调用者追到接口，先核对返回值

在项目根打开 PowerShell；这是 Windows 的命令解释器名称。
下面使用 **rg**，即 ripgrep 文本检索工具的命令名；若本机没有该工具，可用编辑器的目录内搜索完成同样检索。
`-n` 显示行号，目录参数限制查询范围，避免混入缓存里的其他版本。

```powershell
rg -n 'k_msleep' samples/bringup/src/main.c include/zephyr
```

当前源码会把接口定位到 [include/zephyr/sleep.h](../../../include/zephyr/sleep.h)，
不应因为旧文章写着另一个文件名，就断言本仓库损坏。
函数前的说明给出毫秒参数，并说明返回零或提前唤醒后剩余的时间。
先核对这一契约，再往下找实现，可以避免只看函数名字猜测返回值总为零。

### 1.3.2 发现一层包装以后，继续找谁真正改变状态

**包装函数（wrapper function）**把较方便的调用形式转换为另一层接口调用。
当前的 k_msleep 是头文件中的内联包装；**内联（inline）**是把函数定义提供给编译器使用的一种声明方式，
不能由此保证最终二进制一定保留独立的同名函数符号。

源码中的函数标识符 **k_sleep** 接收已经包装好的等待时间，
**k_sleep_ticks** 是底层按系统计时单位处理休眠的接口；系统计时单位的换算细节留给时间专题。
宏标识符 **Z_TIMEOUT_MS** 将毫秒请求转换为这一调用需要的等待时间表示。
这几个名字不是三种互相替代的应用任务，而是同一次请求经过的接口层次。

```powershell
rg -n 'k_msleep|k_sleep_ticks|Z_TIMEOUT_MS' include/zephyr/sleep.h
rg -n 'z_impl_k_sleep_ticks' kernel
```

在这份快照中，底层实现标识符 **z_impl_k_sleep_ticks** 出现在
[kernel/sleep.c](../../../kernel/sleep.c) 和 [kernel/nothread.c](../../../kernel/nothread.c)。
名字中的 z_impl 是 Zephyr 系统调用实现所用的命名部分，不应被读成另一个公开应用接口。
仅发现两个定义还不够：下一步要判断本次构建选择了哪个。

### 1.3.3 配置决定了哪条实现有资格进入结论

**Kconfig** 是 Zephyr 用来描述和选择软件功能的配置系统专名。
本例需要检查配置项 **CONFIG_MULTITHREADING**，它控制是否具备多线程支持。
目录中的 CMakeLists.txt 是构建规则文件；其中按软件配置选择需要编译的源文件。

```powershell
rg -n 'MULTITHREADING|sleep.c|nothread.c' kernel/CMakeLists.txt
```

多线程条件下才应把“当前线程从可执行集合移除、登记等待、切换出去”这条实现用于解释心跳。
禁用多线程时采用另一条后备路径。你不能把某一分支的解释直接搬到所有构建配置上。

**.config** 是构建目录中保存最终软件选项的生成文件名。
如果已有通过构建的心跳产物，可以额外检查：

```powershell
Select-String -LiteralPath build/bringup/zephyr/.config -Pattern '^CONFIG_MULTITHREADING='
```

这条命令需要该产物确实存在。没有构建目录时，本章仍可完成源码阅读，
但证据卡必须把“本次镜像的生效配置”标为未核对，不能由源码中的默认值代填观察结果。

## 1.4 动手完成一张版本化证据卡

本实验只读文件与 Git 元数据，不安装依赖、不改版本、不构建或刷写固件。
开始前位于本项目克隆的根目录；路径由你实际克隆的位置决定，不需要同级官方源码仓库。

### 1.4.1 记录起点并核对选中的文件

下面 Get-FileHash 是 PowerShell 计算文件摘要的命令，SHA256 是其算法参数值，对应前面解释的 SHA-256。
先核对工程身份，再逐文件核对内容身份；命令不会改变这些文件。

```powershell
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short
Get-Content -LiteralPath VERSION
Get-Content -LiteralPath dependencies.lock.json
git hash-object include/zephyr/sleep.h kernel/sleep.c
rg -n 'include/zephyr/sleep.h|kernel/sleep.c' governance/architecture/source-manifest.tsv
Get-FileHash -Algorithm SHA256 -LiteralPath include/zephyr/sleep.h,kernel/sleep.c
```

确认仓库根是你正在学习的项目，再比较两个文件的 Git 对象标识与清单对应行。
文件名匹配后才能比较值，不能只看两串长度相同的数字。
如果不一致，保留差异并判断它是不是本项目有意修改；不应自动覆盖本地文件来“修复”比较结果。

### 1.4.2 用失败检查身份边界

先预测：既然只导入源码快照，没有导入上游历史，在本项目查询上游提交对象会怎样？

`$LASTEXITCODE` 是 PowerShell 保存最近外部命令退出码的变量名；零表示成功，非零表示该命令没有成功。
必须紧接目标命令读取，避免被后面的其他外部命令覆盖。

```powershell
git cat-file -e 'f19d03c78ba70a670e3dadc2121523d33984a5c7^{commit}'
$LASTEXITCODE
```

cat-file 是 Git 检查对象的子命令，`-e` 只判断对象是否存在。
本次实际查询返回非零退出码并报告不是有效对象名，与快照策略一致。
这是预期反例，不是故障恢复动作；查询没有修改文件，因此不需要撤销操作。
若某个后来克隆主动取得了上游历史，这项查询可能成功，应如实记录该克隆的状态。

## 1.5 换一个问题，复用同一种调查方法

迁移练习：把问题改成“一个 GPIO 配置函数返回零，能否证明灯已经点亮？”
GPIO 是 **通用输入输出（General-Purpose Input/Output）**硬件接口；这里仅用它作为另一种证据判断场景。
请先列出软件返回值、设备配置、物理连接和电平测量各能证明哪一步，再找对应文件。

参考判断是：返回零只能支持驱动报告该调用成功；驱动实现、输出极性、引脚连接和实际电平还要各自核对。
一条软件返回值不包含整个电路的测量结果。后面的板卡专题会完整走这条链。

读到新教程时，可以复用三个动作：先固定身份，再找到与问题相符的契约和实现，最后匹配足以支持结论的观察。
