# 1. 从断言到可核对的实验结果

你已经能判断一个指针是否仍然有效，也能确认编译器和源码来自正确的工程。
现在给数据采集程序写一个小函数：接收 10、20、30 三个数，输出它们的和。
程序打印“完成”以后，这件事是否就验证好了？如果实际结果是 59，主机上的测试命令会不会仍显示成功？

本章建立一条完整的实验链：把判断写进程序，让目标上的错误进入测试报告，再让主机命令以失败退出。
**Zephyr** 是本工程使用的嵌入式操作系统专名；本实验会启动它并执行测试，
不需要传感器或开发板。结束时，你将能运行同一个实验的正常、故障与恢复版本，并解释三份结果。

## 1.1 先把“正确”写成可检查的条件

**断言（assertion）**是对某个条件必须成立的检查。测试断言失败时，应记录失败，而不是继续显示成功。
**返回值（return value）**是被调用函数交还给调用者的结果；它可以用于报告错误，但只有调用者检查它，
错误才会进入后续处理。打印一行文字、返回错误和测试失败是三种不同动作。

本实验的应用函数叫 **sample_sum**，这是我们定义的函数标识符。
它借用调用者的输入数组，在函数返回以前完成计算；不会把指针交给其他线程，也不保留输入地址。
函数检查输入和结果地址非空、输入个数在 1 到 4 之间。
调用者还必须保证输入对象在整个调用期间存活且可读、数组实际拥有所声明的元素数，
并保证结果对象存活且可写；非空地址并不能证明这些条件。

正常输入的验收条件是“返回成功且结果等于 60”。
无效的空输入验收条件是“返回指定错误且结果保持原值”。
后者故意给函数不合法参数，但它期待测试通过，因为正确的程序行为就是拒绝这份输入。

### 1.1.1 为什么输入和输出采用不同宽度

C 标识符 **uint16_t** 表示恰好 16 位的无符号整数类型，**uint32_t** 表示恰好 32 位的无符号整数类型；
此目标通过标准头文件 stdint.h 提供它们。
四个最大 16 位无符号数之和为 262140，可以由 32 位结果表示。
因此，在已经限定的个数和取值范围内，累加不会溢出结果类型。

**size_t** 是 C 的对象大小与元素计数常用的无符号整数类型；本例的 count 参数采用它。
**NULL** 是空指针常量宏，用于表达没有有效对象地址。
**EINVAL** 是 errno.h 中的错误码宏名称，表示无效参数；本函数按照本工程常见约定返回它的负值。
零表示成功。这是本函数的约定，并不说明所有 C 函数都采用同样的返回方式。

下面是本实验的完整被测函数；完整可构建应用还包括后文解释的测试注册与配置文件。

```c
static int sample_sum(const uint16_t *values, size_t count, uint32_t *result)
{
    uint32_t total = 0;

    /* 验证可检查的参数；失败时还没有写调用者的输出。 */
    if (values == NULL || result == NULL || count == 0 || count > 4) {
        return -EINVAL;
    }
    for (size_t i = 0; i < count; ++i) {
        total += values[i];
    }
    *result = total;
    return 0;
}
```

循环中的临时累加值归当前调用所有；完成以后才一次写入调用者的结果。
失败路径在写结果以前返回，所以调用者可以用预置值判断“失败是否破坏了旧输出”。
本函数没有申请需要释放的内存，局部对象随调用结束失效；借来的地址也不会逃出这次调用。

完整源码在 [src/main.c](../../../tests/learning/first_evidence/src/main.c)。
T02 的[对象与生命期](../c_lifetime/README.md)进一步解释这种同步借用与值转交的差别。

## 1.2 目标上的框架与主机上的工具各管什么

先认识运行在固件里的 **ztest**：这是 Zephyr 的测试框架专名，负责注册用例、执行断言和汇总用例结果。
**测试用例（test case）**是一项独立判断；**测试套件（test suite）**是一组相关用例。
本实验的套件名称是 first_evidence，包含正确求和和拒绝空输入两个用例。

再认识运行在电脑上的 **Twister**：这是 Zephyr 的测试编排工具专名。
它选择目标和测试场景，调用构建工具，启动具备运行条件的目标，并读取目标输出形成报告。
**测试场景（test scenario）**是测试描述中命名的一组应用和配置选择；
一个场景可能包含多个套件和用例，不能把“1 个场景通过”误报成“只有 1 项断言”。

本例由 **QEMU** 模拟器项目提供可运行的虚拟目标。
目标标识 **mps2/an386** 指向 Zephyr 所描述的模拟板配置，包含对应处理器和设备模型。
它不是 HC32 芯片模型；HC32 是本项目目标芯片的系列专名。
模拟执行可验证本次 C 代码和测试失败传播，不能测量本板引脚、电气时序和功耗。

```mermaid
flowchart LR
    A["电脑：学习实验入口"] -->|"指定应用、目标与配置"| B["电脑：Twister"]
    B -->|"构建并启动"| C["QEMU：Zephyr 与 ztest"]
    C -->|"调用并检查返回值"| D["sample_sum：本次输入与输出"]
    D -->|"成功值或错误码"| C
    C -->|"用例结果与结束标记"| B
    B -->|"测试报告与退出码"| A
```

图中固件和电脑是两处执行环境。应用函数返回错误先交给 ztest，
测试判断成立或失败以后才产生面向 Twister 的用例结果；不是函数的负数直接充当电脑进程的退出码。
官方 [Test Framework](https://docs.zephyrproject.org/latest/develop/test/ztest.html) 的
“Quick start - Integration testing”和“Creating a test suite”可用于对照框架职责；
本工程的接口和文件约定仍以[本地同版说明](../../../doc/develop/test/ztest.rst)为准。

### 1.2.1 两个用例怎样进入框架

**ZTEST** 是 ztest 提供的宏标识符，不是需要展开英文全称的缩写，用于向指定套件注册一个用例函数；
**ZTEST_SUITE** 注册套件及可选的初始化、逐用例准备和清理动作。
断言宏 **zassert_equal** 比较两个值，不相等时报告当前用例失败。
这三个宏都由 ztest 提供，不是 C 语言关键字。

第一个用例先检查 sample_sum 返回零，再检查输出和等于预期。
第二个用例把输出初始化为 1234，调用个数为零的函数，
然后分别检查返回值为负 EINVAL、输出仍为 1234。
两个断言分开写，是为了区分“错误类型不对”和“虽然拒绝了输入，却已经破坏输出”。

套件注册使用空回调，因为每个用例都拥有独立的局部输入，没有跨用例共享资源需要分配和释放。
完整应用没有自己编写普通主函数；启用 ztest 后，其默认启动路径会执行已登记套件。
查[本地 ztest.c](../../../subsys/testsuite/ztest/src/ztest.c)时，可搜索 test_main 函数标识符，
核对它怎样进入套件执行和结束报告；本章不展开框架内部线程实现。

### 1.2.2 日志为什么不能代替断言

函数标识符 **printk** 是 Zephyr 的基础文本输出接口，本例用它输出输入个数、返回值、实际和与预期和。
它帮助定位失败，却不负责判断正确性；即使日志完整打印了错误结果，只有后续断言才把它判为失败。

宏标识符 **ARRAY_SIZE** 求已知数组的元素数；本例直接用于局部数组，不用于只有地址信息的指针。
**IS_ENABLED** 是 Zephyr 检查布尔配置是否启用的辅助宏。
配置项 **CONFIG_LEARNING_INJECT_FAILURE** 由本实验定义；关闭时预期为 60，开启时故意改为 61。
代码不执行非法内存访问，而是制造可控的期望不一致。

**功能的负面用例**与**测试框架的失败注入**需要分清：
前者确认空输入被正确拒绝，结果应通过；后者故意提出错误断言，结果必须失败。
若两者都显示通过，就要怀疑测试并未运行，或报告解析漏掉了失败。

## 1.3 一个能执行的实验必须有哪些输入文件

**CMake** 是生成构建规则的工具专名；**Ninja** 是执行这些规则的构建工具专名。
**Kconfig** 是 Zephyr 描述和选择软件功能的配置系统专名。
本章先闭合每个文件的最小职责，后续构建专题再解释它们的完整语法和优先级。

| 输入文件 | 当前职责 | 缺失或错误时会怎样 |
| --- | --- | --- |
| CMakeLists.txt | 找到本仓库 Zephyr，给应用命名并加入 src/main.c | 配置失败，或被测源码没有进入构建 |
| prj.conf | 设置配置项 CONFIG_ZTEST 为 y，启用测试框架 | ztest 符号或启动机制不可用 |
| Kconfig | 声明本实验的故障开关，再引入 Zephyr 的配置定义 | 故障配置项不存在，配置阶段报错 |
| fail.conf | 单独启用故障开关，保留正常配置作为基线 | 不传这份配置时不会注入失败 |
| tests.yaml | 定义场景 learning.first_evidence、允许目标与运行超时 | 工具找不到场景，或目标被过滤 |
| src/main.c | 被测函数、输入、断言与套件注册 | 程序的实际行为与判断来源 |

文件都已保存在[实验目录](../../../tests/learning/first_evidence)。
tests.yaml 是本快照使用的名称，不能直接套用旧教程中的 testcase.yaml。
该场景没有设置只构建选项，允许运行的目标是 mps2/an386。
配置中的 timeout 值为 15 秒，由 Twister 对目标运行施加期限；它不是被测函数运行了 15 秒。

## 1.4 从准备环境到第一次通过

下面命令使用 **PowerShell** 命令解释器，在本项目根执行。
先按 T05 准备主机环境；环境脚本只设置本次终端，不会自动连接开发板。
**Python** 是运行项目工具所用的解释器专名。

```powershell
. ./scripts/Enter-Environment.ps1
python scripts/project.py doctor
python scripts/learning/run.py test --app tests/learning/first_evidence --variant normal
$LASTEXITCODE
```

新入口 **run.py** 是本项目的学习实验脚本文件名。test 选择构建并运行，
`--app` 指定仓库内的实验目录，`--variant` 给此次配置起一个结果索引名称。
默认目标为 mps2/an386；`$LASTEXITCODE` 是 PowerShell 保存最近一个外部程序退出码的变量。
应紧接实验命令读取它，避免被其他命令覆盖；零表示这次命令通过，非零要求检查原因。

正常运行的教学预测是：求和日志中的实际和与预期和都是 60，两个用例通过，进程退出零。
本章后面的实际结果表记录了已经执行的结果；预测不替代报告。
Twister 原始报告还要确认实际用例数为 2，没有过滤、跳过或仅构建。

### 1.4.1 怎样找到本次结果，而不是读到上一次产物

**JSON（JavaScript Object Notation，JavaScript 对象表示法）**是一种结构化文本格式。
这里用它保存命令、报告和校验信息，不要求你会写 JavaScript 程序。
每次运行创建一个新的短目录 `build/learning/runs/<运行标识>/`，终端会显示 Evidence 路径。
原始证据文件叫 evidence.json；同名配置索引里的 latest.json 指向最近一次结果。

```powershell
$experimentIndex = Get-Content -LiteralPath build/learning/tests/first_evidence/mps2_an386/normal/latest.json -Raw | ConvertFrom-Json
$experimentEvidence = Get-Content -LiteralPath $experimentIndex.evidence -Raw | ConvertFrom-Json
$experimentEvidence.success
$experimentEvidence.test_summary
$experimentEvidence.commands
```

本段两个变量是临时保存本次索引与证据的 PowerShell 变量，不修改系统目录或工具配置。
在证据中先看 success，再看 test_summary 的 cases、passed 和 all_executed_and_passed 字段；
后者只有场景可以运行、实际存在用例且所有用例都通过时才为真。
命令日志的文件名逐条保存在 commands 中；当前 step-1.log 和 step-2.log 记录编译器身份，
step-3.log 记录 Twister 执行输出，原始报告与模拟输出在 twister 子目录。

短目录还解决了本次遇到的真实主机故障：初版结果路径嵌套过深，
Windows 上归档工具无法读取某些对象文件。现在调用 Twister 的短路径选项，
让构建工作目录缩短，并通过映射保留可读报告位置。
这修复的是构建路径问题，不能把那次构建错误误当成被测函数断言失败。

## 1.5 故意失败一次，再证明已经恢复

先不改被测函数，只通过额外配置把预期的 60 改成 61。
`--extra-conf` 的参数相对应用目录解析，因此 fail.conf 指向本实验的文件。
故障版本与正常版本有独立配置索引，每次也各自创建新的实际构建目录。

```powershell
python scripts/learning/run.py test --app tests/learning/first_evidence --variant fault --extra-conf fail.conf
$LASTEXITCODE
```

预期一个用例仍然通过：空输入被正确拒绝，且输出未改变。
求和用例则在比较实际 60 与预期 61 时失败；Twister 判场景失败，学习入口返回非零。
不要在教程命令末尾吞掉退出码，也不要把这次报告复制成正常报告。

恢复只需不再传入故障配置，源码和正常配置都没有被破坏：

```powershell
python scripts/learning/run.py test --app tests/learning/first_evidence --variant recovered
$LASTEXITCODE
```

恢复后的两个用例应重新通过。由于使用全新的构建目录，
之前启用的故障开关不会残留在当前配置缓存中。
需要判断实际开关时，在该次产物的 .config 中查 CONFIG_LEARNING_INJECT_FAILURE，而不是只看输入文件。

### 1.5.1 失败在哪一层，就从哪一层定位

| 观察到的现象 | 先检查什么 | 正常恢复方式 |
| --- | --- | --- |
| 应用目录无效 | 参数是否在 samples/learning 或 tests/learning 内，CMakeLists.txt 是否存在 | 选回真实应用目录 |
| 配置报未知选项 | Kconfig 定义、配置项拼写、传入的附加配置 | 修正配置后重新运行 |
| 编译或归档失败 | step 日志中第一个编译原因，工具版本与路径长度 | 解决主机输入后重新构建 |
| 用例失败 | 模拟输出中的实际值、预期值及失败断言 | 判断算法问题还是故意失败配置 |
| 运行超时 | 模拟器是否启动、用例是否阻塞、是否出现结束标记 | 修复运行路径，不把调大超时当作完成 |
| 零用例或只构建 | 场景筛选、可运行性、报告中的用例状态 | 确认选择了实际可运行场景 |

本入口还有默认每条主机命令 600 秒的外层期限，通过 `--timeout` 设置。
它限制一次工具调用的等待，并在超时时清理该次启动的进程树；场景里的 15 秒则限制目标测试运行。
两者不是实时性能指标。模拟器的耗时还受电脑负载影响，本实验没有进行硬件性能测量。

## 1.7 把实验迁移到下一个问题

迁移练习一：增加“四个最大输入”的用例，先算出期望 262140，再检查实际结果。
这验证当前上界，却不能把函数的最大输入个数自动扩展到五个；后者需要重新检查契约和容量。

迁移练习二：增加“结果地址为空”的用例，只检查错误码，不访问空地址。
如果测试为了观察错误而真的访问空指针，就已经换成了另一个未定义行为问题，失去本实验的确定性。

迁移练习三：把本组 T02 的测试目录传给同一入口，比较场景数与用例数。
输入、断言和结果身份都应该随应用变化；不能沿用本页的 2/2 作为另一个实验的通过记录。
