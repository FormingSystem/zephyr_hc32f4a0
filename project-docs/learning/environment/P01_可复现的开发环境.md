# P01 可复现的开发环境

前面的编译知识解释了源文件怎样变成程序，但它还留下一个工程问题：
在新终端里输入同样的构建命令，为什么可能找到另一套编译器，甚至编译了旁边的源码？
如果只保留一句“我这里可以编译”，别人无法判断差异来自工具、配置还是源文件。

本章从本项目的环境检查入口出发，先建立“谁运行工具、谁运行固件”的关系，
再用正常检查和可恢复的失败实验证明源码边界。
**Zephyr** 是本工程所用操作系统项目的名称；本仓库包含它的源码快照以及目标芯片所需模块。
本章讨论的是主机环境和源码选择，不重新安装软件、不重做硬件移植，也不访问开发板。
完成后，应能回答每个工具来自哪里、每个源码路径为何属于本项目、环境错误应在哪一层修复。

## 1. 为什么电脑能编译自己不能直接运行的程序

**主机（host）** 是运行编辑器、编译器和检查脚本的电脑。
**目标（target）** 是最终运行所生成程序的系统；本项目可以生成目标芯片的固件，也可以生成模拟板程序。
二者是本次操作中的角色，不表示固定的设备品牌。
同一台电脑可以作为编译主机，并在模拟器内运行另一个目标系统。

**交叉编译器（cross compiler）** 是运行在主机上、为另一目标生成机器代码的工具。
**工具链（toolchain）** 则把编译、汇编、链接及检查产物等相关工具组织在一起。
这些工具在电脑上执行，生成物却要遵循目标处理器的指令和内存布局，
所以不能因为某个文件在 Windows 上产生，就把它当作 Windows 应用双击运行。

本项目工具名 `arm-zephyr-eabi-gcc` 是一个目标工具链命令标识。
**GCC（GNU Compiler Collection，GNU 编译器套件）** 在这里执行 C 编译；
**EABI（Embedded Application Binary Interface，嵌入式应用二进制接口）**
约定编译结果之间的二进制协作方式，例如调用时如何传参。
工具名前缀用于辨认该编译器的目标角色，不能替代版本检查。

**软件开发套件（Software Development Kit，SDK）** 是一套可安装的开发工具与相关文件。
**Zephyr SDK** 是本项目采用的套件名称，包含目标工具链及部分主机辅助工具。
它位于仓库外部，因为源码工程需要携带可审查的实现，而不是把每台电脑的安装目录一起复制进版本库。
源码能够完整拉取与工具已经安装好，是两项不同条件。

当读者看到“缺少编译器”时，应先问主机工具是否存在；
看到“缺少目标头文件”时，则要继续区分工具链包含文件与项目模块源码。
盲目重新下载整个源码树只可能碰巧掩盖其中一种问题，不能解释错误发生的位置。

## 2. 每个工具为什么存在

程序进入编译前，需要把硬件和软件配置转成编译输入；大量文件还需要按依赖关系构建。
因此本工程入口会调用多类工具，它们并非都负责生成机器指令。
先建立分工，后面才能从失败消息定位到具体阶段。

**Python** 是脚本语言及其解释器的名称，本工程入口、配置处理和测试工具由它执行。
**CMake** 是生成构建规则的工具专名，它读取项目描述并形成适合当前构建器的规则；
**Ninja** 是执行这些规则的构建工具专名，按文件依赖决定需要运行哪些编译或链接命令。
“CMake 已经配置成功”并不说明 Ninja 的后续编译已经成功。

**设备树（devicetree）** 描述目标硬件及其连接。
**DTC（Devicetree Compiler，设备树编译器）** 是设备树相关主机工具的名称，
本项目环境检查要求能够找到它，但这一点不表示它独自完成 Zephyr 的全部设备树处理。
**gperf** 是完美哈希函数生成器的工具专名；哈希把键映射为查找位置，
“完美”在此指对给定键集合避免冲突。本项目将它作为构建所需的主机命令进行检查。

**Git** 是保存和比较源文件历史的版本控制工具名称；
**pip** 是给选定 Python 解释器安装和检查包的工具名称；
**pyOCD** 是面向微控制器调试的工具专名，本项目还用它执行调试配置的离线检查。
离线检查指不连接探针、不访问目标硬件的检查方式，不能用其通过宣称固件已运行。

| 当前对象 | 本轮承担的职责 | 能找到它仍不能证明什么 |
| --- | --- | --- |
| Python 与包 | 执行工程脚本及配置处理 | 所有包版本正确或目标编译器存在 |
| CMake、Ninja | 生成和执行构建规则 | 工程选中了正确源码或驱动能运行 |
| SDK 内交叉编译器 | 生成目标机器代码 | 板上晶振、引脚和物理时序正确 |
| DTC、gperf | 完成构建中的辅助处理 | 已经发生相应构建阶段 |
| Git | 标识并审查当前源码历史与差异 | 工作树没有未记录改动 |
| pyOCD | 检查调试配置或按明确命令调试 | 执行了实板操作；离线检查尤其不能证明这一点 |

现在可以把错误分层：解释器报错、配置生成失败、编译失败、链接失败和硬件运行失败发生在不同交接。
本章只验证进入构建前的工具与源码条件；后续构建专题再把失败追到具体编译单元和链接对象。

## 3. 环境是进程看到的选择规则

**进程（process）** 是主机上一次正在运行的程序实例。
**环境变量（environment variable）** 是进程收到的一组名称和值，常用于选择工具目录与运行参数。
**PATH** 是其中用于搜索可执行命令目录的变量名，按顺序影响 `python`、`cmake` 等命令解析到哪个程序。
文件夹存在与命令能够被当前进程找到，不是同一回事。

**虚拟环境（virtual environment）** 是为一个 Python 使用场景隔离解释器入口及已安装包的目录。
Python 的 `venv` 模块负责创建这种环境；`VIRTUAL_ENV` 是激活脚本通常设置的目录变量名。
虚拟环境能隔离 Python 包，不能自动固定系统上的 CMake、编译器或本项目源文件。
也不能只检查 `VIRTUAL_ENV` 非空就认定当前 `python` 真正在该环境中执行。

最直接的观察是让正在运行的解释器报告 `sys.executable`：
`sys` 是 Python 的运行时信息模块，`executable` 字段保存实际解释器路径。
安装或检查包时使用 `python -m pip`，会把 pip 绑定到这次选中的解释器；
如果直接调用另一个目录的 pip，就可能把包装到与构建无关的环境里。
Python 官方[虚拟环境工作方式](https://docs.python.org/3.12/library/venv.html#how-venvs-work)
说明了激活脚本与直接调用解释器的关系；此处应重点核对“激活只是选择入口，环境目录本身不是可随意移动的源码”。

**PowerShell** 是本项目 Windows 入口使用的命令终端及脚本语言名称。
命令前的点和空格，例如 `. ./scripts/Enter-Environment.ps1`，表示在当前终端作用域中加载脚本。
脚本设置的是该进程的环境，关闭终端即可离开；它不把这些值写成机器永久环境变量。
新终端需要重新进入环境，正是为了让这次工具选择可见、可复查。

Windows 与 Linux 的路径分隔、可执行文件命名和激活脚本不同。
本章实际验证的是 Windows/PowerShell；不能把 Windows 的 `.ps1` 当作 Linux shell 脚本执行。
跨主机操作仍应保持相同的源码边界与版本约束，但 Linux 的工具发现和构建需要独立验证。
不要用“都是 Python”跳过主机依赖、路径大小写和 SDK 平台包的差别。

## 4. 本仓库怎样把工具选择和源码选择分开

本项目的 [Enter-Environment.ps1](../../../scripts/Enter-Environment.ps1) 负责在当前终端选择工具。
它根据脚本位置确定项目根，再选择 Python 环境和 SDK，追加必要工具目录，最后切换到项目根。
它可以读取本机 `.local/environment.json` 配置文件；`.local` 是本仓库约定的忽略目录。
该文件记录机器相关位置，不是新克隆必须携带的源文件。

脚本选择 Python 环境时，优先看进程变量 `VIRTUAL_ENV`，再看本机配置，
没有时尝试仓库内 `.venv`，最后兼容项目父目录中的共享 `.venv`。
SDK 的选择依次来自进程变量、本机配置和基于版本记录的默认位置。
这种共享工具环境是当前实现允许的工具复用，不能据此允许源码也回退到父目录。
若终端早已激活错误环境，前面的优先级也解释了为何本机配置没有覆盖它。

**JSON（JavaScript Object Notation，JavaScript 对象表示法）** 是保存结构化数据的文本格式。
本项目[依赖记录](../../../dependencies.lock.json)使用这种格式保存源码节点和工具版本。
**CMSIS（Common Microcontroller Software Interface Standard，微控制器通用软件接口标准）**
在本工程对应 Arm 提供的处理器相关支持模块；华大 HAL 是硬件抽象层模块，包含芯片驱动库。
这两个模块的源文件已经在本仓库内，SDK 和虚拟环境则是主机工具。

实际构建入口 [project.py](../../../scripts/project.py) 又做了一次独立限定。
它的 `ROOT` 变量从脚本自身文件位置求得，不把当前终端目录直接当成源码根。
`environment()` 是该脚本内返回子进程环境字典的 Python 函数，**不是命令行子命令**。
本项目没有 `python scripts/project.py environment` 这一命令，查看它要读源码或在 Python 中调用函数。

该函数先确认项目根存在基本 Zephyr 源文件和 SDK 标记，然后建立以下选择：

| 环境变量标识符 | 值如何产生 | 为什么需要它 |
| --- | --- | --- |
| `ZEPHYR_BASE` | 覆盖为当前项目脚本确定的根目录 | 防止继承另一个终端中的官方源码路径 |
| `ZEPHYR_MODULES` | 只列依赖记录中的两个仓库内模块路径 | 不让外部工作区自动补入未声明模块 |
| `ZEPHYR_SDK_INSTALL_DIR` | 检查后规范化的 SDK 目录 | 把工具位置与源码位置分别确定 |
| `ZEPHYR_TOOLCHAIN_VARIANT` | 设为 `zephyr`，这是工具链选择值 | 让构建按本工程的 SDK 方案选择工具链 |
| `EXTRA_ZEPHYR_MODULES`、`ZEPHYR_EXTRA_MODULES` | 从子进程环境中删除 | 清除上一个工程可能留下的额外模块入口 |

`module_paths()` 是负责定位仓库内模块的函数：它读依赖记录中的相对路径，
规范化路径并检查仍在项目根内，再确认模块描述文件存在。
因此，一个“工具都齐全，但模块路径逃出了仓库”的环境仍应失败，不能偷偷使用邻居工程补齐。
直接 CMake 构建时还会显式传入对应参数，具体参数展开在后续构建专题继续追踪。

## 5. 正常实验：先拿到可以解释的环境检查

实验前提是已经安装本项目要求的工具，并处于这个项目的克隆根目录。
第一次安装的具体入口见[开发说明](../../development.md)；本章不为了复现检查而重新安装已有环境。
本机确切路径由[协作说明](../../../AGENTS.md)中的私人环境配置入口提供，公共正文不写操作者盘符和用户名。

先进入环境，再让工具自己报告身份：

```powershell
. ./scripts/Enter-Environment.ps1
python -c 'import sys; print(sys.executable); print(sys.version)'
python scripts/project.py doctor
cmake --version
ninja --version
dtc --version
gperf --version
arm-zephyr-eabi-gcc --version
```

`doctor` 是工程命令名称，含义是检查当前开发条件，不是自动修复或下载器。
它检查 Python 最低版本、pyOCD 固定版本、主机命令可发现性、Zephyr 版本标记、
必要源文件、SDK 版本、模块描述格式，再执行 Python 包依赖检查和调试离线检查。
其中 `pip check` 的职责是验证已安装包声明的依赖关系，不表示所有包都与历史运行完全相同。

2026-09-10 实际执行上述检查，项目源码提交为
`d79a7bff3115163d79e4462ed7044cb26ed6bc04`；本批工作树新增学习文档，未修改被检查的环境入口。
命令均退出为 0。公共结果只记录可复用的版本信息，工具的私人绝对位置仍保留在本机输出中。

| 对象 | 本次真实观察 |
| --- | --- |
| Python | 3.12.10 |
| Zephyr SDK / 交叉编译器 | 1.0.1 / GCC 14.3.0 |
| CMake / Ninja | 4.4.3 / 1.13.2 |
| DTC / gperf | 1.6.1 / 3.1 |
| Zephyr 源码标记 | 4.4.99，记录的上游节点为 `f19d03c78ba70a670e3dadc2121523d33984a5c7` |
| Python 包依赖检查 | `No broken requirements found.` |
| 调试离线检查 | `PASS`；`probe_opened` 和 `hardware_tested` 两个输出字段均为 `false` |

还可以验证当前目录不是源码身份的决定因素：
`LASTEXITCODE` 是 PowerShell 保存最近一次原生命令退出码的变量名，下面用它检测检查失败。

```powershell
$projectRoot = (Get-Location).Path
$projectPython = (Get-Command python).Source
Push-Location (Split-Path -Parent $projectRoot)
try {
    & $projectPython (Join-Path $projectRoot 'scripts/project.py') doctor
    if ($LASTEXITCODE -ne 0) { throw '独立目录检查失败' }
} finally {
    Pop-Location
}
```

`$projectRoot` 和 `$projectPython` 是本实验临时变量，分别保存已确认的项目目录和解释器路径。
`Push-Location` 临时进入父目录，`finally` 保证即使检查失败也恢复原终端目录。
本次从父目录调用同一脚本仍然检查当前项目并通过，退出码为 0；没有查用相邻官方源码。
此结论来自脚本身份和显式路径，并不是因为当前目录恰好也叫 Zephyr。

## 6. 反例实验：缺工具和错源码怎样产生不同证据

下面的实验只在子进程里制造三种条件。**子进程（child process）** 是由当前程序启动的另一个进程，
它接收给定的环境副本，结束后不会反向修改父进程的环境或 Python 变量。
因此可以暂时令命令搜索路径为空，或替换检查函数看到的项目根，而不卸载软件、不移动源码。

输入由脚本内固定值产生，不需要手工改系统设置。
`subprocess` 是 Python 启动子进程的标准模块；`run` 调用等待子进程退出并保存输出和退出码。
`assert` 是 Python 断言语句的关键字名称：预期不成立就终止实验，避免“错误没发生也算通过”。
`VERSION` 是 Zephyr 版本标记文件的名称，后面缺源码实验会检查是否仍能找到它。
`-B` 禁止产生字节码缓存，末尾 `-` 让解释器读取终端送入的多行程序。

```powershell
@'
import os
from pathlib import Path
import subprocess
import sys
from scripts import project

root = project.ROOT.resolve()
probe = '''from pathlib import Path
from scripts import project
env = project.environment()
root = project.ROOT.resolve()
assert Path(env["ZEPHYR_BASE"]).resolve() == root
assert all(Path(p).resolve().is_relative_to(root) for p in env["ZEPHYR_MODULES"].split(";"))
assert "EXTRA_ZEPHYR_MODULES" not in env
assert "ZEPHYR_EXTRA_MODULES" not in env
print("PASS: source root and modules stay inside repository")
'''
# 只污染子进程接收的环境，检查入口应覆盖错误源码并清除额外模块。
bad = os.environ.copy()
bad.update(ZEPHYR_BASE=str(root / '.local/other-zephyr'),
           EXTRA_ZEPHYR_MODULES=str(root / '.local/other-module'),
           ZEPHYR_EXTRA_MODULES=str(root / '.local/other-module'))
r = subprocess.run([sys.executable, '-B', '-c', probe], env=bad,
                   capture_output=True, text=True)
print(r.stdout.strip()); print('source_isolation_exit:', r.returncode)
assert r.returncode == 0

# 保持源码和工具文件原样，只让子进程无法按名称找到主机命令。
bad = os.environ.copy()
bad['PATH'] = ''
r = subprocess.run([sys.executable, '-B', 'scripts/project.py', 'doctor'],
                   env=bad, capture_output=True, text=True)
print(r.stderr.strip()); print('missing_tool_exit:', r.returncode)
assert r.returncode != 0 and 'Missing host command: git' in r.stderr

# 替换子进程中的函数输入，不创建目录，也不改真实源码文件。
probe = '''from scripts import project
project.ROOT = project.ROOT / ".local/t05-missing-source"
assert not project.ROOT.exists()
try:
    project.environment()
except RuntimeError as error:
    print(error)
    raise SystemExit(7)
raise SystemExit(0)
'''
r = subprocess.run([sys.executable, '-B', '-c', probe],
                   capture_output=True, text=True)
print(r.stdout.strip()); print('missing_source_exit:', r.returncode)
assert r.returncode == 7 and 'missing Zephyr source: VERSION' in r.stdout
print('parent_source_unchanged:',
      Path(project.environment()['ZEPHYR_BASE']).resolve() == root)
'@ | python -B -
```

第一个子进程故意继承错误的源码目录字符串。`environment()` 应覆盖它并重新选择仓库内模块。
这里不创建那个假目录，因为本实验验证的是选择规则，而非另一份源码是否能编译。
第二个子进程使用绝对路径启动 Python，因此清空 PATH 不会阻止解释器启动；
接下来 `doctor` 按顺序查找主机工具，在第一个缺少的 Git 命令处报错，尚未进入构建。

第三个子进程只在内存中把 `project.ROOT` 指向不存在的目录，
随后 `environment()` 查不到基本的 `VERSION` 源文件标记，产生另一类错误。
脚本把预期的异常转成退出码 7，供父进程确认命中了实验目标；7 是本教学脚本选定的代码，
不是工程 `doctor` 的通用缺源码错误码。
若该假目录已经存在，断言会停止实验，应选择另一个不存在的本机临时名称，不删除已有目录。

同日实际输出如下，外层 Python 退出码为 0，表示三项预期全部成立：

```text
PASS: source root and modules stay inside repository
source_isolation_exit: 0
ERROR: Missing host command: git; activate the project environment
missing_tool_exit: 1
This repository is missing Zephyr source: VERSION
missing_source_exit: 7
parent_source_unchanged: True
```

恢复不是把全局配置再改回来，而是等待这些子进程结束；父进程仍选择原项目。
本次随后再次执行正常 `doctor`，返回 0，确认正常环境仍可使用。
如果复现时输出不符，应检查 Python 身份、源码版本和第一个失败断言，
不能把非零退出笼统标为“预期失败”，更不能通过改全局 PATH 来绕过实验。

## 7. 可复现要记录什么，不能保证什么

本项目固定了 Zephyr、CMSIS 和华大模块的源码节点，SDK 与 pyOCD 也有明确版本约束。
不过，依赖记录不等于所有主机 Python 包及系统工具均按逐文件散列锁定。
`doctor` 也只是检查所需源文件和版本标记，并非对整个源码树重新计算内容校验。
因此“doctor 通过”表示当前实现规定的入场条件成立，不表示任意主机都会生成逐字节相同的固件。

保存实验记录时，至少写项目提交、未提交差异、实际解释器与工具版本、完整命令、退出码和目标。
公开正文保留版本、相对源码入口和结论；本机安装目录、个人用户名、串口号及原始路径日志放在忽略目录。
需要分享日志时先提取与问题相关的内容，不能把私人环境配置当成所有读者都能使用的安装方案。

迁移练习：设想终端继承了一个已有但版本不符的 SDK，或先激活了另一个 Python 环境。
按照选择优先级先预测哪个入口会选中它，再检查对应工具身份和错误输出，最后在新终端中恢复正确选择。
该练习没有在本次通过安装或替换工具实际执行；目的是让读者从优先级推导恢复位置。

| 状态 | 本篇结果 |
| --- | --- |
| 文档 | 已结合当前环境脚本、官方 Python 说明及实际输出审阅 |
| 构建 | 未新增固件构建；本篇验证构建前条件 |
| 软件运行 | 正常 doctor、独立工作目录、三项子进程实验和恢复检查通过 |
| 硬件运行 | 不适用；没有探针访问、目标下载或寄存器操作 |

现在可以用三句话描述一次运行的身份：脚本属于哪个项目，工具由当前进程怎样选中，
子进程最终得到哪些源码与模块路径。下一步 T06 把这种身份记录带进有断言、退出码和日志的软件实验，
由“环境成立”继续推进到“预期行为确实发生”。
