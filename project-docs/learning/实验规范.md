# 学习实验的编写与验收约定

一个实验要回答一个可检验的问题。例如“等待队列满时会发生什么”，不能只用“串口打印正常”验收。
本页约定实验怎样保存、怎样执行、怎样解释结果。已实现的起点为 T02、T03 与 T06，具体状态见[第一组验收记录](第一组验收记录.md)。
专题与依赖顺序见[完整蓝图](专题蓝图.md)，已有学习入口见[阅读路线](README.md)。

## 从一个问题形成最小实验

每个专题至少设计正常路径、一个相关反例和一个迁移练习，但不为简单主题机械凑多个工程。
三者可以共用一个应用，通过独立配置或测试用例改变条件。

例如，生产者每隔一段时间生成一条记录，消费者负责保存；队列是两者之间暂存记录的有界容器。
先让消费者足够快，再让消费者变慢，最后改变队列容量。比较接收数、丢弃数和等待时间，
才能判断程序选择了阻塞、丢弃还是覆盖策略。日志条数本身不能证明每条数据都被完整消费。
这些是实验设计示例，具体接口、频率、容量、代码和运行结果在对应专题实现时确定。

实验正文必须交代下面这些内容，标题可按题型调整。

| 项目 | 必须提供的内容 |
| --- | --- |
| 要验证的判断 | 哪个条件变化会引发哪个可观察结果；哪种结果会推翻预期 |
| 前置知识 | 已有专题编号与本章必要术语的简短解释 |
| 环境与能力 | 源码提交、目标板、主机工具、所需驱动/模块、配置和额外器件 |
| 输入与初始化 | 输入数据、时钟、缓冲区、对象、接线和初始状态来自哪里 |
| 完整执行 | 初始化、正常操作、失败处理、退出/取消和资源回收 |
| 观察点 | 返回值、计数器、状态、日志、寄存器或波形；观察动作会不会干扰结果 |
| 预期与允许误差 | 确定性结果、时序上下界、误差来源和样本数量的依据 |
| 反例与定位 | 故意改变哪个条件，应该在哪里出现失败，如何回到基线 |
| 实际结果 | 真实执行的命令、退出码、产物与观察；没有执行就标“未执行” |
| 证明边界 | 已排除什么，仍不能证明什么，换平台后哪些结论需要重新验证 |

## 文档、实验代码和运行结果的位置

以下为已开始采用的实验组织约定，尚未实现的专题不创建空目录或占位源码。
根协作说明的文件名为 AGENTS.md，表中通过它寻找私人环境记录；文件名不是技术缩写。
已有 `samples/bringup/` 保持为最小启动回归，新的实验从小工程开始独立维护。

| 内容 | 后续存放约定 |
| --- | --- |
| 专题正文 | `project-docs/learning/<topic>/PXX_中文主题.md`；目录用英文小写加下划线 |
| 专题阅读入口 | 该专题 `README.md`，只列真实已写章节，并回链总路线 |
| 机制源码导读 | 专题内 `navigation/` 讲模块关系；`source_explanations/` 讲具体实现，按需要创建 |
| 应用型实验源码 | `samples/learning/<topic>/<experiment>/` |
| 自动化机制测试 | `tests/learning/<topic>/`，避免为相同代码维护两份实现 |
| 可共享的辅助工具 | `scripts/learning/`，在确有共同需求时建立 |
| 构建与原始日志 | 通用入口每次使用 `build/learning/runs/<运行标识>/` 短路径；按应用/目标/变体保存 latest.json 索引，均由 Git 忽略 |
| 本机工具/端口配置 | 通过根 AGENTS.md 的私人环境配置入口查找，不写回公共说明 |
| 实验结论 | 对应专题的实验章节；只保存必要、可公开的证据摘要，并关联原始结果的校验信息 |

Git 是本项目使用的版本管理工具。源码、配置、测试输入和教程纳入管理；
编译产物、缓存、私人路径、真实凭据和未经确认许可的参考附件按[项目约定](../../AGENTS.md)留在忽略目录。

每个实验需要独立构建入口，通常包括 CMake 项目描述、软件选项文件、应用源码和测试描述。
CMake 是生成构建规则的工具；Kconfig 是 Zephyr 的软件选项系统；设备树是描述目标硬件及连接的输入数据。
具体文件与选项必须在实验正文中解释作用、默认值、错误后果及实际消费位置。
不要只粘贴配置片段后让读者猜测放在哪个目录。

## 构建入口必须与工程实际一致

HC32 是本工程目标芯片系列的简称，不是接口名称或可展开的缩写。
当前[工程命令](../../scripts/project.py)的 `build` 固定构建 `samples/bringup`，
支持 HC32 与 `mps2/an386` 两个目标；`test` 固定选择该示例的模拟回归。
它目前没有“任意实验目录”参数，后续教程不得编造 `--app` 等不存在的选项。

T06 已实现独立[学习实验入口](../../scripts/learning/run.py)，不会改变 project.py 的既有启动回归职责：

```powershell
python scripts/learning/run.py build --app tests/learning/first_evidence --board mps2/an386
python scripts/learning/run.py test --app tests/learning/first_evidence --variant normal
python scripts/learning/run.py test --app tests/learning/first_evidence --variant fault --extra-conf fail.conf
```

最后一条是故意失败的教学配置，预期退出非零。入口接受仓库内 samples/learning 或 tests/learning 下的应用，
使用当前快照的 tests.yaml 描述；test 目前只自动运行 mps2/an386，不访问实板。
build 可选模拟目标或 HC32 目标，后者仍需应用本身支持，并执行已有镜像审计；构建成功不等于已下载。
输入、命令、退出码、日志和产物摘要由 evidence.json 记录；输出为新目录，避免把旧镜像当成新结果。
索引使用 `build/learning/<samples或tests>/<应用相对路径>/<target>/<variant>/latest.json`；
应用相对路径从 samples/learning 或 tests/learning 之后开始，保留其全部子目录；目标名中的斜杠替换为下划线。
T03 是单独的目标文件观察实验，使用其正文里的 inspect_objects.py，不需要伪造 Zephyr 应用配置。
所有入口必须锁定本仓库源码和已声明模块，不得回退到同级官方源码或未声明的缓存。

上游示例常用的 `west` 是 Zephyr 的工作区与扩展命令工具，本项目当前采用直接 CMake 构建。
学习 west 的用法时，要同时解释其工作区与模块发现方式；不要求为运行一个课程而下载整个上游模块清单。

## 文档进度和验证进度分别记录

每篇实验至少保留下面四个状态栏。它们是独立证据，不能仅凭前一栏通过推断后一栏通过。

| 状态栏 | 可用值与含义 |
| --- | --- |
| 文档 | 规划 / 编写中 / 已审阅；正文和链接已完成不等于代码已运行 |
| 构建 | 未执行 / 失败 / 通过；注明目标、配置、源码状态和镜像审计范围 |
| 软件运行 | 未执行 / 失败 / 通过；注明主机或具体模拟目标及用例范围 |
| 硬件运行 | 不适用 / 缺前置 / 未执行 / 失败 / 通过；注明实际板卡、操作与测量 |

新增实验不得继承旧心跳示例的“已通过”。构建目标为 HC32 而尚未接板时，只能记录构建证据。
模拟器上复现的并发反例，可以验证该执行模型下的软件机制；它不能证明本板的电气波形、功耗或极限时延。

自动化时使用 Zephyr 的 `ztest` 测试框架编写断言，用 `Twister` 测试编排工具选择目标、配置和用例。
这些名称是框架/工具专名。零失败还必须同时核对实际运行用例数、跳过或过滤原因，以及是否只执行了构建。
接口规则与本地官方入口见[资料索引](资料索引.md)。

## 记录到足以复现的粒度

结果记录至少包含日期、本项目提交、未提交差异的说明或补丁校验值、上游基线、工具版本、目标与配置。
对可执行链接文件 ELF（Executable and Linkable Format，保存程序段与符号的文件格式）及相关配置计算校验值，
把运行对象与源码状态对应起来。只有提交号而遗漏工作树修改，不能完整标识实际构建内容。

建议正文提供一张经过填写的结果表；还未运行时保留文字“待实验实现后填写”，不制造示范性的成功输出。
预期日志可以作为教学预测展示，但必须与实际日志分开标记。

| 结果要素 | 记录要求 |
| --- | --- |
| 构建输入 | 目标、选项、设备树附加配置、模块节点和实际执行命令 |
| 生效配置 | 最终软件选项、生成硬件描述、链接布局和关键符号 |
| 运行输入 | 测试数据、随机种子、外部输入、复位方式和迭代次数 |
| 原始证据 | 测试报告、退出码、串口记录、调试器记录或波形；各自注明来源 |
| 量化指标 | 完成数、失败数、丢失数、最大占用或时延分布，注明统计范围 |
| 反例恢复 | 何种失败是预期结果，恢复以后是否重新得到基线行为 |
| 结论 | 只覆盖实际执行的平台、条件和路径 |

时序实验使用单调时间或明确校准的测量方式；单调时间是只向前推进、适合计算间隔的时基。
串口输出、调试断点和测量探针都可能改变程序时序，必须说明测量开销。
不把主机模拟的执行速度换算成本板性能，也不把一次运行没有失败解释为并发问题不存在。

## HC32 实验的具体约束

每次涉及寄存器、引脚、时钟和存储修改时，先回到[硬件依据](../hardware.md)核对实装型号与连接。
其中晶振输入、未引出引脚、主内存布局和板载调试器操作是本板事实；专题不要维护另一套相互漂移的参数表。

外设实验先完成电路连接、驱动能力、配置和退出方法的核对，再取得实际运行证据。
内核中断实验可以先在模拟目标进行；新增 HC32 外设中断还需要芯片内部路由与 Zephyr 中断入口同时正确。
板载调试器通过通用串行总线（Universal Serial Bus，USB）连接电脑；这里 USB 指主机与设备连接的总线体系。
该连接不代表目标芯片的 USB 驱动已经实现。

存储写入实验必须使用为实验明确分配的区域，并说明该区域原有内容如何处理；
升级、故障恢复与掉电实验需要对应的恢复方案，不能隐藏在通用构建或检查命令里自动执行。
缓存厂商示例用于查依据，不能直接把其他封装、评估板或晶振配置整套复制到本板。

## 每次专题交付的检查顺序

1. 冷读正文，确认不点击链接也能解释问题、状态变化和结论；必要术语在使用前说明。
2. 核对固定版本的官方接口、实现和本板前置，检查所有真实链接及配置消费路径。
3. 构建本次新增或修改的实验，并运行具备条件的软件用例；保留反例结果。
4. 具备条件时执行对应实板实验；不具备条件就写出具体缺项和能够先完成的证据。
5. 更新专题入口和项目移植状态，记录本次覆盖范围；硬件事实变化回写唯一硬件记录。

这套约定保证每一批都交付完整的局部学习闭环。后续出现需要新环境或新驱动的专题时，
可以先交付完整原理与软件实验，再单独登记本板待验收项，不以空标题代替尚未完成的讲解。
