# 第1章\_文档仓库与实验工程的职责

这份说明面向资料维护者，规定文档保存在哪里、实验在哪里进行，以及两边怎样对照。读者从 `learning/` 正文进入实验，不需要了解文档发布仓库的位置。

## 1.1\_两个目录各自负责什么

| 目录 | 职责 | 日常工作 |
| --- | --- | --- |
| `F:\git_storage\zephyr_hc32f4a0` | 文档维护和推送仓库，保存已有 HC32F4A0 移植与相关环境资料 | 修改、校对和发布 Markdown、PPT；查询已有实现；分析移植涉及的文件和修改 |
| `G:\zephyr_practice\zephyr-main` | 从原生 Zephyr 开始的实验工程 | 按资料准备工具和依赖，逐步编译、调试、适配 HC32，并记录实际结果 |

F 盘保留 Zephyr 源码，是因为它承载了早期移植参考与已经完成的 HC32 适配。它可以帮助定位从零复现中遇到的问题，也可以用于识别板级适配改了哪些文件。源码不是要求读者跳过实验、直接使用成品的理由。移植实现已存在与各项实板验证已完成，是两个不同结论；验证状态仍以[移植记录](porting-status.md)为准。

G 盘也不会永久停留在原生源码状态。它随着实验逐步增加模块、HC32 板级与 SoC 支持、驱动、示例、环境和调试工具、学习材料，最终形成与 F 盘参考工程相应的组织方式和开发能力。两边适配首先指目录与工具接口能够对应、实验步骤能够解释，不能直接等同于文件逐字相同或 Git 历史相同。

## 1.2\_按实验推进工程形态

| 阶段 | G 盘实验要建立的内容 | 进入下一阶段前的依据 |
| --- | --- | --- |
| 原生起点 | Zephyr 源码及准确的版本身份 | 能定位 `VERSION`、`SDK_VERSION`、`west.yml` |
| 工具与依赖 | Windows Python 环境、SDK、主机工具、匹配的源码模块 | 能说明各项输入从哪里来，并完成原生目标构建 |
| 工具实验 | `learning/` 材料、练习副本和独立生成目录 | 在对应章节观察配置、编译或运行结果 |
| HC32 适配 | board、SoC、设备树、时钟、驱动、HAL 与应用接入 | 每项修改在实验源码中核对，分别记录编译与实板证据 |
| 工程化 | 可复用的构建、环境和调试入口及说明 | 脚本先创建、讲解并验证，再成为后续实验入口 |

表格定义推进目标，不表示所有阶段已经在 G 盘完成。已有板级配置章节属于移植完成后的练习；其前提必须明确，不能把原生源码中不存在的文件写成现成输入。后续补充移植章节时，应补齐从原生状态到这些前提的创建过程。

同一工具或脚本可以最终用于两边工程，但应从当前工程根解析路径。教程不得通过硬编码 F 盘路径、引用旁边的模块或隐式选择另一套 Python，让 G 盘实验表面成功。

## 1.3\_learning 的写作与验证要求

- 正文、目录、PPT 和讲解备注以 G 盘实验为操作现场，不引导读者切回文档发布仓库。
- 配套材料是读者取得的实验输入；原生 Zephyr ZIP 不自带 `learning/`，准备章说明材料放置方式。
- 每章先交代已有文件和环境，再创建本章新增内容。读者不应通过猜测补出成品工程的隐藏前提。
- 使用 F 盘实现排错时，维护者先核对两边源码版本，提炼需要的修改及原因，再写回实验步骤；不整树覆盖实验成果。
- 历史日志保留当时的位置、版本和结果。F 盘旧构建成功不能转记为 G 盘从零复现成功；文档静态检查、编译、模拟和实板运行分别记录。

## 1.4\_Git 更新与材料同步暂缓确定

后续需求是便于查询和修改官方最新 Zephyr 源码及 `learning` 材料。驱动和其他板级适配提交不属于已经确定的自动同步范围。

目前尚未确定官方更新的接入方式、学习材料的同步方向、冲突处理、分支命名和历史组织规则。因此本次只记录需求，不实现同步脚本，不迁移或重写两边 Git 历史，也不自动传递驱动改动。此前讨论过的浅克隆、补全历史和重放提交均不作为已采纳方案。

后续规则明确后，再分别说明官方源码更新和学习材料同步的输入、目标、覆盖范围、差异预览及恢复方式。目录职责与逐步实验的安排不依赖提前选定某一种 Git 策略。
